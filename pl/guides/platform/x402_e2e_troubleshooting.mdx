X402 obejmuje HTTP, SDK, podpisy, Facilitator i transakcje on-chain. Podczas diagnozowania problemów z podpisem lub rozliczeniem zaleca się potwierdzanie warstwa po warstwie w kolejności „publiczny punkt wejścia -> odpowiedź 402 -> SDK payment handler -> settlement on-chain”. Ten samouczek opisuje sposoby sprawdzania każdej warstwy oraz wymienia typowe błędy.

## Sprawdź publiczny punkt wejścia

Deklaracja możliwości Facilitatora:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Jeśli zwracane są `facilitator`, `supportedKinds` i punkty końcowe protokołu, metadane możliwości są prawidłowe. Wykrywanie zasobów API zostało wycofane; wywołuj bezpośrednio docelowe API i opieraj się na bieżącej odpowiedzi 402.

Obsługiwane możliwości Facilitatora:

```bash
curl https://facilitator.acedata.cloud/supported
```

Jeśli zwracane jest `kinds`, punkt wejścia Facilitatora działa prawidłowo.

## Sprawdź 402 `accepts`

Wyślij nieuwierzytelnione żądanie, które nie spowoduje opłaty:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Sprawdź, czy zwrócone `accepts` zawiera sieć, której chcesz użyć. `network` jest identyfikatorem CAIP-2:

- `eip155:8453` + `exact` (Base)
- `eip155:8453` + `upto` (Base, rozliczanie po użyciu)
- `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` + `exact` (Solana)

Jeśli docelowa sieć nie jest dostępna, oznacza to, że dane API lub bieżące środowisko nie ma skonfigurowanej odpowiedniej metody płatności X402.

## Uruchom zaawansowane narzędzia walidacyjne X402Client

Repozytorium X402Client oferuje zaawansowane narzędzia walidacyjne, których można użyć do potwierdzenia wyboru odpowiedzi 402, generowania podpisu, paid retry i settlement on-chain. Wymagają one funded wallet, RPC, klucza prywatnego oraz zależności deweloperskich. Do standardowej integracji biznesowej zaleca się w pierwszej kolejności użycie SDK TypeScript lub Python; uruchamiaj te narzędzia tylko wtedy, gdy potrzebujesz zlokalizować problemy z podpisem lub rozliczeniem on-chain.

Adres repozytorium: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)

```bash
git clone https://github.com/AceDataCloud/X402Client.git
cd X402Client/typescript
npm install
npm install --no-save ethers @solana/spl-token bs58 tsx
```

Base:

```bash
export X402B_BASE_PAYER_PRIVATE_KEY=0x...
TEST_API_PATH='/openai/chat/completions' \
TEST_BODY='{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}],"max_tokens":10}' \
npx tsx scripts/test-real-e2e.ts
```

Solana:

```bash
export X402B_SOLANA_PAYER_PRIVATE_KEY=...
npx tsx scripts/test-solana-e2e.ts
```

Narzędzia walidacyjne zazwyczaj wyświetlają:

1. Odpowiedź 402 dla pierwszego żądania.
2. Wybrane payment requirement.
3. Skrót podpisanego `PAYMENT-SIGNATURE`.
4. Status HTTP i treść odpowiedzi po ponownej próbie.
5. Transakcję settlement on-chain albo przyczynę błędu Facilitatora w przypadku niepowodzenia.

Nie wysyłaj kluczy prywatnych ani pełnego `PAYMENT-SIGNATURE` do systemów logowania ani zgłoszeń.

Przykład wyników walidacji publicznego API:

```text
Base exact
HTTP 402 -> HTTP 200
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC

Solana exact
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run because public RPC lookup hit 429

Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Wyjaśnienie:

- Base `exact`, Solana `exact` i Base `upto` wszystkie ukończyły paid retry z HTTP 402 do HTTP 200.
- Transakcję on-chain Base `exact` można sprawdzić w BaseScan, a kwota rozliczenia wynosi `95215` atomic USDC.
- Limit podpisu dla Base `upto` wynosi `95215` atomic USDC, ale rzeczywisty settlement on-chain wynosi `3` atomic USDC, co wskazuje, że rozliczanie po użyciu obciąża opłatą według rzeczywistego wykorzystania.
- Dla ścieżki Solana potwierdzono paid retry i wynik modelu. Publiczne RPC może podlegać limitowaniu; gdy wymagane jest ścisłe uzgadnianie on-chain, użyj własnego Solana RPC lub potwierdź podpis transakcji na podstawie zapisów rozliczeniowych po stronie platformy.

## SDK smoke test

Zaawansowane narzędzia walidacyjne służą do sprawdzania podpisów i rozliczeń on-chain. Strona biznesowa powinna także wykonać SDK smoke test, aby potwierdzić, że kod aplikacji może automatycznie obsługiwać 402 przez payment handler. Poniżej pokazano tylko kluczowe fragmenty; pełny kod wymaga uzupełnienia portfela, providera i importów.

TypeScript:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const res = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly ADC_SDK_X402_OK' }],
  max_tokens: 8
});
```

Python:

```python
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
    )
)

res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly ADC_PY_X402_OK"}],
    max_tokens=8,
)
```

Jeśli model zwróci stały ciąg zgodnie z wymaganiem, oznacza to, że SDK, payment handler, Gateway, Facilitator i docelowe API są połączone.

Powyższe dwa smoke testy używają Base `exact` i rozliczają stałą kwotę podaną w wycenie 402. Uzupełnienia czatu należą do scenariuszy rozliczanych według tokenów; przy integracji produkcyjnej zaleca się przekazanie `preferScheme: 'upto'` (w Pythonie `prefer_scheme="upto"`), aby rozliczać według rzeczywistego wykorzystania.

Obiekt zwracany przez Python SDK jest `dict`; można użyć `res["choices"][0]["message"]["content"]`, aby odczytać treść.

## E2E płatności za zamówienia

Płatności za zamówienia używają platformowego API `platform.acedata.cloud` i wymagają tokenu konta platformy. Pełny przepływ wygląda następująco: utworzenie zamówienia Pending, wywołanie `POST /api/v1/orders/{order_id}/pay/` w celu wyzwolenia 402, a następnie ponowienie próby z `PAYMENT-SIGNATURE`.

Przykład wyników walidacji płatności za zamówienie o małej wartości:

> Poniższe rekordy transakcji są historycznymi próbkami rzeczywistych testów zgodnie ze starą polityką; kwoty i hashe transakcji zachowano w oryginalnej formie. Nowe zamówienia X402 nie oferują już zniżek zależnych od metody płatności; jako podstawy podpisu i płatności użyj `amount` z bieżącej odpowiedzi 402.
```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
accepts [('eip155:8453', 'exact', '1200000'), ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000')]

status 200
order state Finished
pay_way X402
pay_id 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}

Base tx status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Wyjaśnienie wyniku:

- Po utworzeniu zamówienia jego status to `Pending`, a cena wynosi `1.26`.
- Pierwsze żądanie `pay/` zwraca HTTP 402, w `accepts` znajdują się Base `exact` i Solana `exact`, a kwoty w obu przypadkach wynoszą `1200000` atomic USDC.
- Po ponowieniu próby z Base `PAYMENT-SIGNATURE` zwracany jest HTTP 200, status zamówienia zmienia się na `Finished`, a `pay_way` to `X402`.
- Po zdekodowaniu `PAYMENT-RESPONSE` widoczne są `success=True`, `network=base` oraz ten sam hash transakcji.
- Na BaseScan status transakcji wynosi `1`, a kwota transferu to `1200000` atomic USDC, czyli `1.2` USDC.
- Cena utworzenia `1.26` została opłacona w okresie starej polityki rabatów płatności X402, a końcowa podpisana i rozliczona kwota wynosi `1.2` USDC.

Jeśli płatność za zamówienie nie zawiera `Authorization: Bearer {platform_token}` albo zamówienie nie należy do bieżącego konta, zakończy się niepowodzeniem na warstwie uprawnień platformy; różni się to od bezkontowego API X402 wywoływanego bezpośrednio w `x402.acedata.cloud`.

## Częste błędy

| Zjawisko                                           | Kierunek diagnostyki                                                                |
| -------------------------------------------- | ------------------------------------------------------------------- |
| Pierwsze żądanie nie zwraca 402                                  | Sprawdź, czy `Authorization` nie zostało dodane omyłkowo, albo czy dane API nadal nie ma X402 pricing.                  |
| `No payment requirement for network`         | Docelowa sieć nie znajduje się w `accepts`; zmień sieć lub sprawdź konfigurację Gateway.                               |
| `invalid_402`                                | Odpowiedź 402 nie jest prawidłowym JSON-em; sprawdź proxy, gateway lub stronę błędu.                                        |
| `Authorization nonce already processed`      | Ten sam `PAYMENT-SIGNATURE` został użyty ponownie; podpisz ponownie.                                  |
| `invalid_upto_evm_payload_invalid_signature` | Sprawdź, czy chainId `upto`, Permit2 domain, adres facilitator oraz konto podpisujące są zgodne.         |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Wykonaj `approve-permit2` dla USDC w docelowym łańcuchu.                                     |
| `Payer has insufficient USDC balance`        | Portfel płatnika ma niewystarczającą ilość USDC.                                                       |
| HTTP 200, ale bez tx hash                         | Rzeczywista kwota `upto` może wynosić 0 albo rekord settlement jest nadal zapisywany asynchronicznie.                             |
| Solana `Missing transaction payload`         | W envelope `PAYMENT-SIGNATURE` nie ma serializowanej transakcji lub signature; sprawdź wallet adapter. |

## Lista kontrolna Base `upto`

`upto` jest obecnie dostępne tylko w Base (`eip155:8453`). Ponieważ podpis `upto` wiąże więcej parametrów EVM typed data, podczas integracji należy szczególnie potwierdzić, że pola czasu rzeczywistego w odpowiedzi 402 są dokładnie zgodne z podpisem klienta.

```text
Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Jeśli Base `upto` zwraca `invalid_upto_evm_payload_invalid_signature`, w pierwszej kolejności sprawdź:

1. `extra.chainId` (powinno wynosić `8453`) w elemencie `eip155:8453` + `upto` zwróconym przez API.
2. `extra.facilitatorAddress` zwrócone przez API.
3. Adres Base `upto` facilitator zwrócony przez `https://facilitator.acedata.cloud/supported`.
4. Permit2 domain, spender, kontrakt USDC i konto podpisujące.
5. Czy portfel zatwierdził już Permit2 dla Base USDC.

Digest podpisu `upto` wiąże jednocześnie Permit2 domain, chain ID, spender, adres odbiorcy, adres facilitator i validAfter. Jeśli którakolwiek pozycja jest niezgodna, Facilitator odzyska nieprawidłowego signer, a następnie zwróci invalid signature. Jeśli wszystkie są zgodne, ale nadal zwracane jest 402, następnym krokiem jest sprawdzenie Permit2 allowance; przy braku autoryzacji zwracane jest `PERMIT2_ALLOWANCE_REQUIRED`.

## Zapisywanie informacji weryfikacyjnych

Pełna weryfikacja powinna zapisać co najmniej:

- API path oraz skrót treści żądania;
- wybrane network i scheme;
- `maxAmountRequired`;
- adres portfela payer;
- końcowy status HTTP;
- wynik modelu lub ID zadania w odpowiedzi;
- link do transakcji settlement;
- Gateway trace ID lub ID rekordu użycia platformy.

Nie zapisuj kluczy prywatnych, pełnego `PAYMENT-SIGNATURE`, pełnego EIP-712 signature ani frazy odzyskiwania.

## Ustrukturyzowane błędy płatności

Niepowodzenia X402 po podpisaniu zwracają stabilne `code`, bezpieczne parametry interpolacji, etap oraz flagę możliwości ponowienia w `extensions.acedatacloud.paymentError`. Do diagnostyki w pierwszej kolejności używaj tej struktury; nie analizuj najwyższego poziomu angielskiego `error` i nie wymagaj od użytkownika podania podpisu portfela ani oryginalnego tekstu symulacji on-chain.

- `charged: false`: weryfikacja została wyraźnie odrzucona przed settlement; w tym przypadku nie zainicjowano obciążenia.
- Brak `charged`: wynik jest nieznany lub wszedł już w etap settlement; najpierw sprawdź zamówienie i status on-chain, nie wolno bezpośrednio powtarzać płatności.
- `settlement_pending`: nie powtarzaj jeszcze płatności; najpierw odśwież zamówienie lub skontaktuj się ze wsparciem.
- Nierozpoznany code: traktuj jako `payment_failed` i zachowaj publiczny kod techniczny do wyszukania przez obsługę klienta.
