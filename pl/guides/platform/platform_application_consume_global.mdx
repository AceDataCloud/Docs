---
title: "Konfigurowanie globalnego współdzielenia salda AceDataCloud Application"
description: "Platform API guide - Ace Data Cloud"
---

Ustaw `allow_consume_global`. Po włączeniu kwalifikujące się rozliczane według użycia Application mogą nadal korzystać z globalnego salda konta, gdy ich własne saldo jest niewystarczające.

## Przygotowanie

- Utwórz i bezpiecznie zapisz [Account Token](https://platform.acedata.cloud/documents/platform-token).
- Pobierz należący do Ciebie `application_id` z [listy zgłoszeń usług](https://platform.acedata.cloud/documents/platform-application-list).

```shell
export PLATFORM_TOKEN='twój token konta'
export APPLICATION_ID='twój Application ID'
```

## Przegląd interfejsu

| Element    | Treść                                                                                              |
| ---------- | -------------------------------------------------------------------------------------------------- |
| Metoda     | `POST`                                                                                             |
| URL        | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| Autoryzacja | Account Token                                                                                      |
| Body       | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

Po powodzeniu zwracany jest zaktualizowany obiekt Application. Należy kierować się wartością `allow_consume_global` w odpowiedzi, zamiast zakładać, że wartość żądania została na pewno zapisana.

> Application typu `Period` nie może zużywać globalnego salda. Nawet jeśli zażądano `true`, serwer zachowa wartość tego pola jako `false`.

## Obsługa błędów

- `401`: Account Token jest nieprawidłowy lub nieobecny.
- `403`: Bieżące konto nie jest właścicielem tego Application.
- `404`: Application ID nie istnieje.

Wejście do doładowania globalnego salda i dostępne pakiety podlegają platformowej konsoli oraz rzeczywistym pakietom zwracanym przez [tworzenie zamówienia](https://platform.acedata.cloud/documents/platform-order-create); nie należy zakładać istnienia pakietów typu `Wallet`.

## Aplikacje z autoryzowanym debetem

Gdy pole tylko do odczytu `allow_overdraft=true` aplikacji rozliczanej według użycia, aplikacja może nadal pobierać opłaty z własnego salda, nawet jeśli saldo stanie się ujemne, i nie przełączy się na konto globalne z powodu niewystarczającego salda. Aplikacje bez włączonego debetu nadal stosują się do `allow_consume_global`; to, czy debet jest dozwolony po przełączeniu, zależy od ustawień globalnego Application, z którego faktycznie pobierana jest opłata.

## Limit współbieżności dla kont próbnych

System używa znacznika użytkownika tylko do odczytu `has_recharged`, aby rejestrować, czy kiedykolwiek pomyślnie ukończono płatne doładowanie lub administrator ręcznie dodał środki; znacznik jest aktualizowany po pomyślnym wykonaniu operacji, a dla użytkowników historycznych zostanie jednolicie uzupełniony na podstawie zamówień lub wyraźnych zapisów o dodaniu środków. Konta, które ani nie wykonały płatnego doładowania, ani nie otrzymały ręcznie dodanych środków przez administratora, mogą jednocześnie wykonywać tylko jedno rozliczane żądanie w całym koncie; różne API Key i różne usługi współdzielą ten jeden limit. Nagrody, karty wymiany i przekazane limity nie są uznawane za płatne doładowanie. Konta, które ukończyły płatne doładowanie lub otrzymały ręcznie dodane środki przez administratora, nie podlegają temu limitowi współbieżności dla wersji próbnej i nadal stosują się do pierwotnych kontroli salda i limitów poświadczeń.

Gdy istniejące żądanie jest już wykonywane, nowe żądanie zwraca `429 too_many_requests`. Bezpłatne interfejsy odpytywania, takie jak zapytania o zadania, nadal mogą być normalnie wywoływane. Uwierzytelnianie połączeń Realtime zachowuje pierwotny proces rozliczania każdej rundy i nie zajmuje tego zwykłego limitu żądań.

Gdy interfejs asynchroniczny zwraca „przyjęto”, zadanie nadal jest wykonywane i przed przesłaniem kolejnego żądania generowania należy poczekać na wynik końcowy. Przerwanie sieci lub przekroczenie limitu czasu proxy nie oznacza, że zadanie zostało zatrzymane; jeśli zadanie przez długi czas nie ma stanu końcowego, przekaż `trace_id` i skontaktuj się z pomocą techniczną w celu weryfikacji.

To ograniczenie nie zmienia interfejsów dostępnych w ramach okresu próbnego ani nie zmienia pierwotnych zasad rozliczania. Opłaty są nadal rozliczane po zakończeniu żądania na podstawie rzeczywistego użycia.
