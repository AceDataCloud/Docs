Ace Data Cloud X402 obecnie rozlicza się wokół USDC i obsługuje dwa rodzaje łańcuchów: EVM i Solana. Metody podpisu, adresy aktywów, zachowanie gasu i odpowiednie scenariusze różnią się w zależności od sieci, dlatego przed integracją należy najpierw wybrać sieć.

## Identyfikatory sieci używają CAIP-2

`accepts[].network` w x402 v2 jest identyfikatorem CAIP-2, a nie skróconą nazwą taką jak `base` czy `skale`. Klient musi porównywać sieci według ciągów CAIP-2:

| Sieć             | Identyfikator CAIP-2                       |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| SKALE Base     | `eip155:1187947933`                       |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Macierz wsparcia

| Sieć     | scheme  | Aktyw                  | Metoda podpisu                         | Odpowiedni scenariusz              |
| ------ | ------- | ------------------- | ------------------------------------ | --------------------------- |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Zalecane domyślnie, dojrzałe wsparcie portfeli i płynności. |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | API z rozliczaniem po fakcie, takie jak czat i modele. |
| SKALE  | `exact` | SKALE bridged USDC  | EIP-3009 `TransferWithAuthorization` | Niski koszt gasu, odpowiednie do weryfikacji płatności EVM i wywołań niskokosztowych. |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Portfele Solana, Agent lub scenariusze aplikacji on-chain. |

`upto` jest obecnie dostępne tylko na Base. Faktycznie dostępne pozycje są określane przez `accepts` zwracane przez API. Możesz również sprawdzić Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

Odpowiedź Facilitator `/supported`:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    { "x402Version": 2, "scheme": "exact", "network": "eip155:1187947933" },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Objaśnienie wyników:

- `exact` dla Base, SKALE i Solana jest ścieżką płatności o stałej kwocie.
- Tylko Base oferuje ścieżkę rozliczania po fakcie `upto`, zależną od approve Permit2.
- `extra.facilitatorAddress` w pozycji `upto` to adres, który klient musi zapisać w witness podczas podpisywania, i musi on być zgodny z wartością zwróconą przez serwer.

## Base

Base używa oficjalnego kontraktu USDC:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

W schemacie `exact` klient podpisuje EIP-712 `TransferWithAuthorization`. Treść podpisu obejmuje:

- `from`: adres portfela płatnika
- `to`: adres odbiorcy Ace Data Cloud
- `value`: kwota tej płatności
- `validAfter` / `validBefore`: okno czasowe ważności podpisu
- `nonce`: 32-bajtowy losowy nonce

Po zweryfikowaniu podpisu Facilitator wywoła on-chain `transferWithAuthorization` USDC, aby zakończyć transfer.

Base jest najbardziej zalecaną siecią do produkcyjnej integracji, szczególnie odpowiednią dla rozliczania po fakcie `upto`, ponieważ ekosystem Permit2, USDC i portfeli jest bardziej dojrzały.

Przykład wyniku weryfikacji Base `exact`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Objaśnienie wyników:

- Płatna ponowna próba API zwraca treść modelu `ADC_BASE_E2E_OK`.
- Transakcję on-chain można sprawdzić w BaseScan, a numer bloku to `46726299`.
- `95215` atomic USDC odpowiada `0.095215` USDC i jest faktyczną kwotą rozliczenia tego wywołania API.

Wynik uruchomienia programu płatności zamówienia Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Objaśnienie wyników:

- Końcowy stan zamówienia na platformie to `Finished`.
- `pay_id` zamówienia zapisuje ten sam hash transakcji Base.
- `1200000` atomic USDC odpowiada `1.2` USDC i jest historyczną faktycznie zapłaconą kwotą tego zamówienia 10 Credits w ramach starej polityki; nowe zamówienia nie otrzymują już dodatkowej zniżki za metodę płatności X402, a konkretna kwota podpisu zależy od bieżącej odpowiedzi 402.

## SKALE

SKALE używa bridged USDC, a metoda podpisu jest podobna do Base, również EIP-3009. Jest odpowiednia dla scenariuszy płatności EVM o niskim koszcie gasu; faktyczne wywołania nadal zależą od `accepts` zwracanego przez API.

Typowe `accepts` odpowiedzi 402 SKALE zawiera:

```json
{
  "network": "eip155:1187947933",
  "scheme": "exact",
  "extra": {
    "name": "Bridged USDC (SKALE Bridge)",
    "version": "2",
    "chainId": 1187947933,
    "verifyingContract": "0x85889c8c714505E0c94b30fcfcF64fE3Ac8FCb20"
  }
}
```

SKALE obecnie oferuje tylko `exact`. Jeśli potrzebujesz rozliczania po fakcie, użyj Base `upto`.

Przykład wyniku weryfikacji SKALE `exact`:

```text
content ADC_SKALE_E2E_OK
tx 0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
block 1969317
explorer https://skale-base-explorer.skalenodes.com/tx/0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
paid 0.095215 USDC
```

Objaśnienie wyników:
- API paid retry zwraca treść modelu `ADC_SKALE_E2E_OK`。
- Transakcję można sprawdzić w SKALE explorer, numer bloku to `1969317`。
- Kwota rozliczenia tej płatności `exact` wynosi `0.095215` USDC。

## Solana

Solana używa SPL USDC `TransferChecked`。Klient konstruuje transakcję transferu, podpisuje ją i wysyła, a następnie umieszcza podpis transakcji lub zserializowaną transakcję w envelope `PAYMENT-SIGNATURE`。

Cechy Solana：

- używa Solana wallet adapter lub base58 secret key；
- aktywem jest Solana USDC mint；
- obecnie obsługiwane jest tylko `exact`；
- Facilitator zweryfikuje mint, destination, authority i amount instrukcji transferu。

Jeśli używany jest tryb wallet fee payer, portfel bezpośrednio wysyła transakcję, a Facilitator odpowiada za potwierdzenie transakcji i zwrócenie wyniku settlement。

Przykład wyniku weryfikacji Solana `exact`：

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Wyjaśnienie wyniku：

- paid retry zwróciło już HTTP 200, a model zwrócił `ADC_SOLANA_E2E_OK`。
- Przy zapytaniu do publicznego RPC o on-chain signature można napotkać ograniczenie liczby żądań。
- Ponieważ publiczne zapytania RPC mogą podlegać limitom, nie podajemy tutaj Solana explorer。Gdy wymagane jest ścisłe uzgodnienie, użyj własnego Solana RPC lub rekordów settlement po stronie platformy, aby potwierdzić podpis transakcji。

## Jak wybrać

| Co chcesz zrobić        | Zalecana sieć                         |
| ------------ | ---------------------------- |
| Szybko uruchomić minimalny przepływ     | SKALE `exact` lub Base `exact` |
| Dla zwykłych użytkowników Web3 | Base                         |
| Do późniejszego naliczania, np. uzupełniania czatu   | Base `upto`                  |
| Aplikacje ekosystemu Solana  | Solana `exact`               |
| Weryfikacja płatności EVM o niskim koszcie | SKALE `exact`                |

Niezależnie od wybranego łańcucha, nie koduj ceny na stałe w kliencie。Cena jest określana przez `accepts[].maxAmountRequired` zwrócone przez serwer。

## Nowe sieci EVM

Płatności w stałej kwocie natywnym USDC dla poniższych sieci mają zapewnioną obsługę w kodzie i są udostępniane osobno dla każdej sieci。
Dostępność zależy od `accepts` zwróconego przez zamówienie lub API；nie oznacza to, że wszystkie sieci są już włączone na produkcji。

| Sieć      | Alias      | CAIP-2         | Natywny USDC                                  |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

Te sieci obsługują tylko `exact`, a precyzja tokena wynosi 6。Nie używaj bridged USDC o tej samej nazwie。
Podczas używania oficjalnego TypeScript/Python X402 Client można przekazać skróconą nazwę z tabeli lub identyfikator CAIP-2。
Klient konstruuje podpis przy użyciu docelowego chain ID；portfel musi obsługiwać sieć docelową。

Oficjalna tabela obsługiwanych sieci portfela rozszerzenia Phantom wymienia Arbitrum i Polygon；Optimism i Avalanche
obecnie nie są wymienione w tej tabeli, można użyć Rabby lub MetaMask obsługujących sieć docelową。Adresy EVM mogą być takie same w różnych łańcuchach，
ale salda są niezależne od siebie, a adresy Solana nie mają zastosowania do EVM USDC。
Zobacz [tabelę obsługi portfela Phantom](https://docs.phantom.com/wallet-sdks-overview#chain-support)。

### Wejście do stopniowego wdrażania nowych sieci

Wejście do nowych łańcuchów jest domyślnie ukryte。Podczas dostępu do konsoli lub Studio można użyć `?features=x402-arbitrum`
aby włączyć odpowiedni łańcuch; wiele flag należy rozdzielać przecinkami。Aby wyłączyć pojedynczy łańcuch, użyj `?features=-x402-arbitrum`，
aby wyczyścić lokalne nadpisania, użyj `?features=none`。Przełączniki są zapisywane osobno dla każdej domeny。
Wycena zamówienia i ponowienie płatności używają tego samego przełącznika, serwer weryfikuje je niezależnie；istniejące rekordy płatności nadal można przeglądać。
Samo włączenie flagi strony nie aktywuje łańcucha, który nie został jeszcze skonfigurowany, a konkretne dostępne sieci płatnicze nadal zależą od bieżącego `accepts`。
