Wyszukiwanie zamówienia według ID zamówienia. Ten punkt końcowy obsługuje dwa tryby odczytu: dostęp anonimowy zwraca tylko minimalne pola wymagane przez stronę płatności; właściciel zamówienia z Account Token otrzymuje pełne szczegóły.

## Przegląd interfejsu API

| Element   | Treść                                                        |
| --- | --------------------------------------------------------- |
| Metoda  | `GET`                                                     |
| URL | `https://platform.acedata.cloud/api/v1/orders/{order_id}` |
| Uwierzytelnianie  | Opcjonalne; anonimowo minimalna projekcja, uwierzytelniony właściciel pełna projekcja                                    |

`/orders/{id}` oraz `/orders/{id}/` są obecnie dostępne. ID zamówienia jest częścią linku płatności i należy traktować je jako wrażliwy nieprzezroczysty identyfikator; nie należy go publicznie rozpowszechniać.

## Zapytanie anonimowe

Strona płatności może odczytywać dane bezpośrednio po utracie stanu logowania:

```shell
export ORDER_ID='twoje ID zamówienia'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json'
```

Odpowiedź anonimowa zawiera tylko `id`, `description`, `price`, `state`, `pay_way`, `pay_url`, `expired_at`, `created_at`. Nie zwraca konta, Application, Package, wewnętrznych identyfikatorów płatności ani metadata.

## Zapytanie uwierzytelnione

```shell
export PLATFORM_TOKEN='twój token konta'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

Właściciel zamówienia otrzyma pełne szczegóły Order, w tym `application` / `applications`, `package` / `packages`, `bank_details`, `invoice_automation` oraz pola modelu. Jeśli użytkownik jest uwierzytelniony, ale nie jest właścicielem zamówienia, zwracany jest `403`; z wyjątkiem superadministratorów.

## Kluczowe pola

| Pole            | Opis                                                          |
| ------------- | ----------------------------------------------------------- |
| `state`       | `Pending`, `Paid`, `Finished`, `Expired`, `Failed` lub `Refunded` |
| `pay_way`     | Bieżąca metoda płatności zamówienia; nazwa pola nie jest `payment_method`                             |
| `pay_url`     | Adres hostowanej strony płatności lub kodu QR; może być pusty                                           |
| `price`       | Ostateczna kwota do zapłaty za zamówienie; obecny model zamówienia nie udostępnia pola `final_price`                         |
| `amount`      | Ilość limitu pakietu; widoczna tylko w pełnej odpowiedzi uwierzytelnionej                                            |
| `finished_at` | Czas ukończenia zamówienia; nazwa pola nie jest `paid_at`                                      |

Pełna odpowiedź może zawierać dodatkowe pola zależne od metody płatności; klient powinien odczytywać je w razie potrzeby i zawsze unikać rejestrowania wrażliwych metadata z pełnej odpowiedzi.

## Obsługa błędów

- `404`: ID zamówienia nie istnieje.
- `403`: Użytkownik jest zalogowany, ale nie jest właścicielem zamówienia.
- Anonimowe żądania nie zwracają `401`; otrzymują jedynie minimalną publiczną projekcję.

## Korekta faktury i ponowne wnioskowanie

Za pomocą `GET /api/v1/orders/{order_id}/invoice/` można odczytać bieżącą fakturę zamówienia. Po automatycznym przesłaniu korekty faktura nadal ma status `Issued`, a `red_state` wskazuje postęp korekty; pomyślne przesłanie nie oznacza ukończenia korekty. Podczas oczekiwania na potwierdzenie, wystawiania faktury korygującej lub archiwizacji zamówienie nie może ponownie wnioskować o fakturę.

Gdy administrator wnioskuje o korektę z powodu błędnych danych fakturowych, takich jak nazwa nabywcy lub numer podatkowy, powodem korekty jest „błąd wystawienia faktury”; automatyczna korekta wywołana zwrotem zamówienia nadal używa „zakończenie usługi”.

Po pomyślnym wystawieniu i zarchiwizowaniu faktury korygującej pierwotna faktura staje się `Voided` i dopiero wtedy zamówienie może ponownie wnioskować o fakturę. Pierwotną fakturę można zobaczyć w historii faktur. Gdy korekta nie powiedzie się lub wynik wymaga weryfikacji, obsługą zajmuje się dział finansowy, a ograniczenie wystawiania faktur dla zamówienia nie zostanie zniesione przedwcześnie. Faktury wystawione ręcznie muszą najpierw zostać unieważnione lub skorygowane w systemie podatkowym lub fakturowym, a następnie potwierdzone przez dział finansowy na platformie.
