---
title: "Schematy rozliczeń X402 `exact` i `upto`"

---

Ace Data Cloud X402 obecnie używa dwóch typów scheme: `exact` i `upto`. Rozwiązują one różne problemy rozliczeniowe.

## `exact`

`exact` oznacza, że cena tego żądania może zostać określona przed wejściem do docelowego API. Kwota podpisana przez klienta jest ostateczną kwotą obciążenia.

Odpowiednie dla:

- generowania obrazów o stałej cenie;
- tworzenia zadań wideo o stałej cenie;
- API wyszukiwania lub narzędzi o stałej cenie;
- płatności za zamówienia.

EVM `exact` używa USDC EIP-3009 `TransferWithAuthorization`:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": {
    "authorization": {
      "from": "0x...",
      "to": "0x...",
      "value": "95215",
      "validAfter": "1780237345",
      "validBefore": "1780240945",
      "nonce": "0x..."
    },
    "signature": "0x..."
  }
}
```

Facilitator na etapie `/verify` weryfikuje podpis i kwotę, a na etapie `/settle` przesyła to upoważnienie do łańcucha.

## `upto`

`upto` oznacza, że klient autoryzuje maksymalny limit, a Ace Data Cloud rozlicza się według rzeczywistego użycia po zakończeniu żądania; rzeczywista kwota obciążenia nie może przekroczyć limitu.

Odpowiednie dla:

- uzupełniania czatu: ostateczna cena zależy od prompt tokens i completion tokens;
- odpowiedzi strumieniowych: rzeczywista długość wyjścia jest znana dopiero po zakończeniu;
- przyszłych API z rozliczaniem po fakcie.

`upto` używa Permit2 `PermitWitnessTransferFrom`. Klient podpisuje nie stały transfer, lecz autoryzację limitu z witness:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2Authorization": {
      "from": "0x...",
      "spender": "0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002",
      "nonce": "123456789",
      "deadline": "1780240945",
      "permitted": {
        "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "amount": "95215"
      },
      "witness": {
        "to": "0x...",
        "facilitator": "0x...",
        "validAfter": "1780237345"
      }
    },
    "signature": "0x..."
  }
}
```

`permitted.amount` jest limitem, niekoniecznie ostateczną kwotą obciążenia. Gateway na etapie `/record` przekształca rzeczywiste użycie na `amount` i przekazuje je do Facilitatora. Facilitator zezwala tylko na rozliczenie `amount &lt;= permitted.amount`.

Wynik działania programu Base `upto`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
elapsed_ms 5104
content ADC_BASE_UPTO_OK
id chatcmpl-DlcbyS4IT8kUAMo4Ri97HiIHc9T8V
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Wyjaśnienie:

- Limit autoryzacji zwrócony w 402 wynosi `95215` atomic USDC, klient podpisuje zgodnie z tym limitem.
- Po rzeczywistej odpowiedzi modelu rozliczane jest tylko `3` atomic USDC, a transakcję on-chain można sprawdzić na BaseScan.
- Ten wynik pokazuje kluczową różnicę `upto`: podpisana kwota jest limitem, a settlement on-chain może być niższy niż limit.
- Jeśli rzeczywiste użycie przekroczy limit, Facilitator powinien odrzucić settlement, a klient musi ponownie autoryzować wyższy limit.

`upto` jest obecnie dostępne tylko na Base. Gdy wymagane jest rozliczanie po fakcie, używaj Base.

## Dlaczego potrzebne jest approve Permit2

`upto` ostatecznie pobiera USDC z portfela płatnika przez x402 proxy za pośrednictwem Permit2. Przed pierwszym użyciem portfel płatnika musi jednorazowo przyznać Permit2 ERC-20 allowance.

Python CLI:

```bash
pip install 'acedatacloud-x402[cli]'
X402_PRIVATE_KEY=0x... acedatacloud-x402 approve-permit2 --network base
```

Programowo:

```python
from acedatacloud_x402 import EVMAccountSigner, approve_permit2

approve_permit2(
    rpc_url="https://mainnet.base.org",
    signer=EVMAccountSigner.from_private_key("0x..."),
    token_address="0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
)
```

Po zakończeniu autoryzacji każde żądanie nadal wymaga podpisania nowej koperty `upto`, ponieważ nonce, deadline, witness i limit kwoty są różne.

## Rozliczenie zerowej kwoty

`upto` obsługuje przypadek, gdy rzeczywista kwota wynosi 0. Na przykład docelowe API nie wygenerowało pomyślnie rozliczalnego użycia, wtedy Gateway może przekazać `amount = "0"`. Facilitator zwróci sukces, ale nie wyśle transakcji on-chain.

Pozwala to uniknąć problemu „żądanie nie zakończyło się sukcesem, ale nadal pobierana jest opłata on-chain”.

## Zalecenia dotyczące wyboru

| Scenariusz                   | Zalecenie                       |
| ---------------------------- | ------------------------------ |
| API o stałej cenie           | Użyj `exact`, logika jest prosta. |
| Płatność za zamówienie       | Użyj `exact`.                  |
| Uzupełnianie czatu, rozliczanie za token | Użyj Base `upto`.              |
| Permit2 approve nie zostało jeszcze wykonane | Najpierw uruchom `exact`, a następnie przejdź na `upto`. |

Jeśli nie masz pewności, który wybrać, najpierw użyj domyślnego zachowania SDK; SDK wybierze wymaganie płatności dla pasującej sieci zwrócone przez serwer.

## Lista kontrolna Base `upto`

Podczas integracji lub diagnozowania problemów potwierdź, że poniższe parametry pochodzą z tej samej odpowiedzi 402 i pozostają zgodne podczas podpisywania przez klienta:

| Parametr                         | Punkt kontrolny                                          |
| -------------------------- | -------------------------------------------- |
| `network`                  | Musi być `eip155:8453`.                           |
| `scheme`                   | Musi być `upto`.                                  |
| `extra.chainId`            | Base chain id to `8453`.                      |
| `asset`                    | Użyj adresu kontraktu Base USDC z odpowiedzi 402.                  |
| `extra.facilitatorAddress` | Musi uczestniczyć w witness i być zgodny z Facilitator `/supported`. |
| Permit2 allowance          | Portfel płatnika musi najpierw autoryzować Permit2 dla Base USDC.               |

Typowe błędy i sposoby obsługi:

| Błąd                                           | Sposób obsługi                                                                          |
| -------------------------------------------- | ----------------------------------------------------------------------------- |
| `invalid_upto_evm_payload_invalid_signature` | Sprawdź, czy chain id, adres facilitatora, Permit2 domain, spender, konto podpisujące i witness są zgodne z odpowiedzią 402. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Wykonaj Permit2 approve dla USDC w docelowym łańcuchu, a następnie ponownie wyślij żądanie.                                         |
| `amount exceeds permitted amount`            | Rzeczywiste użycie przekracza podpisany limit; wymagane jest ponowne podpisanie wyższego limitu.                                                       |
