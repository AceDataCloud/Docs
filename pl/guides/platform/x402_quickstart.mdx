Ten samouczek przedstawia kompletny proces Ace Data Cloud X402 za pomocą minimalnego żądania API. Celem nie jest najpierw pisanie złożonego kodu, lecz najpierw zrozumienie: dlaczego pierwsze żądanie zwraca 402, co znajduje się w `accepts` oraz w jaki sposób `PAYMENT-SIGNATURE` zmienia to samo żądanie API w opłacone żądanie.

## Przygotowanie

Musisz przygotować:

| Element   | Opis                                                   |
| ---- | ---------------------------------------------------- |
| Portfel   | Portfel obsługujący docelową sieć. Base używa portfela EVM, Solana używa portfela Solana.      |
| USDC | W portfelu musi znajdować się wystarczająca ilość USDC. Rzeczywista kwota zależy od `maxAmountRequired` w odpowiedzi 402. |
| Środowisko programistyczne | Dla TypeScript zalecany jest Node.js 18+; dla Python zalecany jest Python 3.10+.    |
| SDK  | Zalecane jest użycie oficjalnego SDK, nie zaleca się ręcznego pisania szczegółów podpisu.                                |

Podczas wywoływania Ace Data Cloud API przez X402 nie jest wymagany API Token. Pierwsze żądanie SDK nie zawiera `Authorization`, Gateway zwróci `402 Payment Required` oraz wymagania płatności; po podpisaniu SDK automatycznie ponowi próbę.

## Instalacja SDK

Adresy źródeł i pakietów:

- Repozytorium SDK: [https://github.com/AceDataCloud/SDK](https://github.com/AceDataCloud/SDK)
- Repozytorium X402 Client: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)
- npm: `@acedatacloud/sdk`、`@acedatacloud/x402-client`
- PyPI: `acedatacloud`、`acedatacloud-x402`

TypeScript:

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client ethers
```

Python:

```bash
pip install acedatacloud acedatacloud-x402
```

Jeśli chcesz używać Solana, musisz również zainstalować odpowiednie zależności:

```bash
npm install @solana/web3.js
```

Zależność Solana signer dla wersji Python jest już zawarta w `acedatacloud-x402`.

Wynik instalacji i sprawdzenia importów w czystym środowisku tymczasowym:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
ethers@6.16.0
@solana/web3.js@1.98.4

acedatacloud 2026.4.26.1
acedatacloud-x402 2026.5.31.3
imports_ok True True True True True True
usage: acedatacloud-x402 [-h] {approve-permit2} ...
```

Wyjaśnienie wyników:

- Zarówno pakiety npm, jak i PyPI są rzeczywiście opublikowanymi pakietami, a nie nazwami zastępczymi w dokumentacji.
- `acedatacloud-x402[cli]` zainstaluje CLI, a podkomenda `approve-permit2` może być używana do autoryzacji Permit2 w scenariuszu `upto`.

## Pierwsze żądanie zwróci 402

Możesz najpierw użyć `curl`, aby zobaczyć, co zwraca nieopłacone żądanie. Poniższy przykład nie spowoduje obciążenia, ponieważ nie zawiera `PAYMENT-SIGNATURE`:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Treść odpowiedzi będzie zawierać tablicę `accepts`, której typowa struktura jest następująca:

```json
{
  "x402Version": 2,
  "resource": {
    "url": "/openai/chat/completions",
    "description": "AceDataCloud API call",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "maxAmountRequired": "95215",
      "amount": "95215",
      "maxTimeoutSeconds": 3600,
      "resource": "/openai/chat/completions",
      "description": "...",
      "payTo": "0x...",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913"
      }
    }
  ],
  "error": "PAYMENT-SIGNATURE header is required"
}
```

Ta sama treść wyzwania jest również umieszczana w formacie base64 w nagłówku odpowiedzi `PAYMENT-REQUIRED`, aby klient mógł odczytać wymagania płatności bez parsowania body.

Podsumowanie wyjścia programu dla nieopłaconego żądania produkcyjnego API jest następujące:

```text
status=402
x402Version 2
accepts [
  ('eip155:8453', 'exact', '95215'),
  ('eip155:8453', 'upto', '95215'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '95215'),
]
```

Wyjaśnienie wyników:

- Pierwsze żądanie nie zawiera `Authorization` ani `PAYMENT-SIGNATURE`, dlatego zwraca HTTP 402 i nie powoduje obciążenia.
- `accepts` jest jedyną wiarygodną podstawą podpisu dla tego żądania i zawiera dostępne sieci, scheme, limit kwoty, adres odbiorcy oraz adres aktywa.
- `network` jest identyfikatorem CAIP-2; podczas wyboru sieci klient musi dopasować ciąg CAIP-2.
- Limit kwoty dla tego minimalnego żądania czatu `gpt-4o-mini` wynosi `95215` atomic USDC, czyli `0.095215` USDC.
- Dla każdego żądania należy odczytać bieżącą odpowiedź 402; nie należy na stałe kodować przykładowej kwoty w kodzie biznesowym.

Znaczenie pól:

| Pole                  | Opis                                                             |
| ------------------- | -------------------------------------------------------------- |
| `scheme`            | Schemat płatności. `exact` oznacza stałą kwotę, a `upto` oznacza limit autoryzacji i rozliczenie według rzeczywistego użycia.                     |
| `network`           | Identyfikator CAIP-2 sieci płatności, na przykład `eip155:8453`、`solana:5eykt4...`.           |
| `maxAmountRequired` | Maksymalna kwota płatności w USDC atomic units; `95215` oznacza `0.095215` USDC.       |
| `amount`            | Kwota do rozliczenia tym razem; `exact` jest taka sama jak `maxAmountRequired`, a `upto` jest podczas rozliczenia zmieniane zgodnie z rzeczywistym użyciem. |
| `payTo`             | Adres odbiorcy.                                                          |
| `asset`             | Adres kontraktu USDC lub adres mint Solana.                                     |
| `extra`             | Rozszerzone informacje wymagane do podpisu, takie jak chain ID, EIP-712 domain i adres Permit2.                      |

## Ukończenie ponownej próby płatności za pomocą SDK

Poniżej znajduje się minimalny przykład TypeScript. Określa on `network: 'base'`, a handler wybierze wymaganie płatności Base z bieżącej odpowiedzi 402; rzeczywista kwota i adres odbiorcy nadal są określane przez `accepts`:
```ts
import { Wallet } from 'ethers';
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') {
      throw new Error(`unsupported method: ${method}`);
    }
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const response = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly: hello' }],
  max_tokens: 8
});

console.log(response.choices[0].message.content);
```

Za tą częścią kodu stoją cztery kroki:

1. SDK wysyła zwykłe żądanie API bez `Authorization`.
2. Gateway zwraca `402 Payment Required` oraz `accepts`.
3. `createX402PaymentHandler` wybiera payment requirement dla `network = 'base'` i podpisuje `PAYMENT-SIGNATURE`.
4. SDK ponawia żądanie z tym samym body, a Gateway wywołuje Facilitator w celu weryfikacji i rozliczenia, po czym przepuszcza je do docelowego API.

## Sprawdzanie obsługiwanych możliwości Facilitator

X402 API nie zależy od katalogu zasobów. Klient bezpośrednio wywołuje znane API i wykorzystuje zwrócone w czasie rzeczywistym przez to żądanie
`402 Payment Required` oraz `accepts` jako jedyną podstawę ceny i podpisu.

Deklaracja możliwości Facilitator znajduje się pod adresem:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Opisuje ona tylko `/supported`, `/verify`, `/settle` oraz aktualnie włączone sieci płatności, nie wymienia zasobów API.

Adres produkcyjnego Facilitator Ace Data Cloud to:

```text
https://facilitator.acedata.cloud
```

Można sprawdzić, jakie sieci i scheme obsługuje:

```bash
curl https://facilitator.acedata.cloud/supported
```

Zwrócone `kinds` wyświetlą sieci i scheme obsługiwane przez Facilitator. Podczas rzeczywistych wywołań nadal należy kierować się `accepts` zwróconym przez API.

Wynik `/supported` Facilitator:

```text
kinds [
  ('eip155:8453', 'exact'),
  ('eip155:8453', 'upto', {'facilitatorAddress': '0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708'}),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact')
]
```

Wynik oznacza:

- `/supported` wskazuje, że Facilitator ma możliwości weryfikacji i rozliczania dla tych sieci i scheme.
- Zarówno Base, jak i Solana obsługują `exact`; `upto` jest obecnie dostępne tylko w Base.
- To, czy konkretne API zezwala na daną sieć, nadal zależy od 402 `accepts` tego API.
