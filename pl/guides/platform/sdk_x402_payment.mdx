[X402](https://www.x402.org/) to zaproponowany przez Coinbase protokół płatności on-chain „rozliczany przez HTTP 402”: serwer zwraca `402 Payment Required` dla żądań bez tokena, dołączając pole `accepts: [...]` z listą akceptowanych łańcuchów / aktywów / cen; klient lokalnie podpisuje autoryzację (na EVM jest to Permit2 / EIP-712, na Solana jest to autoryzacja transferu tokenu SPL), umieszcza envelope po base64 w nagłówku `PAYMENT-SIGNATURE` i ponownie wysyła żądanie. Po weryfikacji serwer faktycznie rozlicza płatność on-chain, a następnie zwraca wynik biznesowy.

> Klient X402 Ace Data Cloud bezpośrednio wywołuje docelowe API i używa zwracanego w czasie rzeczywistym przez to żądanie `402 Payment Required` oraz `accepts` jako podstawy ceny i podpisu. Możliwość płatności Facilitatora można zweryfikować pod [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

Zarówno `@acedatacloud/sdk`, jak i `acedatacloud` udostępniają hook `paymentHandler`: gdy żądanie wysłane przez sam SDK otrzyma `402`, wywołuje on wstrzyknięty przez Ciebie handler, aby uzyskać nagłówek `PAYMENT-SIGNATURE`, a następnie ponownie wysyła pierwotne żądanie. Łącząc `@acedatacloud/x402-client` / `acedatacloud-x402` z SDK, **cały proces jest całkowicie transparentny dla kodu biznesowego** — używasz tylko `client.openai.chat.completions.create(...)`, wygląda to dokładnie tak samo jak tryb tokenowy, lecz pod spodem jest płatność za wywołanie bez potrzeby wcześniejszego doładowania.

Ten artykuł:

- faktycznie przeprowadza łańcuch „bez tokena + wstrzyknięcie handlera X402” po stronie TS ([weryfikacja T12](#cztery-rzeczywista-weryfikacja-uruchomienia))
- wymienia różnice między dwoma łańcuchami podpisów EVM / Solana
- przedstawia trzy adaptacje: tryb klucza prywatnego `viem`, tryb portfela przeglądarkowego oraz tryb Python `EVMAccountSigner`
- wyjaśnia pole `preferScheme` / `prefer_scheme`, na którym łatwo się potknąć

## I. Przegląd protokołu (koniecznie przeczytaj)

Jedno udane wywołanie X402 obejmuje **3 HTTP RTT**:

```text
1. SDK -> /openai/v1/chat/completions               (bez Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. Wewnętrznie SDK -> paymentHandler({ url, method, body, accepts })   (lokalny podpis, 0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (wstrzyknięty nagłówek PAYMENT-SIGNATURE)
   <- 200 + business response   (rozliczenie jest wykonywane na serwerze)
```

Envelope X402 to fragment JSON, który po zakodowaniu base64 jest umieszczany w nagłówku `PAYMENT-SIGNATURE`. Struktura (fragment):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

Na najwyższym poziomie envelope znajduje się `x402Version: 2`, a obiekt `accepted` deklaruje `scheme` i `network` (identyfikator CAIP-2) wybrane dla tej płatności.

| scheme  | Znaczenie                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Stała cena (scenariusze z ustalonym cennikiem, takie jak generowanie obrazów / wideo, wyszukiwanie itd.). Podpisywana kwota = kwota wymagana przez serwer.                                                         |
| `upto`  | Rozliczanie mierzone (chat completions / typ tokenowy). Podpisywana jest kwota **maksymalna**, a faktycznie rozliczana jest wyłącznie wykorzystana część (na podstawie Permit2 + witness). **Zdecydowanie zalecane** dla API typu sesyjnego. |

`preferScheme` / `prefer_scheme` służy do wyboru preferencji, gdy serwer **jednocześnie udostępnia wiele scheme**. Jeśli serwer udostępnia tylko `exact`, to pole zostanie zignorowane; jeśli ustawisz `upto`, ale serwer go nie udostępnia, nastąpi powrót do pierwszej pasującej pozycji.

## II. TypeScript: dwie metody użycia — portfel przeglądarkowy + serwerowe viem

### Instalacja

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Przetestowane numery wersji:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Pełna sygnatura `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' 必填
  evmProvider?: EVMProvider;                // network='base' 必填，EIP-1193
  evmAddress?: string;                      // network='base' 必填
  preferScheme?: 'exact' | 'upto';
}
```

Wartością zwracaną jest `(ctx) => Promise&lt;{ headers: Record<string, string> }>`, co dokładnie odpowiada sygnaturze hooka SDK `paymentHandler`.

### Użycie 1: przeglądarka (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. 让用户连钱包
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. 切到 Base 主网
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. 构造 SDK 客户端，注入 X402 handler
//    注意：不传 apiToken，让 SDK 走 402 路径
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat 类必选 upto
  })
});

// 4. 正常调
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Przy pierwszym wywołaniu przeglądarka wyświetli **dwa monity o podpis**: pierwszy to jednorazowe approve Permit2 dla USDC (kwota to `MaxUint256`, zapisywana on-chain); drugi to podpis EIP-712 dla envelope X402 (nie jest zapisywany on-chain, służy tylko do weryfikacji przez facilitator). Kolejne wywołania wymagają tylko drugiego podpisu, więc z perspektywy użytkownika jest to „kliknij raz, aby podpisać → uzyskaj wynik”.

### Użycie 2: serwer Node + klucz prywatny viem (odpowiednie dla backendu / CLI)

`@acedatacloud/x402-client` po stronie TS **akceptuje wyłącznie providera EIP-1193** — nie zarządza bezpośrednio kluczami prywatnymi. W scenariuszach Node / CLI standardowym sposobem jest opakowanie klucza prywatnego jako `WalletClient` za pomocą [`viem`](https://viem.sh/), a następnie użycie adaptacji EIP-1193 przez [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) lub wewnętrznej adaptacji viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient ma wbudowaną kompatybilną z EIP-1193 metodę .request(), można go bezpośrednio użyć jako evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request spełnia EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Jeśli uważasz, że adaptacja EIP-1193 w viem nie jest wystarczająco stabilna, możesz również skorzystać z bardziej niskopoziomowego [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts), samodzielnie łącząc ścieżkę `accepts → signed envelope → PAYMENT-SIGNATURE header` i pomijając hook SDK; jednak nadal zalecane jest przede wszystkim użycie `createX402PaymentHandler`, aby nie musieć samodzielnie utrzymywać aktualizacji protokołu.

### Sposób użycia 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

W sieci Solana obecnie **udostępniany jest tylko scheme `exact`**, więc `preferScheme` nie działa w Solanie.

## III. Python: tryb klucza prywatnego

`acedatacloud-x402` w Pythonie korzysta ze ścieżki **bezpośredniego podpisywania kluczem prywatnym** (bez abstrakcji EIP-1193), co lepiej nadaje się do serwerów / executorów zadań.

### Instalacja

```bash
pip install acedatacloud acedatacloud-x402
```

Przetestowane wersje:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. Utwórz signer z klucza prywatnego
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. Utwórz SDK: nie przekazuj api_token, aby SDK używało ścieżki 402
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # dla typu chat zawsze wybierz upto
    )
)

# 3. Normalne wywołanie
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # opcjonalne
    )
)
```

### Jednorazowe approve (tylko przy pierwszym użyciu EVM)

X402 na EVM Base korzysta z Permit2, co wymaga, aby portfel jednorazowo wykonał approve `MaxUint256` dla USDC na rzecz kontraktu Permit2. `acedatacloud-x402` ma wbudowane `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Tę transakcję wystarczy wysłać raz, a później wszystkie płatności X402 EVM będą korzystać z tego upoważnienia. Solana tego nie wymaga.

## IV. Weryfikacja rzeczywistego uruchomienia

Cel testu: **SDK TS nie przekazuje tokena, wstrzykuje handler X402 i może poprawnie skonstruować oraz zainicjować żądanie** (lekka weryfikacja bez wydawania prawdziwego USDC w sieci).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // provider zastępczy
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Wynik:

```text
handler_type function
client_ctor_ok AceDataCloud
```

Wynik oznacza:

- Nie przekazano `apiToken`, a konstrukcja SDK **nie zgłasza błędu**, co dowodzi, że tryb X402 rzeczywiście jest prawidłowym zamiennikiem tokena.
- `createX402PaymentHandler` zwraca funkcję (hook), którą SDK wywoła dopiero po otrzymaniu 402.
- Kompleksowy test end-to-end faktycznej płatności w sieci nie został umieszczony w tym poradniku, ponieważ wiąże się z rzeczywistym pobraniem USDC; możesz zapoznać się z przykładem e2e w [przewodniku integracji X402](https://platform.acedata.cloud/documents/x402-integration).

> Pythonowe `create_x402_payment_handler` również przeszło taką samą weryfikację — wartość zwracana przez funkcję jest callable, a konstrukcja `AceDataCloud(...)` nie zgłasza błędu przy wstrzyknięciu `payment_handler=...`. Semantyka po obu stronach jest zgodna.

## V. Porównanie z „trybem tokena Bearer”

| Wymiar              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Zastosowanie            | Własny backend, projekty długoterminowe                                                         | Zewnętrzni deweloperzy, płatności za użycie na żądanie, wywołania Agentic                        |
| Rejestracja              | Wymaga złożenia wniosku w [konsoli](https://platform.acedata.cloud/console/applications) | Nie jest wymagana; wystarczy portfel on-chain                                     |
| Dokładność rozliczeń            | Doładowanie z góry, rozliczanie według tabeli tokenów                                                   | Rozliczanie on-chain w czasie rzeczywistym za każde wywołanie                                         |
| Saldo              | Można sprawdzić w konsoli                                                           | Sprawdź USDC w portfelu on-chain                                      |
| Koszt początkowy            | Bezpłatny limit przy rejestracji e-mail                                                        | Wymaga przeniesienia USDC na Base, pierwszego approve Permit2              |
| Odpowiednie dla typu chat       | ✅                                                                 | ✅ (wymaga `preferScheme=upto`)                       |
| Odpowiednie dla jednorazowych płatności / opłacania za inne konto | ❌                                                                 | ✅                                               |
| Zmiany w kodzie            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Dwa tryby mogą współistnieć — w tym samym procesie wystarczy skonfigurować różne metody uwierzytelniania dla różnych instancji `client`.

## VI. Częste pułapki

1. **Klasa chat musi mieć `preferScheme=upto`**: użycie `exact` sprawi, że facilitator pobierze USDC zgodnie z `maxAmountRequired` (a nie rzeczywistym użyciem).
2. **Po stronie Node nie przekazuj surowego klucza prywatnego do `createX402PaymentHandler`**: pakiet TS nie akceptuje `{ privateKey }`, należy opakować go jako provider EIP-1193 (zalecany viem `WalletClient`).
3. **Pierwsze wywołanie wymaga podwójnego podpisu**: pierwszy podpis zatwierdza Permit2 approve (on-chain, z gas), drugi podpisuje X402 envelope (nie on-chain). Kolejne wywołania wymagają już tylko drugiego.
4. **Solana nie ma koncepcji Permit2**: bezpośrednio podpisuje autoryzację transferu tokenów SPL, bez potrzeby approve; ale obecnie on-chain Solana obsługuje tylko `exact`.
5. **Rozróżniaj błędy biznesowe i błędy płatności**: 402 → niepowodzenie handlera rzuca `X402SignError` (konkretny typ zależy od łańcucha); błędy interfejsu biznesowego po ponownym wysłaniu (401 / 422 / 5xx) są nadal klasyfikowane jako zwykłe wyjątki SDK.
6. **Najstabilniejszy sposób adaptacji `viem`**: `evmProvider: walletClient as any` traci sprawdzanie typów, ale zapewnia najlepszą kompatybilność; jeśli chcesz zachować typy, opakuj osobno `.transport.request` z viem w obiekt `{ request }` i przekaż go dalej.
