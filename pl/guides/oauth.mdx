---
title: "Integracja Ace Data Cloud OAuth 2.0"
---

Pozwól użytkownikom autoryzować Twoją aplikację do uzyskiwania dostępu do ich profilu Ace Data Cloud, subskrypcji usług, API Key, użycia lub zamówień. Użyj standardowego **Authorization Code + S256 PKCE**: aplikacja otwiera stronę autoryzacji, a po wyrażeniu zgody przez użytkownika otrzymuje jednorazowy `code`, który następnie wymienia na OAuth access token.

OAuth access token służy do uzyskiwania dostępu do interfejsów zasobów konta; do wywoływania model API użyj odpowiedniego API Key. Autoryzacja OAuth nie tworzy automatycznie API Key, nie aktywuje usług ani nie zwiększa salda.

## Wybór sposobu integracji

| Sposób            | Scenariusze zastosowania                                | Po zakończeniu autoryzacji                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Standardowe przekierowanie OAuth   | Niezależne strony internetowe, klienci desktopowi lub mobilni; osadzona strona samodzielnie inicjuje autoryzację            | Przeglądarka wraca do `redirect_uri` zarejestrowanego przez aplikację, a aplikacja przetwarza `code` i `state` |
| Autoryzacja komponentu strony Studio | Strona osadza stronę główną Studio i chce używać bieżącego konta Studio odwiedzającego | Studio wysyła do aplikacji komunikat z wynikiem autoryzacji, aplikacja nie przekierowuje, pierwotna strona pozostaje                  |

Standardowe przekierowanie nie wymaga `embed=studio`, `embed_origin` ani `postMessage`. W trybie komponentu Studio host tworzy stronę autoryzacji i utrzymuje most komunikatów; strony trzecie integrują się zgodnie z protokołem komponentu na końcu tego dokumentu i nie powinny samodzielnie konstruować tych dwóch parametrów.

## Endpointy i dokument wykrywania

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Zastosowanie                | Adres                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Strona autoryzacji w przeglądarce            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| Wymiana／odświeżanie OAuth token | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Wysłanie żądania unieważnienia            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Informacje o bieżącym użytkowniku            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| Strona zarządzania aplikacjami OAuth      | [Aplikacje OAuth](https://auth.acedata.cloud/user/oauth-apps)                            |
| Lista aplikacji／interfejs rejestracji zalogowanego użytkownika   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Publiczne dane aplikacji używane przez stronę autoryzacji      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Istniejące API Key użytkownika     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<ID użytkownika>&limit=100` |

Interfejs zarządzania aplikacjami wymaga uwierzytelnienia zalogowanego konta i nie jest interfejsem anonimowej dynamicznej rejestracji (DCR). Własne adresy wykrywania／rejestracji usługi MCP oraz endpointy OAuth konta w tej tabeli są różnymi wejściami; podczas łączenia z konkretnym MCP postępuj zgodnie z dokumentacją i wynikami wykrywania tej usługi.

Dokument wykrywania służy do uzyskiwania endpointów i możliwości protokołu. Bieżący proces zwraca OAuth token, a nie `id_token`; nie obsługuj go jako pełnego procesu logowania OpenID Connect wyłącznie dlatego, że istnieje scope `openid`.

## Zakresy uprawnień: używaj bieżących nazw scope

`scope` to rozdzielone spacjami, rozróżniające wielkość liter nazwy uprawnień. Nowe aplikacje używają konkretnych uprawnień, takich jak `profile:read`, `email:read`, `phone:read`.

### Skąd uzyskać dostępne do żądania uprawnienia

Po zalogowaniu interfejs listy aplikacji OAuth `GET /api/v1/oauth2/applications/` zwraca `available_scopes`; selektor uprawnień na stronie zarządzania aplikacją używa tego samego katalogu. Są to opcjonalne zakresy, których powinny używać zwykłe aplikacje samoobsługowe.

**`scopes_supported` w Discovery zawiera wszystkie nazwy uprawnień rozpoznawane przez platformę, nie oznacza to, że Twoja aplikacja może żądać każdej z nich.** Rzeczywista autoryzacja sprawdza jednocześnie:

1. czy uprawnienie może być delegowane do tego typu aplikacji;
2. czy uprawnienie zostało zarejestrowane w dozwolonych zakresach tej aplikacji OAuth;
3. czy bieżący użytkownik posiada żądane uprawnienie.

Nieznane, niezarejestrowane, niedozwolone do delegowania lub nieposiadane przez użytkownika uprawnienia zwracają `invalid_scope`. Podczas wymiany kodu autoryzacyjnego i odświeżania są one również ponownie sprawdzane; uprawnienia nie są automatycznie uzupełniane ani podnoszone.

### Opcjonalne uprawnienia dla zwykłych aplikacji samoobsługowych

Poniżej znajduje się bieżący katalog (2026-10-09); podczas integracji kieruj się `available_scopes`.

| Scope                                            | Zastosowanie                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Odczyt／aktualizacja profilu                               |
| `email:read`                                     | Odczyt adresu e-mail                                    |
| `phone:read`                                     | Odczyt numeru telefonu i regionu                                |
| `billing-profile:read` / `billing-profile:write` | Odczyt／zarządzanie danymi rozliczeniowymi                               |
| `applications:read` / `applications:write`       | Odczyt／zarządzanie subskrypcjami usług                               |
| `credentials:read` / `credentials:write`         | Odczyt／zarządzanie API Key                           |
| `usage:read`                                     | Odczyt historii wywołań                                  |
| `orders:read` / `orders:write`                   | Odczyt／tworzenie i zarządzanie zamówieniami                              |
| `auto-recharge:read` / `auto-recharge:write`     | Odczyt／zarządzanie ustawieniami automatycznego doładowania                             |
| `recharge-cards:redeem`                          | Realizacja kart doładowań                                   |
| `coin:read`                                      | Odczyt informacji związanych z tokenami                                |
| `distribution:read`                              | Odczyt informacji o dystrybucji                                  |
| `connections:read` / `connections:write`         | Odczyt／zarządzanie połączeniami                                 |
| `skills:read` / `skills:write`                   | Odczyt／zarządzanie umiejętnościami                                 |
| `openid`                                         | Bieżąca implementacja pozwala także UserInfo zwracać podstawowe dane; nie zwraca ID Token    |
| `offline_access`                                 | Żądanie refresh token, aby odświeżyć po wygaśnięciu access token |

Na przykład do samego odczytu profilu użyj `profile:read`; jeśli potrzebny jest również e-mail, dodaj `email:read`; aby odczytać istniejące API Key, użyj `profile:read credentials:read`. O `credentials:write` proś tylko wtedy, gdy rzeczywiście musisz tworzyć lub modyfikować Key, a jeśli potrzebujesz odświeżania, dodaj `offline_access`.

Niektóre uprawnienia są przeznaczone wyłącznie dla zaufanych aplikacji zatwierdzonych przez platformę, na przykład `sites:read`, `sites:write`, `platform-tokens:read`; inne uprawnienia nie są otwarte dla zwykłych aplikacji OAuth stron trzecich. Typ klienta `public`／`confidential` opisuje, czy może on bezpiecznie przechowywać secret, i nie ma związku z tym, czy aplikacja jest zaufana. Aplikacje tworzone samoobsługowo nie mogą samodzielnie włączać zaufanych uprawnień.

`account` to selektor uprawnień konta używany przez wskazany oficjalny MCP zarządzania kontem, a nie scope „wszystkie uprawnienia” dla aplikacji stron trzecich i nie może być mieszany z innymi scope. Strony trzecie powinny wyraźnie wymieniać wymagane konkretne uprawnienia.

### Migracja ze starej dokumentacji

| Stary zapis                                         | Bieżący sposób                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Wymień osobno konkretnie potrzebne uprawnienia; nie istnieje ogólny odpowiednik „zaznacz wszystko” |

Stare nazwy nie są akceptowane jako kompatybilne aliasy. Równocześnie zaktualizuj scopes zarejestrowane dla aplikacji OAuth, adres URL autoryzacji i własną kontrolę uprawnień; zmiana konfiguracji aplikacji nie doda uprawnień do już wydanych tokenów, użytkownik musi ponownie dokonać autoryzacji.

## Krok 1: zarejestruj aplikację OAuth

Otwórz [zarządzanie aplikacjami OAuth](https://auth.acedata.cloud/user/oauth-apps), utwórz aplikację i wypełnij:
- Nazwa, opis, logo aplikacji: wyświetlane po stronie aplikacji na stronie autoryzacji.
- Typ klienta: dla czysto frontendowych, mobilnych lub desktopowych klientów wybierz **Public**; dla usług, które mogą przechowywać secret na backendzie, wybierz **Confidential**.
- Adres zwrotny: w środowisku produkcyjnym używaj HTTPS i zarejestruj pełny URL, pod którym aplikacja faktycznie obsługuje callback.
- Uprawnienia: wybierz faktycznie potrzebne scopes z katalogu dostępnego na stronie.

Zapisz `client_id`. Klient Confidential przechowuje `client_secret` po stronie serwera; nie może on trafić do HTML, zmiennych budowania frontendu ani URL. Klient Public nie używa secret podczas wymiany tokenu; nawet jeśli odpowiedź rejestracji zawiera to pole, nie należy traktować go jako poświadczenia, które klient może zachować w tajemnicy.

`redirect_uri` musi być dokładnie taki sam podczas rejestracji, autoryzacji i wymiany tokenu, w tym ścieżka, końcowy ukośnik i parametry zapytania. Każde konto może utworzyć maksymalnie 20 aplikacji. Secret jest wyświetlany tylko podczas tworzenia／rotacji; po rotacji stary secret nie może być dalej używany do wymian wymagających uwierzytelnienia klienta.

## Krok 2: przycisk inicjuje autoryzację

Przy każdym kliknięciu połączenia wygeneruj nowe losowe `state` i `code_verifier`, oblicz:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Zapisz `state`, verifier i adres zwrotny w własnej sesji aplikacji, a następnie otwórz stronę autoryzacji z parametrami zakodowanymi w URL:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<pełny adres callback>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<losowa wartość dla tego razu>
  &code_challenge=<wartość wyzwania S256 dla tego razu>
  &code_challenge_method=S256
```

Klient Public musi wysyłać PKCE S256. Chociaż Discovery nadal wymienia `plain`, klient Public nie może go używać. Klientowi Confidential również zaleca się używanie S256; jeśli podczas inicjowania autoryzacji użyto PKCE, podczas wymiany należy przesłać odpowiadający verifier.

Po wyrażeniu zgody przez użytkownika następuje powrót do `redirect_uri`, a parametry zapytania zawierają `code` i zwrócony bez zmian `state`. W przypadku odmowy zwracane są `error=access_denied`, opis błędu oraz `state`. Przed obsługą callbacku najpierw zweryfikuj, że state pasuje do bieżącej sesji. Kod autoryzacyjny jest ważny przez 10 minut i można go wymienić tylko raz; po niepowodzeniu należy ponownie zainicjować połączenie, zamiast wielokrotnie odświeżać stary URL callbacku.

## Krok 3: wymiana na token OAuth

Klient Public wymienia token bezpośrednio z przeglądarki lub klienta; klient Confidential wymienia go na własnym backendzie. Treść żądania obsługuje kodowanie formularza, a poniższe zmienne reprezentują dane uzyskane przez aplikację w tej autoryzacji:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Klient Confidential musi dodatkowo dodać po stronie serwera pole formularza `client_secret`. Obecnie obsługiwane jest `client_secret_post`; nie traktuj uwierzytelnienia klienta HTTP Basic jako obsługiwanej metody.

Z udanej odpowiedzi odczytaj `access_token`, `token_type`, `expires_in` oraz faktycznie przyznany `scope`. `refresh_token` jest dostępny tylko, jeśli zażądano i przyznano `offline_access`. Nie traktuj OAuth access token jako API Key API modelu i nie zapisuj tokenu, verifiera ani kodu autoryzacyjnego w logach, zdarzeniach analitycznych ani linkach udostępniania.

## Krok 4: odczyt informacji o użytkowniku i API Key

Najpierw użyj OAuth access token do wysłania żądania UserInfo:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Zwracane pola zależą od scope: `id` jest identyfikatorem użytkownika; `profile:read` lub `openid` umożliwia odczyt podstawowych danych (takich jak `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); e-mail wymaga `email:read`, a numer telefonu i region wymagają `phone:read`. Nie zakładaj, że nieautoryzowane pola zawsze istnieją.

Gdy potrzebny jest istniejący API Key i przyznano `credentials:read`, użyj `id` z UserInfo jako warunku filtrowania:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Zwracana lista używa `count` i `items`, a pole Key to **`items[*].token`**, nie `data[0].value`. `user_id=me` nie jest prawidłowym ID użytkownika dla tego interfejsu. Dane z wielu stron odczytuj dalej za pomocą `offset`／`limit`; nie traktuj pierwszej strony jako wszystkich poświadczeń.

Wybieraj odpowiednie poświadczenia według aplikacji, usługi i statusu ważności; nie pobieraj bezrefleksyjnie pierwszego wpisu. Pusta lista nie oznacza niepowodzenia autoryzacji; użytkownik mógł jeszcze nie utworzyć odpowiedniego Key. Kontrola uprawnień OAuth access token oraz zakres usługi, limity i warunki wygaśnięcia samego API Key są odrębnymi ograniczeniami.

**Zezwolenie na odczyt API Key oznacza, że strona trzecia może go zapisać i używać. Cofnięcie żądania OAuth lub wyczyszczenie stanu logowania aplikacji nie unieważni już skopiowanego API Key; użytkownik musi osobno cofnąć lub zrotować ten Key w zarządzaniu poświadczeniami.**

## Działający przykład przeglądarkowy Public / PKCE

Wdróż poniższą stronę pod zarejestrowanym `REDIRECT_URI`, zastąp `CLIENT_ID` i adres callbacku. Przycisk inicjuje standardową autoryzację, a po powrocie na tę samą stronę odczytuje dane profilu i liczbę istniejących Key. Przykład nie wyświetla ani nie utrwala Key; aplikacja produkcyjna wykorzystuje wyniki zgodnie z rzeczywistym zastosowaniem. Najpierw zweryfikuj na niezależnej stronie przeglądarki, a następnie przeprowadź odbiór zgodnie z późniejszymi wymaganiami dotyczącymi iframe.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>连接 Ace Data Cloud</title>
<button id="connect" type="button">连接账号</button>
<p id="status" role="status">尚未连接</p>
<script type="module">
const CLIENT_ID = '替换为你的 client_id';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`接口返回 HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = '无法开始连接，请检查浏览器存储设置后重试。';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('授权会话不匹配，请重新连接。');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('授权会话已失效，请重新连接。');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('未完成授权，可以重新连接。');
    if (!code) throw new Error('回调缺少授权码，请重新连接。');
    status.textContent = '正在连接…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('未取得授权令牌。');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('未取得用户标识。');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('凭证列表格式不符。');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `已连接 ${profile.nickname || profile.username || profile.id}；本页有 ${keyCount} 条 API Key。`;
  } catch (error) {
    status.textContent = `连接未完成：${error.message || '网络异常'} 请重新点击连接。`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Przykładowe wywołanie zwrotne i punkt wejścia muszą znajdować się pod tym samym originem, w tej samej karcie przeglądarki / iframe, aby można było odczytać wcześniej zapisany `sessionStorage`. Aplikacja produkcyjna powinna zarządzać tokenami we własnym mechanizmie sesji, obsługiwać ich wygaśnięcie oraz usuwać parametry URL autoryzacji po otrzymaniu odpowiedzi; główny interfejs strony powinien zostać wyrenderowany najpierw, a awarie sieci powinny wpływać wyłącznie na stan połączenia.

## iframe na stronie white-label

### Strona klienta samodzielnie przekierowuje na stronę autoryzacji

Wystarczy użyć standardowych parametrów OAuth i własnej obsługi wywołania zwrotnego; `window.location.assign()` nawiguje bieżący iframe, a strona nadrzędna pozostaje w domenie white-label. Nie ma potrzeby dodawania `embed=studio` dla ikon ani implementowania protokołu wiadomości Studio.

Należy spełnić następujące warunki:

- Strona aplikacji i strona wywołania zwrotnego używają HTTPS, są faktycznie dostępne i zezwalają na osadzenie przez iframe z domeny nadrzędnej white-label; sprawdź `Content-Security-Policy: frame-ancestors` i `X-Frame-Options` po obu stronach.
- Sandbox zezwala na wymagane przez stronę skrypty, formularze oraz możliwości originu / przechowywania danych. Przy obsłudze logowania w wyskakującym oknie wymagane są również odpowiednie możliwości wyskakujących okien; preferuj konfigurację komponentu Website udostępnianą przez Studio.
- Przeglądarka zezwala na używanie w bieżącym scenariuszu osadzenia pamięci wymaganej przez stan autoryzacji. Stan logowania do strony white-label i stan logowania AuthFrontend mogą się różnić; nie należy zakładać, że zalogowanie do strony white-label oznacza już zalogowanie na stronie autoryzacji.
- Usługa wymiany tokenów w wywołaniu zwrotnym jest dostępna, a żądania międzyoriginowe zezwalają na origin aplikacji; błędy DNS, CORS i HTTP muszą wyświetlać stan umożliwiający ponowienie próby i nie mogą powodować zatrzymania renderowania całej strony.

Lewa strona strony autoryzacji odczytuje Logo aplikacji OAuth; prawa strona odczytuje favicon / logo tej Site, gdy przeglądarka może przekazać origin nadrzędny, a domena nadrzędna przejdzie weryfikację zweryfikowanej strony, w przeciwnym razie wyświetlana jest domyślna ikona. Decyduje to wyłącznie o prezentacji marki, nie ustanawia sesji logowania ani nie udostępnia stronie klienta uprawnień do konta.

**Bieżące ograniczenie: gdy zwykły OAuth w iframe wymaga ponownego logowania, nadal występuje luka w procesie powrotu do strony autoryzacji po ukończeniu logowania.** Przed wdrożeniem należy osobno przeprowadzić odbiór dla „Auth zalogowany” oraz „Auth niezalogowany / wygasły”. Dopóki ta luka nie zostanie naprawiona i zweryfikowana, pierwsze logowanie może używać osobnej strony do ukończenia standardowego OAuth albo autoryzacji komponentu Studio opisanej poniżej; nie należy obiecywać działania we wszystkich scenariuszach iframe wyłącznie na podstawie wyników testów w stanie zalogowania.

### Używanie do autoryzacji bieżącego konta Studio

W Studio włącz OAuth w „Ustawienia → Strona główna → Komponenty strony”, wpisz `client_id` i zarejestrowany adres wywołania zwrotnego. Strona i wywołanie zwrotne muszą używać tego samego originu HTTPS oraz różnić się od originu Studio. Strona trzecia musi:

1. Wysłać `acedatacloud:oauth:ready` do dokładnego originu strony nadrzędnej, odebrać i zweryfikować `acedatacloud:oauth:init`.
2. Przycisk generuje state i verifier PKCE, wysyła `acedatacloud:oauth:authorize` (state, wyzwanie S256); verifier pozostaje wewnątrz własnej strony.
3. Zweryfikować okno nadrzędne, origin i state, obsłużyć code lub error w `acedatacloud:oauth:result` oraz wymienić je zgodnie ze standardowym punktem końcowym tokenów.
Studio wyświetla stronę autoryzacji w obszarze komponentu, po zgodzie użytkownika zwraca kod autoryzacyjny w wiadomości, aplikacja nie musi przekierowywać. Gdy nie ma logowania, zwracane jest `login_required`, przy odmowie zwracane jest `access_denied`, a po przekroczeniu czasu oczekiwania zwracane jest `authorization_timeout`. Zmiana konta przebuduje iframe aplikacji i anuluje nieukończoną autoryzację.

Komponent obecnie żąda `profile:read credentials:read`, nie obejmuje `offline_access`. Nie zakładaj, że zawsze można otrzymać refresh token. `embed=studio` i `embed_origin` są utrzymywane przez hosta Studio oraz stronę autoryzacji, strona klienta musi jedynie przestrzegać protokołu wiadomości.

Pełny przykład przycisku znajduje się w [Przewodniku integracji OAuth komponentów witryny Studio](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Cykl życia, odświeżanie i unieważnianie

Domyślny okres ważności access tokena wynosi 15 dni, odświeżanie lub ponowną autoryzację należy zaplanować na podstawie `expires_in` z każdej odpowiedzi; refresh token domyślnie jest ważny 30 dni, a jego okres zależy od konfiguracji usługi. Nie koduj tych dwóch wartości na stałe jako wieczystych gwarancji.

Po przyznaniu `offline_access` można wywołać:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Odświeżenie zwróci nowe tokeny, aplikacja powinna zapisać najnowsze wartości. Podczas odświeżania sprawdzane jest, czy aplikacja jest nadal ważna, użytkownik jest dostępny i uprawnienia są nadal przyznane. W przypadku niepowodzenia wyczyść własny stan połączenia i przeprowadź ponowną autoryzację.

**Obecna implementacja odświeżania OAuth nie gwarantuje natychmiastowego unieważnienia starego refresh tokena po odświeżeniu.** Nie traktuj otrzymania nowego tokena jako oznaki, że stary token został unieważniony, ani nie zastępuj zakończenia istniejących tokenów rotacją secretu.

Sposób wywołania żądania unieważnienia to:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Obecny endpoint unieważniania zwraca HTTP 200, ale nie implementuje natychmiastowego unieważniania wydanych JWT.** Aplikacja powinna wyczyścić zapisane przez siebie tokeny i nie może traktować 200 jako dowodu, że wszystkie wydane tokeny lub API Key zostały unieważnione. W przypadku ujawnionych lub skopiowanych API Key należy oddzielnie unieważnić lub obrócić odpowiednie poświadczenia.

## Typowe błędy i odbiór

| Zjawisko／błąd                         | Diagnostyka                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Użyj aktualnych nazw uprawnień; sprawdź zakresy rejestracji aplikacji, ograniczenia delegowania i uprawnienia użytkownika. Cały katalog Discovery nie jest katalogiem wybieralnym przez aplikację                      |
| `invalid_request`             | Wymagane parametry, dokładny adres callback, challenge i method S256 klienta Public                        |
| `invalid_client`              | client ID, stan aplikacji, secret klienta Confidential; sprawdź, czy błędnie użyto uwierzytelniania Basic             |
| `invalid_grant`               | code wygasł／został wykorzystany, verifier lub redirect URI nie pasuje; podczas odświeżania sprawdzane są także zmiany aplikacji i uprawnień                 |
| `access_denied`               | Użytkownik odmówił, przywróć przycisk połączenia, nie wyświetlaj cyklicznie autoryzacji                                                  |
| `unsupported_grant_type`      | Obecnie obsługiwane są `authorization_code`、`refresh_token`                             |
| HTTP 401／403                  | Rozróżnij nieprawidłowy stan logowania, token, scope autoryzacji i uprawnienia dostępu do samego zasobu                                     |
| `Failed to fetch`、błędy DNS／CORS | Zweryfikuj rzeczywistego hosta żądania i dostępność backendu klienta, nie można przypisywać tego „brakowi Key u użytkownika”                                      |
| Autoryzowano, ale nie można odczytać Key                   | Użyj `platform.acedata.cloud`, rzeczywistego user ID, `items[*].token`; rozróżnij pustą listę, paginację i odpowiedzi z błędem |
| Cała strona jest pusta po powrocie z autoryzacji                     | Najpierw renderuj stronę; obsługuj błędy callbacku, tokena, UserInfo i żądań poświadczeń osobno; nie pozwól, aby błąd inicjalizacji zatrzymał całą stronę                      |
| iframe nie kontynuuje po zalogowaniu                 | Postępuj zgodnie z istniejącymi ograniczeniami opisanymi powyżej, testuj scenariusze niezalogowania, wygaśnięcia, odmowy i ponownego połączenia                                          |

Przed dostarczeniem zweryfikuj co najmniej: poprawny callback, odmowę, błędny state, wygasły／wykorzystany code, brak Key, awarię sieci, wygaśnięcie tokena, brak wymaganego scope, a także pierwsze logowanie i zmianę konta w scenariuszu iframe. W dowodach testowych nie zapisuj pełnego code, tokena ani API Key.

## Weryfikacja dwuetapowa i ponowna autoryzacja

Po włączeniu przez użytkownika weryfikacji dwuetapowej Ace Data Cloud przeprowadzi na stronie autoryzacji weryfikację kodu z aplikacji uwierzytelniającej lub jednorazowego kodu odzyskiwania, a następnie dostarczy kod autoryzacyjny. Twoja aplikacja nadal używa standardowego przepływu OAuth i nie powinna żądać od użytkownika, zapisywać ani przekazywać kluczy aplikacji uwierzytelniającej ani kodów odzyskiwania.

Po włączeniu, zmianie, wyłączeniu weryfikacji dwuetapowej przez użytkownika lub odzyskaniu konta poprzednie sesje konta, tokeny odświeżania i powiązane tokeny autoryzacji platformy mogą utracić ważność. Po otrzymaniu nieprawidłowej sesji lub `invalid_grant` ponownie uruchom widoczny dla użytkownika proces autoryzacji, nie używaj wielokrotnie starego kodu autoryzacyjnego ani nie próbuj omijać weryfikacji. Sposób uwierzytelniania zwykłych API Key modeli pozostaje bez zmian; jeśli istnieje podejrzenie przejęcia konta, należy oddzielnie sprawdzić i unieważnić dotknięte API Key.
