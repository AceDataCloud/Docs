Este tutorial usa uma solicitação mínima de API para explicar o fluxo completo do Ace Data Cloud X402. O objetivo não é primeiro escrever código complexo, mas entender primeiro: por que a primeira solicitação retorna 402, o que há em `accepts` e como `PAYMENT-SIGNATURE` transforma a mesma solicitação de API em uma solicitação paga.

## Preparação

Você precisa preparar:

| Item   | Descrição                                                   |
| ---- | ---------------------------------------------------- |
| Carteira   | Uma carteira compatível com a rede de destino. Base usa uma carteira EVM, Solana usa uma carteira Solana.      |
| USDC | A carteira precisa ter USDC suficiente. O valor real está sujeito a `maxAmountRequired` na resposta 402. |
| Ambiente de desenvolvimento | Para TypeScript, recomenda-se Node.js 18+; para Python, recomenda-se Python 3.10+.    |
| SDK  | Recomenda-se usar o SDK oficial; não é recomendado escrever manualmente os detalhes de assinatura.                                |

Não é necessário API Token ao chamar a API Ace Data Cloud com X402. A primeira solicitação do SDK não inclui `Authorization`, o Gateway retorna `402 Payment Required` e os requisitos de pagamento; o SDK tenta novamente automaticamente após assinar.

## Instalar o SDK

Código-fonte e endereços dos pacotes:

- Repositório do SDK: [https://github.com/AceDataCloud/SDK](https://github.com/AceDataCloud/SDK)
- Repositório do X402 Client: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)
- npm: `@acedatacloud/sdk`、`@acedatacloud/x402-client`
- PyPI: `acedatacloud`、`acedatacloud-x402`

TypeScript:

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client ethers
```

Python:

```bash
pip install acedatacloud acedatacloud-x402
```

Se for usar Solana, também será necessário instalar as dependências correspondentes:

```bash
npm install @solana/web3.js
```

A dependência do signer Solana para a versão Python já está incluída em `acedatacloud-x402`.

A saída da verificação de instalação e importação em um ambiente temporário limpo:


Explicação dos resultados:

- Os pacotes npm e PyPI são ambos pacotes realmente publicados, não nomes de placeholder na documentação.
- `acedatacloud-x402[cli]` instala a CLI, e o subcomando `approve-permit2` pode ser usado para autorização Permit2 em cenários `upto`.

## A primeira solicitação retornará 402

Você pode primeiro usar `curl` para ver o que uma solicitação não paga retorna. O exemplo abaixo não gerará cobrança, porque não inclui `PAYMENT-SIGNATURE`:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

O corpo da resposta incluirá o array `accepts`, com uma estrutura comum como a seguinte:

```json
{
  "x402Version": 2,
  "resource": {
    "url": "/openai/chat/completions",
    "description": "AceDataCloud API call",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "maxAmountRequired": "95215",
      "amount": "95215",
      "maxTimeoutSeconds": 3600,
      "resource": "/openai/chat/completions",
      "description": "...",
      "payTo": "0x...",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913"
      }
    }
  ],
  "error": "PAYMENT-SIGNATURE header is required"
}
```

O mesmo conteúdo do desafio também será colocado no cabeçalho de resposta `PAYMENT-REQUIRED` em formato base64, facilitando ao cliente ler os requisitos de pagamento sem analisar o body.

O resumo da saída do programa para uma solicitação não paga da API de produção é o seguinte:

```text
status=402
x402Version 2
accepts [
  ('eip155:8453', 'exact', '95215'),
  ('eip155:8453', 'upto', '95215'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '95215'),
]
```

Explicação dos resultados:

- A primeira solicitação não inclui `Authorization` ou `PAYMENT-SIGNATURE`, portanto retorna HTTP 402 e não gera cobrança.
- `accepts` é a única base confiável de assinatura para esta solicitação, incluindo redes opcionais, scheme, limite de valor, endereço de recebimento e endereço do ativo.
- `network` é um identificador CAIP-2, e o cliente deve corresponder pela string CAIP-2 ao selecionar a rede.
- O limite de valor para esta solicitação mínima de chat `gpt-4o-mini` é `95215` USDC atomic, ou seja, `0.095215` USDC.
- Cada solicitação deve ler a resposta 402 daquela vez; não codifique rigidamente o valor de exemplo no código de negócio.

Significado dos campos:

| Campo                  | Descrição                                                             |
| ------------------- | -------------------------------------------------------------- |
| `scheme`            | Esquema de pagamento. `exact` indica um valor fixo, e `upto` indica um limite de autorização, liquidado de acordo com o uso real.                     |
| `network`           | Identificador CAIP-2 da rede de pagamento, por exemplo, `eip155:8453`、`solana:5eykt4...`.           |
| `maxAmountRequired` | Valor máximo de pagamento, em USDC atomic units; `95215` representa `0.095215` USDC.       |
| `amount`            | O valor a ser liquidado desta vez; `exact` é igual a `maxAmountRequired`, enquanto `upto` é reescrito na etapa de liquidação conforme o uso real. |
| `payTo`             | Endereço de recebimento.                                                          |
| `asset`             | Endereço do contrato USDC ou endereço mint do Solana.                                     |
| `extra`             | Informações estendidas necessárias para a assinatura, como chain ID, domínio EIP-712 e endereço Permit2.                      |

## Concluir a nova tentativa de pagamento com o SDK

Abaixo está o exemplo mínimo em TypeScript. Ele especifica `network: 'base'`, e o handler selecionará o payment requirement do Base na resposta 402 desta vez; o valor real e o endereço de recebimento ainda estão sujeitos a `accepts`:
```ts
import { Wallet } from 'ethers';
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') {
      throw new Error(`unsupported method: ${method}`);
    }
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const response = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly: hello' }],
  max_tokens: 8
});

console.log(response.choices[0].message.content);
```

Por trás deste código, ocorrem quatro etapas:

1. O SDK envia uma solicitação de API comum, sem `Authorization`.
2. O Gateway retorna `402 Payment Required` e `accepts`.
3. `createX402PaymentHandler` seleciona o payment requirement de `network = 'base'` e assina `PAYMENT-SIGNATURE`.
4. O SDK tenta novamente com o mesmo corpo da solicitação, e o Gateway chama o Facilitator para verificar e liquidar antes de permitir a passagem para a API de destino.

## Ver as capacidades suportadas pelo Facilitator

A API X402 não depende de um diretório de recursos. O cliente chama diretamente uma API conhecida e usa o
`402 Payment Required` e o `accepts` retornados em tempo real por essa solicitação como a única base para preço e assinatura.

A declaração de capacidades do Facilitator está em:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Ela descreve apenas `/supported`, `/verify`, `/settle` e as redes de pagamento atualmente habilitadas, sem listar recursos de API.

O endereço do Facilitator de produção da Ace Data Cloud é:

```text
https://facilitator.acedata.cloud
```

É possível verificar quais redes e schemes ele suporta:

```bash
curl https://facilitator.acedata.cloud/supported
```

Os `kinds` retornados listarão as redes e os schemes suportados pelo Facilitator. Durante a chamada real, ainda deve-se usar o `accepts` retornado pela API como referência.

Saída de `/supported` do Facilitator:

```text
kinds [
  ('eip155:8453', 'exact'),
  ('eip155:8453', 'upto', {'facilitatorAddress': '0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708'}),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact')
]
```

O resultado indica:

- `/supported` indica que o Facilitator possui capacidades de verificação e liquidação para essas redes e schemes.
- Tanto Base quanto Solana suportam `exact`; `upto` está atualmente disponível apenas na Base.
- Se uma API específica permite determinada rede ainda depende do `accepts` 402 dessa API.
