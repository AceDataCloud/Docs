Além de pagar diretamente por solicitações de API, o Ace Data Cloud também oferece suporte ao uso do X402 para pagar pedidos no console. O protocolo central para pagamento de pedidos e chamadas de API é o mesmo: a primeira solicitação retorna 402, o cliente assina `PAYMENT-SIGNATURE` e então tenta novamente com a mesma solicitação.

A diferença é que o pagamento de pedidos pertence à API da plataforma e requer um token de conta; enquanto chamar diretamente a API de IA em `x402.acedata.cloud` pode usar apenas X402, sem precisar de um API Token.

## Preparar o pedido

Acesse o [console do Ace Data Cloud](https://platform.acedata.cloud/console/orders), selecione o pedido que precisa ser pago e registre o ID do pedido.

Se você ainda não tem um pedido, pode criar um pedido pendente de pagamento na página de planos. O preço do pedido está sujeito ao que é exibido na página, e o `amount` na resposta 402 do X402 é a base final para a assinatura.

## Criar um token de conta

As solicitações de pagamento de pedidos exigem um token de conta. Abra a [página de Tokens da plataforma](https://platform.acedata.cloud/console/platform-tokens) e crie um token no formato `platform-v1-...`.

Use nas solicitações subsequentes:

```http
Authorization: Bearer {platform_token}
```

O token de conta é diferente de um API Token comum. Um API Token comum é usado para consumir créditos de API; o token de conta é usado para operar recursos da plataforma em nome da sua conta, como pagamentos de pedidos.

## Acionar 402

Primeiro, envie uma solicitação sem `PAYMENT-SIGNATURE`:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

O status retornado é 402, e a resposta inclui `accepts`:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

O pagamento de pedidos usa o x402 v2 oficial: `x402Version` é `2`, `network` usa o identificador CAIP-2, e o campo de valor é `amount`.

## Assinar e tentar novamente

O pagamento de pedidos pode reutilizar as funções de assinatura de baixo nível de `@acedatacloud/x402-client` ou `acedatacloud-x402`. Abaixo está um exemplo em TypeScript:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

## Resposta bem-sucedida e recibo

Após o pagamento do pedido ser bem-sucedido, o corpo da resposta contém as informações do pedido. A plataforma também transportará no cabeçalho de resposta `PAYMENT-RESPONSE` a settlement response codificada em Base64, cujos campos comuns após a decodificação incluem:

| Campo            | Descrição                           |
| ------------- | ---------------------------- |
| `success`     | Se o settlement do Facilitator foi bem-sucedido. |
| `transaction` | Hash da transação de settlement on-chain.                    |
| `network`     | Rede de pagamento.                        |
| `payer`       | Endereço da carteira pagadora.                      |
| `amount`      | Valor efetivamente liquidado, usando atomic units.      |

Se você precisar de reconciliação, é recomendável salvar simultaneamente o ID do pedido, o endereço da carteira pagadora, `transaction` e o status final do pedido.

## Observações

- O pagamento do pedido requer o token da conta da plataforma, não podendo ser concluído apenas com a assinatura da carteira X402.
- `amount` usa USDC atomic units, `1200000` representa `1.2` USDC.
- Não monte por conta própria o endereço de recebimento ou o endereço do ativo; prevalece o `accepts` na resposta 402.
- Se o mesmo `PAYMENT-SIGNATURE` for submetido repetidamente, o Facilitator realizará proteção contra replay com base no nonce.

## Resposta de falha de pagamento

O primeiro HTTP 402 sem `PAYMENT-SIGNATURE` é um desafio de pagamento normal e não representa falha de pagamento. A falha de verificação ou settlement após a assinatura ainda preserva a string padrão `error` como fallback de compatibilidade e retorna uma estrutura de erro estável em `extensions.acedatacloud.paymentError`:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

O cliente deve priorizar a localização com base em `code`; códigos desconhecidos devem recorrer à falha de pagamento genérica. `charged` é um campo de três estados: somente retornará `false` quando houver uma rejeição explícita antes do settlement; a ausência do campo indica que o status da cobrança é desconhecido e não pode ser interpretada como “não cobrado”. Após o pedido atual entrar em `Failed`, não é possível tentar novamente o pedido original; crie um novo pedido após corrigir o problema da carteira.

`metadata.x402.last_error` e `metadata.x402.errors` da lista e dos detalhes do pedido preservam o mesmo conjunto de `code`, `stage`, `retryable`, `charged` e `params`; o texto explicativo público é armazenado em `reason`, e o momento da ocorrência é armazenado em `timestamp`. Por exemplo, `insufficient_token_balance` indica saldo insuficiente de USDC na rede selecionada, e `invalid_signature` indica uma assinatura de pagamento inválida; reler o pedido não os transformará em um `payment_failed` genérico.

Não registre nem envie o `PAYMENT-SIGNATURE` completo, a assinatura da carteira, o payload de autorização, os diagnósticos originais do Facilitator ou as respostas RPC. Para a investigação do suporte, basta o ID do pedido e o `code` de erro público.

## Recompra e queima de ACE para pagamentos na Base e Solana

Após ativar a estratégia de recompra, 3% dos valores efetivamente recebidos elegíveis de Circle USDC na rede principal da Base e USDC na rede principal da Solana são usados para comprar e queimar ACE, sem cobrança adicional da carteira pagadora. A provisão é feita uma vez no momento da recarga; o uso posterior desses Credits para chamar a API não gera provisão repetida; pedidos históricos com desconto e pedidos de políticas antigas não recebem provisão retroativa automaticamente.

Os pagamentos na Base retêm o recibo de pagamento na cadeia Base, e a compra e queima de ACE são executadas de forma assíncrona na Solana. Os pagamentos elegíveis recebem uma provisão precisa de 3% com base no valor efetivamente recebido, sem limite fixo de valor de recompra por transação ou por dia; os fundos disponíveis, as cotações de mercado e as confirmações on-chain ainda podem afetar o tempo de conclusão. O objeto `ace_burn` nos detalhes do pedido fornece `settlement_network`, `settlement_transaction` e `execution_network`, e fornece `swap_signature` e `burn_signature` após a conclusão. `Pending` ou `Processing` não indicam que a queima já ocorreu; somente `Completed` representa que a prova final on-chain foi verificada. Quando um pagamento na Base ainda não atingiu a confirmação final, a recompra aguardará a confirmação, mas isso não afeta os Credits já creditados.
