[X402](https://www.x402.org/) é um protocolo de pagamento on-chain de “cobrança por HTTP 402” proposto pela Coinbase: o servidor retorna `402 Payment Required` em solicitações sem token, incluindo o campo `accepts: [...]` que lista as chains / ativos / preços aceitos; o cliente assina localmente uma autorização (na EVM é Permit2 / EIP-712, na Solana é autorização de transferência de token SPL), coloca o envelope codificado em base64 no cabeçalho `PAYMENT-SIGNATURE` e reenvia. Após a validação, o servidor efetivamente liquida on-chain e então retorna o resultado de negócio.

> O cliente X402 do Ace Data Cloud chama diretamente a API de destino e usa o `402 Payment Required` e o `accepts` retornados em tempo real por essa solicitação como base para preço e assinatura. A capacidade de pagamento do Facilitator pode ser verificada em [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

Tanto `@acedatacloud/sdk` quanto `acedatacloud` expõem um hook `paymentHandler`: quando uma solicitação emitida pelo próprio SDK recebe `402`, ele chama o handler que você injetou para obter o cabeçalho `PAYMENT-SIGNATURE` e então reenvia a solicitação original. Combinando `@acedatacloud/x402-client` / `acedatacloud-x402` com o SDK, **todo o processo é completamente transparente para o código de negócio** — você só usa `client.openai.chat.completions.create(...)`, parecendo exatamente igual ao modo token, mas por baixo é pagamento por chamada, sem precisar recarregar antecipadamente.

Este artigo:

- Executa de verdade a cadeia de “sem token + injeção de handler X402” no lado TS ([validação T12](#quatro-validação-de-execução-real))
- Lista as diferenças entre as duas cadeias de assinatura EVM / Solana
- Fornece três adaptações: modo de chave privada `viem`, modo de carteira do navegador e modo Python `EVMAccountSigner`
- Explica claramente o campo `preferScheme` / `prefer_scheme`, que é fácil de causar problemas

## Um, Visão geral do protocolo (leitura obrigatória)

Uma chamada X402 bem-sucedida envolve **3 RTTs HTTP**:

```text
1. SDK -> /openai/v1/chat/completions               (sem Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK 内部 -> paymentHandler({ url, method, body, accepts })   (本地签名，0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (PAYMENT-SIGNATURE 头注入)
   <- 200 + business response   (结算在服务端完成)
```

O envelope X402 é um trecho de JSON que, após ser codificado em base64, é inserido no cabeçalho `PAYMENT-SIGNATURE`. Estrutura (excerto):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

No nível superior, o envelope possui `x402Version: 2` e declara o `scheme` e o `network` selecionados nesta ocasião por meio do objeto `accepted` (identificador CAIP-2).

| scheme  | Significado                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Preço fixo (cenários de preço como geração de imagem / vídeo, busca etc.). O valor assinado = o valor exigido pelo servidor.                                                         |
| `upto`  | Cobrança por medição (chat completions / tipos de token). Assina um valor de **limite superior**, e apenas a parte realmente utilizada é liquidada (com base em Permit2 + witness). **Altamente recomendado** para APIs do tipo sessão. |

`preferScheme` / `prefer_scheme` é usado para selecionar uma preferência quando o servidor **oferece simultaneamente vários schemes**. Se o servidor expuser apenas `exact`, esse campo será ignorado; se `upto` for definido mas não estiver exposto pelo servidor, haverá fallback para o primeiro item correspondente.

## Dois, TypeScript: dois usos, carteira do navegador + viem no servidor

### Instalação

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Versões testadas:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Assinatura completa de `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' 必填
  evmProvider?: EVMProvider;                // network='base' 必填，EIP-1193
  evmAddress?: string;                      // network='base' 必填
  preferScheme?: 'exact' | 'upto';
}
```

O valor retornado é um `(ctx) => Promise&lt;{ headers: Record<string, string> }>`, correspondendo exatamente à assinatura do hook `paymentHandler` do SDK.

### Uso 1: navegador (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. 让用户连钱包
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. 切到 Base 主网
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. 构造 SDK 客户端，注入 X402 handler
//    注意：不传 apiToken，让 SDK 走 402 路径
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat 类必选 upto
  })
});

// 4. 正常调
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Na primeira chamada, o navegador exibirá **dois prompts de assinatura**: o primeiro é um approve único de Permit2 para USDC (o valor é `MaxUint256`, gravado on-chain); o segundo é a assinatura EIP-712 do envelope X402 (não vai on-chain, apenas para validação pelo facilitator). As chamadas subsequentes precisam apenas da segunda assinatura; em termos de experiência, é “clicar uma vez para assinar → obter o resultado”.

### Uso 2: servidor Node + chave privada viem (adequado para backend / CLI)

No lado TS, `@acedatacloud/x402-client` **aceita apenas provider EIP-1193** — ele não gerencia chaves privadas diretamente. Em cenários Node / CLI, a prática padrão é usar [`viem`](https://viem.sh/) para empacotar a chave privada como `WalletClient`, e então passar pelo adaptador EIP-1193 de [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) ou interno do viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient 自带 EIP-1193 兼容的 .request()，可以直接当 evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request 满足 EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Se achar que a adaptação EIP-1193 do viem não é estável o suficiente, também pode seguir pelo [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts) de nível mais baixo, encadeando por conta própria o caminho `accepts → signed envelope → PAYMENT-SIGNATURE header` e ignorando o hook do SDK; porém, ainda é recomendável priorizar `createX402PaymentHandler`, para evitar ter que manter atualizações do protocolo por conta própria.

### Uso 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

Atualmente, na cadeia Solana, **apenas o scheme `exact` é exposto**, portanto `preferScheme` não tem efeito na Solana.

## III. Python: modo de chave privada

O `acedatacloud-x402` do Python segue o caminho de **assinar diretamente com a chave privada** (sem abstração EIP-1193), sendo mais adequado para servidores / executores de tarefas.

### Instalação

```bash
pip install acedatacloud acedatacloud-x402
```

Versões testadas:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. 从私钥构造签名器
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. 构造 SDK：不传 api_token，让 SDK 走 402 路径
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # chat 类一定选 upto
    )
)

# 3. 正常调
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # 可选
    )
)
```

### Approve único (somente na primeira vez no EVM)

No EVM Base, o X402 usa Permit2, sendo necessário que a carteira faça uma vez um approve de `MaxUint256` de USDC para o contrato Permit2. O `acedatacloud-x402` inclui o `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Essa transação só precisa ser enviada uma vez; depois disso, todos os pagamentos X402 EVM usam essa autorização. A Solana não precisa disso.

## IV. Verificação de execução real

Objetivo do teste: **o SDK TS não passa token, injeta o handler X402 e consegue construir e iniciar requisições normalmente** (verificação leve que não consome USDC real na cadeia).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // 占位 provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Saída:

```text
handler_type function
client_ctor_ok AceDataCloud
```

O resultado indica:

- Sem passar `apiToken`, a construção do SDK **não gera erro**, provando que o modo X402 é de fato uma alternativa válida ao token.
- `createX402PaymentHandler` retorna uma função (hook), que o SDK só chamará ao receber um 402.
- O teste ponta a ponta do pagamento real na cadeia, por envolver desconto real de USDC, não foi incluído neste tutorial; consulte o exemplo e2e no [guia de integração X402](https://platform.acedata.cloud/documents/x402-integration).

> No lado Python, `create_x402_payment_handler` também realizou a mesma validação — o valor de retorno da função é callable, e a construção de `AceDataCloud(...)` não gera erro ao injetar `payment_handler=...`. A semântica dos dois lados está alinhada.

## V. Comparação com o «modo Bearer token»

| Dimensão              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Cenário aplicável            | Backend próprio, projetos de longo prazo                                                         | Desenvolvedores terceiros, pagamento sob demanda por uso, chamadas Agentic                        |
| Registro              | É necessário solicitar no [console](https://platform.acedata.cloud/console/applications) | Não é necessário; basta ter uma carteira na cadeia                                     |
| Precisão de cobrança            | Recarga antecipada, cobrada conforme tabela de tokens                                                   | Na cadeia em tempo real por chamada                                         |
| Saldo              | Pode ser consultado no console                                                           | Consultar o USDC da carteira na cadeia                                      |
| Custo inicial            | O registro por e-mail já concede cota gratuita                                                        | É necessário transferir USDC para a Base, primeiro approve do Permit2              |
| Adequado para tipo chat       | ✅                                                                 | ✅ (é obrigatório `preferScheme=upto`)                       |
| Adequado para pagamento único / pagamento entre contas em nome de terceiros | ❌                                                                 | ✅                                               |
| Alteração de código            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Os dois modos podem coexistir — no mesmo processo, basta configurar métodos de autenticação diferentes para diferentes instâncias de `client`.

## VI. Armadilhas comuns

1. **A classe chat deve usar `preferScheme=upto`**: usar `exact` fará o facilitator deduzir USDC com base em `maxAmountRequired` (e não no uso real).
2. **No lado Node, não passe a chave privada bruta para `createX402PaymentHandler`**: o pacote TS não aceita `{ privateKey }`, é necessário encapsulá-la como um provider EIP-1193 (recomenda-se o `WalletClient` do viem).
3. **A primeira chamada exige duas assinaturas**: a primeira assina o approve do Permit2 (on-chain, com gas), a segunda assina o envelope X402 (não on-chain). As chamadas subsequentes terão apenas a segunda.
4. **Solana não possui o conceito de Permit2**: assina diretamente a autorização de transferência de token SPL, sem necessidade de approve; porém, atualmente, on-chain no Solana suporta apenas `exact`.
5. **Diferencie erros de negócio e erros de pagamento**: 402 → a falha do handler lança `X402SignError` (o tipo específico varia conforme a chain); após o reenvio, os erros da interface de negócio (401 / 422 / 5xx) ainda são classificados como exceções normais do SDK.
6. **A forma mais estável de adaptar `viem`**: `evmProvider: walletClient as any` perde a verificação de tipos, mas tem a melhor compatibilidade; se quiser manter os tipos, encapsule separadamente o `.transport.request` do viem em um objeto `{ request }` e passe-o.
