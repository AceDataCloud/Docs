---
title: "Configurar o compartilhamento global de saldo da Application AceDataCloud"
description: "Platform API guide - Ace Data Cloud"
---

Configure `allow_consume_global`. Após ativá-lo, as Applications por consumo que atendem às condições poderão continuar usando o saldo global da conta quando seu próprio saldo for insuficiente.

## Preparativos

- Crie e armazene com segurança o [Account Token](https://platform.acedata.cloud/documents/platform-token).
- Obtenha o `application_id` que você possui na [lista de solicitações de serviço](https://platform.acedata.cloud/documents/platform-application-list).

```shell
export PLATFORM_TOKEN='你的账户令牌'
export APPLICATION_ID='你的 Application ID'
```

## Visão geral da interface

| Item    | Conteúdo                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------- |
| Método   | `POST`                                                                                             |
| URL  | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| Autenticação   | Account Token                                                                                      |
| Body | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

Em caso de sucesso, retorna o objeto Application atualizado. Use como referência o `allow_consume_global` na resposta, em vez de presumir que o valor da solicitação foi necessariamente salvo.

> Applications do tipo `Period` não têm permissão para consumir o saldo global. Mesmo que seja solicitado `true`, o servidor manterá esse campo como `false`.

## Tratamento de erros

- `401`: Account Token inválido ou ausente.
- `403`: A conta atual não é a proprietária desta Application.
- `404`: O ID da Application não existe.

A entrada para recarga do saldo global e os planos disponíveis devem seguir o console da plataforma e os planos reais retornados pela [criação de pedido](https://platform.acedata.cloud/documents/platform-order-create); não presuma que exista um plano do tipo `Wallet`.

## Aplicações autorizadas para cheque especial

Quando o campo somente leitura `allow_overdraft=true` de uma aplicação por consumo estiver definido, essa aplicação poderá continuar debitando de seu próprio saldo, mesmo que o saldo se torne negativo, e não alternará para a conta global devido a saldo insuficiente. Aplicações sem cheque especial ativado continuam seguindo `allow_consume_global`; após a alternância, a permissão de cheque especial segue a configuração da Application global que efetivamente realiza a cobrança.

## Limite de concorrência para contas de teste

O sistema usa a marca de usuário somente leitura `has_recharged` para registrar se uma recarga paga foi concluída com sucesso ou se créditos foram adicionados manualmente por um administrador; a marca é atualizada após o sucesso da operação, e os usuários históricos serão preenchidos de forma unificada com base em pedidos ou registros explícitos de adição de créditos. Para contas que não realizaram recarga paga nem receberam créditos adicionados manualmente por um administrador, todo o conjunto da conta permite a execução simultânea de apenas uma solicitação cobrável; diferentes API Keys e diferentes serviços compartilham essa única vaga. Recompensas, cartões de resgate e créditos transferidos não são considerados recarga paga. Contas que já concluíram uma recarga paga ou receberam créditos adicionados manualmente por um administrador não estão sujeitas a esta limitação de concorrência de teste e continuam seguindo as verificações originais de saldo e cota de credenciais.

Quando já houver uma solicitação em execução, novas solicitações retornam `429 too_many_requests`. Interfaces gratuitas de consulta, como consulta de tarefas, ainda podem ser chamadas normalmente. A autenticação de conexão do Realtime continua usando o fluxo original de cobrança por rodada e não ocupa esta vaga de solicitação comum.

Quando uma interface assíncrona retornar “aceito”, a tarefa ainda estará em execução, sendo necessário aguardar o resultado final antes de enviar a próxima solicitação de geração. Desconexão de rede ou timeout do proxy não significa que a tarefa foi interrompida; caso a tarefa permaneça por muito tempo sem um estado final, forneça o `trace_id` para entrar em contato com o suporte para verificação.

Esta limitação não altera as interfaces disponíveis para teste nem as regras de cobrança originais. Os custos continuam sendo liquidados após o término da solicitação, de acordo com o uso real.
