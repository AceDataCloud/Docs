---
title: "Planos de cobrança X402 `exact` e `upto`"
description: "Platform API guide - Ace Data Cloud"
---

A Ace Data Cloud X402 atualmente utiliza dois tipos de scheme: `exact` e `upto`. Eles resolvem problemas de cobrança diferentes.

## `exact`

`exact` indica que o preço desta solicitação pode ser determinado antes de entrar na API de destino. O valor assinado pelo cliente é o valor final cobrado.

Adequado para:

- geração de imagens com preço fixo;
- criação de tarefas de vídeo com preço fixo;
- APIs de busca ou ferramentas com preço fixo;
- pagamento de pedidos.

O EVM `exact` utiliza USDC EIP-3009 `TransferWithAuthorization`:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": {
    "authorization": {
      "from": "0x...",
      "to": "0x...",
      "value": "95215",
      "validAfter": "1780237345",
      "validBefore": "1780240945",
      "nonce": "0x..."
    },
    "signature": "0x..."
  }
}
```

O Facilitator verifica a assinatura e o valor na fase `/verify` e envia esta autorização para a blockchain na fase `/settle`.

## `upto`

`upto` indica que o cliente autoriza um limite máximo, e a Ace Data Cloud faz a liquidação com base no uso real após a conclusão da solicitação; a cobrança real não pode exceder o limite.

Adequado para:

- completamentos de chat: o preço final depende dos prompt tokens e completion tokens;
- respostas em streaming: só se sabe o comprimento real da saída depois que ela termina;
- futuras APIs de medição posterior.

`upto` utiliza Permit2 `PermitWitnessTransferFrom`. O cliente não assina uma transferência fixa, mas uma autorização de limite com witness:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2Authorization": {
      "from": "0x...",
      "spender": "0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002",
      "nonce": "123456789",
      "deadline": "1780240945",
      "permitted": {
        "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "amount": "95215"
      },
      "witness": {
        "to": "0x...",
        "facilitator": "0x...",
        "validAfter": "1780237345"
      }
    },
    "signature": "0x..."
  }
}
```

`permitted.amount` é o limite, não necessariamente a cobrança final. O Gateway converterá o uso real em `amount` e o enviará ao Facilitator na fase `/record`. O Facilitator só permite a liquidação de `amount &lt;= permitted.amount`.

Resultado da execução do programa Base `upto`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
elapsed_ms 5104
content ADC_BASE_UPTO_OK
id chatcmpl-DlcbyS4IT8kUAMo4Ri97HiIHc9T8V
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Explicação:

- O limite de autorização retornado em 402 é `95215` atomic USDC, e o cliente assina com base nesse limite.
- Após a resposta real do modelo, apenas `3` atomic USDC são liquidados, e a transação on-chain já pode ser consultada no BaseScan.
- Este resultado demonstra a diferença fundamental de `upto`: o valor assinado é o limite, e o settlement on-chain pode ser menor que o limite.
- Se o uso real exceder o limite, o Facilitator deverá rejeitar o settlement, e o cliente precisará autorizar novamente com um limite maior.

`upto` atualmente é fornecido apenas na Base. Quando for necessária medição posterior, use a Base.

## Por que é necessário o approve do Permit2

No fim, `upto` faz com que o proxy x402 retire USDC da carteira pagadora através do Permit2. Antes do primeiro uso, a carteira pagadora precisa conceder ao Permit2 uma allowance ERC-20 única.

CLI Python:

```bash
pip install 'acedatacloud-x402[cli]'
X402_PRIVATE_KEY=0x... acedatacloud-x402 approve-permit2 --network base
```

De forma programática:

```python
from acedatacloud_x402 import EVMAccountSigner, approve_permit2

approve_permit2(
    rpc_url="https://mainnet.base.org",
    signer=EVMAccountSigner.from_private_key("0x..."),
    token_address="0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
)
```

Após a autorização ser concluída, cada solicitação ainda precisa assinar um novo envelope `upto`, porque nonce, deadline, witness e o limite de valor são todos diferentes.

## Liquidação de valor zero

`upto` suporta casos em que o valor real é 0. Por exemplo, se a API de destino não produziu com sucesso uso faturável, o Gateway pode passar `amount = "0"`. O Facilitator retornará sucesso, mas não enviará uma transação on-chain.

Isso pode evitar o problema de “a solicitação não foi bem-sucedida, mas ainda assim são cobradas taxas on-chain”.

## Recomendações de escolha

| Cenário                   | Recomendação                       |
| ------------------------- | ---------------------------------- |
| API de preço fixo         | Use `exact`, a lógica é simples.   |
| Pagamento de pedido       | Use `exact`.                       |
| Completamento de chat, cobrança por token | Use Base `upto`.       |
| Ainda não fez Permit2 approve | Primeiro faça funcionar com `exact`, depois mude para `upto`. |

Se você não tiver certeza de qual escolher, primeiro use o comportamento padrão do SDK; o SDK escolherá o payment requirement de rede correspondente retornado pelo servidor.

## Lista de verificação do Base `upto`

Ao integrar ou investigar problemas, confirme que os seguintes parâmetros vêm da mesma resposta 402 e permanecem consistentes ao assinar no cliente:

| Parâmetro                  | Ponto de verificação                                          |
| -------------------------- | ------------------------------------------------------------ |
| `network`                  | Deve ser `eip155:8453`.                                      |
| `scheme`                   | Deve ser `upto`.                                             |
| `extra.chainId`            | O chain id da Base é `8453`.                                 |
| `asset`                    | Use o endereço do contrato Base USDC na resposta 402.        |
| `extra.facilitatorAddress` | Deve participar do witness e corresponder ao `/supported` do Facilitator. |
| Permit2 allowance          | A carteira pagadora precisa primeiro autorizar o Permit2 para Base USDC. |

Erros comuns e formas de tratamento:

| Erro                                         | Forma de tratamento                                                                          |
| -------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `invalid_upto_evm_payload_invalid_signature` | Verifique se chain id, endereço do facilitator, domínio Permit2, spender, conta de assinatura e witness correspondem à resposta 402. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Após executar Permit2 approve para o USDC da chain de destino, inicie a solicitação novamente. |
| `amount exceeds permitted amount`            | O uso real excede o limite assinado; é necessário assinar novamente com um limite maior. |
