Ace Data Cloud X402 est actuellement centré sur le règlement en USDC et prend en charge deux types de chaînes : EVM et Solana. Les méthodes de signature, les adresses d'actifs, le comportement du gas et les cas d'usage applicables diffèrent selon les réseaux ; vous devez donc choisir le réseau avant l'intégration.

## Les identifiants réseau utilisent CAIP-2

Le champ `accepts[].network` de x402 v2 est un identifiant CAIP-2, et non une abréviation telle que `base` ou `solana`. Lorsqu'un client fait correspondre un réseau, il doit comparer selon la chaîne CAIP-2 :

| Réseau             | Identifiant CAIP-2                         |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Matrice de prise en charge

| Réseau     | scheme  | Actif                  | Méthode de signature                                 | Cas d'usage applicable                     |
| ------ | ------- | ------------------- | ------------------------------------ | ------------------------ |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Recommandé par défaut, avec une prise en charge mature des portefeuilles et de la liquidité.         |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | API à comptage différé telles que le chat et les modèles.          |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Portefeuilles Solana, Agents ou scénarios d'applications on-chain. |

`upto` est actuellement fourni uniquement sur Base. Les éléments réellement disponibles dépendent des `accepts` renvoyés par l'API. Vous pouvez également consulter le Facilitator :

```bash
curl https://facilitator.acedata.cloud/supported
```

La réponse de Facilitator `/supported` :

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Explication des résultats :

- Les `exact` de Base et Solana sont des parcours de paiement à montant fixe.
- Seule Base fournit le parcours de comptage différé `upto`, qui dépend de l'approbation Permit2.
- L'élément `extra.facilitatorAddress` dans l'entrée `upto` est l'adresse à écrire dans le witness lors de la signature côté client ; elle doit être identique à la valeur renvoyée par le serveur.

## Base

Base utilise le contrat USDC officiel :

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

Dans le schéma `exact`, le client signe EIP-712 `TransferWithAuthorization`. Le contenu de la signature comprend :

- `from` : adresse du portefeuille payeur
- `to` : adresse de réception d'Ace Data Cloud
- `value` : montant de ce paiement
- `validAfter` / `validBefore` : fenêtre de validité de la signature
- `nonce` : nonce aléatoire de 32 octets

Après avoir vérifié la signature, le Facilitator appellera `transferWithAuthorization` de l'USDC on-chain pour effectuer le transfert.

Base est le réseau de production le plus recommandé pour l'intégration, particulièrement adapté au comptage différé `upto`, car les écosystèmes Permit2, USDC et des portefeuilles y sont plus matures.

Exemple de résultat de vérification Base `exact` :

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Explication des résultats :

- Le paid retry de l'API renvoie le contenu du modèle `ADC_BASE_E2E_OK`.
- La transaction on-chain est consultable sur BaseScan, et le numéro du bloc est `46726299`.
- `95215` USDC atomiques correspondent à `0.095215` USDC, qui est le montant réel réglé pour cet appel API.

Résultat d'exécution du programme pour le paiement de commande Base `exact` :

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Explication des résultats :

- L'état final de la commande sur la plateforme est `Finished`.
- Le `pay_id` de la commande enregistre le même hash de transaction Base.
- `1200000` USDC atomiques correspondent à `1.2` USDC, qui est le montant historique effectivement payé pour cette commande de 10 Credits selon l'ancienne politique ; les nouvelles commandes ne bénéficient plus d'une remise supplémentaire pour le mode de paiement X402, et le montant de signature spécifique dépend de la réponse 402 actuelle.

## Solana

Solana utilise SPL USDC `TransferChecked`. Le client construit une transaction de transfert, la signe et la soumet, puis place la signature de transaction ou la transaction sérialisée dans l'enveloppe `PAYMENT-SIGNATURE`.

Caractéristiques de Solana :

- utilisation de Solana wallet adapter ou d'une clé secrète base58 ;
- l'actif est le mint Solana USDC ;
- seul `exact` est actuellement pris en charge ;
- le Facilitator vérifie le mint, la destination, l'authority et le amount de la transfer instruction.

Si le mode fee payer du portefeuille est utilisé, le portefeuille soumet directement la transaction, et le Facilitator est responsable de confirmer la transaction et de renvoyer le résultat du règlement.

Exemple de résultat de vérification Solana `exact` :

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Explication des résultats :

- Le paid retry a déjà renvoyé HTTP 200, et le modèle a produit `ADC_SOLANA_E2E_OK`.
- Des limites de débit peuvent être rencontrées lors de l'interrogation de la signature on-chain via un RPC public.
- Comme les requêtes RPC publiques peuvent être limitées en débit, aucun explorer Solana n'est indiqué ici. Lorsqu'un rapprochement strict est nécessaire, veuillez utiliser votre propre RPC Solana ou les enregistrements de règlement côté plateforme pour confirmer la signature de transaction.

## Comment choisir

| Ce que vous voulez faire        | Réseau recommandé           |
| ------------ | -------------- |
| Exécuter rapidement le parcours minimal     | Base `exact`   |
| S'adresser aux utilisateurs Web3 ordinaires | Base           |
| Effectuer du comptage différé pour des complétions de chat, etc.   | Base `upto`    |
| Applications de l'écosystème Solana  | Solana `exact` |

Quelle que soit la chaîne choisie, ne codez pas les prix en dur dans le client. Le prix est déterminé par `accepts[].maxAmountRequired` renvoyé par le serveur.

## Ajouter un réseau EVM
以下网络的原生 USDC 固定金额支付已提供代码支持，按网络逐一开放。
是否可用以订单或 API 返回的 `accepts` 为准；不代表所有网络已在生产启用。

| Réseau       | Alias      | CAIP-2         | USDC natif                                   |
| ------------ | ---------- | -------------- | --------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

Ces réseaux ne prennent en charge que `exact`, avec une précision de devise de 6. N'utilisez pas d'USDC ponté portant le même nom.
Lors de l'utilisation du Client X402 officiel TypeScript/Python, vous pouvez transmettre l'alias du tableau ou l'identifiant CAIP-2.
Le client utilise l'ID de la chaîne cible pour construire la signature ; le portefeuille doit prendre en charge le réseau cible.

Le tableau officiel de prise en charge du portefeuille d'extension Phantom répertorie Arbitrum et Polygon ; Optimism, Avalanche
ne sont actuellement pas inclus dans ce tableau ; vous pouvez utiliser Rabby ou MetaMask prenant en charge la chaîne cible. Les adresses EVM peuvent être identiques sur différentes chaînes,
mais les soldes sont indépendants les uns des autres, et les adresses Solana ne s'appliquent pas à l'USDC EVM.
Voir le [tableau de prise en charge du portefeuille Phantom](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### Point d'entrée de déploiement progressif des nouveaux réseaux

Les points d'entrée des nouvelles chaînes sont masqués par défaut. Lors de l'accès à la console ou à Studio, vous pouvez utiliser `?features=x402-arbitrum`
pour activer la chaîne correspondante, plusieurs flags étant séparés par des virgules. Pour désactiver une seule chaîne, utilisez `?features=-x402-arbitrum`,
et pour effacer le remplacement local, utilisez `?features=none`. Les interrupteurs sont enregistrés séparément pour chaque domaine.
Les devis de commande et les tentatives de paiement utilisent le même interrupteur, le serveur effectuant une validation indépendante ; les enregistrements de paiement existants restent consultables.
L'activation du seul flag de page n'activera pas une chaîne qui n'est pas encore configurée, et les réseaux effectivement payables restent déterminés par les `accepts` en temps réel.
