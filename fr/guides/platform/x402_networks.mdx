Ace Data Cloud X402 effectue actuellement les règlements autour de l'USDC et prend en charge deux types de chaînes : EVM et Solana. Les méthodes de signature, les adresses d'actifs, le comportement du gas et les scénarios applicables diffèrent selon les réseaux ; vous devez choisir le réseau avant l'intégration.

## Les identifiants réseau utilisent CAIP-2

Le `accepts[].network` de x402 v2 est un identifiant CAIP-2, et non une forme abrégée telle que `base` ou `skale`. Le client doit comparer les réseaux selon la chaîne CAIP-2 :

| Réseau             | Identifiant CAIP-2                         |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| SKALE Base     | `eip155:1187947933`                       |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Matrice de prise en charge

| Réseau     | scheme  | Actif                  | Méthode de signature                                 | Scénario applicable                        |
| ------ | ------- | ------------------- | ------------------------------------ | --------------------------- |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Recommandé par défaut, prise en charge mature des portefeuilles et de la liquidité.            |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | API à comptage différé telles que le chat et les modèles.             |
| SKALE  | `exact` | USDC bridgé SKALE  | EIP-3009 `TransferWithAuthorization` | Faible coût de gas, adapté à la vérification des paiements EVM et aux appels à faible coût. |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Portefeuilles Solana, Agent ou scénarios d'applications on-chain.    |

`upto` n'est actuellement disponible que sur Base. Les éléments réellement disponibles dépendent des `accepts` renvoyés par l'API. Vous pouvez également consulter le Facilitator :

```bash
curl https://facilitator.acedata.cloud/supported
```

Le retour du Facilitator `/supported` :

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    { "x402Version": 2, "scheme": "exact", "network": "eip155:1187947933" },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Explication des résultats :

- Les `exact` de Base, SKALE et Solana sont des parcours de paiement à montant fixe.
- Seul Base fournit le parcours de comptage différé `upto`, qui dépend de l'approbation Permit2.
- L'`extra.facilitatorAddress` dans l'entrée `upto` est l'adresse que le client doit inscrire dans le witness lors de la signature ; elle doit être identique à la valeur renvoyée par le serveur.

## Base

Base utilise le contrat USDC officiel :

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

Dans le schéma `exact`, le client signe EIP-712 `TransferWithAuthorization`. Le contenu de la signature comprend :

- `from` : l'adresse du portefeuille payeur
- `to` : l'adresse de réception d'Ace Data Cloud
- `value` : le montant de ce paiement
- `validAfter` / `validBefore` : la fenêtre de validité de la signature
- `nonce` : un nonce aléatoire de 32 octets

Après avoir vérifié la signature, le Facilitator appelle `transferWithAuthorization` d'USDC on-chain pour effectuer le transfert.

Base est le réseau d'intégration en production le plus recommandé, particulièrement adapté au comptage différé `upto`, car l'écosystème Permit2, USDC et des portefeuilles y est plus mature.

Exemple de résultat de vérification Base `exact` :

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Explication des résultats :

- Le paid retry de l'API renvoie le contenu du modèle `ADC_BASE_E2E_OK`.
- La transaction on-chain est consultable sur BaseScan, et le numéro de bloc est `46726299`.
- `95215` atomic USDC correspond à `0.095215` USDC, ce qui est le montant réel réglé pour cet appel API.

Résultat d'exécution du programme pour le paiement de commande Base `exact` :

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Explication des résultats :

- L'état final de la commande de la plateforme est `Finished`.
- Le `pay_id` de la commande inscrit le même hachage de transaction Base.
- `1200000` atomic USDC correspond à `1.2` USDC, qui est le montant historique réellement payé pour cette commande de 10 Credits sous l'ancienne politique ; les nouvelles commandes ne bénéficient plus d'une réduction supplémentaire pour le mode de paiement X402, et le montant spécifique signé dépend de la réponse 402 actuelle.

## SKALE

SKALE utilise de l'USDC bridgé, avec une méthode de signature similaire à celle de Base, également EIP-3009. Il est adapté aux scénarios de paiement EVM à faible coût de gas ; les appels réels dépendent toujours des `accepts` renvoyés par l'API.

Les `accepts` 402 typiques de SKALE incluent :

```json
{
  "network": "eip155:1187947933",
  "scheme": "exact",
  "extra": {
    "name": "Bridged USDC (SKALE Bridge)",
    "version": "2",
    "chainId": 1187947933,
    "verifyingContract": "0x85889c8c714505E0c94b30fcfcF64fE3Ac8FCb20"
  }
}
```

SKALE ne fournit actuellement que `exact`. Si vous avez besoin d'un comptage différé, utilisez Base `upto`.

Exemple de résultat de vérification SKALE `exact` :

```text
content ADC_SKALE_E2E_OK
tx 0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
block 1969317
explorer https://skale-base-explorer.skalenodes.com/tx/0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
paid 0.095215 USDC
```

Explication des résultats :
- La relance API payante renvoie le contenu du modèle `ADC_SKALE_E2E_OK`。
- La transaction est consultable dans l’explorer SKALE, le numéro de bloc est `1969317`。
- Le montant de règlement de ce paiement `exact` est de `0.095215` USDC。

## Solana

Solana utilise SPL USDC `TransferChecked`。Le client construit une transaction de transfert, la signe et la soumet, puis place la signature de la transaction ou la transaction sérialisée dans l’enveloppe `PAYMENT-SIGNATURE`。

Caractéristiques de Solana：

- utilisation de Solana wallet adapter ou d’une clé secrète base58；
- l’actif est le mint USDC Solana；
- seul `exact` est actuellement pris en charge；
- le Facilitator vérifie le mint, la destination, l’authority et le amount de l’instruction de transfert。

Si le mode wallet fee payer est utilisé, le wallet soumet directement la transaction, et le Facilitator est responsable de confirmer la transaction et de renvoyer le résultat de règlement。

Exemple de résultat de vérification Solana `exact`：

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Explication des résultats：

- La relance payante a déjà renvoyé HTTP 200, et le modèle a produit `ADC_SOLANA_E2E_OK`。
- La consultation de la signature on-chain via le RPC public peut rencontrer une limitation de débit。
- Comme les requêtes RPC publiques peuvent être limitées, l’explorer Solana n’est pas indiqué ici。Lorsqu’un rapprochement strict est nécessaire, veuillez utiliser votre propre RPC Solana ou les enregistrements de règlement côté plateforme pour confirmer la signature de la transaction。

## Comment choisir

| Ce que vous voulez faire | Réseau recommandé |
| ------------ | ---------------------------- |
| Valider rapidement le flux minimal | SKALE `exact` ou Base `exact` |
| S’adresser aux utilisateurs Web3 ordinaires | Base |
| Effectuer une mesure a posteriori pour les complétions de chat, etc. | Base `upto` |
| Application de l’écosystème Solana | Solana `exact` |
| Validation de paiement EVM à faible coût | SKALE `exact` |

Quel que soit le réseau choisi, ne codez pas le prix en dur dans le client。Le prix est déterminé par `accepts[].maxAmountRequired` renvoyé par le serveur。

## Nouveaux réseaux EVM

Les paiements à montant fixe en USDC natif des réseaux suivants bénéficient d’une prise en charge dans le code, et sont activés réseau par réseau。
La disponibilité dépend de `accepts` renvoyé par la commande ou l’API ; cela ne signifie pas que tous les réseaux sont activés en production。

| Réseau | Alias | CAIP-2 | USDC natif |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

Ces réseaux prennent uniquement en charge `exact`, avec une précision monétaire de 6。N’utilisez pas l’USDC bridgé portant le même nom。
Lors de l’utilisation du X402 Client officiel TypeScript/Python, vous pouvez transmettre l’abréviation du tableau ou l’identifiant CAIP-2。
Le client utilise l’ID de la chaîne cible pour construire la signature ; le wallet doit prendre en charge le réseau cible。

Le tableau officiel de prise en charge du wallet d’extension Phantom liste Arbitrum et Polygon ; Optimism et Avalanche
ne sont actuellement pas inclus dans ce tableau, vous pouvez utiliser Rabby ou MetaMask qui prend en charge la chaîne cible。Les adresses EVM peuvent être identiques sur différentes chaînes,
mais les soldes sont indépendants les uns des autres, et les adresses Solana ne s’appliquent pas à l’USDC EVM。
Voir le [tableau de prise en charge du wallet Phantom](https://docs.phantom.com/wallet-sdks-overview#chain-support)。

### Point d’entrée de déploiement progressif des nouveaux réseaux

Les entrées des nouvelles chaînes sont masquées par défaut。Lors de l’accès à la console ou à Studio, vous pouvez utiliser `?features=x402-arbitrum`
pour activer la chaîne correspondante, et séparer plusieurs flags par des virgules。Pour désactiver une seule chaîne, utilisez `?features=-x402-arbitrum`，
et pour effacer les surcharges locales, utilisez `?features=none`。Les commutateurs sont enregistrés séparément pour chaque domaine。
Le devis de commande et la relance de paiement utilisent le même commutateur, et le serveur effectue une vérification indépendante ; les enregistrements de paiement existants restent consultables。
L’activation du seul flag de page n’active pas une chaîne qui n’est pas encore configurée, les réseaux réellement payables dépendent toujours de `accepts` en temps réel。
