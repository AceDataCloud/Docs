---
title: "Configurer le partage global du solde d’AceDataCloud Application"
description: "Platform API guide - Ace Data Cloud"
---

Configurez `allow_consume_global`. Une fois activé, les Applications à l’usage éligibles peuvent continuer à utiliser le solde global du compte lorsque leur propre solde est insuffisant.

## Préparatifs

- Créez et conservez de manière sécurisée un [Account Token](https://platform.acedata.cloud/documents/platform-token).
- Obtenez l’`application_id` que vous possédez depuis la [liste des demandes de services](https://platform.acedata.cloud/documents/platform-application-list).

```shell
export PLATFORM_TOKEN='votre jeton de compte'
export APPLICATION_ID='votre Application ID'
```

## Aperçu de l’API

| Élément    | Contenu                                                                                            |
| ---- | -------------------------------------------------------------------------------------------------- |
| Méthode   | `POST`                                                                                             |
| URL  | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| Authentification   | Account Token                                                                                      |
| Body | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

En cas de succès, l’objet Application mis à jour est renvoyé. Veuillez vous référer à `allow_consume_global` dans la réponse, plutôt que de supposer que la valeur demandée a nécessairement été enregistrée.

> Les Applications de type `Period` ne sont pas autorisées à consommer le solde global. Même si vous demandez `true`, le serveur conservera ce champ à `false`.

## Gestion des erreurs

- `401` : Account Token invalide ou manquant.
- `403` : le compte actuel n’est pas le propriétaire de cette Application.
- `404` : l’Application ID n’existe pas.

Le point d’entrée pour recharger le solde global et les forfaits disponibles sont déterminés par la console de la plateforme et les forfaits réels renvoyés par la [création de commande](https://platform.acedata.cloud/documents/platform-order-create) ; ne supposez pas qu’un forfait de type `Wallet` existe.

## Applications autorisées au découvert

Lorsque le champ en lecture seule `allow_overdraft=true` d’une Application à l’usage est défini, cette Application peut continuer à débiter son propre solde, même si celui-ci devient négatif, et ne basculera pas vers le compte global en raison d’un solde insuffisant. Les Applications sans découvert activé continuent de suivre `allow_consume_global` ; après le basculement, l’autorisation du découvert dépend de la configuration de l’Application globale réellement débitée.

## Limite de concurrence des comptes d’essai

Le système utilise le marqueur utilisateur en lecture seule `has_recharged` pour indiquer si une recharge payante a déjà été effectuée avec succès ou si des crédits ont été ajoutés manuellement par un administrateur. Le marqueur est mis à jour après la réussite de l’opération, et les utilisateurs historiques seront complétés de manière uniforme selon les commandes ou les enregistrements explicites d’ajout de crédits. Pour les comptes qui n’ont ni effectué de recharge payante ni reçu de crédits ajoutés manuellement par un administrateur, un seul appel facturable est autorisé à s’exécuter simultanément pour l’ensemble du compte ; les différentes API Keys et les différents services partagent cette unique place. Les récompenses, cartes d’échange et crédits transférés ne sont pas considérés comme des recharges payantes. Les comptes ayant déjà effectué une recharge payante ou reçu des crédits ajoutés manuellement par un administrateur ne sont pas soumis à cette limite de concurrence d’essai et continuent de suivre les vérifications existantes du solde et des quotas d’identifiants.

Lorsqu’une requête existante est en cours d’exécution, les nouvelles requêtes renvoient `429 too_many_requests`. Les interfaces gratuites d’interrogation, telles que la consultation des tâches, peuvent toujours être appelées normalement. L’authentification de connexion Realtime continue d’utiliser le processus existant de facturation par tour et n’occupe pas cette place de requête ordinaire.

Lorsqu’une interface asynchrone renvoie « accepté », la tâche est toujours en cours d’exécution ; vous devez attendre le résultat final avant d’envoyer la prochaine requête de génération. Une déconnexion réseau ou un délai d’expiration du proxy ne signifie pas que la tâche s’est arrêtée ; si une tâche ne présente pas d’état final pendant une longue période, veuillez fournir le `trace_id` et contacter le support pour vérification.

Cette limitation ne modifie pas les interfaces pouvant être essayées, ni les règles de facturation existantes. Les frais sont toujours réglés selon l’utilisation réelle après la fin de la requête.
