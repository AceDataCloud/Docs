Créez ou actualisez une session de paiement pour une commande `Pending`. L’action de paiement accède aux canaux de paiement et peut modifier l’état de la commande ; avant l’appel, vous devez confirmer l’ID de la commande, le montant et le mode de paiement.

## Aperçu de l’interface

| Élément    | Contenu                                                             |
| ---- | -------------------------------------------------------------- |
| Méthode   | `POST`                                                         |
| URL  | `https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/` |
| Authentification   | Les paiements par redirection hébergée peuvent être anonymes ; les autres méthodes nécessitent une session de connexion ou un Account Token                            |
| Body | JSON, les commandes non payées doivent fournir `pay_way`                                       |

## Limites du paiement anonyme

L’accès anonyme est destiné aux scénarios où la session de connexion est perdue après l’ouverture d’un lien de paiement copié ; il ne nécessite pas et ne doit pas inclure d’Account Token à long terme. Les appels anonymes :

- n’autorisent que les modes de paiement par redirection hébergée configurés côté serveur ;
- utilisent systématiquement la page de paiement sur ordinateur ;
- ne peuvent pas réclamer les commandes à prix zéro ;
- sont soumis à une limitation de débit par IP et par commande ;
- renvoient une projection minimale de la commande, sans compte, Application ni metadata interne.

Les appelants authentifiés doivent être le propriétaire de la commande ou un super administrateur. Les méthodes nécessitant un contexte utilisateur, telles que X402 et l’échange de récompenses, ne peuvent pas être appelées anonymement.

## Exemples de requêtes

```shell
export ORDER_ID='votre ID de commande Pending'

curl -X POST \
  "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}/pay/" \
  -H 'Content-Type: application/json' \
  -d '{"pay_way":"Stripe"}'
```

Modes de paiement nécessitant une authentification :

```shell
export PLATFORM_TOKEN='votre jeton de compte'

curl -X POST \
  "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}/pay/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"pay_way":"X402"}'
```

`pay_way` utilise les valeurs réelles prises en charge par le modèle de commande, par exemple `WechatPay`, `AliPay`, `Stripe`, `Card`, `Airwallex`, `X402`, `PayPal`, `AppleIAP`, `Reward`, `BankTransfer`. Toutes les valeurs ne sont pas disponibles pour les requêtes anonymes ou sur chaque site.

## Description de la réponse

Une réponse réussie est l’objet commande mis à jour, qui fournit généralement l’entrée de l’étape suivante via `pay_url` ; selon le mode de paiement, elle peut également renvoyer dans des champs contrôlés les informations nécessaires au client pour poursuivre le paiement. La réponse anonyme utilise une liste blanche minimale de champs, tandis que le propriétaire authentifié obtient les détails complets.

Ne vous fiez pas aux anciens noms de champs tels que `payment_url`, `qr_code_url` ou `payment_method` ; le contrat Order actuel utilise `pay_url` et `pay_way`.

## Virement bancaire

Les comptes personnels et les comptes professionnels connectés peuvent tous utiliser `BankTransfer`, sans nécessiter de vérification d’entreprise. Les virements en RMB nationaux et les virements internationaux en USD exigent tous que le montant de la commande soit d’au moins 300 USD ; le montant payable en RMB est basé sur le montant affiché au moment du paiement.

Avant le paiement, vous pouvez interroger les itinéraires de virement disponibles et les seuils de montant pour la commande actuelle via `GET /api/v1/orders/{order_id}/payment-options/`. Les virements bancaires doivent être initiés après connexion par le propriétaire de la commande, et sont soumis à la configuration des canaux de réception et au champ d’application des forfaits ; les requêtes anonymes ne peuvent pas les utiliser.

## Achats intégrés iOS

Le propriétaire connecté de la commande peut transmettre `pay_way: "AppleIAP"`. Cette requête met à jour la commande en attente de paiement selon `metadata.apple_price` du forfait sélectionné et supprime les remises ; elle ne génère aucun débit, n’attribue aucun crédit et ne renvoie aucun lien de paiement. Les anciennes commandes en attente de paiement doivent d’abord effectuer cette étape, puis initier le paiement natif Apple. Seul un forfait Usage disposant d’un produit Apple et d’un prix configurés est pris en charge ; les forfaits non pris en charge ou les commandes groupées renvoient `400`.

Après le paiement natif Apple, soumettez `transaction_id` via `/api/v1/orders/{id}/apple-verify/` pour terminer la vérification côté serveur et l’attribution des crédits. Le nombre de crédits provient du forfait ; le montant utilise le prix prédéfini indépendant en USD d’Apple, sans cumul de remise membre ni de majoration du site, et le montant débité en devise locale dans les autres régions est déterminé par la page de confirmation Apple.

## Erreurs et nouvelles tentatives

- La commande n’est pas `Pending` : renvoie `400` ; ne recréez pas de session de paiement.
- `pay_way` n’est pas fourni : une commande d’un montant non nul renvoie `400`.
- Un appel anonyme utilise une méthode non autorisée ou une commande à prix zéro : renvoie `403`, reconnectez-vous puis réessayez en tant que propriétaire.
- L’appelant est authentifié mais n’est pas le propriétaire de la commande : renvoie `403`.
- Échec du canal de paiement : ne soumettez pas à nouveau aveuglément ; interrogez d’abord les détails de la commande, confirmez qu’elle est toujours `Pending`, puis réessayez.
