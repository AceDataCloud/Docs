X402 est un protocole de paiement on-chain basé sur HTTP `402 Payment Required`. Grâce à la capacité X402 d’Ace Data Cloud, les appelants peuvent ne pas créer d’API Token, ne pas prérecharger le solde de leur compte, et effectuer directement un paiement on-chain en USDC dans chaque requête API.

Cet ensemble de documents est organisé selon l’ordre réel d’intégration : exécutez d’abord une requête minimale, puis intégrez le SDK, et comprenez ensuite les réseaux, les modèles de facturation, le paiement des commandes et le Facilitator. ## Parcours d’intégration recommandé

Si vous souhaitez seulement appeler l’API Ace Data Cloud, privilégiez le SDK officiel :

- TypeScript : `@acedatacloud/sdk` + `@acedatacloud/x402-client`
- Python : `acedatacloud` + `acedatacloud-x402`

Code source public et adresses des packages :

| Projet                 | Adresse                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| SDK Ace Data Cloud | [https://github.com/AceDataCloud/SDK](https://github.com/AceDataCloud/SDK)                                         |
| Client X402        | [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)                           |
| Facilitator X402   | [https://github.com/AceDataCloud/FacilitatorX402](https://github.com/AceDataCloud/FacilitatorX402)                 |

| SDK PyPI           | [https://pypi.org/project/acedatacloud/](https://pypi.org/project/acedatacloud/)                                   |
| Client X402 PyPI   | [https://pypi.org/project/acedatacloud-x402/](https://pypi.org/project/acedatacloud-x402/)                         |

Le SDK effectuera automatiquement ces étapes : première requête non authentifiée, analyse de `402 Payment Required`, appel du payment handler et nouvelle tentative avec `PAYMENT-SIGNATURE`. Vous devez seulement préparer un portefeuille contenant des USDC et choisir le réseau que vous souhaitez utiliser.

Si vous souhaitez également permettre à votre propre API d’accepter des paiements X402, vous devez lire la documentation du Facilitator afin de comprendre la relation entre `paymentRequirements`, `paymentPayload`, `/verify` et `/settle`.

## État de prise en charge

Ace Data Cloud X402 a été validé sur les API publiques, les SDK officiels, le Facilitator et le flux de règlement on-chain. Le tableau ci-dessous récapitule l’état actuel selon les dimensions de capacité les plus couramment utilisées lors de l’intégration par les développeurs.

| Capacité                       | État                  | Description                                                                 |
| ------------------------ | ------------------- | ------------------------------------------------------------------ |
| Capacités du Facilitator | Disponible                  | `https://facilitator.acedata.cloud/.well-known/x402` renvoie les réseaux de paiement et les points de terminaison du protocole.  |
| API 402 `accepts`        | Disponible                  | Les requêtes non payées renvoient les payment requirements disponibles pour Base et Solana.                    |
| SDK TypeScript           | Disponible                  | `@acedatacloud/sdk` et `@acedatacloud/x402-client` peuvent gérer automatiquement 402, la signature et les nouvelles tentatives. |
| SDK Python               | Disponible                  | `acedatacloud` et `acedatacloud-x402` peuvent gérer automatiquement 402, la signature et les nouvelles tentatives.              |
| Base `exact`             | Validé on-chain               | Adapté aux API à montant fixe et au paiement des commandes.                                                  |
| Base `upto`              | Validé on-chain               | Adapté aux API à mesure postérieure telles que la complétion de chat ; c’est actuellement le seul réseau fournissant `upto`.                                 |
| Solana `exact`           | Nouvelle tentative HTTP payante validée | La nouvelle tentative API payante et les réponses de modèle ont été validées ; il est recommandé d’utiliser votre propre RPC Solana pour le rapprochement des confirmations de signature on-chain.               |
| Paiement des commandes                     | Validé on-chain               | Le paiement de commande Base `exact` a effectué le règlement on-chain et mis à jour l’état de la commande.                                   |

Remarques :

- Les paquets npm et PyPI ont tous été installés et importés avec succès dans un environnement propre.
- Les requêtes API non payées renvoient 402, et `accepts` contient les méthodes de paiement disponibles pour Base et Solana.
- `accepts[].network` est un identifiant CAIP-2 ; le client doit effectuer la sélection du réseau en faisant correspondre la chaîne CAIP-2.

## Points d'attention pour l'intégration

Lors de l'intégration, les développeurs doivent prioritairement prêter attention aux exigences de paiement en temps réel renvoyées par la requête actuelle, plutôt que de copier les montants ou adresses d'exemple de la documentation :

- `accepts[].maxAmountRequired` est le montant maximal pouvant être signé pour la requête actuelle.
- `accepts[].asset` est le contrat USDC ou le mint à utiliser pour cette requête.
- `accepts[].extra.chainId`, `accepts[].extra.facilitatorAddress` et `accepts[].extra.verifyingContract` participent à la signature des données typées EVM.
- `upto` nécessite que le portefeuille autorise d'abord Permit2 pour l'USDC de la chaîne cible ; en l'absence d'autorisation, `PERMIT2_ALLOWANCE_REQUIRED` sera renvoyé.
- Si vous souhaitez explicitement utiliser la facturation a posteriori, transmettez `preferScheme: 'upto'` dans le SDK TypeScript ; sinon, le SDK sélectionnera la première requirement disponible renvoyée par le serveur sur ce réseau.

## Portée pouvant être vérifiée publiquement

Avant l'intégration, vous pouvez d'abord vérifier ces points d'entrée publics et comportements des SDK :

- Les requêtes API sans `Authorization` ou `PAYMENT-SIGNATURE` renvoient `402 Payment Required` ; les `accepts` dans la réponse constituent l'unique base de signature pour cette requête.
- Le SDK TypeScript et le SDK Python fournissent tous deux un payment handler ; après réception d'un 402, la couche de transport du SDK appellera le handler et effectuera une nouvelle tentative.
- `https://facilitator.acedata.cloud/.well-known/x402` : renvoie les réseaux, schemes et points de terminaison de protocole pris en charge par le Facilitator ; le prix de l'API reste basé sur le 402 renvoyé en temps réel par la requête cible.
- `https://facilitator.acedata.cloud/supported` : renvoie les réseaux et schemes pris en charge par le Facilitator.
- Le dépôt X402Client contient des outils avancés de vérification on-chain, qui peuvent être utilisés pour confirmer les comportements de signature, de nouvelle tentative et de settlement ; la sortie des outils ne remplace pas les `accepts` renvoyés par l'API en ligne.

`upto` relève du règlement par facturation a posteriori, adapté aux API telles que les complétions de chat et les appels de modèles, dont l'utilisation réelle n'est connue qu'après la réponse. Actuellement, seule Base fournit `upto` ; si la vérification de signature échoue, vérifiez que le chain id, l'adresse du facilitator, le spender, le contrat USDC et l'allocation Permit2 correspondent à la réponse 402.
