---
title: "Schémas de facturation X402 `exact` et `upto`"
description: "Platform API guide - Ace Data Cloud"
---

Ace Data Cloud X402 utilise actuellement deux types de schéma : `exact` et `upto`. Ils résolvent des problèmes de facturation différents.

## `exact`

`exact` indique que le prix de cette requête peut être déterminé avant son entrée dans l’API cible. Le montant signé par le client est le montant final débité.

Convient pour :

- la génération d’images à prix fixe ;
- la création de tâches vidéo à prix fixe ;
- les API de recherche ou d’outils à prix fixe ;
- le paiement de commandes.

EVM `exact` utilise USDC EIP-3009 `TransferWithAuthorization` :

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": {
    "authorization": {
      "from": "0x...",
      "to": "0x...",
      "value": "95215",
      "validAfter": "1780237345",
      "validBefore": "1780240945",
      "nonce": "0x..."
    },
    "signature": "0x..."
  }
}
```

Le Facilitator vérifie la signature et le montant à l’étape `/verify`, puis soumet cette autorisation on-chain à l’étape `/settle`.

## `upto`

`upto` indique que le client autorise un plafond maximal ; Ace Data Cloud règle selon l’utilisation réelle après la fin de la requête, et le montant réellement débité ne peut pas dépasser le plafond.

Convient pour :

- les complétions de chat : le prix final dépend des tokens du prompt et des tokens de complétion ;
- les réponses en streaming : la longueur réelle de sortie n’est connue qu’à la fin ;
- les futures API de mesure a posteriori.

`upto` utilise Permit2 `PermitWitnessTransferFrom`. Ce que le client signe n’est pas un transfert fixe, mais une autorisation de plafond avec witness :

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2Authorization": {
      "from": "0x...",
      "spender": "0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002",
      "nonce": "123456789",
      "deadline": "1780240945",
      "permitted": {
        "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "amount": "95215"
      },
      "witness": {
        "to": "0x...",
        "facilitator": "0x...",
        "validAfter": "1780237345"
      }
    },
    "signature": "0x..."
  }
}
```

`permitted.amount` est le plafond, et n’est pas nécessairement le montant final débité. Le Gateway convertit l’utilisation réelle en `amount` à l’étape `/record` et le transmet au Facilitator. Le Facilitator autorise uniquement le règlement lorsque `amount &lt;= permitted.amount`.

Résultat d’exécution du programme Base `upto` :

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
elapsed_ms 5104
content ADC_BASE_UPTO_OK
id chatcmpl-DlcbyS4IT8kUAMo4Ri97HiIHc9T8V
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Explication :

- Le plafond d’autorisation renvoyé dans le 402 est de `95215` atomic USDC, et le client signe selon ce plafond.
- Après la réponse effective du modèle, seuls `3` atomic USDC sont réglés ; la transaction on-chain peut être consultée sur BaseScan.
- Ce résultat démontre la différence clé de `upto` : le montant signé est un plafond, et le settlement on-chain peut être inférieur au plafond.
- Si l’utilisation réelle dépasse le plafond, le Facilitator doit refuser le settlement, et le client doit réautoriser selon un plafond plus élevé.

`upto` est actuellement fourni uniquement sur Base. Lorsque vous avez besoin d’une mesure a posteriori, veuillez utiliser Base.

## Pourquoi un approve Permit2 est nécessaire

`upto` récupère finalement les USDC depuis le portefeuille payeur via Permit2 par l’intermédiaire du proxy x402. Avant la première utilisation, le portefeuille payeur doit accorder une allowance ERC-20 unique à Permit2.

CLI Python :

```bash
pip install 'acedatacloud-x402[cli]'
X402_PRIVATE_KEY=0x... acedatacloud-x402 approve-permit2 --network base
```

Par programmation :

```python
from acedatacloud_x402 import EVMAccountSigner, approve_permit2

approve_permit2(
    rpc_url="https://mainnet.base.org",
    signer=EVMAccountSigner.from_private_key("0x..."),
    token_address="0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
)
```

Une fois l’autorisation terminée, chaque requête doit toujours signer une nouvelle enveloppe `upto`, car le nonce, la deadline, le witness et le plafond du montant sont tous différents.

## Règlement à montant zéro

`upto` prend en charge les cas où le montant réel est de 0. Par exemple, si l’API cible ne produit pas avec succès une utilisation facturable, le Gateway peut transmettre `amount = "0"`. Le Facilitator renverra un succès, mais n’émettra pas de transaction on-chain.

Cela permet d’éviter le problème consistant à « payer des frais on-chain alors que la requête n’a pas réussi ».

## Recommandations de choix

| Scénario                   | Recommandation                       |
| -------------------------- | ------------------------------------ |
| API à prix fixe            | Utilisez `exact`, la logique est simple. |
| Paiement de commande       | Utilisez `exact`.                    |
| Complétions de chat, facturation au token | Utilisez Base `upto`.                |
| Permit2 approve pas encore effectué | Utilisez d’abord `exact`, puis passez à `upto`. |

Si vous ne savez pas lequel choisir, utilisez d’abord le comportement par défaut du SDK ; le SDK sélectionnera la payment requirement du réseau correspondant renvoyée par le serveur.

## Liste de vérification Base `upto`

Lors de l’intégration ou du dépannage, veuillez confirmer que les paramètres suivants proviennent de la même réponse 402 et restent cohérents lors de la signature côté client :

| Paramètre                  | Point de vérification                                          |
| -------------------------- | ------------------------------------------------------------ |
| `network`                  | Doit être `eip155:8453`.                                     |
| `scheme`                   | Doit être `upto`.                                            |
| `extra.chainId`            | Le chain id de Base est `8453`.                              |
| `asset`                    | Utilisez l’adresse du contrat USDC Base de la réponse 402.   |
| `extra.facilitatorAddress` | Doit participer au witness et correspondre à `/supported` du Facilitator. |
| Permit2 allowance          | Le portefeuille payeur doit d’abord autoriser Permit2 pour l’USDC Base. |

Erreurs courantes et méthodes de traitement :

| Erreur                                        | Méthode de traitement                                                                          |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `invalid_upto_evm_payload_invalid_signature`  | Vérifiez que le chain id, l’adresse du facilitator, le domaine Permit2, le spender, le compte de signature et le witness correspondent à la réponse 402. |
| `PERMIT2_ALLOWANCE_REQUIRED`                  | Exécutez Permit2 approve pour l’USDC de la chaîne cible, puis relancez la requête.             |
| `amount exceeds permitted amount`             | L’utilisation réelle dépasse le plafond signé ; vous devez signer de nouveau avec un plafond plus élevé. |
