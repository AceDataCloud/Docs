---
title: "Actualiser le statut d’une commande sur la plateforme AceDataCloud"
description: "Platform API guide - Ace Data Cloud"
---

Interrogez activement le dernier statut du moyen de paiement correspondant à la commande et synchronisez-le avec la plateforme. Cette requête peut accéder au service de paiement et modifier le statut de la commande ; utilisez-la uniquement en cas de retard du callback ou lorsqu’une confirmation immédiate est nécessaire.

## Préparation

- Utilisez le [Account Token](https://platform.acedata.cloud/documents/platform-token).
- Obtenez votre ID de commande depuis la [liste des commandes](https://platform.acedata.cloud/documents/platform-order-list).

```shell
export PLATFORM_TOKEN='你的账户令牌'
export ORDER_ID='你的订单 ID'
```

## Aperçu de l’interface

| Élément    | Contenu                                                            |
| -------- | ------------------------------------------------------------------ |
| Méthode   | `POST`                                                             |
| URL      | `https://platform.acedata.cloud/api/v1/orders/{order_id}/refresh/` |
| Authentification   | Propriétaire de la commande ou super administrateur                                                        |
| Body | Généralement vide ; le scénario de callback PayPal peut nécessiter `payer_id` / `PayerID`                         |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}/refresh/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

En cas de succès, l’objet Order complet actualisé est renvoyé. Utilisez `state` pour déterminer le résultat, et `finished_at` comme heure de finalisation ; le modèle actuel ne possède pas de champ `paid_at`. Les valeurs de statut incluent `Pending`, `Paid`, `Finished`, `Expired`, `Failed`, `Refunded`.

La date limite de paiement ne fait passer en `Expired` que les commandes toujours à l’état `Pending`. Les commandes `Refunded` déjà remboursées restent à l’état remboursé après une actualisation ou la réception d’un callback de paiement tardif.

## Recommandations de nouvelle tentative

- Pour les paiements normaux, privilégiez les callbacks de la plateforme ; n’effectuez un refresh actif que lorsque le statut ne se met pas à jour pendant longtemps.
- N’effectuez pas de polling fréquent fixe. Il est recommandé d’utiliser un backoff exponentiel et de s’arrêter après avoir atteint un état final explicite.
- `401` indique que le jeton est invalide ; `403` indique que vous n’êtes pas le propriétaire de la commande ; `404` indique que la commande n’existe pas.
- En cas d’échec de la requête vers le service de paiement, conservez l’ID de commande et l’ID de trace, puis réessayez plus tard ; ne créez pas de commandes dupliquées pour remplacer la confirmation de statut.
