Ce tutoriel utilise une requête API minimale pour expliquer le processus complet d’Ace Data Cloud X402. L’objectif n’est pas d’écrire d’abord du code complexe, mais de comprendre d’abord : pourquoi la première requête renvoie 402, ce que contient `accepts`, et comment `PAYMENT-SIGNATURE` transforme la même requête API en requête payée.

## Préparatifs

Vous devez préparer :

| Élément   | Description                                                   |
| ---- | ---------------------------------------------------- |
| Portefeuille   | Un portefeuille prenant en charge le réseau cible. Base utilise un portefeuille EVM, Solana utilise un portefeuille Solana.      |
| USDC | Le portefeuille doit contenir suffisamment d’USDC. Le montant réel est déterminé par `maxAmountRequired` dans la réponse 402. |
| Environnement de développement | Node.js 18+ est recommandé pour TypeScript ; Python 3.10+ est recommandé pour Python.    |
| SDK  | Il est recommandé d’utiliser le SDK officiel ; il n’est pas conseillé d’écrire manuellement les détails de signature.                                |

Aucun API Token n’est requis lors de l’appel de l’API Ace Data Cloud avec X402. La première requête du SDK ne contient pas `Authorization`, Gateway renvoie `402 Payment Required` et les exigences de paiement ; le SDK réessaie automatiquement après signature.

## Installer le SDK

Sources et adresses des paquets :

- Dépôt SDK : [https://github.com/AceDataCloud/SDK](https://github.com/AceDataCloud/SDK)
- Dépôt X402 Client : [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)
- npm : `@acedatacloud/sdk`、`@acedatacloud/x402-client`
- PyPI : `acedatacloud`、`acedatacloud-x402`

TypeScript :

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client ethers
```

Python :

```bash
pip install acedatacloud acedatacloud-x402
```

Pour utiliser Solana, vous devez également installer les dépendances correspondantes :

```bash
npm install @solana/web3.js
```

La dépendance du signer Solana pour la version Python est déjà incluse dans `acedatacloud-x402`.

La sortie de vérification de l’installation et des imports dans un environnement temporaire propre :

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
ethers@6.16.0
@solana/web3.js@1.98.4

usage: acedatacloud-x402 [-h] {approve-permit2} ...
```

Explication des résultats :

- Les paquets npm et PyPI sont tous deux des paquets réellement publiés, et non des noms fictifs dans la documentation.
- `acedatacloud-x402[cli]` installe la CLI, et la sous-commande `approve-permit2` peut être utilisée pour l’autorisation Permit2 dans les scénarios `upto`.

## La première requête renvoie 402

Vous pouvez d’abord utiliser `curl` pour voir ce que renvoie une requête non payée. L’exemple ci-dessous ne générera aucun débit, car il ne contient pas `PAYMENT-SIGNATURE` :

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Le corps de la réponse contient un tableau `accepts`, avec une structure courante comme suit :

```json
{
  "x402Version": 2,
  "resource": {
    "url": "/openai/chat/completions",
    "description": "AceDataCloud API call",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "maxAmountRequired": "95215",
      "amount": "95215",
      "maxTimeoutSeconds": 3600,
      "resource": "/openai/chat/completions",
      "description": "...",
      "payTo": "0x...",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913"
      }
    }
  ],
  "error": "PAYMENT-SIGNATURE header is required"
}
```

Le même contenu de challenge est également placé sous forme base64 dans l’en-tête de réponse `PAYMENT-REQUIRED`, afin que le client puisse lire les exigences de paiement sans analyser le body.

Le résumé de sortie du programme pour une requête non payée à l’API de production est le suivant :

```text
status=402
x402Version 2
accepts [
  ('eip155:8453', 'exact', '95215'),
  ('eip155:8453', 'upto', '95215'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '95215'),
]
```

Explication des résultats :

- La première requête ne contient ni `Authorization` ni `PAYMENT-SIGNATURE`, elle renvoie donc HTTP 402 et ne génère aucun débit.
- `accepts` est la seule base de signature fiable pour cette requête ; il contient les réseaux disponibles, le scheme, le plafond de montant, l’adresse du bénéficiaire et l’adresse de l’actif.
- `network` est un identifiant CAIP-2 ; le client doit effectuer la correspondance du réseau selon la chaîne CAIP-2.
- Le montant maximal de cette requête de chat minimale `gpt-4o-mini` est de `95215` atomic USDC, soit `0.095215` USDC.
- Chaque requête doit lire sa réponse 402 correspondante ; n’encodez pas en dur le montant de l’exemple dans le code métier.

Signification des champs :

| Champ                  | Description                                                             |
| ------------------- | -------------------------------------------------------------- |
| `scheme`            | Schéma de paiement. `exact` indique un montant fixe, `upto` indique un plafond d’autorisation et un règlement selon l’utilisation réelle.                     |
| `network`           | Identifiant CAIP-2 du réseau de paiement, par exemple `eip155:8453`、`solana:5eykt4...`.           |
| `maxAmountRequired` | Montant maximal du paiement, en unités atomiques USDC ; `95215` correspond à `0.095215` USDC.       |
| `amount`            | Montant à régler cette fois-ci ; `exact` est identique à `maxAmountRequired`, tandis que `upto` est réécrit selon l’utilisation réelle lors de la phase de règlement. |
| `payTo`             | Adresse du bénéficiaire.                                                          |
| `asset`             | Adresse du contrat USDC ou adresse mint Solana.                                     |
| `extra`             | Informations d’extension nécessaires à la signature, telles que l’ID de chaîne, le domaine EIP-712 et l’adresse Permit2.                      |

## Effectuer une nouvelle tentative de paiement avec le SDK

Voici l’exemple TypeScript minimal. Il spécifie `network: 'base'`, et le handler sélectionne la payment requirement de Base depuis la réponse 402 de cette requête ; le montant réel et l’adresse du bénéficiaire restent déterminés par `accepts` :
```ts
import { Wallet } from 'ethers';
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') {
      throw new Error(`unsupported method: ${method}`);
    }
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const response = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly: hello' }],
  max_tokens: 8
});

console.log(response.choices[0].message.content);
```

Quatre étapes se produisent derrière ce code :

1. Le SDK envoie une requête API ordinaire, sans `Authorization`.
2. La Gateway renvoie `402 Payment Required` et `accepts`.
3. `createX402PaymentHandler` sélectionne le payment requirement de `network = 'base'` et signe `PAYMENT-SIGNATURE`.
4. Le SDK réessaie avec le même corps de requête, et la Gateway appelle le Facilitator pour vérifier et régler avant d'autoriser l'accès à l'API cible.

## Consulter les capacités prises en charge par le Facilitator

L'API X402 ne dépend pas d'un répertoire de ressources. Le client appelle directement une API connue et utilise le
`402 Payment Required` et `accepts` renvoyés en temps réel par cette requête comme seule base pour le prix et la signature.

La déclaration de capacités du Facilitator se trouve à l'adresse :

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Elle décrit uniquement `/supported`, `/verify`, `/settle` et les réseaux de paiement actuellement activés, sans répertorier les ressources API.

L'adresse du Facilitator de production d'Ace Data Cloud est :

```text
https://facilitator.acedata.cloud
```

Vous pouvez voir quels réseaux et schemes il prend en charge :

```bash
curl https://facilitator.acedata.cloud/supported
```

Les `kinds` renvoyés listent les réseaux et schemes pris en charge par le Facilitator. Lors des appels réels, référez-vous toujours aux `accepts` renvoyés par l'API.

Sortie du Facilitator `/supported` :

```text
kinds [
  ('eip155:8453', 'exact'),
  ('eip155:8453', 'upto', {'facilitatorAddress': '0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708'}),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact')
]
```

Le résultat indique :

- `/supported` indique que le Facilitator dispose de capacités de vérification et de règlement pour ces réseaux et schemes.
- Base et Solana prennent tous deux en charge `exact` ; `upto` n'est actuellement proposé que sur Base.
- La question de savoir si une API spécifique autorise un réseau donné dépend toujours des `accepts` du 402 de cette API.
