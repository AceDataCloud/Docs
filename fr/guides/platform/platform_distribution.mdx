AceDataCloud ne dispose actuellement pas d’un point de terminaison agrégé `/api/v1/distribution/`. Les données de récompense de recommandation sont composées de quatre groupes d’interfaces : statut, historique, niveau et échange ; veuillez appeler les ressources nécessaires et éviter de dépendre d’une réponse récapitulative inexistante.

## Préparatifs

1. Créez et enregistrez un Account Token dans la [console Account Token](https://platform.acedata.cloud/console/platform-tokens).
2. Utilisez `GET /api/v1/platform-tokens/me/` pour obtenir l’UUID du compte actuel.

```shell
export PLATFORM_TOKEN='你的账户令牌'
export USER_ID='你的账户 UUID'
```

## Interfaces disponibles

| Méthode     | URL                                                  | Utilisation                                   |
| ------ | ---------------------------------------------------- | ------------------------------------ |
| `GET`  | `/api/v1/distribution-statuses/?user_id=${USER_ID}`  | Montant cumulé des recommandations, récompenses et niveau du compte actuel                     |
| `POST` | `/api/v1/distribution-statuses/initialize/`          | Initialiser ou actualiser pour la première fois le niveau du compte actuel ; écrit des données                 |
| `GET`  | `/api/v1/distribution-histories/?user_id=${USER_ID}` | Historique des récompenses de recommandation                               |
| `GET`  | `/api/v1/distribution-levels/`                       | Règles des niveaux et des proportions                              |
| `GET`  | `/api/v1/distribution-redemptions/preview/`          | Prévisualiser les récompenses actuellement échangeables ; `amount` est facultatif                |
| `GET`  | `/api/v1/distribution-redemptions/`                  | Enregistrements des échanges terminés                             |
| `POST` | `/api/v1/distribution-redemptions/redeem/`           | Confirmer l’échange ; nécessite `idempotency_key` et produit un échange irréversible |

## Exemples de requêtes en lecture seule

```shell
curl --get 'https://platform.acedata.cloud/api/v1/distribution-statuses/' \
  --data-urlencode "user_id=${USER_ID}" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"

curl --get 'https://platform.acedata.cloud/api/v1/distribution-histories/' \
  --data-urlencode "user_id=${USER_ID}" \
  --data-urlencode 'limit=100' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"

curl 'https://platform.acedata.cloud/api/v1/distribution-levels/' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"

curl 'https://platform.acedata.cloud/api/v1/distribution-redemptions/preview/' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

Les formats de réponse vérifiés en ligne sont les suivants :

- status, history, level, redemption list : `{count, items}` ;
- redemption preview : un objet unique, comprenant des champs tels que `eligible`, `reason`, `reward_amount`, `credit_amount`, `credits_per_usd`, `currency`, `package`, `global_application`, etc.

Les éléments de statut et d’historique évolueront avec le contrôle des risques de recommandation, les compensations et les règles de récompense ; le client doit les lire selon les besoins et ne doit pas dépendre de champs agrégés tels que `referral_url`, `recent_orders`, `withdrawable_balance`, etc., qui ne sont pas renvoyés par l’interface dans les anciennes documentations.

> L’initialisation et l’échange sont tous deux des opérations d’écriture. Les scripts de production doivent d’abord appeler les interfaces en lecture seule pour vérifier l’état, et conserver une `idempotency_key` unique pour les requêtes d’échange ; ne réessayez pas automatiquement un échange dont le résultat est inconnu.

## Commandes avec majoration des sous-sites

Pour les commandes de sous-sites auxquelles les nouvelles règles s’appliquent, la commission de recommandation est calculée sur le prix de base après remise, tandis que la différence de majoration après remise revient intégralement au webmaster lors de la création de la commande. Les deux parties de la récompense pour le même bénéficiaire sont regroupées dans l’enregistrement de distribution d’origine, et l’historique de distribution affichera leur composition ; les commandes sans majoration et les commandes historiques conservent les anciennes règles.

Par exemple, avec un prix de base de 100 et un prix après majoration de 120, si le webmaster est également le seul recommandant et que le taux est de 10 %, la récompense de cette commande est de 10 + 20 = 30. Si le webmaster et le recommandant ne sont pas la même personne, ils obtiennent chacun la récompense correspondante.

Le règlement en espèces reste effectué manuellement par la plateforme. La plateforme procède au paiement manuel après avoir déduit du compte de récompenses d’origine le montant disponible pour cette fois ; les parties déjà échangées contre des crédits ne peuvent pas être payées une nouvelle fois en espèces. Si un déficit de récompense apparaît après un remboursement, il sera d’abord compensé par les récompenses ultérieures.
