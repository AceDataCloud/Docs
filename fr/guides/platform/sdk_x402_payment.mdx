[X402](https://www.x402.org/) est un protocole de paiement on-chain « facturé via HTTP 402 » proposé par Coinbase : le serveur renvoie `402 Payment Required` pour les requêtes sans token, avec un champ `accepts: [...]` listant les chaînes / actifs / prix acceptables ; le client signe localement une autorisation (Permit2 / EIP-712 sur EVM, autorisation de transfert de token SPL sur Solana), place l'envelope encodée en base64 dans l'en-tête `PAYMENT-SIGNATURE`, puis renvoie la requête. Après vérification, le serveur effectue réellement le règlement on-chain, puis renvoie le résultat métier.

> Le client X402 d'Ace Data Cloud appelle directement l'API cible, et utilise le `402 Payment Required` et `accepts` renvoyés en temps réel par cette requête comme base de prix et de signature. La capacité de paiement du Facilitator peut être vérifiée sur [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

`@acedatacloud/sdk` et `acedatacloud` exposent tous deux un crochet `paymentHandler` : lorsqu'une requête émise par le SDK lui-même reçoit un `402`, il appelle le handler que vous injectez pour obtenir l'en-tête `PAYMENT-SIGNATURE`, puis renvoie la requête d'origine. En combinant `@acedatacloud/x402-client` / `acedatacloud-x402` avec le SDK, **l'ensemble du processus est totalement transparent pour le code métier** — vous utilisez uniquement `client.openai.chat.completions.create(...)`, ce qui semble identique au mode token, mais le paiement s'effectue à l'appel sous-jacent, sans nécessiter de recharge préalable.

Cet article :

- parcourt réellement la chaîne « sans token + injection du handler X402 » côté TS ([validation T12](#quatre-validation-dexécution-réelle))
- liste les différences entre les deux chaînes de signature EVM / Solana
- fournit trois adaptations : mode clé privée `viem`, mode portefeuille navigateur, mode Python `EVMAccountSigner`
- clarifie le champ `preferScheme` / `prefer_scheme`, dans lequel il est facile de tomber dans un piège

## I. Vue d'ensemble du protocole (à lire absolument)

Un appel X402 réussi implique **3 RTT HTTP** :

```text
1. SDK -> /openai/v1/chat/completions               (无 Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK 内部 -> paymentHandler({ url, method, body, accepts })   (本地签名，0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (PAYMENT-SIGNATURE 头注入)
   <- 200 + business response   (结算在服务端完成)
```

L'envelope X402 est un JSON, placé dans l'en-tête `PAYMENT-SIGNATURE` après encodage en base64. Structure (extrait) :

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

La racine de l'envelope est `x402Version: 2`, et utilise l'objet `accepted` pour déclarer le `scheme` et le `network` sélectionnés pour cette fois-ci (identifiant CAIP-2).

| scheme  | Signification                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Prix fixe (scénarios tarifés tels que la génération d'images / vidéos, la recherche, etc.). Le montant signé = le montant demandé par le serveur.                                                         |
| `upto`  | Facturation mesurée (chat completions / catégorie token). Signe un montant **plafond**, et seule la partie effectivement utilisée est réglée (basé sur Permit2 + witness). **Fortement recommandé** pour les API de type session. |

`preferScheme` / `prefer_scheme` permet de sélectionner une préférence lorsque le serveur propose **simultanément plusieurs schemes**. Si le serveur n'expose que `exact`, ce champ sera ignoré ; si `upto` est défini mais que le serveur ne l'expose pas, un repli vers le premier élément correspondant aura lieu.

## II. TypeScript : deux usages, portefeuille navigateur + viem côté serveur

### Installation

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Versions testées :

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Signature complète de `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' 必填
  evmProvider?: EVMProvider;                // network='base' 必填，EIP-1193
  evmAddress?: string;                      // network='base' 必填
  preferScheme?: 'exact' | 'upto';
}
```

La valeur de retour est un `(ctx) => Promise&lt;{ headers: Record<string, string> }>`, qui correspond exactement à la signature du crochet `paymentHandler` du SDK.

### Usage 1 : navigateur (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. 让用户连钱包
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. 切到 Base 主网
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. 构造 SDK 客户端，注入 X402 handler
//    注意：不传 apiToken，让 SDK 走 402 路径
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat 类必选 upto
  })
});

// 4. 正常调
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Lors du premier appel, le navigateur affichera **deux invites de signature** : la première correspond à une approbation unique Permit2 de l'USDC (le montant est `MaxUint256`, écrit on-chain) ; la seconde est la signature EIP-712 de l'envelope X402 (elle n'est pas on-chain, elle sert seulement à la vérification du facilitator). Les appels suivants ne nécessitent que la seconde signature ; en termes d'expérience, c'est « cliquer une fois pour signer → obtenir le résultat ».

### Usage 2 : serveur Node + clé privée viem (adapté au backend / CLI)

Côté TS, `@acedatacloud/x402-client` **n'accepte que les providers EIP-1193** — il ne gère pas directement les clés privées. Dans les scénarios Node / CLI, la pratique standard consiste à utiliser [`viem`](https://viem.sh/) pour encapsuler la clé privée dans un `WalletClient`, puis à passer par l'adaptateur EIP-1193 de [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) ou interne à viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient 自带 EIP-1193 兼容的 .request()，可以直接当 evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request 满足 EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Si vous pensez que l’adaptation EIP-1193 de viem n’est pas suffisamment stable, vous pouvez aussi passer par [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts), qui est plus bas niveau, pour relier vous-même le chemin `accepts → signed envelope → PAYMENT-SIGNATURE header` et ignorer le hook SDK ; toutefois, il est tout de même recommandé de privilégier `createX402PaymentHandler`, afin d’éviter de devoir maintenir vous-même les mises à niveau du protocole.

### Utilisation 3 : Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

Sur la chaîne Solana, **seul le schéma `exact` est actuellement exposé**, donc `preferScheme` ne fonctionne pas sur Solana.

## III. Python : mode clé privée

`acedatacloud-x402` en Python suit la voie de la **signature directe avec une clé privée** (sans abstraction EIP-1193), ce qui est plus adapté aux serveurs / exécuteurs de tâches.

### Installation

```bash
pip install acedatacloud acedatacloud-x402
```

Versions testées :

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. 从私钥构造签名器
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. 构造 SDK：不传 api_token，让 SDK 走 402 路径
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # chat 类一定选 upto
    )
)

# 3. 正常调
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # 可选
    )
)
```

### Approbation unique (uniquement lors de la première utilisation EVM)

Sur EVM Base, X402 utilise Permit2, ce qui nécessite que le portefeuille effectue une fois une approbation `MaxUint256` de l’USDC au contrat Permit2. `acedatacloud-x402` intègre `approve_permit2` :

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Cette transaction ne doit être envoyée qu’une fois ; tous les paiements X402 EVM ultérieurs utiliseront cette autorisation. Solana n’en a pas besoin.

## IV. Vérification d’exécution réelle

Objectif du test : **le SDK TS ne reçoit pas de token, injecte un handler X402, et peut normalement construire et initier des requêtes** (vérification légère qui ne consomme pas de véritables USDC on-chain).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // 占位 provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Sortie :

```text
handler_type function
client_ctor_ok AceDataCloud
```

Le résultat indique :

- Sans transmettre `apiToken`, la construction du SDK **ne renvoie pas d’erreur**, ce qui prouve que le mode X402 est bien une alternative valide au token.
- `createX402PaymentHandler` renvoie une fonction (hook), que le SDK n’appellera qu’après réception d’un 402.
- Le test de bout en bout du paiement réel on-chain n’est pas inclus dans ce tutoriel, car il implique une déduction réelle d’USDC ; vous pouvez vous référer à l’exemple e2e dans le [guide d’intégration X402](https://platform.acedata.cloud/documents/x402-integration).

> Côté Python, `create_x402_payment_handler` effectue également la même vérification —— la valeur de retour de la fonction est callable, et la construction de `AceDataCloud(...)` ne renvoie pas d’erreur lors de l’injection de `payment_handler=...`. Les sémantiques des deux côtés sont alignées.

## V. Comparaison avec le « mode token Bearer »

| Dimension              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Cas d’utilisation            | Votre propre backend, projets à long terme                                                         | Développeurs tiers, paiement à l’usage, appels Agentic                        |
| Inscription              | Nécessite une demande dans la [console](https://platform.acedata.cloud/console/applications) | Non nécessaire ; il suffit d’avoir un portefeuille on-chain                                     |
| Précision de facturation            | Recharge préalable, débit selon le tableau des tokens                                                   | Paiement on-chain en temps réel par appel                                         |
| Solde              | Consultable dans la console                                                           | Voir les USDC du portefeuille on-chain                                      |
| Coût initial            | Une allocation gratuite est offerte dès l’inscription par e-mail                                                        | Nécessite de transférer des USDC vers Base, puis une première approbation Permit2              |
| Adapté aux appels de type chat       | ✅                                                                 | ✅ (doit utiliser `preferScheme=upto`)                       |
| Adapté au paiement unique / au paiement délégué inter-comptes | ❌                                                                 | ✅                                               |
| Modification du code            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Les deux modes peuvent coexister — dans le même processus, il suffit de configurer différentes méthodes d’authentification pour différentes instances de `client`.

## VI. Pièges courants

1. **Les catégories chat doivent obligatoirement utiliser `preferScheme=upto`** : utiliser `exact` fera déduire au facilitator des USDC selon `maxAmountRequired` (et non selon l’utilisation réelle).
2. **Ne transmettez pas une clé privée brute à `createX402PaymentHandler` côté Node** : le package TS n’accepte pas `{ privateKey }`, elle doit être encapsulée dans un provider EIP-1193 (le `WalletClient` de viem est recommandé).
3. **Le premier appel nécessite une double signature** : la première signe l’approbation Permit2 (on-chain, avec gas), la deuxième signe l’enveloppe X402 (hors chaîne). Les appels suivants ne conservent que la deuxième.
4. **Solana n’a pas de concept Permit2** : signez directement l’autorisation de transfert de token SPL, sans besoin d’approve ; mais actuellement, seule la méthode `exact` est prise en charge on-chain sur Solana.
5. **Distinguez les erreurs métier des erreurs de paiement** : 402 → l’échec du handler lève `X402SignError` (le type spécifique dépend de la chaîne) ; après une nouvelle tentative, les erreurs de l’interface métier (401 / 422 / 5xx) sont toujours classées comme des exceptions SDK ordinaires.
6. **La manière la plus fiable d’adapter `viem`** : `evmProvider: walletClient as any` perd la vérification de types mais offre la meilleure compatibilité ; si vous souhaitez conserver les types, encapsulez séparément `.transport.request` de viem dans un objet `{ request }` et transmettez-le.
