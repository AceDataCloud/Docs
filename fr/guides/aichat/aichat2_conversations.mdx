L’API AI Chat v2 (`/aichat2/conversations`) est une interface de conversation de nouvelle génération, représentant une mise à niveau complète de [l’API AI Chat](https://platform.acedata.cloud/documents/aichat-conversations). Sur la base de la simplicité et de la gestion hébergée des conversations multi-tours de v1, elle étend :

- **Entrée utilisateur multimodale** : transmettez directement des blocs de texte + images + fichiers via le champ structuré `message`, sans devoir d’abord les joindre indirectement avec `references`.
- **Appels d’outils orientés Agent** : intègre un ensemble d’outils de recherche en ligne, d’exploration de pages web, de lecture de fichiers, etc., et peut connecter des serveurs MCP autorisés par l’utilisateur (Google Drive, Notion, Slack, GitHub, etc.). Le modèle peut appeler autonomement des outils sur plusieurs tours dans une seule requête pour accomplir des tâches complexes.
- **Événements structurés en streaming** : via `accept: text/event-stream` ou `application/x-ndjson`, vous pouvez obtenir des événements tels que `text_delta`, `tool_use`, `tool_result`, `thinking`, `citation`, `card`, `artifact`, etc., token par token, afin de les rendre séparément dans le frontend selon leur type.
- **Interruptible / reprenable** : lorsque le modèle a besoin que l’utilisateur complète des informations, il émet un événement `ask_user_question` et se met en pause. Lors de l’appel suivant, il suffit de renseigner la réponse via `tool_results` pour poursuivre.
- **Nouvelles actions CRUD** : utilisez le champ `action` sur le même endpoint pour effectuer `retrieve` / `retrieve_batch` / `update` / `delete`, sans API supplémentaire de gestion des conversations.
- **Liste de modèles continuellement mise à jour** : intègre par défaut des modèles contemporains tels que GPT-5.4, Claude Opus 4.8, Claude Sonnet 4.6, Gemini 3.1 Pro, GLM 5.1, DeepSeek V4, Kimi K3, etc.

Parallèlement, au niveau du corps de la requête, elle est **entièrement rétrocompatible avec v1** : transmettez uniquement `model` + `question` (+ éventuellement `stateful` / `id` / `references` / `preset`) pour obtenir une réponse JSON `{answer, id}` équivalente à celle de v1. Ainsi, migrer depuis `/aichat/conversations` ne nécessite pas de réécrire le client : il suffit de remplacer le chemin par `/aichat2/conversations`.

> Si vous utilisez actuellement `/aichat/conversations`, l’ancienne interface restera disponible et vous pourrez migrer à votre propre rythme.

## Processus de demande

Pour utiliser l’API AI Chat v2, rendez-vous d’abord sur la [console Ace Data Cloud](https://platform.acedata.cloud/console/applications) pour obtenir votre API Token, à conserver pour plus tard.

![](https://cdn.acedata.cloud/dvc3cg.jpg)

Si vous n’êtes pas encore connecté ou inscrit, vous serez automatiquement redirigé vers la page de connexion afin de vous inviter à vous inscrire et à vous connecter. Une fois terminé, vous reviendrez automatiquement sur la page actuelle.

**Un seul API Token permet d’appeler tous les services de la plateforme, sans avoir à en demander un séparément pour chaque service.** Lors de votre première demande, un quota gratuit vous sera offert afin de pouvoir essayer le service gratuitement ; lorsque le quota est insuffisant, vous pouvez recharger votre solde général dans la [console](https://platform.acedata.cloud/console/coin).

## Utilisation de base

L’utilisation la plus simple est exactement la même que v1 : transmettez `model` + `question`, et récupérez `{answer, id}`.

Exemple CURL :

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "Présentez AceDataCloud en une phrase."
  }'
```

Résultat renvoyé :

```json
{
  "answer": "AceDataCloud est une plateforme API unifiée qui regroupe les principaux modèles d’IA et services multimodaux. Les développeurs peuvent appeler des services tels que GPT, Claude, Gemini, Midjourney, Suno et Veo avec une seule clé.",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Exemple Python :

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "Présentez AceDataCloud en une phrase.",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

Les valeurs disponibles pour `model` peuvent être directement consultées dans la liste déroulante du panneau Try à droite ; les catégories courantes incluent :

## Conversation multi-tours

Comme avec v1, transmettez `stateful: true` pour activer la sauvegarde de la conversation. L’API renverra un `id` ; il suffira de transmettre cet `id` dans les requêtes suivantes pour poursuivre la conversation, sans avoir à maintenir vous-même l’historique des messages.

Première requête :

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "Mémorisez un nombre : 42."
  }'
```

Retour :

```json
{
  "answer": "D’accord, j’ai mémorisé 42. Que voulez-vous que j’en fasse ?",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Deuxième requête, avec le même `id` :
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "我刚才让你记住的数字是多少？"
  }'
```

```json
{
  "answer": "你让我记住的数字是 42。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` est défini sur `true` par défaut, l’omettre est équivalent à transmettre explicitement `true`. Définir `stateful: false` ignore le chargement de l’historique de conversation précédent ; cela ne signifie pas que le résultat de ce tour ne sera pas enregistré, et ne s’applique pas non plus aux flux d’outils qui doivent reprendre après une pause.

### Conversations longues et conservation du texte original

La compression du contexte organise uniquement le contenu envoyé au modèle pour ce tour, sans remplacer les enregistrements de chat déjà sauvegardés. Il est toujours possible de lire l’intégralité des messages sauvegardés via `action: retrieve` ; la modification ou la suppression explicite d’une conversation reste effective conformément à la requête.

Le modèle peut rechercher et lire de manière paginée le texte original de l’historique dans la conversation actuelle. Lorsqu’il faut continuer à modifier un article, citer des chiffres ou préparer une publication, le texte original correspondant doit être lu, et un résumé ne peut pas remplacer le corps du texte. Cette capacité ne restaure pas automatiquement les messages déjà perdus dans les anciennes versions.

Si l’organisation du contexte échoue, conservez l’ID de conversation et vérifiez l’événement `error` ; le service ne remplacera pas le texte original par un résumé vide. Les opérations d’outils terminées avant l’échec peuvent encore être valides ; consultez d’abord leurs résultats afin d’éviter des générations ou publications en double. Lorsqu’une seule conversation atteint la limite de stockage, une erreur explicite est renvoyée ; les enregistrements déjà sauvegardés ne libèrent pas d’espace par découpage. Vous pouvez exporter le contenu nécessaire puis ouvrir une nouvelle conversation.

## Réponse en streaming

v2 prend en charge deux formats de streaming, sélectionnés selon l’en-tête `accept` :

| Scénario                    | `accept`               | Format des données                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Frontend Web / EventSource  | `text/event-stream`    | `data: {json}\n\n`, dernière ligne `data: [DONE]\n\n` |
| Serveur / CLI / analyse de flux Node | `application/x-ndjson` | Un objet JSON par ligne                               |
| Streaming non requis                 | `application/json`（par défaut） | Retour unique de `{answer, id}`                       |

### Exemple NDJSON

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "用三句话介绍杭州。",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # 与 v1 兼容：增量片段同时通过 delta_answer 字段提供
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

Chaque ligne NDJSON est un événement structuré, le plus courant étant `text_delta` :

```json
{"type":"text_delta","content":"杭","delta_answer":"杭","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"州","delta_answer":"州","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"是","delta_answer":"是","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### Exemple SSE

L’utilisation de `EventSource` côté navigateur ne prend pas en charge les corps de requête personnalisés ; il est recommandé d’utiliser `fetch` + une analyse manuelle par découpage sur `\n\n` :

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "用三句话介绍杭州。",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### Types d’événements de streaming

| `type`              | Signification                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `text_delta`        | Fragment de texte incrémentiel de la réponse de l’assistant. `content` contient le nouveau contenu ; pour la compatibilité avec v1, le même événement contient également `delta_answer` (égal à `content`) et `id`.                                        |
| `thinking`          | Processus de réflexion du modèle (apparaît uniquement lorsque le modèle sélectionné expose le raisonnement).                                                                                      |
| `tool_use`          | Le modèle décide d’appeler un outil ; l’événement contient `tool_id`, `tool_name`, `input`.                                                                        |
| `tool_result`       | Résultat de l’exécution de l’outil, associé au `tool_use` précédent via `tool_id`, `is_error` indique si l’exécution a échoué.                                                             |
| `card`              | Carte structurée produite par un outil (comme une image ou un aperçu de lien), adaptée au rendu direct.                                                                                          |
| `citation`          | URL source utilisée pour compléter la citation du fragment de texte correspondant.                                                                                                  |
| `ask_user_question` | Émis lorsque le modèle a besoin que l’utilisateur fournisse des informations supplémentaires ; la conversation passe à l’état `awaiting_user_input`, voir ci-dessous [Reprendre une conversation en pause](#恢复暂停的对话)。                                                 |
| `artifact`          | Produit autonome généré par le modèle (comme un bloc de code ou un document), pouvant être enregistré ou téléchargé.                                                                                            |
| `system_message`    | Message d’invite système (ni contenu utilisateur ni assistant), uniquement utilisé pour les indications de l’interface.                                                                                           |
| `compact`           | Le contexte du modèle a été organisé ; les messages originaux sauvegardés restent inchangés, le client n’a pas besoin de supprimer l’historique de chat.                                                                                    |
| `error`             | Une erreur est survenue pendant ce tour ; `message` décrit le contenu de l’erreur.                                                                                              |
| `done`              | L’enregistrement final de la conversation de ce tour a été sauvegardé avec succès ; contient `usage` (incluant `prompt_tokens` / `completion_tokens` / `total_tokens`) et `terminal_reason` ; il faut toujours déterminer si la tâche est terminée selon la raison de terminaison. |
Pour les clients qui ne s'intéressent qu'à la réponse finale, concaténer tous les `content` de `text_delta` est équivalent à `answer` en mode `application/json`.

## Entrée multimodale

Si l'entrée utilisateur contient des images ou des fichiers, transmettez `message` (un tableau) au lieu de `question`. Chaque élément du tableau est un bloc de contenu :

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "这张图片里有几只猫？" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

Types de blocs pris en charge :

- `text` — Texte ordinaire, champ `text` obligatoire.
- `image_url` — Image, `image_url.url` obligatoire.
- `file_url` — Fichier (PDF, CSV, TXT, etc.), `file_url.url` obligatoire.

### Relation avec les `references` de v1

Afin de rester compatible avec les anciens clients, v2 reconnaît toujours le champ `references: ["https://...", ...]` :

- Si le suffixe de l'URL est `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif`, il est automatiquement converti en bloc `image_url` ;
- Les autres extensions sont converties en blocs `file_url` ;
- Si `question` est également fourni, il est placé en tête comme bloc `text`.

Par conséquent, si vous souhaitez seulement migrer depuis v1 sans modifier le corps de la requête, remplacez simplement le chemin par `/aichat2/conversations`, et l'utilisation originale de `references` continuera de fonctionner normalement.

Si vous avez besoin d'un contrôle plus précis (par exemple, placer plusieurs images entre des textes, ou si l'ordre est important), utilisez directement le tableau `message`.

## Appel d'outils et MCP

L'amélioration principale de v2 est que le modèle peut appeler des outils de manière autonome pour accomplir des tâches en plusieurs étapes, **cela est activé par défaut**, sans aucune configuration supplémentaire de la part du client dans la requête. Cas courants :

- L'utilisateur demande « Aidez-moi à rechercher quelles nouvelles expositions ont récemment lieu à Shanghai » → le modèle appelle la recherche web intégrée → organise les résultats en réponse.
- L'utilisateur demande « Lisez ce PDF puis rédigez un résumé » → le modèle appelle `file_read` → rédige un résumé.
- L'utilisateur a déjà autorisé Google Drive / GitHub / Notion, etc. dans [Connections](https://platform.acedata.cloud/connections) → le modèle peut appeler les outils MCP correspondants pour lire et écrire leurs données.

Dans le flux NDJSON / SSE, les appels d'outils sont présentés via deux types d'événements, `tool_use` et `tool_result`, par exemple :

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"上海 2026 春季展览"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"目前","delta_answer":"目前","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"上海","delta_answer":"上海","id":"f2f4b3e8-..."}
...
```

Si vous ne souhaitez pas afficher les détails des appels d'outils dans le frontend, ignorez simplement les événements `tool_use` / `tool_result` / `card` / `citation`, la sortie finale du modèle continuera d'être diffusée via `text_delta`.

`max_turns` peut limiter le nombre maximal de tours pendant lesquels le modèle peut s'appeler lui-même avec des outils dans cette requête ; la plage va de 1 à 500, et la valeur par défaut est 500 si elle est omise. Le définir à une petite valeur (par exemple `max_turns: 1`) peut forcer une réponse unique et empêcher tout appel d'outil.

## Exécution asynchrone et autorisation sans supervision

Si votre appel provient d'un Webhook d'alerte, d'un CI/CD, d'un système de surveillance ou d'une autre tâche en arrière-plan, vous pouvez définir `async: true` afin que l'API renvoie immédiatement un ID de tâche et poursuive l'exécution en arrière-plan :

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Exemple de réponse :

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

Vous pouvez ensuite utiliser `action: retrieve` + `id` pour interroger le résultat de la conversation ; vous pouvez également fournir `callback_url`, et une fois la tâche terminée, la plateforme enverra `{ status, answer, usage, error }` par POST à votre adresse de rappel. `callback_url` doit utiliser `http` / `https` et ne peut pas indiquer directement `localhost` ou une adresse IP privée littérale.

Les tâches en arrière-plan ne disposent généralement de personne pour cliquer sur une confirmation. Si vous souhaitez que certaines compétences ou certains serveurs MCP exécutent des actions telles que l'envoi, la publication ou l'écriture en mode sans supervision, veuillez transmettre explicitement une liste de préautorisation dans le corps de la requête :

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Les valeurs dans `allowed_skills` sont les slugs des Skills connectés ; les valeurs dans `allowed_mcp_servers` sont les slugs des serveurs MCP connectés. Les Skills / serveurs MCP non inclus dans la préautorisation ne peuvent toujours qu'afficher un aperçu, effectuer un dry-run ou refuser les opérations d'écriture en mode sans supervision.

Si un contrôle plus fin est nécessaire, vous pouvez également utiliser l'objet équivalent `unattended_policy` :

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

La préautorisation correspond à ces deux listes elles-mêmes : une liste vide n'autorise aucune capacité, sans nécessiter de champ interrupteur supplémentaire.

Remarque : la préautorisation signifie uniquement que « cette requête autorise ces capacités à ignorer la confirmation humaine en mode sans supervision ». Le Skill concerné doit toujours prendre en charge `--unattended-confirm` ou le mécanisme de sécurité correspondant ; sinon, il continuera en dry-run et n'exécutera pas directement les opérations d'écriture.

## Reprendre une conversation suspendue

Certains outils peuvent amener le modèle à « poser une question à l'utilisateur » ; le modèle émet alors un événement `ask_user_question`, et la conversation est gelée dans l'état `awaiting_user_input` :

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "你希望生成的报告是中文还是英文？",
  "options": ["中文", "英文"],
  "id": "f2f4b3e8-..."
}
```

Dans le frontend, affichez cet événement sous forme de carte afin que l'utilisateur puisse choisir une réponse, puis lancez la requête suivante avec le même `id` et renseignez la réponse via `tool_results` :
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

Dans le corps de la requête, `tool_use_id` **doit** correspondre exactement à `tool_id` au moment de la suspension ; sinon, une erreur 400 sera renvoyée. Lorsque `tool_results` est présent dans la requête, `question` / `message` / `references` sont tous ignorés.

Si l'utilisateur décide d'abandonner cette question, transmettez directement un nouveau `question` / `message`, et la plateforme marquera automatiquement l'appel d'outil suspendu comme « ignoré par l'utilisateur ».

## Gestion des conversations (CRUD)

v2 fournit une gestion légère des conversations sur le même endpoint via le champ `action`, sans avoir besoin d'ouvrir une autre API.

### `action: retrieve` —— Récupérer une conversation

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

Renvoie le document complet de la conversation (incluant l'historique `messages`, `model`, `title`, `tools_used`, etc.).

### `action: retrieve_batch` —— Lister les résumés des conversations

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

Renvoie `{ items: [...], total }`. **Les résumés ne contiennent pas `messages`**, ce qui convient pour créer une liste dans une barre latérale ; si l'utilisateur ouvre une conversation, utilisez ensuite `action: retrieve` pour récupérer séparément ses messages complets.

Paramètres de filtrage facultatifs : `user_id`, `application_id`, `model_group`, `model`.

### `action: update` —— Modifier le titre ou réécrire l'historique

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "杭州旅行计划"
}
```

`messages` peut également être transmis, mais le serveur effectuera une validation stricte du schéma (il doit s'agir de la forme `ToolUseContent` repliée) ; une erreur 400 sera renvoyée s'il n'est pas conforme. En général, il est recommandé de l'utiliser uniquement pour modifier `title`.

### `action: delete` —— Supprimer une conversation

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Renvoie `{ id, success: true }`. Après suppression, la conversation ne peut pas être récupérée ; veuillez confirmer avant d'appeler cette action.

## Migration fluide depuis v1

Si vous utilisez déjà [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations), la migration vers v2 ne nécessite presque aucune modification de code :

1. Remplacez l'URL `https://api.acedata.cloud/aichat/conversations` par `https://api.acedata.cloud/aichat2/conversations`.
2. Si vous utilisiez auparavant un nom de modèle v1 (tel que `gpt-3.5`, `gpt-4-browsing`, etc.), il est recommandé de passer à un modèle contemporain lors du basculement vers v2 (tel que `gpt-5.4`, `claude-opus-4-8`, `gemini-3.1-pro-preview`, etc.).
3. Les champs du flux NDJSON restent rétrocompatibles : chaque événement `text_delta` contient toujours `delta_answer` et `id`, donc les clients existants qui analysent `delta_answer` ligne par ligne n'ont pas besoin d'être modifiés.

Après la migration, vous pouvez activer selon vos besoins les nouvelles capacités de v2 (entrée multimodale `message`, SSE, appels d'outils, CRUD via `action`) et avancer à votre rythme.

## Gestion des erreurs

Les réponses d'erreur suivent toutes le format suivant :

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

Erreurs courantes :

- `400 bad_request` : champ obligatoire manquant, `tool_use_id` non correspondant, schéma `messages` invalide, etc.
- `401 invalid_token` : l'en-tête `authorization` est incorrect.
- `404 not_found` : la conversation correspondant à `id` n'existe pas lors de `action: retrieve / update / delete`.
- `413 conversation_storage_limit` : la conversation dépasse la limite de stockage, les enregistrements existants sauvegardés n'ont pas été écrasés.
- `429 too_many_requests` : la limite de débit a été déclenchée.
- `503 context_compaction_failed` : l'organisation du contexte a échoué, les enregistrements existants sont conservés.
- `500 conversation_persist_failed` : l'enregistrement final de ce tour a échoué ; le texte déjà reçu ne signifie pas que l'enregistrement final a été sauvegardé avec succès, veuillez interroger par ID de conversation.
- `500 chat_error` : le service est temporairement indisponible, ou aucun contenu n'a été généré pendant ce tour (aucun frais ne sera facturé).

Dans les réponses en flux, les erreurs sont envoyées via des événements `{"type":"error","message":"..."}`, puis le flux se termine. `[DONE]` indique uniquement la fin du transport ; en présence d'une `error`, cela ne peut pas être considéré comme un succès, et aucun événement `done` de succès ne sera envoyé.

## Conclusion

Tout en restant rétrocompatible avec v1, l'API AI Chat v2 fait évoluer la conversation de « questions-réponses à un tour / plusieurs tours » vers une « conversation observable orientée Agent » : entrées multimodales, appels d'outils, suspension / reprise, événements structurés en flux et CRUD intégré. Il est recommandé aux nouvelles intégrations d'utiliser directement v2 ; les intégrations v1 existantes peuvent migrer progressivement par étapes. Pour toute question, n'hésitez pas à contacter notre équipe de support technique.
