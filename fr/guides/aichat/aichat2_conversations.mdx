L’API AI Chat v2 (`/aichat2/conversations`) est une interface de conversation de nouvelle génération et une version entièrement améliorée de [l’API AI Chat](https://platform.acedata.cloud/documents/aichat-conversations). En s’appuyant sur la simplicité de v1 et la gestion hébergée des conversations multi-tours, elle étend :

- **Entrées utilisateur multimodales** : envoyez directement des blocs de texte + image + fichier via le champ `message` structuré, sans devoir d’abord les joindre indirectement avec `references`.
- **Appels d’outils orientés Agent** : intègre un ensemble d’outils de recherche en ligne, d’extraction de pages web, de lecture de fichiers, etc., et peut également connecter des serveurs MCP autorisés par l’utilisateur (Google Drive, Notion, Slack, GitHub, etc.) ; le modèle peut appeler les outils de manière autonome sur plusieurs tours au sein d’une seule requête afin d’accomplir des tâches complexes.
- **Événements de streaming structurés** : via `accept: text/event-stream` ou `application/x-ndjson`, vous pouvez obtenir des événements tels que `text_delta`, `tool_use`, `tool_result`, `thinking`, `citation`, `card`, `artifact`, etc., token par token, facilitant leur rendu séparé par type dans le frontend.
- **Interrompable / reprenable** : lorsque le modèle a besoin que l’utilisateur fournisse des informations supplémentaires, il émet un événement `ask_user_question` et se met en pause ; lors de l’appel suivant, il suffit de renseigner la réponse via `tool_results` pour continuer.
- **Nouvelles actions CRUD** : effectuez `retrieve` / `retrieve_batch` / `update` / `delete` via le champ `action` sur le même endpoint, sans API supplémentaire de gestion des conversations.
- **Liste de modèles continuellement mise à jour** : intègre par défaut des modèles contemporains tels que GPT-5.4, Claude Opus 4.8, Claude Sonnet 4.6, Gemini 3.1 Pro, GLM 5.1, DeepSeek V4, Kimi K3, etc.

En même temps, au niveau du corps de la requête, elle est **entièrement rétrocompatible avec v1** : en envoyant seulement `model` + `question` (+ éventuellement `stateful` / `id` / `references` / `preset`), vous pouvez obtenir une réponse JSON `{answer, id}` équivalente à v1. Ainsi, une migration depuis `/aichat/conversations` ne nécessite pas de réécrire le client ; il suffit de remplacer le chemin par `/aichat2/conversations`.

> Si vous utilisez actuellement `/aichat/conversations`, l’ancienne interface continuera d’être maintenue ; vous pouvez migrer à votre propre rythme.

## Processus de demande

Pour utiliser l’API AI Chat v2, rendez-vous d’abord sur la [console Ace Data Cloud](https://platform.acedata.cloud/console/applications) afin d’obtenir votre API Token, à conserver pour une utilisation ultérieure.

![](https://cdn.acedata.cloud/dvc3cg.jpg)

Si vous n’êtes pas encore connecté ou inscrit, vous serez automatiquement redirigé vers la page de connexion pour vous inviter à vous inscrire et à vous connecter ; une fois cela fait, vous reviendrez automatiquement à la page actuelle.

**Un seul API Token permet d’appeler tous les services de la plateforme, sans devoir en demander un séparément pour chaque service.** Une demande initiale offre un crédit gratuit permettant de tester le service gratuitement ; lorsque le crédit est insuffisant, vous pouvez recharger votre solde universel dans la [console](https://platform.acedata.cloud/console/coin).

## Utilisation de base

L’utilisation la plus simple est exactement la même que pour v1 : envoyez `model` + `question`, et obtenez `{answer, id}`.

Exemple CURL :

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "Présentez AceDataCloud en une phrase."
  }'
```

Résultat retourné :

```json
{
  "answer": "AceDataCloud est une plateforme d’API unifiée regroupant les principaux modèles d’IA et services multimodaux, permettant aux développeurs d’appeler des services tels que GPT, Claude, Gemini, Midjourney, Suno et Veo à l’aide d’une seule clé.",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Exemple Python :

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "Présentez AceDataCloud en une phrase.",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

Les valeurs `model` disponibles peuvent être consultées directement dans la liste déroulante du panneau Try à droite ; les catégories courantes comprennent :

- Google : `gemini-3.1-pro-preview`, `gemini-3.1-pro-preview`, `gemini-3.1-flash-image`, `gemini-3.1-pro-preview`, `gemini-2.5-flash-lite`, etc.
- xAI : `grok-4`, etc.
- DeepSeek : `deepseek-v4-pro`, `deepseek-v4.1-flash`, `deepseek-v4-flash`, `deepseek-v3.2-exp`, `deepseek-r1-0528`, etc.

## Conversation multi-tours

Comme avec v1, envoyez `stateful: true` pour activer la sauvegarde de la conversation ; l’API retourne un `id` ; il suffit de renvoyer cet `id` dans les requêtes suivantes pour continuer la conversation, sans devoir maintenir vous-même l’historique des messages.

Première requête :

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "Souvenez-vous d’un nombre : 42."
  }'
```

Retour :

```json
{
  "answer": "D’accord, je me souviens déjà de 42. Que souhaitez-vous que j’en fasse ?",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Deuxième requête, avec le même `id` :
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "我刚才让你记住的数字是多少？"
  }'
```

```json
{
  "answer": "你让我记住的数字是 42。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` est défini sur `true` par défaut ; l’omettre est équivalent à transmettre explicitement `true`. Si vous ne souhaitez pas que le serveur enregistre ce tour de conversation, vous pouvez définir explicitement `stateful: false`.

## Réponse en streaming

v2 prend en charge deux formats de streaming, sélectionnés selon l’en-tête `accept` :

| Scénario                    | `accept`               | Format des données                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Frontend Web / EventSource  | `text/event-stream`    | `data: {json}\n\n`, avec comme dernière ligne `data: [DONE]\n\n` |
| Serveur / CLI / analyse de flux Node | `application/x-ndjson` | Un objet JSON par ligne                               |
| Streaming non requis                 | `application/json`（par défaut） | Retourne `{answer, id}` en une seule fois                       |

### Exemple NDJSON

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "用三句话介绍杭州。",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # 与 v1 兼容：增量片段同时通过 delta_answer 字段提供
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

Chaque ligne NDJSON est un événement structuré, le plus courant étant `text_delta` :

```json
{"type":"text_delta","content":"杭","delta_answer":"杭","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"州","delta_answer":"州","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"是","delta_answer":"是","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### Exemple SSE

L’utilisation de `EventSource` côté navigateur ne prend pas en charge les corps de requête personnalisés ; il est recommandé d’utiliser `fetch` + une analyse manuelle par découpage sur `\n\n` :

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "用三句话介绍杭州。",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### Types d’événements de streaming

| `type`              | Signification                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| `text_delta`        | Fragment de texte incrémentiel de la réponse de l’assistant. `content` correspond au nouveau contenu ; pour la compatibilité avec v1, le même événement contient également `delta_answer` (égal à `content`) et `id`.                  |
| `thinking`          | Processus de réflexion du modèle (apparaît uniquement lorsque le modèle sélectionné expose le raisonnement).                                                                |
| `tool_use`          | Le modèle décide d’appeler un outil ; l’événement contient `tool_id`, `tool_name`, `input`.                                                  |
| `tool_result`       | Résultat de l’exécution de l’outil, associé au `tool_use` précédent via `tool_id` ; `is_error` indique s’il a échoué.                                       |
| `card`              | Carte structurée produite par un outil (par exemple une image, un aperçu de lien), adaptée à un rendu direct.                                                                    |
| `citation`          | URL source utilisée pour compléter les citations du fragment de texte correspondant.                                                                            |
| `ask_user_question` | Émis lorsque le modèle a besoin que l’utilisateur fournisse des informations supplémentaires ; la conversation entre dans l’état `awaiting_user_input`, voir [Reprendre une conversation suspendue](#恢复暂停的对话) ci-dessous.                           |
| `artifact`          | Produit indépendant généré par le modèle (par exemple un bloc de code, un document), pouvant être enregistré ou téléchargé.                                                                      |
| `system_message`    | Message d’invite système (ni contenu utilisateur ni contenu assistant), utilisé uniquement pour les indications de l’interface utilisateur.                                                                     |
| `compact`           | Événement indiquant que le contexte interne a été compressé, ne nécessitant aucun traitement particulier.                                                                             |
| `error`             | Une erreur est survenue durant ce tour ; `message` décrit le contenu de l’erreur.                                                                        |
| `done`              | La réponse en streaming est terminée ; contient `usage` (avec `prompt_tokens` / `completion_tokens` / `total_tokens`) et `terminal_reason`. |

Pour les clients qui ne s’intéressent qu’à la réponse finale, concaténer les `content` de tous les `text_delta` est équivalent à `answer` en mode `application/json`.

## Entrée multimodale

Si l’entrée utilisateur contient des images ou des fichiers, transmettez `message` (un tableau) à la place de `question`. Chaque élément du tableau est un bloc de contenu :

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "这张图片里有几只猫？" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

Types de blocs pris en charge :

- `text` — Texte ordinaire, champ `text` obligatoire.
- `image_url` — Image, champ `image_url.url` obligatoire.
- `file_url` — Fichier (PDF, CSV, TXT, etc.), champ `file_url.url` obligatoire.

### Relation avec `references` de v1

Afin d’assurer la compatibilité avec les anciens clients, v2 reconnaît toujours le champ `references: ["https://...", ...]` :
- Les suffixes d’URL sont `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif`, convertis automatiquement en blocs `image_url` ;
- Les autres extensions sont converties en blocs `file_url` ;
- Si un `question` est également fourni, il est alors placé en tête en tant que bloc `text`.

Par conséquent, si vous souhaitez uniquement migrer depuis v1 sans modifier le corps de la requête, remplacez simplement le chemin par `/aichat2/conversations`, et l’usage original de `references` continuera de fonctionner normalement.

Si vous avez besoin d’un contrôle plus précis (par exemple, placer plusieurs images entre des textes, ou si l’ordre est très important), utilisez directement le tableau `message`.

## Appels d’outils et MCP

L’amélioration principale de v2 est que le modèle peut appeler lui-même des outils afin d’accomplir des tâches en plusieurs étapes, **cela est activé par défaut**, et ne nécessite aucune configuration supplémentaire du client dans la requête. Scénarios courants :

- L’utilisateur demande « Aidez-moi à chercher quelles nouvelles expositions sont prévues récemment à Shanghai » → Le modèle appelle la recherche web intégrée → Il organise les résultats en réponse.
- L’utilisateur demande « Lisez ce PDF puis rédigez un résumé » → Le modèle appelle file_read → Il rédige un résumé.
- L’utilisateur a déjà autorisé Google Drive / GitHub / Notion, etc. dans [Connections](https://platform.acedata.cloud/connections) → Le modèle peut appeler les outils MCP correspondants pour lire et écrire leurs données.

Dans le flux NDJSON / SSE, les appels d’outils sont présentés par deux types d’événements, `tool_use` et `tool_result`, par exemple :

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"上海 2026 春季展览"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"目前","delta_answer":"目前","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"上海","delta_answer":"上海","id":"f2f4b3e8-..."}
...
```

Si vous ne souhaitez pas afficher les détails des appels d’outils dans le frontend, ignorez simplement les événements de type `tool_use` / `tool_result` / `card` / `citation`, la sortie finale du modèle continuera d’être diffusée via `text_delta`.

`max_turns` peut limiter le nombre maximal de cycles d’auto-appel d’outils du modèle dans cette requête, avec une plage de 1 à 500, et la valeur par défaut est 500 lorsqu’il est omis. Le définir à une petite valeur (par exemple `max_turns: 1`) peut forcer une réponse unique et n’autoriser aucun appel d’outil.

## Exécution asynchrone et autorisation sans supervision

Si votre appel provient d’un Webhook d’alerte, d’un CI/CD, d’un système de surveillance ou d’une autre tâche en arrière-plan, vous pouvez définir `async: true` afin que l’interface renvoie immédiatement l’ID de la tâche et poursuive l’exécution en arrière-plan :

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Exemple de retour :

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

Vous pouvez ensuite utiliser `action: retrieve` + `id` pour consulter le résultat de la conversation ; vous pouvez également fournir `callback_url`, et une fois la tâche terminée, la plateforme enverra `{ status, answer, usage, error }` par POST à votre adresse de rappel. `callback_url` doit utiliser `http` / `https`, et ne peut pas indiquer directement `localhost` ou une adresse IP privée littérale.

Les tâches en arrière-plan ne disposent généralement de personne pour cliquer sur une confirmation. Si vous souhaitez que certains Skill ou MCP Server exécutent des actions d’envoi, de publication, d’écriture, etc. en mode sans supervision, transmettez explicitement une liste de préautorisation dans le corps de la requête :

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Les valeurs dans `allowed_skills` sont les slugs des Skill connectés ; les valeurs dans `allowed_mcp_servers` sont les slugs des MCP Server connectés. Les Skill / MCP Server non inclus dans la préautorisation ne peuvent toujours qu’afficher un aperçu, effectuer un dry-run ou refuser les opérations d’écriture en mode sans supervision.

Si un contrôle plus fin est nécessaire, vous pouvez également utiliser l’objet `unattended_policy` équivalent :

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

La préautorisation correspond à ces deux listes elles-mêmes : une liste vide n’autorise aucune capacité, aucun champ d’activation supplémentaire n’est nécessaire.

Remarque : la préautorisation signifie uniquement que « cette requête autorise ces capacités à ignorer la confirmation humaine en mode sans supervision ». Le Skill spécifique doit toujours prendre en charge `--unattended-confirm` ou le mécanisme de sécurité correspondant ; sinon, il continuera en dry-run et n’exécutera pas directement les opérations d’écriture.

## Reprendre les conversations suspendues

Certains outils peuvent amener le modèle à « poser une question à l’utilisateur » ; le modèle émet alors un événement `ask_user_question`, et la conversation est gelée dans l’état `awaiting_user_input` :

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "你希望生成的报告是中文还是英文？",
  "options": ["中文", "英文"],
  "id": "f2f4b3e8-..."
}
```

Dans le frontend, affichez cet événement sous forme de carte afin que l’utilisateur puisse choisir une réponse, puis lancez la requête suivante avec le même `id`, en renseignant la réponse via `tool_results` :

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

Le `tool_use_id` dans le corps de la requête **doit** être exactement identique au `tool_id` au moment de la suspension ; dans le cas contraire, une erreur 400 sera renvoyée. Lorsque `tool_results` est présent dans la requête, `question` / `message` / `references` seront tous ignorés.

Si l’utilisateur décide d’abandonner cette question, transmettez directement un nouveau `question` / `message`, et la plateforme marquera automatiquement l’appel d’outil suspendu comme « ignoré par l’utilisateur ».

## Gestion des conversations (CRUD)

v2 fournit une gestion légère des conversations via le champ `action` sur le même endpoint, sans nécessiter d’API supplémentaire.
### `action: retrieve` —— Récupérer une conversation

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

Renvoie le document complet de la conversation (y compris l’historique `messages`, `model`, `title`, `tools_used`, etc.).

### `action: retrieve_batch` —— Lister les résumés des conversations

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

Renvoie `{ items: [...], total }`. **Les résumés ne contiennent pas `messages`**, ils conviennent pour créer une liste dans la barre latérale ; si l’utilisateur ouvre une conversation, utilisez ensuite `action: retrieve` pour récupérer séparément ses messages complets.

Paramètres de filtrage facultatifs : `user_id`, `application_id`, `model_group`, `model`.

### `action: update` —— Modifier le titre ou réécrire l’historique

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "Plan de voyage à Hangzhou"
}
```

`messages` peut également être transmis, mais le serveur effectue une validation stricte du schéma (il doit obligatoirement être sous la forme `ToolUseContent` repliée) ; sinon, une erreur 400 sera renvoyée. En général, il est recommandé de l’utiliser uniquement pour modifier `title`.

### `action: delete` —— Supprimer une conversation

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Renvoie `{ id, success: true }`. La suppression est irréversible, veuillez confirmer avant d’appeler cette action.

## Migration fluide depuis v1

Si vous utilisez déjà [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations), la migration vers v2 ne nécessite pratiquement aucune modification du code :

1. Remplacez l’URL `https://api.acedata.cloud/aichat/conversations` par `https://api.acedata.cloud/aichat2/conversations`.
2. Si vous transmettiez auparavant des noms de modèles v1 (tels que `gpt-3.5`, `gpt-4-browsing`, etc.), il est recommandé de passer à des modèles contemporains lors du basculement vers v2 (tels que `gpt-5.4`, `claude-opus-4-8`, `gemini-3.1-pro-preview`, etc.).
3. Les champs du flux NDJSON restent rétrocompatibles : chaque événement `text_delta` contient toujours `delta_answer` et `id`, les clients qui analysaient auparavant `delta_answer` ligne par ligne ne nécessitent donc aucune modification.

Après la migration, vous pouvez activer selon vos besoins les nouvelles fonctionnalités de v2 (`message` multimodal, SSE, appels d’outils, CRUD `action`) et progresser à votre rythme.

## Gestion des erreurs

Les réponses d’erreur sont uniformisées comme suit :

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

Erreurs courantes :

- `400 bad_request` : champs obligatoires manquants, incompatibilité de `tool_use_id`, schéma `messages` invalide, etc.
- `401 invalid_token` : l’en-tête `authorization` est incorrect.
- `404 not_found` : la conversation correspondant à `id` n’existe pas lors de `action: retrieve / update / delete`.
- `429 too_many_requests` : la limite de débit a été déclenchée.
- `500 chat_error` : erreur du LLM en amont ou `completion_tokens=0` pour ce tour (traité comme non consommé, aucun frais ne sera facturé).

Dans les réponses en flux, les erreurs sont émises sous forme d’événement `{"type":"error","message":"..."}`, puis le flux se termine immédiatement.

## Conclusion

Tout en restant rétrocompatible avec v1, l’API AI Chat v2 fait évoluer les conversations de « questions-réponses à un tour / plusieurs tours » vers des « conversations observables orientées Agent » : entrées multimodales, appels d’outils, mise en pause / reprise, événements structurés en flux, CRUD intégré. Il est recommandé aux nouvelles intégrations d’utiliser directement v2 ; les intégrations v1 existantes peuvent migrer progressivement par étapes. Pour toute question, n’hésitez pas à contacter notre équipe de support technique.
