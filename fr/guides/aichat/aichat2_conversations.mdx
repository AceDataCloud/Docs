L’API AI Chat v2 (`/aichat2/conversations`) est une interface de conversation de nouvelle génération et constitue une mise à niveau complète de [l’API AI Chat](https://platform.acedata.cloud/documents/aichat-conversations). Sur la base des conversations multi-tours hébergées et simplifiées de la v1, elle apporte les extensions suivantes :

- **Entrées utilisateur multimodales** : transmettez directement du texte + des images + des blocs de fichiers via le champ structuré `message`, sans avoir besoin de les joindre indirectement au préalable à l’aide de `references`.
- **Appels d’outils de type Agent** : intègre un ensemble d’outils tels que la recherche sur Internet, l’extraction de pages Web et la lecture de fichiers, et permet de connecter des serveurs MCP autorisés par l’utilisateur (Google Drive, Notion, Slack, GitHub, etc.). Le modèle peut appeler les outils de manière autonome plusieurs fois au cours d’une seule requête afin d’accomplir des tâches complexes.
- **Événements de flux structurés** : grâce à `accept: text/event-stream` ou `application/x-ndjson`, vous pouvez recevoir des événements tels que `text_delta`, `tool_use`, `tool_result`, `thinking`, `citation`, `card` et `artifact` token par token, ce qui facilite leur affichage séparé selon leur type correspondant dans l’interface front-end.
- **Interruptible / reprenable** : lorsque le modèle a besoin d’informations supplémentaires de la part de l’utilisateur, il émet un événement `ask_user_question` et se met en pause. Lors de l’appel suivant, il suffit de renseigner la réponse via `tool_results` pour poursuivre.
- **Nouvelles opérations CRUD** : sur le même endpoint, le champ `action` permet d’effectuer `retrieve` / `retrieve_batch` / `update` / `delete`, sans nécessiter d’API supplémentaire de gestion des conversations.
- **Liste de modèles continuellement mise à jour** : accès par défaut à des modèles contemporains tels que GPT-5.4, Claude Opus 4.8, Claude Sonnet 4.6, Gemini 3.1 Pro, GLM 5.1, DeepSeek V4, Kimi K3, etc.

Parallèlement, elle est **entièrement rétrocompatible avec la v1 au niveau du corps de la requête** : il suffit de transmettre `model` + `question` (+ éventuellement `stateful` / `id` / `references` / `preset`) pour obtenir une réponse JSON `{answer, id}` équivalente à celle de la v1. Ainsi, la migration depuis `/aichat/conversations` ne nécessite aucune réécriture du client : il suffit de remplacer le chemin par `/aichat2/conversations`.

> Si vous utilisez actuellement `/aichat/conversations`, l’ancienne interface continuera à être prise en charge. Vous pouvez effectuer la migration à votre propre rythme.

## Procédure de demande

Pour utiliser l’API AI Chat v2, rendez-vous d’abord sur la [console Ace Data Cloud](https://platform.acedata.cloud/console/applications) afin d’obtenir votre API Token et de le conserver pour une utilisation ultérieure.

![]()

Si vous n’êtes pas encore connecté ou inscrit, vous serez automatiquement redirigé vers la page de connexion, qui vous invitera à vous inscrire et à vous connecter. Une fois cette opération terminée, vous serez automatiquement redirigé vers la page actuelle.

**Un seul API Token suffit pour appeler tous les services de la plateforme : il n’est pas nécessaire d’en demander un séparément pour chaque service.** Lors de la première demande, un quota gratuit vous sera offert pour effectuer des essais sans frais. Lorsque le quota sera insuffisant, vous pourrez recharger votre solde général dans la [console](https://platform.acedata.cloud/console/coin).

## Utilisation de base

La méthode d’utilisation la plus simple est exactement la même que pour la v1 : transmettez `model` + `question` et obtenez `{answer, id}`.

Exemple CURL :

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。"
  }'
```

Résultat retourné :

```json
{
  "answer": "AceDataCloud 是一个聚合主流 AI 模型与多模态服务的统一 API 平台，开发者通过一个密钥即可调用 GPT、Claude、Gemini、Midjourney、Suno、Veo 等多家服务。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Exemple Python :

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

Les valeurs disponibles pour `model` sont directement visibles dans la liste déroulante du panneau Try situé à droite. Les catégories couramment utilisées comprennent :

- OpenAI : `gpt-5.4-mini`, `gpt-5.4-nano`, `gpt-5.2-pro`, `gpt-5.1-all`, `gpt-5-all`, `gpt-4.1`, `gpt-4o`, `gpt-4o-image`, `o3`, `o4-mini`, etc.
- Anthropic : `claude-opus-4-8`, `claude-opus-4-7`, `claude-opus-4-6`, `claude-opus-4-5-20251101`, `claude-sonnet-4-6`, `claude-sonnet-4-5-20250929`, `claude-haiku-4-5-20251001`, etc.
- Google : `gemini-3.1-pro-preview`, `gemini-3.1-pro-preview`, `gemini-3.1-flash-image`, `gemini-3.1-pro-preview`, `gemini-2.5-flash-lite`, etc.
- xAI : `grok-4`, etc.
- DeepSeek : `deepseek-flash`, `deepseek-v4-pro`, `deepseek-v3.2`. Flash accepte également `deepseek-v4.1-flash`, `deepseek-v4.1-flash-1017` et `deepseek-v4-flash`.
- Moonshot : `kimi-k3.1-pro`, `kimi-k3`, `kimi-k2.6`, `kimi-k2.7-code`
- Zhipu : `glm-5.3`, `glm-5.2`, `glm-5.1`, `glm-5`, `glm-5-turbo`, `glm-4.7`, `glm-4.5v`, etc.

Pour connaître les règles de facturation spécifiques, consultez la carte Pricing de la page du service.

## Conversations multi-tours

Comme pour la v1, transmettez `stateful: true` pour activer la sauvegarde des conversations. L’API renverra un `id` ; il vous suffira de renvoyer cet `id` dans les requêtes suivantes pour poursuivre la conversation, sans avoir à gérer vous-même l’historique des messages.

Première requête :

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "记住一个数字：42。"
  }'
```

Réponse :

```json
{
  "answer": "好的，我已经记住了 42。需要我用它做什么吗？",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Deuxième requête, en incluant le même `id` :
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "Quel était le nombre que je t’ai demandé de retenir tout à l’heure ?"
  }'
```

```json
{
  "answer": "Le nombre que tu m’as demandé de retenir est 42.",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` vaut `true` par défaut ; l’omettre ou transmettre explicitement `true` revient au même. Définir `stateful: false` permet d’ignorer le chargement de l’historique des conversations précédentes ; cela ne signifie pas que le résultat de ce tour ne sera pas sauvegardé et ne s’applique pas aux processus d’outils qui nécessitent une mise en pause puis une reprise.

### Conversations longues et conservation du texte original

La compression du contexte organise uniquement le contenu envoyé au modèle lors du tour en cours, sans remplacer l'historique de conversation sauvegardé. L'action `retrieve` permet toujours de consulter l'intégralité des messages sauvegardés ; les modifications et suppressions explicites de conversations restent effectives conformément à la demande.

Le modèle peut rechercher et lire l'historique original par pages au sein de la conversation actuelle. Lorsqu'il est nécessaire de continuer à modifier un article, de citer des chiffres ou de préparer une publication, il faut lire le texte original correspondant et ne pas remplacer le corps du texte par un résumé. Cette capacité ne restaure pas automatiquement les messages déjà perdus dans les anciennes versions.

Si l'organisation du contexte échoue, veuillez conserver l'identifiant de conversation et vérifier l'événement `error` ; le service ne remplacera pas le texte original par un résumé vide. Les opérations sur les outils déjà terminées avant l'échec peuvent toujours être effectives : veuillez d'abord vérifier leurs résultats afin d'éviter toute génération ou publication en double. Lorsqu'une conversation atteint la limite de stockage, une erreur explicite est renvoyée ; les enregistrements déjà sauvegardés ne seront pas supprimés par troncature pour libérer de l'espace. Vous pouvez exporter le contenu nécessaire, puis ouvrir une nouvelle conversation.

## Réponses en streaming

La v2 prend en charge deux formats de streaming, sélectionnés à l'aide de l'en-tête `accept` :

| Scénario                    | `accept`               | Format des données                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Interface Web / EventSource  | `text/event-stream`    | `data: {json}\n\n`, avec une dernière ligne `data: [DONE]\n\n` |
| Serveur / CLI / analyse du flux Node.js | `application/x-ndjson` | Un objet JSON par ligne                               |
| Sans streaming                 | `application/json` (par défaut) | Retour unique `{answer, id}`                       |

### Exemple NDJSON

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "用三句话介绍杭州。",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # Compatible avec v1 : les fragments incrémentiels sont également fournis via le champ delta_answer
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

Chaque ligne NDJSON est un événement structuré, le plus courant étant `text_delta` :

```json
{"type":"text_delta","content":"杭","delta_answer":"杭","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"州","delta_answer":"州","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"是","delta_answer":"是","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### Exemple SSE

Dans le navigateur, `EventSource` ne prend pas en charge les corps de requête personnalisés. Il est recommandé d'utiliser `fetch` avec une analyse manuelle par découpage sur `\n\n` :

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "用三句话介绍杭州。",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### Types d'événements de streaming

| `type`              | Signification                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `text_delta`        | Fragment de texte incrémentiel de la réponse de l'assistant. `content` contient le nouveau contenu ; pour assurer la compatibilité avec v1, le même événement contient également `delta_answer` (égal à `content`) et `id`.                                        |
| `thinking`          | Processus de réflexion du modèle (apparaît uniquement lorsque le modèle sélectionné expose son raisonnement).                                                                                      |
| `tool_use`          | Le modèle décide d'appeler un outil ; l'événement contient `tool_id`, `tool_name` et `input`.                                                                        |
| `tool_result`       | Résultat de l'exécution de l'outil, associé à l'événement `tool_use` précédent via `tool_id` ; `is_error` indique si l'opération a échoué.                                                             |
| `card`              | Carte structurée produite par un outil (par exemple, une image ou un aperçu de lien), adaptée à un affichage direct.                                                                                          |
| `citation`          | URL source permettant de compléter la citation du fragment de texte correspondant.                                                                                                  |
| `ask_user_question` | Émis lorsque le modèle a besoin d'informations supplémentaires de la part de l'utilisateur ; la conversation passe à l'état `awaiting_user_input`. Voir ci-dessous [Reprendre une conversation suspendue](#恢复暂停的对话).                                                 |
| `artifact`          | Élément indépendant généré par le modèle (par exemple, un bloc de code ou un document), pouvant être enregistré ou téléchargé.                                                                                            |
| `system_message`    | Message d'information du système (ne faisant pas partie du contenu de l'utilisateur ou de l'assistant), destiné uniquement à l'affichage dans l'interface utilisateur.                                                                                           |
| `compact`           | Le contexte du modèle a été réorganisé ; les messages originaux sauvegardés restent inchangés et le client n'a pas besoin de supprimer l'historique de conversation.                                                                                    |
| `error`             | Une erreur s'est produite pendant ce tour ; `message` décrit son contenu.                                                                                              |
| `done`              | L'enregistrement final de la conversation pour ce tour a été sauvegardé avec succès. Contient `usage` (avec `prompt_tokens` / `completion_tokens` / `total_tokens`) et `terminal_reason` ; il faut néanmoins déterminer si la tâche est terminée en fonction de la raison de terminaison.        |
Pour les clients qui ne s’intéressent qu’à la réponse finale, la concaténation du champ `content` de tous les `text_delta` est équivalente à `answer` en mode `application/json`.

## Entrées multimodales

Si l’entrée de l’utilisateur contient une image ou un fichier, transmettez `message` (un tableau) à la place de `question`. Chaque élément du tableau est un bloc de contenu :

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "Combien de chats y a-t-il dans cette image ?" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

Types de blocs pris en charge :

- `text` — Texte ordinaire, champ `text` obligatoire.
- `image_url` — Image, champ `image_url.url` obligatoire.
- `file_url` — Fichier (PDF, CSV, TXT, etc.), champ `file_url.url` obligatoire.

### Relation avec les `references` de v1

Pour assurer la compatibilité avec les anciens clients, v2 reconnaît toujours le champ `references: ["https://...", ...]` :

- Les URL dont l’extension est `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif` sont automatiquement converties en blocs `image_url` ;
- Les autres extensions sont converties en blocs `file_url` ;
- Si `question` est également fourni, il est ajouté au début en tant que bloc `text`.

Par conséquent, si vous souhaitez uniquement migrer depuis v1 sans modifier le corps de la requête, il vous suffit de remplacer le chemin par `/aichat2/conversations`. L’utilisation de `references` reste inchangée.

Si vous avez besoin d’un contrôle plus précis (par exemple, placer plusieurs images entre des blocs de texte ou respecter un ordre particulier), utilisez directement le tableau `message`.

## Appels d’outils et MCP

L’amélioration principale de v2 est que le modèle peut appeler des outils de manière autonome pour accomplir des tâches en plusieurs étapes. **Cette fonctionnalité est activée par défaut** et ne nécessite aucune configuration supplémentaire de la part du client dans la requête. Cas d’utilisation courants :

- L’utilisateur demande « Recherche les nouvelles expositions récentes à Shanghai » → le modèle appelle la recherche Web intégrée → organise les résultats dans une réponse.
- L’utilisateur demande « Lis ce PDF et rédige un résumé » → le modèle appelle file_read → rédige le résumé.
- L’utilisateur a déjà autorisé Google Drive / GitHub / Notion, etc. dans [Connections](https://platform.acedata.cloud/connections) → le modèle peut appeler les outils MCP correspondants pour lire et écrire ses données.

Dans les flux NDJSON / SSE, les appels d’outils sont représentés par deux types d’événements : `tool_use` et `tool_result`, par exemple :

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"Expositions de printemps à Shanghai 2026"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"Actuellement","delta_answer":"Actuellement","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"Shanghai","delta_answer":"Shanghai","id":"f2f4b3e8-..."}
...
```

Si vous ne souhaitez pas afficher les détails des appels d’outils dans l’interface utilisateur, ignorez simplement les événements `tool_use` / `tool_result` / `card` / `citation`. La sortie finale du modèle continuera d’être transmise via le flux `text_delta`.

`max_turns` permet de limiter le nombre maximal de cycles d’appels d’outils autonomes du modèle pour cette requête. La plage autorisée est de 1 à 500, et la valeur par défaut est 500 si le paramètre est omis. En définissant une valeur faible (par exemple, `max_turns: 1`), vous pouvez imposer une réponse unique sans autoriser aucun appel d’outil.

## Exécution asynchrone et autorisation sans surveillance

Si votre appel provient d’un Webhook d’alerte, d’un système CI/CD, d’un système de surveillance ou d’une autre tâche en arrière-plan, vous pouvez définir `async: true` afin que l’interface renvoie immédiatement un identifiant de tâche, tandis que l’exécution se poursuit en arrière-plan :

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "Mon service a déclenché une alerte. Utilise mon compte WeChat personnel pour envoyer une notification au groupe WeChat « Équipe AceDataCloud »……"
}
```

Exemple de réponse :

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

Vous pouvez ensuite utiliser `action: retrieve` + `id` pour récupérer le résultat de la conversation. Vous pouvez également fournir `callback_url` : une fois la tâche terminée, la plateforme enverra une requête POST contenant `{ status, answer, usage, error }` à votre adresse de rappel. `callback_url` doit utiliser `http` / `https` et ne peut pas être directement défini sur `localhost` ou une adresse IP privée littérale.

En règle générale, personne ne peut cliquer sur un bouton de confirmation pour les tâches en arrière-plan. Si vous souhaitez que certains Skills ou MCP Servers puissent effectuer des actions telles que l’envoi, la publication ou l’écriture sans surveillance, veuillez transmettre explicitement une liste de préautorisation dans le corps de la requête :

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "Mon service a déclenché une alerte. Utilise mon compte WeChat personnel pour envoyer une notification au groupe WeChat « Équipe AceDataCloud »……"
}
```

Les valeurs de `allowed_skills` correspondent aux slugs des Skills connectés ; les valeurs de `allowed_mcp_servers` correspondent aux slugs des MCP Servers connectés. Les Skills / MCP Servers qui ne figurent pas dans la liste de préautorisation ne peuvent toujours, en mode sans surveillance, que prévisualiser, effectuer un dry-run ou refuser les opérations d’écriture.

Si vous avez besoin d’un contrôle plus précis, vous pouvez également utiliser l’objet équivalent `unattended_policy` :

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

La préautorisation correspond uniquement à ces deux listes : une liste vide signifie qu’aucune capacité n’est autorisée. Aucun champ d’activation supplémentaire n’est nécessaire.

Remarque : la préautorisation signifie uniquement que « cette requête autorise ces capacités à ignorer la confirmation humaine en mode sans surveillance ». Le Skill concerné doit toujours prendre en charge `--unattended-confirm` ou un mécanisme de sécurité équivalent ; dans le cas contraire, il continuera à effectuer un dry-run et n’exécutera pas directement les opérations d’écriture.

## Reprendre les conversations suspendues

Certains outils peuvent amener le modèle à « poser une question à l’utilisateur ». Dans ce cas, le modèle émet un événement `ask_user_question` et la conversation est suspendue dans l’état `awaiting_user_input` :

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "Souhaitez-vous que le rapport généré soit en chinois ou en anglais ?",
  "options": ["Chinois", "Anglais"],
  "id": "f2f4b3e8-..."
}
```

Dans l’interface utilisateur, affichez cet événement sous forme de carte afin que l’utilisateur puisse sélectionner une réponse, puis envoyez une nouvelle requête avec le même `id`, en transmettant la réponse via `tool_results` :
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

Dans le corps de la requête, `tool_use_id` **doit** correspondre exactement au `tool_id` au moment de la suspension ; toute incohérence entraînera une réponse 400. Lorsque `tool_results` est présent dans la requête, `question` / `message` / `references` sont tous ignorés.

Si l'utilisateur décide d'abandonner cette question, il suffit de transmettre un nouveau `question` / `message` ; la plateforme marquera automatiquement l'appel d'outil suspendu comme « ignoré par l'utilisateur ».

## Gestion des conversations (CRUD)

v2 fournit une gestion légère des conversations via le champ `action` sur le même endpoint, sans nécessiter d'API supplémentaire.

### `action: retrieve` —— Récupérer une conversation

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

Renvoie le document complet de la conversation (y compris l'historique `messages`, `model`, `title`, `tools_used`, etc.).

### `action: retrieve_batch` —— Lister les résumés des conversations

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

Renvoie `{ items: [...], total }`. **Les résumés ne contiennent pas `messages`**, ce qui convient à l'affichage d'une liste dans une barre latérale ; lorsque l'utilisateur ouvre une conversation, utilisez ensuite `action: retrieve` pour récupérer séparément l'ensemble de ses messages.

Paramètres de filtrage facultatifs : `user_id`, `application_id`, `model_group`, `model`.

### `action: update` —— Modifier le titre ou réécrire l'historique

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "杭州旅行计划"
}
```

Il est également possible de transmettre `messages`, mais le serveur effectuera une validation stricte du schéma (ils doivent obligatoirement respecter la forme `ToolUseContent` après aplatissement) ; en cas de non-conformité, une réponse 400 sera renvoyée. En général, il est uniquement recommandé de l'utiliser pour modifier `title`.

### `action: delete` —— Supprimer une conversation

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Renvoie `{ id, success: true }`. Une fois supprimée, la conversation ne peut pas être récupérée ; veuillez confirmer avant d'effectuer l'appel.

## Migration fluide depuis v1

Si vous utilisez déjà [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations), la migration vers v2 ne nécessite pratiquement aucune modification du code :

1. Remplacez l'URL `https://api.acedata.cloud/aichat/conversations` par `https://api.acedata.cloud/aichat2/conversations`.
2. Si vous utilisiez auparavant des noms de modèles v1 (tels que `gpt-3.5`, `gpt-4-browsing`, etc.), il est recommandé de passer à des modèles contemporains lors de la migration vers v2 (tels que `gpt-5.4`, `claude-opus-4-8`, `gemini-3.1-pro-preview`, etc.).
3. Les champs du flux NDJSON restent rétrocompatibles : chaque événement `text_delta` contient toujours `delta_answer` et `id`. Par conséquent, les clients qui analysaient auparavant `delta_answer` ligne par ligne n'ont pas besoin d'être modifiés.

Après la migration, vous pouvez activer les nouvelles fonctionnalités de v2 selon vos besoins (messages multimodaux `message`, SSE, appels d'outils, CRUD via `action`) et procéder progressivement.

## Gestion des erreurs

Les réponses d'erreur suivent un format uniforme :

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

Erreurs courantes :

- `400 bad_request` : champ obligatoire manquant, `tool_use_id` non correspondant, schéma `messages` invalide, etc.
- `401 invalid_token` : en-tête `authorization` incorrect.
- `404 not_found` : la conversation correspondant à `id` n'existe pas lors de l'utilisation de `action: retrieve / update / delete`.
- `413 conversation_storage_limit` : la conversation dépasse la limite de stockage, sans écraser les enregistrements sauvegardés existants.
- `429 too_many_requests` : la limite de débit a été atteinte.
- `503 context_compaction_failed` : échec de la consolidation du contexte, les enregistrements existants sont conservés.
- `500 conversation_persist_failed` : échec de l'enregistrement final de ce tour ; la réception du texte ne signifie pas que l'enregistrement final a été sauvegardé avec succès. Veuillez effectuer une recherche par ID de conversation.
- `500 chat_error` : le service est temporairement indisponible ou aucun contenu n'a été généré au cours de ce tour (aucun frais ne sera facturé).

Dans les réponses en streaming, les erreurs sont émises sous forme d'événements `{"type":"error","message":"..."}`, puis le flux prend fin. `[DONE]` indique uniquement la fin du transfert ; en présence de `error`, la requête ne peut pas être considérée comme réussie et aucun événement `done` de réussite ne sera envoyé.

## Conclusion

Tout en garantissant la rétrocompatibilité avec v1, l'API AI Chat v2 fait évoluer les conversations de « questions-réponses en un ou plusieurs tours » vers des « conversations observables de type Agent » : entrées multimodales, appels d'outils, suspension / reprise, événements structurés en streaming et CRUD intégré. Il est recommandé d'utiliser directement v2 pour toute nouvelle intégration ; les intégrations v1 existantes peuvent migrer progressivement et en douceur. Pour toute question, n'hésitez pas à contacter notre équipe d'assistance technique.
