---
title: "AceDataCloud Application のグローバル残高共有を設定する"
description: "Platform API guide - Ace Data Cloud"
---

`allow_consume_global` を設定します。有効化すると、条件を満たす従量制 Application は自身の残高が不足した場合でも、アカウントのグローバル残高を引き続き使用できます。

## 準備作業

- [Account Token](https://platform.acedata.cloud/documents/platform-token) を作成し、安全に保存します。
- [サービス申請リスト](https://platform.acedata.cloud/documents/platform-application-list)から、自身が所有する `application_id` を取得します。

```shell
export PLATFORM_TOKEN='你的账户令牌'
export APPLICATION_ID='你的 Application ID'
```

## API 概要

| 項目    | 内容                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------- |
| メソッド   | `POST`                                                                                             |
| URL  | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| 認証   | Account Token                                                                                      |
| Body | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

成功時には、更新後の Application オブジェクトが返されます。リクエスト値が必ず保存されたと仮定せず、レスポンス内の `allow_consume_global` を基準にしてください。

> `Period` タイプの Application はグローバル残高の消費を許可されていません。`true` をリクエストしても、サーバー側ではこのフィールドが `false` のまま維持されます。

## エラー処理

- `401`：Account Token が無効または欠落しています。
- `403`：現在のアカウントはこの Application の所有者ではありません。
- `404`：Application ID が存在しません。

グローバル残高のチャージ入口および利用可能なプランは、プラットフォームコンソールと[注文作成](https://platform.acedata.cloud/documents/platform-order-create)で返される実際のプランに従ってください。`Wallet` タイプのプランが存在すると仮定しないでください。

## 許可された超過利用のアプリケーション

従量制アプリケーションの読み取り専用フィールドが `allow_overdraft=true` の場合、そのアプリケーションは残高がマイナスになっても自身の残高から引き続き料金を差し引くことができ、残高不足を理由にグローバルアカウントへ切り替わることはありません。超過利用が有効でないアプリケーションは引き続き `allow_consume_global` に従います。切り替え後に超過利用が許可されるかどうかは、実際に課金されるグローバル Application の設定に従います。

## トライアルアカウントの同時実行制限

システムは、読み取り専用のユーザーマーク `has_recharged` を使用して、支払いを伴うチャージが正常に完了したか、または管理者によって手動でクレジットが追加されたことがあるかを記録します。このマークは操作が成功した後に更新され、既存ユーザーについては注文または明確な加点記録に基づいて一括補完されます。支払いを伴うチャージを行ったことがなく、かつ管理者による手動の加点も受けたことがないアカウントは、アカウント全体で同時に実行できる課金リクエストは 1 件のみです。異なる API Key および異なるサービスでも、この 1 件の枠を共有します。報酬、引換カード、および譲渡された利用枠は、支払いを伴うチャージとは見なされません。支払いを伴うチャージを完了したか、または管理者によって手動でクレジットを追加されたことがあるアカウントは、このトライアル同時実行制限の対象外ですが、引き続き既存の残高および認証情報の利用枠チェックに従います。

すでにリクエストが実行中の場合、新しいリクエストは `429 too_many_requests` を返します。タスク照会などの無料ポーリング API は引き続き正常に呼び出すことができます。Realtime の接続認証は既存のラウンドごとの課金フローに従い、この通常リクエスト枠を占有しません。

非同期 API が「受理済み」を返した場合でも、タスクは引き続き実行中です。次の生成リクエストを送信する前に、最終結果を待つ必要があります。ネットワーク切断またはプロキシのタイムアウトは、タスクが停止したことを意味しません。タスクが長時間にわたり終端状態にならない場合は、`trace_id` を添えてサポートへお問い合わせください。

この制限は、試用可能な API を変更するものではなく、既存の課金ルールも変更しません。料金は引き続きリクエスト終了後に実際の使用量に応じて精算されます。
