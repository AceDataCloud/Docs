Ace Data Cloud X402 は現在 USDC 決済を中心としており、EVM と Solana の2種類のチェーンをサポートしています。ネットワークごとに署名方式、資産アドレス、gas の挙動、および適用シナリオが異なるため、統合前にネットワークを選択する必要があります。

## ネットワーク識別子は CAIP-2 を使用

x402 v2 の `accepts[].network` は CAIP-2 識別子であり、`base`、`solana` のような略称ではありません。クライアントがネットワークを照合する際は、CAIP-2 文字列で比較する必要があります：

| ネットワーク             | CAIP-2 識別子                                 |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## サポートマトリクス

| ネットワーク     | scheme  | 資産                  | 署名方式                                 | 適用シナリオ                     |
| ------ | ------- | ------------------- | ------------------------------------ | ------------------------ |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | デフォルト推奨、ウォレットと流動性のサポートが成熟。         |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | チャット、モデルなどの後払い計測 API。          |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Solana ウォレット、Agent またはオンチェーンアプリケーションのシナリオ。 |

`upto` は現在 Base でのみ提供されています。実際に利用可能な項目は API が返す `accepts` に従います。Facilitator を確認することもできます：

```bash
curl https://facilitator.acedata.cloud/supported
```

Facilitator `/supported` の返却：

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

結果の説明：

- Base と Solana の `exact` は固定金額の支払いパスです。
- Base のみが `upto` 後払い計測パスを提供しており、Permit2 approve に依存します。
- `upto` エントリ内の `extra.facilitatorAddress` は、クライアントが署名時に witness へ書き込むアドレスであり、サーバーが返す値と一致しなければなりません。

## Base

Base は公式 USDC コントラクトを使用します：

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

`exact` スキームでは、クライアントは EIP-712 `TransferWithAuthorization` に署名します。署名内容には以下が含まれます：

- `from`：支払いウォレットアドレス
- `to`：Ace Data Cloud の受取アドレス
- `value`：今回の支払い金額
- `validAfter` / `validBefore`：署名の有効時間ウィンドウ
- `nonce`：32バイトのランダム nonce

Facilitator は署名を検証した後、オンチェーンで USDC の `transferWithAuthorization` を呼び出して送金を完了します。

Base は最も推奨される本番統合ネットワークであり、特に `upto` 後払い計測に適しています。これは Permit2、USDC、およびウォレットのエコシステムがより成熟しているためです。

Base `exact` 検証結果の例：

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

結果の説明：

- API の paid retry はモデルコンテンツ `ADC_BASE_E2E_OK` を返します。
- オンチェーン取引は BaseScan で確認でき、ブロック番号は `46726299` です。
- `95215` atomic USDC は `0.095215` USDC に相当し、今回の API 呼び出しの実際の決済金額です。

注文支払い Base `exact` のプログラム実行結果：

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

結果の説明：

- プラットフォーム注文の最終状態は `Finished` です。
- 注文の `pay_id` には同じ Base 取引ハッシュが書き込まれます。
- `1200000` atomic USDC は `1.2` USDC に相当し、旧ポリシーにおけるこの 10 Credits 注文の過去の実支払い金額です。新規注文では X402 支払い方法の割引は追加で適用されなくなり、具体的な署名金額は今回の 402 レスポンスに従います。

## Solana

Solana は SPL USDC `TransferChecked` を使用します。クライアントは送金トランザクションを構築し、署名して送信した後、トランザクション署名またはシリアライズ済みトランザクションを `PAYMENT-SIGNATURE` envelope に格納します。

Solana の特徴：

- Solana wallet adapter または base58 secret key を使用；
- 資産は Solana USDC mint；
- 現在は `exact` のみサポート；
- Facilitator は transfer instruction の mint、destination、authority、および amount を検証します。

ウォレット fee payer モードを使用する場合、ウォレットが直接トランザクションを送信し、Facilitator はトランザクションの確認と settlement 結果の返却を担当します。

Solana `exact` 検証結果の例：

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

結果の説明：

- paid retry はすでに HTTP 200 を返しており、モデルは `ADC_SOLANA_E2E_OK` を出力しています。
- パブリック RPC でオンチェーン signature を照会する際、レート制限に遭遇する可能性があります。
- パブリック RPC の照会はレート制限される可能性があるため、ここでは Solana explorer を記載しません。厳密な照合が必要な場合は、自前の Solana RPC またはプラットフォーム側の決済記録を使用してトランザクション署名を確認してください。

## 選択方法

| 何をしたいか        | 推奨ネットワーク           |
| ------------ | -------------- |
| 最小フローを迅速に通す     | Base `exact`   |
| 一般的な Web3 ユーザー向け | Base           |
| チャット補完などの後払い計測を行う   | Base `upto`    |
| Solana エコシステムアプリケーション  | Solana `exact` |

どのチェーンを選択する場合でも、クライアントに価格をハードコードしないでください。価格はサーバーが返す `accepts[].maxAmountRequired` によって決まります。

## 新しい EVM ネットワークの追加
以下のネットワークにおけるネイティブ USDC の固定金額支払いはコードでサポートされており、ネットワークごとに順次公開されます。
利用可能かどうかは注文または API が返す `accepts` に準拠します。すべてのネットワークが本番環境で有効になっていることを意味するものではありません。

| Network      | Alias      | CAIP-2         | Native USDC                                  |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

これらのネットワークは `exact` のみをサポートし、通貨精度は 6 です。同名のブリッジ USDC を使用しないでください。
公式 TypeScript/Python X402 Client を使用する場合、表内の略称または CAIP-2 識別子を渡すことができます。
クライアントは対象チェーン ID を使用して署名を構築します。ウォレットは対象ネットワークをサポートしている必要があります。

Phantom 拡張ウォレットの公式サポート表には Arbitrum と Polygon が掲載されています。Optimism、Avalanche
は現在この表に掲載されていないため、対象チェーンをサポートする Rabby または MetaMask を使用できます。EVM アドレスは異なるチェーン間で同一にすることができますが、
残高は相互に独立しており、Solana アドレスは EVM USDC には適用されません。
[Phantom ウォレットのサポート表](https://docs.phantom.com/wallet-sdks-overview#chain-support)を参照してください。

### 新ネットワークのカナリア公開入口

新しいチェーンの入口はデフォルトで非表示です。コンソールまたは Studio にアクセスする際、`?features=x402-arbitrum`
を使用して対応するチェーンを有効にできます。複数の flag はカンマで区切ります。単一チェーンを無効にするには `?features=-x402-arbitrum` を使用し、
ローカルの上書きをクリアするには `?features=none` を使用します。スイッチはドメインごとに保存されます。
注文見積もりと支払い再試行では同じスイッチを使用し、サーバー側で独立して検証されます。既存の支払い記録は引き続き閲覧できます。
ページの flag のみを有効にしても、まだ設定されていないチェーンは有効になりません。実際に支払い可能なネットワークは、引き続きリアルタイムの `accepts` に準拠します。
