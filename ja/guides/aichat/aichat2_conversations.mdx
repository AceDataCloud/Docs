AI Chat v2 API（`/aichat2/conversations`）は、新世代の対話インターフェースであり、[AI Chat API](https://platform.acedata.cloud/documents/aichat-conversations) を全面的にアップグレードしたバージョンです。v1 のシンプルでホスト型のマルチターン対話機能を基盤として、以下の機能が拡張されています。

- **マルチモーダルユーザー入力**：構造化された `message` フィールドを通じて、テキスト + 画像 + ファイルブロックを直接送信できます。事前に `references` を使用して間接的に添付する必要はありません。
- **Agent 型ツール呼び出し**：インターネット検索、Web ページ取得、ファイル読み取りなどのツールが組み込まれており、ユーザーが認証した MCP サーバー（Google Drive、Notion、Slack、GitHub など）も接続できます。モデルは1回のリクエスト内で複数回にわたり自律的にツールを呼び出し、複雑なタスクを完了できます。
- **構造化ストリーミングイベント**：`accept: text/event-stream` または `application/x-ndjson` を通じて、トークン単位の `text_delta`、`tool_use`、`tool_result`、`thinking`、`citation`、`card`、`artifact` などのイベントを取得できます。これにより、フロントエンドで対応する種類ごとに個別にレンダリングできます。
- **中断 / 再開が可能**：ユーザーによる追加情報が必要な場合、モデルは `ask_user_question` イベントを発行して一時停止します。次回の呼び出し時に `tool_results` を通じて回答を返すだけで、処理を続行できます。
- **新しい CRUD アクション**：同じ endpoint 上で `action` フィールドを使用して `retrieve` / `retrieve_batch` / `update` / `delete` を実行でき、追加のセッション管理 API は不要です。
- **継続的に更新されるモデル一覧**：デフォルトで GPT-5.4、Claude Opus 4.8、Claude Sonnet 4.6、Gemini 3.1 Pro、GLM 5.1、DeepSeek V4、Kimi K3 などの最新モデルに対応しています。

同時に、リクエストボディのレベルでは**v1 と完全な後方互換性**があります。`model` + `question`（+ オプションの `stateful` / `id` / `references` / `preset`）のみを送信すれば、v1 と同等の `{answer, id}` JSON レスポンスを取得できます。そのため、`/aichat/conversations` から移行する際にクライアントを書き直す必要はなく、パスを `/aichat2/conversations` に変更するだけで済みます。

> 現在 `/aichat/conversations` を使用している場合でも、旧インターフェースは引き続き利用できます。ご自身のペースで移行できます。

## 基本的な使い方

最も簡単な使用方法は v1 とまったく同じです。`model` + `question` を送信し、`{answer, id}` を取得します。

CURL の例：

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。"
  }'
```

レスポンス結果：

```json
{
  "answer": "AceDataCloud 是一个聚合主流 AI 模型与多模态服务的统一 API 平台，开发者通过一个密钥即可调用 GPT、Claude、Gemini、Midjourney、Suno、Veo 等多家服务。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Python の例：

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

## マルチターン対話

v1 と同様に、`stateful: true` を送信してセッション保存を有効にすると、API は `id` を返します。以降のリクエストで同じ `id` を送信すれば、自分で messages の履歴を管理することなく、対話を続けることができます。

最初のリクエスト：

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "记住一个数字：42。"
  }'
```

レスポンス：

```json
{
  "answer": "好的，我已经记住了 42。需要我用它做什么吗？",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

2回目のリクエストでは、同じ `id` を付けます：
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "先ほど私に覚えておくように頼んだ数字は何ですか？"
  }'
```

```json
{
  "answer": "あなたが私に覚えておくように頼んだ数字は42です。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` のデフォルト値は `true` であり、省略することと明示的に `true` を渡すことは同じです。`stateful: false` を設定すると、以前の会話履歴の読み込みがスキップされます。これは今回の結果が保存されないことを意味するものではなく、一時停止後に再開する必要があるツールフローには適用されません。

### 長時間の会話と原文の保持

コンテキストの圧縮では、今回モデルに送信する内容を整理するだけで、保存済みのチャット履歴が置き換えられることはありません。`action: retrieve` を使用すれば、保存済みのメッセージ全体を引き続き読み取ることができます。会話の明示的な編集や削除も、引き続きリクエストどおりに反映されます。

モデルは現在の会話内で履歴の原文を検索し、ページ単位で読み取ることができます。記事の編集を続けたり、数字を引用したり、公開の準備をしたりする場合は、対応する原文を読み取る必要があり、本文の代わりに要約を使用してはいけません。この機能では、以前のバージョンですでに失われたメッセージが自動的に復元されることはありません。

コンテキストの整理に失敗した場合は、会話 ID を保持し、`error` イベントを確認してください。サービスが空の要約で原文を上書きすることはありません。失敗する前に完了したツール操作は、引き続き有効な場合があります。重複生成や重複公開を避けるため、まずその結果を確認してください。1つの会話がストレージ上限に達した場合は、明確なエラーが返されます。既存の保存記録は、切り詰めることで空き容量を確保することはありません。必要な内容をエクスポートした後、新しい会話を開始できます。

## ストリーミング応答

v2 は2種類のストリーミング形式に対応しており、`accept` ヘッダーに応じて選択されます。

| シナリオ | `accept` | データ形式 |
| --------------------- | ---------------------- | ------------------------------------------ |
| Web フロントエンド / EventSource | `text/event-stream` | `data: {json}\n\n`、最後の行は `data: [DONE]\n\n` |
| サーバー / CLI / Node ストリーミング解析 | `application/x-ndjson` | 1行につき1つの JSON オブジェクト |
| ストリーミング不要 | `application/json`（デフォルト） | `{answer, id}` を一括で返す |

### NDJSON の例

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "杭州を3文で紹介してください。",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # v1 との互換性：増分テキストは delta_answer フィールドでも同時に提供されます
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

NDJSON の各行は構造化イベントであり、最も一般的なのは `text_delta` です。

```json
{"type":"text_delta","content":"杭","delta_answer":"杭","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"州","delta_answer":"州","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"は","delta_answer":"は","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### SSE の例

ブラウザー側の `EventSource` はカスタムリクエストボディに対応していないため、`fetch` と `\n\n` による手動分割解析の使用を推奨します。

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "杭州を3文で紹介してください。",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### ストリーミングイベントの種類

| `type` | 意味 |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `text_delta` | アシスタントの回答の増分テキスト。`content` は新たに追加された内容です。v1 との互換性を保つため、同じイベントには `delta_answer`（`content` と同じ値）と `id` も含まれます。 |
| `thinking` | モデルの思考プロセス（選択したモデルが reasoning を公開する場合のみ表示されます）。 |
| `tool_use` | モデルがツールの呼び出しを決定したことを示します。イベントには `tool_id`、`tool_name`、`input` が含まれます。 |
| `tool_result` | ツールの実行結果です。直前の `tool_use` と `tool_id` によって対応付けられ、`is_error` は失敗したかどうかを示します。 |
| `card` | ツールが生成した構造化カード（画像、リンクプレビューなど）で、直接レンダリングするのに適しています。 |
| `citation` | 対応するテキスト部分の引用元 URL を補足するために使用されます。 |
| `ask_user_question` | モデルがユーザーに追加情報を求める際に発行されます。会話は `awaiting_user_input` 状態に移行します。詳細については、以下の[一時停止した会話の再開](#一時停止した会話の再開)を参照してください。 |
| `artifact` | モデルが生成した独立した成果物（コードブロック、ドキュメントなど）で、保存またはダウンロードできます。 |
| `system_message` | システムからの通知情報（ユーザーとアシスタントの内容ではありません）で、UI 上の通知にのみ使用されます。 |
| `compact` | モデルのコンテキストが整理されたことを示します。保存済みの元のメッセージは変更されないため、クライアント側でチャット履歴を削除する必要はありません。 |
| `error` | 今回の処理でエラーが発生したことを示し、`message` にエラーの内容が記述されます。 |
| `done` | 今回の最終的な会話記録の保存が成功したことを示します。`usage`（`prompt_tokens` / `completion_tokens` / `total_tokens` を含む）と `terminal_reason` が含まれます。タスクが完了したかどうかは、引き続き終了理由に基づいて判断する必要があります。 |
最終的な回答のみを必要とするクライアントの場合、すべての `text_delta` の `content` を連結すると、`application/json` モードの `answer` と同等になります。

## マルチモーダル入力

ユーザーの入力に画像またはファイルが含まれる場合は、`question` の代わりに `message`（配列）を渡します。配列の各要素はコンテンツブロックです。

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "この画像には何匹の猫がいますか？" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

サポートされているブロックタイプ：

- `text` — 通常のテキスト。`text` フィールドが必須です。
- `image_url` — 画像。`image_url.url` が必須です。
- `file_url` — ファイル（PDF、CSV、TXT など）。`file_url.url` が必須です。

### v1 の `references` との関係

旧クライアントとの互換性を保つため、v2 でも引き続き `references: ["https://...", ...]` フィールドを認識します。

- URL の拡張子が `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif` の場合、自動的に `image_url` ブロックに変換されます。
- その他の拡張子は `file_url` ブロックに変換されます。
- 同時に `question` も指定されている場合、それを先頭の `text` ブロックとして追加します。

したがって、v1 から移行する際にリクエストボディを変更したくない場合は、パスを `/aichat2/conversations` に変更するだけで、従来の `references` の使用方法をそのまま利用できます。

より細かく制御したい場合（たとえば、複数の画像をテキストの間に配置する場合や、順序が重要な場合）は、直接 `message` 配列を使用してください。

## ツール呼び出しと MCP

v2 の主な強化点は、モデルが自律的にツールを呼び出して複数ステップのタスクを完了できることです。**これはデフォルトで有効になっており**、クライアント側でリクエストに追加設定を行う必要はありません。一般的な使用例：

- ユーザーが「上海で最近開催される新しい展覧会を検索して」と尋ねる → モデルが組み込みの Web Search を呼び出す → 結果を整理して回答する。
- ユーザーが「この PDF を読んで要約を書いて」と尋ねる → モデルが file_read を呼び出す → 要約を作成する。
- ユーザーが [Connections](https://platform.acedata.cloud/connections) で Google Drive / GitHub / Notion などをすでに認証している → モデルは対応する MCP ツールを呼び出して、そのデータを読み書きできる。

NDJSON / SSE ストリームでは、ツール呼び出しは `tool_use` と `tool_result` の2種類のイベントで表されます。例：

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"上海 2026 春季展覧会"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"現在","delta_answer":"現在","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"上海","delta_answer":"上海","id":"f2f4b3e8-..."}
...
```

フロントエンドでツール呼び出しの詳細を表示したくない場合は、`tool_use` / `tool_result` / `card` / `citation` の各イベントを無視するだけで構いません。モデルの最終出力は引き続き `text_delta` を通じて送信されます。

`max_turns` を使用すると、今回のリクエストでモデルがツールを自己呼び出しできる最大回数を制限できます。範囲は1～500で、省略した場合のデフォルト値は500です。値を小さく設定する（たとえば `max_turns: 1`）ことで、単一の回答を強制し、すべてのツール呼び出しを禁止できます。

## 非同期実行と無人実行の事前承認

アラート Webhook、CI/CD、監視システム、その他のバックグラウンドタスクから呼び出す場合は、`async: true` を設定すると、API はタスク ID を即座に返し、バックグラウンドで処理を継続します。

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "サービスでアラートが発生しました。個人の WeChat を使ってグループチャット「AceDataCloudチーム」に通知してください……"
}
```

戻り値の例：

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

その後、`action: retrieve` と `id` を使用して会話の結果を取得できます。また、`callback_url` を指定することもできます。タスクの完了後、プラットフォームは `{ status, answer, usage, error }` をコールバック URL に POST します。`callback_url` には `http` / `https` を使用する必要があり、`localhost` またはプライベート IP のリテラルアドレスを直接指定することはできません。

バックグラウンドタスクでは、通常、誰かがクリックして確認することはできません。無人実行モードで一部の Skill または MCP Server に送信、公開、書き込みなどの操作を実行させたい場合は、リクエストボディで事前承認リストを明示的に指定してください。

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "サービスでアラートが発生しました。個人の WeChat を使ってグループチャット「AceDataCloudチーム」に通知してください……"
}
```

`allowed_skills` の値は、接続済み Skill の slug です。`allowed_mcp_servers` の値は、接続済み MCP Server の slug です。事前承認リストに含まれていない Skill / MCP Server は、無人実行モードでもプレビュー、dry-run、または書き込み操作の拒否のみが可能です。

より細かい制御が必要な場合は、同等の `unattended_policy` オブジェクトを使用することもできます。

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

事前承認は、この2つのリストそのものによって決まります。リストが空の場合は、いかなる機能も承認されていないことを意味し、追加の有効化フィールドは必要ありません。

注意：事前承認は、「今回のリクエストで、これらの機能が無人実行モードにおいて人間による確認を省略することを許可する」という意味にすぎません。各 Skill は引き続き `--unattended-confirm` または対応するセキュリティメカニズムをサポートしている必要があります。そうでない場合は、引き続き dry-run が実行され、書き込み操作が直接実行されることはありません。

## 一時停止した会話の再開

一部のツールでは、モデルが「ユーザーに質問を返す」ことがあります。このとき、モデルは `ask_user_question` イベントを送信し、会話は `awaiting_user_input` 状態で一時停止されます。

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "生成するレポートは中国語と英語のどちらにしますか？",
  "options": ["中国語", "英語"],
  "id": "f2f4b3e8-..."
}
```

フロントエンドでこのイベントをカードとして表示し、ユーザーに回答を選択してもらいます。その後、同じ `id` を使用して次のリクエストを開始し、回答を `tool_results` に渡して補完します。
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

リクエストボディ内の `tool_use_id` は、一時停止時の `tool_id` と**必ず**完全に一致している必要があります。一致しない場合は 400 が返されます。リクエストに `tool_results` が同時に含まれている場合、`question` / `message` / `references` はすべて無視されます。

ユーザーがこの質問を放棄すると決めた場合は、新しい `question` / `message` を直接送信するだけで、プラットフォームが一時停止中のツール呼び出しを自動的に「ユーザーによるスキップ」としてマークします。

## 会話管理（CRUD）

v2 では、同じ endpoint 上で `action` フィールドを使用して軽量な会話管理機能を提供しており、別途 API を用意する必要はありません。

### `action: retrieve` —— 会話の取得

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

会話ドキュメント全体（`messages` 履歴、`model`、`title`、`tools_used` などを含む）が返されます。

### `action: retrieve_batch` —— 会話の概要一覧を取得

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

`{ items: [...], total }` が返されます。**概要には `messages` は含まれません**。サイドバーの一覧表示に適しています。ユーザーが会話を開いた場合は、`action: retrieve` を使用して、その会話の完全なメッセージを個別に取得してください。

オプションのフィルタリングパラメータ：`user_id`、`application_id`、`model_group`、`model`。

### `action: update` —— タイトルの変更または履歴の書き換え

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "杭州旅行計画"
}
```

`messages` も渡すことができますが、サーバー側で厳格な schema 検証が行われます（折りたたまれた `ToolUseContent` 形式である必要があります）。条件を満たさない場合は 400 が返されます。通常は `title` の変更のみに使用することを推奨します。

### `action: delete` —— 会話の削除

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

`{ id, success: true }` が返されます。削除後は復元できないため、呼び出す前に必ず確認してください。

## v1 からのスムーズな移行

すでに [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations) を使用している場合、v2 への移行に必要なコード変更はほとんどありません。

1. URL を `https://api.acedata.cloud/aichat/conversations` から `https://api.acedata.cloud/aichat2/conversations` に変更します。
2. 以前 v1 のモデル名（`gpt-3.5`、`gpt-4-browsing` など）を指定していた場合、v2 への切り替え時に、現行モデル（`gpt-5.4`、`claude-opus-4-8`、`gemini-3.1-pro-preview` など）へのアップグレードを推奨します。
3. NDJSON ストリームのフィールドは後方互換性を維持しています。各 `text_delta` イベントには引き続き `delta_answer` と `id` が含まれるため、従来どおり `delta_answer` を行単位で解析するクライアントは変更する必要がありません。

移行後は、必要に応じて v2 の新機能（マルチモーダルな `message`、SSE、ツール呼び出し、`action` CRUD）を有効にし、段階的に導入できます。

## エラー処理

エラーレスポンスは以下の形式に統一されています。

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

よくあるエラー：

- `400 bad_request`：必須フィールドの不足、`tool_use_id` の不一致、`messages` schema の不正など。
- `401 invalid_token`：`authorization` ヘッダーが正しくありません。
- `404 not_found`：`action: retrieve / update / delete` の実行時に、指定された `id` に対応する会話が存在しません。
- `413 conversation_storage_limit`：会話がストレージ制限を超過しており、既存の保存済み記録は上書きされていません。
- `429 too_many_requests`：レート制限に達しました。
- `503 context_compaction_failed`：コンテキストの整理に失敗しました。既存の記録は保持されます。
- `500 conversation_persist_failed`：今回の最終保存に失敗しました。テキストを受信できたとしても、最終的な記録の保存が成功したとは限りません。会話 ID を使用して照会してください。
- `500 chat_error`：サービスが一時的に利用できないか、今回の内容が生成されませんでした（料金は発生しません）。

ストリーミングレスポンスでは、エラーは `{"type":"error","message":"..."}` イベントとして送信され、その後ストリームが終了します。`[DONE]` は転送の終了のみを意味します。`error` が存在する場合、成功とは見なせず、成功を示す `done` イベントも送信されません。

## 結論

AI Chat v2 API は、v1 との後方互換性を維持しながら、対話機能を「単一ターン / 複数ターンの質疑応答」から「Agent 化された可観測な対話」へと進化させました。マルチモーダル入力、ツール呼び出し、一時停止 / 再開、ストリーミングによる構造化イベント、組み込み CRUD に対応しています。

新規導入では v2 の直接利用を推奨します。既存の v1 統合については、段階的かつスムーズに移行できます。ご不明な点がございましたら、いつでも弊社のテクニカルサポートチームまでお問い合わせください。
