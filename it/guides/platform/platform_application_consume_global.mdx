---
title: "Configurare la condivisione globale del saldo di AceDataCloud Application"
description: "Platform API guide - Ace Data Cloud"
---

Configurare `allow_consume_global`. Dopo l'attivazione, le Application a consumo idonee possono continuare a utilizzare il saldo globale dell'account quando il proprio saldo è insufficiente.

## Preparazione

- Creare e conservare in modo sicuro l'[Account Token](https://platform.acedata.cloud/documents/platform-token).
- Ottenere l'`application_id` posseduto dall'[elenco delle richieste di servizio](https://platform.acedata.cloud/documents/platform-application-list).

```shell
export PLATFORM_TOKEN='你的账户令牌'
export APPLICATION_ID='你的 Application ID'
```

## Panoramica dell'interfaccia

| Voce    | Contenuto                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------- |
| Metodo   | `POST`                                                                                             |
| URL  | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| Autenticazione   | Account Token                                                                                      |
| Body | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

In caso di successo viene restituito l'oggetto Application aggiornato. Fare riferimento a `allow_consume_global` nella risposta, anziché presumere che il valore della richiesta venga necessariamente salvato.

> Le Application di tipo `Period` non sono autorizzate a consumare il saldo globale. Anche richiedendo `true`, il server manterrà questo campo su `false`.

## Gestione degli errori

- `401`: Account Token non valido o mancante.
- `403`: l'account corrente non è il proprietario di questa Application.
- `404`: Application ID inesistente.

Per l'accesso alla ricarica del saldo globale e i pacchetti disponibili, fare riferimento alla console della piattaforma e ai pacchetti effettivamente restituiti dalla [creazione dell'ordine](https://platform.acedata.cloud/documents/platform-order-create); non presumere l'esistenza di pacchetti di tipo `Wallet`.

## Applicazioni autorizzate allo scoperto

Quando il campo di sola lettura `allow_overdraft=true` di un'applicazione a consumo è impostato, questa applicazione può continuare ad addebitare dal proprio saldo e, anche se il saldo diventa negativo, non passerà all'account globale a causa di un saldo insufficiente. Le applicazioni senza scoperto abilitato continuano a seguire `allow_consume_global`; dopo il passaggio, l'eventuale autorizzazione allo scoperto dipende dalle impostazioni dell'Application globale effettivamente addebitata.

## Limite di concorrenza per gli account di prova

Il sistema utilizza il flag utente di sola lettura `has_recharged` per registrare se è stata completata con successo una ricarica a pagamento o se un amministratore ha aggiunto manualmente crediti; il flag viene aggiornato dopo il successo dell'operazione e gli utenti storici verranno aggiornati in modo uniforme in base agli ordini o a registrazioni esplicite di aggiunta di crediti. Per gli account che non hanno né effettuato una ricarica a pagamento né ricevuto crediti aggiunti manualmente da un amministratore, l'intero account consente l'esecuzione simultanea di una sola richiesta fatturabile; API Key e servizi diversi condividono questo unico posto. Ricompense, carte di riscatto e importi trasferiti non sono considerati ricariche a pagamento. Gli account che hanno già completato una ricarica a pagamento o ricevuto crediti aggiunti manualmente da un amministratore non sono soggetti a questo limite di concorrenza di prova e continuano a seguire i controlli originali del saldo e della quota delle credenziali.

Quando è già in esecuzione una richiesta, le nuove richieste restituiscono `429 too_many_requests`. Le interfacce gratuite di polling, come la consultazione delle attività, possono ancora essere chiamate normalmente. L'autenticazione della connessione di Realtime continua a utilizzare il flusso di fatturazione originale per ciclo e non occupa questo posto per le richieste normali.

Quando un'interfaccia asincrona restituisce “accettata”, l'attività è ancora in esecuzione ed è necessario attendere il risultato finale prima di inviare la successiva richiesta di generazione. La disconnessione di rete o il timeout del proxy non significano che l'attività sia stata interrotta; se l'attività non raggiunge uno stato finale per molto tempo, fornire `trace_id` e contattare il supporto per una verifica.

Questa limitazione non modifica le interfacce utilizzabili in prova, né modifica le regole di fatturazione originali. I costi vengono comunque regolati in base all'utilizzo effettivo dopo la conclusione della richiesta.
