---
title: "Schemi di fatturazione X402 `exact` e `upto`"
description: "Platform API guide - Ace Data Cloud"
---

Ace Data Cloud X402 utilizza attualmente due tipi di scheme: `exact` e `upto`. Risolvono problemi di fatturazione diversi.

## `exact`

`exact` indica che il prezzo può essere determinato prima che questa richiesta entri nell'API di destinazione. L'importo firmato dal client è l'importo finale addebitato.

Adatto per:

- Generazione di immagini a prezzo fisso;
- Creazione di attività video a prezzo fisso;
- API di ricerca o strumenti API a prezzo fisso;
- Pagamento degli ordini.

EVM `exact` utilizza USDC EIP-3009 `TransferWithAuthorization`:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": {
    "authorization": {
      "from": "0x...",
      "to": "0x...",
      "value": "95215",
      "validAfter": "1780237345",
      "validBefore": "1780240945",
      "nonce": "0x..."
    },
    "signature": "0x..."
  }
}
```

Il Facilitator verifica la firma e l'importo nella fase `/verify` e invia questa autorizzazione on-chain nella fase `/settle`.

## `upto`

`upto` indica che il client autorizza un limite massimo e Ace Data Cloud effettua il regolamento in base all'utilizzo effettivo dopo il completamento della richiesta; l'addebito effettivo non può superare il limite massimo.

Adatto per:

- Completamenti chat: il prezzo finale dipende dai prompt token e dai completion token;
- Risposte in streaming: la reale lunghezza dell'output è nota solo al termine;
- Future API con misurazione successiva.

`upto` utilizza Permit2 `PermitWitnessTransferFrom`. Il client non firma un trasferimento fisso, ma un'autorizzazione con limite massimo con witness:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2Authorization": {
      "from": "0x...",
      "spender": "0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002",
      "nonce": "123456789",
      "deadline": "1780240945",
      "permitted": {
        "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "amount": "95215"
      },
      "witness": {
        "to": "0x...",
        "facilitator": "0x...",
        "validAfter": "1780237345"
      }
    },
    "signature": "0x..."
  }
}
```

`permitted.amount` è il limite massimo, non necessariamente l'addebito finale. Il Gateway converte l'utilizzo effettivo in `amount` e lo passa al Facilitator nella fase `/record`. Il Facilitator consente il regolamento solo se `amount &lt;= permitted.amount`.

Risultato dell'esecuzione del programma Base `upto`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
elapsed_ms 5104
content ADC_BASE_UPTO_OK
id chatcmpl-DlcbyS4IT8kUAMo4Ri97HiIHc9T8V
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Spiegazione:

- Il limite di autorizzazione restituito nel 402 è `95215` atomic USDC e il client firma in base a questo limite.
- Dopo la risposta effettiva del modello, vengono regolati solo `3` atomic USDC; la transazione on-chain è consultabile su BaseScan.
- Questo risultato dimostra la differenza chiave di `upto`: l'importo firmato è un limite massimo e il settlement on-chain può essere inferiore al limite massimo.
- Se l'utilizzo effettivo supera il limite massimo, il Facilitator deve rifiutare il settlement e il client deve autorizzare nuovamente con un limite massimo più elevato.

`upto` è attualmente disponibile solo su Base. Quando è necessaria una misurazione successiva, utilizzare Base.

## Perché è necessario Permit2 approve

`upto` preleva infine USDC dal wallet pagatore tramite Permit2 attraverso il proxy x402. Prima del primo utilizzo, il wallet pagatore deve concedere a Permit2 una ERC-20 allowance una tantum.

CLI Python:

```bash
pip install 'acedatacloud-x402[cli]'
X402_PRIVATE_KEY=0x... acedatacloud-x402 approve-permit2 --network base
```

A livello di programma:

```python
from acedatacloud_x402 import EVMAccountSigner, approve_permit2

approve_permit2(
    rpc_url="https://mainnet.base.org",
    signer=EVMAccountSigner.from_private_key("0x..."),
    token_address="0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
)
```

Dopo il completamento dell'autorizzazione, ogni richiesta deve comunque firmare un nuovo envelope `upto`, poiché nonce, deadline, witness e limite massimo dell'importo sono tutti diversi.

## Regolamento a importo zero

`upto` supporta i casi in cui l'importo effettivo è 0. Ad esempio, se l'API di destinazione non produce correttamente un utilizzo fatturabile, il Gateway può passare `amount = "0"`. Il Facilitator restituisce un esito positivo, ma non invia una transazione on-chain.

Questo può evitare il problema di “la richiesta non è andata a buon fine ma vengono comunque addebitate commissioni on-chain”.

## Suggerimenti per la scelta

| Scenario                   | Suggerimento                       |
| -------------------------- | ---------------------------------- |
| API a prezzo fisso         | Utilizzare `exact`, la logica è semplice. |
| Pagamento degli ordini     | Utilizzare `exact`.                |
| Completamenti chat, fatturazione per token | Utilizzare Base `upto`. |
| Permit2 approve non ancora eseguito | Prima utilizzare `exact` per verificarne il funzionamento, poi passare a `upto`. |

Se non sei sicuro di quale scegliere, utilizza prima il comportamento predefinito dell'SDK; l'SDK selezionerà il payment requirement della rete corrispondente restituito dal server.

## Lista di controllo Base `upto`

Durante l'integrazione o la risoluzione dei problemi, assicurarsi che i seguenti parametri provengano dalla stessa risposta 402 e rimangano coerenti durante la firma del client:

| Parametro                  | Punto di controllo                                          |
| -------------------------- | ----------------------------------------------------------- |
| `network`                  | Deve essere `eip155:8453`.                                  |
| `scheme`                   | Deve essere `upto`.                                         |
| `extra.chainId`            | Il chain id di Base è `8453`.                               |
| `asset`                    | Utilizzare l'indirizzo del contratto Base USDC nella risposta 402. |
| `extra.facilitatorAddress` | Deve partecipare al witness e corrispondere a Facilitator `/supported`. |
| Permit2 allowance          | Il wallet pagatore deve prima autorizzare Permit2 per Base USDC. |

Errori comuni e modalità di gestione:

| Errore                                           | Modalità di gestione                                                                          |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `invalid_upto_evm_payload_invalid_signature` | Verificare che chain id, indirizzo del facilitator, domain Permit2, spender, account di firma e witness corrispondano alla risposta 402. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Eseguire Permit2 approve per USDC sulla chain di destinazione, quindi avviare nuovamente la richiesta. |
| `amount exceeds permitted amount`            | L'utilizzo effettivo supera il limite firmato; è necessario firmare nuovamente con un limite più alto. |
