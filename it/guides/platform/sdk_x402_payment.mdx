[X402](https://www.x402.org/) è un protocollo di pagamento on-chain “fatturato tramite HTTP 402” proposto da Coinbase: il server restituisce `402 Payment Required` alle richieste senza token, allegando il campo `accepts: [...]` che elenca chain / asset / prezzo accettabili; il client firma localmente un'autorizzazione (Permit2 / EIP-712 su EVM, autorizzazione al trasferimento di SPL token su Solana), inserisce l'envelope codificato in base64 nell'header `PAYMENT-SIGNATURE` e reinvia. Dopo la verifica, il server effettua effettivamente il regolamento on-chain, quindi restituisce il risultato di business.

> Il client X402 di Ace Data Cloud chiama direttamente l'API di destinazione e utilizza il `402 Payment Required` e `accepts` restituiti in tempo reale da tale richiesta come base per il prezzo e la firma. La capacità di pagamento del Facilitator può essere verificata su [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

Sia `@acedatacloud/sdk` sia `acedatacloud` espongono un hook `paymentHandler`: quando una richiesta inviata dallo SDK riceve un `402`, richiama l'handler da te iniettato per ottenere l'header `PAYMENT-SIGNATURE`, quindi reinvia la richiesta originale. Usando `@acedatacloud/x402-client` / `acedatacloud-x402` insieme allo SDK, **l'intero processo è completamente trasparente al codice di business**——ti basta usare `client.openai.chat.completions.create(...)`, e sembra esattamente uguale alla modalità token, ma sotto il cofano il pagamento è per chiamata e non richiede ricariche preventive.

Questo articolo:

- percorre realmente la catena «senza token + iniezione dell'handler X402» sul lato TS ([verifica T12](#quattro-verifica-di-esecuzione-reale))
- elenca le differenze tra le due catene di firma EVM / Solana
- fornisce tre adattamenti: modalità chiave privata `viem`, modalità wallet del browser e modalità Python `EVMAccountSigner`
- chiarisce il campo `preferScheme` / `prefer_scheme`, in cui è facile imbattersi in problemi

## I. Panoramica del protocollo (da leggere assolutamente)

Una chiamata X402 riuscita coinvolge **3 HTTP RTT**:

```text
1. SDK -> /openai/v1/chat/completions               (senza Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK interno -> paymentHandler({ url, method, body, accepts })   (firma locale, 0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (header PAYMENT-SIGNATURE iniettato)
   <- 200 + risposta di business   (il regolamento viene completato sul server)
```

L'envelope X402 è un JSON, codificato in base64 e inserito nell'header `PAYMENT-SIGNATURE`. Struttura (estratto):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

Il livello superiore dell'envelope è `x402Version: 2` e dichiara tramite l'oggetto `accepted` lo `scheme` e il `network` selezionati per questa volta (identificatore CAIP-2).

| scheme  | Significato                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Prezzo fisso (scenari a prezzo definito come generazione di immagini / video, ricerca ecc.). L'importo firmato = l'importo richiesto dal server.                                                         |
| `upto`  | Fatturazione a consumo (chat completions / tipo token). Si firma un importo **massimo**, mentre viene regolata effettivamente solo la parte utilizzata (basata su Permit2 + witness). **Fortemente consigliato** per API di tipo conversazione. |

`preferScheme` / `prefer_scheme` serve a scegliere una preferenza quando il server **fornisce simultaneamente più scheme**. Se il server espone solo `exact`, questo campo verrà ignorato; se viene impostato `upto` ma il server non lo espone, verrà usato come fallback il primo elemento corrispondente.

## II. TypeScript: due utilizzi, wallet del browser + viem sul server

### Installazione

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Versioni testate:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Firma completa di `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // obbligatorio per network='solana'
  evmProvider?: EVMProvider;                // obbligatorio per network='base', EIP-1193
  evmAddress?: string;                      // obbligatorio per network='base'
  preferScheme?: 'exact' | 'upto';
}
```

Il valore restituito è un `(ctx) => Promise&lt;{ headers: Record<string, string> }>` che corrisponde esattamente alla firma dell'hook `paymentHandler` dello SDK.

### Utilizzo 1: browser (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. Fai collegare il wallet all'utente
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. Passa alla mainnet Base
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. Costruisci il client SDK e inietta l'handler X402
//    Nota: non passare apiToken, per far seguire allo SDK il percorso 402
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // per le chat è obbligatorio upto
  })
});

// 4. Chiama normalmente
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Alla prima chiamata il browser mostrerà **due richieste di firma**: la prima è un approve una tantum di Permit2 per USDC (l'importo è `MaxUint256`, scritto on-chain); la seconda è la firma EIP-712 dell'envelope X402 (non va on-chain, serve solo alla verifica del facilitator). Le chiamate successive richiedono solo la seconda firma; dal punto di vista dell'esperienza è “fare clic una volta per firmare → ottenere il risultato”.

### Utilizzo 2: server Node + chiave privata viem (adatto a backend / CLI)

`@acedatacloud/x402-client` sul lato TS **accetta solo provider EIP-1193**——non gestisce direttamente le chiavi private. Negli scenari Node / CLI, l'approccio standard è usare [`viem`](https://viem.sh/) per incapsulare la chiave privata in un `WalletClient`, quindi passare attraverso l'adattamento EIP-1193 di [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) o quello interno di viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient 自带 EIP-1193 兼容的 .request()，可以直接当 evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request 满足 EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Se ritieni che l'adattamento EIP-1193 di viem non sia abbastanza stabile, puoi anche usare il più basso livello [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts), concatenando autonomamente il percorso `accepts → signed envelope → PAYMENT-SIGNATURE header` e saltando gli hook dell'SDK; tuttavia, è comunque consigliato scegliere prima `createX402PaymentHandler`, per evitare di dover gestire autonomamente gli aggiornamenti del protocollo.

### Utilizzo 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

Sulla chain Solana al momento viene esposto **solo lo scheme `exact`**, quindi `preferScheme` non ha effetto su Solana.

## III. Python: modalità chiave privata

`acedatacloud-x402` per Python segue il percorso di **firma diretta con la chiave privata** (senza astrazione EIP-1193), ed è più adatto a server / esecutori di attività.

### Installazione

```bash
pip install acedatacloud acedatacloud-x402
```

Versioni testate:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. 从私钥构造签名器
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. 构造 SDK：不传 api_token，让 SDK 走 402 路径
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # chat 类一定选 upto
    )
)

# 3. 正常调
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # 可选
    )
)
```

### Approve una tantum (solo la prima volta su EVM)

Su EVM Base, X402 usa Permit2 e richiede che il wallet esegua una volta un approve `MaxUint256` dell'USDC verso il contratto Permit2. `acedatacloud-x402` include `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Questa transazione deve essere inviata una sola volta; in seguito, tutti i pagamenti X402 EVM useranno questa autorizzazione. Solana non ne ha bisogno.

## IV. Verifica dell'esecuzione reale

Obiettivo del test: **l'SDK TS non riceve un token, viene iniettato un handler X402 e riesce a costruire e avviare normalmente le richieste** (una verifica leggera che non consuma vero USDC on-chain).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // 占位 provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Output:

```text
handler_type function
client_ctor_ok AceDataCloud
```

Il risultato indica:

- Non viene passato `apiToken` e la costruzione dell'SDK **non genera errori**, dimostrando che la modalità X402 è effettivamente un'alternativa valida al token.
- `createX402PaymentHandler` restituisce una funzione (hook), che l'SDK invocherà solo dopo aver ricevuto un 402.
- Il test end-to-end del pagamento effettivo on-chain, poiché comporta un reale addebito di USDC, non è incluso in questo tutorial; puoi fare riferimento all'esempio e2e nella [guida all'integrazione X402](https://platform.acedata.cloud/documents/x402-integration).

> Anche `create_x402_payment_handler` lato Python ha effettuato la stessa verifica: il valore restituito dalla funzione è callable e la costruzione di `AceDataCloud(...)` non genera errori quando viene iniettato `payment_handler=...`. La semantica è allineata su entrambi i lati.

## V. Confronto con la «modalità Bearer token»

| Dimensione              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Scenario applicabile            | Backend proprietario, progetti a lungo termine                                                         | Sviluppatori terzi, pagamenti su richiesta per singola volta, chiamate Agentic                        |
| Registrazione              | Richiede una richiesta nella [console](https://platform.acedata.cloud/console/applications) | Non necessaria; basta avere un wallet on-chain                                     |
| Precisione di fatturazione            | Ricarica anticipata, addebito secondo la tabella dei token                                                   | Registrazione on-chain in tempo reale per chiamata                                         |
| Saldo              | Consultabile nella console                                                           | Consultare l'USDC nel wallet on-chain                                      |
| Costo iniziale            | La registrazione via e-mail offre subito credito gratuito                                                        | Richiede il bridge di USDC su Base, primo approve Permit2              |
| Adatto alle richieste chat       | ✅                                                                 | ✅ (deve usare `preferScheme=upto`)                       |
| Adatto a pagamenti una tantum / pagamenti per conto terzi tra account | ❌                                                                 | ✅                                               |
| Modifiche al codice            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Le due modalità possono coesistere: nello stesso processo, basta configurare metodi di autenticazione diversi per diverse istanze `client`.

## VI. Insidie comuni

1. **Le classi chat devono usare `preferScheme=upto`**: usare `exact` farà sì che il facilitator addebiti USDC in base a `maxAmountRequired` (non al consumo effettivo).
2. **Sul lato Node non passare una chiave privata nuda a `createX402PaymentHandler`**: il pacchetto TS non accetta `{ privateKey }`, deve essere incapsulata in un provider EIP-1193 (si raccomanda viem `WalletClient`).
3. **La prima chiamata richiede una doppia firma**: la prima firma l'approve Permit2 (on-chain, con gas), la seconda firma l'envelope X402 (non on-chain). Nelle chiamate successive rimane solo la seconda.
4. **Solana non ha il concetto di Permit2**: firma direttamente l'autorizzazione di trasferimento del token SPL, senza bisogno di approve; ma attualmente sulla chain Solana è supportato solo `exact`.
5. **Distinguere gli errori di business dagli errori di pagamento**: 402 → il fallimento dell'handler genera `X402SignError` (il tipo specifico varia in base alla chain); gli errori dell'interfaccia business dopo il reinvio (401 / 422 / 5xx) vengono comunque classificati come normali eccezioni SDK.
6. **Il modo più stabile per adattare `viem`**: `evmProvider: walletClient as any` perde il controllo dei tipi ma offre la migliore compatibilità; se si desidera mantenere i tipi, usare `.transport.request` di viem per incapsularlo separatamente in un oggetto `{ request }` e passarlo.
