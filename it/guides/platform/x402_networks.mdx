Ace Data Cloud X402 attualmente effettua il regolamento in USDC e supporta due tipi di catene: EVM e Solana. Le modalità di firma, gli indirizzi degli asset, il comportamento del gas e gli scenari applicabili differiscono tra le reti; è necessario scegliere prima la rete prima dell'integrazione.

## Gli identificatori di rete utilizzano CAIP-2

L'`accepts[].network` di x402 v2 è un identificatore CAIP-2, non un'abbreviazione come `base` o `solana`. Il client deve confrontare le reti in base alla stringa CAIP-2:

| Rete             | Identificatore CAIP-2                      |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Matrice di supporto

| Rete     | scheme  | Asset                  | Metodo di firma                       | Scenario applicabile                     |
| ------ | ------- | ------------------- | ------------------------------------ | ------------------------ |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Consigliato per impostazione predefinita, supporto maturo per wallet e liquidità.         |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | API a misurazione successiva come chat e modelli.          |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Scenari di wallet Solana, Agent o applicazioni on-chain. |

`upto` è attualmente disponibile solo su Base. Le opzioni effettivamente disponibili dipendono da `accepts` restituito dall'API. Puoi anche consultare il Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

La risposta del Facilitator `/supported`:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Spiegazione dei risultati:

- Gli `exact` di Base e Solana sono percorsi di pagamento a importo fisso.
- Solo Base fornisce il percorso di misurazione successiva `upto`, che dipende dall'approve Permit2.
- L'`extra.facilitatorAddress` nella voce `upto` è l'indirizzo da inserire nel witness durante la firma del client e deve corrispondere al valore restituito dal server.

## Base

Base utilizza il contratto USDC ufficiale:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

Nello schema `exact`, il client firma EIP-712 `TransferWithAuthorization`. Il contenuto della firma include:

- `from`: indirizzo del wallet pagatore
- `to`: indirizzo di incasso di Ace Data Cloud
- `value`: importo del pagamento corrente
- `validAfter` / `validBefore`: finestra temporale di validità della firma
- `nonce`: nonce casuale di 32 byte

Dopo aver verificato la firma, il Facilitator chiamerà on-chain `transferWithAuthorization` di USDC per completare il trasferimento.

Base è la rete di integrazione ufficiale più consigliata, particolarmente adatta alla misurazione successiva `upto`, poiché gli ecosistemi di Permit2, USDC e wallet sono più maturi.

Esempio di risultato della verifica Base `exact`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Spiegazione dei risultati:

- Il paid retry dell'API restituisce il contenuto del modello `ADC_BASE_E2E_OK`.
- La transazione on-chain è consultabile su BaseScan, e il numero del blocco è `46726299`.
- `95215` atomic USDC corrisponde a `0.095215` USDC, ossia l'importo effettivamente regolato per questa chiamata API.

Risultato dell'esecuzione del programma per il pagamento dell'ordine Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Spiegazione dei risultati:

- Lo stato finale dell'ordine della piattaforma è `Finished`.
- Il `pay_id` dell'ordine viene scritto nello stesso hash della transazione Base.
- `1200000` atomic USDC corrisponde a `1.2` USDC, ossia l'importo storico effettivamente pagato per questo ordine da 10 Credits secondo la vecchia politica; i nuovi ordini non usufruiscono più di sconti aggiuntivi per il metodo di pagamento X402, e l'importo specifico della firma dipende dalla risposta 402 corrente.

## Solana

Solana utilizza SPL USDC `TransferChecked`. Il client costruisce una transazione di trasferimento, la firma e la invia, quindi inserisce la firma della transazione o la transazione serializzata nell'envelope `PAYMENT-SIGNATURE`.

Caratteristiche di Solana:

- Utilizza Solana wallet adapter o base58 secret key;
- L'asset è il mint di Solana USDC;
- Attualmente supporta solo `exact`;
- Il Facilitator verifica mint, destination, authority e amount della transfer instruction.

Se viene utilizzata la modalità wallet fee payer, il wallet invierà direttamente la transazione e il Facilitator sarà responsabile della conferma della transazione e della restituzione del risultato del settlement.

Esempio di risultato della verifica Solana `exact`:

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Spiegazione dei risultati:

- Il paid retry ha già restituito HTTP 200 e il modello ha prodotto `ADC_SOLANA_E2E_OK`.
- Quando si interroga la signature on-chain tramite RPC pubblici, è possibile incontrare limitazioni di frequenza.
- Poiché le query RPC pubbliche possono essere soggette a limitazioni di frequenza, qui non viene indicato Solana explorer. Quando è necessario un riconciliazione rigorosa, utilizza il tuo Solana RPC o i record di settlement lato piattaforma per confermare la firma della transazione.

## Come scegliere

| Cosa vuoi fare        | Rete consigliata           |
| ------------ | -------------- |
| Completare rapidamente il flusso minimo     | Base `exact`   |
| Rivolgersi a normali utenti Web3 | Base           |
| Effettuare misurazione successiva per completamenti chat e simili   | Base `upto`    |
| Applicazioni dell'ecosistema Solana  | Solana `exact` |

Indipendentemente dalla catena scelta, non codificare i prezzi in modo hardcoded nel client. Il prezzo è determinato da `accepts[].maxAmountRequired` restituito dal server.

## Aggiungere reti EVM
Il supporto nel codice per pagamenti a importo fisso in USDC nativo sulle seguenti reti è stato fornito, e viene abilitato rete per rete.
La disponibilità effettiva è determinata dall'`accepts` restituito dall'ordine o dall'API; ciò non significa che tutte le reti siano già abilitate in produzione.

| Rete         | Alias      | CAIP-2         | USDC nativo                                 |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

Queste reti supportano solo `exact`, e la precisione della valuta è 6. Non utilizzare USDC bridged con lo stesso nome.
Quando si utilizza il Client X402 TypeScript/Python ufficiale, è possibile passare l'abbreviazione nella tabella o l'identificatore CAIP-2.
Il client utilizza l'ID della catena di destinazione per costruire la firma; il wallet deve supportare la rete di destinazione.

La tabella di supporto ufficiale del wallet estensione Phantom elenca Arbitrum e Polygon; Optimism, Avalanche
non sono attualmente inclusi in questa tabella, ed è possibile utilizzare Rabby o MetaMask che supportano la catena di destinazione. Gli indirizzi EVM possono essere uguali su catene diverse,
ma i saldi sono indipendenti tra loro, e gli indirizzi Solana non sono applicabili a USDC EVM.
Vedere la [tabella di supporto del wallet Phantom](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### Punto di accesso graduale per nuove reti

I punti di accesso alle nuove catene sono nascosti per impostazione predefinita. Quando si accede alla console o a Studio, è possibile utilizzare `?features=x402-arbitrum`
per abilitare la catena corrispondente, e separare più flag con virgole. Per disabilitare una singola catena, utilizzare `?features=-x402-arbitrum`,
per cancellare le sovrascritture locali utilizzare `?features=none`. Le impostazioni vengono salvate separatamente per ciascun dominio.
Il preventivo dell'ordine e i tentativi di pagamento utilizzano lo stesso interruttore, e il server esegue una convalida indipendente; i record di pagamento esistenti restano visualizzabili.
L'abilitazione del solo flag della pagina non attiva una catena non ancora configurata, e le reti effettivamente pagabili restano determinate dall'`accepts` in tempo reale.
