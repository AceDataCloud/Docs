title: "Tutorial sul pagamento degli ordini X402"

Oltre a pagare direttamente per richiesta API, Ace Data Cloud supporta anche il pagamento degli ordini della console con X402. Il protocollo principale del pagamento degli ordini e delle chiamate API è lo stesso: la prima richiesta restituisce 402, il client firma `PAYMENT-SIGNATURE`, quindi riprova con la stessa richiesta.

La differenza è che il pagamento degli ordini appartiene alle API della piattaforma e richiede un token dell'account; mentre la chiamata diretta alle API AI di `x402.acedata.cloud` può usare solo X402, senza richiedere un API Token.

## Preparare l'ordine

Accedi alla [console Ace Data Cloud](https://platform.acedata.cloud/console/orders), seleziona l'ordine da pagare e annota l'ID dell'ordine.

Se non hai ancora un ordine, puoi creare un ordine in attesa di pagamento nella pagina dei piani. Il prezzo dell'ordine fa fede a quanto visualizzato nella pagina, mentre l'`amount` nella risposta X402 402 è la base finale per la firma.

## Creare un token dell'account

Le richieste di pagamento degli ordini richiedono un token dell'account. Apri la [pagina dei Token della piattaforma](https://platform.acedata.cloud/console/platform-tokens) e crea un token nel formato `platform-v1-...`.

Le richieste successive usano:

```http
Authorization: Bearer {platform_token}
```

Il token dell'account è diverso dal normale API Token. Il normale API Token viene usato per consumare il credito API; il token dell'account viene usato per operare sulle risorse della piattaforma per conto del tuo account, ad esempio il pagamento degli ordini.

## Attivare 402

Invia prima una richiesta senza `PAYMENT-SIGNATURE`:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

Lo stato restituito è 402 e la risposta contiene `accepts`:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

Il pagamento degli ordini utilizza l'ufficiale x402 v2: `x402Version` è `2`, `network` usa l'identificatore CAIP-2 e il campo dell'importo è `amount`.

Risultato dell'esecuzione del programma per la creazione di un ordine da 10 Credits e l'attivazione di 402:

> I seguenti record di transazione sono campioni storici testati realmente con la vecchia politica; l'importo e l'hash della transazione sono mantenuti invariati. I nuovi ordini X402 non prevedono più sconti sul metodo di pagamento; usa l'`amount` della risposta 402 corrente come base per firma e pagamento.

```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
error Payment required for this order.
accepts [
  ('eip155:8453', 'exact', '1200000', '0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000', '5iVXFrYaYWX2GUTbkQj8mDBoBhAX8bneYigS2LJTia43')
]
description Ace Data Cloud Credits x 10.0
```

Spiegazione dei risultati:

- Dopo la creazione riuscita dell'ordine, lo stato è `Pending`; a questo punto non c'è ancora alcun pagamento on-chain.
- La prima richiesta `pay/` non include `PAYMENT-SIGNATURE`, quindi restituisce HTTP 402.
- `accepts` fornisce contemporaneamente Base `exact` e Solana `exact`; questo tutorial seleziona Base nei passaggi successivi.
- Il prezzo al momento della creazione dell'ordine è `1.26`; durante il periodo della vecchia politica di sconto per il pagamento X402, l'importo effettivo firmato e regolato era `1.2` USDC, corrispondente a `1200000` atomic USDC.

Nota che qui `resource` è un campo restituito dal server e incluso nella firma; il client non deve modificare autonomamente il protocollo, il percorso o l'ID dell'ordine al suo interno.

## Firmare e riprovare

Il pagamento degli ordini può riutilizzare le funzioni di firma di basso livello di `@acedatacloud/x402-client` o `acedatacloud-x402`. Di seguito è riportato un esempio TypeScript:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

Risultato dell'esecuzione del programma dopo la firma e il nuovo tentativo con Base `exact` per lo stesso ordine:

```text

has_x_payment_response True
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order {'id': '78481793-304e-47f7-bc0c-8231aec9cc1e', 'state': 'Finished', 'pay_way': 'X402', 'price': 1.2, 'pay_id': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}
```

Risultato della conferma on-chain:


Spiegazione dei risultati:

- `status 200` indica che l'interfaccia di pagamento dell'ordine della piattaforma ha accettato questa `PAYMENT-SIGNATURE`.
- `has_x_payment_response True` indica che l'intestazione della risposta contiene la ricevuta `PAYMENT-RESPONSE` codificata in Base64.
- `settle_header.success=True` e `network=base` indicano che il Facilitator ha completato il settlement su Base.
- Lo stato finale dell'ordine è `Finished`, `pay_way` è `X402` e `pay_id` contiene l'hash della transazione on-chain.
- L'evento `Transfer` su BaseScan mostra che l'indirizzo pagante ha trasferito `1200000` USDC atomic all'indirizzo ricevente della piattaforma, ovvero `1.2` USDC.

## Risposta di successo e ricevuta

Dopo che il pagamento dell'ordine è andato a buon fine, il corpo della risposta contiene le informazioni dell'ordine. La piattaforma trasporta inoltre nell'intestazione della risposta `PAYMENT-RESPONSE` la settlement response codificata in Base64; dopo la decodifica, i campi comuni includono:

| Campo            | Descrizione                           |
| ------------- | ---------------------------- |
| `success`     | Se il settlement del Facilitator è riuscito. |
| `transaction` | Hash della transazione di settlement on-chain.                    |
| `network`     | Rete di pagamento.                        |
| `payer`       | Indirizzo del wallet pagante.                      |
| `amount`      | Importo effettivamente regolato, in atomic units.      |

Se devi effettuare la riconciliazione, si consiglia di salvare contemporaneamente l'ID dell'ordine, l'indirizzo del wallet pagante, `transaction` e lo stato finale dell'ordine.

## Note

- Il pagamento dell'ordine richiede il token dell'account della piattaforma e non può essere completato solo con la firma del wallet X402.
- `amount` usa USDC atomic units; `1200000` indica `1.2` USDC.
- Non comporre autonomamente l'indirizzo di ricezione o l'indirizzo dell'asset; fai riferimento a `accepts` nella risposta 402.
- Se la stessa `PAYMENT-SIGNATURE` viene inviata ripetutamente, il Facilitator applicherà la protezione dai replay in base al nonce.

## Risposta di pagamento non riuscito

La prima HTTP 402 senza `PAYMENT-SIGNATURE` è una normale richiesta di pagamento e non indica un pagamento non riuscito. Gli errori di verifica o settlement dopo la firma mantengono comunque la stringa standard `error` come fallback compatibile e restituiscono una struttura di errore stabile in `extensions.acedatacloud.paymentError`:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

Il client dovrebbe localizzare innanzitutto in base a `code`; per i code sconosciuti, usare come fallback un errore di pagamento generico. `charged` è un campo a tre stati: solo quando viene esplicitamente rifiutato prima del settlement verrà restituito `false`; l'assenza del campo indica che lo stato dell'addebito è sconosciuto e non può essere interpretata come “nessun addebito”. Dopo che l'ordine entra in `Failed`, non può essere ritentato sullo stesso ordine; crea un nuovo ordine dopo aver corretto il problema del wallet.

`metadata.x402.last_error` e `metadata.x402.errors` nell'elenco e nei dettagli degli ordini mantengono lo stesso gruppo di `code`, `stage`, `retryable`, `charged` e `params`; il testo descrittivo pubblico è conservato in `reason`, mentre l'ora dell'evento è conservata in `timestamp`. Ad esempio, `insufficient_token_balance` indica un saldo USDC insufficiente sulla rete selezionata, mentre `invalid_signature` indica che la firma di pagamento non è valida; rileggere l'ordine non li trasformerà in un generico `payment_failed`.

Non registrare né inviare la `PAYMENT-SIGNATURE` completa, la firma del wallet, il payload di autorizzazione, la diagnostica originale del Facilitator o le risposte RPC. Per la verifica da parte dell'assistenza sono necessari solo l'ID dell'ordine e il `code` di errore pubblico.

## Riacquisto e burn di ACE per pagamenti Base e Solana

Dopo aver abilitato la strategia di riacquisto, il 3% dell'importo effettivamente ricevuto di Circle USDC sulla mainnet Base e USDC sulla mainnet Solana che soddisfa le condizioni viene utilizzato per acquistare e distruggere ACE, senza alcun addebito aggiuntivo al wallet pagante. L'accantonamento avviene una volta al momento della ricarica; l'uso successivo di questi Credits per chiamare l'API non comporta ulteriori accantonamenti; gli ordini storici scontati e gli ordini con vecchie strategie non ricevono automaticamente accantonamenti retroattivi.

I pagamenti Base conservano la ricevuta di pagamento sulla chain Base, mentre l'acquisto e la distruzione di ACE vengono eseguiti in modo asincrono su Solana. L'oggetto `ace_burn` nei dettagli dell'ordine fornisce `settlement_network`, `settlement_transaction` e `execution_network`, e fornisce `swap_signature` e `burn_signature` dopo il completamento. `Pending` o `Processing` non indicano che il burn è stato completato; solo `Completed` rappresenta che la prova on-chain finale è stata verificata. Quando il pagamento Base non ha ancora raggiunto la conferma finale, il riacquisto attenderà la conferma, ma ciò non influisce sui Credits già accreditati.
