Questo tutorial utilizza una richiesta API minima per illustrare il flusso completo di Ace Data Cloud X402. L'obiettivo non è scrivere subito codice complesso, ma capire prima: perché la prima richiesta restituisce 402, cosa contiene `accepts` e come `PAYMENT-SIGNATURE` trasforma la stessa richiesta API in una richiesta già pagata.

## Preparazione

Devi preparare:

| Elemento   | Descrizione                                                   |
| ---- | ---------------------------------------------------- |
| Wallet   | Un wallet che supporti la rete di destinazione. Base utilizza un wallet EVM, Solana utilizza un wallet Solana.      |
| USDC | Il wallet deve disporre di USDC sufficienti. L'importo effettivo è soggetto a `maxAmountRequired` nella risposta 402. |
| Ambiente di sviluppo | Per TypeScript è consigliato Node.js 18+; per Python è consigliato Python 3.10+.    |
| SDK  | Si consiglia di utilizzare l'SDK ufficiale, non è consigliato scrivere manualmente i dettagli della firma.                                |

Non è necessario un API Token quando si chiama l'API Ace Data Cloud tramite X402. La prima richiesta dell'SDK non include `Authorization`, il Gateway restituirà `402 Payment Required` e i requisiti di pagamento; l'SDK riprova automaticamente dopo la firma.

## Installare l'SDK

Codice sorgente e indirizzi dei pacchetti:

- Repository SDK: [https://github.com/AceDataCloud/SDK](https://github.com/AceDataCloud/SDK)
- Repository X402 Client: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)
- npm: `@acedatacloud/sdk`、`@acedatacloud/x402-client`
- PyPI: `acedatacloud`、`acedatacloud-x402`

TypeScript:

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client ethers
```

Python:

```bash
pip install acedatacloud acedatacloud-x402
```

Se vuoi utilizzare Solana, devi anche installare le dipendenze corrispondenti:

```bash
npm install @solana/web3.js
```

La dipendenza del signer Solana per la versione Python è già inclusa in `acedatacloud-x402`.

Output di installazione e controllo degli import in un ambiente temporaneo pulito:

## La prima richiesta restituirà 402

Puoi prima usare `curl` per vedere cosa restituisce una richiesta non pagata. L'esempio seguente non comporterà alcun addebito, perché non include `PAYMENT-SIGNATURE`:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Il corpo della risposta includerà l'array `accepts`, con una struttura comune come segue:

```json
{
  "x402Version": 2,
  "resource": {
    "url": "/openai/chat/completions",
    "description": "AceDataCloud API call",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "maxAmountRequired": "95215",
      "amount": "95215",
      "maxTimeoutSeconds": 3600,
      "resource": "/openai/chat/completions",
      "description": "...",
      "payTo": "0x...",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913"
      }
    }
  ],
  "error": "PAYMENT-SIGNATURE header is required"
}
```

Lo stesso contenuto della challenge viene anche inserito in formato base64 nell'header di risposta `PAYMENT-REQUIRED`, per consentire al client di leggere i requisiti di pagamento senza analizzare il body.

Il riepilogo dell'output del programma per una richiesta non pagata dell'API di produzione è il seguente:

```text
status=402
x402Version 2
accepts [
  ('eip155:8453', 'exact', '95215'),
  ('eip155:8453', 'upto', '95215'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '95215'),
]
```

Spiegazione dei risultati:

- La prima richiesta non include `Authorization` o `PAYMENT-SIGNATURE`, quindi restituisce HTTP 402 e non comporta alcun addebito.
- `accepts` è l'unica base affidabile per la firma di questa richiesta e contiene le reti opzionali, lo scheme, il limite massimo dell'importo, l'indirizzo del destinatario e l'indirizzo dell'asset.
- `network` è un identificatore CAIP-2; il client deve effettuare la corrispondenza in base alla stringa CAIP-2 quando seleziona la rete.
- Il limite massimo per questa richiesta di chat minima `gpt-4o-mini` è `95215` atomic USDC, ovvero `0.095215` USDC.
- Ogni richiesta dovrebbe leggere la risposta 402 corrente; non codificare rigidamente gli importi di esempio nel codice aziendale.

Significato dei campi:

| Campo                                                                  | Descrizione                                                             |
| ------------------------------------------------------------------- | -------------------------------------------------------------- |
| `scheme`                                                            | Schema di pagamento. `exact` indica un importo fisso, `upto` indica un limite di autorizzazione e il regolamento in base all'utilizzo effettivo.                     |
| `network`                                                           | Identificatore CAIP-2 della rete di pagamento, ad esempio `eip155:8453`, `solana:5eykt4...`.           |
| `maxAmountRequired`                                                 | Importo massimo di pagamento, l'unità è USDC atomic units, `95215` indica `0.095215` USDC.       |
| `amount`                                                            | L'importo da regolare questa volta; `exact` è uguale a `maxAmountRequired`, mentre `upto` viene riscritto in base all'utilizzo reale nella fase di regolamento. |
| `payTo`                                                             | Indirizzo del destinatario.                                                          |
| `asset``maxAmountRequired = costo Credits di questa chiamata × 0.095215``cost.amount` | Indirizzo del contratto USDC o indirizzo mint Solana.                                     |
| `extra`                                                             | Informazioni estese come chain ID necessario per la firma, domain EIP-712, indirizzo Permit2 e così via.                      |

## Completare il nuovo tentativo di pagamento con l'SDK

Di seguito è riportato l'esempio TypeScript minimo. Specifica `network: 'base'`; l'handler selezionerà il payment requirement di Base dalla risposta 402 corrente; l'importo effettivo e l'indirizzo del destinatario restano soggetti a `accepts`:
```ts
import { Wallet } from 'ethers';
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') {
      throw new Error(`unsupported method: ${method}`);
    }
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const response = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly: hello' }],
  max_tokens: 8
});

console.log(response.choices[0].message.content);
```

Dietro questo codice avvengono quattro passaggi:

1. L'SDK invia una normale richiesta API, senza `Authorization`.
2. Il Gateway restituisce `402 Payment Required` e `accepts`.
3. `createX402PaymentHandler` seleziona il payment requirement con `network = 'base'` e firma `PAYMENT-SIGNATURE`.
4. L'SDK ritenta con lo stesso corpo della richiesta, e il Gateway chiama il Facilitator per verificare e regolare prima di consentire l'accesso all'API di destinazione.

## Visualizzare le capacità supportate dal Facilitator

L'API X402 non dipende da un catalogo di risorse. Il client chiama direttamente un'API nota e usa
`402 Payment Required` e `accepts`, restituiti in tempo reale da quella richiesta, come unica base per il prezzo e la firma.

La dichiarazione delle capacità del Facilitator si trova in:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Descrive solo `/supported`, `/verify`, `/settle` e le reti di pagamento attualmente abilitate, senza elencare le risorse API.

L'indirizzo del Facilitator di produzione di Ace Data Cloud è:

```text
https://facilitator.acedata.cloud
```

È possibile vedere quali reti e scheme supporta:

```bash
curl https://facilitator.acedata.cloud/supported
```

I `kinds` restituiti elencano le reti e gli scheme supportati dal Facilitator. Durante le chiamate effettive, fare comunque riferimento agli `accepts` restituiti dall'API.

Output di Facilitator `/supported`:

```text
kinds [
  ('eip155:8453', 'exact'),
  ('eip155:8453', 'upto', {'facilitatorAddress': '0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708'}),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact')
]
```

Il risultato indica:

- `/supported` indica che il Facilitator dispone delle capacità di verifica e regolamento per queste reti e scheme.
- Sia Base sia Solana supportano `exact`; `upto` è attualmente disponibile solo su Base.
- Se una specifica API consente una determinata rete dipende comunque dagli `accepts` 402 di quell'API.
