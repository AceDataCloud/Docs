La funzione principale della Producer Tasks API consiste nel verificare lo stato di esecuzione di un'attività inserendo l'ID dell'attività generato dalla Producer Audios Generation API.

Questo documento illustrerà nel dettaglio le istruzioni di integrazione della Producer Tasks API, aiutandovi a integrarla facilmente e a sfruttare appieno le potenti funzionalità di questa API. Tramite la Producer Tasks API, potete facilmente effettuare la verifica dello stato di esecuzione delle attività della Producer Audios Generation API.

## Processo di richiesta

Per utilizzare la Producer Audios Generation API, ottenete innanzitutto il vostro API Token dalla [console di Ace Data Cloud](https://platform.acedata.cloud/console/applications) e conservatelo per l'uso successivo.

![](https://cdn.acedata.cloud/dvc3cg.jpg)

Se non avete ancora effettuato l'accesso o la registrazione, sarete reindirizzati automaticamente alla pagina di accesso per invitarvi a registrarvi e ad accedere; al termine, tornerete automaticamente alla pagina corrente.

**Un solo API Token può richiamare tutti i servizi della piattaforma, senza necessità di richiederne uno separato per ciascun servizio.** Alla prima richiesta verrà fornito un credito gratuito, che consente di provare il servizio gratuitamente; quando il credito è insufficiente, potete ricaricare il saldo generale nella [console](https://platform.acedata.cloud/console/coin).

> 📘 Documentazione completa: [Producer Audios Generation API →](https://platform.acedata.cloud/documents/producer-audios)

## Esempio di richiesta

La Producer Tasks API può essere utilizzata per verificare i risultati della Producer Audios Generation API. Per sapere come utilizzare la Producer Audios Generation API, consultate la documentazione [Producer Audios Generation API ](https://platform.acedata.cloud/documents/producer-audios-integration).

Prendiamo come esempio un ID attività restituito dal servizio Producer Audios Generation API per mostrare come utilizzare questa API. Supponiamo di avere un ID attività: 1a6ac2ad-10f2-4e2b-b500-66ec27fe82ad, di seguito mostreremo come farlo passando un ID attività.

### Impostare gli header e il body della richiesta

Gli **Request Headers** includono:

- `accept`: specifica la ricezione dei risultati della risposta in formato JSON; qui va impostato su `application/json`.
- `authorization`: la chiave per richiamare l'API, che dopo la richiesta può essere selezionata direttamente dal menu a discesa.

Il **Request Body** include:

- `id`: l'ID dell'attività caricata.
- `action`: il metodo di operazione sull'attività.

Impostare come mostrato nella figura seguente:

#### CURL

```bash
curl -X POST 'https://api.acedata.cloud/producer/tasks' \
-H 'accept: application/json' \
-H 'authorization: Bearer {token}' \
-H 'content-type: application/json' \
-d '{
  "id": "1a6ac2ad-10f2-4e2b-b500-66ec27fe82ad",
  "action": "retrieve"
}'
```

Il risultato restituito contiene diversi campi: il campo request è il request body al momento dell'avvio dell'attività, mentre il campo response è il response body restituito dopo il completamento dell'attività. L'introduzione dei campi è la seguente.
- `id`, l'ID dell'attività di generazione, utilizzato per identificare univocamente questa attività di generazione.
- `request`, le informazioni sulla richiesta nell'attività di interrogazione.
- `response`, le informazioni di ritorno nell'attività di interrogazione.
- `created_at`, l'ora di creazione dell'attività, timestamp Unix (secondi, virgola mobile).
- `started_at`, l'ora di inizio dell'esecuzione dell'attività, timestamp Unix (secondi, virgola mobile).
- `finished_at`, l'ora di completamento dell'attività, timestamp Unix (secondi, virgola mobile). Questo campo non viene restituito quando l'attività non è completata.
- `elapsed`, il tempo impiegato per l'esecuzione dell'attività, in secondi (virgola mobile, mantenendo 3 cifre decimali). Questo campo non viene restituito quando l'attività non è completata.

- `action`: la modalità di operazione sull'attività.

## Gestione degli errori

Quando si chiama l'API, se si verifica un errore, l'API restituirà il codice e il messaggio di errore corrispondenti. Ad esempio:

- `400 token_mismatched`：Richiesta non valida, probabilmente a causa di parametri mancanti o non validi.
- `400 api_not_implemented`：Richiesta non valida, probabilmente a causa di parametri mancanti o non validi.
- `401 invalid_token`：Non autorizzato, token di autorizzazione non valido o mancante.
- `429 too_many_requests`：Troppe richieste, hai superato il limite di frequenza.
- `500 api_error`：Errore interno del server, qualcosa è andato storto sul server.

### Esempio di risposta di errore

```json

    "message": "fetch failed"

  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```
