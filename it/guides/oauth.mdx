---
title: "Integrare Ace Data Cloud OAuth 2.0"
---

Consenti agli utenti di autorizzare la tua applicazione ad accedere al loro profilo Ace Data Cloud, agli abbonamenti ai servizi, alle API Key, all'utilizzo o agli ordini. Usa il metodo standard **Authorization Code + S256 PKCE**: l'applicazione apre la pagina di autorizzazione, l'utente acconsente e riceve un `code` monouso, che viene poi scambiato con un OAuth access token.

L'OAuth access token viene utilizzato per accedere alle API delle risorse dell'account; per chiamare le API dei modelli, utilizza la relativa API Key. L'autorizzazione OAuth non crea automaticamente API Key, non attiva servizi né aumenta il saldo.

## Scegliere il metodo di integrazione

| Metodo            | Scenari applicabili                                | Dopo il completamento dell'autorizzazione                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Reindirizzamento OAuth standard   | Siti web indipendenti, client desktop o mobili; i siti incorporati avviano autonomamente l'autorizzazione            | Il browser torna al `redirect_uri` registrato dall'applicazione, che gestisce `code` e `state` |
| Autorizzazione del componente del sito Studio | Il sito incorpora la home page di Studio e desidera utilizzare l'account Studio corrente del visitatore | Studio invia un messaggio con il risultato dell'autorizzazione all'applicazione; l'applicazione non viene reindirizzata e la pagina originale viene mantenuta                  |

Il reindirizzamento standard non richiede `embed=studio`, `embed_origin` o `postMessage`. La modalità componente Studio prevede che l'host crei la pagina di autorizzazione e mantenga il bridge dei messaggi; le terze parti si integrano secondo il protocollo del componente alla fine di questo documento e non devono concatenare autonomamente questi due parametri.

## Endpoint e documento di discovery

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Utilizzo                | Indirizzo                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Pagina di autorizzazione nel browser            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| Scambiare／aggiornare OAuth token | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Inviare una richiesta di revoca            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Informazioni sull'utente corrente            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| Pagina di gestione delle applicazioni OAuth      | [Applicazioni OAuth](https://auth.acedata.cloud/user/oauth-apps)                            |
| Elenco delle applicazioni／interfaccia di registrazione dell'utente autenticato   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Dati pubblici dell'applicazione utilizzati dalla pagina di autorizzazione      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| API Key esistenti dell'utente     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<ID utente>&limit=100` |

L'interfaccia di gestione delle applicazioni richiede l'autenticazione con l'account e non è un'interfaccia di registrazione dinamica anonima (DCR). Gli endpoint di discovery／registrazione del servizio MCP stesso sono punti di accesso diversi dagli endpoint OAuth dell'account in questa tabella; quando ti connetti a uno specifico MCP, segui la documentazione e i risultati della discovery di quel servizio.

Il documento di discovery viene utilizzato per ottenere endpoint e capacità del protocollo. Il flusso corrente restituisce OAuth token, non restituisce `id_token`; non gestire il processo come un flusso di accesso OpenID Connect completo solo perché esiste lo scope `openid`.

## Ambiti di autorizzazione: utilizzare i nomi scope correnti

`scope` è un insieme di nomi di autorizzazione separati da spazi e sensibili alle maiuscole/minuscole. Le nuove applicazioni utilizzano autorizzazioni specifiche come `profile:read`, `email:read`, `phone:read`.

### Da dove ottenere le autorizzazioni richiedibili

Dopo l'accesso, l'interfaccia dell'elenco delle applicazioni OAuth `GET /api/v1/oauth2/applications/` restituisce `available_scopes`; il selettore delle autorizzazioni nella pagina di gestione delle applicazioni utilizza lo stesso catalogo. Questi sono gli ambiti facoltativi che dovrebbero essere adottati dalle normali applicazioni self-service.

**`scopes_supported` di Discovery include tutti i nomi delle autorizzazioni riconosciute dalla piattaforma, ma non significa che la tua applicazione possa richiederle tutte.** L'autorizzazione effettiva controlla contemporaneamente:

1. se l'autorizzazione può essere delegata a questo tipo di applicazione;
2. se l'autorizzazione è stata registrata negli ambiti consentiti di questa applicazione OAuth;
3. se l'utente corrente possiede l'autorizzazione richiesta.

Le autorizzazioni sconosciute, non registrate, non delegabili o non possedute dall'utente restituiscono `invalid_scope`. Vengono ricontrollate anche durante lo scambio del codice di autorizzazione e l'aggiornamento, e le autorizzazioni non vengono completate o elevate automaticamente.

### Autorizzazioni facoltative per le normali applicazioni self-service

Di seguito è riportato il catalogo corrente (2026-10-09); durante l'integrazione, fai riferimento a `available_scopes`.

| Scope                                            | Utilizzo                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Leggere／aggiornare il profilo personale                               |
| `email:read`                                     | Leggere l'email                                    |
| `phone:read`                                     | Leggere il numero di telefono e l'area geografica                                |
| `billing-profile:read` / `billing-profile:write` | Leggere／gestire i dati di fatturazione                               |
| `applications:read` / `applications:write`       | Leggere／gestire gli abbonamenti ai servizi                               |
| `credentials:read` / `credentials:write`         | Leggere／gestire le API Key                           |
| `usage:read`                                     | Leggere i record delle chiamate                                  |
| `orders:read` / `orders:write`                   | Leggere／creare e gestire gli ordini                              |
| `auto-recharge:read` / `auto-recharge:write`     | Leggere／gestire le impostazioni di ricarica automatica                             |
| `recharge-cards:redeem`                          | Riscattare carte di ricarica                                   |
| `coin:read`                                      | Leggere le informazioni relative ai token                                |
| `distribution:read`                              | Leggere le informazioni di distribuzione                                  |
| `connections:read` / `connections:write`         | Leggere／gestire le connessioni                                 |
| `skills:read` / `skills:write`                   | Leggere／gestire le skill                                 |
| `openid`                                         | L'implementazione corrente consente inoltre a UserInfo di restituire i dati di base; non restituisce ID Token    |
| `offline_access`                                 | Richiedere un refresh token per l'aggiornamento dopo la scadenza dell'access token |

Ad esempio, per leggere solo il profilo personale usa `profile:read`; per l'email aggiungi `email:read`; per leggere le API Key esistenti usa `profile:read credentials:read`. Richiedi `credentials:write` solo quando è effettivamente necessario creare o modificare Key, e aggiungi `offline_access` quando è necessario l'aggiornamento.

Alcune autorizzazioni sono disponibili solo per applicazioni affidabili approvate dalla piattaforma, ad esempio `sites:read`, `sites:write`, `platform-tokens:read`; altre autorizzazioni non sono aperte alle normali applicazioni OAuth di terze parti. I tipi di client `public`／`confidential` descrivono se è possibile custodire un secret e non sono correlati al fatto che l'applicazione sia affidabile. Le applicazioni create self-service non possono attivare autonomamente autorizzazioni affidabili.

`account` è il selettore delle autorizzazioni dell'account utilizzato dal MCP ufficiale designato per la gestione dell'account, non è uno scope di “tutte le autorizzazioni” per applicazioni di terze parti e non può essere combinato con altri scope. Le terze parti devono elencare esplicitamente le autorizzazioni specifiche necessarie.

### Migrazione dalla documentazione precedente

| Sintassi precedente                                         | Metodo corrente                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Elenca singolarmente le autorizzazioni specifiche effettivamente necessarie; non esiste un valore sostitutivo generico “seleziona tutto” |

I vecchi nomi non vengono accettati come alias di compatibilità. Aggiorna contemporaneamente gli scopes registrati dell'applicazione OAuth, l'URL di autorizzazione e il controllo delle autorizzazioni interno; modificare la configurazione dell'applicazione non aggiunge autorizzazioni ai token già emessi e richiede una nuova autorizzazione dell'utente.

## Passaggio 1: registrare un'applicazione OAuth

Apri [Gestione applicazioni OAuth](https://auth.acedata.cloud/user/oauth-apps), crea un'applicazione e compila:
- Nome, descrizione, logo dell'applicazione: visualizzati sul lato dell'applicazione nella pagina di autorizzazione.
- Tipo di client: per client puramente frontend, mobili o desktop selezionare **Public**; per servizi che possono conservare il secret nel backend selezionare **Confidential**.
- Indirizzo di callback: nell'ambiente di produzione usare HTTPS e registrare l'URL completo realmente gestito dall'applicazione per il callback.
- Permessi: selezionare gli scopes effettivamente necessari dall'elenco fornito dalla pagina.

Salvare `client_id`. I client Confidential conservano `client_secret` sul lato server e non possono inserirlo in HTML, variabili di build frontend o URL. I client Public non usano un secret per ottenere il token; anche se la risposta di registrazione include questo campo, non può essere trattato come una credenziale che il client possa mantenere segreta.

`redirect_uri` deve corrispondere esattamente nella registrazione, nell'autorizzazione e nello scambio del token, inclusi percorso, barra finale e parametri di query. Ogni account può creare al massimo 20 applicazioni. Il secret viene mostrato solo alla creazione/rotazione; dopo la rotazione, il vecchio secret non può più effettuare scambi che richiedono l'autenticazione del client.

## Passaggio 2: il pulsante avvia l'autorizzazione

A ogni clic su connetti, generare nuovi `state` e `code_verifier` casuali e calcolare:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Salvare `state`, verifier e indirizzo di callback nella sessione dell'applicazione stessa, quindi aprire la pagina di autorizzazione con parametri codificati in URL:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<URL completo di callback>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<valore casuale di questa volta>
  &code_challenge=<valore della sfida S256 di questa volta>
  &code_challenge_method=S256
```

I client Public devono inviare PKCE S256. Sebbene Discovery elenchi ancora `plain`, i client Public non possono usarlo. Anche i client Confidential sono consigliati di usare S256; se PKCE è stato usato all'avvio dell'autorizzazione, nello scambio deve essere inviato il verifier corrispondente.

Dopo il consenso dell'utente, si torna a `redirect_uri`, i parametri di query includono `code` e lo `state` restituito senza modifiche. In caso di rifiuto, vengono restituiti `error=access_denied`, una descrizione dell'errore e `state`. Prima di gestire il callback, verificare che state corrisponda alla sessione corrente. Il codice di autorizzazione è valido per 10 minuti e può essere scambiato una sola volta; dopo un errore, avviare nuovamente la connessione, senza aggiornare ripetutamente il vecchio URL di callback.

## Passaggio 3: scambiare il token OAuth

I client Public effettuano lo scambio direttamente dal browser o dal client; i client Confidential effettuano lo scambio nel proprio backend. Il corpo della richiesta supporta la codifica form e le seguenti variabili rappresentano i dati ottenuti dall'applicazione in questa autorizzazione:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

I client Confidential devono inoltre aggiungere il campo form `client_secret` sul lato server. Attualmente è supportato `client_secret_post`; non considerare l'autenticazione del client HTTP Basic come una modalità supportata.

Nella risposta di successo leggere `access_token`, `token_type`, `expires_in` e lo `scope` effettivamente concesso. `refresh_token` è disponibile solo se è stato richiesto e approvato `offline_access`. Non trattare l'access token OAuth come API Key dell'API del modello, né scrivere token, verifier o codice di autorizzazione nei log, negli eventi di analisi o nei link condivisi.

## Passaggio 4: leggere le informazioni utente e l'API Key

Usare prima l'access token OAuth per richiedere UserInfo:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

I campi restituiti dipendono dallo scope: `id` è l'identificatore dell'utente; `profile:read` o `openid` consentono di leggere i dati di base (come `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); per l'email è necessario `email:read`, mentre per il numero di telefono e la regione è necessario `phone:read`. Non presumere che i campi non autorizzati siano sempre presenti.

Quando è necessaria un'API Key già esistente ed è stato concesso `credentials:read`, usare l'`id` di UserInfo come condizione di filtro:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

La lista restituita usa `count` e `items`, e il campo Key è **`items[*].token`**, non `data[0].value`. `user_id=me` non è un ID utente valido per questa interfaccia. Per i dati su più pagine, continuare a leggere in base a `offset`/`limit`, senza considerare la prima pagina come tutte le credenziali.

Selezionare la credenziale applicabile in base ad applicazione, servizio e stato di validità, senza prendere ciecamente la prima. Una lista vuota non significa che l'autorizzazione sia fallita; l'utente potrebbe non aver ancora creato una Key applicabile. Il controllo dei permessi dell'access token OAuth e l'ambito del servizio, le quote e le condizioni di scadenza dell'API Key stessa sono vincoli diversi.

**Consentire la lettura delle API Key significa che una terza parte può salvarle e utilizzarle. Revocare la richiesta OAuth o cancellare lo stato di accesso dell'applicazione non invaliderà le API Key già copiate; l'utente deve revocare o ruotare separatamente tale Key nella gestione delle credenziali.**

## Esempio eseguibile di browser Public / PKCE

Distribuire la pagina seguente al `REDIRECT_URI` registrato, sostituendo `CLIENT_ID` e l'indirizzo di callback. Il pulsante avvia l'autorizzazione standard e, tornando alla stessa pagina, legge il profilo e il numero di Key esistenti. L'esempio non mostra né persiste le Key; l'applicazione di produzione consuma i risultati in base all'uso effettivo. Verificare prima in una pagina browser indipendente, quindi eseguire il collaudo secondo i requisiti iframe successivi.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Connetti Ace Data Cloud</title>
<button id="connect" type="button">Connetti account</button>
<p id="status" role="status">Non ancora connesso</p>
<script type="module">
const CLIENT_ID = 'sostituisci con il tuo client_id';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`L'API ha restituito HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = 'Impossibile avviare la connessione, controlla le impostazioni di archiviazione del browser e riprova.';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('La sessione di autorizzazione non corrisponde, riconnetti.');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('La sessione di autorizzazione è scaduta, riconnetti.');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('L'autorizzazione non è stata completata, puoi riconnetterti.');
    if (!code) throw new Error('Nel callback manca il codice di autorizzazione, riconnetti.');
    status.textContent = 'Connessione in corso…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('Token di autorizzazione non ottenuto.');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('Identificatore utente non ottenuto.');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('Il formato dell'elenco delle credenziali non è conforme.');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `Connesso ${profile.nickname || profile.username || profile.id}; questa pagina contiene ${keyCount} API Key.`;
  } catch (error) {
    status.textContent = `Connessione non completata: ${error.message || 'errore di rete'} Fai di nuovo clic su connetti.`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Il callback e il punto di ingresso dell'esempio devono trovarsi nella stessa origine e nella stessa scheda del browser/iframe, per poter leggere il `sessionStorage` precedentemente salvato. Le applicazioni di produzione devono gestire i token nel proprio schema di sessione, gestire la scadenza e rimuovere i parametri URL di autorizzazione dopo aver ricevuto la risposta; l'interfaccia principale della pagina deve essere renderizzata per prima e gli errori di rete devono influire solo sullo stato della connessione.

## iframe nei siti white-label

### Il sito del cliente reindirizza autonomamente alla pagina di autorizzazione

È sufficiente utilizzare i parametri OAuth standard e gestire il proprio callback; `window.location.assign()` naviga nell'iframe corrente e la pagina padre rimane nel dominio white-label. Non è necessario aggiungere `embed=studio` per l'icona né implementare il protocollo di messaggi Studio.

Devono essere soddisfatte le seguenti condizioni:

- La pagina dell'applicazione e la pagina di callback utilizzano HTTPS, sono effettivamente accessibili e consentono l'incorporamento tramite iframe da parte del dominio padre white-label; verificare `Content-Security-Policy: frame-ancestors` e `X-Frame-Options` di entrambe le parti.
- Il sandbox consente gli script, i moduli e le capacità di origine/archiviazione richiesti dalla pagina. Quando è supportato l'accesso tramite popup, sono necessarie anche le corrispondenti capacità popup; dare priorità alla configurazione del componente Website fornito da Studio.
- Il browser consente allo scenario di incorporamento corrente di utilizzare l'archiviazione richiesta dallo stato di autorizzazione. Lo stato di accesso del sito white-label e lo stato di accesso di AuthFrontend potrebbero essere diversi; non si deve presumere che aver effettuato l'accesso al sito white-label significhi aver già effettuato l'accesso alla pagina di autorizzazione.
- Il servizio di scambio token nel callback è disponibile e le richieste cross-origin consentono l'origine dell'applicazione; DNS, CORS ed errori HTTP devono tutti mostrare uno stato riprovabile e non devono interrompere il rendering dell'intera pagina.

Il lato sinistro della pagina di autorizzazione legge il Logo dell'applicazione OAuth; il lato destro legge favicon/logo di quel Site quando il browser può fornire l'origine padre e il dominio padre supera la verifica del sito verificato, altrimenti mostra l'icona predefinita. Questo determina solo la visualizzazione del branding, non stabilisce una sessione di accesso né fornisce autorizzazioni dell'account alla pagina del cliente.

**Limitazione attuale: quando OAuth normale richiede un nuovo accesso all'interno di un iframe, il flusso per continuare a tornare alla pagina di autorizzazione dopo il completamento dell'accesso presenta ancora una lacuna.** Prima della pubblicazione, è necessario verificare separatamente "Auth con accesso effettuato" e "Auth senza accesso/accesso scaduto". Prima che questa lacuna venga risolta e verificata, per il primo accesso è possibile utilizzare una pagina separata per completare OAuth standard, oppure adottare l'autorizzazione del componente Studio riportata sotto; non promettere che tutti gli scenari iframe funzionino basandosi solo sui risultati dei test con accesso già effettuato.

### Utilizzare l'autorizzazione dell'account corrente di Studio

In Studio, attiva OAuth in «Impostazioni → Home → Componenti sito», quindi inserisci `client_id` e l'indirizzo di callback registrato. Il sito e il callback devono utilizzare la stessa origine HTTPS e devono essere diversi dall'origine Studio. La pagina di terze parti deve:

1. Inviare `acedatacloud:oauth:ready` all'origin esatto del sito padre, ricevere e verificare `acedatacloud:oauth:init`.
2. Il pulsante genera state e verifier PKCE, invia `acedatacloud:oauth:authorize` (state, challenge S256); il verifier rimane nella propria pagina.
3. Verificare finestra padre, origin e state, gestire code o error in `acedatacloud:oauth:result` e scambiarli tramite l'endpoint token standard.
Studio visualizza la pagina di autorizzazione nell'area del componente; dopo il consenso dell'utente restituisce il codice di autorizzazione tramite messaggio, senza che l'applicazione debba reindirizzare. In assenza di accesso restituisce `login_required`, in caso di rifiuto restituisce `access_denied`, e in caso di timeout dell'attesa restituisce `authorization_timeout`. La modifica dell'account ricrea l'iframe dell'applicazione e annulla le autorizzazioni non completate.

Il componente richiede attualmente `profile:read credentials:read` e non include `offline_access`. Non presumere di ricevere necessariamente un refresh token. `embed=studio` e `embed_origin` sono gestiti dall'host Studio e dalla pagina di autorizzazione; la pagina del cliente deve solo rispettare il protocollo di messaggistica.

Per un esempio completo del pulsante, consulta la [Guida all'integrazione OAuth dei componenti del sito Studio](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Ciclo di vita, rinnovo e revoca

Il periodo di validità predefinito dell'access token è di 15 giorni; pianifica il rinnovo o la nuova autorizzazione in base a `expires_in` di ogni risposta; il refresh token è predefinito a 30 giorni e il periodo è soggetto alla configurazione del servizio. Non codificare rigidamente questi due valori come promesse permanenti.

Dopo aver ottenuto `offline_access`, puoi chiamare:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Il rinnovo restituisce nuovi token e l'applicazione deve salvare i valori più recenti. Durante il rinnovo viene verificato se l'applicazione è ancora valida, se l'utente è disponibile e se le autorizzazioni sono ancora concesse. In caso di errore, cancella il proprio stato di connessione e autorizza nuovamente.

**L'attuale implementazione del rinnovo OAuth non garantisce che il vecchio refresh token diventi immediatamente non valido dopo il rinnovo.** Non considerare l'ottenimento di un nuovo token come prova che il vecchio token sia stato revocato e non sostituire la terminazione dei token esistenti con la rotazione del secret.

La richiesta di revoca viene chiamata nel modo seguente:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**L'attuale endpoint di revoca restituisce HTTP 200, ma non implementa l'invalidazione immediata dei JWT già emessi.** L'applicazione deve cancellare i token che ha salvato e non può considerare il 200 come prova che tutti i token emessi o le API Key siano diventati non validi. Per API Key esposte o copiate, revoca o ruota separatamente le credenziali corrispondenti.

## Errori comuni e accettazione

| Fenomeno／errore                         | Verifica                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Utilizza i nomi delle autorizzazioni correnti; verifica l'ambito di registrazione dell'applicazione, le limitazioni di delega e le autorizzazioni dell'utente. L'intero catalogo Discovery non è un catalogo selezionabile dall'applicazione                      |
| `invalid_request`             | Parametri obbligatori, indirizzo di callback esatto, challenge e method S256 per client Public                        |
| `invalid_client`              | client ID, stato dell'applicazione, secret del client Confidential; verifica l'uso errato dell'autenticazione Basic             |
| `invalid_grant`               | code scaduto／già usato, verifier o redirect URI non corrispondenti; durante il rinnovo verifica anche le modifiche a applicazione e autorizzazioni                 |
| `access_denied`               | L'utente rifiuta; ripristina il pulsante di connessione, non mostrare ripetutamente l'autorizzazione                                                  |
| `unsupported_grant_type`      | Attualmente sono supportati `authorization_code`, `refresh_token`                             |
| HTTP 401／403                  | Distingui tra stato di accesso non valido, token, scope autorizzato e autorizzazioni di accesso alla risorsa stessa                                     |
| `Failed to fetch`, errori DNS／CORS | Verifica l'host della richiesta reale e la disponibilità del backend del cliente; non attribuirli a “l'utente non ha una Key”                                      |
| Autorizzato ma non riesce a leggere la Key                   | Utilizza `platform.acedata.cloud`, il vero user ID, `items[*].token`; distingui tra lista vuota, paginazione e risposte fallite |
| Pagina interamente vuota dopo il ritorno dell'autorizzazione                     | Renderizza prima la pagina; gestisci separatamente gli errori di callback, token, UserInfo e richiesta delle credenziali; non lasciare che un'eccezione di inizializzazione fermi l'intera pagina                      |
| Non prosegue dopo il login nell'iframe                 | Gestisci secondo le limitazioni esistenti sopra; testa gli scenari di non accesso, scadenza, rifiuto e riconnessione                                          |

Prima della consegna, verifica almeno: callback corretto, rifiuto, state errato, code scaduto／già usato, assenza di Key, errore di rete, scadenza del token, assenza dello scope richiesto, nonché il primo accesso e il cambio di account nello scenario iframe. Non salvare code, token o API Key completi nelle prove di test.

## Verifica in due passaggi e nuova autorizzazione

Dopo che l'utente ha attivato la verifica in due passaggi, Ace Data Cloud completerà nella pagina di autorizzazione la verifica del codice dell'autenticatore o del codice di recupero monouso, quindi consegnerà il codice di autorizzazione. La tua applicazione continua a utilizzare il flusso OAuth standard e non deve richiedere, salvare o inoltrare all'utente chiavi dell'autenticatore o codici di recupero.

Quando l'utente attiva, sostituisce, disattiva la verifica in due passaggi o recupera l'account, le precedenti sessioni dell'account, i refresh token e i relativi token di autorizzazione della piattaforma potrebbero non essere più validi. Quando ricevi una sessione non valida o `invalid_grant`, avvia nuovamente un flusso di autorizzazione visibile all'utente; non riutilizzare ripetutamente vecchi codici di autorizzazione e non tentare di aggirare la verifica. Il metodo di autenticazione delle normali API Key del modello rimane invariato; se sospetti che l'account sia stato compromesso, verifica e revoca separatamente le API Key interessate.
