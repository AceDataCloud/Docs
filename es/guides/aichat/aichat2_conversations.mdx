La API AI Chat v2 (`/aichat2/conversations`) es una interfaz de conversación de nueva generación y una actualización integral de [AI Chat API](https://platform.acedata.cloud/documents/aichat-conversations). Sobre la base de las conversaciones de múltiples turnos alojadas y simplificadas de v1, amplía las siguientes funcionalidades:

- **Entradas de usuario multimodales**: permite enviar directamente texto + imágenes + bloques de archivos mediante el campo estructurado `message`, sin necesidad de adjuntarlos indirectamente mediante `references`.
- **Llamadas a herramientas basadas en agentes**: incorpora un conjunto de herramientas para búsquedas en Internet, extracción de páginas web, lectura de archivos, etc., y permite conectar servidores MCP autorizados por el usuario (Google Drive, Notion, Slack, GitHub, etc.). El modelo puede realizar de forma autónoma múltiples llamadas a herramientas durante una misma solicitud para completar tareas complejas.
- **Eventos de transmisión estructurados**: mediante `accept: text/event-stream` o `application/x-ndjson`, se pueden recibir eventos como `text_delta`, `tool_use`, `tool_result`, `thinking`, `citation`, `card` y `artifact` token por token, lo que facilita su representación por separado en el frontend según el tipo correspondiente.
- **Interrumpible / reanudable**: cuando el modelo necesita que el usuario proporcione información adicional, emite un evento `ask_user_question` y se pausa. En la siguiente llamada, basta con completar la respuesta mediante `tool_results` para continuar.
- **Nuevas acciones CRUD**: en el mismo endpoint, se pueden realizar las operaciones `retrieve` / `retrieve_batch` / `update` / `delete` mediante el campo `action`, sin necesidad de una API adicional para gestionar las conversaciones.
- **Lista de modelos en actualización continua**: incluye de forma predeterminada modelos actuales como GPT-5.4, Claude Opus 4.8, Claude Sonnet 4.6, Gemini 3.1 Pro, GLM 5.1, DeepSeek V4, Kimi K3, entre otros.

Al mismo tiempo, es **totalmente compatible con versiones anteriores de v1 a nivel del cuerpo de la solicitud**: basta con enviar `model` + `question` (+ los campos opcionales `stateful` / `id` / `references` / `preset`) para obtener una respuesta JSON `{answer, id}` equivalente a la de v1. Por lo tanto, la migración desde `/aichat/conversations` no requiere reescribir el cliente; solo hay que cambiar la ruta a `/aichat2/conversations`.

> Si actualmente utilizas `/aichat/conversations`, la interfaz antigua seguirá estando disponible. Puedes migrar según tu propio ritmo.

## Proceso de solicitud

Para utilizar AI Chat v2 API, primero accede a la [consola de Ace Data Cloud](https://platform.acedata.cloud/console/applications) para obtener tu API Token y guardarlo para utilizarlo posteriormente.

![]()

Si todavía no has iniciado sesión o no te has registrado, serás redirigido automáticamente a la página de inicio de sesión, donde se te invitará a registrarte e iniciar sesión. Una vez completado el proceso, volverás automáticamente a la página actual.

**Un único API Token permite utilizar todos los servicios de la plataforma, sin necesidad de solicitar uno por separado para cada servicio.** La primera solicitud incluye una cuota gratuita para que puedas probar el servicio sin coste; cuando el saldo sea insuficiente, puedes recargar el saldo general en la [consola](https://platform.acedata.cloud/console/coin).

## Uso básico

El uso más sencillo es exactamente igual que en v1: enviar `model` + `question` y obtener `{answer, id}`.

Ejemplo con CURL:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。"
  }'
```

Resultado devuelto:

```json
{
  "answer": "AceDataCloud 是一个聚合主流 AI 模型与多模态服务的统一 API 平台，开发者通过一个密钥即可调用 GPT、Claude、Gemini、Midjourney、Suno、Veo 等多家服务。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Ejemplo en Python:

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

## Conversaciones de múltiples turnos

Al igual que en v1, envía `stateful: true` para activar el almacenamiento de sesiones. La API devolverá un `id`; en las solicitudes posteriores, basta con volver a enviar ese mismo `id` para continuar la conversación, sin necesidad de mantener por tu cuenta el historial de messages.

Primera solicitud:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "记住一个数字：42。"
  }'
```

Respuesta:

```json
{
  "answer": "好的，我已经记住了 42。需要我用它做什么吗？",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Segunda solicitud, incluyendo el mismo `id`:
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "¿Cuál es el número que te pedí que recordaras hace un momento?"
  }'
```

```json
{
  "answer": "El número que me pediste que recordara es 42.",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` es `true` de forma predeterminada; omitirlo y pasar explícitamente `true` son opciones equivalentes. Establecer `stateful: false` omitirá la carga del historial de conversaciones anteriores; esto no significa que los resultados de esta ronda no se guarden, ni se aplica a los flujos de herramientas que requieren pausarse y continuar más tarde.

### Conversaciones largas y conservación del texto original

La compresión del contexto solo organiza el contenido que se envía al modelo en esta ronda, no sustituye los registros de chat guardados. Mediante `action: retrieve` se siguen pudiendo leer todos los mensajes guardados; la edición o eliminación explícita de una conversación seguirá surtiendo efecto según lo solicitado.

El modelo puede buscar y leer de forma paginada el texto original del historial dentro de la conversación actual. Cuando sea necesario seguir modificando un artículo, citar cifras o preparar una publicación, se debe leer el texto original correspondiente y no sustituir el contenido principal por un resumen. Esta capacidad no restaura automáticamente los mensajes que ya se hayan perdido en versiones anteriores.

Si falla la organización del contexto, conserva el ID de la conversación y comprueba el evento `error`; el servicio no sobrescribirá el texto original con un resumen vacío. Las operaciones de herramientas que ya se hayan completado antes del fallo pueden seguir siendo válidas; consulta primero sus resultados para evitar generar o publicar contenido duplicado. Cuando una conversación individual alcance el límite de almacenamiento, se mostrará un error explícito; los registros guardados existentes no se recortarán para liberar espacio. Puedes exportar el contenido necesario y luego iniciar una nueva conversación.

## Respuestas en streaming

v2 admite dos formatos de streaming, seleccionados según el encabezado `accept`:

| Escenario                    | `accept`               | Formato de los datos                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Interfaz web / EventSource  | `text/event-stream`    | `data: {json}\n\n`, la última línea es `data: [DONE]\n\n` |
| Servidor / CLI / análisis de streaming en Node | `application/x-ndjson` | Un objeto JSON por línea                               |
| Sin necesidad de streaming                 | `application/json` (predeterminado) | Devuelve `{answer, id}` de una sola vez                       |

### Ejemplo de NDJSON

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "Presenta Hangzhou en tres frases.",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # Compatible con v1: los fragmentos incrementales también se proporcionan mediante el campo delta_answer
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

Cada línea de NDJSON es un evento estructurado; el más habitual es `text_delta`:

```json
{"type":"text_delta","content":"Han","delta_answer":"Han","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"g","delta_answer":"g","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"zhou","delta_answer":"zhou","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### Ejemplo de SSE

En el navegador, `EventSource` no admite cuerpos de solicitud personalizados, por lo que se recomienda utilizar `fetch` + análisis manual dividiendo por `\n\n`:

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "Presenta Hangzhou en tres frases.",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### Tipos de eventos de streaming

| `type`              | Significado                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `text_delta`        | Fragmento de texto incremental de la respuesta del asistente. `content` contiene el contenido nuevo; para mantener la compatibilidad con v1, el mismo evento también incluye `delta_answer` (igual a `content`) e `id`.                                        |
| `thinking`          | Proceso de razonamiento del modelo (solo aparece cuando el modelo seleccionado expone el razonamiento).                                                                                      |
| `tool_use`          | El modelo decide llamar a una herramienta; el evento incluye `tool_id`, `tool_name` e `input`.                                                                        |
| `tool_result`       | Resultado de la ejecución de la herramienta, vinculado al `tool_use` anterior mediante `tool_id`; `is_error` indica si se ha producido un fallo.                                                             |
| `card`              | Tarjeta estructurada generada por una herramienta (como imágenes o vistas previas de enlaces), adecuada para mostrarse directamente.                                                                                          |
| `citation`          | URL de la fuente utilizada para complementar la cita del fragmento de texto correspondiente.                                                                                                  |
| `ask_user_question` | Se emite cuando el modelo necesita que el usuario proporcione información adicional; la conversación pasa al estado `awaiting_user_input`. Consulta más abajo [Reanudar una conversación pausada](#reanudar-una-conversación-pausada).                                                 |
| `artifact`          | Elemento independiente generado por el modelo (como un bloque de código o un documento), que se puede guardar o descargar.                                                                                            |
| `system_message`    | Mensaje informativo del sistema (no forma parte del contenido del usuario ni del asistente), utilizado únicamente para mostrar avisos en la interfaz.                                                                                           |
| `compact`           | El contexto del modelo se ha organizado; los mensajes originales guardados permanecen sin cambios y el cliente no necesita eliminar el historial del chat.                                                                                    |
| `error`             | Se ha producido un error en esta ronda; `message` describe el contenido del error.                                                                                              |
| `done`              | El registro final de la conversación de esta ronda se ha guardado correctamente. Incluye `usage` (con `prompt_tokens` / `completion_tokens` / `total_tokens`) y `terminal_reason`; aun así, se debe determinar si la tarea se ha completado según el motivo de finalización. |
Para los clientes que solo se preocupan por la respuesta final, concatenar el `content` de todos los `text_delta` es equivalente a `answer` en el modo `application/json`.

## Entrada multimodal

Si la entrada del usuario incluye imágenes o archivos, pasa `message` (un array) en lugar de `question`. Cada elemento del array es un bloque de contenido:

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "¿Cuántos gatos hay en esta imagen?" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

Tipos de bloques compatibles:

- `text` — Texto normal, el campo `text` es obligatorio.
- `image_url` — Imagen, `image_url.url` es obligatorio.
- `file_url` — Archivo (PDF, CSV, TXT, etc.), `file_url.url` es obligatorio.

### Relación con `references` de v1

Para garantizar la compatibilidad con clientes antiguos, v2 sigue reconociendo el campo `references: ["https://...", ...]`:

- Si el sufijo de la URL es `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif`, se convierte automáticamente en un bloque `image_url`;
- Las demás extensiones se convierten en bloques `file_url`;
- Si también se proporciona `question`, se añade al principio como un bloque `text`.

Por lo tanto, si solo quieres migrar desde v1 sin modificar el cuerpo de la solicitud, basta con cambiar la ruta a `/aichat2/conversations`, y el uso original de `references` seguirá funcionando con normalidad.

Si necesitas un control más preciso (por ejemplo, colocar varias imágenes entre fragmentos de texto o si el orden es importante), utiliza directamente el array `message`.

## Llamadas a herramientas y MCP

La principal mejora de v2 es que el modelo puede llamar a herramientas de forma autónoma para completar tareas de varios pasos. **Esta función está habilitada de forma predeterminada** y no requiere ninguna configuración adicional por parte del cliente en la solicitud. Casos habituales:

- El usuario pregunta «Ayúdame a buscar qué exposiciones nuevas hay recientemente en Shanghái» → El modelo llama a la búsqueda web integrada → Organiza los resultados en una respuesta.
- El usuario pregunta «Lee este PDF y luego escribe un resumen» → El modelo llama a file_read → Escribe el resumen.
- El usuario ya ha autorizado Google Drive / GitHub / Notion, etc., en [Connections](https://platform.acedata.cloud/connections) → El modelo puede llamar a las herramientas MCP correspondientes para leer y escribir sus datos.

En los flujos NDJSON / SSE, las llamadas a herramientas se presentan mediante dos tipos de eventos: `tool_use` y `tool_result`. Por ejemplo:

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"Exposiciones de primavera de Shanghái 2026"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"Actualmente","delta_answer":"Actualmente","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"Shanghái","delta_answer":"Shanghái","id":"f2f4b3e8-..."}
...
```

Si no quieres mostrar los detalles de las llamadas a herramientas en el frontend, basta con ignorar estos tipos de eventos: `tool_use` / `tool_result` / `card` / `citation`. La salida final del modelo seguirá transmitiéndose mediante `text_delta`.

`max_turns` permite limitar el número máximo de rondas en las que el modelo puede llamar a herramientas por sí mismo durante esta solicitud. El rango es de 1–500 y, si se omite, el valor predeterminado es 500. Establecer un valor pequeño (por ejemplo, `max_turns: 1`) permite forzar una única respuesta e impedir cualquier llamada a herramientas.

## Ejecución asíncrona y autorización desatendida

Si tu llamada proviene de un Webhook de alertas, un sistema CI/CD, un sistema de monitorización u otra tarea en segundo plano, puedes establecer `async: true` para que la interfaz devuelva inmediatamente un ID de tarea mientras la ejecución continúa en segundo plano:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "Mi servicio ha activado una alerta. Notifica al grupo de WeChat «Equipo AceDataCloud» utilizando mi cuenta personal de WeChat..."
}
```

Ejemplo de respuesta:

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

Posteriormente, puedes utilizar `action: retrieve` + `id` para consultar el resultado de la conversación. También puedes proporcionar `callback_url`; cuando la tarea finalice, la plataforma enviará `{ status, answer, usage, error }` mediante una solicitud POST a tu dirección de devolución de llamada. `callback_url` debe utilizar `http` / `https` y no puede especificar directamente `localhost` ni una dirección IP privada literal.

Las tareas en segundo plano normalmente no tienen a nadie que pueda hacer clic para confirmar. Si deseas que determinados Skill o MCP Server ejecuten acciones como enviar, publicar o escribir en modo desatendido, debes proporcionar explícitamente una lista de autorizaciones previas en el cuerpo de la solicitud:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "Mi servicio ha activado una alerta. Notifica al grupo de WeChat «Equipo AceDataCloud» utilizando mi cuenta personal de WeChat..."
}
```

Los valores de `allowed_skills` son los slug de los Skill conectados; los valores de `allowed_mcp_servers` son los slug de los MCP Server conectados. Los Skill / MCP Server que no estén incluidos en la lista de autorizaciones previas solo podrán realizar vistas previas, ejecuciones dry-run o rechazar operaciones de escritura en modo desatendido.

El control de `text` también puede utilizar el objeto equivalente `text`ttended_policy`:

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

La autorización previa consiste precisamente en estas dos listas: si las listas están vacías, no se autoriza ninguna capacidad, sin necesidad de campos de activación adicionales.

Nota: La autorización previa solo significa que «esta solicitud permite que estas capacidades omitan la confirmación manual en modo desatendido». El Skill correspondiente también debe admitir `--unattended-confirm` o el mecanismo de seguridad equivalente; de lo contrario, seguirá ejecutando dry-run y no realizará directamente operaciones de escritura.

## Reanudar conversaciones pausadas

Algunas herramientas hacen que el modelo «pregunte al usuario». En ese momento, el modelo emitirá un evento `ask_user_question` y la conversación quedará congelada en el estado `awaiting_user_input`:

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "¿Quieres que el informe generado esté en chino o en inglés?",
  "options": ["Chino", "Inglés"],
  "id": "f2f4b3e8-..."
}
```

En el frontend, representa este evento como una tarjeta para que el usuario seleccione una respuesta y, a continuación, inicia la siguiente solicitud utilizando el mismo `id` y devuelve la respuesta mediante `tool_results`:
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

En el cuerpo de la solicitud, `tool_use_id` **debe** coincidir exactamente con el `tool_id` cuando se pausó; de lo contrario, se devolverá un error 400. Cuando la solicitud contiene `tool_results` al mismo tiempo, `question` / `message` / `references` se ignorarán.

Si el usuario decide abandonar esta pregunta, basta con enviar directamente un nuevo `question` / `message`; la plataforma marcará automáticamente la llamada a la herramienta pausada como «omitida por el usuario».

## Gestión de sesiones (CRUD)

v2 proporciona una gestión ligera de sesiones mediante el campo `action` en el mismo endpoint, sin necesidad de abrir una API adicional.

### `action: retrieve` —— Recuperar una sesión

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

Devuelve el documento completo de la sesión (incluido el historial de `messages`, `model`, `title`, `tools_used`, etc.).

### `action: retrieve_batch` —— Enumerar resúmenes de sesiones

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

Devuelve `{ items: [...], total }`. **El resumen no incluye la lista de mensajes `messages`; si el usuario abre una sesión, se debe utilizar `action: retrieve` para recuperar por separado todos sus mensajes.**

Parámetros de filtrado opcionales: `user_id`, `application_id`, `model_group`, `model`.

### `action: update` —— Cambiar el título o reescribir el historial

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "Plan de viaje a Hangzhou"
}
```

También se puede enviar `messages`, pero el servidor realizará una validación estricta del esquema (debe tener el formato `ToolUseContent` plegado); si no cumple los requisitos, se devolverá un error 400. En general, se recomienda utilizar esta función únicamente para modificar `title`.

### `action: delete` —— Eliminar una sesión

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Devuelve `{ id, success: true }`. Una vez eliminada, la sesión no se podrá recuperar; confirma la operación antes de ejecutarla.

## Migración fluida desde v1

Si ya estás utilizando [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations), la migración a v2 prácticamente no requiere cambios en el código:

1. Cambia la URL de `https://api.acedata.cloud/aichat/conversations` a `https://api.acedata.cloud/aichat2/conversations`.
2. Si anteriormente utilizabas nombres de modelos de v1 (como `gpt-3.5`, `gpt-4-browsing`, etc.), al cambiar a v2 se recomienda actualizar a modelos actuales (como `gpt-5.4`, `claude-opus-4-8`, `gemini-3.1-pro-preview`, etc.).
3. Los campos del flujo NDJSON mantienen la compatibilidad con versiones anteriores: cada evento `text_delta` sigue incluyendo `delta_answer` e `id`, por lo que los clientes que anteriormente analizaban `delta_answer` línea por línea no necesitan realizar cambios.

Después de la migración, puedes habilitar las nuevas capacidades de v2 según tus necesidades (entrada multimodal `message`, SSE, llamadas a herramientas, CRUD mediante `action`) e implementarlas progresivamente.

## Gestión de errores

Las respuestas de error tienen un formato unificado:

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

Errores comunes:

- `400 bad_request`: faltan campos obligatorios, `tool_use_id` no coincide, el esquema de `messages` no es válido, etc.
- `401 invalid_token`: el encabezado `authorization` es incorrecto.
- `404 not_found`: la sesión correspondiente al `id` no existe al ejecutar `action: retrieve / update / delete`.
- `413 conversation_storage_limit`: la sesión ha superado el límite de almacenamiento; los registros guardados existentes no se han sobrescrito.
- `429 too_many_requests`: se ha activado el límite de velocidad.
- `503 context_compaction_failed`: ha fallado la compactación del contexto; los registros existentes se conservan.
- `500 conversation_persist_failed`: ha fallado el guardado final de esta ronda; haber recibido el texto no significa que el registro final se haya guardado correctamente. Consulta la sesión mediante su ID.
- `500 chat_error`: el servicio no está disponible temporalmente o no se ha generado contenido en esta ronda (no se cobrará).

En las respuestas en streaming, los errores se envían mediante eventos con el formato `{"type":"error","message":"..."}`, tras lo cual el flujo finalizará. `[DONE]` solo indica que la transmisión ha terminado; si existe un `error`, no debe considerarse una operación exitosa y tampoco se enviará un evento `done` de éxito.

## Conclusión

La API AI Chat v2, al tiempo que mantiene la compatibilidad con versiones anteriores de v1, transforma las conversaciones de «preguntas y respuestas de una o varias rondas» en «conversaciones observables basadas en agentes»: entrada multimodal, llamadas a herramientas, capacidad de pausa y reanudación, eventos estructurados en streaming y CRUD integrado. Se recomienda utilizar directamente v2 para las nuevas integraciones; las integraciones existentes de v1 pueden migrarse gradualmente sin interrupciones. Si tienes alguna pregunta, no dudes en ponerte en contacto con nuestro equipo de soporte técnico.
