---
title: "Configurar el uso compartido del saldo global de AceDataCloud Application"
description: "Platform API guide - Ace Data Cloud"
---

Configure `allow_consume_global`. Después de activarlo, las Application de pago por uso que cumplan las condiciones podrán seguir utilizando el saldo global de la cuenta cuando su propio saldo sea insuficiente.

## Preparativos

- Cree y guarde de forma segura el [Account Token](https://platform.acedata.cloud/documents/platform-token).
- Obtenga el `application_id` de la Application que posee desde la [lista de solicitudes de servicio](https://platform.acedata.cloud/documents/platform-application-list).

```shell
export PLATFORM_TOKEN='你的账户令牌'
export APPLICATION_ID='你的 Application ID'
```

## Resumen de la API

| Elemento    | Contenido                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------- |
| Método   | `POST`                                                                                             |
| URL  | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| Autenticación   | Account Token                                                                                      |
| Body | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

Si tiene éxito, devuelve el objeto Application actualizado. Tome como referencia `allow_consume_global` en la respuesta, en lugar de asumir que el valor solicitado se guardó necesariamente.

> Las Application de tipo `Period` no tienen permitido consumir el saldo global. Incluso si se solicita `true`, el servidor mantendrá este campo como `false`.

## Manejo de errores

- `401`: El Account Token no es válido o falta.
- `403`: La cuenta actual no es la propietaria de esta Application.
- `404`: El ID de Application no existe.

El acceso para recargar el saldo global y los paquetes disponibles se basarán en la consola de la plataforma y en los paquetes reales devueltos por la [creación de pedidos](https://platform.acedata.cloud/documents/platform-order-create); no asuma que existe un paquete de tipo `Wallet`.

## Aplicaciones con sobregiro autorizado

Cuando el campo de solo lectura `allow_overdraft=true` de una aplicación de pago por uso está activado, esta aplicación puede seguir descontando cargos de su propio saldo, incluso si el saldo se vuelve negativo, y no cambiará a la cuenta global debido a un saldo insuficiente. Las aplicaciones sin sobregiro activado siguen `allow_consume_global`; después del cambio, si se permite el sobregiro dependerá de la configuración de la Application global desde la que se realiza el cobro real.

## Límite de concurrencia para cuentas de prueba

El sistema utiliza la marca de usuario de solo lectura `has_recharged` para registrar si alguna vez se completó correctamente una recarga de pago o si un administrador añadió créditos manualmente; la marca se actualiza después de que la operación tenga éxito, y los usuarios históricos se actualizarán de forma uniforme según los pedidos o los registros explícitos de adición de créditos. Para las cuentas que no hayan realizado una recarga de pago ni hayan recibido créditos añadidos manualmente por un administrador, solo se permite ejecutar una solicitud facturable de forma simultánea en toda la cuenta; diferentes API Key y diferentes servicios comparten esta única plaza. Las recompensas, las tarjetas de canje y los saldos transferidos no se consideran recargas de pago. Las cuentas que ya hayan completado una recarga de pago o hayan recibido créditos añadidos manualmente por un administrador no están sujetas a este límite de concurrencia de prueba, y siguen cumpliendo las comprobaciones originales de saldo y cuota de credenciales.

Cuando ya hay una solicitud en ejecución, las nuevas solicitudes devuelven `429 too_many_requests`. Las APIs gratuitas de sondeo, como las consultas de tareas, pueden seguir utilizándose normalmente. La autenticación de conexión de Realtime sigue el flujo original de facturación por rondas y no ocupa esta plaza de solicitudes normales.

Cuando una API asíncrona devuelve “aceptado”, la tarea aún está en ejecución, y debe esperar al resultado final antes de enviar la siguiente solicitud de generación. La desconexión de la red o el tiempo de espera del proxy no significa que la tarea se haya detenido; si la tarea no alcanza un estado final durante mucho tiempo, proporcione el `trace_id` para contactar con el soporte y solicitar una verificación.

Este límite no cambia las APIs disponibles para prueba ni modifica las reglas de facturación originales. Los cargos siguen liquidándose según el uso real después de que finalice la solicitud.
