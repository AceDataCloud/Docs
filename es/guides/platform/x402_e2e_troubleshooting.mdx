X402 involucra HTTP, SDK, firmas, Facilitator y transacciones on-chain. Al solucionar problemas de firma o liquidación, se recomienda confirmar capa por capa en el orden de “entrada pública -> respuesta 402 -> SDK payment handler -> settlement on-chain”. Este tutorial explica cómo verificar cada capa y enumera errores comunes.

## Verificar la entrada pública

Declaración de capacidades del Facilitator:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Si devuelve `facilitator`, `supportedKinds` y los endpoints del protocolo, indica que los metadatos de capacidades son normales. El descubrimiento de recursos de API ha sido retirado; llama directamente a la API objetivo y toma como referencia la respuesta 402 en tiempo real.

Capacidades compatibles con Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

Si devuelve `kinds`, indica que la entrada del Facilitator funciona correctamente.

## Verificar 402 `accepts`

Envía una solicitud no autenticada que no genere cargos:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Verifica si el `accepts` devuelto incluye la red que deseas usar. `network` es un identificador CAIP-2:

- `eip155:8453` + `exact` (Base)
- `eip155:8453` + `upto` (Base, medición posterior)
- `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` + `exact` (Solana)

Si no está la red objetivo, indica que esa API o el entorno actual no tiene configurado el método de cobro X402 correspondiente.

## Ejecutar las herramientas avanzadas de validación de X402Client

El repositorio X402Client proporciona herramientas avanzadas de validación, que pueden utilizarse para confirmar la selección de respuestas 402, la generación de firmas, el paid retry y el settlement on-chain. Requieren una funded wallet, RPC, clave privada y dependencias de desarrollo. Para una integración empresarial normal, se recomienda priorizar el SDK de TypeScript o Python; ejecuta estas herramientas solo cuando necesites localizar problemas de firma o liquidación on-chain.

Dirección del repositorio: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)

```bash
git clone https://github.com/AceDataCloud/X402Client.git
cd X402Client/typescript
npm install
npm install --no-save ethers @solana/spl-token bs58 tsx
```

Base:

```bash
export X402B_BASE_PAYER_PRIVATE_KEY=0x...
TEST_API_PATH='/openai/chat/completions' \
TEST_BODY='{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}],"max_tokens":10}' \
npx tsx scripts/test-real-e2e.ts
```

Solana:

```bash
export X402B_SOLANA_PAYER_PRIVATE_KEY=...
npx tsx scripts/test-solana-e2e.ts
```

Las herramientas de validación normalmente imprimen:

1. La respuesta 402 de la primera solicitud.
2. El payment requirement seleccionado.
3. El resumen de `PAYMENT-SIGNATURE` después de firmar.
4. El estado HTTP y el cuerpo de respuesta después del reintento.
5. La transacción de settlement on-chain, o el motivo del error del Facilitator en caso de fallo.

No envíes claves privadas ni `PAYMENT-SIGNATURE` completos al sistema de registros ni a los tickets.

Explicación:

- Base `exact`, Solana `exact` y Base `upto` completaron el paid retry de HTTP 402 a HTTP 200.

## SDK smoke test

Las herramientas avanzadas de validación se utilizan para comprobar las firmas y la liquidación on-chain. El lado empresarial también debe ejecutar un SDK smoke test para confirmar que el código de aplicación puede procesar automáticamente 402 mediante el payment handler. A continuación solo se muestran los fragmentos principales; el código completo debe completar la wallet, el provider y los import.

TypeScript:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const res = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly ADC_SDK_X402_OK' }],
  max_tokens: 8
});
```

Python:

```python
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
    )
)

res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly ADC_PY_X402_OK"}],
    max_tokens=8,
)
```

Si el modelo devuelve la cadena fija según lo solicitado, indica que el SDK, el payment handler, el Gateway, el Facilitator y la API objetivo están conectados.

Los dos smoke test anteriores usan Base `exact`, y realizan la liquidación por el monto fijo cotizado en 402. Las completaciones de chat pertenecen a escenarios medidos por token; para la integración formal, se recomienda pasar `preferScheme: 'upto'` (en Python, `prefer_scheme="upto"`), para liquidar según el uso real.

El objeto devuelto por el SDK de Python es un `dict`, y se puede usar `res["choices"][0]["message"]["content"]` para leer el contenido.

## E2E de pago de pedidos

El pago de pedidos utiliza la API de plataforma de `platform.acedata.cloud`, y requiere un token de cuenta de la plataforma. La cadena completa es: crear un pedido Pending, `POST /api/v1/orders/{order_id}/pay/` activa 402 y luego reintentar con `PAYMENT-SIGNATURE`.

Ejemplo de resultados de validación de pago de pedidos de pequeño importe:

> Los siguientes registros de transacciones son muestras históricas de pruebas reales bajo la política anterior; los importes y hashes de transacción se conservan sin cambios. Los nuevos pedidos X402 ya no ofrecen descuentos por método de pago; utiliza el `amount` de la respuesta 402 actual como base para la firma y el pago.
```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
accepts [('eip155:8453', 'exact', '1200000'), ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000')]

status 200
order state Finished
pay_way X402
pay_id 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}

Base tx status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Explicación de los resultados:

- Después de crear el pedido, el estado del pedido es `Pending`, y el precio es `1.26`.
- La primera solicitud `pay/` devuelve HTTP 402, hay Base `exact` y Solana `exact` en `accepts`, y los importes son ambos `1200000` atomic USDC.
- Después de reintentar con Base `PAYMENT-SIGNATURE`, devuelve HTTP 200, el estado del pedido cambia a `Finished`, y `pay_way` es `X402`.
- Después de decodificar `PAYMENT-RESPONSE`, muestra `success=True`, `network=base`, y proporciona el mismo hash de transacción.
- En BaseScan, el estado de la transacción es `1`, el importe de la transferencia es `1200000` atomic USDC, es decir, `1.2` USDC.
- El precio de creación `1.26` se pagó durante el período de la antigua política de descuentos de pago X402, y el importe final de la firma y liquidación es `1.2` USDC.

Si el pago del pedido no tiene `Authorization: Bearer {platform_token}`, o el pedido no pertenece a la cuenta actual, fallará en la capa de permisos de la plataforma; esto es diferente de la API X402 sin cuenta que llama directamente a `x402.acedata.cloud`.

## Errores comunes

| Fenómeno                                           | Dirección de investigación                                                                |
| -------------------------------------------- | ------------------------------------------------------------------- |
| La primera solicitud no es 402                                  | Compruebe si se incluyó `Authorization` por error, o si esa API todavía no tiene X402 pricing.                  |
| `No payment requirement for network`         | La red objetivo no está en `accepts`; cambie de red o compruebe la configuración del Gateway.                               |
| `invalid_402`                                | La respuesta 402 no es JSON válido; compruebe el proxy, la puerta de enlace o la página de error.                                        |
| `Authorization nonce already processed`      | Se reutilizó el mismo `PAYMENT-SIGNATURE`; vuelva a firmar.                                  |
| `invalid_upto_evm_payload_invalid_signature` | Compruebe si el chainId de `upto`, el domain de Permit2, la dirección del facilitator y la cuenta de firma son coherentes.         |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Ejecute `approve-permit2` para USDC de la cadena objetivo.                                     |
| `Payer has insufficient USDC balance`        | La billetera pagadora no tiene suficiente USDC.                                                       |
| HTTP 200 pero no hay tx hash                         | El importe real de `upto` puede ser 0, o el registro de settlement todavía se está escribiendo de forma asíncrona.                             |
| Solana `Missing transaction payload`         | No hay transacción serializada ni signature en el envelope `PAYMENT-SIGNATURE`; compruebe el wallet adapter. |

## Lista de verificación de Base `upto`

`upto` actualmente solo se proporciona en Base (`eip155:8453`). Debido a que la firma `upto` vincula más parámetros de EVM typed data, al integrarla se debe confirmar especialmente que los campos en tiempo real de la respuesta 402 coincidan completamente con la firma del cliente.

```text
Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Si Base `upto` devuelve `invalid_upto_evm_payload_invalid_signature`, compruebe primero:

1. El `extra.chainId` (debe ser `8453`) en la entrada `eip155:8453` + `upto` devuelta por la API.
2. El `extra.facilitatorAddress` devuelto por la API.
3. La dirección del facilitator Base `upto` devuelta por `https://facilitator.acedata.cloud/supported`.
4. El domain de Permit2, spender, contrato USDC y cuenta de firma.
5. Si la billetera ya ha hecho approve Permit2 para Base USDC.

El digest de firma de `upto` vincula simultáneamente el domain de Permit2, chain ID, spender, dirección de recepción, dirección del facilitator y validAfter. Si cualquiera de ellos no coincide, el Facilitator recuperará un signer incorrecto y devolverá invalid signature. Si todos ellos coinciden pero aún devuelve 402, el siguiente paso es comprobar la allowance de Permit2; cuando no está autorizada, devuelve `PERMIT2_ALLOWANCE_REQUIRED`.

## Guardar información de verificación

Una verificación completa debe guardar al menos:

- API path y resumen del cuerpo de la solicitud;
- network y scheme seleccionados;
- `maxAmountRequired`;
- dirección de la billetera payer;
- estado final HTTP;
- salida del modelo o ID de tarea en la respuesta;
- enlace de la transacción de settlement;
- ID de trace del Gateway o ID de registro de uso de la plataforma.

No guarde claves privadas, `PAYMENT-SIGNATURE` completo, signature EIP-712 completa ni frase mnemotécnica.

## Errores de pago estructurados

Los fallos de X402 después de firmar devolverán `code` estable, parámetros de interpolación seguros, etapa y marca de reintento en `extensions.acedatacloud.paymentError`. Priorice el uso de esta estructura para investigar, no analice el `error` en inglés de nivel superior, ni solicite a los usuarios firmas de billetera o texto original de simulación on-chain.

- `charged: false`: la validación rechazó explícitamente antes del settlement; no se inició ningún cobro esta vez.
- Sin `charged`: el resultado es desconocido o ya entró en la etapa de settlement; primero consulte el pedido y el estado on-chain, está prohibido repetir directamente el pago.
- `settlement_pending`: no repita el pago por ahora; primero actualice el pedido o contacte con soporte.
- code no reconocido: trátelo como `payment_failed` y conserve el código técnico público para que el servicio de atención al cliente pueda buscarlo.
