---
title: "Esquemas de facturación X402 `exact` y `upto`"
description: "Platform API guide - Ace Data Cloud"
---

Ace Data Cloud X402 actualmente utiliza dos tipos de scheme: `exact` y `upto`. Resuelven diferentes problemas de facturación.

## `exact`

`exact` significa que el precio puede determinarse antes de que esta solicitud entre en la API objetivo. El importe firmado por el cliente es el importe final cobrado.

Adecuado para:

- Generación de imágenes con precio fijo;
- Creación de tareas de video con precio fijo;
- APIs de búsqueda o herramientas con precio fijo;
- Pago de pedidos.

EVM `exact` utiliza USDC EIP-3009 `TransferWithAuthorization`:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": {
    "authorization": {
      "from": "0x...",
      "to": "0x...",
      "value": "95215",
      "validAfter": "1780237345",
      "validBefore": "1780240945",
      "nonce": "0x..."
    },
    "signature": "0x..."
  }
}
```

El Facilitator verifica la firma y el importe durante la fase `/verify`, y envía esta autorización a la cadena durante la fase `/settle`.

## `upto`

`upto` significa que el cliente autoriza un límite máximo, y Ace Data Cloud liquida según el uso real después de que se complete la solicitud; el cargo real no puede superar el límite.

Adecuado para:

- Completado de chat: el precio final depende de los prompt tokens y los completion tokens;
- Respuestas en streaming: solo se conoce después de que termina la longitud real de salida;
- Futuras APIs de medición posterior.

`upto` utiliza Permit2 `PermitWitnessTransferFrom`. Lo que firma el cliente no es una transferencia fija, sino una autorización de límite con witness:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2Authorization": {
      "from": "0x...",
      "spender": "0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002",
      "nonce": "123456789",
      "deadline": "1780240945",
      "permitted": {
        "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "amount": "95215"
      },
      "witness": {
        "to": "0x...",
        "facilitator": "0x...",
        "validAfter": "1780237345"
      }
    },
    "signature": "0x..."
  }
}
```

`permitted.amount` es el límite máximo, no necesariamente el cargo final. El Gateway convertirá el uso real en `amount` y lo pasará al Facilitator durante la fase `/record`. El Facilitator solo permite liquidar `amount &lt;= permitted.amount`.

Resultado de ejecución del programa Base `upto`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
elapsed_ms 5104
content ADC_BASE_UPTO_OK
id chatcmpl-DlcbyS4IT8kUAMo4Ri97HiIHc9T8V
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036

explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Explicación:

- El límite de autorización devuelto en 402 es `95215` atomic USDC, y el cliente firma según este límite.
- Después de la respuesta real del modelo, solo se liquidan `3` atomic USDC, y la transacción en cadena ya se puede consultar en BaseScan.
- Este resultado puede demostrar la diferencia clave de `upto`: el importe firmado es el límite máximo, y el settlement en cadena puede ser menor que el límite máximo.
- Si el uso real supera el límite máximo, el Facilitator debe rechazar el settlement, y el cliente necesita autorizar nuevamente según un límite máximo más alto.

`upto` actualmente solo se proporciona en Base. Cuando se requiera medición posterior, utilice Base.

## Por qué se necesita Permit2 approve

`upto` finalmente permite que el proxy x402 retire USDC de la cartera pagadora mediante Permit2. Antes del primer uso, la cartera pagadora debe otorgar a Permit2 una ERC-20 allowance.

Python CLI:

```bash
pip install 'acedatacloud-x402[cli]'
X402_PRIVATE_KEY=0x... acedatacloud-x402 approve-permit2 --network base
```

De forma programática:

```python
from acedatacloud_x402 import EVMAccountSigner, approve_permit2

approve_permit2(
    rpc_url="https://mainnet.base.org",
    signer=EVMAccountSigner.from_private_key("0x..."),
    token_address="0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
)
```

Después de completar la autorización, cada solicitud aún necesita firmar un nuevo envelope `upto`, porque nonce, deadline, witness y el límite de importe son todos diferentes.

## Liquidación de importe cero

`upto` admite casos donde el importe real es 0. Por ejemplo, si la API objetivo no produjo exitosamente un uso facturable, el Gateway puede pasar `amount = "0"`. El Facilitator devolverá éxito, pero no enviará una transacción en cadena.

Esto puede evitar el problema de “la solicitud no tuvo éxito pero aún se cobran tarifas en cadena”.

## Recomendaciones de selección

| Escenario                   | Recomendación                       |
| --------------------------- | ----------------------------------- |
| API de precio fijo          | Use `exact`, la lógica es simple.   |
| Pago de pedidos             | Use `exact`.                        |
| Completado de chat, cobro por token | Use Base `upto`.             |
| Aún no se ha realizado Permit2 approve | Primero use `exact` para verificar el flujo, luego cambie a `upto`. |

Si no está seguro de cuál elegir, primero use el comportamiento predeterminado del SDK; el SDK seleccionará el payment requirement de red coincidente devuelto por el servidor.

## Lista de comprobación de Base `upto`

Al integrar o solucionar problemas, confirme que los siguientes parámetros provengan de la misma respuesta 402 y se mantengan consistentes al firmar en el cliente:

| Parámetro                  | Punto de comprobación                                          |
| -------------------------- | -------------------------------------------------------------- |
| `network`                  | Debe ser `eip155:8453`.                                        |
| `scheme`                   | Debe ser `upto`.                                               |
| `extra.chainId`            | El chain id de Base es `8453`.                                 |
| `asset`                    | Use la dirección del contrato Base USDC en la respuesta 402.   |
| `extra.facilitatorAddress` | Debe participar en witness y coincidir con Facilitator `/supported`. |
| Permit2 allowance          | La cartera pagadora debe autorizar primero Permit2 para Base USDC. |

Errores comunes y formas de manejarlos:

| Error                                        | Forma de manejo                                                                          |
| -------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `invalid_upto_evm_payload_invalid_signature` | Compruebe si el chain id, la dirección del facilitator, el domain de Permit2, spender, la cuenta firmante y witness coinciden con la respuesta 402. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Después de ejecutar Permit2 approve para el USDC de la cadena objetivo, inicie nuevamente la solicitud. |
| `amount exceeds permitted amount`            | El uso real supera el límite firmado; se necesita firmar nuevamente según un límite más alto. |
