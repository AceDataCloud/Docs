TypeScript es una de las formas más recomendadas para integrar Ace Data Cloud X402. El SDK oficial se encarga de las llamadas API normales, el sondeo de tareas, el manejo de errores y los reintentos automáticos; `@acedatacloud/x402-client` se encarga de firmar el encabezado de solicitud `PAYMENT-SIGNATURE` al encontrar `402 Payment Required`.

Direcciones de código fuente y paquetes:

- Repositorio del SDK: [https://github.com/AceDataCloud/SDK](https://github.com/AceDataCloud/SDK)
- Repositorio de X402 Client: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)
- SDK npm: [https://www.npmjs.com/package/@acedatacloud/sdk](https://www.npmjs.com/package/@acedatacloud/sdk)
- X402 Client npm: [https://www.npmjs.com/package/@acedatacloud/x402-client](https://www.npmjs.com/package/@acedatacloud/x402-client)

## Instalar dependencias

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Si se usa Base, se necesita capacidad de firma EVM:

```bash
npm install ethers
```

Si se usa Solana, se necesita un adaptador de wallet de Solana o `@solana/web3.js`:

```bash
npm install @solana/web3.js
```

Salida de comprobación de instalación e importación de un proyecto npm limpio:

```text

@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3

```

Explicación de los resultados:

- Tanto `@acedatacloud/sdk` como `@acedatacloud/x402-client` se pueden instalar desde npm e importar mediante Node.js.
- `ethers` se utiliza para la firma de typed data de EVM, y `@solana/web3.js` se utiliza para la construcción de transacciones de Solana.

## Ejemplo de Base

En el navegador se puede usar directamente `window.ethereum`. En Node.js se puede envolver `ethers.Wallet` con un provider de estilo EIP-1193.

```ts
import { Wallet } from 'ethers';
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') {
      throw new Error(`unsupported method: ${method}`);
    }
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const result = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Say hi in 3 words' }],
  max_tokens: 10
});

console.log(result.choices[0].message.content);
```

## Ejemplo de wallet de navegador

Al usar MetaMask, Coinbase Wallet o WalletConnect en una aplicación frontend, normalmente se pasa directamente el provider EIP-1193:

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const [address] = await window.ethereum.request({ method: 'eth_requestAccounts' });

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: window.ethereum,
    evmAddress: address
  })
});

const image = await client.images.generate({
  provider: 'nano-banana',
  prompt: 'a yellow banana on a white background'
});
```

La wallet del navegador mostrará una confirmación de firma. Lo que firma el usuario no es un mensaje arbitrario, sino el requisito de pago devuelto por la API: la dirección de recepción, el contrato USDC, el importe, el período de validez y el nonce están todos incluidos en la firma.

## Ejemplo de Solana

Solana utiliza SPL USDC `TransferChecked`. El wallet adapter pasado debe exponer `publicKey` y `signAndSendTransaction`.

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: phantomWallet
  })
});

const result = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Say hi in 3 words' }],
  max_tokens: 10
});
```

Actualmente, la ruta de Solana solo admite `exact`, no admite `upto`. Si la API devuelve varios `accepts`, el handler seleccionará el elemento con `network = 'solana'`.

La ruta de Solana se ha verificado en la misma API pública, donde el reintento de pago puede devolver HTTP 200 y `ADC_SOLANA_E2E_OK`. Las consultas RPC públicas pueden estar limitadas por tasa, por lo que este artículo no escribe el hash de tx de Solana; cuando se necesite conciliación en cadena, utiliza tu propio RPC de Solana o confirma mediante los registros de la consola.

## Elegir `exact` o `upto`

El handler actual de TypeScript elegirá el primer payment requirement de la red coincidente devuelto por el servidor. La API de Ace Data Cloud normalmente coloca el `exact` de la misma red antes de `upto`, por lo que si explícitamente deseas usar medición posterior, debes pasar `preferScheme: 'upto'`.

Ejemplo:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address,
    preferScheme: 'upto'
  })
});
```

Si el servidor no devuelve un requirement `upto` para esa red, el handler volverá automáticamente al primer requirement disponible de esa red, normalmente `exact`.

`upto` requiere una autorización única de Permit2. Actualmente, `upto` solo se proporciona en Base, por lo que solo se necesita realizar una autorización para Base USDC:

```bash
npx tsx scripts/approve-permit2.ts --network base
```

Base `upto` ha completado la verificación de API pública: HTTP 402 -> HTTP 200, la tx de settlement posterior es `0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036`. La salida completa se encuentra en la explicación del esquema de facturación.

## Qué hace el SDK

El transport de `@acedatacloud/sdk` ejecutará una vez el payment handler al recibir 402:

```ts
type PaymentHandler = (ctx: {
  url: string;
  method: string;
  body?: unknown;
  accepts: PaymentRequirement[];
}) => Promise<{ headers: Record<string, string> }>;
```

El handler devuelto por `@acedatacloud/x402-client` hará lo siguiente:

1. Selecciona el payment requirement de la red objetivo de `ctx.accepts`.
2. Construye una firma EVM EIP-712 o una transacción de transferencia Solana según la red.
3. Serializa el envelope como Base64.
4. Devuelve `{ headers: { 'PAYMENT-SIGNATURE': '<base64>' } }`.
5. El SDK reintenta automáticamente con el cuerpo de solicitud original.

Esto significa que el código de negocio solo necesita escribirse como una llamada SDK normal, sin necesidad de manejar manualmente los reintentos 402.
