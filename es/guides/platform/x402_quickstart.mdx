Este tutorial utiliza una solicitud mínima de API para explicar el flujo completo de Ace Data Cloud X402. El objetivo no es escribir primero código complejo, sino entender primero: por qué la primera solicitud devuelve 402, qué contiene `accepts` y cómo `PAYMENT-SIGNATURE` convierte la misma solicitud de API en una solicitud pagada.

## Preparativos

Necesitas preparar:

| Elemento   | Descripción                                                   |
| ---- | ---------------------------------------------------- |
| Billetera   | Una billetera compatible con la red objetivo. Base utiliza una billetera EVM y Solana utiliza una billetera Solana.      |
| USDC | Debe haber suficiente USDC en la billetera. El importe real está sujeto a `maxAmountRequired` en la respuesta 402. |
| Entorno de desarrollo | Para TypeScript se recomienda Node.js 18+; para Python se recomienda Python 3.10+.    |
| SDK  | Se recomienda utilizar el SDK oficial; no se recomienda escribir manualmente los detalles de la firma.                                |

No se necesita un API Token al llamar a Ace Data Cloud API mediante X402. La primera solicitud del SDK no incluye `Authorization`, Gateway devolverá `402 Payment Required` y los requisitos de pago; el SDK vuelve a intentarlo automáticamente después de firmar.

## Instalar el SDK

Código fuente y direcciones de los paquetes:

- Repositorio del SDK: [https://github.com/AceDataCloud/SDK](https://github.com/AceDataCloud/SDK)
- Repositorio de X402 Client: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)
- npm: `@acedatacloud/sdk`, `@acedatacloud/x402-client`
- PyPI: `acedatacloud`, `acedatacloud-x402`

TypeScript:

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client ethers
```

Python:

```bash
pip install acedatacloud acedatacloud-x402
```

Si deseas utilizar Solana, también necesitas instalar las dependencias correspondientes:

```bash
npm install @solana/web3.js
```

La dependencia de signer de Solana para la versión de Python ya está incluida en `acedatacloud-x402`.

La salida de la comprobación de instalación e importación en un entorno temporal limpio:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
ethers@6.16.0
@solana/web3.js@1.98.4

acedatacloud 2026.4.26.1
acedatacloud-x402 2026.5.31.3
imports_ok True True True True True True
usage: acedatacloud-x402 [-h] {approve-permit2} ...
```

Resultados:

- Tanto los paquetes npm como los paquetes PyPI son paquetes publicados reales, no nombres de marcador de posición en la documentación.
- `acedatacloud-x402[cli]` instala la CLI, y el subcomando `approve-permit2` puede utilizarse para la autorización Permit2 en escenarios `upto`.

## La primera solicitud devolverá 402

Primero puedes usar `curl` para ver qué devuelve una solicitud sin pagar. El siguiente ejemplo no generará ningún cargo, porque no incluye `PAYMENT-SIGNATURE`:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

El cuerpo de la respuesta incluirá un array `accepts`, cuya estructura habitual es la siguiente:

```json
{
  "x402Version": 2,
  "resource": {
    "url": "/openai/chat/completions",
    "description": "AceDataCloud API call",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "maxAmountRequired": "95215",
      "amount": "95215",
      "maxTimeoutSeconds": 3600,
      "resource": "/openai/chat/completions",
      "description": "...",
      "payTo": "0x...",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913"
      }
    }
  ],
  "error": "PAYMENT-SIGNATURE header is required"
}
```

El mismo contenido del desafío también se coloca en formato base64 en el encabezado de respuesta `PAYMENT-REQUIRED`, lo que permite al cliente leer los requisitos de pago sin analizar el body.

El resumen de salida del programa para solicitudes no pagadas de la API de producción es el siguiente:

```text
status=402
x402Version 2
accepts [
  ('eip155:8453', 'exact', '95215'),
  ('eip155:8453', 'upto', '95215'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '95215'),
]
```

Resultados:

- La primera solicitud no incluye `Authorization` ni `PAYMENT-SIGNATURE`, por lo que devuelve HTTP 402 y no genera ningún cargo.
- `accepts` es la única base de firma fiable para esta solicitud, e incluye las redes opcionales, el scheme, el límite de importe, la dirección de cobro y la dirección del activo.
- `network` es un identificador CAIP-2, y el cliente debe coincidir con la cadena CAIP-2 al seleccionar la red.
- El importe máximo para esta solicitud mínima de chat de `gpt-4o-mini` es `95215` atomic USDC, es decir, `0.095215` USDC.
- Cada solicitud debe leer la respuesta 402 de esa ocasión; no codifiques de forma rígida el importe de ejemplo en el código de negocio.

Significado de los campos:

| Campo                  | Descripción                                                             |
| ------------------- | -------------------------------------------------------------- |
| `scheme`            | Esquema de pago. `exact` indica un importe fijo, y `upto` indica un límite de autorización y liquidación según el uso real.                     |
| `network`           | Identificador CAIP-2 de la red de pago, por ejemplo, `eip155:8453`, `solana:5eykt4...`.           |
| `maxAmountRequired` | Importe máximo de pago, en USDC atomic units; `95215` representa `0.095215` USDC.       |
| `amount`            | El importe que se liquidará esta vez; `exact` es igual a `maxAmountRequired`, y `upto` se reescribe según el uso real durante la fase de liquidación. |
| `payTo`             | Dirección de cobro.                                                          |
| `asset`             | Dirección del contrato USDC o dirección mint de Solana.                                     |
| `extra`             | Información ampliada necesaria para la firma, como el ID de cadena, el domain EIP-712 y la dirección Permit2.                      |

## Completar el reintento de pago con el SDK

A continuación se muestra un ejemplo mínimo de TypeScript. Especifica `network: 'base'`; el handler seleccionará el payment requirement de Base de la respuesta 402 de esta solicitud; el importe real y la dirección de cobro siguen estando sujetos a `accepts`:
```ts
import { Wallet } from 'ethers';
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') {
      throw new Error(`unsupported method: ${method}`);
    }
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const response = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly: hello' }],
  max_tokens: 8
});

console.log(response.choices[0].message.content);
```

Detrás de este código ocurren cuatro pasos:

1. El SDK envía una solicitud de API normal, sin `Authorization`.
2. El Gateway devuelve `402 Payment Required` y `accepts`.
3. `createX402PaymentHandler` selecciona el requisito de pago de `network = 'base'` y firma `PAYMENT-SIGNATURE`.
4. El SDK vuelve a intentar con el mismo cuerpo de solicitud, y el Gateway llama al Facilitator para verificar y liquidar antes de permitir el acceso a la API de destino.

## Consultar las capacidades compatibles del Facilitator

La API X402 no depende de un directorio de recursos. El cliente llama directamente a la API conocida y utiliza el
`402 Payment Required` y `accepts` devueltos en tiempo real por esa solicitud como la única base para el precio y la firma.

La declaración de capacidades del Facilitator se encuentra en:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Solo describe `/supported`, `/verify`, `/settle` y las redes de pago actualmente habilitadas, sin enumerar los recursos de la API.

La dirección del Facilitator de producción de Ace Data Cloud es:

```text
https://facilitator.acedata.cloud
```

Puedes consultar qué redes y schemes admite:

```bash
curl https://facilitator.acedata.cloud/supported
```

El `kinds` devuelto enumerará las redes y schemes admitidos por el Facilitator. En las llamadas reales, se seguirá tomando como referencia el `accepts` devuelto por la API.

Salida de Facilitator `/supported`:

```text
kinds [
  ('eip155:8453', 'exact'),
  ('eip155:8453', 'upto', {'facilitatorAddress': '0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708'}),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact')
]
```

Los resultados indican:

- `/supported` indica que el Facilitator tiene capacidades de verificación y liquidación para estas redes y schemes.
- Tanto Base como Solana admiten `exact`; `upto` actualmente solo se proporciona en Base.
- Si una API específica permite una red determinada sigue dependiendo del `accepts` de 402 de esa API.
