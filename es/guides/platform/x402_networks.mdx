Ace Data Cloud X402 actualmente se liquida en torno a USDC y admite dos tipos de cadenas: EVM y Solana. Los métodos de firma, direcciones de activos, comportamiento del gas y escenarios aplicables difieren entre redes, por lo que es necesario elegir la red antes de la integración.

## El identificador de red utiliza CAIP-2

El `accepts[].network` de x402 v2 es un identificador CAIP-2, no una abreviatura como `base` o `solana`. El cliente debe comparar según la cadena CAIP-2 al hacer coincidir redes:

| Red             | Identificador CAIP-2                       |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Matriz de soporte

| Red     | scheme  | Activo              | Método de firma                       | Escenario aplicable                     |
| ------ | ------- | ------------------- | ------------------------------------ | ------------------------ |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Recomendado por defecto, soporte maduro de wallets y liquidez.         |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | API de medición posterior para chat, modelos, etc.          |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Escenarios de wallets de Solana, Agents o aplicaciones on-chain. |

`upto` actualmente solo se proporciona en Base. Los elementos realmente disponibles se rigen por los `accepts` devueltos por la API. También puedes consultar el Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

La respuesta de Facilitator `/supported`:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Explicación de los resultados:

- Los `exact` de Base y Solana son rutas de pago de importe fijo.
- Solo Base proporciona la ruta de medición posterior `upto`, que depende de la aprobación de Permit2.
- El `extra.facilitatorAddress` en la entrada `upto` es la dirección que el cliente debe escribir en el witness al firmar, y debe coincidir con el valor devuelto por el servidor.

## Base

Base utiliza el contrato oficial de USDC:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

En el esquema `exact`, el cliente firma EIP-712 `TransferWithAuthorization`. El contenido de la firma incluye:

- `from`: dirección de la wallet pagadora
- `to`: dirección receptora de Ace Data Cloud
- `value`: importe de este pago
- `validAfter` / `validBefore`: ventana de tiempo de validez de la firma
- `nonce`: nonce aleatorio de 32 bytes

Después de verificar la firma, el Facilitator llamará a `transferWithAuthorization` de USDC on-chain para completar la transferencia.

Base es la red más recomendada para la integración formal, especialmente adecuada para la medición posterior `upto`, porque los ecosistemas de Permit2, USDC y wallets son más maduros.

Ejemplo de resultado de verificación de Base `exact`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Explicación de los resultados:

- El reintento pagado de la API devuelve el contenido del modelo `ADC_BASE_E2E_OK`.
- La transacción on-chain ya se puede consultar en BaseScan, y el número de bloque es `46726299`.
- `95215` atomic USDC corresponde a `0.095215` USDC, que es el importe real liquidado para esta llamada de API.

Resultado de ejecución del programa de pago de pedidos con Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Explicación de los resultados:

- El estado final del pedido en la plataforma es `Finished`.
- El `pay_id` del pedido escribe el mismo hash de transacción de Base.
- `1200000` atomic USDC corresponde a `1.2` USDC, que es el importe histórico realmente pagado por este pedido de 10 Credits bajo la política anterior; los pedidos nuevos ya no disfrutan de un descuento adicional por el método de pago X402, y el importe específico de la firma se rige por la respuesta 402 de esta vez.

## Solana

Solana utiliza SPL USDC `TransferChecked`. El cliente construye una transacción de transferencia, la firma y la envía, y luego coloca la firma de la transacción o la transacción serializada en el envelope `PAYMENT-SIGNATURE`.

Características de Solana:

- Utiliza Solana wallet adapter o una clave secreta base58;
- El activo es Solana USDC mint;
- Actualmente solo admite `exact`;
- El Facilitator verificará el mint, destination, authority y amount de la instrucción de transferencia.

Si se utiliza el modo de wallet fee payer, la wallet enviará directamente la transacción, y el Facilitator será responsable de confirmar la transacción y devolver el resultado de settlement.

Ejemplo de resultado de verificación de Solana `exact`:

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Explicación de los resultados:

- El reintento pagado ya devolvió HTTP 200, y el modelo generó `ADC_SOLANA_E2E_OK`.
- Al consultar la signature on-chain mediante RPC público, es posible encontrar limitación de tasa.
- Debido a que las consultas mediante RPC público pueden tener limitación de tasa, aquí no se escribe el explorer de Solana. Cuando se requiera una conciliación estricta, utiliza tu propio RPC de Solana o los registros de settlement de la plataforma para confirmar la firma de la transacción.

## Cómo elegir

| Qué quieres hacer        | Red recomendada           |
| ------------ | -------------- |
| Ejecutar rápidamente el flujo mínimo     | Base `exact`   |
| Orientado a usuarios Web3 comunes | Base           |
| Realizar medición posterior para completado de chat, etc.   | Base `upto`    |
| Aplicaciones del ecosistema Solana  | Solana `exact` |

Independientemente de la cadena que elijas, no codifiques los precios de forma fija en el cliente. El precio lo determina `accepts[].maxAmountRequired` devuelto por el servidor.

## Añadir redes EVM
El soporte de código para pagos de importe fijo en USDC nativo en las siguientes redes se ha proporcionado, y se habilita red por red.
La disponibilidad se determina por los `accepts` devueltos por el pedido o la API; no representa que todas las redes estén habilitadas en producción.

| Red          | Alias      | CAIP-2         | USDC nativo                                 |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

Estas redes solo admiten `exact`, y la precisión de la moneda es 6. No utilices USDC puenteado con el mismo nombre.
Al utilizar el X402 Client oficial de TypeScript/Python, puedes pasar la abreviatura de la tabla o el identificador CAIP-2.
El cliente utiliza el ID de la cadena de destino para construir la firma; la billetera debe admitir la red de destino.

La tabla oficial de soporte de la billetera de extensión Phantom incluye Arbitrum y Polygon; Optimism y Avalanche
actualmente no están incluidos en esta tabla, se puede utilizar Rabby o MetaMask que admita la cadena de destino. Las direcciones EVM pueden ser iguales en diferentes cadenas,
pero los saldos son independientes entre sí, y las direcciones de Solana no son aplicables a USDC de EVM.
Consulta la [tabla de soporte de la billetera Phantom](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### Entrada de despliegue gradual de nuevas redes

La entrada para nuevas cadenas está oculta de forma predeterminada. Al acceder a la consola o Studio, puedes utilizar `?features=x402-arbitrum`
para habilitar la cadena correspondiente, y separar varios flags con comas. Para deshabilitar una sola cadena, utiliza `?features=-x402-arbitrum`,
y para eliminar las anulaciones locales, utiliza `?features=none`. Los interruptores se guardan por separado para cada dominio.
La cotización del pedido y los reintentos de pago utilizan el mismo interruptor, el servidor realizará una validación independiente; los registros de pago existentes aún pueden consultarse.
Habilitar únicamente el flag de la página no habilitará cadenas que aún no estén configuradas; las redes específicas que pueden pagarse siguen determinándose por los `accepts` en tiempo real.
