Ace Data Cloud X402 actualmente se centra en la liquidación en USDC y admite dos tipos de cadenas: EVM y Solana. Los métodos de firma, las direcciones de activos, el comportamiento del gas y los escenarios aplicables difieren según la red, por lo que es necesario elegir la red antes de la integración.

## Los identificadores de red usan CAIP-2

El `accepts[].network` de x402 v2 es un identificador CAIP-2, no abreviaturas como `base` o `skale`. Al coincidir redes, el cliente debe comparar mediante cadenas CAIP-2:

| Red             | Identificador CAIP-2                       |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| SKALE Base     | `eip155:1187947933`                       |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Matriz de soporte

| Red      | scheme  | Activo                | Método de firma                       | Escenario aplicable                              |
| ------ | ------- | ------------------- | ------------------------------------ | ------------------------------------------- |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Recomendado por defecto, soporte maduro de wallets y liquidez. |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | API de medición posterior para chat, modelos, etc. |
| SKALE  | `exact` | SKALE bridged USDC  | EIP-3009 `TransferWithAuthorization` | Bajo coste de gas, adecuado para verificación de pagos EVM y llamadas de bajo coste. |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Escenarios de wallets Solana, Agent o aplicaciones on-chain. |

`upto` actualmente solo se proporciona en Base. Los elementos realmente disponibles están sujetos a los `accepts` devueltos por la API. También puedes consultar el Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

La respuesta de Facilitator `/supported`:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    { "x402Version": 2, "scheme": "exact", "network": "eip155:1187947933" },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Explicación de los resultados:

- Los `exact` de Base, SKALE y Solana son rutas de pago de importe fijo.
- Solo Base proporciona la ruta de medición posterior `upto`, que depende de la aprobación de Permit2.
- El `extra.facilitatorAddress` de la entrada `upto` es la dirección que debe escribirse en el witness al firmar en el cliente, y debe coincidir con el valor devuelto por el servidor.

## Base

Base utiliza el contrato oficial de USDC:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

En el esquema `exact`, el cliente firma EIP-712 `TransferWithAuthorization`. El contenido de la firma incluye:

- `from`: dirección de la wallet pagadora
- `to`: dirección receptora de Ace Data Cloud
- `value`: importe de este pago
- `validAfter` / `validBefore`: ventana de validez de la firma
- `nonce`: nonce aleatorio de 32 bytes

Después de verificar la firma, el Facilitator llamará a `transferWithAuthorization` de USDC on-chain para completar la transferencia.

Base es la red de integración formal más recomendada, especialmente adecuada para la medición posterior `upto`, ya que el ecosistema de Permit2, USDC y wallets es más maduro.

Ejemplo de resultado de verificación de Base `exact`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Explicación de los resultados:

- El reintento pagado de la API devuelve el contenido del modelo `ADC_BASE_E2E_OK`.
- La transacción on-chain ya puede consultarse en BaseScan, y el número de bloque es `46726299`.
- `95215` atomic USDC corresponde a `0.095215` USDC, que es el importe de liquidación real de esta llamada a la API.

Resultado de ejecución del programa de pago de pedidos Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Explicación de los resultados:

- El estado final del pedido de la plataforma es `Finished`.
- El `pay_id` del pedido se escribe en el mismo hash de transacción de Base.
- `1200000` atomic USDC corresponde a `1.2` USDC, que es el importe histórico realmente pagado por este pedido de 10 Credits bajo la política anterior; los nuevos pedidos ya no disfrutan adicionalmente del descuento por el método de pago X402, y el importe específico de la firma está sujeto a la respuesta 402 de esta ocasión.

## SKALE

SKALE utiliza USDC bridged, y el método de firma es similar al de Base, también EIP-3009. Es adecuado para escenarios de pago EVM de bajo coste de gas; las llamadas reales siguen estando sujetas a los `accepts` devueltos por la API.

Los `accepts` 402 típicos de SKALE incluirán:

```json
{
  "network": "eip155:1187947933",
  "scheme": "exact",
  "extra": {
    "name": "Bridged USDC (SKALE Bridge)",
    "version": "2",
    "chainId": 1187947933,
    "verifyingContract": "0x85889c8c714505E0c94b30fcfcF64fE3Ac8FCb20"
  }
}
```

SKALE actualmente solo proporciona `exact`. Si necesitas medición posterior, utiliza Base `upto`.

Ejemplo de resultado de verificación de SKALE `exact`:

```text
content ADC_SKALE_E2E_OK
tx 0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
block 1969317
explorer https://skale-base-explorer.skalenodes.com/tx/0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
paid 0.095215 USDC
```

Explicación de los resultados：
- API paid retry returns model content `ADC_SKALE_E2E_OK`.
- The transaction is searchable in the SKALE explorer, and the block number is `1969317`.
- The settlement amount for this `exact` payment is `0.095215` USDC.

## Solana

Solana uses SPL USDC `TransferChecked`. The client constructs a transfer transaction, signs and submits it, then places the transaction signature or serialized transaction into the `PAYMENT-SIGNATURE` envelope.

Solana characteristics:

- Uses a Solana wallet adapter or base58 secret key;
- The asset is the Solana USDC mint;
- Currently only supports `exact`;
- The Facilitator verifies the mint, destination, authority, and amount of the transfer instruction.

If using wallet fee payer mode, the wallet directly submits the transaction, and the Facilitator is responsible for confirming the transaction and returning the settlement result.

Example of Solana `exact` verification result:

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Result description:

- The paid retry has returned HTTP 200, and the model output is `ADC_SOLANA_E2E_OK`.
- Rate limiting may be encountered when querying the on-chain signature through a public RPC.
- Because public RPC queries may be rate-limited, the Solana explorer is not included here. When strict reconciliation is required, please use your own Solana RPC or platform-side settlement records to confirm the transaction signature.

## How to choose

| What you want to do | Recommended network |
| ------------ | ---------------------------- |
| Quickly run through the minimum flow | SKALE `exact` or Base `exact` |
| Target ordinary Web3 users | Base |
| Perform postpaid metering for chat completions and similar use cases | Base `upto` |
| Solana ecosystem applications | Solana `exact` |
| Low-cost EVM payment verification | SKALE `exact` |

Regardless of which chain you choose, do not hardcode prices in the client. Prices are determined by `accepts[].maxAmountRequired` returned by the server.

## Added EVM networks

Code support has been provided for fixed-amount native USDC payments on the following networks, which will be enabled one by one by network.
Availability is determined by the order or the API-returned `accepts`; this does not mean that all networks have been enabled in production.

| Network      | Alias      | CAIP-2         | Native USDC                                  |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

These networks only support `exact`, and the token precision is 6. Do not use bridged USDC with the same name.
When using the official TypeScript/Python X402 Client, you can pass the alias or CAIP-2 identifier from the table.
The client constructs the signature using the target chain ID; the wallet must support the target network.

The official support table for the Phantom extension wallet lists Arbitrum and Polygon; Optimism and Avalanche
are currently not listed in that table, and you can use Rabby or MetaMask that supports the target chain. EVM addresses can be the same across different chains,
but balances are independent from each other, and Solana addresses do not apply to EVM USDC.
See the [Phantom wallet support table](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### New network gradual rollout entry

New chain entries are hidden by default. When accessing the console or Studio, you can use `?features=x402-arbitrum`
to enable the corresponding chain, with multiple flags separated by commas. To disable a single chain, use `?features=-x402-arbitrum`,
and to clear local overrides, use `?features=none`. Switches are stored separately for each domain.
Order quotes and payment retries use the same switch, while the server performs independent validation; existing payment records can still be viewed.
Enabling only the page flag will not enable chains that have not yet been configured; the specific payable networks are still determined by real-time `accepts`.
