Este documento explica cómo se determinan los precios al llamar a la API de Ace Data Cloud con X402, y cuál es su relación con los precios normales de **Credits** (créditos) de la plataforma.

## Conclusión principal

X402 no es un sistema de precios independiente. Cada llamada a la API ya tiene un coste en **Credits**, que es la única fuente de precios compartida por todos los métodos de facturación (deducción de créditos con API Token, saldo de cuenta, pago on-chain con X402). X402 simplemente convierte este coste en Credits a USDC on-chain según un tipo de cambio fijo:

> **1 Credit = 0.095215 USDC** (es decir, `95215` atomic USDC, con USDC de 6 decimales)

Es decir:

```text
Precio X402 (USDC) = coste en Credits de esta llamada × 0.095215
```

Este tipo de cambio no se establece de la nada; equivale al precio unitario de Credits del **nivel óptimo (gran volumen)** de la plataforma. Por lo tanto, pagar con X402 ≈ comprar Credits al precio unitario del nivel óptimo y luego consumirlos, **sin recargo de X402**; por el contrario, se disfruta directamente del precio unitario de Credits más barato, sin necesidad de recargar previamente ni de usar API Token.

## Base de precios

| Concepto        | Valor                          | Descripción                                                    |
| --------- | ------------------------------ | ----------------------------------------------------- |
| Tipo de conversión      | `1 Credit = 0.095215 USDC`     | Tipo de cambio fijo establecido uniformemente por la plataforma                                           |
| Unidad atomic | `1 Credit = 95215 atomic USDC` | USDC tiene 6 decimales, `atomic = floor(credits × 0.095215 × 1e6)` |
| Cobro mínimo      | `1 atomic USDC`（$0.000001）     | Incluso si el coste es extremadamente bajo, se liquida al menos 1 atomic                                 |
| Moneda de precios      | USDC                           | Base usa ERC-20 USDC, Solana usa SPL USDC                  |

La conversión la realiza uniformemente la plataforma, y el importe es el mismo para todas las redes compatibles (Base, Solana); las diferentes redes solo difieren en el contrato de activos y el método de firma, el precio es el mismo.

### Relación con el precio unitario normal de Credits

Los Credits de la plataforma se venden por niveles de «cuanto mayor sea el volumen, menor será el precio unitario». Al facturar por llamada con X402, se utiliza uniformemente el precio unitario del nivel óptimo:

| Método de compra/pago        | Precio unitario aproximado de Credits            | Descripción                   |
| -------------- | ------------------------ | -------------------- |
| Recarga inicial / pequeña      | aprox. `$0.13 / Credit`       | Precio de lista, precio unitario al comprar Credits en pequeñas cantidades |
| Gran volumen / nivel óptimo       | `$0.095215 / Credit`     | El precio unitario más barato               |
| **Pago por llamada con X402** | **`$0.095215 / Credit`** | **Siempre equivale al precio unitario del nivel óptimo**        |

En otras palabras, X402 liquida cada llamada según el precio unitario de Credits del nivel óptimo. Para los usuarios que compran Credits mediante recargas pequeñas, el precio unitario será mayor que X402; solo el precio unitario de los usuarios con recargas grandes coincide con X402.

## Dos formas de precio: `exact` y `upto`

En la respuesta 402 de X402, `maxAmountRequired` es el importe que debes firmar. Tiene dos formas:

- **`exact` (precio fijo)**: el precio puede determinarse antes de procesar la solicitud (imágenes, vídeos, música, búsquedas, pago de pedidos). `maxAmountRequired = coste en Credits de esta llamada × 0.095215`, es decir, el importe pagadero de esta llamada (coincide con `cost.amount` en la respuesta exitosa).
- **`upto` (medición de uso posterior)**: interfaces como chat completions, para las que «solo se sabe cuántos tokens se usaron al terminar la respuesta». `maxAmountRequired` es un **límite superior** (convertido según el límite de créditos establecido para ese modelo: Credits máximos × 0.095215); la liquidación real se realiza según el uso real y no supera el límite superior.

Para los detalles del protocolo sobre estos dos esquemas, consulta [esquemas de facturación `exact` y `upto`](https://platform.acedata.cloud/documents/x402-metered-upto). A continuación solo se explican los precios.

## Precios de Chat (chat completions)

Chat completions utiliza medición `upto`: se factura según el uso real de tokens de prompt / completion. El precio por cada millón (1M) de tokens = `coste en Credits de ese modelo por 1M tokens × 0.095215`, que coincide completamente con el precio unitario en USD mostrado en el catálogo público de modelos de la plataforma (`/api/v1/models?with_pricing=true`).

La siguiente tabla muestra los precios reales (tomados del catálogo de modelos y calculados según el tipo de cambio de X402), en USD / 1M tokens:

| ----------------- | ------- | -------- | --------------------- |
| gpt-4o-mini       | $0.0796 | $0.3183  | 1 Credit（$0.095215）   |
| gemini-2.5-flash  | $0.1591 | $1.3262  | 5 Credits（$0.476074）  |
| gpt-5 / gpt-5.1   | $0.6631 | $5.3050  | 20 Credits（$1.904299） |
| gemini-2.5-pro    | $0.6631 | $5.3050  | 50 Credits（$4.760750） |
| gpt-4.1           | $1.0610 | $4.2440  | 20 Credits（$1.904299） |
| claude-sonnet-4-5 | $0.6006 | $3.0028  | 50 Credits（$4.760750） |
| grok-4            | $1.5915 | $7.9574  | 10 Credits（$0.952149） |
| claude-opus-4-1   | $3.0028 | $15.0140 | 50 Credits（$4.760750） |

Notas:

- La tabla muestra los precios unitarios medidos por token; el coste de una solicitud = tokens de entrada × precio unitario de entrada + tokens de salida × precio unitario de salida.
- El límite `upto` es el importe máximo permitido para firmar en una solicitud de ese modelo; no es el cargo real, y la gran mayoría de las solicitudes está muy por debajo del límite superior.
- El límite superior solo determina «cuánto se podría cobrar como máximo»; la liquidación real se calcula según el uso de tokens.

### Ejemplo: la cotización y el cobro son consistentes (`exact`)

A continuación se muestra una **llamada de pago real** iniciada a `serp/google` con el X402Client oficial (Base `exact`). Demuestra la consistencia entre los tres: la cotización 402, el importe firmado y el `cost` devuelto en la respuesta exitosa.

```text
# 1) Solicitud no pagada -> 402, obtener cotización (sin cobro)
POST /serp/google  ->  402
base/exact maxAmountRequired = 952 atomic = $0.000952 = 0.01 Credit
# 0.01 × 0.095215 = 0.00095215, redondeado hacia abajo a atomic = 952

# 2) Firmar PAYMENT-SIGNATURE de 952 atomic con la billetera y reintentar
POST /serp/google (PAYMENT-SIGNATURE) -> 200
body.cost = {"amount": 0.000952, "currency": "usdc", "settlement": "authorized"}
```
El `cost.amount` devuelto (0.000952 USDC) coincide completamente con la cotización 402 y con `Credits × 0.095215`. El campo `settlement` es el estado de liquidación de este pago (`authorized` = autorizado); la liquidación en cadena es gestionada por la plataforma, y el mecanismo se describe en los [planes de facturación `exact` y `upto`](https://platform.acedata.cloud/documents/x402-metered-upto).

### Cálculo de cotización `upto` (chat)

El chat se mide por tokens. La cotización de una solicitud (no el límite superior) se calcula de la siguiente manera (tomando gpt-4o-mini como ejemplo):

```text
Credits = 1e-6 × (0.835733 × prompt_tokens + 3.342933 × completion_tokens)
USDC    = Credits × 0.095215
```

Una solicitud de 500 tokens de prompt + 200 tokens de completion:

```text
Credits = 1e-6 × (0.835733 × 500 + 3.342933 × 200) ≈ 0.001086 Credits
报价 USDC ≈ 0.001086 × 0.095215 ≈ $0.0001034
```

El cliente firma según el límite superior `upto` (para gpt-4o-mini, 1 Credit = `95215` atomic), esto es solo **cuánto podría descontarse como máximo**; la cotización real de esta solicitud (en el ejemplo anterior, aproximadamente $0.0001) está muy por debajo del límite superior, y se liquida según el uso de tokens. El mecanismo de liquidación en cadena de `upto` se describe en los [planes de facturación `exact` y `upto`](https://platform.acedata.cloud/documents/x402-metered-upto).

- Para este tipo de interfaces de precio fijo (`exact`), el `maxAmountRequired` en la respuesta 402 de la solicitud es el importe pagadero de esa vez (coincide con el `cost.amount` de la respuesta exitosa, como se verificó en la sección anterior).

## Precio de pago de pedidos

Al pagar pedidos de consola con X402 (compra de paquetes / recarga de Credits), el precio mostrado en la página del pedido prevalece, y el `amount` de 402 es la base final para la firma. El pago de pedidos utiliza la API de la plataforma y requiere un token de cuenta; consulte el [tutorial de pago de pedidos](https://platform.acedata.cloud/documents/x402-order-payment) para más detalles.

Un ejemplo real en el tutorial de pago de pedidos (compra de 10 Credits):

```text
description Ace Data Cloud Credits x 10.0
created price 1.26          # 订单创建价（USD）
settled    1.20 USDC        # 最终签名/结算金额（= 402 amount）
            = 1200000 atomic USDC
```

Nota: **pago por llamada** (Chat / otros servicios anteriores) y **pago de pedidos** son dos rutas diferentes. El pago por llamada utiliza de forma uniforme el precio de nivel óptimo de `0.095215`/Credit; el pago de pedidos se basa en el precio del paquete, y la diferencia entre su precio de creación y el importe final de liquidación se rige por el [tutorial de pago de pedidos](https://platform.acedata.cloud/documents/x402-order-payment).

## Cómo obtener precios en tiempo real

Los precios varían según el modelo y los parámetros; obténgalos en tiempo real mediante programa y no los codifique de forma fija:

- **Precio por llamada**: envíe una solicitud a la API objetivo **sin** `PAYMENT-SIGNATURE` (ni `Authorization`), y lea el 402 `accepts[].maxAmountRequired` devuelto. Este paso no genera cargos. Para interfaces `exact`, es el precio final; para interfaces `upto` (chat), es el límite superior, y el importe real se liquida según el uso.
- **Precio por token de chat**: `GET https://platform.acedata.cloud/api/v1/models?with_pricing=true&type=chat`, lea `pricing.input_usd` / `pricing.output_usd` de cada modelo (ya calculados según `credit_usd_rate`).
- **Verificación de conversión**: `atomic = floor(Credits × 0.095215 × 1e6)`, `USDC = atomic / 1e6` (es decir, `USDC ≈ Credits × 0.095215`).

Ejemplo de solicitud mínima para obtener el precio:

```bash
curl -sS -X POST https://x402.acedata.cloud/midjourney/imagine \
  -H 'Content-Type: application/json' \
  -d '{"prompt": "a cat"}'
# 返回 402，accepts[].maxAmountRequired 即为该次（exact）调用价格
```

## Resumen
- Precio de X402 = el coste en Credits de esta llamada × `0.095215`, es **el mismo precio** que la facturación normal de Credits, solo que se liquida con USDC en cadena.
- `0.095215`/Credit es el precio unitario de Credits del **mejor nivel** (gran volumen) de la plataforma; las recargas de menor importe tienen un precio unitario de Credits más alto, por lo que X402 equivale a obtener automáticamente el mejor precio unitario.
- Las interfaces `exact` (imagen / vídeo / música / búsqueda / pedido) firman un importe que es el importe pagadero de esta vez; las interfaces `upto` (chat) firman un límite superior y se liquidan según el uso real.
- El precio autorizado se basa en el `maxAmountRequired` devuelto por 402: para `exact`, es el importe pagadero (coincide con el `cost.amount` de la respuesta exitosa, ya verificado); para `upto`, es el límite superior, y el `cost.amount` de la respuesta exitosa es el importe real liquidado según el uso (≤ límite superior).
