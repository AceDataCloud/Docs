[X402](https://www.x402.org/) es un protocolo de pago on-chain de “facturación por HTTP 402” propuesto por Coinbase: el servidor devuelve `402 Payment Required` en solicitudes sin token, adjuntando un campo `accepts: [...]` que enumera las cadenas / activos / precios aceptables; el cliente firma localmente una autorización (Permit2 / EIP-712 en EVM, autorización de transferencia de token SPL en Solana), coloca el envelope codificado en base64 en el encabezado `PAYMENT-SIGNATURE` y reenvía la solicitud. Tras la validación, el servidor realiza realmente la liquidación on-chain y luego devuelve el resultado de negocio.

> El cliente X402 de Ace Data Cloud llama directamente a la API de destino, y utiliza el `402 Payment Required` y `accepts` devueltos en tiempo real por esa solicitud como base para el precio y la firma. La capacidad de pago del Facilitator puede verificarse en [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

Tanto `@acedatacloud/sdk` como `acedatacloud` exponen un gancho `paymentHandler`: cuando una solicitud enviada por el propio SDK recibe un `402`, llama al handler que inyectaste para obtener el encabezado `PAYMENT-SIGNATURE`, y después reenvía la solicitud original. Al usar `@acedatacloud/x402-client` / `acedatacloud-x402` junto con el SDK, **todo el proceso es completamente transparente para el código de negocio**——solo usas `client.openai.chat.completions.create(...)`, y parece idéntico al modo token, pero por debajo se paga por llamada y no se necesita recargar por adelantado.

Este artículo:

- Recorre realmente la cadena de «sin token + inyección de handler X402» del lado de TS ([verificación T12](#cuatro-verificación-de-ejecución-real))
- Enumera las diferencias entre las dos cadenas de firma EVM / Solana
- Proporciona tres adaptaciones: modo de clave privada `viem`, modo de billetera de navegador y modo Python `EVMAccountSigner`
- Explica claramente el campo `preferScheme` / `prefer_scheme`, con el que es fácil cometer errores

## I. Resumen del protocolo (lectura obligatoria)

Una llamada X402 exitosa involucra **3 RTT HTTP**:

```text
1. SDK -> /openai/v1/chat/completions               (无 Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK 内部 -> paymentHandler({ url, method, body, accepts })   (本地签名，0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (PAYMENT-SIGNATURE 头注入)
   <- 200 + business response   (结算在服务端完成)
```

El envelope X402 es un fragmento JSON, que se codifica en base64 y se coloca en el encabezado `PAYMENT-SIGNATURE`. Estructura (extracto):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

La capa superior del envelope es `x402Version: 2`, y utiliza el objeto `accepted` para declarar el `scheme` y `network` seleccionados en esta ocasión (identificador CAIP-2).

| scheme  | Significado                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Precio fijo (escenarios con precio definido como generación de imágenes / videos, búsquedas, etc.). El importe firmado = el importe requerido por el servidor.                                                         |
| `upto`  | Facturación medida (chat completions / tipo token). Se firma un importe **máximo**, y realmente solo se liquida la parte utilizada (basado en Permit2 + witness). **Muy recomendado** para API de tipo sesión. |

`preferScheme` / `prefer_scheme` se utiliza para elegir la preferencia cuando el servidor **proporciona simultáneamente múltiples scheme**. Si el servidor solo expone `exact`, este campo se ignorará; si se establece `upto` pero el servidor no lo expone, se volverá al primer elemento coincidente.

## II. TypeScript: dos usos, billetera de navegador + viem de servidor

### Instalación

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Versiones probadas:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Firma completa de `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' 必填
  evmProvider?: EVMProvider;                // network='base' 必填，EIP-1193
  evmAddress?: string;                      // network='base' 必填
  preferScheme?: 'exact' | 'upto';
}
```

El valor de retorno es un `(ctx) => Promise&lt;{ headers: Record<string, string> }>`, que coincide exactamente con la firma del gancho `paymentHandler` del SDK.

### Uso 1: navegador (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. 让用户连钱包
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. 切到 Base 主网
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. 构造 SDK 客户端，注入 X402 handler
//    注意：不传 apiToken，让 SDK 走 402 路径
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat 类必选 upto
  })
});

// 4. 正常调
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

En la primera llamada, el navegador mostrará **dos avisos de firma**: el primero es un approve único de Permit2 para USDC (el importe es `MaxUint256`, escrito on-chain); el segundo es la firma EIP-712 del envelope X402 (no se envía on-chain, solo sirve para que el facilitator la verifique). Las llamadas posteriores solo necesitan la segunda firma; en términos de experiencia es “hacer clic una vez para firmar → obtener el resultado”.

### Uso 2: servidor Node + clave privada viem (adecuado para backend / CLI)

`@acedatacloud/x402-client` **solo acepta proveedores EIP-1193** en el lado TS——no gestiona directamente las claves privadas. En escenarios Node / CLI, la práctica estándar es usar [`viem`](https://viem.sh/) para empaquetar la clave privada como `WalletClient`, y luego usar el adaptador EIP-1193 interno de [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) o viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient 自带 EIP-1193 兼容的 .request()，可以直接当 evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request 满足 EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Si consideras que la adaptación EIP-1193 de viem no es lo suficientemente estable, también puedes usar el [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts) de nivel más bajo y conectar por tu cuenta la ruta `accepts → signed envelope → PAYMENT-SIGNATURE header`, omitiendo el hook del SDK; sin embargo, se recomienda seguir priorizando `createX402PaymentHandler`, para evitar tener que mantener las actualizaciones del protocolo por tu cuenta.

### Uso 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

Actualmente, en la cadena Solana **solo se expone el scheme `exact`**, por lo que `preferScheme` no tiene efecto en Solana.

## III. Python: modo de clave privada

El `acedatacloud-x402` de Python sigue la ruta de **firmar directamente con la clave privada** (sin abstracción EIP-1193), y es más adecuado para servidores / ejecutores de tareas.

### Instalación

```bash
pip install acedatacloud acedatacloud-x402
```

Versiones verificadas:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. 从私钥构造签名器
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. 构造 SDK：不传 api_token，让 SDK 走 402 路径
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # chat 类一定选 upto
    )
)

# 3. 正常调
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # 可选
    )
)
```

### Approve único (solo la primera vez en EVM)

En EVM Base, X402 utiliza Permit2, por lo que la wallet debe realizar una vez un approve de `MaxUint256` al contrato Permit2 para USDC. `acedatacloud-x402` incluye `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Esta transacción solo debe enviarse una vez; posteriormente, todos los pagos X402 de EVM utilizarán esta autorización. Solana no lo necesita.

## IV. Verificación de ejecución real

Objetivo de prueba: **el SDK de TS no pasa token, inyecta el handler X402 y puede construir e iniciar solicitudes normalmente** (verificación ligera sin consumir USDC real en cadena).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // 占位 provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Salida:

```text
handler_type function
client_ctor_ok AceDataCloud
```

Los resultados indican:

- No se pasó `apiToken`, y la construcción del SDK **no produce errores**, lo que demuestra que el modo X402 es efectivamente una alternativa válida al token.
- `createX402PaymentHandler` devuelve una función (hook), que el SDK solo invocará al recibir un 402.
- La prueba integral que confirma que el pago real en cadena funciona, dado que implica descuentos reales de USDC, no se ha incluido en este tutorial; puedes consultar el ejemplo e2e en la [guía de integración X402](https://platform.acedata.cloud/documents/x402-integration).

> En Python, `create_x402_payment_handler` también realizó la misma verificación — el valor de retorno de la función es callable, y la construcción de `AceDataCloud(...)` no produce errores al inyectar `payment_handler=...`. La semántica está alineada en ambos lados.

## V. Comparación con el «modo Bearer token»

| Dimensión              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Escenarios aplicables            | Backend propio, proyectos a largo plazo                                                         | Desarrolladores externos, pago por uso bajo demanda, llamadas Agentic                        |
| Registro              | Requiere solicitarlo en la [consola](https://platform.acedata.cloud/console/applications) | No se requiere; basta con tener una wallet en cadena                                     |
| Precisión de facturación            | Recarga previa, cobro según la tabla de tokens                                                   | En cadena en tiempo real por llamada                                         |
| Saldo              | Puede consultarse en la consola                                                           | Consultar el USDC de la wallet en cadena                                      |
| Costo inicial            | El registro por correo incluye crédito gratuito                                                        | Requiere puentear USDC a Base, primer approve de Permit2              |
| Adecuado para tipo chat       | ✅                                                                 | ✅ (debe ser `preferScheme=upto`)                       |
| Adecuado para pagos únicos / pago en nombre de otra cuenta | ❌                                                                 | ✅                                               |
| Cambios de código            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Los dos modos pueden coexistir; basta con configurar diferentes métodos de autenticación para distintas instancias de `client` dentro del mismo proceso.

## VI. Errores comunes

1. **La clase `chat` debe usar `preferScheme=upto`**: usar `exact` hará que el facilitator descuente USDC según `maxAmountRequired` (no según el uso real).
2. **No pases una clave privada sin envolver a `createX402PaymentHandler` en Node**: el paquete TS no acepta `{ privateKey }`, debe envolverse como un provider EIP-1193 (se recomienda `WalletClient` de viem).
3. **La primera llamada requiere doble firma**: primero se firma el approve de Permit2 (en cadena, con gas), y después se firma el envelope X402 (fuera de cadena). Las llamadas posteriores solo requieren la segunda.
4. **Solana no tiene el concepto de Permit2**: se firma directamente la autorización de transferencia de tokens SPL, sin necesidad de approve; pero actualmente en la cadena de Solana solo se admite `exact`.
5. **Distingue entre errores de negocio y errores de pago**: 402 → el fallo del handler lanza `X402SignError` (el tipo específico varía según la cadena); tras el reenvío, los errores de la interfaz de negocio (401 / 422 / 5xx) siguen clasificándose como excepciones normales del SDK.
6. **La forma más estable de adaptar `viem`**: `evmProvider: walletClient as any` pierde la comprobación de tipos, pero ofrece la mejor compatibilidad; si quieres conservar los tipos, envuelve por separado `.transport.request` de viem en un objeto `{ request }` y pásalo.
