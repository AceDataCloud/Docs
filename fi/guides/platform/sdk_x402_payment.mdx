[X402](https://www.x402.org/) on Coinbasen ehdottama ketjupohjainen maksuprotokolla ”HTTP 402 -laskutukselle”: palvelin palauttaa tokenittomalle pyynnölle `402 Payment Required` ja liittää mukaan `accepts: [...]` -kentän, joka luettelee hyväksyttävät ketjut / varat / hinnat; asiakas allekirjoittaa valtuutuksen paikallisesti (EVM:ssä Permit2 / EIP-712, Solanassa SPL token transfer -valtuutus), asettaa base64-koodatun envelopen `PAYMENT-SIGNATURE`-otsikkoon ja lähettää pyynnön uudelleen. Vahvistuksen jälkeen palvelin tekee varsinaisen ketjussa tapahtuvan selvityksen ja palauttaa sitten liiketoimintatuloksen.

> Ace Data Cloudin X402-asiakas kutsuu kohde-APIa suoraan ja käyttää kyseisen pyynnön reaaliaikaisesti palauttamaa `402 Payment Required` -vastausta ja `accepts`-kenttää hinnan ja allekirjoituksen perusteena. Facilitatorin maksukyvykkyydet voidaan tarkistaa osoitteessa [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

Sekä `@acedatacloud/sdk` että `acedatacloud` tarjoavat `paymentHandler`-koukun: kun SDK:n itse lähettämä pyyntö vastaanottaa `402`-vastauksen, se kutsuu injektoimaasi handleria saadakseen `PAYMENT-SIGNATURE`-otsikon ja lähettää alkuperäisen pyynnön uudelleen. Käyttämällä `@acedatacloud/x402-client` / `acedatacloud-x402` yhdessä SDK:n kanssa **koko prosessi on täysin läpinäkyvä liiketoimintakoodille**——käytät vain `client.openai.chat.completions.create(...)` , ja se näyttää täysin samalta kuin token-tila, mutta taustalla maksetaan kutsukohtaisesti ilman ennakkolatausta.

Tässä artikkelissa:

- Käydään todellisuudessa läpi TS-puolen ”ei tokenia + X402-handlerin injektointi” -ketju ([T12-vahvistus](#neljä-todellisen-ajon-vahvistus))
- Luetellaan EVM- ja Solana-allekirjoitusketjujen erot
- Annetaan kolme sovitusta: `viem`-yksityisavain-tila, selainlompakkotila ja Python `EVMAccountSigner` -tila
- Selvennetään helposti virheille altis `preferScheme` / `prefer_scheme` -kenttä

## I. Protokollan yleiskatsaus (pakollinen lukeminen)

Yksi onnistunut X402-kutsu sisältää **3 HTTP RTT:tä**:

```text
1. SDK -> /openai/v1/chat/completions               (ei Authorizationia)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK:n sisäinen -> paymentHandler({ url, method, body, accepts })   (paikallinen allekirjoitus, 0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (PAYMENT-SIGNATURE-otsikko injektoitu)
   <- 200 + liiketoimintavastaus   (selvitys tehdään palvelinpuolella)
```

X402-envelope on JSON-katkelma, joka base64-koodataan ja asetetaan `PAYMENT-SIGNATURE`-otsikkoon. Rakenne (ote):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

Envelopen ylimmällä tasolla on `x402Version: 2`, ja se ilmoittaa `accepted`-objektilla tässä tapauksessa valitun `scheme`- ja `network`-arvon (CAIP-2-tunniste).

| scheme  | Merkitys                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Kiinteä hinta (hinnoitellut skenaariot, kuten kuvien / videoiden generointi, haku jne.). Allekirjoitettu summa = palvelimen vaatima summa.                                                         |
| `upto`  | Mittariperusteinen laskutus (chat completions / token-tyyppiset). Allekirjoitetaan **enimmäissumma**, ja todellisuudessa selvitetään vain käytetty osuus (Permit2 + witness -pohjaisesti). **Erittäin suositeltu** keskustelutyyppisille API:lle. |

`preferScheme` / `prefer_scheme` käytetään ensisijaisen vaihtoehdon valitsemiseen, kun palvelin **tarjoaa samanaikaisesti useita schemejä**. Jos palvelin tarjoaa vain `exact`-vaihtoehdon, tämä kenttä ohitetaan; jos arvoksi asetetaan `upto`, mutta palvelin ei tarjoa sitä, palataan ensimmäiseen vastaavaan vaihtoehtoon.

## II. TypeScript: kaksi käyttötapaa, selainlompakko + palvelinpuolen viem

### Asennus

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Testatut versionumerot:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### `createX402PaymentHandler`-funktion täydellinen allekirjoitus

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // pakollinen, kun network='solana'
  evmProvider?: EVMProvider;                // pakollinen, kun network='base', EIP-1193
  evmAddress?: string;                      // pakollinen, kun network='base'
  preferScheme?: 'exact' | 'upto';
}
```

Paluuarvo on `(ctx) => Promise&lt;{ headers: Record<string, string> }>` , joka vastaa täsmälleen SDK:n `paymentHandler`-koukun allekirjoitusta.

### Käyttö 1: selain (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. Anna käyttäjän yhdistää lompakkonsa
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. Vaihda Base-pääverkkoon
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. Luo SDK-asiakas ja injektoi X402-handler
//    Huomaa: älä välitä apiTokenia, jotta SDK käyttää 402-polun
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat-tyyppisille pakollinen upto
  })
});

// 4. Kutsu normaalisti
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Ensimmäisellä kutsulla selain näyttää **kaksi allekirjoituskehotetta**: ensimmäinen on Permit2:n kertaluonteinen USDC-approve (summa on `MaxUint256`, kirjoitetaan ketjuun); toinen on X402-envelopen EIP-712-allekirjoitus (ei mene ketjuun, vaan facilitator käyttää sitä vahvistukseen). Seuraavat kutsut tarvitsevat vain toisen allekirjoituksen, joten käyttökokemus on ”napsauta allekirjoitus kerran → saat tuloksen”.

### Käyttö 2: Node-palvelin + viem-yksityisavain (sopii backendille / CLI:lle)

`@acedatacloud/x402-client` hyväksyy TS-puolella **vain EIP-1193-providerin**——se ei käsittele yksityisavaimia suoraan. Node / CLI -skenaarioissa vakiotapa on paketoida yksityisavain [`viem`](https://viem.sh/)-kirjastolla `WalletClient`-objektiksi ja käyttää sitten [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) -kirjastoa tai viemin sisäistä EIP-1193-sovitusta.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient sisältää EIP-1193-yhteensopivan .request()-metodin, joten sitä voi käyttää suoraan evmProviderina
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request täyttää EIP-1193-vaatimukset
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Jos viemin EIP-1193-sovitus ei tunnu riittävän vakaalta, voit myös käyttää alemman tason [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts) -metodia, yhdistää itse polun `accepts → signed envelope → PAYMENT-SIGNATURE header` ja ohittaa SDK-koukun; ensisijaisesti suositellaan kuitenkin edelleen `createX402PaymentHandler`-metodia, jotta protokollapäivityksiä ei tarvitse ylläpitää itse.

### Käyttö 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

Solana-ketjussa on tällä hetkellä **esillä vain `exact`-scheme**, joten `preferScheme` ei vaikuta Solanassa.

## III. Python: yksityisavain-tila

Pythonin `acedatacloud-x402` käyttää **suoraan yksityisavaimella allekirjoittamisen** mallia (ilman EIP-1193-abstraktiota), mikä sopii paremmin palvelinpuolelle / tehtäväsuorittajille.

### Asennus

```bash
pip install acedatacloud acedatacloud-x402
```

Testatut versiot:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. Muodosta allekirjoittaja yksityisavaimesta
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. Muodosta SDK: älä välitä api_tokenia, jotta SDK käyttää 402-polku
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # chat-tyyppisille on aina valittava upto
    )
)

# 3. Kutsu normaalisti
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # valinnainen
    )
)
```

### Kertaluonteinen approve (vain ensimmäisellä EVM-kerralla)

EVM Basessa X402 käyttää Permit2:ta, joten lompakon on tehtävä USDC:lle kerran `MaxUint256`-approve Permit2-sopimukselle. `acedatacloud-x402` sisältää `approve_permit2`-metodin:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Tämä tapahtuma tarvitsee lähettää vain kerran, minkä jälkeen kaikki X402 EVM -maksut käyttävät tätä valtuutusta. Solana ei tarvitse sitä.

## IV. Todellisen suorituksen varmistus

Testitavoite: **TS SDK ei välitä tokenia, injektoi X402-handlerin ja pystyy normaalisti muodostamaan sekä lähettämään pyynnön** (kevyt varmennus, joka ei kuluta oikeaa ketjussa olevaa USDC:tä).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // paikkamerkkiprovider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Tuloste:

```text
handler_type function
client_ctor_ok AceDataCloud
```

Tulos osoittaa:

- `apiToken`-arvoa ei välitetä, eikä SDK:n muodostus **aiheuta virhettä**, mikä todistaa, että X402-tila on todella kelvollinen vaihtoehto tokenille.
- `createX402PaymentHandler` palauttaa funktion (koukun), jota SDK kutsuu vasta saatuaan 402-vastauksen.
- Todellinen päästä päähän -testi onnistuneesta ketjun maksusta ei sisälly tähän ohjeeseen, koska se sisältää oikean USDC:n veloituksen; voit tutustua [X402-integrointioppaassa](https://platform.acedata.cloud/documents/x402-integration) olevaan e2e-esimerkkiin.

> Python-puolen `create_x402_payment_handler` on myös varmennettu samalla tavalla —— funktion palautusarvo on callable, eikä `AceDataCloud(...)`-muodostus aiheuta virhettä, kun `payment_handler=...` injektoidaan. Molempien puolien semantiikka on yhtenäinen.

## V. Vertailu "Bearer token -tilaan"

| Ulottuvuus              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Käyttötilanne            | Oma taustajärjestelmä, pitkäaikaiset projektit                                                         | Kolmannen osapuolen kehittäjät, käytön mukaan maksu, Agentic-kutsut                        |
| Rekisteröinti              | Edellyttää hakemista [konsolissa](https://platform.acedata.cloud/console/applications) | Ei tarvita; kunhan käytössä on ketjulompakko                                     |
| Laskutustarkkuus            | Ladataan etukäteen, veloitus token-hinnaston mukaan                                                   | Ketjuun kirjattava reaaliaikainen veloitus kutsukohtaisesti                                         |
| Saldo              | Nähtävissä konsolissa                                                           | Tarkista ketjulompakon USDC                                      |
| Ensimmäinen kustannus            | Sähköpostirekisteröinti antaa ilmaista käyttökiintiötä                                                        | USDC on siirrettävä Baseen, ensimmäinen Permit2 approve              |
| Sopii chat-tyyppisille       | ✅                                                                 | ✅ (edellyttää `preferScheme=upto`)                       |
| Sopii kertaluonteiseen maksuun / maksamiseen toisen tilin puolesta | ❌                                                                 | ✅                                               |
| Koodimuutokset            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Kaksi tilaa voivat olla rinnakkain — samassa prosessissa riittää, että eri `client`-instansseille määritetään eri todennustavat.

## Kuusi, yleiset sudenkuopat

1. **chat-tyypin täytyy käyttää `preferScheme=upto`**: `exact` saa facilitatorin veloittamaan USDC:tä `maxAmountRequired`-arvon (ei todellisen käytön) mukaan.
2. **Älä välitä paljasta yksityisavainta Node-puolella `createX402PaymentHandler`-funktiolle**: TS-paketti ei hyväksy `{ privateKey }`-muotoa, vaan se täytyy kääriä EIP-1193-provideriksi (suositus: viem `WalletClient`).
3. **Ensimmäinen kutsu sisältää kaksi allekirjoitusta**: ensimmäinen allekirjoittaa Permit2 approve -toiminnon (ketjussa, kuluttaa gasia), toinen allekirjoittaa X402 envelope -toiminnon (ei ketjussa). Seuraavissa kutsuissa jää jäljelle vain toinen.
4. **Solanassa ei ole Permit2-konseptia**: allekirjoita suoraan SPL token transfer -valtuutus, approve-toimintoa ei tarvita; mutta tällä hetkellä Solana-ketjussa tuetaan vain `exact`-tilaa.
5. **Erottele liiketoimintavirheet ja maksuhäiriöt**: 402 → handlerin epäonnistuminen heittää `X402SignError`-virheen (tarkka tyyppi vaihtelee ketjun mukaan); uudelleenlähetyksen jälkeen liiketoimintarajapinnan virheet (401 / 422 / 5xx) luokitellaan edelleen tavallisiksi SDK-poikkeuksiksi.
6. **Vakaimmin toimiva `viem`-sovitus**: `evmProvider: walletClient as any` menettää tyyppitarkistuksen, mutta tarjoaa parhaan yhteensopivuuden; jos haluat säilyttää tyypit, kääri viem:n `.transport.request` erikseen ja välitä sille `{ request }`-objekti.
