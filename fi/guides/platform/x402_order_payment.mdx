Sen lisäksi, että maksat suoraan API-pyynnöistä, Ace Data Cloud tukee myös X402-maksua konsolitilauksista. Tilausmaksun ja API-kutsujen ydinprotokolla on sama: ensimmäinen pyyntö palauttaa 402:n, asiakas allekirjoittaa `PAYMENT-SIGNATURE`-tunnisteen ja yrittää sitten uudelleen samalla pyynnöllä.

Erona on, että tilausmaksu kuuluu alustan API:hin ja vaatii tilitunnuksen; kun taas `x402.acedata.cloud`-palvelun AI API:a voidaan kutsua suoraan pelkällä X402:lla ilman API Tokenia.

## Valmistele tilaus

Siirry [Ace Data Cloud -konsoliin](https://platform.acedata.cloud/console/orders), valitse maksettava tilaus ja tallenna tilauksen ID.

Jos sinulla ei vielä ole tilausta, voit luoda maksua odottavan tilauksen pakettisivulla. Tilauksen hinta määräytyy sivulla näkyvän hinnan mukaan, ja X402 402 -vastauksen `amount` on lopullinen allekirjoituksen peruste.

## Luo tilitunnus

Tilausmaksupyyntö vaatii tilitunnuksen. Avaa [alustan Token-sivu](https://platform.acedata.cloud/console/platform-tokens) ja luo `platform-v1-...`-muotoinen token.

Käytä seuraavissa pyynnöissä:

```http
Authorization: Bearer {platform_token}
```

Tilitunnus eroaa tavallisesta API Tokenista. Tavallista API Tokenia käytetään API-kiintiön kuluttamiseen; tilitunnusta käytetään tilisi edustamiseen alustan resursseja, kuten tilausmaksuja, käsiteltäessä.

## Käynnistä 402

Lähetä ensin pyyntö ilman `PAYMENT-SIGNATURE`-tunnistetta:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

Palautettu tila on 402, ja vastaus sisältää `accepts`-kentän:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

Tilausmaksu käyttää virallista x402 v2:ta: `x402Version` on `2`, `network` käyttää CAIP-2-tunnistetta ja summakenttä on `amount`.

Ohjelman suoritus tulos, kun luodaan 10 Credits -tilaus ja käynnistetään 402:

> Seuraavat tapahtumatiedot ovat vanhan käytännön mukaisia historiallisia käytännön testiesimerkkejä; summa ja tapahtumahajautus on säilytetty alkuperäisinä. Uusiin X402-tilauksiin ei enää sovelleta maksutapa-alennusta; käytä tämän 402-vastauksen `amount`-arvoa allekirjoituksen ja maksun perusteena.

```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
error Payment required for this order.
accepts [
  ('eip155:8453', 'exact', '1200000', '0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000', '5iVXFrYaYWX2GUTbkQj8mDBoBhAX8bneYigS2LJTia43')
]
description Ace Data Cloud Credits x 10.0
```

Tulosten selitys:

- Kun tilaus on luotu onnistuneesti, sen tila on `Pending`, eikä ketjussa ole vielä suoritettu maksua.
- Ensimmäinen `pay/`-pyyntö ei sisällä `PAYMENT-SIGNATURE`-tunnistetta, joten se palauttaa HTTP 402:n.
- `accepts` antaa samanaikaisesti Base `exact`- ja Solana `exact`-vaihtoehdot; tässä ohjeessa valitaan myöhemmin Base.
- Tilauksen hinta luotaessa oli `1.26`, ja vanhan X402-maksualennuskäytännön aikana maksettaessa todellinen allekirjoitus- ja selvityssumma oli `1.2` USDC:tä, mikä vastaa arvoa `1200000` atomic USDC.

Huomaa, että `resource` on palvelimen palauttama ja allekirjoitukseen osallistuva kenttä; asiakas ei saa itse muuttaa siinä olevaa protokollaa, polkua tai tilauksen ID:tä.

## Allekirjoita ja yritä uudelleen

Tilausmaksu voi hyödyntää uudelleen `@acedatacloud/x402-client`- tai `acedatacloud-x402`-paketin matalan tason allekirjoitusfunktioita. Alla on TypeScript-esimerkki:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

Ohjelman suoritus tulos, kun sama tilaus allekirjoitetaan Base `exact`-vaihtoehdolla ja yritetään uudelleen:

```text
status 200
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
has_x_payment_response True
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order {'id': '78481793-304e-47f7-bc0c-8231aec9cc1e', 'state': 'Finished', 'pay_way': 'X402', 'price': 1.2, 'pay_id': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}
```

Ketjussa vahvistettu tulos:
```text
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer {"from":"0x5d4f08D5c2bb60703284bc06671Eb680fA41B105","to":"0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7","value":"1200000"}
```

Tulosten selitys:

- `status 200` tarkoittaa, että alustan tilausmaksurajapinta hyväksyi tämän `PAYMENT-SIGNATURE`-arvon.
- `has_x_payment_response True` tarkoittaa, että vastausotsikko sisältää Base64-koodatun `PAYMENT-RESPONSE`-kuitin.
- `settle_header.success=True` ja `network=base` tarkoittavat, että Facilitator on suorittanut Base-selvityksen.
- Tilauksen lopullinen tila on `Finished`, `pay_way` on `X402`, ja `pay_id`:hen kirjoitetaan ketjussa olevan tapahtuman tiiviste.
- BaseScanin `Transfer`-tapahtuma näyttää, että maksajan osoite siirsi alustan vastaanottavaan osoitteeseen `1200000` atomic USDC:tä eli `1.2` USDC:tä.

## Onnistunut vastaus ja kuitti

Kun tilausmaksu onnistuu, vastausrunkona ovat tilaustiedot. Alusta sisällyttää myös vastausotsikkoon `PAYMENT-RESPONSE` Base64-koodatun settlement response -vastauksen, jonka dekoodauksen jälkeen tavallisia kenttiä ovat:

| Kenttä            | Kuvaus                           |
| ------------- | ---------------------------- |
| `success`     | Onnistuiko Facilitator settlement. |
| `transaction` | Ketjussa olevan selvitystapahtuman tiiviste.                    |
| `network`     | Maksuverkko.                        |
| `payer`       | Maksajan lompakon osoite.                      |
| `amount`      | Todellinen selvityssumma, käytetään atomic units -yksiköitä.      |

Jos tarvitset täsmäytystä, on suositeltavaa tallentaa samanaikaisesti tilauksen ID, maksajan lompakon osoite, `transaction` ja tilauksen lopullinen tila.

## Huomioitavaa

- Tilausmaksu edellyttää alustan tilitunnusta, eikä sitä voi suorittaa pelkällä X402-lompakon allekirjoituksella.
- `amount` käyttää USDC atomic units -yksiköitä, `1200000` tarkoittaa `1.2` USDC:tä.
- Älä muodosta vastaanottajan osoitetta tai omaisuusosoitetta itse, vaan noudata 402-vastauksen `accepts`-arvoa.
- Jos sama `PAYMENT-SIGNATURE` lähetetään toistuvasti, Facilitator tekee uudelleentoistosuojauksen noncen perusteella.

## Maksun epäonnistumisvastaus

Ensimmäinen HTTP 402 ilman `PAYMENT-SIGNATURE`-arvoa on normaali maksupyyntö, eikä se tarkoita maksun epäonnistumista. Allekirjoituksen jälkeinen vahvistus- tai selvitysvirhe säilyttää edelleen vakiomuotoisen merkkijonon `error` yhteensopivana vararatkaisuna ja palauttaa vakaan virherakenteen kohdassa `extensions.acedatacloud.paymentError`:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

Asiakkaan tulee ensisijaisesti lokalisoida `code`-arvon mukaan ja palata yleiseen maksun epäonnistumiseen tuntemattoman coden kohdalla. `charged` on kolmitilainen kenttä: `false` palautetaan vain, kun maksu hylätään nimenomaisesti ennen selvitystä; kentän puuttuminen tarkoittaa, että veloitustila on tuntematon, eikä sitä voi tulkita ”ei veloitettu” -merkityksessä. Kun nykyinen tilaus siirtyy tilaan `Failed`, alkuperäistä tilausta ei voi yrittää uudelleen; korjaa lompakko-ongelma ja luo uusi tilaus.

Tilausluettelon ja tietojen `metadata.x402.last_error` ja `metadata.x402.errors` säilyttävät saman joukon `code`-, `stage`-, `retryable`-, `charged`- ja `params`-arvoja; julkinen kuvausteksti tallennetaan kohtaan `reason`, ja tapahtuma-aika kohtaan `timestamp`. Esimerkiksi `insufficient_token_balance` tarkoittaa, että valitun verkon USDC-saldo on riittämätön, ja `invalid_signature` tarkoittaa, että maksun allekirjoitus on virheellinen; tilauksen uudelleen lukeminen ei muuta niitä yleiseksi `payment_failed`-virheeksi.

Älä tallenna tai lähetä täydellistä `PAYMENT-SIGNATURE`-arvoa, lompakon allekirjoitusta, valtuutuksen payloadia, Facilitatorin alkuperäisiä diagnostiikkatietoja tai RPC-vastausta. Asiakaspalvelun selvitykseen tarvitaan vain tilauksen ID ja julkinen virhe `code`.

## ACE:n takaisinosto ja poltto Base- ja Solana-maksuille

Kun takaisinostostrategia on käytössä, ehdot täyttävien Base-pääverkon Circle USDC- ja Solana-pääverkon USDC -maksujen tosiasiallisesti vastaanotetusta summasta käytetään 3 % ACE:n ostamiseen ja polttamiseen ilman ylimääräistä veloitusta maksajan lompakosta. Se kirjataan kerran latauksen yhteydessä, eikä näitä Creditejä myöhemmin API-kutsuihin käytettäessä kirjata uudelleen; historiallisia alennustilauksia ja vanhojen strategioiden tilauksia ei kirjata automaattisesti takautuvasti.

Base-maksu säilyttää maksukuitin Base-ketjussa, ja ACE:n osto sekä poltto suoritetaan asynkronisesti Solanassa. Tilaustietojen `ace_burn`-objekti tarjoaa `settlement_network`-, `settlement_transaction`- ja `execution_network`-arvot sekä valmistumisen jälkeen `swap_signature`- ja `burn_signature`-arvot. `Pending` tai `Processing` ei tarkoita, että poltto on jo tehty; vain `Completed` tarkoittaa, että lopullinen ketjussa oleva todiste on tarkistettu. Kun Base-maksu ei ole vielä saavuttanut lopullista vahvistusta, takaisinosto odottaa vahvistusta, mutta tämä ei vaikuta jo saapuneisiin Crediteihin.
