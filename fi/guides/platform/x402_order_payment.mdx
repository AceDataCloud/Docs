API-pyyntöjen suoran maksamisen lisäksi Ace Data Cloud tukee myös X402-maksukonsolin tilausten maksamista. Tilausmaksun ja API-kutsun ydinprotokolla on sama: ensimmäinen pyyntö palauttaa 402:n, asiakas allekirjoittaa `PAYMENT-SIGNATURE`-allekirjoituksen ja yrittää sitten uudelleen samalla pyynnöllä.

Erona on, että tilausmaksu kuuluu alustan API:hin ja vaatii tilitunnuksen; kun taas `x402.acedata.cloud`-palvelun AI API:a voi kutsua suoraan vain X402:lla, ilman API Tokenia.

## Valmistele tilaus

Siirry [Ace Data Cloud -konsoliin](https://platform.acedata.cloud/console/orders), valitse maksettava tilaus ja kirjaa tilauksen ID.

Jos sinulla ei vielä ole tilausta, voit luoda odottavan maksun tilauksen pakettisivulla. Tilauksen hinta määräytyy sivulla näkyvän hinnan mukaan, ja X402 402 -vastauksen `amount` on lopullinen allekirjoituksen peruste.

## Luo tilitunnus

Tilausmaksupyyntö vaatii tilitunnuksen. Avaa [alustan Token-sivu](https://platform.acedata.cloud/console/platform-tokens) ja luo `platform-v1-...`-muotoinen token.

Käytä seuraavissa pyynnöissä:

```http
Authorization: Bearer {platform_token}
```

Tilitunnus eroaa tavallisesta API Tokenista. Tavallista API Tokenia käytetään API-kiintiön kuluttamiseen; tilitunnusta käytetään tilisi edustamiseen alustan resurssien, kuten tilausmaksujen, käsittelyssä.

## Käynnistä 402

Lähetä ensin pyyntö ilman `PAYMENT-SIGNATURE`-allekirjoitusta:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

Palautettava tila on 402, ja vastaus sisältää `accepts`:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

Tilausmaksu käyttää virallista x402 v2:ta: `x402Version` on `2`, `network` käyttää CAIP-2-tunnistetta ja summakenttä on `amount`.

Ohjelman suoritusresultaatti, kun luodaan 10 Credits -tilaus ja käynnistetään 402:

> Seuraavat tapahtumatiedot ovat historiallisia, vanhan käytännön mukaisia käytännön testiesimerkkejä; summa ja tapahtumahajautus on säilytetty alkuperäisinä. Uudet X402-tilaukset eivät enää saa maksutapa-alennuksia; käytä tämän 402-vastauksen `amount`-arvoa allekirjoituksen ja maksun perustana.

```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
error Payment required for this order.
accepts [
  ('eip155:8453', 'exact', '1200000', '0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000', '5iVXFrYaYWX2GUTbkQj8mDBoBhAX8bneYigS2LJTia43')
]
description Ace Data Cloud Credits x 10.0
```

Tulosten selitys:

- Kun tilaus on luotu onnistuneesti, tila on `Pending`, eikä ketjussa ole vielä maksua.
- Ensimmäisessä `pay/`-pyynnössä ei ole `PAYMENT-SIGNATURE`-allekirjoitusta, joten se palauttaa HTTP 402:n.
- `accepts` antaa samanaikaisesti Base `exact`- ja Solana `exact` -vaihtoehdot; tässä oppaassa valitaan myöhemmin Base.
- Tilauksen luonnin yhteydessä hinta on `1.26`; vanhan X402-maksualennuskäytännön aikana maksettaessa todellinen allekirjoitettava ja selvitettävä summa on `1.2` USDC, joka vastaa arvoa `1200000` atomic USDC.

Huomaa, että `resource` on palvelimen palauttama ja allekirjoitukseen osallistuva kenttä; asiakas ei saa itse muuttaa sen protokollaa, polkua tai tilauksen ID:tä.

## Allekirjoita ja yritä uudelleen

Tilausmaksussa voidaan käyttää uudelleen `@acedatacloud/x402-client`- tai `acedatacloud-x402`-paketin matalan tason allekirjoitusfunktioita. Alla on TypeScript-esimerkki:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

Ohjelman suoritusresultaatti, kun sama tilaus allekirjoitetaan Base `exact` -menetelmällä ja yritetään uudelleen:

```text
status 200
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
has_x_payment_response True
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order {'id': '78481793-304e-47f7-bc0c-8231aec9cc1e', 'state': 'Finished', 'pay_way': 'X402', 'price': 1.2, 'pay_id': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}
```

Ketjun vahvistustulos:
```text
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer {"from":"0x5d4f08D5c2bb60703284bc06671Eb680fA41B105","to":"0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7","value":"1200000"}
```

Tulosten selitys:

- `status 200` tarkoittaa, että alustan tilauksenmaksurajapinta hyväksyi tämän `PAYMENT-SIGNATURE`-allekirjoituksen.
- `has_x_payment_response True` tarkoittaa, että vastausotsikko sisältää Base64-koodatun `PAYMENT-RESPONSE`-kuitin.
- `settle_header.success=True` ja `network=base` tarkoittavat, että Facilitator on suorittanut Base-settlementin.
- Tilauksen lopullinen tila on `Finished`, `pay_way` on `X402`, ja `pay_id`-kenttään kirjoitetaan ketjussa olevan tapahtuman tiiviste.
- BaseScanin `Transfer`-tapahtuma osoittaa, että maksajan osoite siirsi alustan vastaanotto-osoitteeseen `1200000` atomic USDC:tä, eli `1.2` USDC:tä.

## Onnistunut vastaus ja kuitti

Kun tilauksen maksu onnistuu, vastausrunko sisältää tilaustiedot. Alusta välittää myös vastausotsikossa `PAYMENT-RESPONSE` Base64-koodatun settlement response -vastauksen, jonka purkamisen jälkeen yleisiä kenttiä ovat:

| Kenttä            | Selitys                           |
| ------------- | ---------------------------- |
| `success`     | Onnistuiko Facilitator settlement. |
| `transaction` | Ketjussa olevan settlement-tapahtuman tiiviste.                    |
| `network`     | Maksuverkko.                        |
| `payer`       | Maksajan lompakko-osoite.                      |
| `amount`      | Todellinen settlement-määrä, atomic units -muodossa.      |

Jos tarvitset täsmäytystä, on suositeltavaa tallentaa samanaikaisesti tilauksen ID, maksajan lompakko-osoite, `transaction` ja tilauksen lopullinen tila.

## Huomioitavaa

- Tilauksen maksu vaatii alustan tilitunnuksen, eikä sitä voi suorittaa pelkällä X402-lompakon allekirjoituksella.
- `amount` käyttää USDC atomic units -yksiköitä, ja `1200000` tarkoittaa `1.2` USDC:tä.
- Älä muodosta vastaanotto-osoitetta tai omaisuusosoitetta itse, vaan käytä 402-vastauksen `accepts`-kenttää.
- Jos sama `PAYMENT-SIGNATURE` lähetetään uudelleen, Facilitator käyttää noncea uudelleenlähetyssuojaukseen.

## Maksun epäonnistumisvastaus

Ensimmäinen HTTP 402 ilman `PAYMENT-SIGNATURE`-allekirjoitusta on normaali maksupyyntö, eikä se tarkoita maksun epäonnistumista. Allekirjoittamisen jälkeinen vahvistus- tai settlement-epäonnistuminen säilyttää edelleen vakiomerkkijonon `error` yhteensopivuuden varmistuksena ja palauttaa vakaan virherakenteen kohdassa `extensions.acedatacloud.paymentError`:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

Asiakkaan tulee ensisijaisesti lokalisoida `code`-kentän perusteella, ja tuntemattomissa code-arvoissa palata yleiseen maksun epäonnistumiseen. `charged` on kolmitilainen kenttä: `false` palautetaan vain, kun maksu hylätään nimenomaisesti ennen settlementiä; puuttuva kenttä tarkoittaa, että veloituksen tila on tuntematon, eikä sitä voi tulkita tarkoittavan ”ei veloitettu”. Kun nykyinen tilaus siirtyy tilaan `Failed`, alkuperäistä tilausta ei voi yrittää uudelleen; korjaa lompakko-ongelma ja luo uusi tilaus.

Tilausluettelon ja -tietojen `metadata.x402.last_error` ja `metadata.x402.errors` säilyttävät saman joukon `code`-, `stage`-, `retryable`-, `charged`- ja `params`-kenttiä; julkinen kuvausteksti tallennetaan kenttään `reason`, ja tapahtuma-aika kenttään `timestamp`. Esimerkiksi `insufficient_token_balance` tarkoittaa, että USDC-saldo valitussa verkossa ei riitä, ja `invalid_signature` tarkoittaa, että maksuallekirjoitus on virheellinen; tilauksen uudelleen lukeminen ei muuta niitä yleiseksi `payment_failed`-virheeksi.

Älä tallenna tai lähetä täydellistä `PAYMENT-SIGNATURE`-allekirjoitusta, lompakon allekirjoituksia, valtuutus-payloadia, Facilitatorin alkuperäisiä diagnostiikkatietoja tai RPC-vastauksia. Asiakaspalvelun selvitystä varten tarvitaan vain tilauksen ID ja julkinen virhe-`code`.

## ACE:n takaisinosto ja poltto Base- ja Solana-maksuissa

Kun takaisinostostrategia on käytössä, ehdot täyttävistä Base-pääverkon Circle USDC- ja Solana-pääverkon USDC -todellisista vastaanotetuista määristä käytetään 3 % ACE:n ostamiseen ja polttamiseen ilman lisäveloitusta maksajan lompakosta. Hyvityksen yhteydessä tehdään yksi kirjaus, eikä näitä Creditsiä myöhemmin API-kutsuihin käytettäessä tehdä uutta kirjausta; historiallisia alennustilauksia ja vanhan strategian tilauksia ei kirjata takautuvasti automaattisesti.

Base-maksu säilyttää maksukuitin Base-ketjussa, ja ACE:n osto ja poltto suoritetaan asynkronisesti Solanassa. Ehdot täyttävät maksut kirjataan tarkalleen 3 %:n mukaan todellisesta vastaanotetusta määrästä ilman kiinteää yksittäisen maksun tai päivittäisen takaisinoston ylärajaa; käytettävissä olevat varat, markkinahinnat ja ketjussa olevat vahvistukset voivat silti vaikuttaa valmistumisaikaan. Tilaustietojen `ace_burn`-objekti tarjoaa `settlement_network`-, `settlement_transaction`- ja `execution_network`-kentät sekä valmistumisen jälkeen `swap_signature`- ja `burn_signature`-kentät. `Pending` tai `Processing` ei tarkoita, että poltto on jo suoritettu; vain `Completed` tarkoittaa, että lopullinen ketjussa oleva todiste on tarkistettu. Jos Base-maksu ei ole vielä saavuttanut lopullista vahvistusta, takaisinosto odottaa vahvistusta, mutta se ei vaikuta jo saapuneisiin Creditseihin.
