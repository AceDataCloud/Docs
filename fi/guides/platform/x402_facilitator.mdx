Facilitator on palvelinpuolen selvityskomponentti X402-ketjussa. Asiakas vastaa allekirjoituksesta, ja Gateway tai palvelimesi vastaa Facilitatorin `/verify`- ja `/settle`-kutsujen tekemisestä.

Ace Data Cloudin tuotanto-Facilitator-osoite on:

```text
https://facilitator.acedata.cloud
```

Lähdekoodivarasto: [https://github.com/AceDataCloud/FacilitatorX402](https://github.com/AceDataCloud/FacilitatorX402)

## v2 wire -sopimus

Ace Data Cloudin X402-ketju käyttää kokonaisuudessaan virallista x402 v2:ta eikä enää hyväksy v1:n `X-Payment`-pyyntöotsaketta. Integroinnissa on huomioitava kolme asiaa:

- Pyyntöotsake on `PAYMENT-SIGNATURE`, ja sen arvo on base64-koodattu JSON envelope.
- envelopen ylimmällä tasolla täytyy olla `x402Version: 2`, ja tämän kerran valittu `scheme` ja `network` on ilmoitettava `accepted`-objektilla.
- `network` käyttää CAIP-2-tunnistetta (kuten `eip155:8453`), eikä siihen voi kirjoittaa lyhenteitä kuten `base`.

envelopen rakenne:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": { "...": "..." }
}
```

JSON bodyn lisäksi 402-vastaus sisältää myös `PAYMENT-REQUIRED`-vastausotsakkeen, jonka arvo on saman haasteen sisällön base64-koodaus. Tämä helpottaa asiakasta lukemaan maksuvaatimukset ilman bodyn jäsentämistä.

## Ydinrajapinnat

### `GET /supported`

Tarkastele tuettuja verkkoja ja schemejä:

```bash
curl https://facilitator.acedata.cloud/supported
```

Palautusesimerkki:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ],
  "extensions": [],
  "signers": {
    "eip155:*": [
      "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708"
    ],
    "solana:*": ["3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq"]
  }
}
```

Tuloksen selitys:

- `network` käyttää CAIP-2-tunnistetta, ei lyhenteitä kuten `base` tai `solana`.
- `/supported` tarkoittaa, että Facilitatorilla on vastaavat varmennus- ja selvitysominaisuudet.
- Sekä Base että Solana tukevat `exact`-vaihtoehtoa; `upto` on tällä hetkellä tarjolla vain Basessa.
- `signers` ovat osoitteita, joita Facilitator käyttää selvitystapahtumien lähettämiseen.
- Se, salliiko jokin tietty API nämä vaihtoehdot, määräytyy edelleen kyseisen API:n 402 `accepts` -kohdan mukaan.

### `POST /verify`

Varmista, täyttääkö asiakkaan lähettämä `PAYMENT-SIGNATURE` jonkin payment requirementin.

Pyynnön body:

```json
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "accepted": {
      "scheme": "exact",
      "network": "eip155:8453"
    },
    "payload": { "...": "..." }
  },
  "paymentRequirements": {
    "scheme": "exact",
    "network": "eip155:8453",
    "asset": "0x...",
    "amount": "95215",
    "payTo": "0x...",
    "maxTimeoutSeconds": 3600,
    "extra": { "...": "..." }
  }
}
```

v2:n `paymentRequirements`-kentät ovat `scheme`, `network`, `asset`, `amount`, `payTo`, `maxTimeoutSeconds` ja `extra`, ja summakenttä on `amount`. API:n 402-vastauksen `accepts[]` palauttaa lisäksi `maxAmountRequired`-arvon asiakkaan luettavaksi, mutta se ei kuulu Facilitatorin pyynnön bodyn kenttiin.

Onnistunut vastaus:

```json
{
  "isValid": true,
  "invalidReason": null,
  "payer": "0x..."
}
```

Tuotantotilauksen maksun `PAYMENT-RESPONSE`-vastausotsake sisältää dekoodattuna settlement-tuloksen. Base-tilauksen maksun ohjelman suoritustulos:

```text
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order 78481793-304e-47f7-bc0c-8231aec9cc1e state Finished pay_way X402 price 1.2
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Tuloksen selitys:

- `success=True` tarkoittaa, että Facilitator settlement onnistui.
- `transaction` on ketjun tapahtumahajautus, ja myös tilauksen `pay_id` kirjoitetaan samaan arvoon.
- explorerissa näkyy `1200000` atomic USDC:n Base USDC -siirto.
- `errorReason=None` tarkoittaa, että tämä settlement ei palauttanut liiketoimintavirhettä.

Varmennuksen epäonnistuminen palauttaa myös yleensä HTTP 200:n, mutta `isValid` on `false`. Liiketoimintapuolen tulisi lukea `invalidReason` eikä katsoa vain HTTP-tilakoodia.

### `POST /settle`

Selvitä jo varmennettu valtuutus ketjuun.

Pyynnön body on käytännössä sama kuin `/verify`-kutsussa. `upto`-vaihtoehdon ero on: `paymentRequirements.amount` kirjoitetaan settle-vaiheessa todelliseksi selvitettäväksi summaksi; Facilitator tallentaa allekirjoituksen ylärajan verify-vaiheessa, ja settle-vaiheessa se tarkistaa, ettei todellinen summa ylitä tätä ylärajaa.

Onnistunut vastaus:

```json
{
  "success": true,
  "errorReason": null,
  "transaction": "0x...",
  "network": "eip155:8453",
  "payer": "0x...",
  "amount": "3"
}
```

Jos `upto`-vaihtoehdon todellinen summa on 0, `transaction` voi olla tyhjä merkkijono, mikä tarkoittaa, ettei ketjutapahtumaa tarvitse lähettää.

## Kuinka Ace Data Cloud Gateway käyttää Facilitatoria

Ace Data Cloud API Gatewayn ketju on seuraava:

1. Asiakas pyytää APIa ensimmäisen kerran ilman `Authorization`- ja `PAYMENT-SIGNATURE`-otsakkeita.
2. Gateway laskee pyynnön arvioidun hinnan ja palauttaa 402:n sekä `accepts`-arvon.
3. Asiakas allekirjoittaa ja yrittää uudelleen `PAYMENT-SIGNATURE`-otsakkeen kanssa.
4. Gateway dekoodaa `PAYMENT-SIGNATURE`-arvon ja valitsee vastaavan payment requirementin.
5. Gateway kutsuu Facilitatorin `/verify`-rajapintaa.
6. Kun `/verify` onnistuu, Gateway päästää pyynnön kohde-APIin.
7. Kun kohde-API on palauttanut vastauksen, Gateway kutsuu Facilitatorin `/settle`-rajapintaa `/record`-vaiheessa.
8. Gateway kirjoittaa ketjun tapahtumahajautuksen käyttötietueen metadataan.

`exact` selvittää allekirjoitetun summan vaiheessa 7; `upto` kirjoittaa `amount`-arvoon todellisen käytön perusteella vaiheessa 7 ja selvittää sitten todellisen summan.

## Kuinka oma API integroidaan

Jos haluat, että oma APIisi tukee X402:ta, voit toteuttaa sen tämän rakenteen mukaisesti:
1. Valmistele jokaiselle maksulliselle rajapinnalle `paymentRequirements`, jotka sisältävät verkon, summan, vastaanotto-osoitteen, omaisuusosoitteen ja allekirjoituksen domainin.
2. Jos pyynnössä ei ole `PAYMENT-SIGNATURE`-otsaketta, palauta HTTP 402 ja `accepts`.
3. Jos pyynnössä on `PAYMENT-SIGNATURE`, Base64-dekoodaa se saadaksesi `paymentPayload`in.
4. Kutsu Facilitatorin `/verify`.
5. Suorita liiketoimintalogiikka vahvistuksen onnistuttua.
6. Kutsu Facilitatorin `/settle` liiketoiminnan onnistuttua.
7. Tallenna `payer`, `transaction`, `amount`, `network` täsmäytystä varten.

Palvelimen on kutsuttava `/verify` ja `/settle` omilla luomillaan `paymentRequirements`-tiedoilla, älä luota asiakkaan takaisin lähettämään summaan, vastaanotto-osoitteeseen tai omaisuusosoitteeseen.

## Uudelleentoistosuojaus

Facilitator tallentaa noncen. Saman noncen valtuutusta ei voi vahvistaa ja selvittää uudelleen.

Tämä tarkoittaa:

- Asiakkaan tulee allekirjoittaa uusi envelope jokaiselle pyynnölle;
- Jos `/settle` on jo lähettänyt tapahtuman mutta sitä ei ole vielä vahvistettu, voit yrittää `/settle`-kutsua uudelleen samalla noncella idempotenttia täsmäytystä varten;
- Älä tallenna samaa `PAYMENT-SIGNATURE`a välimuistiin käytettäväksi useissa API-kutsuissa.

## Yleiset virheet

| Virhe                                           | Yleinen syy                                                             |
| -------------------------------------------- | ---------------------------------------------------------------- |
| `Authorization nonce already processed`      | Samaa `PAYMENT-SIGNATURE`a käytettiin uudelleen.                                    |
| `Authorization destination mismatch`         | Asiakkaan allekirjoituksen `to` ei vastaa payment requirementin `payTo`ta.                |
| `invalid_upto_evm_payload_invalid_signature` | `upto` typed datan chainId, facilitator, Permit2 domain tai allekirjoitusosoite eivät täsmää. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Lompakko ei ole vielä approvannut Permit2:lle riittävää USDC allowancea.                        |
| `Payer has insufficient USDC balance`        | Maksulompakossa ei ole riittävästi USDC:tä.                                                    |
| `Solana signer private key not configured`   | Facilitatorin on allekirjoitettava fee payerina, mutta palvelimelta puuttuu Solana signer -määritys.           |
