X402 kattaa HTTP:n, SDK:n, allekirjoitukset, Facilitatorin ja ketjussa tehtävät transaktiot. Allekirjoitus- tai selvitysongelmia tutkittaessa on suositeltavaa varmistaa asiat kerros kerrokselta järjestyksessä ”julkinen päätepiste -> 402-vastaus -> SDK:n payment handler -> ketjussa tapahtuva settlement”. Tässä oppaassa kuvataan kunkin kerroksen tarkistustavat ja luetellaan yleiset virheet.

## Tarkista julkinen päätepiste

Facilitatorin kykyjen ilmoitus:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Jos palautetaan `facilitator`, `supportedKinds` ja protokollan päätepisteet, kykyjen metatiedot ovat kunnossa. API-resurssien löytäminen on poistettu käytöstä; kutsu suoraan kohde-APIa ja käytä reaaliaikaista 402-vastausta lähteenä.

Facilitatorin tukemat ominaisuudet:

```bash
curl https://facilitator.acedata.cloud/supported
```

Jos palautetaan `kinds`, Facilitatorin päätepiste toimii normaalisti.

## Tarkista 402 `accepts`

Lähetä tunnistautumaton pyyntö, josta ei veloiteta:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Tarkista, sisältääkö palautettu `accepts` verkon, jota haluat käyttää. `network` on CAIP-2-tunniste:

- `eip155:8453` + `exact` (Base)
- `eip155:8453` + `upto` (Base, jälkikäteen tapahtuva mittaus)
- `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` + `exact` (Solana)

Jos kohdeverkkoa ei ole, kyseistä X402-maksutapaa ei ole määritetty kyseiselle APIlle tai nykyiseen ympäristöön.

## Suorita X402Clientin edistynyt validointityökalu

X402Client-tietovarasto tarjoaa edistyneitä validointityökaluja, joilla voidaan varmistaa 402-vastauksen valinta, allekirjoituksen luonti, maksullinen uudelleenyritys ja ketjussa tapahtuva settlement. Ne edellyttävät rahoitettua lompakkoa, RPC:tä, yksityisavainta ja kehitysriippuvuuksia. Tavallisessa liiketoimintaintegraatiossa on suositeltavaa käyttää ensisijaisesti TypeScript- tai Python-SDK:ta; suorita nämä työkalut vain, kun allekirjoitus- tai ketjussa tapahtuvia selvitysongelmia on tarpeen paikantaa.

Tietovaraston osoite: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)

```bash
git clone https://github.com/AceDataCloud/X402Client.git
cd X402Client/typescript
npm install
npm install --no-save ethers @solana/spl-token bs58 tsx
```

Base:

```bash
export X402B_BASE_PAYER_PRIVATE_KEY=0x...
TEST_API_PATH='/openai/chat/completions' \
TEST_BODY='{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}],"max_tokens":10}' \
npx tsx scripts/test-real-e2e.ts
```

Solana:

```bash
export X402B_SOLANA_PAYER_PRIVATE_KEY=...
npx tsx scripts/test-solana-e2e.ts
```

Validointityökalut tulostavat yleensä:

1. Ensimmäisen pyynnön 402-vastauksen.
2. Valitun payment requirementin.
3. Allekirjoitetun `PAYMENT-SIGNATURE`-tiivistelmän.
4. Uudelleenyrityksen jälkeisen HTTP-tilan ja vastausrungon.
5. Ketjussa tapahtuvan settlement transactionin tai epäonnistumistilanteessa Facilitatorin virhesyyn.

Älä lähetä yksityisavaimia tai kokonaista `PAYMENT-SIGNATURE`-arvoa lokijärjestelmään tai tukipyyntöön.

Esimerkki julkisen API:n validointituloksista:

```text
Base exact
HTTP 402 -> HTTP 200
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC

Solana exact
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run because public RPC lookup hit 429

Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Selitys:

- Base `exact`, Solana `exact` ja Base `upto` suorittivat kaikki maksullisen uudelleenyrityksen HTTP 402:sta HTTP 200:aan.
- Base `exact` -ketjutransaktio on löydettävissä BaseScanista, ja selvityssumma on `95215` atomic USDC.
- Base `upto` -allekirjoituksen yläraja on `95215` atomic USDC, mutta todellinen ketjussa tapahtuva settlement on `3` atomic USDC, mikä osoittaa, että jälkikäteen tapahtuva mittaus veloittaa todellisen käytön mukaan.
- Solana-polulla vahvistettiin maksullinen uudelleenyritys ja mallin tuloste. Julkinen RPC voi olla nopeusrajoitettu; jos tarvitset tarkkaa ketjutäsmäytystä, käytä omaa Solana RPC:tä tai vahvista transaktion allekirjoitus alustan selvitystietueista.

## SDK smoke test

Edistynyttä validointityökalua käytetään allekirjoitusten ja ketjussa tapahtuvan selvityksen tarkistamiseen. Liiketoimintapuolella tulee lisäksi suorittaa SDK smoke test, jolla varmistetaan, että sovelluskoodi pystyy käsittelemään 402:n automaattisesti payment handlerin kautta. Alla näytetään vain ydinkohdat; täydelliseen koodiin on lisättävä lompakko, provider ja importit.

TypeScript:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const res = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly ADC_SDK_X402_OK' }],
  max_tokens: 8
});
```

Python:

```python
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
    )
)

res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly ADC_PY_X402_OK"}],
    max_tokens=8,
)
```

Jos malli palauttaa vaaditun kiinteän merkkijonon, SDK, payment handler, Gateway, Facilitator ja kohde-API ovat yhteydessä toisiinsa.

Yllä olevat kaksi smoke test -osiota käyttävät Base `exact` -mallia, jossa selvitys tehdään 402-hinnoittelun kiinteällä summalla. Chat completion kuuluu token-pohjaisesti mitattaviin käyttötapauksiin; varsinaisessa integraatiossa on suositeltavaa välittää `preferScheme: 'upto'` (Pythonissa `prefer_scheme="upto"`), jotta selvitys tehdään todellisen käytön perusteella.

Python SDK:n palautusobjekti on `dict`, ja sisältö voidaan lukea käyttämällä `res["choices"][0]["message"]["content"]`.

## Tilauksen maksu E2E

Tilauksen maksu käyttää `platform.acedata.cloud`-alusta-APIa ja edellyttää alustan tilitunnusta. Koko ketju on: luo Pending-tilaus, `POST /api/v1/orders/{order_id}/pay/` käynnistää 402:n, ja yritä sitten uudelleen `PAYMENT-SIGNATURE`-arvon kanssa.

Esimerkki pienen tilausmaksun validointituloksista:

> Seuraavat transaktiotiedot ovat historiallisia todellisia testinäytteitä vanhan käytännön ajalta, ja summat sekä transaktiohashit on säilytetty alkuperäisinä. Uudet X402-tilaukset eivät enää sisällä maksutapa-alennuksia; käytä tämänkertaisen 402-vastauksen `amount`-arvoa allekirjoituksen ja maksun perusteena.
```text
luotu tilaus 78481793-304e-47f7-bc0c-8231aec9cc1e
luotu tila Pending
luotu hinta 1.26

http_status=402
x402Version 2
accepts [('eip155:8453', 'exact', '1200000'), ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000')]

tila 200
tilauksen tila Finished
pay_way X402
pay_id 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}

Base-tapahtuman tila 1
lohko 46726704
selain https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
siirtoarvo 1200000 atomista USDC:tä
```

Tulosten kuvaus:

- Tilauksen luomisen jälkeen tilauksen tila on `Pending` ja hinta on `1.26`.
- Ensimmäinen `pay/`-pyyntö palauttaa HTTP 402:n, `accepts` sisältää Base `exact`- ja Solana `exact` -vaihtoehdot, ja molempien summa on `1200000` atomista USDC:tä.
- Uudelleenyritys Base `PAYMENT-SIGNATURE` -otsakkeella palauttaa HTTP 200:n, tilauksen tila muuttuu `Finished`-tilaan ja `pay_way` on `X402`.
- `PAYMENT-RESPONSE`-vastauksen purkaminen näyttää `success=True` ja `network=base` sekä antaa saman tapahtumahashin.
- BaseScanissa tapahtuman tila on `1`, siirtosumma on `1200000` atomista USDC:tä eli `1.2` USDC:tä.
- Luontihinta `1.26` maksettiin vanhan X402-maksualennuskäytännön aikana, ja lopullinen allekirjoitus- ja selvityssumma on `1.2` USDC:tä.

Jos tilausmaksussa ei ole `Authorization: Bearer {platform_token}` -otsaketta tai tilaus ei kuulu nykyiselle tilille, se epäonnistuu alustan käyttöoikeustasolla; tämä eroaa suoraan kutsuttavasta `x402.acedata.cloud` -tilittömästä X402-API:sta.

## Yleiset virheet

| Ilmiö                                           | Selvityssuunta                                                                |
| -------------------------------------------- | ------------------------------------------------------------------- |
| Ensimmäinen pyyntö ei ole 402                                  | Tarkista, onko `Authorization` vahingossa mukana tai eikö tällä API:lla vielä ole X402-hinnoittelua.                  |
| `No payment requirement for network`         | Kohdeverkko ei ole `accepts`-luettelossa, vaihda verkkoa tai tarkista Gatewayn määritys.                               |
| `invalid_402`                                | 402-vastaus ei ole kelvollista JSONia, tarkista välityspalvelin, yhdyskäytävä tai virhesivu.                                        |
| `Authorization nonce already processed`      | Samaa `PAYMENT-SIGNATURE`-allekirjoitusta on käytetty uudelleen, allekirjoita uudelleen.                                  |
| `invalid_upto_evm_payload_invalid_signature` | Tarkista, että `upto`-kohdan chainId, Permit2 domain, facilitator-osoite ja allekirjoitustili ovat yhtenäiset.         |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Suorita kohdeketjun USDC:lle `approve-permit2`.                                     |
| `Payer has insufficient USDC balance`        | Maksajan lompakossa ei ole riittävästi USDC:tä.                                                       |
| HTTP 200 mutta ei tx hashia                         | `upto`-kohdan todellinen summa voi olla 0, tai settlement-tietuetta kirjoitetaan yhä asynkronisesti.                             |
| Solana `Missing transaction payload`         | `PAYMENT-SIGNATURE`-envelopessa ei ole sarjoitettua tapahtumaa tai signaturea, tarkista wallet adapter. |

## Base `upto` -tarkistuslista

`upto` on tällä hetkellä tarjolla vain Basessa (`eip155:8453`). Koska `upto`-allekirjoitus sitoo enemmän EVM typed data -parametreja, käyttöönotossa tulee erityisesti varmistaa, että 402-vastauksen reaaliaikaiset kentät vastaavat täysin asiakkaan allekirjoitusta.

```text
Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Jos Base `upto` palauttaa `invalid_upto_evm_payload_invalid_signature`, tarkista ensisijaisesti:

1. API:n palauttaman `eip155:8453` + `upto` -merkinnän `extra.chainId` (sen tulisi olla `8453`).
2. API:n palauttama `extra.facilitatorAddress`.
3. `https://facilitator.acedata.cloud/supported`-osoitteen palauttama Base `upto` facilitator -osoite.
4. Permit2 domain, spender, USDC-sopimus ja allekirjoitustili.
5. Onko lompakko jo hyväksynyt Permit2:n Base USDC:lle.

`upto`-allekirjoituksen digest sitoo samanaikaisesti Permit2 domainin, chain ID:n, spenderin, vastaanottajan osoitteen, facilitator-osoitteen ja validAfter-arvon. Jos jokin niistä ei täsmää, Facilitator palauttaa virheellisen signerin, jolloin se palauttaa invalid signature -virheen. Jos nämä kaikki täsmäävät mutta 402 palautuu edelleen, tarkista seuraavaksi Permit2 allowance; ilman valtuutusta palautetaan `PERMIT2_ALLOWANCE_REQUIRED`.

## Vahvistustietojen tallentaminen

Yksi täydellinen vahvistus tallentaa vähintään:

- API-polun ja pyynnön rungon tiivistelmän;
- valitun networkin ja schemen;
- `maxAmountRequired`-arvon;
- payer-lompakon osoitteen;
- HTTP:n lopullisen tilan;
- vastauksen mallin tulosteen tai tehtävän ID:n;
- settlement transaction -linkin;
- Gateway trace ID:n tai alustan käyttötietueen ID:n.

Älä tallenna yksityisiä avaimia, täydellistä `PAYMENT-SIGNATURE`-arvoa, täydellistä EIP-712 signaturea tai palautuslausetta.

## Rakenteiset maksuvirheet

Allekirjoituksen jälkeiset X402-epäonnistumiset palauttavat `extensions.acedatacloud.paymentError`-kohdassa vakaan `code`-arvon, turvalliset interpolointiparametrit, vaiheen ja uudelleenyritysmerkinnän. Käytä ensisijaisesti tätä rakennetta selvitykseen, älä jäsennä ylimmän tason englanninkielistä `error`-arvoa äläkä pyydä käyttäjää toimittamaan lompakon allekirjoitusta tai ketjussa suoritetun simuloinnin alkuperäistä tekstiä.

- `charged: false`: vahvistus hylättiin selvästi ennen selvitystä, eikä tällä kertaa veloitusta aloitettu.
- Ei sisällä `charged`: tulos on tuntematon tai on jo siirtynyt selvitysvaiheeseen, tarkista ensin tilaus ja ketjun tila, suora uudelleenmaksu on kielletty.
- `settlement_pending`: älä maksa uudelleen toistaiseksi, päivitä ensin tilaus tai ota yhteyttä tukeen.
- Tunnistamaton code: käsittele `payment_failed`-tapauksena ja säilytä julkinen tekninen koodi asiakaspalvelun hakua varten.
