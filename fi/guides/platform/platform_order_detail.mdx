Hae tilaus tilauksen ID:n avulla. Tämä päätepiste tukee kahta lukutilaa: anonyymi käyttö palauttaa vain maksusivun tarvitsemat vähimmäiskentät; tilauksen omistaja saa Account Tokenin mukana täydelliset tiedot.

## Rajapinnan yleiskatsaus

| Kohta   | Sisältö                                                        |
| --- | --------------------------------------------------------- |
| Menetelmä  | `GET`                                                     |
| URL | `https://platform.acedata.cloud/api/v1/orders/{order_id}` |
| Todennus  | Valinnainen; anonyymi on vähimmäisprojektio, todennettu omistaja on täydellinen projektio                                    |

`/orders/{id}` ja `/orders/{id}/` ovat tällä hetkellä molemmat käytettävissä. Tilauksen ID on osa maksulinkkiä, ja sitä tulee käsitellä arkaluonteisena läpinäkymättömänä tunnisteena, jota ei saa levittää julkisesti.

## Anonyymi kysely

Maksusivu voidaan lukea suoraan, kun kirjautumistila on kadonnut:

```shell
export ORDER_ID='你的订单 ID'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json'
```

Anonyymi vastaus sisältää vain `id`-, `description`-, `price`-, `state`-, `pay_way`-, `pay_url`-, `expired_at`- ja `created_at`-kentät. Se ei palauta tiliä, Applicationia, Packagea, maksun sisäisiä tunnisteita tai metadataa.

## Todennettu kysely

```shell
export PLATFORM_TOKEN='你的账户令牌'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

Tilauksen omistaja saa täydelliset Order-tiedot, mukaan lukien `application` / `applications`, `package` / `packages`, `bank_details`, `invoice_automation` sekä mallikentät. Jos käyttäjä on todennettu mutta ei ole tilauksen omistaja, palautetaan `403`; pääkäyttäjät ovat poikkeus.

## Keskeiset kentät

| Kenttä            | Kuvaus                                                          |
| ------------- | ----------------------------------------------------------- |
| `state`       | `Pending`, `Paid`, `Finished`, `Expired`, `Failed` tai `Refunded` |
| `pay_way`     | Tilauksen nykyinen maksutapa; kentän nimi ei ole `payment_method`                             |
| `pay_url`     | Isännöidyn maksusivun tai QR-koodin osoite, voi olla tyhjä                                           |
| `price`       | Tilauksen lopullinen maksettava summa; nykyinen tilausmalli ei tarjoa `final_price`-kenttää                         |
| `amount`      | Paketin kiintiömäärä; näkyy vain todennetussa täydellisessä vastauksessa                                            |
| `finished_at` | Tilauksen valmistumisaika; kentän nimi ei ole `paid_at`                                      |

Täydellinen vastaus voi sisältää maksutavan mukaan lisäkenttiä; asiakkaan tulee lukea niitä tarpeen mukaan ja aina välttää arkaluonteisen metadatan tallentamista täydellisestä vastauksesta.

## Virheenkäsittely

- `404`: Tilauksen ID:tä ei ole olemassa.
- `403`: Käyttäjä on kirjautunut sisään, mutta ei ole tilauksen omistaja.
- Anonyymi pyyntö ei palauta `401`: se saa vain vähimmäisjulkisen projektion.

## Laskun hyvitys ja uudelleenhakeminen

Tilauksen nykyinen lasku voidaan lukea pyynnöllä `GET /api/v1/orders/{order_id}/invoice/`. Automaattisen hyvityksen lähettämisen jälkeen lasku on edelleen `Issued`, ja `red_state` ilmaisee hyvityksen etenemisen; onnistunut lähetys ei tarkoita, että hyvitys on valmis. Vahvistusta, hyvityslaskun laatimista tai arkistointia odotettaessa tilaukselle ei voida hakea laskua uudelleen.

Kun ylläpitäjä hakee hyvitystä laskutustietojen, kuten otsikon tai veronumeron, virheen vuoksi, hyvityksen syynä on ”virheellinen laskutus”; tilauksen palautuksen käynnistämä automaattinen hyvitys käyttää edelleen syytä ”palvelun keskeytys”.

Kun hyvityslasku on laadittu ja arkistoitu onnistuneesti, alkuperäinen lasku muuttuu tilaan `Voided`, ja vasta sitten tilaukselle voidaan hakea uudelleen. Alkuperäinen lasku voidaan tarkastella laskuhistoriassa. Jos hyvitys epäonnistuu tai sen tulos odottaa tarkistusta, taloushallinto käsittelee tarkistuksen, eikä tilauksen laskutusrajoitusta poisteta etukäteen. Manuaalisesti laaditut laskut on ensin mitätöitävä tai hyvitettävä vero- tai laskutusjärjestelmässä, minkä jälkeen taloushallinto vahvistaa sen alustalla.
