---
title: "Ace Data Cloud OAuth 2.0:n integrointi"
---

Anna käyttäjien valtuuttaa sovelluksesi käyttämään heidän Ace Data Cloud -profiiliaan, palvelutilauksiaan, API-avaimiaan, käyttöään tai tilauksiaan. Käytä standardia **Authorization Code + S256 PKCE**: sovellus avaa valtuutussivun, käyttäjä hyväksyy ja vastaanottaa kertakäyttöisen `code`-koodin, joka vaihdetaan sitten OAuth access tokeniin.

OAuth access tokenia käytetään tilin resurssirajapintojen käyttämiseen; malli-API:n kutsumiseen käytetään vastaavaa API Key -avainta. OAuth-valtuutus ei luo automaattisesti API Key -avainta, aktivoi palvelua tai lisää saldoa.

## Integrointitavan valitseminen

| Tapa            | Käyttötapaus                                | Valtuutuksen valmistuttua                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Tavallinen OAuth-uudelleenohjaus   | Erilliset verkkosivustot, työpöytä- tai mobiiliasiakkaat; upotettu verkkosivusto käynnistää valtuutuksen itse            | Selain palaa sovelluksen rekisteröimään `redirect_uri`:in, sovellus käsittelee `code`- ja `state`-arvot |
| Studio-verkkosivustokomponentin valtuutus | Verkkosivusto upottaa Studio-aloitussivun ja haluaa käyttää vierailijan nykyistä Studio-tiliä | Studio lähettää sovellukselle viestin valtuutustuloksesta, sovellus ei uudelleenohjaudu ja alkuperäinen sivu säilyy                  |

Tavallinen uudelleenohjaus ei edellytä `embed=studio`-, `embed_origin`- tai `postMessage`-asetusta. Studio-komponenttitilassa isäntä luo valtuutussivun ja ylläpitää viestisiltaa; kolmannet osapuolet integroituvat tämän artikkelin lopussa olevan komponenttiprotokollan mukaisesti eivätkä muodosta näitä kahta parametria itse.

## Päätepisteet ja löytöasiakirja

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Käyttötarkoitus                | Osoite                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Selaimen valtuutussivu            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| OAuth tokenin vaihtaminen／päivittäminen | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Peruutuspyynnön lähettäminen            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Nykyisen käyttäjän tiedot            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| OAuth-sovelluksen hallintasivu      | [OAuth-sovellukset](https://auth.acedata.cloud/user/oauth-apps)                            |
| Kirjautuneen käyttäjän sovellusluettelo／rekisteröintirajapinta   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Valtuutussivun käyttämät julkiset sovellustiedot      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Käyttäjän olemassa olevat API Key -avaimet     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<käyttäjätunnus>&limit=100` |

Sovellusten hallintarajapinta vaatii tilille kirjautumisen todennuksen, eikä se ole anonyymi dynaaminen rekisteröintirajapinta (DCR). MCP-palvelun omat löytö-／rekisteröintiosoitteet ovat eri sisäänkäyntejä kuin tämän taulukon tilin OAuth-päätepisteet; muodosta yhteys tiettyyn MCP:hen kyseisen palvelun dokumentaation ja löytötulosten mukaisesti.

Löytöasiakirjaa käytetään päätepisteiden ja protokollaominaisuuksien hakemiseen. Nykyinen työnkulku palauttaa OAuth tokenin eikä palauta `id_token`-arvoa; älä käsittele sitä täytenä OpenID Connect -kirjautumisvirtana vain siksi, että `openid` scope on olemassa.

## Käyttöoikeusalueet: käytä nykyisiä scope-nimiä

`scope` koostuu välilyönnein erotelluista, kirjainkoon huomioivista käyttöoikeusnimistä. Uudet sovellukset käyttävät tarkkoja käyttöoikeuksia, kuten `profile:read`, `email:read` ja `phone:read`.

### Mistä haettavat käyttöoikeudet saadaan

Kirjautumisen jälkeen OAuth-sovellusluettelon rajapinta `GET /api/v1/oauth2/applications/` palauttaa `available_scopes`; sovelluksen hallintasivun käyttöoikeusvalitsin käyttää samaa luetteloa. Nämä ovat tavallisten itsepalvelusovellusten käytettävissä olevat valinnaiset käyttöoikeusalueet.

**Löytöasiakirjan `scopes_supported` sisältää kaikki alustan tunnistamat käyttöoikeusnimet, mutta ei tarkoita, että sovelluksesi voi pyytää jokaista niistä.** Todellinen valtuutus tarkistaa samanaikaisesti:

1. saako käyttöoikeuden delegoida tälle sovellustyypille;
2. onko käyttöoikeus rekisteröity tämän OAuth-sovelluksen sallittuihin käyttöoikeusalueisiin;
3. omistaako nykyinen käyttäjä pyydetyn käyttöoikeuden.

Tuntemattomat, rekisteröimättömät, delegointiin sopimattomat tai käyttäjältä puuttuvat käyttöoikeudet palauttavat `invalid_scope`. Valtuutuskoodin vaihdon ja päivityksen yhteydessä tarkistus tehdään myös uudelleen; käyttöoikeuksia ei täydennetä tai koroteta automaattisesti.

### Tavallisten itsepalvelusovellusten valinnaiset käyttöoikeudet

Seuraava on nykyinen luettelo (2026-10-09); käytä integroinnissa `available_scopes`-arvoa ensisijaisena lähteenä.

| Scope                                            | Käyttötarkoitus                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Henkilöprofiilin lukeminen／päivittäminen                               |
| `email:read`                                     | Sähköpostiosoitteen lukeminen                                    |
| `phone:read`                                     | Puhelinnumeron ja alueen lukeminen                                |
| `billing-profile:read` / `billing-profile:write` | Laskutusprofiilin lukeminen／hallinta                               |
| `applications:read` / `applications:write`       | Palvelutilausten lukeminen／hallinta                               |
| `credentials:read` / `credentials:write`         | API Key -avainten lukeminen／hallinta                           |
| `usage:read`                                     | Kutsutietueiden lukeminen                                  |
| `orders:read` / `orders:write`                   | Tilausten lukeminen／luominen ja hallinta                              |
| `auto-recharge:read` / `auto-recharge:write`     | Automaattisen latauksen asetusten lukeminen／hallinta                             |
| `recharge-cards:redeem`                          | Latauskorttien lunastaminen                                   |
| `coin:read`                                      | Tokeniin liittyvien tietojen lukeminen                                |
| `distribution:read`                              | Jakelutietojen lukeminen                                  |
| `connections:read` / `connections:write`         | Yhteyksien lukeminen／hallinta                                 |
| `skills:read` / `skills:write`                   | Taitojen lukeminen／hallinta                                 |
| `openid`                                         | Nykyinen toteutus sallii myös perustietojen palauttamisen UserInfosta; ei palauta ID Tokenia    |
| `offline_access`                                 | Pyydä refresh tokenia, jotta access token voidaan päivittää sen vanhennuttua |

Esimerkiksi pelkkään henkilöprofiilin lukemiseen käytetään `profile:read`; lisää `email:read`, jos myös sähköpostiosoite tarvitaan; olemassa olevien API Key -avainten lukemiseen käytetään `profile:read credentials:read`. Pyydä `credentials:write` vain silloin, kun avaimia todella tarvitsee luoda tai muokata, ja lisää `offline_access` vain päivitystä varten.

Jotkin käyttöoikeudet ovat vain alustan hyväksymien luotettujen sovellusten käytettävissä, kuten `sites:read`, `sites:write` ja `platform-tokens:read`; toiset käyttöoikeudet eivät ole tavallisten kolmansien osapuolten OAuth-sovellusten käytettävissä. Asiakastyyppi `public`／`confidential` kuvaa sitä, voidaanko secret säilyttää turvallisesti, eikä sitä, onko sovellus luotettu. Itsepalveluna luodut sovellukset eivät voi ottaa luotettuja käyttöoikeuksia käyttöön itse.

`account` on määritetyn virallisen tilinhallinta-MCP:n käyttämä tilin käyttöoikeusvalitsin, ei kolmannen osapuolen sovelluksen ”kaikki käyttöoikeudet” -scope, eikä sitä voi käyttää yhdessä muiden scopejen kanssa. Kolmansien osapuolten tulee luetella tarvitsemansa tarkat käyttöoikeudet selkeästi.

### Siirtyminen vanhasta dokumentaatiosta

| Vanha kirjoitustapa                                         | Nykyinen tapa                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Luettele tosiasiallisesti tarvittavat tarkat käyttöoikeudet yksitellen; yleistä ”valitse kaikki” -korvaavaa arvoa ei ole |

Vanhoja nimiä ei hyväksytä yhteensopivuusaliaksina. Päivitä samalla OAuth-sovelluksen rekisteröidyt scopet, valtuutus-URL ja oma käyttöoikeuksien tarkistuksesi; sovellusasetusten muuttaminen ei lisää käyttöoikeuksia jo myönnettyihin tokeneihin, vaan käyttäjän on valtuutettava uudelleen.

## Vaihe 1: OAuth-sovelluksen rekisteröinti

Avaa [OAuth-sovellusten hallinta](https://auth.acedata.cloud/user/oauth-apps), luo sovellus ja täytä:
- Nimi, kuvaus, sovelluksen logo: näytetään sovelluksen puolella valtuutussivulla.
- Asiakastyyppi: puhtaasti frontend-, mobiili- tai työpöytäasiakkaat valitsevat **Public**; palvelut, jotka voivat säilyttää secretin backendissä, valitsevat **Confidential**.
- Takaisinkutsuosoite: käytä tuotantoympäristössä HTTPS:ää ja rekisteröi täydellinen URL, jossa sovellus todella käsittelee takaisinkutsun.
- Oikeudet: valitse sivun tarjoamasta luettelosta tosiasiallisesti tarvittavat scopet.

Tallenna `client_id`. Confidential-asiakas säilyttää `client_secret`in palvelinpuolella, eikä sitä saa sijoittaa HTML:ään, frontendin rakennusmuuttujiin tai URL:ään. Public-asiakas ei käytä secretiä tokenin vaihtamiseen; vaikka rekisteröintivastaus sisältäisi kyseisen kentän, sitä ei saa pitää tunnuksena, jonka asiakas voi pitää salassa.

`redirect_uri`n on oltava täsmälleen sama rekisteröinnissä, valtuutuksessa ja tokenia vaihdettaessa, mukaan lukien polku, lopussa oleva kauttaviiva ja kyselyparametrit. Kukin tili voi luoda enintään 20 sovellusta. Secret näytetään vain luotaessa／kierrettäessä; kierrättämisen jälkeen vanhaa secretiä ei voi enää käyttää asiakastodennusta vaativiin vaihtoihin.

## Vaihe 2: painike käynnistää valtuutuksen

Luo jokaisella yhdistämisklikkauksella uusi satunnainen `state` ja `code_verifier`, laske:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Tallenna `state`, verifier ja takaisinkutsuosoite sovelluksen omaan istuntoon ja avaa sitten valtuutussivu URL-koodatuilla parametreilla:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<完整回调地址>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<本次随机值>
  &code_challenge=<本次S256挑战值>
  &code_challenge_method=S256
```

Public-asiakkaiden on lähetettävä S256 PKCE. Vaikka Discovery luettelee edelleen `plain`in, Public-asiakkaat eivät saa käyttää sitä. Confidential-asiakkaillekin suositellaan S256:ta; jos PKCE:tä käytettiin valtuutusta käynnistettäessä, vastaava verifier on toimitettava vaihdon yhteydessä.

Käyttäjän hyväksynnän jälkeen palataan `redirect_uri`in, ja kyselyparametrit sisältävät `code`n ja alkuperäisessä muodossaan palautetun `state`n. Hylättäessä palautetaan `error=access_denied`, virheen kuvaus sekä `state`. Vahvista ennen takaisinkutsun käsittelyä, että state vastaa tämän istunnon arvoa. Valtuutuskoodi on voimassa 10 minuuttia ja sen voi vaihtaa vain kerran; epäonnistumisen jälkeen yhteys on käynnistettävä uudelleen, eikä vanhaa takaisinkutsu-URL:ää pidä päivittää toistuvasti.

## Vaihe 3: OAuth-tokenin vaihtaminen

Public-asiakkaat vaihtavat tokenin suoraan selaimesta tai asiakkaasta; Confidential-asiakkaat vaihtavat sen omassa backendissään. Pyynnön runko tukee lomakekoodausta, ja seuraavat muuttujat edustavat sovelluksen tämän valtuutuksen aikana saamia tietoja:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Confidential-asiakkaiden on lisäksi lisättävä palvelinpuolella `client_secret`-lomakekenttä. Tällä hetkellä tuetaan `client_secret_post`ia; HTTP Basic -asiakastodennusta ei pidä pitää tuettuna tapana.

Lue onnistuneesta vastauksesta `access_token`, `token_type`, `expires_in` ja tosiasiallisesti myönnetty `scope`. `refresh_token` saadaan vain, jos `offline_access` on pyydetty ja myönnetty. OAuth access tokenia ei saa pitää malli-API:n API Keynä, eikä tokenia, verifieriä tai valtuutuskoodia saa kirjoittaa lokeihin, analytiikkatapahtumiin tai jaettuihin linkkeihin.

## Vaihe 4: käyttäjätietojen ja API Keyn lukeminen

Käytä ensin OAuth access tokenia UserInfo-pyyntöön:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Palautettavat kentät riippuvat scopesta: `id` on käyttäjätunniste; `profile:read` tai `openid` mahdollistaa perustietojen lukemisen (kuten `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); sähköposti vaatii `email:read`in, ja puhelinnumero sekä alue vaativat `phone:read`in. Älä oleta, että valtuuttamattomia kenttiä on aina olemassa.

Kun olemassa oleva API Key tarvitaan ja `credentials:read` on myönnetty, käytä UserInfon `id`-arvoa suodatusehtona:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Palautuslista käyttää kenttiä `count` ja `items`, ja Key-kenttä on **`items[*].token`**, ei `data[0].value`. `user_id=me` ei ole tämän rajapinnan kelvollinen käyttäjä-ID. Lue monisivuiset tiedot jatkamalla `offset`／`limit`-arvoilla; älä pidä ensimmäistä sivua kaikkina tunnuksina.

Valitse sovelluksen, palvelun ja voimassaolotilan perusteella soveltuva tunnus; älä ota sokeasti ensimmäistä. Tyhjä lista ei tarkoita, että valtuutus epäonnistui; käyttäjä ei ehkä ole vielä luonut soveltuvaa Keytä. OAuth access tokenin pääsynhallinta sekä API Keyn oma palvelulaajuus, kiintiö ja vanhenemisehdot ovat eri rajoituksia.

**API Keyn lukemisen salliminen tarkoittaa, että kolmas osapuoli voi tallentaa ja käyttää sitä. OAuth-pyynnön peruuttaminen tai sovelluksen kirjautumistilan tyhjentäminen ei mitätöi jo kopioitua API Keytä; käyttäjän on peruutettava tai kierretettävä kyseinen Key erikseen tunnusten hallinnassa.**

## Suoritettava Public / PKCE -selainesimerkki

Ota seuraava sivu käyttöön rekisteröimässäsi `REDIRECT_URI`ssa ja korvaa `CLIENT_ID` sekä takaisinkutsuosoite. Painike käynnistää standardin valtuutuksen, ja samalle sivulle palattaessa luetaan henkilötiedot sekä olemassa olevien Keyjen määrä. Esimerkki ei näytä eikä tallenna pysyvästi Keytä; tuotantosovellus käyttää tuloksia todellisen käyttötarkoituksen mukaisesti. Vahvista ensin erillisellä selainsivulla ja hyväksy sitten myöhempien iframe-vaatimusten mukaisesti.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Yhdistä Ace Data Cloudiin</title>
<button id="connect" type="button">Yhdistä tili</button>
<p id="status" role="status">Ei vielä yhdistetty</p>
<script type="module">
const CLIENT_ID = 'korvaa omalla client_id:lläsi';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`Rajapinta palautti HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = 'Yhdistämistä ei voitu aloittaa. Tarkista selaimen tallennusasetukset ja yritä uudelleen.';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('Valtuutusistunto ei täsmää, yhdistä uudelleen.');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('Valtuutusistunto on vanhentunut, yhdistä uudelleen.');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('Valtuutusta ei suoritettu loppuun, voit yhdistää uudelleen.');
    if (!code) throw new Error('Takaisinkutsusta puuttuu valtuutuskoodi, yhdistä uudelleen.');
    status.textContent = 'Yhdistetään…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('Valtuutustunnusta ei saatu.');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('Käyttäjätunnistetta ei saatu.');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('Tunnisteiden luettelon muoto ei vastaa vaatimuksia.');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `Yhdistetty: ${profile.nickname || profile.username || profile.id}; tällä sivulla on ${keyCount} API-avainta.`;
  } catch (error) {
    status.textContent = `Yhdistämistä ei suoritettu loppuun: ${error.message || 'verkko-ongelma'} Napsauta yhdistämistä uudelleen.`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Esimerkin takaisinkutsun ja aloitussivun on oltava samassa alkuperässä, samassa selainvälilehdessä／iframe:ssa, jotta aiemmin tallennettu `sessionStorage` voidaan lukea. Tuotantosovelluksen tulee hallita tunnuksia omassa istuntojärjestelmässään, käsitellä vanheneminen ja poistaa valtuutus-URL-parametrit vastauksen vastaanottamisen jälkeen; sivun pääkäyttöliittymä tulee renderöidä ensin, ja verkkovirheet saavat vaikuttaa vain yhteystilaan.

## iframe valkoisen etiketin verkkosivustossa

### Asiakkaan verkkosivusto siirtyy itse valtuutussivulle

Käytä tavallisia OAuth-parametreja ja omaa takaisinkutsukäsittelyäsi; `window.location.assign()` navigoi nykyistä iframe:a, ja yläsivu säilyy valkoisen etiketin verkkotunnuksessa. Kuvaketta varten ei tarvitse lisätä `embed=studio`-parametria eikä toteuttaa Studio-viestiprotokollaa.

Seuraavien ehtojen on täytyttävä:

- Sovellussivun ja takaisinkutsusivun on käytettävä HTTPS:ää, niiden on oltava tosiasiallisesti saavutettavissa ja niiden on sallittava valkoisen etiketin ylätason verkkotunnuksen upotus iframe:n kautta; tarkista molempien `Content-Security-Policy: frame-ancestors` ja `X-Frame-Options`.
- sandboxin on sallittava sivun tarvitsemat komentosarjat, lomakkeet ja alkuperä／tallennusominaisuudet. Ponnahdusikkunakirjautumisen tukeminen edellyttää myös vastaavia ponnahdusikkunaominaisuuksia; käytä ensisijaisesti Studion tarjoamaa Website-komponentin määritystä.
- Selaimen on sallittava valtuutustilan vaatima tallennus nykyisessä upotusskenaariossa. Valkoisen etiketin sivuston kirjautumistila ja AuthFrontend-kirjautumistila voivat olla erilaisia, eikä tule olettaa, että valkoisen etiketin sivustolle kirjautuminen tarkoittaa myös valtuutussivulle kirjautumista.
- Takaisinkutsun token-vaihtopalvelun on oltava käytettävissä, ja alkuperien välisten pyyntöjen on sallittava sovelluksen alkuperä; DNS-, CORS- ja HTTP-virheiden yhteydessä on aina näytettävä uudelleenyrityksen mahdollistava tila, eikä koko sivun renderöinti saa pysähtyä.

Valtuutussivun vasen puoli lukee OAuth-sovelluksen Logon; oikea puoli lukee kyseisen Siten faviconin／logon, kun selain voi tarjota ylätason alkuperän ja ylätason verkkotunnus läpäisee vahvistetun sivuston tarkistuksen, muussa tapauksessa näytetään oletuskuvake. Tämä määrittää vain brändin esitystavan, ei luo kirjautumisistuntoa eikä tarjoa asiakkaan sivulle tilioikeuksia.

**Nykyinen rajoitus: kun tavallisessa OAuthissa iframe:n sisällä on kirjauduttava uudelleen, kirjautumisen jälkeen valtuutussivulle palaavan prosessin jatkamisessa on edelleen puute.** Ennen käyttöönottoa on hyväksyttävä erikseen tilanteet ”Auth on kirjautunut sisään” ja ”Auth ei ole kirjautunut sisään／on vanhentunut”. Ennen kuin tämä puute on korjattu ja varmennettu, ensimmäinen kirjautuminen voidaan suorittaa tavallisella OAuthilla erillisellä sivulla tai käyttää alla olevaa Studio-komponentin valtuutusta; älä lupaa, että kaikki iframe-skenaariot toimivat pelkästään kirjautuneiden testitulosten perusteella.

### Valtuuta Studion nykyisellä tilillä

Ota OAuth käyttöön Studiossa kohdassa ”Asetukset → Etusivu → Verkkosivustokomponentit”, ja täytä `client_id` sekä rekisteröity takaisinkutsuosoite. Verkkosivuston ja takaisinkutsun on käytettävä samaa HTTPS-alkuperää, ja niiden on erottava Studion alkuperästä. Kolmannen osapuolen sivun on:

1. Lähetettävä `acedatacloud:oauth:ready` tarkalleen määritetyn yläsivuston originiin sekä vastaanotettava ja validoitava `acedatacloud:oauth:init`.
2. Painikkeen on luotava state ja PKCE verifier sekä lähetettävä `acedatacloud:oauth:authorize` (state, S256 challenge); verifier jää omalle sivulle.
3. Validoitava ylätason ikkuna, origin ja state, käsiteltävä `acedatacloud:oauth:result`-viestin code tai error sekä vaihdettava ne standardin token-päätepisteen kautta.
Studio näyttää valtuutussivun komponenttialueella, ja käyttäjän hyväksynnän jälkeen valtuutuskoodi palautetaan viestinä, joten sovelluksen ei tarvitse uudelleenohjata. Kun kirjautumista ei ole, palautetaan `login_required`, hylättäessä palautetaan `access_denied`, ja odotuksen aikakatkaistuessa palautetaan `authorization_timeout`. Tilin vaihtuminen luo sovelluksen iframe-kehyksen uudelleen ja peruuttaa keskeneräiset valtuutukset.

Komponentti pyytää tällä hetkellä `profile:read credentials:read`, eikä sisällä `offline_access`-oikeutta. Älä oleta, että refresh token voidaan aina vastaanottaa. `embed=studio` ja `embed_origin` ylläpidetään Studio-isännän ja valtuutussivun toimesta, ja asiakassivun tarvitsee vain noudattaa viestiprotokollaa.

Täydellinen painike-esimerkki on kohdassa [Studio-verkkosivustokomponentin OAuth-integrointiopas](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Elinkaari, uudistus ja peruutus

Access tokenin oletusvoimassaoloaika on 15 päivää, ja uudistus tai uusi valtuutus tulee ajoittaa kunkin vastauksen `expires_in`-arvon perusteella; refresh tokenin oletusvoimassaoloaika on 30 päivää, ja sen kesto riippuu palvelun asetuksista. Älä kovakoodaa näitä kahta arvoa pysyviksi lupauksiksi.

Kun `offline_access` on myönnetty, voidaan kutsua:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Uudistus palauttaa uudet tokenit, ja sovelluksen tulee tallentaa uusimmat arvot. Uudistuksen yhteydessä tarkistetaan, onko sovellus edelleen voimassa, onko käyttäjä käytettävissä ja ovatko oikeudet edelleen myönnettyjä. Virhetilanteessa tyhjennä oma yhteystilasi ja valtuuta uudelleen.

**Nykyinen OAuth-uudistustoteutus ei takaa, että vanha refresh token mitätöityy välittömästi uudistuksen jälkeen.** Älä pidä uuden tokenin saamista merkkinä siitä, että vanha token on peruutettu, äläkä korvaa olemassa olevien tokenien lopettamista secretin kierrättämisellä.

Peruutuspyyntö kutsutaan seuraavasti:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Nykyinen peruutuspäätepiste palauttaa HTTP 200:n, mutta se ei toteuta jo myönnettyjen JWT-tokenien välitöntä mitätöintiä.** Sovelluksen tulee tyhjentää itse tallentamansa tokenit, eikä se voi pitää arvoa 200 todisteena siitä, että kaikki myönnetyt tokenit tai API Keyt ovat mitätöityneet. Vuotaneiden tai kopioitujen API Key -avainten osalta vastaavat tunnistetiedot tulee peruuttaa tai kierrättää erikseen.

## Yleiset virheet ja hyväksyntä

| Ilmiö／virhe                         | Vianmääritys                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Käytä nykyisiä oikeusnimiä; tarkista sovelluksen rekisteröidyt laajuudet, delegointirajoitukset ja käyttäjän oikeudet. Discoveryn koko hakemisto ei ole sovelluksen valittavissa oleva hakemisto                      |
| `invalid_request`             | Pakolliset parametrit, tarkka callback-osoite, Public-asiakkaan S256 challenge ja method                        |
| `invalid_client`              | client ID, sovelluksen tila, Confidential-asiakkaan secret; tarkista, ettei Basic-todennusta käytetä virheellisesti             |
| `invalid_grant`               | code on vanhentunut／jo käytetty, verifier tai redirect URI ei täsmää; uudistettaessa tarkistetaan myös sovellus- ja oikeusmuutokset                 |
| `access_denied`               | Käyttäjä hylkäsi pyynnön, palauta yhteyspainike, älä näytä valtuutusta toistuvasti                                                  |
| `unsupported_grant_type`      | Tällä hetkellä tuetaan `authorization_code`- ja `refresh_token`-tyyppejä                             |
| HTTP 401／403                  | Erottele virheellinen kirjautumistila, token, valtuutettu scope ja itse resurssin käyttöoikeudet                                     |
| `Failed to fetch`、DNS／CORS-virheet | Tarkista todellinen pyyntöisäntä ja asiakastaustan käytettävyys, älä selitä niitä sillä, että ”käyttäjällä ei ole Keytä”                                      |
| Valtuutettu, mutta Keytä ei voi lukea                   | Käytä `platform.acedata.cloud`-osoitetta, todellista user ID:tä ja `items[*].token`-arvoa; erottele tyhjä lista, sivutus ja epäonnistuneet vastaukset |
| Koko sivu on tyhjä valtuutuksen palautumisen jälkeen                     | Renderöi sivu ensin; käsittele callbackin, tokenin, UserInfon ja tunnistetietopyyntöjen virheet erikseen; älä anna alustusvirheen pysäyttää koko sivua                      |
| iframe ei jatka kirjautumisen jälkeen                 | Käsittele edellä mainittujen nykyisten rajoitusten mukaisesti; testaa kirjautumattomuus, vanheneminen, hylkäys ja uudelleenyhdistämistilanteet                                          |

Varmista ennen toimitusta vähintään: oikea callback, hylkäys, virheellinen state, vanhentunut／jo käytetty code, ei Keytä, verkkovirhe, tokenin vanheneminen, vaaditun scopen puuttuminen sekä ensimmäinen kirjautuminen ja tilinvaihto iframe-tilanteessa. Älä tallenna testitodisteisiin täydellistä codea, tokenia tai API Keytä.

## Kaksivaiheinen vahvistus ja uudelleenvaltuutus

Kun käyttäjä ottaa kaksivaiheisen vahvistuksen käyttöön, Ace Data Cloud suorittaa valtuutussivulla autentikaattorin vahvistuskoodin tai kertakäyttöisen palautuskoodin tarkistuksen ja toimittaa sen jälkeen valtuutuskoodin. Sovelluksesi jatkaa tavallisen OAuth-prosessin käyttöä eikä sen tule pyytää, tallentaa tai välittää autentikaattorin avaimia tai palautuskoodeja.

Kun käyttäjä ottaa käyttöön, vaihtaa tai poistaa käytöstä kaksivaiheisen vahvistuksen tai palauttaa tilinsä, aiemmat tilisessiot, refresh tokenit ja niihin liittyvät alustan valtuutustokenit voivat mitätöityä. Kun vastaanotetaan virheellinen sessio tai `invalid_grant`, käynnistä käyttäjälle näkyvä valtuutusprosessi uudelleen; älä käytä vanhaa valtuutuskoodia toistuvasti äläkä yritä ohittaa vahvistusta. Tavallisten mallien API Key -avainten todennustapa säilyy muuttumattomana; jos tilin epäillään joutuneen haltuun, tarkista ja peruuta myös asiaankuuluvat API Keyt erikseen.
