---
title: "Ace Data Cloud OAuth 2.0 -yhteyden muodostaminen"
---

Anna käyttäjien valtuuttaa sovelluksesi käyttämään heidän Ace Data Cloud -profiiliaan, palvelutilauksiaan, API-avaimiaan, käyttöään tai tilauksiaan. Käytä standardia **Authorization Code + S256 PKCE**: sovellus avaa valtuutussivun, käyttäjä saa suostumuksen jälkeen kertakäyttöisen `code`-koodin, joka vaihdetaan OAuth access tokeniin.

OAuth access tokenia käytetään tiliresurssien rajapintojen käyttämiseen; mallin API:n kutsumiseen käytetään vastaavaa API-avainta. OAuth-valtuutus ei automaattisesti luo API-avainta, ota palvelua käyttöön tai lisää saldoa.

## Integraatiotavan valitseminen

| Tapa            | Käyttötapaus                                | Valtuutuksen valmistuttua                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Tavallinen OAuth-uudelleenohjaus   | Itsenäinen verkkosivusto, työpöytä- tai mobiiliasiakas; upotettu verkkosivusto käynnistää valtuutuksen itse            | Selain palaa sovelluksen rekisteröimään `redirect_uri`-osoitteeseen, sovellus käsittelee `code`- ja `state`-arvot |
| Studio-verkkosivustokomponentin valtuutus | Verkkosivusto upottaa Studion etusivun ja haluaa käyttää vierailijan nykyistä Studio-tiliä | Studio lähettää sovellukselle viestin valtuutustuloksesta, sovellusta ei uudelleenohjata ja alkuperäinen sivu säilyy                  |

Tavallinen uudelleenohjaus ei edellytä `embed=studio`-, `embed_origin`- tai `postMessage`-asetusta. Studio-komponenttitilassa isäntä luo valtuutussivun ja ylläpitää viestisiltaa; kolmannet osapuolet integroituvat tämän asiakirjan lopussa olevan komponenttiprotokollan mukaisesti eivätkä muodosta näitä kahta parametria itse.

## Päätepisteet ja löytöasiakirja

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Käyttötarkoitus                | Osoite                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Selaimen valtuutussivu            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| OAuth tokenin vaihtaminen／päivittäminen | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Peruutuspyynnön lähettäminen            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Nykyisen käyttäjän tiedot            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| OAuth-sovellusten hallintasivu      | [OAuth-sovellukset](https://auth.acedata.cloud/user/oauth-apps)                            |
| Kirjautuneen käyttäjän sovellusluettelo／rekisteröintirajapinta   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Valtuutussivun käyttämät julkiset sovellustiedot      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Käyttäjän olemassa olevat API-avaimet     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<käyttäjätunnus>&limit=100` |

Sovellusten hallintarajapinta edellyttää tilin kirjautumistodennusta; se ei ole anonyymi dynaamisen rekisteröinnin (DCR) rajapinta. MCP-palvelun omat löytö-/rekisteröintiosoitteet ovat eri sisääntulopisteitä kuin tämän taulukon tilin OAuth-päätepisteet; kun yhdistät tiettyyn MCP:hen, toimi kyseisen palvelun dokumentaation ja löytötulosten mukaisesti.

Löytöasiakirjaa käytetään päätepisteiden ja protokollaominaisuuksien hakemiseen. Nykyinen työnkulku palauttaa OAuth tokenin, ei `id_token`ia; älä käsittele sitä kokonaisena OpenID Connect -kirjautumisvirtana vain siksi, että `openid` scope on olemassa.

## Käyttöoikeusalueet: käytä nykyisiä scope-nimiä

`scope` on välilyönnein eroteltu, kirjainkoon huomioiva käyttöoikeusnimien luettelo. Uudet sovellukset käyttävät tarkkoja oikeuksia, kuten `profile:read`, `email:read` ja `phone:read`.

### Mistä haetaan haettavissa olevat oikeudet

Kirjautumisen jälkeen OAuth-sovellusluettelorajapinta `GET /api/v1/oauth2/applications/` palauttaa `available_scopes`-arvon; sovellusten hallintasivun käyttöoikeusvalitsin käyttää samaa luetteloa. Nämä ovat tavallisten itsepalvelusovellusten käytettävissä olevat valinnaiset alueet.

**Discoveryn `scopes_supported` sisältää kaikki alustan tunnistamat käyttöoikeusnimet, eikä tarkoita, että sovelluksesi voi hakea jokaista niistä.** Todellinen valtuutus tarkistaa samanaikaisesti:

1. onko oikeus sallittu delegoitavaksi kyseiselle sovellustyypille;
2. onko oikeus rekisteröity tämän OAuth-sovelluksen sallittuihin alueisiin;
3. onko nykyisellä käyttäjällä pyydetty oikeus.

Tuntemattomat, rekisteröimättömät, delegointiin kielletyt tai käyttäjältä puuttuvat oikeudet palauttavat `invalid_scope`-virheen. Ne tarkistetaan uudelleen myös valtuutuskoodin vaihdon ja päivityksen yhteydessä; oikeuksia ei täydennetä tai koroteta automaattisesti.

### Tavallisten itsepalvelusovellusten valittavat oikeudet

Seuraava on nykyinen luettelo (2026-10-09); integraatiossa käytä `available_scopes`-arvoa ensisijaisena lähteenä.

| Scope                                            | Käyttötarkoitus                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Profiilin lukeminen／päivittäminen                               |
| `email:read`                                     | Sähköpostiosoitteen lukeminen                                    |
| `phone:read`                                     | Puhelinnumeron ja alueen lukeminen                                |
| `billing-profile:read` / `billing-profile:write` | Laskutusprofiilin lukeminen／hallinta                               |
| `applications:read` / `applications:write`       | Palvelutilausten lukeminen／hallinta                               |
| `credentials:read` / `credentials:write`         | API-avainten lukeminen／hallinta                           |
| `usage:read`                                     | Kutsutietueiden lukeminen                                  |
| `orders:read` / `orders:write`                   | Tilausten lukeminen／luominen ja hallinta                              |
| `auto-recharge:read` / `auto-recharge:write`     | Automaattisen latauksen asetusten lukeminen／hallinta                             |
| `recharge-cards:redeem`                          | Latauskorttien lunastaminen                                   |
| `coin:read`                                      | Kolikoihin liittyvien tietojen lukeminen                                |
| `distribution:read`                              | Jakelutietojen lukeminen                                  |
| `connections:read` / `connections:write`         | Yhteyksien lukeminen／hallinta                                 |
| `skills:read` / `skills:write`                   | Taitojen lukeminen／hallinta                                 |
| `openid`                                         | Nykyinen toteutus sallii myös UserInfon palauttaa perustiedot; ei palauta ID Tokenia    |
| `offline_access`                                 | Refresh tokenin pyytäminen access tokenin vanhennuttua tapahtuvaa päivitystä varten |

Esimerkiksi pelkkään profiilin lukemiseen käytä `profile:read`; lisää `email:read`, jos tarvitset myös sähköpostin; olemassa olevien API-avainten lukemiseen käytä `profile:read credentials:read`. Hae `credentials:write` vain, kun avaimia todella tarvitsee luoda tai muokata, ja lisää `offline_access`, kun tarvitset päivityksen.

Jotkin oikeudet ovat vain alustan hyväksymien luotettujen sovellusten käytössä, esimerkiksi `sites:read`, `sites:write` ja `platform-tokens:read`; jotkin muut oikeudet eivät ole avoinna tavallisille kolmannen osapuolen OAuth-sovelluksille. Asiakastyyppi `public`／`confidential` kuvaa, voidaanko secret säilyttää, eikä sitä, onko sovellus luotettu. Itsepalveluna luodut sovellukset eivät voi ottaa luotettuja oikeuksia käyttöön itse.

`account` on määritetyn virallisen tilinhallinta-MCP:n käyttämä tilioikeuksien valitsin, ei kolmannen osapuolen sovellusten ”kaikkien oikeuksien” scope, eikä sitä voi käyttää yhdessä muiden scopejen kanssa. Kolmansien osapuolten tulee luetella tarvittavat tarkat oikeudet selkeästi.

### Siirtyminen vanhasta dokumentaatiosta

| Vanha kirjoitusasu                                         | Nykyinen tapa                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Luettele todellisuudessa tarvittavat tarkat oikeudet yksitellen; yleistä ”valitse kaikki” -korvaavaa arvoa ei ole |

Vanhoja nimiä ei hyväksytä yhteensopivuusaliaksina. Päivitä samanaikaisesti OAuth-sovelluksen rekisteröidyt scopet, valtuutus-URL ja oma käyttöoikeuksien tarkistuksesi; sovellusmäärityksen muuttaminen ei lisää oikeuksia jo myönnettyihin tokeneihin, vaan käyttäjän on valtuutettava uudelleen.

## Vaihe 1: OAuth-sovelluksen rekisteröinti

Avaa [OAuth-sovellusten hallinta](https://auth.acedata.cloud/user/oauth-apps), luo sovellus ja täytä:
- Nimi, kuvaus, sovelluksen logo: näytetään sovelluksen puolella valtuutussivulla.
- Asiakastyyppi: valitse **Public** puhtaalle frontendille, mobiili- tai työpöytäasiakkaalle; valitse **Confidential** palvelulle, joka voi säilyttää secretin backendissä.
- Takaisinkutsuosoite: käytä tuotantoympäristössä HTTPS:ää ja rekisteröi sovelluksen todellisuudessa takaisinkutsun käsittelevä täydellinen URL.
- Oikeudet: valitse sivun tarjoamasta luettelosta todellisuudessa tarvittavat scopet.

Tallenna `client_id`. Confidential-asiakkaat säilyttävät `client_secret`in palvelinpuolella, eikä sitä saa sijoittaa HTML:ään, frontendin rakennusmuuttujiin tai URL:ään. Public-asiakkaat eivät käytä secretiä tokenin vaihtamiseen; vaikka rekisteröintivastaus sisältäisi kyseisen kentän, sitä ei saa pitää tunnisteena, jonka asiakas voi pitää salassa.

`redirect_uri`n on oltava täsmälleen sama rekisteröinnin, valtuutuksen ja tokenin vaihdon yhteydessä, mukaan lukien polku, lopussa oleva kauttaviiva ja kyselyparametrit. Kukin tili voi luoda enintään 20 sovellusta. Secret näytetään vain luonnin/kierrätyksen yhteydessä; kierrätyksen jälkeen vanhaa secretiä ei voi enää käyttää asiakastodennusta vaativissa vaihdoissa.

## Vaihe 2: Painike käynnistää valtuutuksen

Luo jokaisella yhdistämisklikkauksella uusi satunnainen `state` ja `code_verifier`, laske:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Tallenna `state`, verifier ja takaisinkutsuosoite sovelluksen omaan istuntoon ja avaa sitten valtuutussivu URL-koodatuilla parametreilla:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<完整回调地址>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<本次随机值>
  &code_challenge=<本次S256挑战值>
  &code_challenge_method=S256
```

Public-asiakkaiden on lähetettävä S256 PKCE. Vaikka Discovery luettelee edelleen `plain`in, Public-asiakkaat eivät saa käyttää sitä. S256:ta suositellaan myös Confidential-asiakkaille; jos PKCE:tä käytettiin valtuutusta käynnistettäessä, vastaava verifier on toimitettava vaihdon yhteydessä.

Käyttäjän hyväksynnän jälkeen palataan osoitteeseen `redirect_uri`, ja kyselyparametrit sisältävät `code`n sekä sellaisenaan palautetun `state`n. Hylkäyksen yhteydessä palautetaan `error=access_denied`, virhekuvaus ja `state`. Vahvista ennen takaisinkutsun käsittelyä, että state vastaa tämän istunnon statea. Valtuutuskoodi on voimassa 10 minuuttia, ja se voidaan vaihtaa vain kerran; epäonnistumisen jälkeen yhteys tulee käynnistää uudelleen, eikä vanhaa takaisinkutsu-URL:ää pidä päivittää toistuvasti.

## Vaihe 3: OAuth-tokenin vaihtaminen

Public-asiakkaat vaihtavat sen suoraan selaimesta tai asiakkaasta; Confidential-asiakkaat vaihtavat sen omassa backendissään. Pyynnön runko tukee lomakekoodausta, ja seuraavat muuttujat edustavat sovelluksen tämän valtuutuksen yhteydessä saamia tietoja:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Confidential-asiakkaiden on lisäksi lisättävä `client_secret`-lomakekenttä palvelinpuolella. Tällä hetkellä tuetaan `client_secret_post`ia; älä pidä HTTP Basic -asiakastodennusta tuettuna tapana.

Lue onnistuneesta vastauksesta `access_token`, `token_type`, `expires_in` ja tosiasiallisesti myönnetty `scope`. `refresh_token` saadaan vain, jos `offline_access` on sekä pyydetty että hyväksytty. Älä pidä OAuth access tokenia malli-API:n API Keynä, äläkä kirjoita tokenia, verifieriä tai valtuutuskoodia lokeihin, analytiikkatapahtumiin tai jaettuihin linkkeihin.

## Vaihe 4: Käyttäjätietojen ja API Keyn lukeminen

Käytä ensin OAuth access tokenia UserInfo-pyynnön tekemiseen:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Palautettavat kentät riippuvat scopesta: `id` on käyttäjätunniste; `profile:read` tai `openid` mahdollistaa perustietojen lukemisen (kuten `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); sähköposti vaatii `email:read`in, ja puhelinnumero sekä alue vaativat `phone:read`in. Älä oleta, että valtuuttamattomia kenttiä on aina olemassa.

Kun olemassa oleva API Key tarvitaan ja `credentials:read` on hyväksytty, käytä UserInfon `id`-arvoa suodatusehtona:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Palautuslista käyttää `count`ia ja `items`iä, ja Key-kenttä on **`items[*].token`**, ei `data[0].value`. `user_id=me` ei ole tämän rajapinnan kelvollinen käyttäjä-ID. Lue monisivuiset tiedot edelleen käyttämällä `offset`ia／`limit`iä; älä pidä ensimmäistä sivua kaikkina tunnisteina.

Valitse sovelluksen, palvelun ja voimassaolotilan perusteella soveltuva tunniste; älä valitse sokeasti ensimmäistä. Tyhjä lista ei tarkoita, että valtuutus epäonnistui; käyttäjä ei ehkä ole vielä luonut soveltuvaa Keytä. OAuth access tokenin käyttöoikeuksien hallinta sekä API Keyn oman palvelualueen, kiintiön ja vanhenemisehtojen hallinta ovat eri rajoituksia.

**API Keyn lukemisen salliminen tarkoittaa, että kolmas osapuoli voi tallentaa ja käyttää sitä. OAuth-pyynnön peruuttaminen tai sovelluksen kirjautumistilan tyhjentäminen ei mitätöi jo kopioitua API Keytä; käyttäjän on peruutettava tai kierrettävä kyseinen Key erikseen tunnisteiden hallinnassa.**

## Ajettava Public / PKCE -selainesimerkki

Ota seuraava sivu käyttöön rekisteröimässäsi `REDIRECT_URI`-osoitteessa ja korvaa `CLIENT_ID` sekä takaisinkutsuosoite. Painike käynnistää vakio-valtuutuksen, ja samalle sivulle palattaessa luetaan profiilitiedot sekä olemassa olevien Keyjen määrä. Esimerkki ei näytä eikä tallenna pysyvästi Keytä; tuotantosovellukset käyttävät tuloksia todellisen käyttötarkoituksen mukaisesti. Vahvista ensin erillisessä selainikkunassa, ja hyväksy sitten myöhemmin esitettyjen iframe-vaatimusten mukaisesti.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Yhdistä Ace Data Cloudiin</title>
<button id="connect" type="button">Yhdistä tili</button>
<p id="status" role="status">Ei vielä yhdistetty</p>
<script type="module">
const CLIENT_ID = 'korvaa omalla client_id:lläsi';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`Rajapinta palautti HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = 'Yhteyden muodostamista ei voi aloittaa. Tarkista selaimen tallennusasetukset ja yritä uudelleen.';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('Valtuutusistunto ei täsmää. Yhdistä uudelleen.');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('Valtuutusistunto on vanhentunut. Yhdistä uudelleen.');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('Valtuutusta ei suoritettu loppuun. Voit yhdistää uudelleen.');
    if (!code) throw new Error('Takaisinkutsusta puuttuu valtuutuskoodi. Yhdistä uudelleen.');
    status.textContent = 'Yhdistetään…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('Valtuutustunnusta ei saatu.');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('Käyttäjätunnistetta ei saatu.');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('Tunnistetietoluettelon muoto ei vastaa odotettua.');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `Yhdistetty käyttäjään ${profile.nickname || profile.username || profile.id}; tällä sivulla on ${keyCount} API Key -avainta.`;
  } catch (error) {
    status.textContent = `Yhteyttä ei suoritettu loppuun: ${error.message || 'verkkovirhe'} Napsauta yhdistämistä uudelleen.`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Esimerkin takaisinkutsun ja aloituskohdan on oltava samassa originissa, samassa selaimen välilehdessä／iframe-kehyksessä, jotta aiemmin tallennettu `sessionStorage` voidaan lukea. Tuotantosovelluksen tulee hallita tunnuksia omassa istuntoratkaisussaan, käsitellä vanheneminen ja poistaa valtuutus-URL:n parametrit vastauksen vastaanottamisen jälkeen; sivun pääkäyttöliittymän tulee renderöityä ensin, ja verkkovirheiden tulee vaikuttaa vain yhteystilaan.

## iframe valkoisen etiketin sivustossa

### Asiakkaan sivusto siirtyy itse valtuutussivulle

Käytä tavallisia OAuth-parametreja ja omaa takaisinkutsunkäsittelyäsi; `window.location.assign()` navigoi nykyistä iframe-kehystä, ja yläsivu säilyy valkoisen etiketin verkkotunnuksessa. Kuvaketta varten ei tarvitse lisätä `embed=studio`-parametria eikä toteuttaa Studio-viestiprotokollaa.

Seuraavien ehtojen on täytyttävä:

- Sovellussivun ja takaisinkutsusivun on käytettävä HTTPS:ää, niiden on oltava tosiasiallisesti saavutettavissa ja niiden on sallittava valkoisen etiketin yläverkkotunnuksen upotus iframeen; tarkista molempien `Content-Security-Policy: frame-ancestors` ja `X-Frame-Options`.
- sandboxin on sallittava sivun tarvitsemat komentosarjat, lomakkeet sekä origin-/tallennusominaisuudet. Ponnahdusikkunakirjautumisen tukeminen edellyttää myös vastaavia ponnahdusikkunaominaisuuksia; käytä ensisijaisesti Studion tarjoamaa Website-komponentin määritystä.
- Selaimen on sallittava nykyisessä upotusskenaariossa valtuutustilan edellyttämä tallennus. Valkoisen etiketin sivuston kirjautumistila ja AuthFrontend-kirjautumistila voivat olla erilaisia; ei tule olettaa, että valkoisen etiketin sivustolle kirjautuminen tarkoittaisi myös kirjautumista valtuutussivulle.
- Takaisinkutsun tokeninvaihtopalvelun on oltava käytettävissä, ja eri originin pyyntöjen on sallittava sovelluksen origin; DNS-, CORS- ja HTTP-virheiden on kaikissa tapauksissa näytettävä uudelleenyrityksen mahdollistava tila, eivätkä ne saa estää koko sivun renderöintiä.

Valtuutussivun vasen puoli lukee OAuth-sovelluksen Logon; oikea puoli lukee kyseisen Siten faviconin／logon, kun selain voi tarjota ylätason originin ja yläverkkotunnus läpäisee varmennetun sivuston tarkistuksen, muussa tapauksessa näytetään oletuskuvake. Tämä määrittää vain brändin esitystavan, ei muodosta kirjautumisistuntoa eikä tarjoa tilioikeuksia asiakkaan sivulle.

**Nykyinen rajoitus: kun tavallinen OAuth tarvitsee iframe-kehyksessä uudelleenkirjautumisen, kirjautumisen jälkeen valtuutussivulle palaavassa jatkoprosessissa on edelleen aukko.** Ennen käyttöönottoa on hyväksyttävä erikseen tilanteet ”Auth on kirjautunut sisään” ja ”Auth ei ole kirjautunut sisään／on vanhentunut”. Ennen kuin tämä aukko on korjattu ja varmennettu, ensimmäinen kirjautuminen voi käyttää erillistä sivua tavallisen OAuthin suorittamiseen tai alla olevaa Studio-komponentin valtuutusta; älä lupaa pelkkien kirjautuneiden testitulosten perusteella, että kaikki iframe-skenaariot toimivat.

### Käytä Studion nykyisen tilin valtuutusta

Ota OAuth käyttöön Studiossa kohdassa 「Asetukset → Etusivu → Verkkosivustokomponentit」, ja täytä `client_id` sekä rekisteröity takaisinkutsuosoite. Verkkosivuston ja takaisinkutsun on käytettävä samaa HTTPS-originia, ja niiden on erottava Studio-originista. Kolmannen osapuolen sivun tulee:

1. Lähettää `acedatacloud:oauth:ready` tarkalle yläsivuston originille, vastaanottaa ja validoida `acedatacloud:oauth:init`.
2. Painike luo staten ja PKCE verifierin ja lähettää `acedatacloud:oauth:authorize`-viestin (state, S256 challenge); verifier pysyy omalla sivulla.
3. Validoida ylätason ikkuna, origin ja state, käsitellä `acedatacloud:oauth:result`-viestin code tai error ja vaihtaa se tavallisen token-päätepisteen kautta.
Studio näyttää valtuutussivun komponenttialueella, ja käyttäjän suostumuksen jälkeen palauttaa valtuutuskoodin viestinä, sovelluksen ei tarvitse uudelleenohjata. Kun ei ole kirjauduttu sisään, palautetaan `login_required`, hylättäessä palautetaan `access_denied`, ja odotuksen aikakatkaisu palauttaa `authorization_timeout`. Tilin vaihtuminen luo sovelluksen iframe-kehyksen uudelleen ja peruuttaa keskeneräiset valtuutukset.

Komponentti pyytää tällä hetkellä `profile:read credentials:read`, eikä sisällä `offline_access`-oikeutta. Älä oleta, että refresh token varmasti voidaan vastaanottaa. `embed=studio` ja `embed_origin` ylläpidetään Studio-isännän ja valtuutussivun toimesta, asiakassivun tarvitsee vain noudattaa viestiprotokollaa.

Täydellinen painike-esimerkki löytyy [Studio-verkkosivukomponentin OAuth-integrointioppaasta](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Elinkaari, päivitys ja peruutus

Access tokenin oletusvoimassaoloaika on 15 päivää, ja päivitys tai uudelleenvaltuutus tulee ajoittaa jokaisen vastauksen `expires_in`-arvon perusteella; refresh tokenin oletusvoimassaoloaika on 30 päivää, ja voimassaoloaikaan vaikuttaa palvelun kokoonpano. Älä kovakoodaa näitä kahta arvoa pysyviksi sitoumuksiksi.

Kun `offline_access` on myönnetty, voidaan kutsua:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Päivitys palauttaa uuden tokenin, ja sovelluksen tulee tallentaa uusin arvo. Päivityksen aikana tarkistetaan, onko sovellus edelleen voimassa, onko käyttäjä käytettävissä ja ovatko oikeudet edelleen myönnettyjä. Epäonnistuessa tyhjennä oma yhteystila ja valtuuta uudelleen.

**Nykyinen OAuth-päivitystoteutus ei takaa, että vanha refresh token mitätöityy välittömästi päivityksen jälkeen.** Älä pidä uuden tokenin saamista merkkinä siitä, että vanha token on peruutettu, äläkä korvaa olemassa olevien tokenien lopettamista secretin kierrolla.

Peruutuspyyntö kutsutaan näin:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Nykyinen peruutuspäätepiste palauttaa HTTP 200:n, mutta ei toteuta jo myönnettyjen JWT:iden välitöntä mitätöintiä.** Sovelluksen tulee tyhjentää itse tallentamansa tokenit, eikä 200-vastausta saa pitää todisteena siitä, että kaikki myönnetyt tokenit tai API Keyt ovat mitätöityneet. Vuotaneiden tai kopioitujen API Key -avainten tapauksessa vastaavat tunnistetiedot tulee peruuttaa tai kierrättää erikseen.

## Yleiset virheet ja hyväksyntä

| Ilmiö／virhe                         | Selvitys                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Käytä nykyisiä käyttöoikeusnimiä; tarkista sovelluksen rekisteröidyt alueet, delegointirajoitukset ja käyttäjän oikeudet. Discoveryn koko hakemisto ei ole sovelluksen valittavissa oleva hakemisto                      |
| `invalid_request`             | Pakolliset parametrit, tarkka callback-osoite, Public-asiakkaan S256 challenge ja method                        |
| `invalid_client`              | client ID, sovelluksen tila, Confidential-asiakkaan secret; tarkista, ettei Basic-autentikointia käytetä virheellisesti             |
| `invalid_grant`               | code on vanhentunut／jo käytetty, verifier tai redirect URI ei täsmää; päivityksessä tarkistetaan myös sovelluksen ja oikeuksien muutokset                 |
| `access_denied`               | Käyttäjä hylkäsi pyynnön, palauta yhteyspainike, älä näytä valtuutuspyyntöä toistuvasti                                                  |
| `unsupported_grant_type`      | Tällä hetkellä tuetaan `authorization_code`- ja `refresh_token`-tyyppejä                             |
| HTTP 401／403                  | Erottele virheellinen kirjautumistila, token, valtuutuksen scope ja itse resurssin käyttöoikeudet                                     |
| `Failed to fetch`, DNS／CORS-virhe | Tarkista todellinen pyyntöisäntä ja asiakastaustan käytettävyys, älä selitä sitä sillä, että ”käyttäjällä ei ole Keytä”                                      |
| Valtuutettu, mutta Keytä ei voi lukea                   | Käytä `platform.acedata.cloud`-osoitetta, todellista user ID:tä ja `items[*].token`-arvoa; erottele tyhjä lista, sivutus ja epäonnistuneet vastaukset |
| Koko sivu on tyhjä valtuutuksen palautuksen jälkeen                     | Renderöi sivu ensin; käsittele callbackin, tokenin, UserInfon ja tunnistepyyntöjen virheet erikseen; älä anna alustuksen poikkeuksen pysäyttää koko sivua                      |
| iframe ei jatka kirjautumisen jälkeen                 | Käsittele yllä mainittujen nykyisten rajoitusten mukaisesti, testaa tilanteet ilman kirjautumista, vanhentuneella istunnolla, hylkäyksellä ja uudelleenyhdistämisellä                                          |

Varmista ennen toimitusta vähintään: oikea callback, hylkäys, virheellinen state, vanhentunut／jo käytetty code, ei Keytä, verkkovirhe, tokenin vanheneminen, vaaditun scopen puuttuminen sekä iframe-tilanteessa ensimmäinen kirjautuminen ja tilin vaihtaminen. Älä tallenna testinäyttöön täydellisiä codeja, tokeneita tai API Key -avaimia.
