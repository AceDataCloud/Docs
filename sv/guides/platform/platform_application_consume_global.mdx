---
title: "Konfigurera global saldodelning för AceDataCloud Application"
description: "Platform API guide - Ace Data Cloud"
---

Konfigurera `allow_consume_global`. När det är aktiverat kan kvalificerade användningsbaserade Application fortsätta använda kontots globala saldo när deras egna saldo är otillräckligt.

## Förberedelser

- Skapa och spara säkert en [Account Token](https://platform.acedata.cloud/documents/platform-token).
- Hämta det `application_id` som du äger från [listan över tjänsteansökningar](https://platform.acedata.cloud/documents/platform-application-list).

```shell
export PLATFORM_TOKEN='din kontotoken'
export APPLICATION_ID='ditt Application-ID'
```

## API-översikt

| Post    | Innehåll                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------- |
| Metod   | `POST`                                                                                             |
| URL  | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| Autentisering   | Account Token                                                                                      |
| Body | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

Vid lyckat resultat returneras det uppdaterade Application-objektet. Använd `allow_consume_global` i svaret som källa, i stället för att anta att det begärda värdet alltid sparas.

> Application av typen `Period` får inte förbruka globalt saldo. Även om `true` begärs kommer servern att behålla detta fält som `false`.

## Felhantering

- `401`: Account Token är ogiltig eller saknas.
- `403`: Det aktuella kontot är inte ägare till denna Application.
- `404`: Application-ID:t finns inte.

För påfyllning av globalt saldo och tillgängliga paket gäller plattformskonsolen och de faktiska paket som returneras av [orderskapande](https://platform.acedata.cloud/documents/platform-order-create); anta inte att det finns paket av typen `Wallet`.

## Applikationer med godkänd övertrassering

När det skrivskyddade fältet `allow_overdraft=true` för en användningsbaserad applikation är satt kan applikationen fortsätta dra avgifter från sitt eget saldo, även om saldot blir negativt, och växlar inte till det globala kontot på grund av otillräckligt saldo. Applikationer utan aktiverad övertrassering följer fortfarande `allow_consume_global`; om övertrassering tillåts efter växlingen beror på inställningen för den globala Application som faktiskt debiteras.

## Begränsning av samtidighet för testkonton

Systemet använder den skrivskyddade användarmarkeringen `has_recharged` för att registrera om en betald påfyllning har slutförts framgångsrikt eller om administratören manuellt har lagt till krediter. Markeringen uppdateras efter att åtgärden har lyckats, och historiska användare kompletteras enhetligt utifrån order eller tydliga register över tillagda krediter. För konton som varken har gjort en betald påfyllning eller fått krediter manuellt tillagda av en administratör får endast en fakturerbar begäran i hela kontot köras samtidigt; olika API Keys och olika tjänster delar denna enda plats. Belöningar, inlösenkort och överförda krediter räknas inte som betald påfyllning. Konton som redan har slutfört en betald påfyllning eller fått krediter manuellt tillagda av en administratör omfattas inte av denna begränsning av samtidighet för testversioner, utan följer fortfarande de ursprungliga kontrollerna av saldo och autentiseringsuppgiftskvoter.

När en befintlig begäran körs returnerar en ny begäran `429 too_many_requests`. Kostnadsfria polling-API:er, såsom uppgiftsfrågor, kan fortfarande anropas normalt. Realtimes anslutningsautentisering fortsätter att använda det ursprungliga debiteringsflödet per omgång och upptar inte denna plats för vanliga begäranden.

När asynkrona API:er returnerar ”mottagen” körs uppgiften fortfarande, och du måste vänta på slutresultatet innan du skickar nästa genereringsbegäran. Nätverksavbrott eller proxy-timeout innebär inte att uppgiften har stoppats; om uppgiften saknar slutstatus under en längre tid, ange `trace_id` och kontakta supporten för kontroll.

Denna begränsning ändrar inte vilka API:er som kan testas och ändrar inte heller de ursprungliga debiteringsreglerna. Avgifter regleras fortfarande efter att begäran har avslutats baserat på faktisk användning.
