[X402](https://www.x402.org/) är ett betalningsprotokoll på kedjan för ”debitering via HTTP 402” som föreslagits av Coinbase: servern returnerar `402 Payment Required` för förfrågningar utan token och bifogar fältet `accepts: [...]` som listar accepterade kedjor / tillgångar / priser; klienten signerar lokalt en auktorisering (Permit2 / EIP-712 på EVM, SPL token transfer-auktorisering på Solana), lägger det base64-kodade envelopet i `PAYMENT-SIGNATURE`-huvudet och skickar förfrågan igen. Efter verifiering genomför servern den faktiska avräkningen på kedjan och returnerar sedan affärsresultatet.

> Ace Data Clouds X402-klient anropar mål-API:t direkt och använder det `402 Payment Required` och `accepts` som returneras i realtid av den förfrågan som grund för pris och signering. Facilitators betalningskapacitet kan verifieras på [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

Både `@acedatacloud/sdk` och `acedatacloud` exponerar en `paymentHandler`-hook: när en förfrågan som SDK:t självt skickar får `402`, anropas handlern du injicerat för att hämta `PAYMENT-SIGNATURE`-huvudet, och den ursprungliga förfrågan skickas sedan igen. Kombinera `@acedatacloud/x402-client` / `acedatacloud-x402` med SDK:t, så blir **hela flödet helt transparent för affärskoden**——du använder bara `client.openai.chat.completions.create(...)`, vilket ser exakt likadant ut som token-läget, men under ytan betalar du per anrop utan att behöva fylla på i förväg.

Denna artikel:

- kopplar ihop hela kedjan med ”ingen token + X402 handler-injektion” på TS-sidan ([T12-verifiering](#fyra-verifiering-vid-verklig-körning))
- listar skillnaderna mellan de två signeringskedjorna EVM / Solana
- ger tre anpassningar: `viem`-privatnyckelläge, webbläsarplånboksläge och Python `EVMAccountSigner`-läge
- förklarar det lättproblematiska fältet `preferScheme` / `prefer_scheme`

## I. Protokollöversikt (måste läsas)

Ett lyckat X402-anrop omfattar **3 HTTP RTT**:

```text
1. SDK -> /openai/v1/chat/completions               (无 Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK 内部 -> paymentHandler({ url, method, body, accepts })   (本地签名，0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (PAYMENT-SIGNATURE 头注入)
   <- 200 + business response   (结算在服务端完成)
```

X402-envelopet är en JSON-sträng som base64-kodas och placeras i `PAYMENT-SIGNATURE`-huvudet. Struktur (utdrag):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

Envelopets toppnivå är `x402Version: 2`, och objektet `accepted` används för att deklarera den `scheme` och `network` (CAIP-2-identifierare) som valts denna gång.

| scheme  | Betydelse                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Fast pris (prissatta scenarier som bild- / videogenerering och sökning). Det signerade beloppet = beloppet som servern kräver.                                                         |
| `upto`  | Mätbaserad debitering (chat completions / token-typer). Signerar ett **maximalt** belopp, och endast den del som faktiskt används regleras (baserat på Permit2 + witness). **Rekommenderas starkt** för API:er av sessionstyp. |

`preferScheme` / `prefer_scheme` används för att välja preferens när servern **samtidigt erbjuder flera scheme**. Om servern endast exponerar `exact` ignoreras detta fält; om `upto` anges men servern inte exponerar det, återgår den till den första matchningen.

## II. TypeScript: två användningssätt för webbläsarplånbok + viem på servern

### Installation

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Testade versionsnummer:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Fullständig signatur för `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' 必填
  evmProvider?: EVMProvider;                // network='base' 必填，EIP-1193
  evmAddress?: string;                      // network='base' 必填
  preferScheme?: 'exact' | 'upto';
}
```

Returvärdet är en `(ctx) => Promise&lt;{ headers: Record<string, string> }>` som exakt matchar SDK:ts `paymentHandler`-hook-signatur.

### Användning 1: webbläsare (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. 让用户连钱包
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. 切到 Base 主网
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. 构造 SDK 客户端，注入 X402 handler
//    注意：不传 apiToken，让 SDK 走 402 路径
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat 类必选 upto
  })
});

// 4. 正常调
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Vid första anropet visar webbläsaren **två signeringsuppmaningar**: den första är ett engångsgodkännande av Permit2 för USDC (beloppet är `MaxUint256`, vilket skrivs till kedjan); den andra är EIP-712-signaturen för X402-envelopet (skrivs inte till kedjan, utan endast för facilitators verifiering). Efterföljande anrop behöver bara den andra signaturen, och upplevelsen blir ”klicka en gång för att signera → få resultatet”.

### Användning 2: Node-server + viem-privatnyckel (lämpligt för backend / CLI)

`@acedatacloud/x402-client` accepterar på TS-sidan **endast EIP-1193 provider**——den hanterar inte privatnycklar direkt. I Node / CLI-scenarier är standardmetoden att använda [`viem`](https://viem.sh/) för att paketera privatnyckeln som en `WalletClient`, och sedan använda [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) eller viems interna EIP-1193-anpassning.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient 自带 EIP-1193 兼容的 .request()，可以直接当 evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request 满足 EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Om du tycker att viems EIP-1193-anpassning inte är tillräckligt stabil kan du också använda den mer lågnivåbaserade [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts), och själv koppla ihop vägen `accepts → signed envelope → PAYMENT-SIGNATURE header`, för att hoppa över SDK-kroken; men det rekommenderas fortfarande att i första hand välja `createX402PaymentHandler`, så att du slipper underhålla protokolluppgraderingar själv.

### Användning 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

På Solana-kedjan exponeras för närvarande **endast `exact` scheme**, så `preferScheme` har ingen effekt på Solana.

## III. Python: privat nyckel-läge

Pythons `acedatacloud-x402` använder vägen med **direkt signering med privat nyckel** (utan EIP-1193-abstraktion), vilket passar bättre för servrar / uppgiftskörningar.

### Installation

```bash
pip install acedatacloud acedatacloud-x402
```

Testade versionsnummer:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. 从私钥构造签名器
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. 构造 SDK：不传 api_token，让 SDK 走 402 路径
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # chat 类一定选 upto
    )
)

# 3. 正常调
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # 可选
    )
)
```

### Engångs-approve (endast första gången på EVM)

På EVM Base använder X402 Permit2, vilket kräver att plånboken utför en `MaxUint256`-approve till Permit2-kontraktet för USDC en gång. `acedatacloud-x402` har inbyggd `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Den här transaktionen behöver bara skickas en gång, och därefter använder alla X402 EVM-betalningar denna auktorisering. Solana behöver inte det.

## IV. Verifiering av faktisk körning

Testmål: **TS SDK skickar inte token, injicerar X402 handler och kan normalt konstruera och initiera begäranden** (en lättviktsverifiering som inte förbrukar verklig USDC på kedjan).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // 占位 provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Utdata:

```text
handler_type function
client_ctor_ok AceDataCloud
```

Resultatet visar:

- Ingen `apiToken` skickades, och SDK-konstruktionen ger **inget fel**, vilket bevisar att X402-läget verkligen är ett giltigt alternativ till token.
- `createX402PaymentHandler` returnerar en funktion (en hook), som SDK:t först anropar när det tar emot 402.
- Ett end-to-end-test där faktisk betalning på kedjan fungerar har inte inkluderats i den här handledningen, eftersom det innebär verkliga USDC-dragningar; du kan hänvisa till e2e-exemplet i [X402-integrationsguiden](https://platform.acedata.cloud/documents/x402-integration).

> Pythons `create_x402_payment_handler` har också genomgått samma verifiering —— funktionens returvärde är callable, och konstruktionen `AceDataCloud(...)` ger inget fel när `payment_handler=...` injiceras. Semantiken är anpassad på båda sidor.

## V. Jämförelse med ”Bearer token-läget”

| Dimension              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Användningsscenario            | Egen backend, långsiktiga projekt                                                         | Tredjepartsutvecklare, betalning per gång vid behov, Agentic-anrop                        |
| Registrering              | Kräver ansökan i [konsolen](https://platform.acedata.cloud/console/applications) | Behövs inte; det räcker med en plånbok på kedjan                                     |
| Faktureringsprecision            | Förhandsinsättning, debitering enligt token-tabell                                                   | I realtid på kedjan per anrop                                         |
| Saldo              | Kan visas i konsolen                                                           | Kontrollera USDC i plånboken på kedjan                                      |
| Första kostnad            | Gratis kvot ges vid e-postregistrering                                                        | Kräver bryggning av USDC till Base, första Permit2 approve              |
| Lämplig för chat-typer       | ✅                                                                 | ✅（måste använda `preferScheme=upto`）                       |
| Lämplig för engångsbetalning / betalning för flera konton | ❌                                                                 | ✅                                               |
| Kodändring            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
De två lägena kan samexistera — i samma process räcker det att konfigurera olika autentiseringssätt för olika `client`-instanser.

## VI. Vanliga fallgropar

1. **chat-klassen måste använda `preferScheme=upto`**: Om du använder `exact` kommer facilitator att dra USDC enligt `maxAmountRequired` (inte den faktiska användningen).
2. **Skicka inte en rå privat nyckel till `createX402PaymentHandler` på Node-sidan**: TS-paketet accepterar inte `{ privateKey }`, utan måste kapslas som en EIP-1193-provider (viem `WalletClient` rekommenderas).
3. **Det första anropet innebär dubbla signaturer**: Först signeras Permit2 approve (on-chain, kräver gas), sedan signeras X402 envelope (inte on-chain). Efterföljande anrop har bara den andra signaturen kvar.
4. **Solana har inget Permit2-koncept**: Signera direkt SPL token transfer-auktorisering, ingen approve behövs; men för närvarande stöder Solana-kedjan endast `exact`.
5. **Skilj mellan affärsfel och betalningsfel**: 402 → handler-fel kastar `X402SignError` (den specifika typen varierar beroende på kedja); efterföljande affärsgränssnittsfel efter återförsök (401 / 422 / 5xx) klassificeras fortfarande som vanliga SDK-undantag.
6. **Det mest stabila sättet att anpassa `viem`**: `evmProvider: walletClient as any` förlorar typkontroll men har bäst kompatibilitet; om du vill behålla typer, kapsla viems `.transport.request` separat i ett `{ request }`-objekt och skicka in det.
