Utöver att betala direkt per API-begäran stöder Ace Data Cloud även betalning av konsolordrar med X402. Kärnprotokollet för orderbetalning och API-anrop är detsamma: den första begäran returnerar 402, klienten signerar `PAYMENT-SIGNATURE` och försöker sedan igen med samma begäran.

Skillnaden är att orderbetalning är ett plattforms-API och kräver en kontotoken; medan AI-API:et som direkt anropar `x402.acedata.cloud` endast kan använda X402 och inte kräver någon API-token.

## Förbered ordern

Gå till [Ace Data Cloud-konsolen](https://platform.acedata.cloud/console/orders), välj ordern som behöver betalas och notera order-ID:t.

Om du ännu inte har någon order kan du skapa en obetald order på paketsidan. Orderpriset baseras på vad som visas på sidan, och `amount` i X402 402-svaret är den slutliga grunden för signering.

## Skapa kontotoken

Orderbetalningsbegäran kräver en kontotoken. Öppna [plattformens tokensida](https://platform.acedata.cloud/console/platform-tokens) och skapa en token i formatet `platform-v1-...`.

Efterföljande begäranden använder:

```http
Authorization: Bearer {platform_token}
```

Kontotoken skiljer sig från en vanlig API-token. Vanliga API-token används för att förbruka API-kvoter; kontotoken används för att representera ditt konto vid hantering av plattformsresurser, till exempel orderbetalning.

## Utlös 402

Skicka först en begäran utan `PAYMENT-SIGNATURE`:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

Statusen som returneras är 402, och svaret innehåller `accepts`:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

Orderbetalning använder officiella x402 v2: `x402Version` är `2`, `network` använder CAIP-2-identifierare och beloppsfältet är `amount`.

Resultatförklaring:

- När ordern har skapats är statusen `Pending`, och det har ännu inte skett någon betalning på kedjan.
- Den första `pay/`-begäran innehåller inte `PAYMENT-SIGNATURE`, och därför returneras HTTP 402.
- `accepts` anger samtidigt Base `exact` och Solana `exact`; den här guiden väljer Base i följande steg.
- Priset när ordern skapades var `1.26`; vid betalning under den gamla rabattpolicyn för X402-betalning var det faktiska signerade och avräknade beloppet `1.2` USDC, vilket motsvarar `1200000` atomic USDC.

Observera att `resource` här är ett fält som returneras av servern och deltar i signeringen. Klienten får inte själv ändra protokollet, sökvägen eller order-ID:t i det.

## Signera och försök igen

Orderbetalning kan återanvända lågnivåsigneringsfunktionerna från `@acedatacloud/x402-client` eller `acedatacloud-x402`. Nedan följer ett TypeScript-exempel:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

Förklaring av resultatet:

- `status 200` innebär att plattformens betalningsgränssnitt för order accepterade denna `PAYMENT-SIGNATURE`.

- Händelsen `Transfer` på BaseScan visar att betalningsadressen överförde `1200000` atomic USDC till plattformens mottagaradress, det vill säga `1.2` USDC.

## Lyckat svar och kvitto

När orderbetalningen har lyckats är svarskroppen orderinformation. Plattformen inkluderar även ett Base64-kodat settlement response i svarshuvudet `PAYMENT-RESPONSE`; vanliga fält efter avkodning inkluderar:

| Fält            | Beskrivning                           |
| ------------- | ---------------------------- |
| `success`     | Om Facilitator settlement lyckades. |
| `transaction` | Transaktionshash för avveckling på kedjan.                    |
| `network`     | Betalningsnätverk.                        |
| `payer`       | Betalande plånboksadress.                      |
| `amount`      | Faktiskt avvecklat belopp, med atomic units.      |

Om du behöver stämma av rekommenderas det att samtidigt spara order-ID, betalande plånboksadress, `transaction` och orderns slutliga status.

## Observera

- Orderbetalning kräver en plattformskontotoken och kan inte slutföras enbart med X402-plånbokssignatur.
- `amount` använder USDC atomic units, `1200000` innebär `1.2` USDC.
- Sätt inte själv ihop mottagaradressen eller tillgångsadressen; använd `accepts` i 402-svaret som referens.
- Om samma `PAYMENT-SIGNATURE` skickas in upprepade gånger utför Facilitator uppspelningsskydd baserat på nonce.

## Svar vid betalningsfel

Den första HTTP 402 utan `PAYMENT-SIGNATURE` är en normal betalningsutmaning och innebär inte att betalningen har misslyckats. Verifierings- eller avvecklingsfel efter signering behåller fortfarande standardsträngen `error` som en kompatibilitetsreserv och returnerar en stabil felstruktur i `extensions.acedatacloud.paymentError`:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

Klienten bör i första hand lokalisera enligt `code`; okända code ska falla tillbaka till generellt betalningsfel. `charged` är ett trestatusfält: endast när betalningen uttryckligen nekas före avveckling returneras `false`; om fältet saknas innebär det att debiteringsstatusen är okänd och får inte tolkas som ”inte debiterad”. När den aktuella ordern har gått till `Failed` kan samma order inte försöka igen; skapa en ny order efter att plånboksproblemet har korrigerats.

`metadata.x402.last_error` och `metadata.x402.errors` i orderlistan och orderdetaljerna behåller samma uppsättning av `code`, `stage`, `retryable`, `charged` och `params`; offentlig förklaringstext sparas i `reason`, och tidpunkten sparas i `timestamp`. Till exempel innebär `insufficient_token_balance` otillräckligt USDC-saldo på det valda nätverket, medan `invalid_signature` innebär att betalningssignaturen är ogiltig; att läsa ordern igen ändrar dem inte till det generella `payment_failed`.

Logga eller skicka inte in fullständig `PAYMENT-SIGNATURE`, plånbokssignaturer, auktoriserings-payload, Facilitators ursprungliga diagnostik eller RPC-svar. Kundtjänstens felsökning behöver endast order-ID och den offentliga felkoden `code`.

## ACE-återköp och förbränning för Base- och Solana-betalningar

Efter att återköpsstrategin har aktiverats används 3 % av det faktiskt mottagna beloppet från berättigad Circle USDC på Base-huvudnätet och USDC på Solana-huvudnätet för att köpa och bränna ACE, utan någon extra debitering av den betalande plånboken. Avsättning görs en gång vid påfyllning; efterföljande API-anrop med dessa Credits avsätts inte igen; historiska rabattordrar och order med gamla strategier får inte automatiskt någon retroaktiv avsättning.

Base-betalningar behåller betalningskvittot på Base-kedjan, medan ACE-köp och förbränning utförs asynkront på Solana. Objektet `ace_burn` i orderdetaljerna tillhandahåller `settlement_network`, `settlement_transaction` och `execution_network`, och tillhandahåller efter slutförandet `swap_signature` och `burn_signature`. `Pending` eller `Processing` innebär inte att förbränningen har utförts; endast `Completed` innebär att det slutliga beviset på kedjan har kontrollerats. När Base-betalningen ännu inte har nått slutlig bekräftelse väntar återköpet på bekräftelse, men detta påverkar inte redan mottagna Credits.
