---
title: "Integrera Ace Data Cloud OAuth 2.0"
---

Låt användare ge din applikation behörighet att komma åt deras Ace Data Cloud-profil, tjänsteprenumerationer, API Key, användning eller beställningar. Använd standard **Authorization Code + S256 PKCE**: applikationen öppnar auktoriseringssidan, användaren samtycker och får sedan en engångs-`code`, som därefter byts mot en OAuth access token.

OAuth access token används för att komma åt kontoresursgränssnitt; för att anropa modell-API:er används motsvarande API Key. OAuth-auktorisering skapar inte automatiskt API Key, aktiverar tjänster eller ökar saldo.

## Välj integrationsmetod

| Metod            | Användningsfall                                | Efter att auktoriseringen har slutförts                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Standard OAuth-omdirigering   | Fristående webbplatser, skrivbords- eller mobilklienter; inbäddade webbplatser initierar auktorisering själva            | Webbläsaren återgår till applikationens registrerade `redirect_uri`, och applikationen hanterar `code` och `state` |
| Studio-webbplatskomponentauktorisering | Webbplatsen bäddar in Studio-startsidan och vill använda besökarens aktuella Studio-konto | Studio skickar ett meddelande med auktoriseringsresultatet till applikationen, applikationen omdirigeras inte och den ursprungliga sidan behålls                  |

Standardomdirigering kräver inte `embed=studio`, `embed_origin` eller `postMessage`. Studio-komponentläget skapar auktoriseringssidan och upprätthåller meddelandebryggan via värden; tredje parter integrerar enligt komponentprotokollet i slutet av denna text och ska inte själva sammanfoga dessa två parametrar.

## Slutpunkter och upptäcktsdokument

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Syfte                | Adress                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Auktoriseringssida i webbläsaren            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| Byta／förnya OAuth token | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Skicka återkallelsebegäran            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Information om aktuell användare            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| Administrationssida för OAuth-applikationer      | [OAuth-applikationer](https://auth.acedata.cloud/user/oauth-apps)                            |
| Applikationslista／registreringsgränssnitt för inloggade användare   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Offentlig applikationsinformation som används av auktoriseringssidan      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Användarens befintliga API Key     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<användar-ID>&limit=100` |

Applikationshanteringsgränssnittet kräver kontoinloggningsautentisering och är inte ett gränssnitt för anonym dynamisk registrering (DCR). MCP-tjänstens egna upptäckts-/registreringsadresser är separata ingångar från kontots OAuth-slutpunkter i denna tabell; följ dokumentationen och upptäcktsresultaten för den specifika MCP-tjänsten vid anslutning.

Upptäcktsdokumentet används för att hämta slutpunkter och protokollfunktioner. Det aktuella flödet returnerar OAuth token, inte `id_token`; hantera inte detta som ett fullständigt OpenID Connect-inloggningsflöde enbart eftersom scopet `openid` finns.

## Behörighetsomfång: använd aktuella scope-namn

`scope` är ett mellanslagsseparerat, skiftlägeskänsligt behörighetsnamn. Nya applikationer använder specifika behörigheter som `profile:read`, `email:read`, `phone:read` och så vidare.

### Var du hämtar behörigheter som kan begäras

Efter inloggning returnerar OAuth-applikationslistans gränssnitt `GET /api/v1/oauth2/applications/` `available_scopes`; behörighetsväljaren på applikationshanteringssidan använder samma katalog. Detta är de valbara omfång som vanliga självbetjäningsapplikationer ska använda.

**Discoverys `scopes_supported` innehåller alla behörighetsnamn som identifieras av plattformen, men innebär inte att din applikation kan begära vart och ett av dem.** Faktisk auktorisering kontrollerar samtidigt:

1. om behörigheten får delegeras till denna applikationstyp;
2. om behörigheten har registrerats inom de tillåtna omfången för denna OAuth-applikation;
3. om den aktuella användaren har den begärda behörigheten.

Okända, oregistrerade, ej tillåtna att delegera eller behörigheter som användaren saknar returnerar `invalid_scope`. Vid utbyte och förnyelse av auktoriseringskod kontrolleras behörigheter också på nytt; behörigheter kompletteras eller höjs inte automatiskt.

### Valbara behörigheter för vanliga självbetjäningsapplikationer

Följande är den aktuella katalogen (2026-10-09); använd `available_scopes` vid integrering.

| Scope                                            | Syfte                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Läsa／uppdatera profil                               |
| `email:read`                                     | Läsa e-post                                    |
| `phone:read`                                     | Läsa mobilnummer och region                                |
| `billing-profile:read` / `billing-profile:write` | Läsa／hantera faktureringsuppgifter                               |
| `applications:read` / `applications:write`       | Läsa／hantera tjänsteprenumerationer                               |
| `credentials:read` / `credentials:write`         | Läsa／hantera API Key                           |
| `usage:read`                                     | Läsa anropshistorik                                  |
| `orders:read` / `orders:write`                   | Läsa／skapa och hantera beställningar                              |
| `auto-recharge:read` / `auto-recharge:write`     | Läsa／hantera inställningar för automatisk påfyllning                             |
| `recharge-cards:redeem`                          | Lösa in påfyllningskort                                   |
| `coin:read`                                      | Läsa tokenrelaterad information                                |
| `distribution:read`                              | Läsa distributionsinformation                                  |
| `connections:read` / `connections:write`         | Läsa／hantera anslutningar                                 |
| `skills:read` / `skills:write`                   | Läsa／hantera färdigheter                                 |
| `openid`                                         | Den aktuella implementeringen tillåter också att UserInfo returnerar grundläggande profiluppgifter; returnerar inte ID Token    |
| `offline_access`                                 | Begär refresh token för att kunna förnya efter att access token har löpt ut |

Till exempel används `profile:read` för att endast läsa profil; lägg till `email:read` om e-post behövs; använd `profile:read credentials:read` för att läsa befintliga API Key. Begär endast `credentials:write` när du verkligen behöver skapa eller ändra Key, och lägg till `offline_access` när förnyelse behövs.

Vissa behörigheter är endast avsedda för betrodda applikationer godkända av plattformen, exempelvis `sites:read`, `sites:write`, `platform-tokens:read`; andra behörigheter är inte öppna för vanliga OAuth-applikationer från tredje part. Klienttypen `public`／`confidential` beskriver huruvida en secret kan förvaras säkert och har inget samband med om applikationen är betrodd. Självbetjäningsskapade applikationer kan inte själva aktivera betrodda behörigheter.

`account` är en behörighetsväljare för konton som används av det angivna officiella MCP för kontohantering, och är inte scopet ”alla behörigheter” för tredjepartsapplikationer; det kan inte användas tillsammans med andra scope. Tredje parter ska uttryckligen lista de specifika behörigheter som behövs.

### Migrera från äldre dokumentation

| Gammal skrivning                                         | Aktuell metod                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Lista specifikt de faktiska behörigheter som behövs, det finns inget generellt ersättningsvärde för ”välj alla” |

Äldre namn accepteras inte som kompatibilitetsalias. Uppdatera samtidigt scopes som registrerats för OAuth-applikationen, auktoriserings-URL:en och dina egna behörighetskontroller; ändring av applikationskonfigurationen ger inte redan utfärdade token fler behörigheter, användaren måste auktorisera på nytt.

## Steg 1: Registrera OAuth-applikationen

Öppna [OAuth-applikationshantering](https://auth.acedata.cloud/user/oauth-apps), skapa en applikation och fyll i:
- Namn, beskrivning, applikationslogo: visas på applikationssidan på auktoriseringssidan.
- Klienttyp: välj **Public** för ren frontend, mobil- eller skrivbordsklienter; välj **Confidential** för tjänster som kan förvara secret på backend.
- Återanropsadress: använd HTTPS i produktionsmiljön och registrera den fullständiga URL där applikationen faktiskt hanterar återanropet.
- Behörigheter: välj de scopes som faktiskt behövs från katalogen som sidan tillhandahåller.

Spara `client_id`. Confidential-klienter ska förvara `client_secret` på serversidan och får inte placera det i HTML, frontend-byggvariabler eller URL:er. Public-klienter använder inte secret för att hämta token; även om registreringssvaret innehåller detta fält får det inte behandlas som en uppgift som klienten kan hålla hemlig.

`redirect_uri` måste vara exakt identisk vid registrering, auktorisering och token-utbyte, inklusive sökväg, avslutande snedstreck och frågeparametrar. Varje konto kan skapa högst 20 applikationer. Secret visas endast vid skapande/rotation; efter rotation kan det gamla secret inte längre användas för utbyten som kräver klientautentisering.

## Steg 2: Knappen initierar auktorisering

Vid varje klick på anslutning, generera nya slumpmässiga `state` och `code_verifier`, beräkna:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Spara `state`, verifier och återanropsadress i applikationens egen session, och öppna sedan auktoriseringssidan med URL-kodade parametrar:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<fullständig återanropsadress>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<slumpvärde för detta tillfälle>
  &code_challenge=<S256-utmaningsvärde för detta tillfälle>
  &code_challenge_method=S256
```

Public-klienter måste skicka S256 PKCE. Även om Discovery fortfarande listar `plain` får Public-klienter inte använda det. Confidential-klienter rekommenderas också att använda S256; om PKCE användes när auktoriseringen initierades måste motsvarande verifier skickas vid utbytet.

Efter att användaren godkänt återgår den till `redirect_uri`, där frågeparametrarna innehåller `code` och det oförändrat returnerade `state`. Vid avslag returneras `error=access_denied`, felbeskrivning och `state`. Verifiera först att state matchar den aktuella sessionen innan återanropet behandlas. Auktoriseringskoden är giltig i 10 minuter och kan endast lösas in en gång; initiera anslutningen på nytt efter fel och uppdatera inte upprepade gånger den gamla återanrops-URL:en.

## Steg 3: Byt mot OAuth-token

Public-klienter löser in direkt från webbläsaren eller klienten; Confidential-klienter löser in på sin egen backend. Begärans brödtext stöder formulärkodning, och följande variabler representerar data som applikationen erhållit från denna auktorisering:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Confidential-klienter måste även lägga till formulärfältet `client_secret` på serversidan. `client_secret_post` stöds för närvarande; behandla inte HTTP Basic-klientautentisering som en metod som stöds.

Läs `access_token`, `token_type`, `expires_in` och den faktiskt beviljade `scope` i det lyckade svaret. Endast om `offline_access` har begärts och beviljats finns en `refresh_token`. Behandla inte OAuth access token som API Key för modell-API:t, och skriv inte token, verifier eller auktoriseringskod till loggar, analyshändelser eller delningslänkar.

## Steg 4: Läs användarinformation och API Key

Använd först OAuth access token för att begära UserInfo:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

De returnerade fälten beror på scope: `id` är användaridentifieraren; `profile:read` eller `openid` kan läsa grundläggande profiluppgifter (såsom `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); e-post kräver `email:read`, och telefonnummer samt region kräver `phone:read`. Förlita dig inte på att obehöriga fält alltid finns.

När en befintlig API Key behövs och `credentials:read` har beviljats, använd UserInfos `id` som filtervillkor:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Den returnerade listan använder `count` och `items`, och Key-fältet är **`items[*].token`**, inte `data[0].value`. `user_id=me` är inte ett giltigt användar-ID för detta gränssnitt. Fortsätt läsa flersidiga data enligt `offset`/`limit`; behandla inte första sidan som alla autentiseringsuppgifter.

Välj lämpliga autentiseringsuppgifter utifrån applikation, tjänst och giltighetsstatus; ta inte blint den första. En tom lista betyder inte att auktoriseringen misslyckades; användaren kan ännu inte ha skapat en lämplig Key. OAuth access tokens behörighetskontroll och API Key:ns egen tjänsteomfattning, kvot och utgångsvillkor är olika begränsningar.

**Att tillåta läsning av API Key innebär att tredje part kan spara och använda den. Att återkalla OAuth-begäran eller rensa applikationens inloggningsstatus gör inte en redan kopierad API Key ogiltig; användaren måste återkalla eller rotera Key:n separat i autentiseringsuppgiftshanteringen.**

## Körbart Public / PKCE-webbläsarexempel

Distribuera följande sida till din registrerade `REDIRECT_URI`, och ersätt `CLIENT_ID` och återanropsadressen. Knappen initierar standardauktorisering och läser personlig information samt antalet befintliga Keys efter återkomst till samma sida. Exemplet visar inte och sparar inte Keys; produktionsapplikationer använder resultatet enligt det faktiska ändamålet. Verifiera först på en separat webbläsarsida och godkänn sedan enligt iframe-kraven längre fram.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Anslut Ace Data Cloud</title>
<button id="connect" type="button">Anslut konto</button>
<p id="status" role="status">Inte ansluten ännu</p>
<script type="module">
const CLIENT_ID = 'ersätt med ditt client_id';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`Gränssnittet returnerade HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = 'Det gick inte att starta anslutningen. Kontrollera webbläsarens lagringsinställningar och försök igen.';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('Auktoriseringssessionen stämmer inte. Anslut igen.');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('Auktoriseringssessionen har upphört. Anslut igen.');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('Auktoriseringen slutfördes inte. Du kan ansluta igen.');
    if (!code) throw new Error('Återanropet saknar auktoriseringskod. Anslut igen.');
    status.textContent = 'Ansluter…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('Auktoriseringstoken erhölls inte.');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('Användaridentifierare erhölls inte.');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('Formatet för autentiseringslistan stämmer inte.');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `Ansluten till ${profile.nickname || profile.username || profile.id}; den här sidan har ${keyCount} API-nycklar.`;
  } catch (error) {
    status.textContent = `Anslutningen slutfördes inte: ${error.message || 'nätverksfel'} Klicka på anslut igen.`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Exemplets återanrop och ingång måste ha samma ursprung och finnas i samma webbläsarflik/iframe för att kunna läsa den tidigare sparade `sessionStorage`. Produktionsapplikationer bör hantera token i sin egen sessionslösning, hantera utgångstid och rensa auktoriserings-URL-parametrar efter att ett svar har tagits emot; sidans huvudgränssnitt bör renderas först, och nätverksfel bör endast påverka anslutningsstatusen.

## iframe på webbplats med white label

### Kundens webbplats navigerar själv till auktoriseringssidan

Använd standardparametrar för OAuth och egen hantering av återanrop; `window.location.assign()` navigerar den aktuella iframe:n, och den överordnade sidan stannar kvar på white label-domänen. Det behövs inte att lägga till `embed=studio` för ikonen eller implementera Studio-meddelandeprotokollet.

Följande villkor måste uppfyllas:

- Applikationssidan och återanropssidan använder HTTPS, är faktiskt åtkomliga och tillåter inbäddning via iframe från white label-föräldradomänen; kontrollera båda sidors `Content-Security-Policy: frame-ancestors` och `X-Frame-Options`.
- sandbox tillåter de skript, formulär och ursprungs-/lagringsfunktioner som sidan behöver. Vid stöd för popup-inloggning behövs även motsvarande popup-funktioner; använd i första hand konfigurationen för Website-komponenten som Studio tillhandahåller.
- Webbläsaren tillåter att lagringen som krävs för auktoriseringstillståndet används i det aktuella inbäddningsscenariot. White label-webbplatsens inloggningsstatus och AuthFrontends inloggningsstatus kan skilja sig åt; anta inte att auktoriseringssidan redan är inloggad bara för att white label-webbplatsen är inloggad.
- Tokenutbytestjänsten i återanropet är tillgänglig, och förfrågningar mellan olika ursprung tillåter applikationens ursprung; DNS-, CORS- och HTTP-fel måste visa ett tillstånd som går att försöka igen, och får inte hindra hela sidan från att renderas.

Auktoriseringssidan läser OAuth-applikationens Logo till vänster; till höger läser den Site:ns favicon/logo när webbläsaren kan tillhandahålla föräldraursprunget och föräldradomänen godkänns genom verifierad webbplatsvalidering, annars visas en standardikon. Detta avgör endast varumärkesvisningen, etablerar ingen inloggningssession och ger inte kundsidan kontobehörigheter.

**Nuvarande begränsning: När vanlig OAuth behöver logga in igen i en iframe finns det fortfarande en lucka i flödet för att återgå till auktoriseringssidan efter att inloggningen har slutförts.** Före lansering måste både ”Auth inloggad” och ”Auth inte inloggad/utgången” godkännas separat. Innan denna lucka har åtgärdats och verifierats kan den första inloggningen slutföras med standard-OAuth på en separat sida, eller med Studio-komponentens auktorisering nedan; lova inte att alla iframe-scenarier fungerar enbart baserat på testresultat där användaren redan är inloggad.

### Använd det aktuella Studio-kontot för auktorisering

Aktivera OAuth i Studio under ”Inställningar → Startsida → Webbplatskomponenter”, och fyll i `client_id` och den registrerade återanropsadressen. Webbplatsen och återanropet måste använda samma HTTPS-ursprung och skilja sig från Studio-ursprunget. Tredjepartssidan behöver:

1. Skicka `acedatacloud:oauth:ready` till det exakta ursprunget för den överordnade webbplatsen, och ta emot samt validera `acedatacloud:oauth:init`.
2. Knappen genererar state och PKCE verifier, och skickar `acedatacloud:oauth:authorize` (state, S256 challenge); verifiern stannar kvar på den egna sidan.
3. Validera det överordnade fönstret, ursprunget och state, hantera code eller error i `acedatacloud:oauth:result`, och byt enligt standardtokenändpunkten.
Studio visar auktoriseringssidan i komponentområdet, och efter att användaren samtyckt returneras auktoriseringskoden via meddelande, applikationen behöver inte omdirigeras. När ingen är inloggad returneras `login_required`, vid avslag returneras `access_denied`, och vid väntetidsgräns returneras `authorization_timeout`. Kontobyte återskapar applikationens iframe och avbryter ofullständiga auktoriseringar.

Komponenten begär för närvarande `profile:read credentials:read`, och inkluderar inte `offline_access`. Anta inte att en refresh token säkert kan tas emot. `embed=studio` och `embed_origin` underhålls av Studio-värden och auktoriseringssidan, kundsidan behöver bara följa meddelandeprotokollet.

Fullständigt knappexempel finns i [OAuth-integrationsguiden för Studio-webbkomponenter](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Livscykel, uppdatering och återkallelse

Access token har en standardgiltighet på 15 dagar och uppdatering eller ny auktorisering bör schemaläggas enligt varje svars `expires_in`; refresh token har som standard 30 dagar, och perioden påverkas av tjänstekonfigurationen. Hårdkoda inte dessa två värden som permanenta löften.

Efter att `offline_access` har beviljats kan följande anropas:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Uppdatering returnerar nya token, applikationen bör spara de senaste värdena. Vid uppdatering kontrolleras om applikationen fortfarande är giltig, användaren är tillgänglig och behörigheterna fortfarande är beviljade. Vid fel ska det egna anslutningstillståndet rensas och auktorisering göras på nytt.

**Den nuvarande OAuth-uppdateringsimplementeringen garanterar inte att den gamla refresh token omedelbart blir ogiltig efter uppdatering.** Betrakta inte att en ny token har erhållits som att den gamla token har återkallats, och använd inte rotering av secret som ersättning för att avsluta befintliga token.

Återkallelsebegäran anropas så här:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Den nuvarande återkallelseändpunkten returnerar HTTP 200, men implementerar inte omedelbar ogiltigförklaring av utfärdade JWT:er.** Applikationen bör rensa sina egna sparade token och kan inte betrakta 200 som bevis på att alla utfärdade token eller API Keys har blivit ogiltiga. API Keys som har läckt eller kopierats ska återkallas eller roteras separat med motsvarande autentiseringsuppgifter.

## Vanliga fel och godkännande

| Fenomen／fel                         | Felsökning                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Använd aktuella behörighetsnamn; kontrollera applikationsregistrerade omfattningar, delegeringsbegränsningar och användarbehörigheter. Discovery:s hela katalog är inte applikationens valbara katalog                      |
| `invalid_request`             | Obligatoriska parametrar, exakt återanropsadress, S256 challenge och method för Public-klient                        |
| `invalid_client`              | client ID, applikationsstatus, secret för Confidential-klient; kontrollera om Basic-autentisering används felaktigt             |
| `invalid_grant`               | code har gått ut／har förbrukats, verifier eller redirect URI stämmer inte; vid uppdatering kontrolleras även applikations- och behörighetsändringar                 |
| `access_denied`               | Användaren avböjer, återställ anslutningsknappen, visa inte auktorisering i en slinga                                                  |
| `unsupported_grant_type`      | Stöder för närvarande `authorization_code` och `refresh_token`                             |
| HTTP 401／403                  | Skilj mellan ogiltigt inloggningstillstånd, token, auktoriserings-scope och själva resursens åtkomstbehörighet                                     |
| `Failed to fetch`、DNS／CORS-fel | Kontrollera den verkliga begärandevärden och kundbackendens tillgänglighet, kan inte tillskrivas att ”användaren inte har någon Key”                                      |
| Auktoriserad men kan inte läsa Key                   | Använd `platform.acedata.cloud`, verkligt user ID, `items[*].token`; skilj mellan tom lista, paginering och felsvar |
| Hela sidan är tom efter auktoriseringssvar                     | Rendera sidan först; hantera fel separat för återanrop, token, UserInfo och begäran om autentiseringsuppgifter; låt inte initieringsundantag stoppa hela sidan                      |
| iframe fortsätter inte efter inloggning                 | Hantera enligt de befintliga begränsningarna ovan, testa scenarier med ej inloggad, utgången, avböjd och återanslutning                                          |

Verifiera minst före leverans: korrekt återanrop, avslag, felaktigt state, utgången／förbrukad code, ingen Key, nätverksfel, utgången token, saknad nödvändig scope samt första inloggning och kontobyte i iframe-scenarier. Spara inte fullständig code, token eller API Key i testbevis.

## Tvåstegsverifiering och ny auktorisering

Efter att användaren aktiverat tvåstegsverifiering genomför Ace Data Cloud verifiering av autentiserarens verifieringskod eller engångsåterställningskod på auktoriseringssidan, och levererar sedan auktoriseringskoden. Din applikation fortsätter att använda standardflödet för OAuth och bör inte be användaren om, spara eller vidarebefordra autentiserarens hemliga nycklar eller återställningskoder.

När användaren aktiverar, byter eller inaktiverar tvåstegsverifiering eller återställer kontot, kan tidigare kontosessioner, refresh tokens och relaterade plattformsauktoriseringstoken bli ogiltiga. När ogiltig session eller `invalid_grant` tas emot, starta det användarsynliga auktoriseringsflödet på nytt, återanvänd inte gamla auktoriseringskoder upprepade gånger och försök inte kringgå verifieringen. Autentiseringssättet för vanliga modell-API Keys förblir oförändrat; om kontointrång misstänks bör berörda API Keys kontrolleras och återkallas separat.
