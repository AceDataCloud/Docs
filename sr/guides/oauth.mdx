---
title: "Integracija Ace Data Cloud OAuth 2.0"
---

Omogućite korisnicima da ovlaste vašu aplikaciju za pristup njihovom Ace Data Cloud profilu, pretplatama na usluge, API ključevima, potrošnji ili porudžbinama. Koristite standardni **Authorization Code + S256 PKCE**: aplikacija otvara stranicu za ovlašćivanje, korisnik nakon pristanka dobija jednokratni `code`, koji se zatim menja za OAuth access token.

OAuth access token se koristi za pristup interfejsima resursa naloga; za pozivanje model API-ja koristi se odgovarajući API Key. OAuth ovlašćivanje ne kreira automatski API Key, ne aktivira usluge niti povećava stanje.

## Izaberite način integracije

| Način            | Primena                                | Nakon završetka ovlašćivanja                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Standardno OAuth preusmeravanje   | Nezavisni veb-sajtovi, desktop ili mobilni klijenti; ugrađeni veb-sajtovi samostalno pokreću ovlašćivanje            | Pregledač se vraća na `redirect_uri` koji je aplikacija registrovala, a aplikacija obrađuje `code` i `state` |
| Ovlašćivanje putem Studio komponente veb-sajta | Veb-sajt ugrađuje Studio početnu stranicu i želi da koristi trenutni Studio nalog posetioca | Studio šalje poruku sa rezultatom ovlašćivanja aplikaciji, aplikacija se ne preusmerava, a originalna stranica ostaje                  |

Standardno preusmeravanje ne zahteva `embed=studio`, `embed_origin` ili `postMessage`. U režimu Studio komponente, domaćin kreira stranicu za ovlašćivanje i održava most za poruke; treće strane se integrišu prema protokolu komponente na kraju ovog dokumenta i ne treba same da sastavljaju ova dva parametra.

## Endpointi i dokument za otkrivanje

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Namena                | Adresa                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Stranica za ovlašćivanje u pregledaču            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| Zamena／osvežavanje OAuth tokena | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Slanje zahteva za opoziv            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Informacije o trenutnom korisniku            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| Stranica za upravljanje OAuth aplikacijama      | [OAuth aplikacije](https://auth.acedata.cloud/user/oauth-apps)                            |
| Lista aplikacija／interfejs za registraciju prijavljenog korisnika   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Javni podaci aplikacije koje koristi stranica za ovlašćivanje      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Postojeći API Key korisnika     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<ID korisnika>&limit=100` |

Interfejs za upravljanje aplikacijama zahteva autentifikaciju prijavljenog naloga i nije interfejs za anonimnu dinamičku registraciju (DCR). Endpointi za otkrivanje／registraciju samog MCP servisa razlikuju se od OAuth endpointa naloga u ovoj tabeli; prilikom povezivanja sa konkretnim MCP-om postupajte prema dokumentaciji i rezultatima otkrivanja tog servisa.

Dokument za otkrivanje se koristi za dobijanje endpointa i mogućnosti protokola. Trenutni tok vraća OAuth token, a ne vraća `id_token`; nemojte obrađivati ovo kao potpuni OpenID Connect tok prijavljivanja samo zato što postoji `openid` scope.

## Opseg dozvola: koristite trenutne nazive scope-ova

`scope` je naziv dozvole razdvojen razmacima i razlikuje velika i mala slova. Nove aplikacije koriste konkretne dozvole kao što su `profile:read`, `email:read`, `phone:read`.

### Gde dobiti dozvole koje se mogu zatražiti

Nakon prijavljivanja, interfejs liste OAuth aplikacija `GET /api/v1/oauth2/applications/` vraća `available_scopes`; birač dozvola na stranici za upravljanje aplikacijama koristi isti katalog. Ovo su opcioni opsezi koje treba da koriste uobičajene aplikacije sa samostalnom registracijom.

**`scopes_supported` iz Discovery-ja sadrži sve nazive dozvola koje platforma prepoznaje, ali ne znači da vaša aplikacija može zatražiti svaku od njih.** Stvarno ovlašćivanje istovremeno proverava:

1. da li je dozvolu moguće delegirati tom tipu aplikacije;
2. da li je dozvola registrovana u dozvoljenim opsezima ove OAuth aplikacije;
3. da li trenutni korisnik poseduje traženu dozvolu.

Nepoznate, neregistrovane, nedozvoljene za delegiranje ili dozvole koje korisnik nema vraćaju `invalid_scope`. Prilikom zamene autorizacionog koda i osvežavanja takođe se ponovo proverava, a dozvole se neće automatski dopuniti ili povećati.

### Opcione dozvole za uobičajene aplikacije sa samostalnom registracijom

Sledi trenutni katalog (2026-10-09); pri integraciji se oslonite na `available_scopes`.

| Scope                                            | Namena                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Čitanje／ažuriranje profila                               |
| `email:read`                                     | Čitanje e-pošte                                    |
| `phone:read`                                     | Čitanje broja mobilnog telefona i regiona                                |
| `billing-profile:read` / `billing-profile:write` | Čitanje／upravljanje podacima za naplatu                               |
| `applications:read` / `applications:write`       | Čitanje／upravljanje pretplatama na usluge                               |
| `credentials:read` / `credentials:write`         | Čitanje／upravljanje API Key-jem                           |
| `usage:read`                                     | Čitanje evidencije poziva                                  |
| `orders:read` / `orders:write`                   | Čitanje／kreiranje i upravljanje porudžbinama                              |
| `auto-recharge:read` / `auto-recharge:write`     | Čitanje／upravljanje podešavanjima automatske dopune                             |
| `recharge-cards:redeem`                          | Iskorišćavanje kartica za dopunu                                   |
| `coin:read`                                      | Čitanje informacija povezanih sa tokenima                                |
| `distribution:read`                              | Čitanje informacija o distribuciji                                  |
| `connections:read` / `connections:write`         | Čitanje／upravljanje vezama                                 |
| `skills:read` / `skills:write`                   | Čitanje／upravljanje veštinama                                 |
| `openid`                                         | Trenutna implementacija takođe dozvoljava UserInfo da vrati osnovne podatke; ne vraća ID Token    |
| `offline_access`                                 | Zahtevanje refresh tokena radi osvežavanja nakon isteka access tokena |

Na primer, za čitanje samo profila koristite `profile:read`; ako je potrebna i e-pošta, dodajte `email:read`; za čitanje postojećeg API Key-ja koristite `profile:read credentials:read`. `credentials:write` zatražite samo kada zaista treba da kreirate ili izmenite Key, a `offline_access` dodajte kada je potrebno osvežavanje.

Neke dozvole su namenjene samo pouzdanim aplikacijama koje je odobrila platforma, kao što su `sites:read`, `sites:write`, `platform-tokens:read`; druge dozvole nisu otvorene za uobičajene OAuth aplikacije trećih strana. Tip klijenta `public`／`confidential` opisuje da li može bezbedno čuvati secret i nema veze sa tim da li je aplikacija pouzdana. Aplikacije kreirane samostalnom registracijom ne mogu same uključiti pouzdane dozvole.

`account` je birač dozvole naloga koji koristi navedeni zvanični MCP za upravljanje nalogom, a nije scope „svih dozvola” za aplikacije trećih strana i ne može se kombinovati sa drugim scope-ovima. Treće strane treba jasno da navedu konkretne dozvole koje su im potrebne.

### Migracija sa stare dokumentacije

| Stari zapis                                         | Trenutni način integracije                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Pojedinačno navedite konkretne dozvole koje su stvarno potrebne; ne postoji univerzalna zamena za „izaberi sve” |

Stari nazivi se ne prihvataju kao kompatibilni aliasi. Sinhrono ažurirajte scope-ove registrovane za OAuth aplikaciju, URL za ovlašćivanje i sopstvenu proveru dozvola; izmena konfiguracije aplikacije neće dodati dozvole već izdatim tokenima, pa je potrebno da korisnik ponovo odobri pristup.

## Korak 1: Registrujte OAuth aplikaciju

Otvorite [upravljanje OAuth aplikacijama](https://auth.acedata.cloud/user/oauth-apps), kreirajte aplikaciju i popunite:
- Naziv, opis, Logo aplikacije: prikazuju se na strani aplikacije na stranici za autorizaciju.
- Tip klijenta: za čisti frontend, mobilne ili desktop klijente izaberite **Public**; za servise koji mogu čuvati secret na backendu izaberite **Confidential**.
- Adresa za povratni poziv: u produkcionom okruženju koristite HTTPS i registrujte puni URL koji aplikacija zaista koristi za obradu povratnog poziva.
- Dozvole: iz direktorijuma dostupnog na stranici izaberite scopes koji su zaista potrebni.

Sačuvajte `client_id`. Confidential klijent čuva `client_secret` na serverskoj strani i ne sme se stavljati u HTML, promenljive za frontend build ili URL. Public klijent ne koristi secret pri razmeni za token; čak i ako odgovor registracije sadrži to polje, ne sme se tretirati kao poverljiva akreditacija koju klijent može sačuvati.

`redirect_uri` mora biti potpuno identičan pri registraciji, autorizaciji i razmeni tokena, uključujući putanju, završnu kosu crtu i parametre upita. Svaki nalog može kreirati najviše 20 aplikacija. Secret se prikazuje samo prilikom kreiranja／rotacije; nakon rotacije stari secret više ne može da obavlja razmene koje zahtevaju autentikaciju klijenta.

## Korak 2: Dugme pokreće autorizaciju

Pri svakom kliku na povezivanje, generišite novi nasumični `state` i `code_verifier`, izračunajte:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Sačuvajte `state`, verifier i adresu za povratni poziv u sopstvenoj sesiji aplikacije, a zatim otvorite stranicu za autorizaciju sa URL-kodiranim parametrima:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<puna adresa za povratni poziv>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<nasumična vrednost za ovaj put>
  &code_challenge=<S256 challenge vrednost za ovaj put>
  &code_challenge_method=S256
```

Public klijent mora slati S256 PKCE. Iako Discovery i dalje navodi `plain`, Public klijent ne sme da ga koristi. Confidential klijentu se takođe preporučuje korišćenje S256; ako je PKCE korišćen pri pokretanju autorizacije, pri razmeni se mora poslati odgovarajući verifier.

Nakon korisnikovog pristanka vraća se na `redirect_uri`, a parametri upita sadrže `code` i neizmenjeno vraćen `state`. Pri odbijanju se vraćaju `error=access_denied`, opis greške i `state`. Pre obrade povratnog poziva prvo proverite da li se state podudara sa ovom sesijom. Autorizacioni kod važi 10 minuta i može se razmeniti samo jednom; nakon neuspeha treba ponovo pokrenuti povezivanje, nemojte stalno osvežavati stari URL povratnog poziva.

## Korak 3: Razmena za OAuth token

Public klijent razmenjuje direktno iz pregledača ili klijenta; Confidential klijent razmenjuje na sopstvenom backendu. Telo zahteva podržava form encoding, a sledeće promenljive predstavljaju podatke koje je aplikacija dobila ovom autorizacijom:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Confidential klijent takođe treba da doda polje obrasca `client_secret` na serverskoj strani. Trenutno je podržan `client_secret_post`; nemojte smatrati HTTP Basic autentikaciju klijenta podržanom metodom.

Iz uspešnog odgovora pročitajte `access_token`, `token_type`, `expires_in` i stvarno odobreni `scope`. `refresh_token` postoji samo ako je zatražen i odobren `offline_access`. Nemojte OAuth access token tretirati kao API Key za model API, niti upisivati token, verifier ili autorizacioni kod u logove, analitičke događaje ili linkove za deljenje.

## Korak 4: Čitanje korisničkih informacija i API Key-a

Najpre koristite OAuth access token za zahtev UserInfo:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Vraćena polja zavise od scope-a: `id` je identifikator korisnika; `profile:read` ili `openid` omogućavaju čitanje osnovnih podataka (kao što su `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); za imejl je potreban `email:read`, a za broj telefona i region potreban je `phone:read`. Nemojte se oslanjati na to da su neodobrena polja uvek prisutna.

Kada je potreban postojeći API Key i odobren je `credentials:read`, koristite `id` iz UserInfo kao uslov filtriranja:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Vraćena lista koristi `count` i `items`, a polje Key-a je **`items[*].token`**, a ne `data[0].value`. `user_id=me` nije važeći korisnički ID za ovaj interfejs. Za podatke na više stranica nastavite čitanje prema `offset`／`limit`; nemojte prvu stranicu tretirati kao sve akreditive.

U skladu sa aplikacijom, servisom i statusom važenja izaberite primenljive akreditive; nemojte naslepo uzimati prvu stavku. Prazna lista ne znači da je autorizacija neuspešna; korisnik možda još nije kreirao primenljivi Key. Kontrola dozvola OAuth access tokena i opseg servisa, kvote i uslovi isteka samog API Key-a su različita ograničenja.

**Dozvola za čitanje API Key-a znači da treća strana može da ga sačuva i koristi. Opoziv OAuth zahteva ili brisanje stanja prijave aplikacije neće učiniti već kopirani API Key nevažećim; korisnik mora zasebno opozvati ili rotirati taj Key u upravljanju akreditivima.**

## Izvršiv Public / PKCE primer za pregledač

Postavite sledeću stranicu na registrovani `REDIRECT_URI`, zamenite `CLIENT_ID` i adresu za povratni poziv. Dugme pokreće standardnu autorizaciju, a nakon povratka na istu stranicu čita lične podatke i broj postojećih Key-eva. Primer ne prikazuje niti trajno čuva Key; produkciona aplikacija koristi rezultate prema stvarnoj nameni. Najpre proverite na zasebnoj stranici pregledača, a zatim izvršite prihvatanje prema kasnijim iframe zahtevima.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>连接 Ace Data Cloud</title>
<button id="connect" type="button">连接账号</button>
<p id="status" role="status">尚未连接</p>
<script type="module">
const CLIENT_ID = '替换为你的 client_id';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`接口返回 HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = '无法开始连接，请检查浏览器存储设置后重试。';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('授权会话不匹配，请重新连接。');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('授权会话已失效，请重新连接。');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('未完成授权，可以重新连接。');
    if (!code) throw new Error('回调缺少授权码，请重新连接。');
    status.textContent = '正在连接…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('未取得授权令牌。');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('未取得用户标识。');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('凭证列表格式不符。');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `已连接 ${profile.nickname || profile.username || profile.id}；本页有 ${keyCount} 条 API Key。`;
  } catch (error) {
    status.textContent = `连接未完成：${error.message || '网络异常'} 请重新点击连接。`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Povratni poziv i ulazni primer moraju biti na istom originu, u istoj kartici pregledača／iframe-u, kako bi mogli da pročitaju prethodno sačuvani `sessionStorage`. Produkciona aplikacija treba da upravlja tokenima u okviru sopstvene šeme sesija, obradi istek i ukloni URL parametre autorizacije nakon prijema odgovora; glavni interfejs stranice treba prvo da se prikaže, a mrežni neuspeh treba da utiče samo na status povezivanja.

## iframe na white-label sajtu

### Klijentski sajt samostalno preusmerava na stranicu za autorizaciju

Dovoljno je koristiti standardne OAuth parametre i sopstvenu obradu povratnog poziva; `window.location.assign()` navigira trenutni iframe, dok roditeljska stranica ostaje na white-label domenu. Nema potrebe dodavati `embed=studio` zbog ikone niti implementirati Studio protokol poruka.

Moraju biti ispunjeni sledeći uslovi:

- Stranica aplikacije i stranica povratnog poziva koriste HTTPS, stvarno su dostupne i dozvoljavaju ugrađivanje putem iframe-a od strane white-label roditeljskog domena; proverite `Content-Security-Policy: frame-ancestors` i `X-Frame-Options` obe strane.
- sandbox dozvoljava skripte, obrasce i mogućnosti origina／skladišta potrebne stranici. Kada je podržana prijava u iskačućem prozoru, potrebne su i odgovarajuće mogućnosti za iskačuće prozore; prednost dajte konfiguraciji Website komponente koju pruža Studio.
- Pregledač dozvoljava skladište potrebno za stanje autorizacije u trenutnom scenariju ugrađivanja. Stanje prijave na white-label sajt i stanje prijave na AuthFrontend mogu biti različiti; ne treba pretpostaviti da je korisnik već prijavljen na stranicu za autorizaciju samo zato što je prijavljen na white-label sajt.
- Usluga za razmenu tokena u povratnom pozivu je dostupna, a zahtevi između različitih origina dozvoljavaju origin aplikacije; DNS, CORS i HTTP greške moraju prikazati stanje koje se može ponovo pokušati, bez prekidanja renderovanja cele stranice.

Leva strana stranice za autorizaciju čita OAuth Application Logo; desna strana čita favicon／logo tog Site-a kada pregledač može da pruži roditeljski origin i kada roditeljski domen prođe verifikovanu proveru sajta, u suprotnom prikazuje podrazumevanu ikonu. Ovo određuje samo prikaz brenda, ne uspostavlja sesiju prijave niti pruža dozvole za nalog klijentskoj stranici.

**Trenutno ograničenje: kada je za obični OAuth unutar iframe-a potrebna ponovna prijava, još postoji nedostatak u toku nastavka povratka na stranicu za autorizaciju nakon završetka prijave.** Pre puštanja u rad morate odvojeno prihvatiti slučajeve „Auth je prijavljen“ i „Auth nije prijavljen／istekao je“. Dok se ovaj nedostatak ne otkloni i ne verifikuje, za prvu prijavu možete koristiti zasebnu stranicu za dovršavanje standardnog OAuth-a ili koristiti autorizaciju Studio komponente navedenu u nastavku; nemojte obećavati da su svi iframe scenariji dostupni oslanjajući se samo na rezultate testiranja pri postojećoj prijavi.

### Korišćenje autorizacije trenutnog Studio naloga

U Studiju, u „Podešavanja → Početna → Website komponente“, uključite OAuth i popunite `client_id` i registrovanu adresu povratnog poziva. Sajt i povratni poziv moraju koristiti isti HTTPS origin i moraju se razlikovati od Studio origina. Stranica treće strane treba da:

1. Pošalje `acedatacloud:oauth:ready` na tačan origin roditeljskog sajta, primi i proveri `acedatacloud:oauth:init`.
2. Dugme generiše state i PKCE verifier, te pošalje `acedatacloud:oauth:authorize` (state, S256 challenge); verifier ostaje unutar sopstvene stranice.
3. Proveri roditeljski prozor, origin i state, obradi code ili error iz `acedatacloud:oauth:result` i razmeni ga putem standardnog token endpoint-a.
Studio prikazuje stranicu za autorizaciju u oblasti komponente, a nakon što korisnik pristane vraća autorizacioni kod putem poruke, aplikacija ne mora da preusmerava. Kada korisnik nije prijavljen vraća se `login_required`, pri odbijanju se vraća `access_denied`, a pri isteku vremena čekanja vraća se `authorization_timeout`. Promena naloga ponovo kreira iframe aplikacije i otkazuje nedovršene autorizacije.

Komponenta trenutno zahteva `profile:read credentials:read`, ne uključuje `offline_access`. Ne pretpostavljajte da se refresh token obavezno može primiti. `embed=studio` i `embed_origin` održavaju Studio domaćin i stranica za autorizaciju, stranica klijenta treba samo da poštuje protokol poruka.

Kompletan primer dugmeta pogledajte u [Vodiču za OAuth integraciju Studio veb komponenti](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Životni ciklus, osvežavanje i opoziv

Podrazumevani period važenja access tokena je 15 dana, a osvežavanje ili ponovnu autorizaciju treba planirati prema `expires_in` iz svakog odgovora; refresh token podrazumevano važi 30 dana, a rok zavisi od konfiguracije usluge. Nemojte ove dve vrednosti tvrdo kodirati kao trajna obećanja.

Nakon odobrenja `offline_access`, može se pozvati:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Osvežavanje vraća nove tokene, a aplikacija treba da sačuva najnovije vrednosti. Pri osvežavanju se proverava da li je aplikacija i dalje važeća, da li je korisnik dostupan i da li su dozvole i dalje odobrene. U slučaju neuspeha, obrišite sopstveno stanje veze i ponovo izvršite autorizaciju.

**Trenutna OAuth implementacija osvežavanja ne garantuje da stari refresh token postaje nevažeći odmah nakon osvežavanja.** Nemojte dobijanje novog tokena smatrati dokazom da je stari token opozvan, niti rotaciju secret-a koristiti kao zamenu za prekid postojećih tokena.

Način pozivanja zahteva za opoziv je:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Trenutna krajnja tačka za opoziv vraća HTTP 200, ali ne implementira trenutno poništavanje već izdatih JWT-ova.** Aplikacija treba da obriše tokene koje je sama sačuvala i ne sme da smatra 200 dokazom da su svi izdati tokeni ili API Key-ovi postali nevažeći. API Key-ove koji su procureli ili kopirani treba zasebno opozvati ili rotirati odgovarajuće akreditive.

U dokazima testiranja ne čuvajte kompletan code, token ili API Key.

## Verifikacija u dva koraka i ponovna autorizacija

Nakon što korisnik uključi verifikaciju u dva koraka, Ace Data Cloud na stranici za autorizaciju završava proveru koda iz autentifikatora ili jednokratnog koda za oporavak, a zatim isporučuje autorizacioni kod. Vaša aplikacija nastavlja da koristi standardni OAuth tok i ne treba da traži od korisnika, čuva niti prosleđuje ključeve autentifikatora i kodove za oporavak.

Nakon što korisnik uključi, promeni, isključi verifikaciju u dva koraka ili oporavi nalog, prethodne sesije naloga, refresh tokeni i povezani tokeni autorizacije platforme mogu postati nevažeći. Kada primite nevažeću sesiju ili `invalid_grant`, ponovo pokrenite korisniku vidljiv tok autorizacije, nemojte više puta koristiti stari autorizacioni kod niti pokušavati da zaobiđete verifikaciju. Način autentifikacije običnih model API Key-ova ostaje nepromenjen; ako se sumnja da je nalog kompromitovan, zasebno proverite i opozovite zahvaćene API Key-ove.
