---
title: "Integracija Ace Data Cloud OAuth 2.0"
---

Omogućite korisnicima da ovlaste vašu aplikaciju za pristup njihovom Ace Data Cloud profilu, pretplatama na usluge, API Key-evima, potrošnji ili porudžbinama. Koristite standardni **Authorization Code + S256 PKCE**: aplikacija otvara stranicu za autorizaciju, korisnik nakon pristanka dobija jednokratni `code`, koji se zatim menja za OAuth access token.

OAuth access token se koristi za pristup interfejsima resursa naloga; za pozivanje model API-ja koristi se odgovarajući API Key. OAuth autorizacija ne kreira automatski API Key, ne aktivira usluge niti povećava stanje.

## Izbor načina integracije

| Način            | Primena                                | Nakon završene autorizacije                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Standardno OAuth preusmeravanje   | Samostalni veb-sajtovi, desktop ili mobilni klijenti; ugrađeni veb-sajt sam pokreće autorizaciju            | Pregledač se vraća na `redirect_uri` koji je aplikacija registrovala, aplikacija obrađuje `code` i `state` |
| Autorizacija putem Studio komponente veb-sajta | Veb-sajt ugrađuje Studio početnu stranicu i želi da koristi trenutni Studio nalog posetioca | Studio šalje poruku sa rezultatom autorizacije aplikaciji, aplikacija se ne preusmerava, originalna stranica ostaje                  |

Standardno preusmeravanje ne zahteva `embed=studio`, `embed_origin` ili `postMessage`. Režim Studio komponente kreira stranicu za autorizaciju preko hosta i održava most za poruke; treće strane se integrišu prema protokolu komponenti na kraju ovog dokumenta, bez samostalnog sastavljanja ova dva parametra.

## Endpointi i dokument za otkrivanje

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Namena                | Adresa                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Stranica za autorizaciju u pregledaču            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| Zamena／osvežavanje OAuth tokena | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Slanje zahteva za opoziv            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Informacije o trenutnom korisniku            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| Stranica za upravljanje OAuth aplikacijama      | [OAuth aplikacije](https://auth.acedata.cloud/user/oauth-apps)                            |
| Lista aplikacija／interfejs za registraciju prijavljenog korisnika   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Javni podaci o aplikaciji koje koristi stranica za autorizaciju      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Postojeći API Key-evi korisnika     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<ID korisnika>&limit=100` |

Interfejs za upravljanje aplikacijama zahteva autentifikaciju prijavljenog naloga i nije interfejs za anonimnu dinamičku registraciju (DCR). Endpoints za otkrivanje／registraciju samog MCP servisa razlikuju se od OAuth endpointa naloga u ovoj tabeli; pri povezivanju sa konkretnim MCP-om postupajte prema dokumentaciji i rezultatu otkrivanja tog servisa.

Dokument za otkrivanje koristi se za dobijanje endpointa i mogućnosti protokola. Trenutni tok vraća OAuth token, a ne vraća `id_token`; nemojte obrađivati tok kao potpuni OpenID Connect tok prijavljivanja samo zato što postoji `openid` scope.

## Opsezi dozvola: koristite trenutne nazive scope-ova

`scope` je naziv dozvole odvojen razmacima i razlikuje velika i mala slova. Nove aplikacije koriste konkretne dozvole kao što su `profile:read`, `email:read`, `phone:read`.

### Gde dobiti dozvole koje se mogu zatražiti

Nakon prijavljivanja, interfejs liste OAuth aplikacija `GET /api/v1/oauth2/applications/` vraća `available_scopes`; birač dozvola na stranici za upravljanje aplikacijama koristi isti katalog. Ovo su opcioni opsezi koje treba da koriste obične samouslužne aplikacije.

**`scopes_supported` iz Discovery-ja sadrži sve nazive dozvola koje platforma prepoznaje, ali ne znači da vaša aplikacija može da zatraži svaku od njih.** Stvarna autorizacija istovremeno proverava:

1. da li je dozvolu moguće delegirati tom tipu aplikacije;
2. da li je dozvola registrovana u dozvoljenim opsezima ove OAuth aplikacije;
3. da li trenutni korisnik poseduje zatraženu dozvolu.

Nepoznate, neregistrovane, nedozvoljene za delegiranje ili dozvole koje korisnik nema vraćaju `invalid_scope`. Pri zameni autorizacionog koda i osvežavanju takođe se vrši ponovna provera; dozvole se ne dopunjuju niti podižu automatski.

### Opcione dozvole za obične samouslužne aplikacije

Sledi trenutni katalog (2026-10-09); pri integraciji se vodite prema `available_scopes`.

| Scope                                            | Namena                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Čitanje／ažuriranje ličnog profila                               |
| `email:read`                                     | Čitanje e-pošte                                    |
| `phone:read`                                     | Čitanje broja mobilnog telefona i regiona                                |
| `billing-profile:read` / `billing-profile:write` | Čitanje／upravljanje podacima za naplatu                               |
| `applications:read` / `applications:write`       | Čitanje／upravljanje pretplatama na usluge                               |
| `credentials:read` / `credentials:write`         | Čitanje／upravljanje API Key-evima                           |
| `usage:read`                                     | Čitanje zapisa o pozivima                                  |
| `orders:read` / `orders:write`                   | Čitanje／kreiranje i upravljanje porudžbinama                              |
| `auto-recharge:read` / `auto-recharge:write`     | Čitanje／upravljanje podešavanjima automatske dopune                             |
| `recharge-cards:redeem`                          | Iskorišćavanje kartica za dopunu                                   |
| `coin:read`                                      | Čitanje informacija povezanih sa tokenima                                |
| `distribution:read`                              | Čitanje informacija o distribuciji                                  |
| `connections:read` / `connections:write`         | Čitanje／upravljanje konekcijama                                 |
| `skills:read` / `skills:write`                   | Čitanje／upravljanje veštinama                                 |
| `openid`                                         | Trenutna implementacija takođe dozvoljava UserInfo da vrati osnovne podatke; ne vraća ID Token    |
| `offline_access`                                 | Zahtevanje refresh tokena radi osvežavanja nakon isteka access tokena |

Na primer, za samo čitanje ličnog profila koristite `profile:read`; za e-poštu dodajte `email:read`; za čitanje postojećih API Key-eva koristite `profile:read credentials:read`. `credentials:write` zatražite samo kada je zaista potrebno kreirati ili menjati Key, a `offline_access` dodajte kada je potrebno osvežavanje.

Neke dozvole su dostupne samo pouzdanim aplikacijama koje je platforma odobrila, na primer `sites:read`, `sites:write`, `platform-tokens:read`; druge dozvole nisu otvorene za obične OAuth aplikacije trećih strana. Tip klijenta `public`／`confidential` opisuje da li može da čuva secret i nije povezan sa time da li je aplikacija pouzdana. Samouslužno kreirane aplikacije ne mogu same da uključe pouzdane dozvole.

`account` je birač dozvola naloga koji koristi određeni zvanični MCP za upravljanje nalozima, a ne scope „svih dozvola“ za aplikacije trećih strana, i ne može se mešati sa drugim scope-ovima. Treće strane treba jasno da navedu konkretne dozvole koje su im potrebne.

### Migracija sa stare dokumentacije

| Stari zapis                                         | Trenutni način                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Pojedinačno navedite konkretne dozvole koje su stvarno potrebne, ne postoji univerzalna zamena „izaberi sve“ |

Stari nazivi se ne prihvataju kao kompatibilni aliasi. Istovremeno ažurirajte scope-ove registrovane za OAuth aplikaciju, URL za autorizaciju i sopstvenu proveru dozvola; izmena konfiguracije aplikacije neće dodati dozvole već izdatim tokenima, korisnik mora ponovo da autorizuje.

## Korak 1: Registrujte OAuth aplikaciju

Otvorite [upravljanje OAuth aplikacijama](https://auth.acedata.cloud/user/oauth-apps), kreirajte aplikaciju i popunite:
- Naziv, opis, Logo aplikacije: prikazuju se na strani aplikacije na stranici za autorizaciju.
- Tip klijenta: za čisto frontend, mobilne ili desktop klijente izaberite **Public**; za servise koji mogu čuvati secret na backendu izaberite **Confidential**.
- Adresa povratnog poziva: u produkcionom okruženju koristite HTTPS i registrujte potpuni URL koji aplikacija zaista koristi za obradu povratnog poziva.
- Dozvole: iz direktorijuma koji pruža stranica izaberite scopes koji su stvarno potrebni.

Sačuvajte `client_id`. Confidential klijenti čuvaju `client_secret` na strani servera i ne smeju ga stavljati u HTML, frontend build promenljive ili URL. Public klijenti ne koriste secret prilikom zamene za token; čak i ako odgovor registracije sadrži to polje, ne sme se tretirati kao podatak koji klijent može držati tajnim.

`redirect_uri` mora biti potpuno identičan pri registraciji, autorizaciji i zameni tokena, uključujući putanju, završnu kosu crtu i parametre upita. Svaki nalog može kreirati najviše 20 aplikacija. Secret se prikazuje samo pri kreiranju／rotaciji; nakon rotacije stari secret više ne može da obavlja zamene koje zahtevaju autentifikaciju klijenta.

## Korak 2: Dugme pokreće autorizaciju

Pri svakom kliku na povezivanje generišite novi nasumični `state` i `code_verifier`, izračunajte:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Sačuvajte `state`, verifier i adresu povratnog poziva u sopstvenoj sesiji aplikacije, a zatim otvorite stranicu za autorizaciju sa URL-kodiranim parametrima:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<完整回调地址>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<本次随机值>
  &code_challenge=<本次S256挑战值>
  &code_challenge_method=S256
```

Public klijenti moraju slati S256 PKCE. Iako Discovery i dalje navodi `plain`, Public klijenti ga ne smeju koristiti. Confidential klijentima se takođe preporučuje korišćenje S256; ako je PKCE korišćen pri pokretanju autorizacije, pri zameni se mora poslati odgovarajući verifier.

Nakon što korisnik pristane, vraća se na `redirect_uri`, a parametri upita sadrže `code` i neizmenjeno vraćeni `state`. Pri odbijanju se vraćaju `error=access_denied`, opis greške i `state`. Pre obrade povratnog poziva prvo proverite da li se state podudara sa trenutnom sesijom. Autorizacioni kod važi 10 minuta i može se zameniti samo jednom; nakon neuspeha ponovo pokrenite povezivanje, nemojte više puta osvežavati stari URL povratnog poziva.

## Korak 3: Preuzimanje OAuth tokena

Public klijenti zamenu obavljaju direktno iz pregledača ili klijenta; Confidential klijenti zamenu obavljaju na sopstvenom backendu. Telo zahteva podržava form-kodiranje, a sledeće promenljive predstavljaju podatke koje je aplikacija dobila ovom autorizacijom:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Confidential klijenti takođe treba da dodaju polje obrasca `client_secret` na strani servera. Trenutno je podržan `client_secret_post`; nemojte HTTP Basic autentifikaciju klijenta smatrati podržanim načinom.

Iz uspešnog odgovora pročitajte `access_token`, `token_type`, `expires_in` i stvarno dodeljeni `scope`. `refresh_token` postoji samo ako je zatražen i odobren `offline_access`. Nemojte OAuth access token tretirati kao API Key za model API, niti upisivati token, verifier ili autorizacioni kod u logove, analitičke događaje ili linkove za deljenje.

## Korak 4: Čitanje korisničkih informacija i API Key-a

Najpre koristite OAuth access token da zatražite UserInfo:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Vraćena polja zavise od scope-a: `id` je identifikator korisnika; `profile:read` ili `openid` omogućavaju čitanje osnovnih podataka (kao što su `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); za e-poštu je potreban `email:read`, a za broj telefona i region potreban je `phone:read`. Nemojte se oslanjati na to da su neautorizovana polja uvek prisutna.

Kada je potreban postojeći API Key i odobren je `credentials:read`, koristite `id` iz UserInfo kao uslov filtriranja:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Vraćena lista koristi `count` i `items`, a polje Key-a je **`items[*].token`**, a ne `data[0].value`. `user_id=me` nije važeći korisnički ID za ovaj interfejs. Za podatke na više stranica nastavite čitanje prema `offset`／`limit`, nemojte prvu stranicu tretirati kao sve kredencijale.

Izaberite primenljivi kredencijal prema aplikaciji, servisu i statusu važenja, nemojte naslepo uzimati prvi. Prazna lista ne znači da je autorizacija neuspešna; korisnik možda još nije kreirao primenljivi Key. Kontrola dozvola OAuth access tokena i opseg servisa, kvote i uslovi isteka samog API Key-a su različita ograničenja.

**Dozvola za čitanje API Key-a znači da ga treća strana može sačuvati i koristiti. Opozivanje OAuth zahteva ili brisanje stanja prijave u aplikaciji neće poništiti već kopirani API Key; korisnik mora zasebno opozvati ili rotirati taj Key u upravljanju kredencijalima.**

## Pokretni Public / PKCE primer za pregledač

Postavite sledeću stranicu na svoj registrovani `REDIRECT_URI`, zamenite `CLIENT_ID` i adresu povratnog poziva. Dugme pokreće standardnu autorizaciju, a nakon povratka na istu stranicu čita lične podatke i broj postojećih Key-eva. Primer ne prikazuje niti trajno čuva Key; produkciona aplikacija koristi rezultate prema stvarnoj nameni. Najpre proverite na zasebnoj stranici pregledača, a zatim izvršite prihvat prema kasnijim iframe zahtevima.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Povezivanje sa Ace Data Cloud</title>
<button id="connect" type="button">Poveži nalog</button>
<p id="status" role="status">Nije povezano</p>
<script type="module">
const CLIENT_ID = 'Zamenite svojim client_id';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`API je vratio HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = 'Nije moguće započeti povezivanje, proverite podešavanja skladišta pregledača i pokušajte ponovo.';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('Sesija autorizacije se ne podudara, povežite ponovo.');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('Sesija autorizacije je istekla, povežite ponovo.');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('Autorizacija nije dovršena, možete ponovo povezati.');
    if (!code) throw new Error('Povratni poziv nema autorizacioni kod, povežite ponovo.');
    status.textContent = 'Povezivanje u toku…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('Autorizacioni token nije dobijen.');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('Identifikator korisnika nije dobijen.');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('Format liste akreditiva nije odgovarajući.');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `Povezan je ${profile.nickname || profile.username || profile.id}; ova stranica ima ${keyCount} API ključeva.`;
  } catch (error) {
    status.textContent = `Povezivanje nije dovršeno: ${error.message || 'mrežna greška'} Kliknite ponovo na povezivanje.`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Povratni poziv i ulaz u primeru moraju biti istog porekla, u istoj kartici pregledača／iframe-u, kako bi mogli da čitaju prethodno sačuvani `sessionStorage`. Produkciona aplikacija treba da upravlja tokenima u okviru sopstvene šeme sesije, obrađuje istek i ukloni parametre autorizacionog URL-a nakon prijema odgovora; glavni interfejs stranice treba prvo da se prikaže, a mrežni neuspeh treba da utiče samo na status povezivanja.

## iframe na white-label sajtu

### Klijentski sajt samostalno preusmerava na stranicu autorizacije

Dovoljno je koristiti standardne OAuth parametre i sopstvenu obradu povratnog poziva; `window.location.assign()` navigira trenutni iframe, dok nadređena stranica ostaje na white-label domenu. Nema potrebe da se radi ikone dodaje `embed=studio` niti da se implementira Studio protokol poruka.

Moraju biti ispunjeni sledeći uslovi:

- Stranica aplikacije i stranica povratnog poziva koriste HTTPS, stvarno su dostupne i dozvoljavaju ugrađivanje putem iframe-a od strane white-label nadređenog domena; proverite `Content-Security-Policy: frame-ancestors` i `X-Frame-Options` obe strane.
- sandbox dozvoljava skripte, obrasce i mogućnosti porekla／skladišta potrebne stranici. Pri podršci za prijavu kroz iskačući prozor potrebne su i odgovarajuće mogućnosti za iskačuće prozore; prednost dajte konfiguraciji Website komponente koju pruža Studio.
- Pregledač dozvoljava skladište potrebno za stanje autorizacije u trenutnom scenariju ugrađivanja. Stanje prijave na white-label sajt i stanje prijave na AuthFrontend mogu se razlikovati, pa ne treba pretpostaviti da prijava na white-label sajt znači i prijavu na stranicu autorizacije.
- Usluga razmene tokena u povratnom pozivu je dostupna, a zahtevi između porekla dozvoljavaju poreklo aplikacije; DNS, CORS i HTTP greške moraju prikazati stanje koje omogućava ponovni pokušaj i ne smeju sprečiti prikazivanje cele stranice.

Leva strana stranice autorizacije čita OAuth aplikacioni Logo; desna strana čita favicon／logo tog Site-a kada pregledač može da pruži poreklo roditelja i kada nadređeni domen prođe proveru verifikovanog sajta, u suprotnom prikazuje podrazumevanu ikonu. Ovo određuje samo prikaz brenda, ne uspostavlja sesiju prijave niti klijentskoj stranici pruža dozvole naloga.

**Trenutno ograničenje: kada je za običan OAuth u iframe-u potrebna ponovna prijava, još postoji praznina u toku povratka na stranicu autorizacije nakon završetka prijave.** Pre puštanja u rad moraju se zasebno prihvatno testirati „Auth je prijavljen” i „Auth nije prijavljen／je istekao”. Dok se ova praznina ne ispravi i ne verifikuje, za prvu prijavu možete koristiti zasebnu stranicu za dovršavanje standardnog OAuth-a ili koristiti autorizaciju Studio komponente u nastavku; nemojte obećavati da su svi iframe scenariji dostupni samo na osnovu rezultata testiranja u prijavljenom stanju.

### Korišćenje autorizacije trenutnog Studio naloga

U Studio-u, u „Podešavanja → Početna → Komponente sajta”, uključite OAuth, popunite `client_id` i registrovanu adresu povratnog poziva. Sajt i povratni poziv moraju koristiti isto HTTPS poreklo i razlikovati se od Studio porekla. Stranica treće strane treba da:

1. Pošalje `acedatacloud:oauth:ready` tačnom origin-u nadređenog sajta, primi i proveri `acedatacloud:oauth:init`.
2. Dugme generiše state i PKCE verifier, pošalje `acedatacloud:oauth:authorize` (state, S256 challenge); verifier ostaje unutar sopstvene stranice.
3. Proveri nadređeni prozor, origin i state, obradi code ili error u `acedatacloud:oauth:result` i razmeni ih preko standardne token krajnje tačke.
Studio prikazuje stranicu za autorizaciju u oblasti komponente, nakon pristanka korisnika vraća autorizacioni kod porukom, aplikacija ne mora da preusmerava. Kada nema prijave vraća `login_required`, pri odbijanju vraća `access_denied`, a pri isteku čekanja vraća `authorization_timeout`. Promena naloga će ponovo izgraditi iframe aplikacije i otkazati nedovršene autorizacije.

Komponenta trenutno zahteva `profile:read credentials:read`, ne uključuje `offline_access`. Ne pretpostavljajte da se refresh token sigurno može primiti. `embed=studio` i `embed_origin` održavaju Studio domaćin i stranica za autorizaciju, stranica klijenta treba samo da poštuje protokol poruka.

Potpun primer dugmeta pogledajte u [Vodiču za OAuth integraciju Studio veb komponente](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Životni ciklus, osvežavanje i opoziv

Podrazumevani period važenja access tokena je 15 dana, osvežavanje ili ponovnu autorizaciju treba zakazati prema `expires_in` iz svakog odgovora; refresh token podrazumevano traje 30 dana, a rok zavisi od konfiguracije usluge. Nemojte ove dve vrednosti tvrdo kodirati kao trajna obećanja.

Nakon odobrenog `offline_access`, može se pozvati:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Osvežavanje vraća nove tokene, aplikacija treba da sačuva najnovije vrednosti. Pri osvežavanju se proverava da li je aplikacija i dalje važeća, da li je korisnik dostupan i da li su dozvole i dalje odobrene. Pri neuspehu obrišite sopstveno stanje veze i ponovo autorizujte.

**Trenutna OAuth implementacija osvežavanja ne garantuje da stari refresh token postaje nevažeći odmah nakon osvežavanja.** Nemojte dobijanje novog tokena smatrati dokazom da je stari token opozvan, niti koristite rotaciju secret-a kao zamenu za ukidanje postojećih tokena.

Način pozivanja zahteva za opoziv je:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Trenutni endpoint za opoziv vraća HTTP 200, ali ne implementira trenutno poništavanje već izdatih JWT-ova.** Aplikacija treba da obriše tokene koje sama čuva i ne može smatrati 200 dokazom da su svi izdati tokeni ili API Key-jevi postali nevažeći. API Key-jeve koji su procureli ili kopirani treba zasebno opozvati ili rotirati odgovarajuće akreditive.

## Uobičajene greške i prihvatanje

| Pojava／greška                         | Provera                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Koristite trenutne nazive dozvola; proverite opseg registracije aplikacije, ograničenja delegiranja i dozvole korisnika. Discovery ceo direktorijum nije direktorijum koji aplikacija može da izabere                      |
| `invalid_request`             | Obavezni parametri, tačna povratna adresa, S256 challenge i method za Public klijente                        |
| `invalid_client`              | client ID, status aplikacije, secret za Confidential klijente; proverite da li je Basic autentifikacija pogrešno korišćena             |
| `invalid_grant`               | code je istekao／već je iskorišćen, verifier ili redirect URI se ne podudaraju; pri osvežavanju se takođe proveravaju promene aplikacije i dozvola                 |
| `access_denied`               | Korisnik je odbio, vratite dugme za povezivanje, nemojte u petlji prikazivati autorizaciju                                                  |
| `unsupported_grant_type`      | Trenutno su podržani `authorization_code`, `refresh_token`                             |
| HTTP 401／403                  | Razlikujte nevažeće stanje prijave, token, autorizacioni scope i prava pristupa samom resursu                                     |
| `Failed to fetch`, DNS／CORS greške | Proverite stvarni host zahteva i dostupnost pozadinskog sistema klijenta, ne može se pripisati tome da „korisnik nema Key“                                      |
| Autorizovano, ali Key ne može da se pročita                   | Koristite `platform.acedata.cloud`, stvarni user ID, `items[*].token`; razlikujte praznu listu, paginaciju i neuspešne odgovore |
| Cela stranica je prazna nakon povratka autorizacije                     | Stranica prvo treba da se prikaže; callback, token, UserInfo i zahtevi za akreditive treba zasebno da obrađuju greške; nemojte dozvoliti da greška inicijalizacije zaustavi celu stranicu                      |
| iframe se ne nastavlja nakon prijave                 | Postupajte prema postojećim ograničenjima iznad, testirajte scenarije neprijavljenosti, isteka, odbijanja i ponovnog povezivanja                                          |

Pre isporuke najmanje proverite: ispravan callback, odbijanje, pogrešan state, istekao／već iskorišćen code, bez Key-ja, neuspeh mreže, istek tokena, nedostajući potreban scope, kao i prvu prijavu i promenu naloga u iframe scenariju. U dokazima testiranja ne čuvajte potpuni code, token ili API Key.
