Facilitator je serverska komponenta za poravnanje u X402 lancu. Klijent je odgovoran za potpisivanje, a Gateway ili vaš server je odgovoran za pozivanje `/verify` i `/settle` Facilitatora.

Adresa produkcionog Facilitatora kompanije Ace Data Cloud je:

```text
https://facilitator.acedata.cloud
```

Repozitorijum izvornog koda: [https://github.com/AceDataCloud/FacilitatorX402](https://github.com/AceDataCloud/FacilitatorX402)

## v2 wire konvencije

X402 lanac kompanije Ace Data Cloud u potpunosti koristi zvanični x402 v2 i više ne prihvata `X-Payment` zaglavlje zahteva iz v1. Prilikom integracije treba obratiti pažnju na tri stvari:

- Zaglavlje zahteva je `PAYMENT-SIGNATURE`, a vrednost je JSON envelope kodiran u base64.
- Najviši nivo envelope-a mora biti `x402Version: 2`, a objekat `accepted` se koristi za deklarisanje izabranih `scheme` i `network` za ovaj put.
- `network` koristi CAIP-2 identifikator (kao što je `eip155:8453`), i ne može se pisati skraćenica poput `base`.

Struktura envelope-a:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": { "...": "..." }
}
```

Pored JSON body-ja, 402 odgovor takođe nosi zaglavlje odgovora `PAYMENT-REQUIRED`, čija je vrednost base64 kodiranje istog sadržaja izazova, što klijentu olakšava čitanje zahteva za plaćanje bez parsiranja body-ja.

## Osnovni interfejsi

### `GET /supported`

Pogledajte podržane mreže i scheme-ove:

```bash
curl https://facilitator.acedata.cloud/supported
```

Primer povratne vrednosti:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ],
  "extensions": [],
  "signers": {
    "eip155:*": [
      "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708"
    ],
    "solana:*": ["3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq"]
  }
}
```

Objašnjenje rezultata:

- `network` koristi CAIP-2 identifikator, a ne skraćenice poput `base` ili `solana`.
- `/supported` označava da Facilitator ima odgovarajuće mogućnosti verifikacije i poravnanja.
- I Base i Solana podržavaju `exact`; `upto` je trenutno dostupan samo na Base-u.
- `signers` su adrese koje Facilitator koristi za slanje transakcija poravnanja.
- Da li određeni API dozvoljava ove opcije i dalje zavisi od `accepts` u 402 odgovoru tog API-ja.

### `POST /verify`

Verifikujte da li `PAYMENT-SIGNATURE` koji je poslao klijent ispunjava određeni payment requirement.

Telo zahteva:

```json
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "accepted": {
      "scheme": "exact",
      "network": "eip155:8453"
    },
    "payload": { "...": "..." }
  },
  "paymentRequirements": {
    "scheme": "exact",
    "network": "eip155:8453",
    "asset": "0x...",
    "amount": "95215",
    "payTo": "0x...",
    "maxTimeoutSeconds": 3600,
    "extra": { "...": "..." }
  }
}
```

Polja `paymentRequirements` u v2 su `scheme`, `network`, `asset`, `amount`, `payTo`, `maxTimeoutSeconds` i `extra`, a polje za iznos je `amount`. `accepts[]` u API 402 odgovoru takođe dodatno vraća `maxAmountRequired` kako bi klijent pročitao gornju granicu, ali ono nije polje tela zahteva Facilitator-a.

Uspešan odgovor:

```json
{
  "isValid": true,
  "invalidReason": null,
  "payer": "0x..."
}
```

Nakon dekodiranja zaglavlja odgovora `PAYMENT-RESPONSE` za plaćanje produkcione porudžbine, ono sadrži rezultat settlement-a. Rezultat izvršavanja programa za plaćanje Base porudžbine:

```text
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order 78481793-304e-47f7-bc0c-8231aec9cc1e state Finished pay_way X402 price 1.2
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Objašnjenje rezultata:

- `success=True` označava da je Facilitator settlement uspešan.
- `transaction` je heš transakcije na lancu, a `pay_id` porudžbine se takođe upisuje kao ista vrednost.
- U explorer-u se može videti transfer od `1200000` atomic USDC na Base-u.
- `errorReason=None` označava da ovaj settlement nije vratio poslovnu grešku.

Neuspešna verifikacija takođe obično vraća HTTP 200, ali je `isValid` `false`. Poslovna strana treba da pročita `invalidReason`, umesto da gleda samo HTTP statusni kod.

### `POST /settle`

Poravnajte već verifikovanu autorizaciju na lancu.

Telo zahteva je u osnovi isto kao za `/verify`. Razlika za `upto` je: `paymentRequirements.amount` se pri settle-u prepisuje stvarnim iznosom poravnanja; gornju granicu potpisa Facilitator beleži u fazi verify, a pri settle-u proverava da stvarni iznos ne premašuje tu granicu.

Uspešan odgovor:

```json
{
  "success": true,
  "errorReason": null,
  "transaction": "0x...",
  "network": "eip155:8453",
  "payer": "0x...",
  "amount": "3"
}
```

Ako je stvarni iznos `upto` 0, `transaction` može biti prazan string, što označava da nije potrebno slati transakciju na lanac.

## Kako Ace Data Cloud Gateway koristi Facilitator

Lanac Ace Data Cloud API Gateway-a je sledeći:

1. Klijent prvi put zahteva API, bez `Authorization` i `PAYMENT-SIGNATURE`.
2. Gateway izračunava procenjenu cenu zahteva, vraća 402 i `accepts`.
3. Klijent nakon potpisivanja ponavlja zahtev sa `PAYMENT-SIGNATURE`.
4. Gateway dekodira `PAYMENT-SIGNATURE` i bira odgovarajući payment requirement.
5. Gateway poziva Facilitator `/verify`.
6. Nakon uspešnog `/verify`, Gateway propušta zahtev do ciljnog API-ja.
7. Nakon što ciljni API vrati odgovor, Gateway u fazi `/record` poziva Facilitator `/settle`.
8. Gateway upisuje heš transakcije na lancu u metadata zapisa o korišćenju.

`exact` u koraku 7 poravnava potpisani iznos; `upto` u koraku 7 upisuje `amount` prema stvarnoj potrošnji, a zatim poravnava stvarni iznos.

## Kako integrisati sopstveni API

Ako želite da vaš sopstveni API podržava X402, možete ga implementirati prema ovoj strukturi:
1. Pripremite `paymentRequirements` za svaki plaćeni interfejs, uključujući mrežu, iznos, adresu primaoca, adresu sredstva i domen potpisa.
2. Ako zahtev nema `PAYMENT-SIGNATURE`, vratite HTTP 402 i `accepts`.
3. Ako zahtev ima `PAYMENT-SIGNATURE`, Base64 dekodiranjem dobijte `paymentPayload`.
4. Pozovite Facilitator `/verify`.
5. Nakon uspešne verifikacije izvršite poslovnu logiku.
6. Nakon uspešne poslovne logike pozovite Facilitator `/settle`.
7. Sačuvajte `payer`, `transaction`, `amount`, `network` radi usklađivanja.

Server mora da koristi sopstveno generisane `paymentRequirements` za pozivanje `/verify` i `/settle`, nemojte verovati iznosu, adresi primaoca ili adresi sredstva koje je klijent vratio.

## Zaštita od ponavljanja

Facilitator beleži nonce. Autorizacija sa istim nonce-om ne može se više puta verifikovati i poravnati.

To znači:

- Klijent bi za svaki zahtev trebalo da potpiše novi envelope;
- Ako je `/settle` već poslao transakciju, ali ona privremeno nije potvrđena, možete ponovo pokušati `/settle` sa istim nonce-om radi idempotentnog usklađivanja;
- Nemojte keširati isti `PAYMENT-SIGNATURE` i zatim ga koristiti za više API poziva.

## Česte greške

| Greška                                           | Čest uzrok                                                             |
| -------------------------------------------- | ---------------------------------------------------------------- |
| `Authorization nonce already processed`      | Ponovo je korišćen isti `PAYMENT-SIGNATURE`.                                    |
| `Authorization destination mismatch`         | `to` u potpisu klijenta se ne podudara sa `payTo` u payment requirement-u.                |
| `invalid_upto_evm_payload_invalid_signature` | chainId, facilitator, Permit2 domain ili adresa potpisa u `upto` typed data se ne podudaraju. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Novčanik još nije odobrio Permit2 dovoljan USDC allowance.                        |
| `Payer has insufficient USDC balance`        | USDC sredstva u novčaniku platioca nisu dovoljna.                                                    |
| `Solana signer private key not configured`   | Facilitator mora da potpiše kao fee payer, ali serveru nedostaje Solana signer konfiguracija.           |
