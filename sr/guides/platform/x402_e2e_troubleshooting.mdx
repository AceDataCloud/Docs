X402 obuhvata HTTP, SDK, potpise, Facilitator i transakcije na lancu. Prilikom otklanjanja problema sa potpisima ili poravnanjem, preporučuje se potvrđivanje sloj po sloj redosledom „javni ulaz -> 402 odgovor -> SDK payment handler -> settlement na lancu“. Ovo uputstvo objašnjava načine provere svakog sloja i navodi uobičajene greške.

## Provera javnog ulaza

Deklaracija mogućnosti Facilitator-a:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Ako se vrate `facilitator`, `supportedKinds` i krajnje tačke protokola, to znači da su metapodaci o mogućnostima ispravni. Otkrivanje API resursa je povučeno; direktno pozovite ciljni API i oslonite se na 402 odgovor u realnom vremenu.

Podržane mogućnosti Facilitator-a:

```bash
curl https://facilitator.acedata.cloud/supported
```

Ako se vrati `kinds`, to znači da Facilitator ulaz radi ispravno.

## Provera 402 `accepts`

Pošaljite neautentifikovan zahtev koji neće naplatiti troškove:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Proverite da li `accepts` u odgovoru sadrži mrežu koju želite da koristite. `network` je CAIP-2 identifikator:

- `eip155:8453` + `exact` (Base)
- `eip155:8453` + `upto` (Base, naknadno merenje)
- `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` + `exact` (Solana)

Ako ciljna mreža ne postoji, to znači da taj API ili trenutno okruženje nema konfigurisan odgovarajući X402 metod naplate.

## Pokretanje naprednih alata za verifikaciju X402Client-a

X402Client repozitorijum pruža napredne alate za verifikaciju, koji se mogu koristiti za potvrđivanje izbora 402 odgovora, generisanja potpisa, paid retry-ja i settlement-a na lancu. Oni zahtevaju funded wallet, RPC, privatni ključ i razvojne zavisnosti. Za uobičajenu poslovnu integraciju preporučuje se da se prvenstveno koriste TypeScript ili Python SDK; ove alate pokrenite samo kada je potrebno locirati probleme sa potpisima ili poravnanjem na lancu.

Adresa repozitorijuma: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)

```bash
git clone https://github.com/AceDataCloud/X402Client.git
cd X402Client/typescript
npm install
npm install --no-save ethers @solana/spl-token bs58 tsx
```

Base:

```bash
export X402B_BASE_PAYER_PRIVATE_KEY=0x...
TEST_API_PATH='/openai/chat/completions' \
TEST_BODY='{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}],"max_tokens":10}' \
npx tsx scripts/test-real-e2e.ts
```

Solana:

```bash
export X402B_SOLANA_PAYER_PRIVATE_KEY=...
npx tsx scripts/test-solana-e2e.ts
```

Alati za verifikaciju obično ispisuju:

1. 402 odgovor prvog zahteva.
2. Izabrani payment requirement.
3. Sažetak potpisanog `PAYMENT-SIGNATURE`.
4. HTTP status i telo odgovora nakon ponovnog pokušaja.
5. Settlement transaction na lancu ili razlog Facilitator greške u slučaju neuspeha.

Ne šaljite privatne ključeve ili puni `PAYMENT-SIGNATURE` u sisteme za logovanje ili tikete.

Primer rezultata verifikacije javnog API-ja:

```text
Base exact
HTTP 402 -> HTTP 200
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC

Solana exact
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run because public RPC lookup hit 429

Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Objašnjenje:

- Base `exact`, Solana `exact` i Base `upto` su svi završili paid retry od HTTP 402 do HTTP 200.
- Transakcija na lancu za Base `exact` može se pronaći na BaseScan-u, a iznos poravnanja je `95215` atomic USDC.
- Limit potpisa za Base `upto` je `95215` atomic USDC, ali stvarni settlement na lancu je `3` atomic USDC, što pokazuje da naknadno merenje naplaćuje prema stvarnoj potrošnji.
- Za Solana putanju su potvrđeni paid retry i izlaz modela. Javni RPC može ograničavati broj zahteva; kada je potrebno strogo usaglašavanje na lancu, koristite sopstveni Solana RPC ili potvrdite potpis transakcije putem platformskih zapisa o poravnanju.

## SDK smoke test

Napredni alati za verifikaciju koriste se za proveru potpisa i settlement-a na lancu. Poslovna strana takođe treba da izvrši SDK smoke test, kako bi potvrdila da aplikacioni kod može automatski da obradi 402 putem payment handler-a. U nastavku su prikazani samo ključni isečci; kompletan kod treba dopuniti novčanikom, provider-om i import-ima.

TypeScript:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const res = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly ADC_SDK_X402_OK' }],
  max_tokens: 8
});
```

Python:

```python
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
    )
)

res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly ADC_PY_X402_OK"}],
    max_tokens=8,
)
```

Ako model vrati fiksni string prema zahtevu, to znači da su SDK, payment handler, Gateway, Facilitator i ciljni API povezani.

Gornja dva smoke test-a koriste Base `exact` i poravnavaju fiksni iznos prema 402 ponudi. Chat completion pripada scenariju koji se meri po tokenima; pri formalnoj integraciji preporučuje se prosleđivanje `preferScheme: 'upto'` (u Python-u `prefer_scheme="upto"`), radi poravnanja prema stvarnoj potrošnji.

Povratni objekat Python SDK-a je `dict`, a sadržaj se može pročitati pomoću `res["choices"][0]["message"]["content"]`.

## E2E plaćanje narudžbine

Plaćanje narudžbine koristi platformski API sa `platform.acedata.cloud` i zahteva token platformskog naloga. Kompletan tok je: kreiranje Pending narudžbine, `POST /api/v1/orders/{order_id}/pay/` pokreće 402, a zatim se zahtev ponavlja sa `PAYMENT-SIGNATURE`.

Primer rezultata verifikacije plaćanja narudžbine malog iznosa:

> Sledeći zapisi transakcija su istorijski stvarni uzorci testirani prema staroj politici; iznosi i heševi transakcija zadržani su neizmenjeni. Nove X402 narudžbine više nemaju popuste po načinu plaćanja; kao osnov za potpis i plaćanje koristite `amount` iz ovog 402 odgovora.
```text
kreirana porudžbina 78481793-304e-47f7-bc0c-8231aec9cc1e
kreirano stanje Pending
kreirana cena 1.26

http_status=402
x402Version 2
accepts [('eip155:8453', 'exact', '1200000'), ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000')]

status 200
stanje porudžbine Finished
pay_way X402
pay_id 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}

Base status tx 1
blok 46726704
istraživač https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
vrednost transfera 1200000 atomic USDC
```

Objašnjenje rezultata:

- Nakon kreiranja porudžbine, stanje porudžbine je `Pending`, a cena je `1.26`.
- Prvi `pay/` zahtev vraća HTTP 402, `accepts` sadrži Base `exact` i Solana `exact`, a iznosi su oba `1200000` atomic USDC.
- Nakon ponovnog pokušaja sa Base `PAYMENT-SIGNATURE`, vraća se HTTP 200, stanje porudžbine se menja u `Finished`, a `pay_way` je `X402`.
- Nakon dekodiranja `PAYMENT-RESPONSE`, prikazuju se `success=True`, `network=base` i isti heš transakcije.
- Na BaseScan-u je status transakcije `1`, iznos transfera je `1200000` atomic USDC, odnosno `1.2` USDC.
- Cena kreiranja `1.26` je plaćena tokom perioda stare politike popusta za X402 plaćanje, a konačni iznos potpisa i poravnanja je `1.2` USDC.

Ako plaćanje porudžbine nema `Authorization: Bearer {platform_token}`, ili porudžbina ne pripada trenutnom nalogu, neuspeh će nastati na sloju platformskih dozvola; to se razlikuje od X402 API-ja bez naloga pri direktnom pozivu `x402.acedata.cloud`.

## Česte greške

| Pojava                                           | Smer provere                                                                |
| -------------------------------------------- | ------------------------------------------------------------------- |
| Prvi zahtev nije 402                                  | Proverite da li je greškom dodat `Authorization`, ili da li taj API još nema X402 pricing.                  |
| `No payment requirement for network`         | Ciljna mreža nije u `accepts`, promenite mrežu ili proverite Gateway konfiguraciju.                               |
| `invalid_402`                                | 402 odgovor nije validan JSON, proverite proxy, gateway ili stranicu greške.                                        |
| `Authorization nonce already processed`      | Isti `PAYMENT-SIGNATURE` je ponovo korišćen, potpišite ponovo.                                  |
| `invalid_upto_evm_payload_invalid_signature` | Proverite da li su chainId za `upto`, Permit2 domain, facilitator adresa i nalog potpisa usklađeni.         |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Izvršite `approve-permit2` za USDC ciljnog lanca.                                     |
| `Payer has insufficient USDC balance`        | USDC sredstva novčanika platioca nisu dovoljna.                                                       |
| HTTP 200 ali bez tx hash                         | Stvarni iznos `upto` može biti 0, ili se settlement zapis još asinhrono upisuje.                             |
| Solana `Missing transaction payload`         | U `PAYMENT-SIGNATURE` envelope-u nema serijalizovane transakcije ili signature, proverite wallet adapter. |

## Base `upto` kontrolna lista

`upto` je trenutno dostupan samo na Base-u (`eip155:8453`). Pošto `upto` potpis vezuje više EVM typed data parametara, pri integraciji treba posebno potvrditi da se polja u realnom vremenu iz 402 odgovora potpuno podudaraju sa potpisom klijenta.

```text
Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Ako Base `upto` vrati `invalid_upto_evm_payload_invalid_signature`, prvo proverite:

1. `extra.chainId` u stavci `eip155:8453` + `upto` koju vraća API (treba da bude `8453`).
2. `extra.facilitatorAddress` koju vraća API.
3. Base `upto` facilitator adresu koju vraća `https://facilitator.acedata.cloud/supported`.
4. Permit2 domain, spender, USDC ugovor i nalog potpisa.
5. Da li je novčanik već odobrio Permit2 za Base USDC.

Digest potpisa za `upto` istovremeno vezuje Permit2 domain, chain ID, spender, adresu primaoca, facilitator adresu i validAfter. Ako bilo koja stavka nije usklađena, Facilitator će oporaviti pogrešan signer, pa će vratiti invalid signature. Ako su sve ove stavke usklađene, ali se i dalje vraća 402, sledeće proverite Permit2 allowance; kada nema odobrenja vraća se `PERMIT2_ALLOWANCE_REQUIRED`.

## Sačuvajte informacije za verifikaciju

Potpuna verifikacija treba najmanje da sačuva:

- API path i sažetak tela zahteva;
- izabrani network i scheme;
- `maxAmountRequired`;
- adresu payer novčanika;
- konačni HTTP status;
- izlaz modela ili ID zadatka iz odgovora;
- link settlement transakcije;
- Gateway trace ID ili ID evidencije korišćenja platforme.

Nemojte čuvati privatne ključeve, kompletan `PAYMENT-SIGNATURE`, kompletan EIP-712 signature ili seed frazu.

## Strukturirane greške plaćanja

X402 neuspeh nakon potpisa vraća stabilan `code`, parametre za bezbednu interpolaciju, fazu i oznaku mogućnosti ponovnog pokušaja u `extensions.acedatacloud.paymentError`. Dajte prednost otklanjanju problema pomoću ove strukture, nemojte parsirati engleski `error` najvišeg nivoa, niti tražiti od korisnika da dostavi potpis novčanika ili originalni tekst simulacije na lancu.

- `charged: false`: verifikacija je jasno odbijena pre poravnanja, za ovaj put nije pokrenuta naplata.
- Bez `charged`: rezultat je nepoznat ili je već ušao u fazu poravnanja, prvo proverite porudžbinu i stanje na lancu, strogo je zabranjeno direktno ponoviti plaćanje.
- `settlement_pending`: za sada nemojte ponavljati plaćanje, prvo osvežite porudžbinu ili kontaktirajte podršku.
- Neprepoznat code: tretirajte kao `payment_failed` i zadržite javni tehnički kod radi pretrage korisničke podrške.
