`allow_consume_global`을 설정합니다. 활성화하면, 조건에 부합하는 종량제 Application은 자체 잔액이 부족할 때 계정 전역 잔액을 계속 사용할 수 있습니다.

## 준비 작업

- [Account Token](https://platform.acedata.cloud/documents/platform-token)을 생성하고 안전하게 보관합니다.
- [서비스 신청 목록](https://platform.acedata.cloud/documents/platform-application-list)에서 본인이 소유한 `application_id`를 가져옵니다.

```shell
export PLATFORM_TOKEN='你的账户令牌'
export APPLICATION_ID='你的 Application ID'
```

## 인터페이스 개요

| 항목   | 내용                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------- |
| 메서드 | `POST`                                                                                             |
| URL  | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| 인증   | Account Token                                                                                      |
| Body | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

성공하면 업데이트된 Application 객체를 반환합니다. 요청 값이 반드시 저장된다고 가정하지 말고, 응답의 `allow_consume_global`을 기준으로 하십시오.

> `Period` 유형의 Application은 전역 잔액을 소비할 수 없습니다. `true`를 요청하더라도 서버는 이 필드를 `false`로 유지합니다.

## 오류 처리

- `401`: Account Token이 유효하지 않거나 누락되었습니다.
- `403`: 현재 계정이 해당 Application의 소유자가 아닙니다.
- `404`: Application ID가 존재하지 않습니다.

전역 잔액의 충전 경로와 사용 가능한 요금제는 플랫폼 콘솔 및 [주문 생성](https://platform.acedata.cloud/documents/platform-order-create)에서 반환되는 실제 요금제를 기준으로 하십시오. `Wallet` 유형 요금제가 존재한다고 가정하지 마십시오.

## 초과 인출이 승인된 애플리케이션

종량제 애플리케이션의 읽기 전용 필드가 `allow_overdraft=true`인 경우, 해당 애플리케이션은 잔액이 음수가 되더라도 자체 잔액에서 계속 요금이 차감되며, 잔액 부족으로 인해 전역 계정으로 전환되지 않습니다. 초과 인출이 활성화되지 않은 애플리케이션은 계속 `allow_consume_global`을 따릅니다. 전환 후 초과 인출 허용 여부는 실제로 요금이 차감되는 전역 Application의 설정을 기준으로 합니다.

## 체험 계정 동시성 제한

시스템은 읽기 전용 사용자 표시 `has_recharged`를 사용하여 유료 충전을 성공적으로 완료했거나 관리자가 수동으로 크레딧을 추가한 적이 있는지를 기록하며, 표시는 작업 성공 후 업데이트되고, 기존 사용자는 주문 또는 명확한 가산 기록에 따라 일괄 보완됩니다. 유료 충전을 하지 않았고 관리자에게 수동으로 크레딧을 추가받지도 않은 계정은 전체 계정에서 동시에 하나의 과금 요청만 실행할 수 있으며, 서로 다른 API Key와 서로 다른 서비스는 이 하나의 자리를 공유합니다. 보상, 교환 카드 및 양도 한도는 유료 충전으로 간주되지 않습니다. 이미 유료 충전을 완료했거나 관리자가 수동으로 크레딧을 추가한 계정은 이 체험 동시성 제한을 받지 않으며, 기존 잔액 및 자격 증명 한도 검사를 계속 따릅니다.

기존 요청이 실행 중인 경우 새 요청은 `429 too_many_requests`를 반환합니다. 작업 조회 등의 무료 폴링 인터페이스는 계속 정상적으로 호출할 수 있습니다. Realtime의 연결 인증은 기존 라운드별 과금 절차를 따르며, 이 일반 요청 자리를 점유하지 않습니다.

비동기 인터페이스가 “접수됨”을 반환할 때 작업은 여전히 실행 중이므로, 최종 결과를 기다린 후 다음 생성 요청을 제출해야 합니다. 네트워크 연결 끊김 또는 프록시 시간 초과는 작업이 이미 중지되었음을 의미하지 않습니다. 작업이 장시간 최종 상태에 도달하지 않으면 `trace_id`를 제공하여 지원팀에 확인을 요청하십시오.

이 제한은 체험 가능한 인터페이스를 변경하지 않으며, 기존 과금 규칙도 변경하지 않습니다. 비용은 계속 요청 종료 후 실제 사용량에 따라 정산됩니다.
