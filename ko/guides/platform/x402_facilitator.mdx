Facilitator는 X402 흐름의 서버 측 정산 구성 요소입니다. 클라이언트는 서명을 담당하고, Gateway 또는 당신의 서버는 Facilitator의 `/verify` 및 `/settle` 호출을 담당합니다.

Ace Data Cloud의 프로덕션 Facilitator 주소는 다음과 같습니다:

```text
https://facilitator.acedata.cloud
```

소스 코드 저장소: [https://github.com/AceDataCloud/FacilitatorX402](https://github.com/AceDataCloud/FacilitatorX402)

## v2 wire 규약

Ace Data Cloud의 X402 흐름은 공식 x402 v2를 전면 사용하며, 더 이상 v1의 `X-Payment` 요청 헤더를 허용하지 않습니다. 연동 시 세 가지 사항에 유의해야 합니다:

- 요청 헤더는 `PAYMENT-SIGNATURE`이며, 값은 base64로 인코딩된 JSON envelope입니다.
- envelope 최상위에는 반드시 `x402Version: 2`가 있어야 하며, `accepted` 객체를 사용하여 이번에 선택한 `scheme` 및 `network`를 선언합니다.
- `network`는 CAIP-2 식별자(예: `eip155:8453`)를 사용하며, `base`와 같은 약칭을 작성할 수 없습니다.

envelope 구조:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": { "...": "..." }
}
```

402 응답은 JSON body 외에도 `PAYMENT-REQUIRED` 응답 헤더를 함께 제공하며, 값은 동일한 challenge 내용의 base64 인코딩입니다. 이를 통해 클라이언트는 body를 파싱하지 않고도 결제 요구 사항을 읽을 수 있습니다.

## 핵심 인터페이스

### `GET /supported`

지원되는 네트워크와 scheme을 확인합니다:

```bash
curl https://facilitator.acedata.cloud/supported
```

반환 예시:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ],
  "extensions": [],
  "signers": {
    "eip155:*": [
      "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708"
    ],
    "solana:*": ["3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq"]
  }
}
```

결과 설명:

- `network`는 CAIP-2 식별자를 사용하며, `base`, `solana`와 같은 약칭이 아닙니다.
- `/supported`는 Facilitator가 해당 검증 및 정산 기능을 보유하고 있음을 나타냅니다.
- Base와 Solana는 모두 `exact`를 지원하며, `upto`는 현재 Base에서만 제공됩니다.
- `signers`는 Facilitator가 정산 트랜잭션을 제출하는 데 사용하는 주소입니다.
- 특정 API가 이러한 옵션을 허용하는지 여부는 여전히 해당 API의 402 `accepts`를 기준으로 합니다.

### `POST /verify`

클라이언트가 전달한 `PAYMENT-SIGNATURE`가 특정 payment requirement를 충족하는지 검증합니다.

요청 body:

```json
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "accepted": {
      "scheme": "exact",
      "network": "eip155:8453"
    },
    "payload": { "...": "..." }
  },
  "paymentRequirements": {
    "scheme": "exact",
    "network": "eip155:8453",
    "asset": "0x...",
    "amount": "95215",
    "payTo": "0x...",
    "maxTimeoutSeconds": 3600,
    "extra": { "...": "..." }
  }
}
```

v2의 `paymentRequirements` 필드는 `scheme`, `network`, `asset`, `amount`, `payTo`, `maxTimeoutSeconds`, `extra`이며, 금액 필드는 `amount`입니다. API 402 응답의 `accepts[]`에는 클라이언트가 상한을 읽을 수 있도록 `maxAmountRequired`도 추가로 반환되지만, 이는 Facilitator 요청 body의 필드에 속하지 않습니다.

성공 응답:

```json
{
  "isValid": true,
  "invalidReason": null,
  "payer": "0x..."
}
```

프로덕션 주문 결제의 `PAYMENT-RESPONSE` 응답 헤더를 디코딩하면 settlement 결과가 포함됩니다. Base 주문 결제의 프로그램 실행 결과:

```text
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order 78481793-304e-47f7-bc0c-8231aec9cc1e state Finished pay_way X402 price 1.2
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

결과 설명:

- `success=True`는 Facilitator settlement가 성공했음을 나타냅니다.
- `transaction`은 온체인 트랜잭션 해시이며, 주문의 `pay_id`에도 동일한 값이 기록됩니다.
- explorer에서 `1200000` atomic USDC의 Base USDC 전송을 확인할 수 있습니다.
- `errorReason=None`은 이번 settlement에서 비즈니스 오류가 반환되지 않았음을 나타냅니다.

검증 실패도 일반적으로 HTTP 200을 반환하지만, `isValid`는 `false`입니다. 비즈니스 측에서는 HTTP 상태 코드만 보지 말고 `invalidReason`을 읽어야 합니다.

### `POST /settle`

이미 검증된 승인을 온체인에 정산합니다.

요청 body는 `/verify`와 기본적으로 동일합니다. `upto`의 차이점은 다음과 같습니다: `paymentRequirements.amount`는 settle 시 실제 정산 금액으로 다시 작성됩니다. 서명 상한은 Facilitator가 verify 단계에서 기록하며, settle 시 실제 금액이 해당 상한을 초과하지 않는지 검증합니다.

성공 응답:

```json
{
  "success": true,
  "errorReason": null,
  "transaction": "0x...",
  "network": "eip155:8453",
  "payer": "0x...",
  "amount": "3"
}
```

`upto`의 실제 금액이 0인 경우, `transaction`은 빈 문자열일 수 있으며, 이는 온체인 트랜잭션을 보낼 필요가 없음을 나타냅니다.

## Ace Data Cloud Gateway가 Facilitator를 사용하는 방법

Ace Data Cloud API Gateway의 흐름은 다음과 같습니다:

1. 클라이언트가 처음으로 API를 요청하며, `Authorization` 및 `PAYMENT-SIGNATURE`를 포함하지 않습니다.
2. Gateway가 요청의 예상 가격을 계산하고, 402 및 `accepts`를 반환합니다.
3. 클라이언트가 서명 후 `PAYMENT-SIGNATURE`를 포함하여 재시도합니다.
4. Gateway가 `PAYMENT-SIGNATURE`를 디코딩하고, 일치하는 payment requirement를 선택합니다.
5. Gateway가 Facilitator `/verify`를 호출합니다.
6. `/verify` 성공 후, Gateway가 요청을 대상 API로 통과시킵니다.
7. 대상 API가 반환된 후, Gateway가 `/record` 단계에서 Facilitator `/settle`을 호출합니다.
8. Gateway가 온체인 트랜잭션 해시를 사용 기록 metadata에 기록합니다.

`exact`는 단계 7에서 서명 금액을 정산하며, `upto`는 단계 7에서 실제 사용량에 따라 `amount`를 기록한 후 실제 금액을 정산합니다.

## 자신의 API를 연동하는 방법

자신의 API가 X402를 지원하도록 하려면, 이 구조에 따라 구현할 수 있습니다:
1. 각 유료 엔드포인트에 대해 네트워크, 금액, 수금 주소, 자산 주소 및 서명 domain을 포함하는 `paymentRequirements`를 준비합니다.
2. 요청에 `PAYMENT-SIGNATURE`가 없으면 HTTP 402와 `accepts`를 반환합니다.
3. 요청에 `PAYMENT-SIGNATURE`가 있으면 Base64 디코딩하여 `paymentPayload`를 얻습니다.
4. Facilitator `/verify`를 호출합니다.
5. 검증 성공 후 비즈니스 로직을 실행합니다.
6. 비즈니스 성공 후 Facilitator `/settle`을 호출합니다.
7. 대사를 위해 `payer`, `transaction`, `amount`, `network`를 저장합니다.

서버는 자체 생성한 `paymentRequirements`를 사용하여 `/verify`와 `/settle`을 호출해야 하며, 클라이언트가 반환한 금액, 수금 주소 또는 자산 주소를 신뢰하지 마십시오.

## 재생 방지

Facilitator는 nonce를 기록합니다. 동일한 nonce의 승인은 중복 검증 및 결제할 수 없습니다.

이는 다음을 의미합니다:

- 클라이언트는 요청할 때마다 새로운 envelope에 서명해야 합니다;
- `/settle`이 트랜잭션을 제출했지만 일시적으로 확인되지 않은 경우, 동일한 nonce로 `/settle`을 재시도하여 멱등성 대사를 수행할 수 있습니다;
- 동일한 `PAYMENT-SIGNATURE`를 캐시한 후 여러 API 호출에 사용하지 마십시오.

## 일반적인 오류

| 오류                                           | 일반적인 원인                                                             |
| -------------------------------------------- | ---------------------------------------------------------------- |
| `Authorization nonce already processed`      | 동일한 `PAYMENT-SIGNATURE`를 재사용했습니다.                                    |
| `Authorization destination mismatch`         | 클라이언트 서명의 `to`가 payment requirement의 `payTo`와 일치하지 않습니다.                |
| `invalid_upto_evm_payload_invalid_signature` | `upto` typed data의 chainId, facilitator, Permit2 domain 또는 서명 주소가 일치하지 않습니다. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | 지갑이 아직 Permit2에 대해 충분한 USDC allowance를 approve하지 않았습니다.                        |
| `Payer has insufficient USDC balance`        | 결제 지갑의 USDC가 부족합니다.                                                    |
| `Solana signer private key not configured`   | Facilitator가 fee payer로 서명해야 하지만 서버에 Solana signer 설정이 없습니다.           |
