---
title: "Abrufen der Liste der AceDataCloud-Plattform-Serviceanträge"
description: "Platform API guide - Ace Data Cloud"

Gibt paginiert Applications zurück, die das Konto besitzt oder zur Nutzung autorisiert wurde, einschließlich Guthaben, Status, Service-Zusammenfassung und zugehörigen Zugangsdaten. Geeignet für die Überwachung von Guthaben in Stapelverarbeitung, das Finden von Application IDs und den Zugriff auf die Zugangsdatenverwaltung.

## Vorbereitung

1. Melden Sie sich bei der [AceDataCloud-Plattform](https://platform.acedata.cloud) an.
2. Erstellen Sie in der [Account-Token-Konsole](https://platform.acedata.cloud/console/platform-tokens) ein Konto-Token.
3. Normale Benutzer verwenden `user_id=me`; Sie können auch Ihre eigene UUID über `GET /api/v1/platform-tokens/me/` abrufen.

```shell
export PLATFORM_TOKEN='Ihr Konto-Token'
```

## Schnittstellenübersicht

| Element   | Inhalt                                                    |
| --- | ----------------------------------------------------- |
| Methode  | `GET`                                                 |
| URL | `https://platform.acedata.cloud/api/v1/applications/` |
| Authentifizierung  | Account Token, OAuth-Token benötigt `applications:read`       |
| Paginierung  | `count` + `items`                                     |

Normale Benutzer sollten `user_id=me` übergeben. Wenn es nicht übergeben wird, wird die Abfrage nicht zuerst nach Konto eingeschränkt, und bei der Paginierung kann bei nicht berechtigten Objekten `403` zurückgegeben werden; Administratoren können ohne Angabe die gesamte Tabelle anzeigen.

## Abfrageparameter

| Parameter            | Typ          | Erforderlich     | Beschreibung                                                  |
| ------------- | ----------- | ------ | --------------------------------------------------- |
| `user_id`     | UUID / `me` | Für normale Benutzer erforderlich | Abfragesubjekt; unterstützt wiederholte Parameter                                         |
| `affiliation` | string      | Nein      | `owner` (Standard) oder `granted`; beide können wiederholt übergeben werden, um die Vereinigungsmenge zu erhalten, wirkt nur bei vorhandenem `user_id` |
| `service_id`  | UUID        | Nein      | Nach Service filtern; unterstützt wiederholte Parameter                                        |
| `scope`       | string      | Nein      | `Individual` oder `Global`; unterstützt wiederholte Parameter                      |
| `type`        | string      | Nein      | `Usage` oder `Period`; unterstützt wiederholte Parameter                           |
| `limit`       | integer     | Nein      | Anzahl der Einträge pro Seite, maximal 100                                         |
| `offset`      | integer     | Nein      | Paginierungsversatz                                               |
| `ordering`    | string      | Nein      | Unterstützt nur `created_at` oder `-created_at`                    |

`paid`, `disabled`, `expired`, `low_balance` und `tag` sind derzeit keine serverseitigen Filterparameter. Für Guthabenwarnungen sollte nach dem Abrufen der Liste auf Clientseite anhand von `remaining_amount`, `service.unit` und Geschäftsschwellenwerten jedes Application entschieden werden.

## Anfragebeispiele

```shell
curl --get 'https://platform.acedata.cloud/api/v1/applications/' \
  --data-urlencode 'user_id=me' \
  --data-urlencode 'affiliation=owner' \
  --data-urlencode 'limit=100' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

Gleichzeitig Applications anzeigen, die Ihnen selbst gehören und die andere Ihnen autorisiert haben:

```shell
curl --get 'https://platform.acedata.cloud/api/v1/applications/' \
  --data-urlencode 'user_id=me' \
  --data-urlencode 'affiliation=owner' \
  --data-urlencode 'affiliation=granted' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

## Antwortbeschreibung

Die Antwort lautet `{count, items}`. Jeder Eintrag enthält die Application-Modellfelder sowie zusätzlich:

- `service`: `id`, `alias`, `title`, `type`, `unit`, `icon_url`;
- `credentials`: Zusammenfassung der Zugangsdaten, die der aktuelle Aufrufer sehen darf;
- `paid`, `remaining_amount`, `used_amount`, `disabled`, `allow_consume_global`, `allow_overdraft`;
- der tatsächliche Wert von `scope` ist `Individual` oder `Global`;
- der tatsächliche Wert von `type` ist `Usage` oder `Period`.

`allow_overdraft` ist ein schreibgeschütztes boolesches Feld, das von Administratoren gesteuert wird und standardmäßig `false` ist. Bei nutzungsbasierten (`Usage`) Applications mit aktiviertem Überziehen verhindert unzureichendes Guthaben keine Aufrufe; die Abrechnung erfolgt weiterhin gemäß der tatsächlichen Nutzung. Ein negatives Guthaben stellt ein noch abzurechnendes Kontingent dar. Deaktivierung, Ablauf und API-Zugangsdatenlimits bleiben weiterhin wirksam.

`remaining_amount` kann leer sein; der Client muss zuerst auf Leerwerte prüfen, bevor numerische Vergleiche durchgeführt werden. Die Kontingenteinheit wird durch `service.unit` bestimmt.
