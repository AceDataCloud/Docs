[X402](https://www.x402.org/) ist ein von Coinbase vorgeschlagenes On-Chain-Zahlungsprotokoll für „Abrechnung per HTTP 402“: Der Server gibt bei einer Anfrage ohne Token `402 Payment Required` zurück und führt über das Feld `accepts: [...]` akzeptierte Chains / Assets / Preise auf; der Client signiert lokal eine Autorisierung (auf EVM Permit2 / EIP-712, auf Solana eine SPL-Token-Transfer-Autorisierung), legt den base64-kodierten Envelope in den Header `PAYMENT-SIGNATURE` und sendet erneut. Nach der Verifizierung wickelt der Server die Zahlung tatsächlich on-chain ab und gibt dann das Geschäftsergebnis zurück.

> Der X402-Client von Ace Data Cloud ruft die Ziel-API direkt auf und verwendet das in dieser Anfrage in Echtzeit zurückgegebene `402 Payment Required` und `accepts` als Grundlage für Preis und Signatur. Die Zahlungsfähigkeit des Facilitators kann unter [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402) verifiziert werden.

Sowohl `@acedatacloud/sdk` als auch `acedatacloud` stellen einen `paymentHandler`-Hook bereit: Wenn eine vom SDK selbst gesendete Anfrage `402` erhält, wird dein injizierter Handler aufgerufen, um den Header `PAYMENT-SIGNATURE` zu erhalten, und die ursprüngliche Anfrage wird erneut gesendet. Wenn du `@acedatacloud/x402-client` / `acedatacloud-x402` zusammen mit dem SDK verwendest, ist **der gesamte Ablauf für den Geschäftscode vollständig transparent** — du verwendest nur `client.openai.chat.completions.create(...)`; es sieht genauso aus wie der Token-Modus, aber darunter wird pro Aufruf bezahlt, ohne vorher aufladen zu müssen.

Dieser Artikel:

- führt die TS-Kette „ohne Token + X402-Handler-Injektion“ tatsächlich vollständig durch ([T12-Verifizierung](#vier-tatsächliche-laufzeitverifizierung))
- listet die Unterschiede zwischen den zwei Signaturketten EVM / Solana auf
- bietet drei Anpassungen: `viem`-Privatschlüsselmodus, Browser-Wallet-Modus und Python-`EVMAccountSigner`-Modus
- erklärt das leicht fehleranfällige Feld `preferScheme` / `prefer_scheme`

## Eins, Protokollübersicht (unbedingt lesen)

Ein erfolgreicher X402-Aufruf umfasst **3 HTTP-RTTs**:

```text
1. SDK -> /openai/v1/chat/completions               (ohne Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK intern -> paymentHandler({ url, method, body, accepts })   (lokale Signatur, 0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (PAYMENT-SIGNATURE-Header injiziert)
   <- 200 + Geschäftsergebnis   (Abwicklung wird auf dem Server abgeschlossen)
```

Der X402-Envelope ist ein JSON-Abschnitt, der nach der Base64-Kodierung in den Header `PAYMENT-SIGNATURE` eingefügt wird. Struktur (Auszug):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

Die oberste Ebene des Envelopes ist `x402Version: 2` und deklariert mit dem Objekt `accepted` das für dieses Mal gewählte `scheme` und `network` (CAIP-2-Kennung).

| scheme  | Bedeutung                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Fester Preis (Szenarien mit festen Preisen wie Bild- / Videogenerierung, Suche usw.). Der signierte Betrag = der vom Server geforderte Betrag.                                                         |
| `upto`  | Verbrauchsbasierte Abrechnung (Chat Completions / Token-Typen). Es wird ein Betrag als **Obergrenze** signiert, tatsächlich wird nur der verwendete Teil abgerechnet (basierend auf Permit2 + Witness). **Dringend empfohlen** für Sitzungs-APIs. |

`preferScheme` / `prefer_scheme` wird verwendet, um eine Präferenz auszuwählen, wenn der Server **gleichzeitig mehrere Schemes bereitstellt**. Wenn der Server nur `exact` bereitstellt, wird dieses Feld ignoriert; wenn `upto` gesetzt ist, der Server es aber nicht bereitstellt, wird auf den ersten passenden Eintrag zurückgefallen.

## Zwei, TypeScript: zwei Verwendungsweisen für Browser-Wallet + serverseitiges viem

### Installation

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Die getesteten Versionsnummern:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Vollständige Signatur von `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' erforderlich
  evmProvider?: EVMProvider;                // network='base' erforderlich, EIP-1193
  evmAddress?: string;                      // network='base' erforderlich
  preferScheme?: 'exact' | 'upto';
}
```

Der Rückgabewert ist ein `(ctx) => Promise&lt;{ headers: Record<string, string> }>`, was genau der Signatur des `paymentHandler`-Hooks des SDK entspricht.

### Verwendung 1: Browser (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. Benutzer mit Wallet verbinden lassen
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. Zu Base Mainnet wechseln
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. SDK-Client konstruieren und X402-Handler injizieren
//    Hinweis: apiToken nicht übergeben, damit das SDK den 402-Pfad verwendet
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // Für Chat-Typen ist upto zwingend
  })
});

// 4. Normal aufrufen
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Beim ersten Aufruf zeigt der Browser **zwei Signaturaufforderungen** an: Die erste ist ein einmaliges Permit2-Approve für USDC (der Betrag ist `MaxUint256`, wird on-chain geschrieben); die zweite ist die EIP-712-Signatur des X402-Envelopes (geht nicht on-chain, sondern dient nur der Verifizierung durch den Facilitator). Bei nachfolgenden Aufrufen ist nur die zweite Signatur erforderlich; vom Erlebnis her ist es „einmal auf Signieren klicken → Ergebnis erhalten“.

### Verwendung 2: Node-Server + viem-Privatschlüssel (geeignet für Backend / CLI)

`@acedatacloud/x402-client` akzeptiert auf der TS-Seite **nur EIP-1193-Provider** — es verwaltet keine Privatschlüssel direkt. Im Node- / CLI-Szenario besteht die Standardvorgehensweise darin, den Privatschlüssel mit [`viem`](https://viem.sh/) in einen `WalletClient` zu verpacken und dann über [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) oder viems interne EIP-1193-Anpassung zu arbeiten.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient verfügt über eine EIP-1193-kompatible .request(), die direkt als evmProvider verwendet werden kann
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request erfüllt EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Wenn die EIP-1193-Anpassung von viem nicht stabil genug erscheint, kann auch der niedrigschwelligere Weg über [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts) gewählt werden, um die Kette `accepts → signed envelope → PAYMENT-SIGNATURE header` selbst zu verbinden und den SDK-Hook zu überspringen; empfohlen wird jedoch weiterhin vorrangig `createX402PaymentHandler`, damit Protokoll-Upgrades nicht selbst gepflegt werden müssen.

### Verwendung 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

In der Solana-Chain wird derzeit **nur das `exact`-Scheme bereitgestellt**, daher hat `preferScheme` auf Solana keine Wirkung.

## III. Python: Modus mit privatem Schlüssel

`acedatacloud-x402` für Python verwendet den Weg der **direkten Signierung mit dem privaten Schlüssel** (ohne EIP-1193-Abstraktion) und eignet sich besser für Server / Task-Executors.

### Installation

```bash
pip install acedatacloud acedatacloud-x402
```

Getestete Versionsnummern:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. Signierer aus privatem Schlüssel erstellen
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. SDK erstellen: api_token nicht übergeben, damit das SDK den 402-Pfad verwendet
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # Für chat-artige Aufrufe unbedingt upto wählen
    )
)

# 3. Normal aufrufen
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # Optional
    )
)
```

### Einmaliges Approve (nur beim ersten EVM-Aufruf)

Bei EVM Base verwendet X402 Permit2, daher muss die Wallet dem Permit2-Vertrag einmal ein `MaxUint256`-Approve für USDC erteilen. `acedatacloud-x402` enthält bereits `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Diese Transaktion muss nur einmal gesendet werden; danach verwenden alle X402-EVM-Zahlungen diese Autorisierung. Solana benötigt dies nicht.

## IV. Verifizierung durch echten Lauf

Testziel: **Das TS SDK übergibt kein Token, injiziert einen X402-Handler und kann Anfragen normal konstruieren und initiieren** (leichte Verifizierung ohne Verbrauch von echtem On-Chain-USDC).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // Platzhalter-Provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Ausgabe:

```text
handler_type function
client_ctor_ok AceDataCloud
```

Die Ergebnisse zeigen:

- Es wurde kein `apiToken` übergeben, und die SDK-Konstruktion erzeugt **keinen Fehler**, was beweist, dass der X402-Modus tatsächlich ein gültiger Ersatz für ein Token ist.
- `createX402PaymentHandler` gibt eine Funktion (einen Hook) zurück, die vom SDK erst bei Empfang eines 402 aufgerufen wird.
- Der End-to-End-Test für erfolgreich durchgeführte tatsächliche On-Chain-Zahlungen ist wegen des Abzugs von echtem USDC nicht in diesem Tutorial enthalten; siehe die e2e-Beispiele im [X402-Integrationsleitfaden](https://platform.acedata.cloud/documents/x402-integration).

> Auf Python-Seite wurde `create_x402_payment_handler` ebenfalls auf die gleiche Weise verifiziert — der Rückgabewert der Funktion ist callable, und die Konstruktion von `AceDataCloud(...)` erzeugt keinen Fehler, wenn `payment_handler=...` injiziert wird. Die Semantik beider Seiten ist abgestimmt.

## V. Vergleich mit dem „Bearer-Token-Modus“

| Dimension              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Anwendungsszenarien            | Eigenes Backend, langfristige Projekte                                                         | Drittentwickler, nutzungsbasierte Bezahlung, Agentic-Aufrufe                        |
| Registrierung              | Beantragung in der [Konsole](https://platform.acedata.cloud/console/applications) erforderlich | Nicht erforderlich; eine On-Chain-Wallet genügt                                     |
| Abrechnungsgenauigkeit            | Vorab aufladen, gemäß Token-Tabelle abrechnen                                                   | Bei jedem Aufruf in Echtzeit on-chain abrechnen                                         |
| Guthaben              | In der Konsole einsehbar                                                           | USDC der On-Chain-Wallet prüfen                                      |
| Erstkosten            | Bei E-Mail-Registrierung gibt es kostenloses Guthaben                                                        | USDC muss zu Base gebrückt werden, erstmaliges Permit2-Approve erforderlich              |
| Geeignet für chat-artige Aufrufe       | ✅                                                                 | ✅ (`preferScheme=upto` ist erforderlich)                       |
| Geeignet für Einmalzahlungen / kontenübergreifende Zahlungen | ❌                                                                 | ✅                                               |
| Codeänderung            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Die beiden Modi können nebeneinander bestehen — im selben Prozess genügt es, verschiedenen `client`-Instanzen unterschiedliche Authentifizierungsmethoden zuzuweisen.

## VI. Häufige Fallstricke

1. **Chat-Typen müssen `preferScheme=upto` verwenden**: Die Verwendung von `exact` führt dazu, dass der Facilitator USDC gemäß `maxAmountRequired` (nicht gemäß der tatsächlichen Nutzung) abbucht.
2. **Übergeben Sie im Node-Ende keinen nackten privaten Schlüssel an `createX402PaymentHandler`**: Das TS-Paket akzeptiert kein `{ privateKey }`; es muss in einen EIP-1193-Provider verpackt werden (empfohlen wird viem `WalletClient`).
3. **Der erste Aufruf umfasst zwei Signaturen**: Zuerst wird Permit2 approve signiert (on-chain, mit Gas), danach wird das X402-Envelope signiert (nicht on-chain). Bei nachfolgenden Aufrufen bleibt nur die zweite Signatur übrig.
4. **Solana kennt kein Permit2-Konzept**: Die SPL-Token-Transferautorisierung wird direkt signiert, ein Approve ist nicht erforderlich; derzeit wird auf der Solana-Chain jedoch nur `exact` unterstützt.
5. **Geschäftsfehler und Zahlungsfehler unterscheiden**: 402 → Bei einem Handler-Fehler wird `X402SignError` ausgelöst (der konkrete Typ variiert je nach Chain); Fehler der Geschäftsschnittstelle nach einem erneuten Senden (401 / 422 / 5xx) werden weiterhin als gewöhnliche SDK-Ausnahmen klassifiziert.
6. **Die stabilste Schreibweise für die `viem`-Anpassung**: `evmProvider: walletClient as any` verliert zwar die Typprüfung, bietet aber die beste Kompatibilität; wenn Sie die Typen beibehalten möchten, können Sie viems `.transport.request` separat in ein `{ request }`-Objekt verpacken und dieses übergeben.
