Neben der direkten Bezahlung per API-Anfrage unterstützt Ace Data Cloud auch die Zahlung von Bestellungen über die X402-Zahlungskonsole. Die Kernprotokolle für Bestellzahlungen und API-Aufrufe sind identisch: Die erste Anfrage gibt 402 zurück, der Client signiert `PAYMENT-SIGNATURE` und wiederholt die Anfrage dann mit derselben Anfrage.

Der Unterschied besteht darin, dass die Bestellzahlung eine Plattform-API ist und ein Konto-Token erfordert; während die direkte Nutzung der AI-API von `x402.acedata.cloud` ausschließlich mit X402 erfolgen kann und kein API-Token benötigt.

## Bestellung vorbereiten

Öffnen Sie die [Ace Data Cloud-Konsole](https://platform.acedata.cloud/console/orders), wählen Sie die zu bezahlende Bestellung aus und notieren Sie die Bestell-ID.

Falls Sie noch keine Bestellung haben, können Sie auf der Tarifseite eine ausstehende Bestellung erstellen. Der Bestellpreis richtet sich nach der Anzeige auf der Seite, und `amount` in der X402-402-Antwort ist die endgültige Grundlage für die Signatur.

## Konto-Token erstellen

Anfragen zur Bestellzahlung erfordern ein Konto-Token. Öffnen Sie die [Plattform-Token-Seite](https://platform.acedata.cloud/console/platform-tokens) und erstellen Sie ein Token im Format `platform-v1-...`.

Verwenden Sie für nachfolgende Anfragen:

```http
Authorization: Bearer {platform_token}
```

Ein Konto-Token unterscheidet sich von einem normalen API-Token. Normale API-Token werden zum Verbrauch von API-Guthaben verwendet; Konto-Token werden verwendet, um Plattformressourcen im Namen Ihres Kontos zu verwalten, beispielsweise Bestellzahlungen.

## 402 auslösen

Senden Sie zunächst eine Anfrage ohne `PAYMENT-SIGNATURE`:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

Der zurückgegebene Status ist 402, und die Antwort enthält `accepts`:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

Die Bestellzahlung verwendet das offizielle x402 v2: `x402Version` ist `2`, `network` verwendet die CAIP-2-Kennung und das Betragsfeld ist `amount`.

Ausführungsergebnis des Programms zum Erstellen einer Bestellung über 10 Credits und zum Auslösen von 402:

> Die folgenden Transaktionsaufzeichnungen sind historische, tatsächlich getestete Beispiele unter der alten Richtlinie; Betrag und Transaktions-Hash bleiben unverändert erhalten. Für neue X402-Bestellungen gilt kein Zahlungsrabatt mehr; verwenden Sie bitte `amount` aus der aktuellen 402-Antwort als Grundlage für Signatur und Zahlung.

```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
error Payment required for this order.
accepts [
  ('eip155:8453', 'exact', '1200000', '0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000', '5iVXFrYaYWX2GUTbkQj8mDBoBhAX8bneYigS2LJTia43')
]
description Ace Data Cloud Credits x 10.0
```

Erläuterung der Ergebnisse:

- Nachdem die Bestellung erfolgreich erstellt wurde, lautet ihr Status `Pending`; zu diesem Zeitpunkt gibt es noch keine On-Chain-Zahlung.
- Die erste `pay/`-Anfrage enthielt keine `PAYMENT-SIGNATURE`, daher wird HTTP 402 zurückgegeben.
- `accepts` gibt gleichzeitig Base `exact` und Solana `exact` an; dieses Tutorial wählt anschließend Base.
- Der Preis bei der Bestellungserstellung betrug `1.26`; während der alten X402-Zahlungsrabattrichtlinie betrugen der tatsächlich signierte und abgerechnete Betrag `1.2` USDC, entsprechend `1200000` atomaren USDC.

Beachten Sie, dass `resource` hier ein vom Server zurückgegebenes und an der Signatur beteiligtes Feld ist; der Client darf das darin enthaltene Protokoll, den Pfad oder die Bestell-ID nicht selbst umschreiben.

## Signieren und erneut versuchen

Für die Bestellzahlung können die Low-Level-Signaturfunktionen von `@acedatacloud/x402-client` oder `acedatacloud-x402` wiederverwendet werden. Nachfolgend ein TypeScript-Beispiel:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

Ausführungsergebnis des Programms nach dem Signieren und erneuten Versuch mit Base `exact` für dieselbe Bestellung:

```text
status 200
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
has_x_payment_response True
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order {'id': '78481793-304e-47f7-bc0c-8231aec9cc1e', 'state': 'Finished', 'pay_way': 'X402', 'price': 1.2, 'pay_id': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}
```

Ergebnis der On-Chain-Bestätigung:
```text
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer {"from":"0x5d4f08D5c2bb60703284bc06671Eb680fA41B105","to":"0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7","value":"1200000"}
```

Ergebniserklärung:

- `status 200` bedeutet, dass die Plattform-Bestellzahlungsschnittstelle diese `PAYMENT-SIGNATURE` akzeptiert hat.
- `has_x_payment_response True` bedeutet, dass der Antwort-Header eine Base64-kodierte `PAYMENT-RESPONSE`-Quittung enthält.
- `settle_header.success=True` und `network=base` bedeuten, dass der Facilitator das Base-Settlement abgeschlossen hat.
- Der endgültige Bestellstatus ist `Finished`, `pay_way` ist `X402`, und `pay_id` enthält den On-Chain-Transaktions-Hash.
- Das `Transfer`-Ereignis auf BaseScan zeigt, dass die zahlende Adresse `1200000` atomic USDC, also `1.2` USDC, an die Empfangsadresse der Plattform übertragen hat.

## Erfolgreiche Antwort und Quittung

Nachdem die Bestellzahlung erfolgreich war, enthält der Antwortkörper die Bestellinformationen. Die Plattform übermittelt außerdem im Antwort-Header `PAYMENT-RESPONSE` eine Base64-kodierte Settlement-Antwort; nach der Dekodierung umfassen häufige Felder:

| Feld            | Beschreibung                           |
| ------------- | ---------------------------- |
| `success`     | Ob das Facilitator-Settlement erfolgreich ist. |
| `transaction` | On-Chain-Settlement-Transaktions-Hash.                    |
| `network`     | Zahlungsnetzwerk.                        |
| `payer`       | Wallet-Adresse des Zahlers.                      |
| `amount`      | Tatsächlicher Settlement-Betrag, in atomic units.      |

Wenn du eine Abstimmung benötigst, wird empfohlen, gleichzeitig die Bestell-ID, die Wallet-Adresse des Zahlers, `transaction` und den endgültigen Bestellstatus zu speichern.

## Hinweise

- Für die Bestellzahlung ist ein Plattform-Kontotoken erforderlich; sie kann nicht allein mit einer X402-Wallet-Signatur abgeschlossen werden.
- `amount` verwendet USDC atomic units, `1200000` bedeutet `1.2` USDC.
- Setze Empfangsadressen oder Asset-Adressen nicht selbst zusammen; maßgeblich ist `accepts` in der 402-Antwort.
- Wenn dieselbe `PAYMENT-SIGNATURE` wiederholt übermittelt wird, führt der Facilitator einen Replay-Schutz anhand der Nonce durch.

## Antwort bei fehlgeschlagener Zahlung

Das erste HTTP 402 ohne `PAYMENT-SIGNATURE` ist eine normale Zahlungsaufforderung und bedeutet nicht, dass die Zahlung fehlgeschlagen ist. Bei fehlgeschlagener Verifizierung oder Settlement nach der Signatur bleibt der standardmäßige String `error` als kompatibler Fallback erhalten, und unter `extensions.acedatacloud.paymentError` wird eine stabile Fehlerstruktur zurückgegeben:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

Der Client sollte vorrangig anhand von `code` lokalisieren; unbekannte Codes fallen auf einen allgemeinen Zahlungsfehler zurück. `charged` ist ein dreistufiges Feld: Nur wenn die Zahlung eindeutig vor dem Settlement abgelehnt wird, wird `false` zurückgegeben; ein fehlendes Feld bedeutet, dass der Abbuchungsstatus unbekannt ist und nicht als „nicht abgebucht“ interpretiert werden kann. Nachdem die aktuelle Bestellung in `Failed` übergeht, kann die ursprüngliche Bestellung nicht erneut versucht werden; erstelle nach Behebung des Wallet-Problems eine neue Bestellung.

`metadata.x402.last_error` und `metadata.x402.errors` in der Bestellliste und den Bestelldetails behalten dieselbe Gruppe aus `code`, `stage`, `retryable`, `charged` und `params` bei; der öffentliche Beschreibungstext wird in `reason` gespeichert, und der Zeitpunkt des Auftretens wird in `timestamp` gespeichert. Beispielsweise bedeutet `insufficient_token_balance`, dass das USDC-Guthaben im ausgewählten Netzwerk nicht ausreicht, und `invalid_signature` bedeutet, dass die Zahlungssignatur ungültig ist; ein erneutes Abrufen der Bestellung ändert sie nicht zu dem allgemeinen `payment_failed`.

Protokolliere oder übermittle nicht die vollständige `PAYMENT-SIGNATURE`, Wallet-Signaturen, Authorization-Payloads, ursprüngliche Facilitator-Diagnosen oder RPC-Antworten. Für die Support-Untersuchung sind nur die Bestell-ID und der öffentliche Fehler-`code` erforderlich.

## ACE-Rückkauf und -Verbrennung für Base- und Solana-Zahlungen

Nach Aktivierung der Rückkaufstrategie werden 3 % der tatsächlich erhaltenen, berechtigten Circle-USDC-Beträge im Base-Mainnet und USDC-Beträge im Solana-Mainnet verwendet, um ACE zu kaufen und zu verbrennen, ohne die Wallet des Zahlers zusätzlich zu belasten. Bei der Aufladung wird dies einmalig berücksichtigt; bei der anschließenden Nutzung dieser Credits zum Aufrufen der API wird es nicht erneut berücksichtigt; historische Rabattbestellungen und Bestellungen mit alten Strategien werden nicht automatisch rückwirkend berücksichtigt.

Base-Zahlungen behalten die Zahlungsquittung auf der Base-Chain, während der Kauf und die Verbrennung von ACE asynchron auf Solana ausgeführt werden. Das Objekt `ace_burn` in den Bestelldetails stellt `settlement_network`, `settlement_transaction` und `execution_network` bereit und nach Abschluss außerdem `swap_signature` und `burn_signature`. `Pending` oder `Processing` bedeuten nicht, dass bereits verbrannt wurde; nur `Completed` bedeutet, dass der endgültige On-Chain-Nachweis geprüft wurde. Wenn die Base-Zahlung noch keine endgültige Bestätigung erreicht hat, wartet der Rückkauf auf die Bestätigung, dies beeinträchtigt jedoch nicht die bereits gutgeschriebenen Credits.
