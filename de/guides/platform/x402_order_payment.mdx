title: "X402-Tutorial zur Bestellzahlung"

Neben der direkten Zahlung pro API-Anfrage unterstützt Ace Data Cloud auch die Zahlung von Bestellungen über die X402-Zahlungskonsole. Die Bestellzahlung und API-Aufrufe verwenden dasselbe Kernprotokoll: Die erste Anfrage gibt 402 zurück, der Client erstellt die Signatur `PAYMENT-SIGNATURE` und versucht die Anfrage dann erneut.

Der Unterschied besteht darin, dass die Bestellzahlung eine Plattform-API ist und ein Kontotoken benötigt; während die direkte Nutzung der AI-API von `x402.acedata.cloud` nur X402 verwenden kann und kein API-Token benötigt.

## Bestellung vorbereiten

Gehe zur [Ace Data Cloud-Konsole](https://platform.acedata.cloud/console/orders), wähle die zu zahlende Bestellung aus und notiere die Bestell-ID.

Falls du noch keine Bestellung hast, kannst du auf der Tarifseite eine ausstehende Bestellung erstellen. Der Bestellpreis richtet sich nach der Anzeige auf der Seite; `amount` in der X402-402-Antwort ist die endgültige Grundlage für die Signatur.

## Kontotoken erstellen

Anfragen zur Bestellzahlung benötigen ein Kontotoken. Öffne die [Plattform-Token-Seite](https://platform.acedata.cloud/console/platform-tokens) und erstelle ein Token im Format `platform-v1-...`.

Verwende für nachfolgende Anfragen:

```http
Authorization: Bearer {platform_token}
```

Das Kontotoken unterscheidet sich von einem gewöhnlichen API-Token. Gewöhnliche API-Tokens werden zum Verbrauch von API-Guthaben verwendet; Kontotokens werden verwendet, um Plattformressourcen im Namen deines Kontos zu bedienen, beispielsweise Bestellzahlungen.

## 402 auslösen

Sende zunächst eine Anfrage ohne `PAYMENT-SIGNATURE`:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

Der zurückgegebene Status ist 402, und die Antwort enthält `accepts`:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

Die Bestellzahlung verwendet das offizielle x402 v2: `x402Version` ist `2`, `network` verwendet die CAIP-2-Kennung und das Betragsfeld ist `amount`.

Programmausgabe beim Erstellen einer Bestellung über 10 Credits und beim Auslösen von 402:

> Die folgenden Transaktionsaufzeichnungen sind historische, praktisch getestete Beispiele unter der alten Richtlinie; Beträge und Transaktions-Hashes bleiben unverändert. Neue X402-Bestellungen erhalten keinen Zahlungsart-Rabatt mehr; verwende bitte `amount` aus der aktuellen 402-Antwort als Grundlage für Signatur und Zahlung.

```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
error Payment required for this order.
accepts [
  ('eip155:8453', 'exact', '1200000', '0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000', '5iVXFrYaYWX2GUTbkQj8mDBoBhAX8bneYigS2LJTia43')
]
description Ace Data Cloud Credits x 10.0
```

Erläuterung der Ergebnisse:

- Nach erfolgreicher Erstellung der Bestellung ist ihr Status `Pending`; zu diesem Zeitpunkt gibt es noch keine On-Chain-Zahlung.
- Die erste `pay/`-Anfrage enthält keine `PAYMENT-SIGNATURE` und gibt daher HTTP 402 zurück.
- `accepts` gibt gleichzeitig Base `exact` und Solana `exact` an; dieses Tutorial wählt im Folgenden Base.
- Der Preis bei der Bestellungserstellung beträgt `1.26`; bei Zahlung während der alten X402-Zahlungsrabattrichtlinie betrug der tatsächlich signierte und abgerechnete Betrag `1.2` USDC, entsprechend `1200000` Atomic-USDC.

Beachte, dass `resource` hier ein vom Server zurückgegebenes und an der Signatur beteiligtes Feld ist; der Client darf das darin enthaltene Protokoll, den Pfad oder die Bestell-ID nicht selbst ändern.

## Signieren und erneut versuchen

Für die Bestellzahlung können die Low-Level-Signaturfunktionen von `@acedatacloud/x402-client` oder `acedatacloud-x402` wiederverwendet werden. Nachfolgend ein TypeScript-Beispiel:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

Programmausgabe nach der Signatur und dem erneuten Versuch derselben Bestellung mit Base `exact`:

```text
status 200
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
has_x_payment_response True
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order {'id': '78481793-304e-47f7-bc0c-8231aec9cc1e', 'state': 'Finished', 'pay_way': 'X402', 'price': 1.2, 'pay_id': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}
```

Ergebnis der On-Chain-Bestätigung:
```text
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer {"from":"0x5d4f08D5c2bb60703284bc06671Eb680fA41B105","to":"0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7","value":"1200000"}
```

Ergebnisbeschreibung:

- `status 200` zeigt an, dass die Zahlungs-API der Plattform diese `PAYMENT-SIGNATURE` akzeptiert hat.
- `has_x_payment_response True` zeigt an, dass der Antwort-Header den Base64-kodierten `PAYMENT-RESPONSE`-Beleg enthält.
- `settle_header.success=True` und `network=base` zeigen an, dass der Facilitator das Base-Settlement abgeschlossen hat.
- Der endgültige Bestellstatus ist `Finished`, `pay_way` ist `X402`, und `pay_id` enthält den On-Chain-Transaktions-Hash.
- Das `Transfer`-Ereignis auf BaseScan zeigt, dass die Zahlungsadresse `1200000` atomic USDC, also `1.2` USDC, an die Empfangsadresse der Plattform überwiesen hat.

## Erfolgreiche Antwort und Beleg

Nach erfolgreicher Bestellzahlung enthält der Antworttext die Bestellinformationen. Die Plattform führt außerdem im Antwort-Header `PAYMENT-RESPONSE` die Base64-kodierte Settlement-Antwort mit, deren häufige Felder nach der Dekodierung Folgendes umfassen:

| Feld            | Beschreibung                           |
| ------------- | ---------------------------- |
| `success`     | Ob das Facilitator-Settlement erfolgreich ist. |
| `transaction` | On-Chain-Settlement-Transaktions-Hash.                    |
| `network`     | Zahlungsnetzwerk.                        |
| `payer`       | Wallet-Adresse des Zahlers.                      |
| `amount`      | Tatsächlicher Settlement-Betrag in atomic units.      |

Wenn Sie eine Abstimmung benötigen, wird empfohlen, gleichzeitig die Bestell-ID, die Wallet-Adresse des Zahlers, `transaction` und den endgültigen Bestellstatus zu speichern.

## Hinweise

- Die Bestellzahlung benötigt ein Plattformkonto-Token und kann nicht allein mit einer X402-Wallet-Signatur abgeschlossen werden.
- `amount` verwendet USDC atomic units, `1200000` steht für `1.2` USDC.
- Setzen Sie Empfangs- oder Asset-Adressen nicht selbst zusammen; maßgeblich sind die `accepts` in der 402-Antwort.
- Wenn dieselbe `PAYMENT-SIGNATURE` wiederholt übermittelt wird, führt der Facilitator anhand des Nonce einen Replay-Schutz durch.

## Antwort bei Zahlungsfehler

Die erste HTTP 402 ohne `PAYMENT-SIGNATURE` ist eine normale Zahlungsaufforderung und bedeutet keinen Zahlungsfehler. Bei einem Fehler bei der signierten Verifizierung oder beim Settlement bleibt der standardmäßige String `error` als kompatibler Fallback erhalten, und unter `extensions.acedatacloud.paymentError` wird eine stabile Fehlerstruktur zurückgegeben:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

Der Client sollte bevorzugt anhand von `code` lokalisieren; unbekannte Codes fallen auf einen allgemeinen Zahlungsfehler zurück. `charged` ist ein dreistufiges Feld: Nur bei einer eindeutigen Ablehnung vor dem Settlement wird `false` zurückgegeben; ein fehlendes Feld bedeutet, dass der Abbuchungsstatus unbekannt ist, und darf nicht als „nicht abgebucht“ interpretiert werden. Nachdem die aktuelle Bestellung in `Failed` übergegangen ist, kann sie nicht als dieselbe Bestellung erneut versucht werden; erstellen Sie nach der Behebung des Wallet-Problems eine neue Bestellung.

`metadata.x402.last_error` und `metadata.x402.errors` in der Bestellliste und den Bestelldetails behalten dieselbe Gruppe aus `code`, `stage`, `retryable`, `charged` und `params`; der öffentliche Beschreibungstext wird in `reason` gespeichert, und der Zeitpunkt des Auftretens wird in `timestamp` gespeichert. Beispielsweise bedeutet `insufficient_token_balance`, dass das USDC-Guthaben im ausgewählten Netzwerk nicht ausreicht, und `invalid_signature` bedeutet, dass die Zahlungssignatur ungültig ist; ein erneutes Abrufen der Bestellung ändert sie nicht in das allgemeine `payment_failed`.

Protokollieren oder übermitteln Sie nicht die vollständige `PAYMENT-SIGNATURE`, Wallet-Signaturen, Autorisierungs-Payloads, ursprüngliche Facilitator-Diagnosen oder RPC-Antworten. Für die Support-Fehlersuche werden nur die Bestell-ID und der öffentliche Fehler-`code` benötigt.

## ACE-Rückkauf und -Verbrennung für Base- und Solana-Zahlungen

Nach Aktivierung der Rückkaufstrategie werden 3 % der tatsächlich eingegangenen Beträge von qualifiziertem Circle USDC im Base-Mainnet und USDC im Solana-Mainnet zum Kauf und zur Verbrennung von ACE verwendet, ohne der Wallet des Zahlers zusätzlich etwas zu berechnen. Die Rückstellung erfolgt einmal bei der Aufladung; bei der späteren Nutzung dieser Credits zum Aufrufen der API erfolgt keine wiederholte Rückstellung; historische rabattierte Bestellungen und Bestellungen mit alten Strategien werden nicht automatisch rückwirkend berücksichtigt.

Base-Zahlungen behalten den Zahlungsbeleg auf der Base-Chain, während der Kauf und die Verbrennung von ACE asynchron auf Solana ausgeführt werden. Für qualifizierte Zahlungen werden exakt 3 % des tatsächlich eingegangenen Betrags zurückgestellt, ohne feste Obergrenze für Rückkäufe pro Einzeltransaktion oder pro Tag; verfügbare Mittel, Marktpreise und On-Chain-Bestätigungen können dennoch die Abschlusszeit beeinflussen. Das Objekt `ace_burn` in den Bestelldetails stellt `settlement_network`, `settlement_transaction` und `execution_network` bereit und stellt nach Abschluss `swap_signature` und `burn_signature` bereit. `Pending` oder `Processing` bedeutet nicht, dass bereits verbrannt wurde; nur `Completed` steht dafür, dass der endgültige On-Chain-Nachweis überprüft wurde. Wenn eine Base-Zahlung noch keine endgültige Bestätigung erreicht hat, wartet der Rückkauf auf die Bestätigung, ohne die bereits eingegangenen Credits zu beeinträchtigen.
