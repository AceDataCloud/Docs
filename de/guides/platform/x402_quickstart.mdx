Dieses Tutorial erläutert den vollständigen Ablauf von Ace Data Cloud X402 anhand einer minimalen API-Anfrage. Das Ziel ist nicht, zuerst komplexen Code zu schreiben, sondern zunächst zu verstehen: Warum die erste Anfrage 402 zurückgibt, was sich in `accepts` befindet und wie `PAYMENT-SIGNATURE` dieselbe API-Anfrage in eine bezahlte Anfrage verwandelt.

## Vorbereitung

Du musst Folgendes vorbereiten:

| Element   | Beschreibung                                                   |
| ---- | ---------------------------------------------------- |
| Wallet   | Eine Wallet, die das Zielnetzwerk unterstützt. Base verwendet eine EVM-Wallet, Solana verwendet eine Solana-Wallet.      |
| USDC | Die Wallet muss über ausreichend USDC verfügen. Der tatsächliche Betrag richtet sich nach `maxAmountRequired` in der 402-Antwort. |
| Entwicklungsumgebung | Für TypeScript wird Node.js 18+ empfohlen; für Python wird Python 3.10+ empfohlen.    |
| SDK  | Es wird empfohlen, das offizielle SDK zu verwenden; das manuelle Schreiben von Signaturdetails wird nicht empfohlen.                                |

Bei X402-Aufrufen der Ace Data Cloud API ist kein API-Token erforderlich. Die erste SDK-Anfrage enthält kein `Authorization`, das Gateway gibt `402 Payment Required` und die Zahlungsanforderungen zurück; nach der SDK-Signatur wird automatisch erneut versucht.

## SDK installieren

Quellcode und Paketadressen:

- SDK-Repository: [https://github.com/AceDataCloud/SDK](https://github.com/AceDataCloud/SDK)
- X402-Client-Repository: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)
- npm: `@acedatacloud/sdk`、`@acedatacloud/x402-client`
- PyPI: `acedatacloud`、`acedatacloud-x402`

TypeScript:

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client ethers
```

Python:

```bash
pip install acedatacloud acedatacloud-x402
```

Für die Verwendung von Solana müssen außerdem die entsprechenden Abhängigkeiten installiert werden:

```bash
npm install @solana/web3.js
```

Die Solana-Signer-Abhängigkeiten der Python-Version sind bereits in `acedatacloud-x402` enthalten.

Installations- und Importprüfungs-Ausgabe in einer sauberen temporären Umgebung:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
ethers@6.16.0
@solana/web3.js@1.98.4

acedatacloud 2026.4.26.1
acedatacloud-x402 2026.5.31.3
imports_ok True True True True True True
usage: acedatacloud-x402 [-h] {approve-permit2} ...
```

Ergebnisbeschreibung:

- Sowohl npm-Pakete als auch PyPI-Pakete sind tatsächlich veröffentlichte Pakete und keine Platzhalternamen in der Dokumentation.
- `acedatacloud-x402[cli]` installiert die CLI; der Unterbefehl `approve-permit2` kann für Permit2-Autorisierungen im `upto`-Szenario verwendet werden.

## Die erste Anfrage gibt 402 zurück

Du kannst zunächst mit `curl` prüfen, was eine unbezahlte Anfrage zurückgibt. Das folgende Beispiel verursacht keine Belastung, da es keine `PAYMENT-SIGNATURE` enthält:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Der Antworttext enthält ein `accepts`-Array, dessen übliche Struktur wie folgt aussieht:

```json
{
  "x402Version": 2,
  "resource": {
    "url": "/openai/chat/completions",
    "description": "AceDataCloud API call",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "maxAmountRequired": "95215",
      "amount": "95215",
      "maxTimeoutSeconds": 3600,
      "resource": "/openai/chat/completions",
      "description": "...",
      "payTo": "0x...",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913"
      }
    }
  ],
  "error": "PAYMENT-SIGNATURE header is required"
}
```

Derselbe Challenge-Inhalt wird auch in Base64-Form im Antwort-Header `PAYMENT-REQUIRED` abgelegt, damit der Client die Zahlungsanforderungen lesen kann, ohne den Body zu parsen.

Die folgende Programmausgabe-Zusammenfassung stammt von einer unbezahlten Anfrage an die Produktions-API:

```text
status=402
x402Version 2
accepts [
  ('eip155:8453', 'exact', '95215'),
  ('eip155:8453', 'upto', '95215'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '95215'),
]
```

Ergebnisbeschreibung:

- Die erste Anfrage enthält weder `Authorization` noch `PAYMENT-SIGNATURE`, daher wird HTTP 402 zurückgegeben und keine Belastung verursacht.
- `accepts` ist die einzige vertrauenswürdige Signaturgrundlage für diese Anfrage und enthält optionale Netzwerke, Schemes, Betragsobergrenzen, Empfangsadressen und Asset-Adressen.
- `network` ist eine CAIP-2-Kennung; der Client muss bei der Netzwerkauswahl anhand der CAIP-2-Zeichenfolge übereinstimmen.
- Die Betragsobergrenze für diese minimale Chat-Anfrage mit `gpt-4o-mini` beträgt `95215` atomic USDC, also `0.095215` USDC.
- Für jede Anfrage sollte die jeweilige 402-Antwort gelesen werden; Beispielbeträge dürfen nicht fest im Geschäftscode codiert werden.

Feldbedeutungen:

| Feld                  | Beschreibung                                                             |
| ------------------- | -------------------------------------------------------------- |
| `scheme`            | Zahlungsschema. `exact` bedeutet einen festen Betrag, `upto` bedeutet eine Autorisierungsobergrenze mit Abrechnung nach tatsächlicher Nutzung.                     |
| `network`           | CAIP-2-Kennung des Zahlungsnetzwerks, zum Beispiel `eip155:8453`、`solana:5eykt4...`.           |
| `maxAmountRequired` | Maximaler Zahlungsbetrag, die Einheit sind USDC atomic units; `95215` bedeutet `0.095215` USDC.       |
| `amount`            | Der in diesem Fall abzurechnende Betrag; `exact` entspricht `maxAmountRequired`, während `upto` in der Abrechnungsphase entsprechend der tatsächlichen Nutzung angepasst wird. |
| `payTo`             | Empfangsadresse.                                                          |
| `asset`             | USDC-Vertragsadresse oder Solana-Mint-Adresse.                                     |
| `extra`             | Erweiterte Informationen wie Chain-ID, EIP-712-Domain und Permit2-Adresse, die für die Signatur erforderlich sind.                      |

## Zahlungswiederholung mit dem SDK abschließen

Im Folgenden steht ein minimales TypeScript-Beispiel. Es gibt `network: 'base'` an, und der Handler wählt aus der jeweiligen 402-Antwort die Zahlungsanforderung für Base aus; der tatsächliche Betrag und die Empfangsadresse richten sich weiterhin nach `accepts`:
```ts
import { Wallet } from 'ethers';
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') {
      throw new Error(`unsupported method: ${method}`);
    }
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const response = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly: hello' }],
  max_tokens: 8
});

console.log(response.choices[0].message.content);
```

Hinter diesem Code passieren vier Schritte:

1. Das SDK sendet eine gewöhnliche API-Anfrage ohne `Authorization`.
2. Das Gateway gibt `402 Payment Required` und `accepts` zurück.
3. `createX402PaymentHandler` wählt die payment requirement von `network = 'base'` aus und signiert `PAYMENT-SIGNATURE`.
4. Das SDK wiederholt die Anfrage mit demselben Anfragekörper, und das Gateway ruft den Facilitator zur Verifizierung und Abwicklung auf, bevor es die Anfrage an die Ziel-API weiterleitet.

## Unterstützte Fähigkeiten des Facilitators anzeigen

Die X402 API ist nicht von einem Ressourcenverzeichnis abhängig. Der Client ruft die bekannte API direkt auf und verwendet das von dieser Anfrage in Echtzeit zurückgegebene
`402 Payment Required` und `accepts` als einzige Grundlage für Preis und Signatur.

Die Fähigkeitserklärung des Facilitators befindet sich unter:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Sie beschreibt nur `/supported`, `/verify`, `/settle` und die aktuell aktivierten Zahlungsnetzwerke, und listet keine API-Ressourcen auf.

Die Produktions-Facilitator-Adresse von Ace Data Cloud lautet:

```text
https://facilitator.acedata.cloud
```

Sie können prüfen, welche Netzwerke und Schemes es unterstützt:

```bash
curl https://facilitator.acedata.cloud/supported
```

Die zurückgegebenen `kinds` listen die vom Facilitator unterstützten Netzwerke und Schemes auf. Bei tatsächlichen Aufrufen gelten weiterhin die von der API zurückgegebenen `accepts`.

Facilitator-`/supported`-Ausgabe:

```text
kinds [
  ('eip155:8453', 'exact'),
  ('eip155:8453', 'upto', {'facilitatorAddress': '0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708'}),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact')
]
```

Die Ergebnisse zeigen:

- `/supported` zeigt, dass der Facilitator über Verifizierungs- und Abwicklungsfähigkeiten für diese Netzwerke und Schemes verfügt.
- Base und Solana unterstützen beide `exact`; `upto` wird derzeit nur auf Base angeboten.
- Ob eine konkrete API ein bestimmtes Netzwerk zulässt, richtet sich weiterhin nach den 402-`accepts` dieser API.
