X402 ist ein On-Chain-Zahlungsprotokoll auf Basis von HTTP `402 Payment Required`. Mit den X402-Funktionen von Ace Data Cloud können Aufrufer API Token nicht erstellen und kein Kontoguthaben im Voraus aufladen, sondern die On-Chain-Zahlung direkt mit USDC in jeder API-Anfrage abschließen.

Diese Dokumentationsreihe ist nach der tatsächlichen Integrationsreihenfolge organisiert: Führe zunächst eine minimale Anfrage aus, integriere dann das SDK und verstehe anschließend Netzwerke, Abrechnungsmodelle, Bestellzahlungen und den Facilitator. ## Empfohlener Integrationspfad

Wenn du nur die Ace Data Cloud API aufrufen möchtest, verwende bevorzugt die offiziellen SDKs:

- TypeScript: `@acedatacloud/sdk` + `@acedatacloud/x402-client`
- Python: `acedatacloud` + `acedatacloud-x402`

Öffentliche Quellcodes und Paketadressen:

Das SDK führt automatisch die Schritte der ersten nicht authentifizierten Anfrage, der Analyse von `402 Payment Required`, des Aufrufs des Payment Handlers und des erneuten Versuchs mit `PAYMENT-SIGNATURE` aus. Du musst nur eine Wallet mit USDC vorbereiten und das gewünschte Netzwerk auswählen.

Wenn du möchtest, dass deine eigene API ebenfalls X402-Zahlungen unterstützt, musst du die Facilitator-Dokumentation lesen und die Beziehung zwischen `paymentRequirements`, `paymentPayload`, `/verify` und `/settle` verstehen.

## Unterstützungsstatus

Ace Data Cloud X402 wurde für öffentliche APIs, offizielle SDKs, den Facilitator und On-Chain-Abrechnungswege validiert. Die folgende Tabelle fasst den aktuellen Status nach den Funktionsdimensionen zusammen, die bei der Entwicklerintegration am häufigsten verwendet werden.

| Funktion                       | Status                  | Beschreibung                                                                 |
| ------------------------ | ------------------- | ------------------------------------------------------------------ |
| Facilitator-Funktionen | Verfügbar                  | `https://facilitator.acedata.cloud/.well-known/x402` gibt Zahlungsnetzwerke und Protokollendpunkte zurück.  |
| API 402 `accepts`        | Verfügbar                  | Unbezahlte Anfragen geben verfügbare Payment Requirements für Base und Solana zurück.                    |
| TypeScript SDK           | Verfügbar                  | `@acedatacloud/sdk` und `@acedatacloud/x402-client` können 402, Signaturen und Wiederholungsversuche automatisch verarbeiten. |
| Python SDK               | Verfügbar                  | `acedatacloud` und `acedatacloud-x402` können 402, Signaturen und Wiederholungsversuche automatisch verarbeiten.              |
| Base `exact`             | On-Chain validiert               | Geeignet für APIs mit festen Beträgen und Bestellzahlungen.                                                  |
| Base `upto`              | On-Chain validiert               | Geeignet für APIs mit nachgelagerter Verbrauchsmessung wie Chat-Vervollständigungen; derzeit das einzige Netzwerk mit `upto`.                                 |
| Solana `exact`           | HTTP Paid Retry validiert | API Paid Retry und Modellantworten wurden validiert; für die Bestätigung von On-Chain-Signaturen wird der Abgleich über einen eigenen Solana RPC empfohlen.               |
| Bestellzahlung                     | On-Chain validiert               | Die Bestellzahlung über Base `exact` wurde On-Chain abgerechnet und der Bestellstatus aktualisiert.                                   |

Hinweise:

- Sowohl npm- als auch PyPI-Pakete wurden in einer sauberen Umgebung installiert und erfolgreich importiert.
- Unbezahlte API-Anfragen geben 402 zurück, und `accepts` enthält verfügbare Zahlungsmethoden für Base und Solana.
- `accepts[].network` ist eine CAIP-2-Kennung; Clients müssen beim Auswählen eines Netzwerks anhand der CAIP-2-Zeichenfolge übereinstimmen.
- Sowohl das TypeScript SDK als auch das Python SDK können 402 automatisch verarbeiten und den bezahlten Retry abschließen.
- Für Base `exact`, Base `upto` und Bestellzahlungen gibt es öffentlich aufrufbare Explorer-Adressen.
- Das signierte Limit von Base `upto` beträgt `95215` Atomic USDC, während das tatsächliche Settlement bei `3` Atomic USDC liegt, was die Eigenschaft der nachgelagerten verbrauchsbasierten Abrechnung nach tatsächlicher Nutzung widerspiegelt.
- Für Solana `exact` wurden HTTP 402 -> HTTP 200 und die Modellausgabe verifiziert. Da öffentliche RPC-Abfragen rate-limitiert sein können, wird für einen strikten Abgleich empfohlen, einen eigenen Solana RPC oder plattformseitige Settlement-Aufzeichnungen zur Bestätigung der Transaktionssignatur zu verwenden.

## Hinweise zur Integration

Bei der Entwickler-Integration sollten Sie vorrangig die Echtzeit-Zahlungsanforderungen der aktuellen Anfrage beachten, statt Beispielbeträge oder Adressen aus der Dokumentation zu kopieren:

- `accepts[].maxAmountRequired` ist der maximal signierbare Betrag für die aktuelle Anfrage.
- `accepts[].asset` ist der USDC-Vertrag oder Mint, der für diese Anfrage verwendet werden soll.
- `accepts[].extra.chainId`, `accepts[].extra.facilitatorAddress` und `accepts[].extra.verifyingContract` werden an der EVM-Typed-Data-Signatur beteiligt.
- `upto` erfordert, dass die Wallet zunächst Permit2 für USDC auf der Ziel-Chain autorisiert; ohne Autorisierung wird `PERMIT2_ALLOWANCE_REQUIRED` zurückgegeben.
- Wenn Sie ausdrücklich nachgelagerte Verbrauchsabrechnung verwenden möchten, übergeben Sie im TypeScript SDK `preferScheme: 'upto'`; andernfalls wählt das SDK die erste verfügbare Requirement, die der Server für dieses Netzwerk zurückgibt.

## Öffentlich überprüfbarer Umfang

Vor der Integration können zunächst diese öffentlichen Endpunkte und SDK-Verhalten überprüft werden:

- API-Anfragen ohne `Authorization` oder `PAYMENT-SIGNATURE` geben `402 Payment Required` zurück; das `accepts` in der Antwort ist die einzige Signaturgrundlage für diese Anfrage.
- Sowohl das TypeScript SDK als auch das Python SDK stellen einen Payment Handler bereit; die SDK-Transportschicht ruft den Handler nach Erhalt von 402 auf und versucht es einmal erneut.
- `https://facilitator.acedata.cloud/.well-known/x402`: Gibt die vom Facilitator unterstützten Netzwerke, Schemes und Protokollendpunkte zurück; die API-Preise richten sich weiterhin nach dem in Echtzeit zurückgegebenen 402 der Zielanfrage.
- `https://facilitator.acedata.cloud/supported`: Gibt die vom Facilitator unterstützten Netzwerke und Schemes zurück.
- Das X402Client-Repository enthält fortgeschrittene On-Chain-Verifizierungstools, die zur Bestätigung von Signaturen, Retries und Settlement-Verhalten verwendet werden können; die Tool-Ausgabe ersetzt nicht das von der Online-API zurückgegebene `accepts`.

`upto` gehört zur nachgelagerten verbrauchsbasierten Abrechnung und eignet sich für APIs wie Chat-Completions und Modellaufrufe, bei denen der tatsächliche Verbrauch erst nach der Antwort bekannt ist. Derzeit bietet nur Base `upto` an; wenn die Signaturvalidierung fehlschlägt, prüfen Sie bitte, ob Chain ID, Facilitator-Adresse, Spender, USDC-Vertrag und Permit2-Allowance mit der 402-Antwort übereinstimmen.
