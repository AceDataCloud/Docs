Fragen Sie eine Bestellung über die Bestell-ID ab. Dieser Endpunkt unterstützt zwei Lesemodi: Der anonyme Zugriff gibt nur die für die Zahlungsseite erforderlichen Mindestfelder zurück; wenn der Bestellbesitzer ein Account Token mitführt, werden vollständige Details zurückgegeben.

## Schnittstellenübersicht

| Element   | Inhalt                                                        |
| --- | --------------------------------------------------------- |
| Methode  | `GET`                                                     |
| URL | `https://platform.acedata.cloud/api/v1/orders/{order_id}` |
| Authentifizierung  | Optional; anonym ist eine minimale Projektion, der authentifizierte Besitzer erhält eine vollständige Projektion                                    |

`/orders/{id}` und `/orders/{id}/` sind derzeit beide verfügbar. Die Bestell-ID ist Teil des Zahlungslinks und sollte als sensible undurchsichtige Kennung behandelt und nicht öffentlich verbreitet werden.

## Anonyme Abfrage

Die Zahlungsseite kann bei Verlust des Login-Status direkt lesen:

```shell
export ORDER_ID='deine Bestell-ID'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json'
```

Die anonyme Antwort enthält nur `id`, `description`, `price`, `state`, `pay_way`, `pay_url`, `expired_at`, `created_at`. Sie gibt weder Konto, Application, Package, interne Zahlungskennungen noch metadata zurück.

## Authentifizierte Abfrage

```shell
export PLATFORM_TOKEN='dein Kontotoken'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

Der Bestellbesitzer erhält vollständige Order-Details, einschließlich `application` / `applications`, `package` / `packages`, `bank_details`, `invoice_automation` und Modellfelder. Wenn authentifiziert, aber nicht der Bestellbesitzer, wird `403` zurückgegeben; Superadministratoren sind ausgenommen.

## Schlüsselfelder

| Feld            | Beschreibung                                                          |
| ------------- | ----------------------------------------------------------- |
| `state`       | `Pending`, `Paid`, `Finished`, `Expired`, `Failed` oder `Refunded` |
| `pay_way`     | Die aktuelle Zahlungsmethode der Bestellung; der Feldname lautet nicht `payment_method`                             |
| `pay_url`     | Gehostete Zahlungsseite oder QR-Code-Adresse, kann leer sein                                           |
| `price`       | Der endgültig zu zahlende Betrag der Bestellung; das aktuelle Bestellmodell stellt kein Feld `final_price` bereit                         |
| `amount`      | Anzahl der Paketkontingente; nur in der vollständigen authentifizierten Antwort sichtbar                                            |
| `finished_at` | Zeitpunkt des Bestellabschlusses; der Feldname lautet nicht `paid_at`                                      |

Die vollständige Antwort kann je nach Zahlungsmethode zusätzliche Felder enthalten. Clients sollten diese nach Bedarf lesen und stets vermeiden, sensible metadata aus der vollständigen Antwort zu protokollieren.

## Fehlerbehandlung

- `404`: Die Bestell-ID existiert nicht.
- `403`: Angemeldet, aber nicht der Bestellbesitzer.
- Anonyme Anfragen geben kein `401` zurück; sie erhalten lediglich die minimale öffentliche Projektion.

## Rechnungsstornierung und erneute Beantragung

Über `GET /api/v1/orders/{order_id}/invoice/` kann die aktuelle Rechnung der Bestellung gelesen werden. Nach dem Einreichen einer automatischen Rechnungsstornierung bleibt die Rechnung `Issued`; `red_state` zeigt den Fortschritt der Stornierung an. Eine erfolgreiche Einreichung bedeutet nicht, dass die Stornierung abgeschlossen ist. Während auf die Bestätigung gewartet wird, eine Stornorechnung ausgestellt oder archiviert wird, kann für die Bestellung keine Rechnung erneut beantragt werden.

Wenn Administratoren aufgrund falscher Rechnungsinformationen wie Rechnungsbezeichnung oder Steuernummer eine Stornierung beantragen, lautet der Stornierungsgrund „Fehlerhafte Rechnungsstellung“; die durch eine Bestellerstattung ausgelöste automatische Stornierung verwendet weiterhin „Dienstbeendigung“.

Nachdem die Stornorechnung erfolgreich ausgestellt und archiviert wurde, wird die ursprüngliche Rechnung zu `Voided`, und die Bestellung kann erst dann erneut beantragt werden. Die ursprüngliche Rechnung kann im Rechnungsverlauf eingesehen werden. Wenn die Stornierung fehlschlägt oder das Ergebnis noch überprüft werden muss, übernimmt die Finanzabteilung die Prüfung; die Rechnungsbeschränkung für die Bestellung wird nicht vorzeitig aufgehoben. Manuell ausgestellte Rechnungen müssen zunächst im Steuer- oder Rechnungssystem storniert oder per Stornorechnung korrigiert werden, bevor die Finanzabteilung dies auf der Plattform bestätigt.
