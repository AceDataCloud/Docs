title: "X402-Abrechnungsschemata `exact` und `upto`"

Ace Data Cloud X402 verwendet derzeit zwei Arten von Schemas: `exact` und `upto`. Sie lösen unterschiedliche Abrechnungsprobleme.

## `exact`

`exact` bedeutet, dass der Preis dieser Anfrage bereits vor dem Eintritt in die Ziel-API bestimmt werden kann. Der vom Client signierte Betrag ist der endgültig abgebuchte Betrag.

Geeignet für:

- Bildgenerierung mit festem Preis;
- Erstellung von Videoaufgaben mit festem Preis;
- Such- oder Tool-APIs mit festem Preis;
- Bestellzahlungen.

EVM `exact` verwendet USDC EIP-3009 `TransferWithAuthorization`:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": {
    "authorization": {
      "from": "0x...",
      "to": "0x...",
      "value": "95215",
      "validAfter": "1780237345",
      "validBefore": "1780240945",
      "nonce": "0x..."
    },
    "signature": "0x..."
  }
}
```

Der Facilitator validiert die Signatur und den Betrag in der Phase `/verify` und übermittelt diese Autorisierung in der Phase `/settle` an die Blockchain.

## `upto`

`upto` bedeutet, dass der Client eine maximale Obergrenze autorisiert und Ace Data Cloud nach Abschluss der Anfrage entsprechend der tatsächlichen Nutzung abrechnet; die tatsächliche Abbuchung darf die Obergrenze nicht überschreiten.

Geeignet für:

- Chat-Vervollständigungen: Der endgültige Preis hängt von Prompt-Tokens und Completion-Tokens ab;
- Streaming-Antworten: Die tatsächliche Ausgabelänge ist erst nach dem Ende bekannt;
- zukünftige APIs mit nachgelagerter Messung.

`upto` verwendet Permit2 `PermitWitnessTransferFrom`. Der Client signiert keine feste Überweisung, sondern eine Obergrenzenautorisierung mit Witness:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2Authorization": {
      "from": "0x...",
      "spender": "0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002",
      "nonce": "123456789",
      "deadline": "1780240945",
      "permitted": {
        "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "amount": "95215"
      },
      "witness": {
        "to": "0x...",
        "facilitator": "0x...",
        "validAfter": "1780237345"
      }
    },
    "signature": "0x..."
  }
}
```

`permitted.amount` ist die Obergrenze und nicht unbedingt die endgültige Abbuchung. Das Gateway wandelt die tatsächliche Nutzung in der Phase `/record` in `amount` um und übergibt sie an den Facilitator. Der Facilitator erlaubt nur eine Abrechnung mit `amount &lt;= permitted.amount`.

Das Programmausführungsergebnis von Base `upto`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
elapsed_ms 5104
content ADC_BASE_UPTO_OK
id chatcmpl-DlcbyS4IT8kUAMo4Ri97HiIHc9T8V
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Erläuterung:

- Die in 402 zurückgegebene Autorisierungsobergrenze beträgt `95215` atomic USDC, der Client signiert entsprechend dieser Obergrenze.
- Nach der tatsächlichen Modellantwort werden nur `3` atomic USDC abgerechnet; die On-Chain-Transaktion ist auf BaseScan einsehbar.
- Dieses Ergebnis zeigt den entscheidenden Unterschied von `upto`: Der signierte Betrag ist eine Obergrenze, die On-Chain-Abrechnung kann unter der Obergrenze liegen.
- Wenn die tatsächliche Nutzung die Obergrenze überschreitet, sollte der Facilitator die Abrechnung ablehnen, und der Client muss erneut mit einer höheren Obergrenze autorisieren.

`upto` wird derzeit nur auf Base angeboten. Wenn eine nachgelagerte Messung erforderlich ist, verwenden Sie bitte Base.

## Warum Permit2 approve erforderlich ist

`upto` zieht USDC letztendlich über den x402-Proxy mittels Permit2 aus der Zahlungswallet ein. Vor der ersten Nutzung muss die Zahlungswallet Permit2 einmalig eine ERC-20-Allowance erteilen.

Python-CLI:

```bash
pip install 'acedatacloud-x402[cli]'
X402_PRIVATE_KEY=0x... acedatacloud-x402 approve-permit2 --network base
```

Programmatisch:

```python
from acedatacloud_x402 import EVMAccountSigner, approve_permit2

approve_permit2(
    rpc_url="https://mainnet.base.org",
    signer=EVMAccountSigner.from_private_key("0x..."),
    token_address="0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
)
```

Nach Abschluss der Autorisierung muss jede Anfrage weiterhin ein neues `upto`-Envelope signieren, da Nonce, Deadline, Witness und die Betragsobergrenze unterschiedlich sind.

## Abrechnung mit Nullbetrag

`upto` unterstützt Fälle, in denen der tatsächliche Betrag 0 ist. Wenn beispielsweise die Ziel-API keine erfolgreich abrechenbare Nutzung erzeugt hat, kann das Gateway `amount = "0"` übergeben. Der Facilitator gibt Erfolg zurück, sendet jedoch keine On-Chain-Transaktion.

Dies kann das Problem vermeiden, dass „die Anfrage nicht erfolgreich war, aber dennoch On-Chain-Gebühren abgebucht werden“.

## Auswahlvorschläge

| Szenario                   | Empfehlung                       |
| -------------------------- | -------------------------------- |
| API mit festem Preis       | Verwenden Sie `exact`, die Logik ist einfach. |
| Bestellzahlung             | Verwenden Sie `exact`.           |
| Chat-Vervollständigung, Abrechnung nach Token | Verwenden Sie Base `upto`.       |
| Permit2 approve noch nicht durchgeführt | Führen Sie zuerst `exact` erfolgreich aus und wechseln Sie dann zu `upto`. |

Wenn Sie nicht sicher sind, welches Sie wählen sollen, verwenden Sie zuerst das SDK-Standardverhalten; das SDK wählt die passende Netzwerk-Payment-Requirement aus, die der Server zurückgibt.

## Base-`upto`-Checkliste

Bei der Integration oder Fehlerbehebung bestätigen Sie bitte, dass die folgenden Parameter aus derselben 402-Antwort stammen und beim Signieren durch den Client konsistent bleiben:

| Parameter                  | Prüfpunkt                                          |
| -------------------------- | -------------------------------------------------- |
| `network`                  | Muss `eip155:8453` sein.                           |
| `scheme`                   | Muss `upto` sein.                                  |
| `extra.chainId`            | Die Base-Chain-ID ist `8453`.                      |
| `asset`                    | Verwenden Sie die Base-USDC-Vertragsadresse aus der 402-Antwort. |
| `extra.facilitatorAddress` | Muss am Witness beteiligt sein und mit Facilitator `/supported` übereinstimmen. |
| Permit2 allowance          | Die Zahlungswallet muss Permit2 zuvor für Base USDC autorisieren. |

Häufige Fehler und Behandlungsmethoden:

| Fehler                                        | Behandlungsmethode                                                                          |
| --------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `invalid_upto_evm_payload_invalid_signature` | Prüfen Sie, ob Chain-ID, Facilitator-Adresse, Permit2-Domain, Spender, Signaturkonto und Witness mit der 402-Antwort übereinstimmen. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Führen Sie Permit2 approve für USDC auf der Ziel-Chain aus und starten Sie die Anfrage erneut. |
| `amount exceeds permitted amount`            | Die tatsächliche Nutzung überschreitet die signierte Obergrenze; es muss erneut mit einer höheren Obergrenze signiert werden. |
