X402 umfasst HTTP, SDK, Signaturen, Facilitator und On-Chain-Transaktionen. Bei der Untersuchung von Signatur- oder Abrechnungsproblemen wird empfohlen, schrittweise in der Reihenfolge „öffentlicher Einstiegspunkt -> 402-Antwort -> SDK payment handler -> On-Chain-settlement“ zu prüfen. Dieses Tutorial erläutert die Prüfmethoden für jede Ebene und führt häufige Fehler auf.

## Öffentlichen Einstiegspunkt prüfen

Facilitator-Fähigkeitserklärung:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Wenn `facilitator`, `supportedKinds` und die Protokollendpunkte zurückgegeben werden, sind die Fähigkeitsmetadaten normal. Die API-Ressourcenerkennung wurde eingestellt; rufen Sie die Ziel-API direkt auf und orientieren Sie sich an der Echtzeit-402-Antwort.

Vom Facilitator unterstützte Fähigkeiten:

```bash
curl https://facilitator.acedata.cloud/supported
```

Wenn `kinds` zurückgegeben wird, funktioniert der Facilitator-Einstiegspunkt normal.

## 402 `accepts` prüfen

Senden Sie eine nicht autorisierte Anfrage, die keine Gebühren verursacht:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Prüfen Sie, ob `accepts` in der Antwort das Netzwerk enthält, das Sie verwenden möchten. `network` ist eine CAIP-2-Kennung:

- `eip155:8453` + `exact` (Base)
- `eip155:8453` + `upto` (Base, nachgelagerte Verbrauchsmessung)
- `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` + `exact` (Solana)

Wenn das Zielnetzwerk nicht vorhanden ist, ist für diese API oder die aktuelle Umgebung keine entsprechende X402-Zahlungsmethode konfiguriert.

## Erweiterte Verifizierungstools von X402Client ausführen

Das X402Client-Repository stellt erweiterte Verifizierungstools bereit, mit denen die Auswahl der 402-Antwort, die Signaturerstellung, paid retry und On-Chain-settlement bestätigt werden können. Sie benötigen eine funded wallet, RPC, einen privaten Schlüssel und Entwicklungsabhängigkeiten. Für die gewöhnliche Geschäftsintegration wird empfohlen, vorrangig das TypeScript- oder Python-SDK zu verwenden; führen Sie diese Tools nur aus, wenn Signatur- oder On-Chain-Abrechnungsprobleme lokalisiert werden müssen.

Repository-Adresse: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)

```bash
git clone https://github.com/AceDataCloud/X402Client.git
cd X402Client/typescript
npm install
npm install --no-save ethers @solana/spl-token bs58 tsx
```

Base:

```bash
export X402B_BASE_PAYER_PRIVATE_KEY=0x...
TEST_API_PATH='/openai/chat/completions' \
TEST_BODY='{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}],"max_tokens":10}' \
npx tsx scripts/test-real-e2e.ts
```

Solana:

```bash
export X402B_SOLANA_PAYER_PRIVATE_KEY=...
npx tsx scripts/test-solana-e2e.ts
```

Die Verifizierungstools geben normalerweise Folgendes aus:

1. Die 402-Antwort der ersten Anfrage.
2. Die ausgewählte payment requirement.
3. Die Zusammenfassung der signierten `PAYMENT-SIGNATURE`.
4. HTTP-Status und Antwortkörper nach dem retry.
5. Die On-Chain-settlement-Transaktion oder bei einem Fehler den vom Facilitator gemeldeten Fehlergrund.

Senden Sie keine privaten Schlüssel oder vollständigen `PAYMENT-SIGNATURE`-Werte an Log-Systeme oder Tickets.

Beispiel für Ergebnisse der öffentlichen API-Verifizierung:

```text
Base exact
HTTP 402 -> HTTP 200
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC

Solana exact
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run because public RPC lookup hit 429

Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Erläuterung:

- Base `exact`, Solana `exact` und Base `upto` haben alle den paid retry von HTTP 402 zu HTTP 200 abgeschlossen.
- Die On-Chain-Transaktion von Base `exact` ist auf BaseScan auffindbar, und der Abrechnungsbetrag beträgt `95215` atomic USDC.
- Die Signaturobergrenze von Base `upto` beträgt `95215` atomic USDC, aber das tatsächliche On-Chain-settlement beträgt `3` atomic USDC, was zeigt, dass bei der nachgelagerten Verbrauchsmessung gemäß dem tatsächlichen Verbrauch abgerechnet wird.
- Der Solana-Pfad hat paid retry und Modellausgabe bestätigt. Öffentliche RPCs können gedrosselt werden; wenn eine strikte On-Chain-Abstimmung erforderlich ist, verwenden Sie bitte Ihren eigenen Solana-RPC oder bestätigen Sie die Transaktionssignatur anhand der Abrechnungsaufzeichnungen der Plattform.

## SDK smoke test

Die erweiterten Verifizierungstools werden zur Prüfung von Signaturen und On-Chain-Abrechnungen verwendet. Auf Geschäftsseite sollte außerdem ein SDK smoke test durchgeführt werden, um zu bestätigen, dass der Anwendungscode 402 automatisch über den payment handler verarbeiten kann. Nachfolgend werden nur die Kernfragmente gezeigt; der vollständige Code muss wallet, provider und import ergänzen.

TypeScript:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const res = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly ADC_SDK_X402_OK' }],
  max_tokens: 8
});
```

Python:

```python
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
    )
)

res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly ADC_PY_X402_OK"}],
    max_tokens=8,
)
```

Wenn das Modell wie gefordert die feste Zeichenfolge zurückgibt, sind SDK, payment handler, Gateway, Facilitator und Ziel-API miteinander verbunden.

Die beiden obigen smoke tests verwenden Base `exact` und rechnen zum in der 402-Preisangabe festgelegten Betrag ab. Chat-Vervollständigungen sind ein nach Tokens abgerechnetes Szenario; bei der produktiven Integration wird empfohlen, `preferScheme: 'upto'` zu übergeben (in Python `prefer_scheme="upto"`), um gemäß dem tatsächlichen Verbrauch abzurechnen.

Das Rückgabeobjekt des Python SDK ist ein `dict`; Inhalte können mit `res["choices"][0]["message"]["content"]` gelesen werden.

## E2E für Bestellzahlungen

Bestellzahlungen verwenden die Plattform-API von `platform.acedata.cloud` und benötigen ein Plattformkonto-Token. Die vollständige Kette lautet: Eine Pending-Bestellung erstellen, mit `POST /api/v1/orders/{order_id}/pay/` 402 auslösen und dann mit `PAYMENT-SIGNATURE` wiederholen.

Beispiel für Verifizierungsergebnisse einer Kleinbestellungszahlung:

> Die folgenden Transaktionsaufzeichnungen sind historische Testbeispiele unter der alten Richtlinie; Beträge und Transaktions-Hashes bleiben unverändert erhalten. Neue X402-Bestellungen bieten keine Rabatte für Zahlungsmethoden mehr; verwenden Sie bitte den `amount` in der jeweiligen 402-Antwort als Grundlage für Signatur und Zahlung.
```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
accepts [('eip155:8453', 'exact', '1200000'), ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000')]

status 200
order state Finished
pay_way X402
pay_id 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}

Base tx status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Ergebniserklärung:

- Nach dem Erstellen der Bestellung ist der Bestellstatus `Pending`, und der Preis beträgt `1.26`.
- Die erste `pay/`-Anfrage gibt HTTP 402 zurück, in `accepts` gibt es Base `exact` und Solana `exact`, die Beträge sind jeweils `1200000` atomic USDC.
- Nach erneutem Versuch mit Base `PAYMENT-SIGNATURE` wird HTTP 200 zurückgegeben, der Bestellstatus ändert sich zu `Finished`, und `pay_way` ist `X402`.
- Nach dem Dekodieren von `PAYMENT-RESPONSE` werden `success=True`, `network=base` angezeigt und derselbe Transaktions-Hash angegeben.
- Auf BaseScan ist der Transaktionsstatus `1`, der Überweisungsbetrag beträgt `1200000` atomic USDC, also `1.2` USDC.
- Der Erstellungspreis `1.26` wurde während des alten X402-Zahlungsrabattzeitraums bezahlt, der endgültige Signatur- und Abrechnungsbetrag beträgt `1.2` USDC.

Wenn die Bestellzahlung kein `Authorization: Bearer {platform_token}` hat oder die Bestellung nicht zum aktuellen Konto gehört, schlägt sie auf der Plattformberechtigungsebene fehl; dies unterscheidet sich von der kontolosen X402-API beim direkten Aufruf von `x402.acedata.cloud`.

## Häufige Fehler

| Erscheinung                                           | Prüfrichtung                                                                |
| -------------------------------------------- | ------------------------------------------------------------------- |
| Die erste Anfrage ist nicht 402                                  | Prüfen, ob versehentlich `Authorization` mitgegeben wurde oder ob diese API noch kein X402 pricing hat.                  |
| `No payment requirement for network`         | Das Zielnetzwerk ist nicht in `accepts`, Netzwerk wechseln oder Gateway-Konfiguration prüfen.                               |
| `invalid_402`                                | Die 402-Antwort ist kein gültiges JSON, Proxy, Gateway oder Fehlerseite prüfen.                                        |
| `Authorization nonce already processed`      | Derselbe `PAYMENT-SIGNATURE` wurde wiederverwendet, erneut signieren.                                  |
| `invalid_upto_evm_payload_invalid_signature` | chainId von `upto`, Permit2 domain, Facilitator-Adresse und Signaturkonto auf Konsistenz prüfen.         |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Für USDC der Ziel-Chain `approve-permit2` ausführen.                                     |
| `Payer has insufficient USDC balance`        | Das USDC-Guthaben der zahlenden Wallet reicht nicht aus.                                                       |
| HTTP 200 aber kein tx hash                         | Der tatsächliche Betrag von `upto` könnte 0 sein oder der settlement-Datensatz wird noch asynchron geschrieben.                             |
| Solana `Missing transaction payload`         | Das `PAYMENT-SIGNATURE` envelope enthält keine serialisierte Transaktion oder signature, wallet adapter prüfen. |

## Base-`upto`-Checkliste

`upto` wird derzeit nur auf Base bereitgestellt (`eip155:8453`). Da die `upto`-Signatur an mehr EVM typed data-Parameter gebunden wird, sollten bei der Integration besonders die Echtzeitfelder in der 402-Antwort und die Client-Signatur auf vollständige Übereinstimmung geprüft werden.

```text
Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Wenn Base `upto` `invalid_upto_evm_payload_invalid_signature` zurückgibt, zuerst Folgendes prüfen:

1. `extra.chainId` im von der API zurückgegebenen Eintrag `eip155:8453` + `upto` (sollte `8453` sein).
2. Die von der API zurückgegebene `extra.facilitatorAddress`.
3. Die von `https://facilitator.acedata.cloud/supported` zurückgegebene Base-`upto`-Facilitator-Adresse.
4. Permit2 domain, spender, USDC-Vertrag und Signaturkonto.
5. Ob die Wallet bereits Permit2 für Base USDC approve hat.

Der Signatur-digest von `upto` bindet gleichzeitig Permit2 domain, chain ID, spender, Empfängeradresse, Facilitator-Adresse und validAfter. Bei Inkonsistenz eines beliebigen Elements stellt der Facilitator den falschen signer wieder her und gibt dadurch invalid signature zurück. Wenn all diese übereinstimmen, aber weiterhin 402 zurückgegeben wird, im nächsten Schritt Permit2 allowance prüfen; bei fehlender Autorisierung wird `PERMIT2_ALLOWANCE_REQUIRED` zurückgegeben.

## Verifizierungsinformationen speichern

Bei einer vollständigen Verifizierung mindestens speichern:

- API path und Anfragekörper-Zusammenfassung;
- das ausgewählte network und scheme;
- `maxAmountRequired`;
- die payer-Wallet-Adresse;
- den endgültigen HTTP-Status;
- die Modellausgabe oder Aufgaben-ID in der Antwort;
- den settlement transaction-Link;
- Gateway trace ID oder Plattformnutzungsdatensatz-ID.

Keine privaten Schlüssel, keine vollständige `PAYMENT-SIGNATURE`, keine vollständige EIP-712 signature und keine Seed-Phrase speichern.

## Strukturierte Zahlungsfehler

X402-Fehler nach der Signatur geben unter `extensions.acedatacloud.paymentError` einen stabilen `code`, sichere Interpolationsparameter, Phase und Wiederholbarkeitskennzeichen zurück. Zur Fehlerbehebung vorrangig diese Struktur verwenden, nicht den englischen `error` der obersten Ebene parsen und Benutzer nicht auffordern, Wallet-Signaturen oder Originaltexte von On-Chain-Simulationen bereitzustellen.

- `charged: false`: Die Verifizierung wurde vor dem settlement eindeutig abgelehnt, bei diesem Vorgang wurde keine Belastung ausgelöst.
- Ohne `charged`: Das Ergebnis ist unbekannt oder hat bereits die settlement-Phase erreicht, zuerst Bestellung und On-Chain-Status prüfen, direkte Wiederholungszahlung ist verboten.
- `settlement_pending`: Zahlung vorerst nicht wiederholen, zuerst Bestellung aktualisieren oder den Support kontaktieren.
- Nicht erkannter code: Als `payment_failed` behandeln und den öffentlichen technischen Code für die Suche durch den Kundenservice aufbewahren.
