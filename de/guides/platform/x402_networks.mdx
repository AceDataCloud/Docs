Ace Data Cloud X402 rechnet derzeit über USDC ab und unterstützt zwei Arten von Chains: EVM und Solana. Die Signaturmethoden, Asset-Adressen, das Gas-Verhalten und die Anwendungsszenarien unterscheiden sich je nach Netzwerk; vor der Integration muss zunächst das Netzwerk ausgewählt werden.

## Netzwerkkennungen verwenden CAIP-2

`accepts[].network` von x402 v2 ist eine CAIP-2-Kennung und keine Kurzbezeichnung wie `base` oder `solana`. Clients müssen Netzwerke durch Vergleich von CAIP-2-Strings abgleichen:

| Netzwerk             | CAIP-2-Kennung                                 |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Unterstützungsmatrix

| Netzwerk     | scheme  | Asset                  | Signaturmethode                                 | Anwendungsszenario                     |
| ------ | ------- | ------------------- | ------------------------------------ | ------------------------ |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Standardempfehlung, ausgereifte Unterstützung durch Wallets und Liquidität.         |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | APIs mit nachgelagerter Abrechnung wie Chat und Modelle.          |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Solana-Wallets, Agents oder On-Chain-Anwendungsszenarien. |

`upto` wird derzeit nur auf Base angeboten. Die tatsächlich verfügbaren Einträge richten sich nach den von der API zurückgegebenen `accepts`. Du kannst auch den Facilitator prüfen:

```bash
curl https://facilitator.acedata.cloud/supported
```

Die Rückgabe von Facilitator `/supported`:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Erläuterung der Ergebnisse:

- `exact` auf Base und Solana ist ein Zahlungspfad mit festem Betrag.
- Nur Base bietet den nachgelagerten Abrechnungspfad `upto`, der von einer Permit2-Approve abhängt.
- `extra.facilitatorAddress` im Eintrag `upto` ist die Adresse, die der Client beim Signieren in den Witness schreiben muss, und muss mit dem vom Server zurückgegebenen Wert übereinstimmen.

## Base

Base verwendet den offiziellen USDC-Vertrag:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

Im Schema `exact` signiert der Client EIP-712 `TransferWithAuthorization`. Der Signaturinhalt umfasst:

- `from`: Adresse der zahlenden Wallet
- `to`: Empfangsadresse von Ace Data Cloud
- `value`: Zahlungsbetrag dieser Transaktion
- `validAfter` / `validBefore`: Gültigkeitszeitfenster der Signatur
- `nonce`: zufälliger Nonce mit 32 Byte

Nach der Überprüfung der Signatur ruft der Facilitator on-chain `transferWithAuthorization` von USDC auf, um die Übertragung abzuschließen.

Base ist das am meisten empfohlene Netzwerk für die offizielle Integration, insbesondere für die nachgelagerte Abrechnung mit `upto`, da das Ökosystem für Permit2, USDC und Wallets ausgereifter ist.

Beispiel für ein Base-`exact`-Verifizierungsergebnis:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Erläuterung der Ergebnisse:

- Der kostenpflichtige API-Wiederholungsversuch gibt den Modellinhalt `ADC_BASE_E2E_OK` zurück.
- Die On-Chain-Transaktion ist bereits auf BaseScan abrufbar; die Blocknummer lautet `46726299`.
- `95215` atomic USDC entsprechen `0.095215` USDC und sind der tatsächlich abgerechnete Betrag dieses API-Aufrufs.

Programmausgabe für die Bestellungzahlung mit Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Erläuterung der Ergebnisse:

- Der endgültige Status der Plattformbestellung ist `Finished`.
- Die `pay_id` der Bestellung wird mit demselben Base-Transaktionshash geschrieben.
- `1200000` atomic USDC entsprechen `1.2` USDC und sind der historische tatsächlich gezahlte Betrag dieser 10-Credits-Bestellung gemäß der alten Richtlinie; neue Bestellungen erhalten keinen zusätzlichen Rabatt mehr für die Zahlungsmethode X402, der konkrete Signaturbetrag richtet sich nach der 402-Antwort dieses Vorgangs.

## Solana

Solana verwendet SPL USDC `TransferChecked`. Der Client erstellt eine Übertragungstransaktion, signiert und übermittelt sie und legt anschließend die Transaktionssignatur oder die serialisierte Transaktion in das `PAYMENT-SIGNATURE`-Envelope.

Merkmale von Solana:

- Verwendung von Solana Wallet Adapter oder einem base58 Secret Key;
- das Asset ist der Solana-USDC-Mint;
- derzeit wird nur `exact` unterstützt;
- der Facilitator prüft Mint, Destination, Authority und Amount der Transfer Instruction.

Wenn der Wallet-Fee-Payer-Modus verwendet wird, übermittelt die Wallet die Transaktion direkt; der Facilitator ist für die Bestätigung der Transaktion und die Rückgabe des Settlement-Ergebnisses verantwortlich.

Beispiel für ein Solana-`exact`-Verifizierungsergebnis:

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Erläuterung der Ergebnisse:

- Der kostenpflichtige Wiederholungsversuch hat bereits HTTP 200 zurückgegeben, und das Modell gibt `ADC_SOLANA_E2E_OK` aus.
- Bei der Abfrage der On-Chain-Signatur über einen öffentlichen RPC kann es zu Rate Limits kommen.
- Da Abfragen über öffentliche RPCs Rate Limits unterliegen können, wird hier kein Solana Explorer angegeben. Wenn eine strikte Abstimmung erforderlich ist, verwende einen eigenen Solana RPC oder bestätige die Transaktionssignatur über die Settlement-Aufzeichnungen der Plattform.

## Auswahlhilfe

| Was du tun möchtest        | Empfohlenes Netzwerk           |
| ------------ | -------------- |
| Schnell den minimalen Ablauf durchlaufen     | Base `exact`   |
| Für gewöhnliche Web3-Nutzer | Base           |
| Nachgelagerte Abrechnung für Chat-Vervollständigungen usw.   | Base `upto`    |
| Solana-Ökosystemanwendungen  | Solana `exact` |

Unabhängig davon, welche Chain ausgewählt wird, dürfen Preise nicht im Client fest codiert werden. Der Preis wird durch `accepts[].maxAmountRequired` bestimmt, das vom Server zurückgegeben wird.

## Neue EVM-Netzwerke
Die Unterstützung für Zahlungen mit nativem USDC in festen Beträgen auf den folgenden Netzwerken wurde im Code bereitgestellt und wird Netzwerk für Netzwerk freigeschaltet.
Ob sie verfügbar sind, richtet sich nach den von der Bestellung oder API zurückgegebenen `accepts`; dies bedeutet nicht, dass alle Netzwerke bereits in der Produktion aktiviert sind.

| Network      | Alias      | CAIP-2         | Native USDC                                  |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

Diese Netzwerke unterstützen nur `exact`, die Währungspräzision beträgt 6. Verwenden Sie nicht den gleichnamigen gebrückten USDC.
Bei Verwendung des offiziellen TypeScript/Python-X402-Clients können Sie die Kurzbezeichnung oder die CAIP-2-Kennung aus der Tabelle übergeben.
Der Client verwendet die Ziel-Chain-ID zum Erstellen der Signatur; die Wallet muss das Zielnetzwerk unterstützen.

Die offizielle Unterstützungstabelle der Phantom-Erweiterungs-Wallet führt Arbitrum und Polygon auf; Optimism, Avalanche
sind derzeit nicht in dieser Tabelle aufgeführt, es können Rabby oder MetaMask verwendet werden, die das Zielnetzwerk unterstützen. EVM-Adressen können auf verschiedenen Chains identisch sein,
aber die Guthaben sind voneinander unabhängig, Solana-Adressen sind nicht für EVM-USDC geeignet.
Siehe [Phantom-Wallet-Unterstützungstabelle](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### Graustufen-Zugang für neue Netzwerke

Der Zugang für neue Chains ist standardmäßig ausgeblendet. Beim Aufrufen der Konsole oder von Studio können Sie mit `?features=x402-arbitrum`
die entsprechende Chain aktivieren, mehrere Flags werden durch Kommas getrennt. Zum Deaktivieren einer einzelnen Chain verwenden Sie `?features=-x402-arbitrum`,
zum Löschen lokaler Überschreibungen verwenden Sie `?features=none`. Die Schalter werden für jede Domain separat gespeichert.
Bestellangebote und Zahlungswiederholungen verwenden denselben Schalter, der Server führt eine unabhängige Validierung durch; vorhandene Zahlungsaufzeichnungen können weiterhin angezeigt werden.
Das Aktivieren nur des Seiten-Flags aktiviert keine noch nicht konfigurierte Chain, die tatsächlich zahlbaren Netzwerke richten sich weiterhin nach den Echtzeit-`accepts`.
