Ace Data Cloud X402 rechnet derzeit über USDC ab und unterstützt zwei Arten von Chains: EVM und Solana. Die Signaturmethoden, Asset-Adressen, das Gas-Verhalten und die Anwendungsszenarien unterscheiden sich je nach Netzwerk; vor der Integration muss zuerst das Netzwerk ausgewählt werden.

## Netzwerkkennungen verwenden CAIP-2

`accepts[].network` in x402 v2 ist eine CAIP-2-Kennung und keine Kurzbezeichnung wie `base` oder `skale`. Clients müssen Netzwerke anhand des CAIP-2-Strings vergleichen:

| Netzwerk             | CAIP-2-Kennung                            |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| SKALE Base     | `eip155:1187947933`                       |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Unterstützungsmatrix

| Netzwerk | scheme  | Asset               | Signaturmethode                       | Anwendungsszenario                                      |
| ------ | ------- | ------------------- | ------------------------------------ | -------------------------------------------------- |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Standardempfehlung, ausgereifte Wallet- und Liquiditätsunterstützung. |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | Nachgelagerte Abrechnungs-APIs wie Chat und Modelle. |
| SKALE  | `exact` | SKALE bridged USDC  | EIP-3009 `TransferWithAuthorization` | Niedrige Gas-Kosten, geeignet für EVM-Zahlungsvalidierung und kostengünstige Aufrufe. |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Solana-Wallets, Agents oder On-Chain-Anwendungsszenarien. |

`upto` wird derzeit nur auf Base angeboten. Die tatsächlich verfügbaren Optionen richten sich nach dem von der API zurückgegebenen `accepts`. Du kannst auch den Facilitator prüfen:

```bash
curl https://facilitator.acedata.cloud/supported
```

Die Rückgabe des Facilitator `/supported`:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    { "x402Version": 2, "scheme": "exact", "network": "eip155:1187947933" },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Erklärung der Ergebnisse:

- `exact` auf Base, SKALE und Solana ist ein Zahlungspfad mit festem Betrag.
- Nur Base bietet den nachgelagerten Abrechnungspfad `upto`, der von Permit2 approve abhängt.
- `extra.facilitatorAddress` im Eintrag `upto` ist die Adresse, die der Client bei der Signatur in witness schreiben muss, und muss mit dem vom Server zurückgegebenen Wert übereinstimmen.

## Base

Base verwendet den offiziellen USDC-Contract:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

Im `exact`-Schema signiert der Client EIP-712 `TransferWithAuthorization`. Der Signaturinhalt umfasst:

- `from`: Adresse der zahlenden Wallet
- `to`: Empfangsadresse von Ace Data Cloud
- `value`: Zahlungsbetrag dieser Transaktion
- `validAfter` / `validBefore`: Gültigkeitszeitfenster der Signatur
- `nonce`: zufälliger 32-Byte-Nonce

Nach der Validierung der Signatur ruft der Facilitator on-chain `transferWithAuthorization` von USDC auf, um die Übertragung abzuschließen.

Base ist das am stärksten empfohlene Netzwerk für die produktive Integration und besonders für die nachgelagerte Abrechnung mit `upto` geeignet, da das Ökosystem für Permit2, USDC und Wallets ausgereifter ist.

Beispiel für ein Base-`exact`-Validierungsergebnis:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Erklärung der Ergebnisse:

- Der API-paid-retry gibt den Modellinhalt `ADC_BASE_E2E_OK` zurück.
- Die On-Chain-Transaktion ist auf BaseScan einsehbar, die Blocknummer ist `46726299`.
- `95215` atomic USDC entsprechen `0.095215` USDC und sind der tatsächlich abgerechnete Betrag dieses API-Aufrufs.

Ausführungsergebnis des Programms für die Bestellungzahlung mit Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Erklärung der Ergebnisse:

- Der endgültige Status der Plattformbestellung ist `Finished`.
- Die `pay_id` der Bestellung wird in denselben Base-Transaktions-Hash geschrieben.
- `1200000` atomic USDC entsprechen `1.2` USDC und sind der historische tatsächlich gezahlte Betrag dieser Bestellung über 10 Credits unter der alten Richtlinie; neue Bestellungen erhalten keinen zusätzlichen Rabatt mehr für die Zahlungsmethode X402, der konkrete Signaturbetrag richtet sich nach der 402-Antwort dieser Transaktion.

## SKALE

SKALE verwendet bridged USDC. Die Signaturmethode ist ähnlich wie bei Base ebenfalls EIP-3009. Es eignet sich für EVM-Zahlungsszenarien mit niedrigen Gas-Kosten; die tatsächlichen Aufrufe richten sich weiterhin nach dem von der API zurückgegebenen `accepts`.

Das typische 402-`accepts` von SKALE enthält:

```json
{
  "network": "eip155:1187947933",
  "scheme": "exact",
  "extra": {
    "name": "Bridged USDC (SKALE Bridge)",
    "version": "2",
    "chainId": 1187947933,
    "verifyingContract": "0x85889c8c714505E0c94b30fcfcF64fE3Ac8FCb20"
  }
}
```

SKALE bietet derzeit nur `exact`. Wenn du eine nachgelagerte Abrechnung benötigst, verwende Base `upto`.

Beispiel für ein SKALE-`exact`-Validierungsergebnis:

```text
content ADC_SKALE_E2E_OK
tx 0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
block 1969317
explorer https://skale-base-explorer.skalenodes.com/tx/0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
paid 0.095215 USDC
```

Erklärung der Ergebnisse:
- API paid retry gibt Modellinhalt `ADC_SKALE_E2E_OK` zurück.
- Die Transaktion ist im SKALE explorer auffindbar, die Blocknummer ist `1969317`.
- Der Abrechnungsbetrag dieser `exact`-Zahlung beträgt `0.095215` USDC.

## Solana

Solana verwendet SPL USDC `TransferChecked`. Der Client erstellt eine Überweisungstransaktion, signiert und übermittelt sie und legt anschließend die Transaktionssignatur oder die serialisierte Transaktion in den `PAYMENT-SIGNATURE` envelope.

Eigenschaften von Solana:

- Verwendung von Solana wallet adapter oder base58 secret key;
- Das Asset ist Solana USDC mint;
- Derzeit wird nur `exact` unterstützt;
- Der Facilitator prüft mint, destination, authority und amount der transfer instruction.

Bei Verwendung des wallet fee payer-Modus übermittelt die Wallet die Transaktion direkt, der Facilitator ist für die Bestätigung der Transaktion und die Rückgabe des settlement-Ergebnisses verantwortlich.

Beispiel für ein Solana-`exact`-Validierungsergebnis:

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Erklärung der Ergebnisse:

- paid retry hat bereits HTTP 200 zurückgegeben, und das Modell gibt `ADC_SOLANA_E2E_OK` aus.
- Bei der Abfrage der On-Chain-signature über öffentliche RPCs kann es zu Rate Limits kommen.
- Da öffentliche RPC-Abfragen möglicherweise Rate Limits haben, wird hier kein Solana explorer angegeben. Wenn ein strikter Abgleich erforderlich ist, verwenden Sie bitte einen eigenen Solana RPC oder Abrechnungsaufzeichnungen auf Plattformseite, um die Transaktionssignatur zu bestätigen.

## Wie wählen

| Was Sie tun möchten        | Empfohlenes Netzwerk                         |
| ------------ | ---------------------------- |
| Schnell den minimalen Ablauf durchlaufen     | SKALE `exact` oder Base `exact` |
| Für gewöhnliche Web3-Nutzer | Base                         |
| Nachgelagerte Verbrauchsmessung für Chat-Vervollständigungen usw.   | Base `upto`                  |
| Solana-Ökosystemanwendungen  | Solana `exact`               |
| Kostengünstige EVM-Zahlungsvalidierung | SKALE `exact`                |

Unabhängig davon, welche Chain gewählt wird, kodieren Sie Preise nicht fest im Client. Der Preis wird durch `accepts[].maxAmountRequired` bestimmt, das vom Server zurückgegeben wird.

## Neue EVM-Netzwerke

Code-Unterstützung für native USDC-Zahlungen mit festen Beträgen in den folgenden Netzwerken wurde bereitgestellt und wird je Netzwerk einzeln freigeschaltet.
Ob sie verfügbar sind, richtet sich nach der Bestellung oder den von der API zurückgegebenen `accepts`; dies bedeutet nicht, dass alle Netzwerke bereits in der Produktion aktiviert sind.

| Network      | Alias      | CAIP-2         | Native USDC                                  |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

Diese Netzwerke unterstützen nur `exact`, die Token-Präzision beträgt 6. Verwenden Sie nicht das gleichnamige gebrückte USDC.
Bei Verwendung des offiziellen TypeScript/Python X402 Client können Sie die Kurzbezeichnung oder die CAIP-2-Kennung aus der Tabelle übergeben.
Der Client verwendet die Ziel-chain ID zum Erstellen der Signatur; die Wallet muss das Zielnetzwerk unterstützen.

Die offizielle Unterstützungstabelle der Phantom-Erweiterungs-Wallet führt Arbitrum und Polygon auf; Optimism, Avalanche
sind derzeit nicht in dieser Tabelle aufgeführt, Rabby oder MetaMask, die die Ziel-chain unterstützen, können verwendet werden. EVM-Adressen können auf verschiedenen Chains identisch sein,
aber die Guthaben sind voneinander unabhängig, Solana-Adressen sind nicht für EVM USDC geeignet.
Siehe [Phantom Wallet-Unterstützungstabelle](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### Stufenweiser Zugang für neue Netzwerke

Der Zugang zu neuen Chains ist standardmäßig ausgeblendet. Beim Zugriff auf die Konsole oder Studio können Sie mit `?features=x402-arbitrum`
die entsprechende Chain aktivieren, mehrere flags werden durch Kommas getrennt. Deaktivieren Sie eine einzelne Chain mit `?features=-x402-arbitrum`,
und löschen Sie lokale Überschreibungen mit `?features=none`. Die Schalter werden für jede Domain separat gespeichert.
Bestellangebote und Zahlungswiederholungen verwenden denselben Schalter, der Server validiert unabhängig; vorhandene Zahlungsaufzeichnungen können weiterhin eingesehen werden.
Das Aktivieren des Seiten-flags allein aktiviert keine noch nicht konfigurierte Chain, die tatsächlich zahlbaren Netzwerke richten sich weiterhin nach den Echtzeit-`accepts`.
