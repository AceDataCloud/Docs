Abfrage der detaillierten Geschäfts-API-Aufrufe des aktuellen Kontos der letzten 60 Tage, geeignet zur Überprüfung von Abbuchungen, zur Lokalisierung fehlgeschlagener Anfragen sowie zur Fehlerbehebung nach Service, Application, API oder Credential.

> Auf dieser Seite werden die Aufrufprotokolle des eigenen Kontos abgefragt. Wenn Sie nur die öffentlichen Aufrufstatistiken einer bestimmten API auf der gesamten Plattform anzeigen möchten, verwenden Sie bitte die [API-Aufrufstatistiken](https://platform.acedata.cloud/documents/platform-api-usage).

## Datenaufbewahrungsbereich

Aufrufaufzeichnungen und Abrechnungszusammenfassungen werden für die letzten 60 Tage aufbewahrt; Anfrage- und Antworttexte werden für die letzten 30 Tage aufbewahrt. Aufzeichnungen von 30–60 Tagen können weiterhin nach Trace, Status, Zeit, Modell, Nutzung und tatsächlicher Abbuchung sowie anderen Zusammenfassungen abgefragt werden, aber `metadata.request` und `metadata.response` in den Details werden nicht mehr zurückgegeben. Die für Modellzusammenfassungen und Statistiken gültiger Ergebnisse erforderlichen Zusammenfassungen werden bis zum Ablauf der Texte aufbewahrt. Wenn Texte langfristig aufbewahrt werden müssen, speichern Sie sie bitte beim Aufruf selbst.

## Vorbereitungen

### 1. Konto-Token erstellen

Diese Schnittstelle gehört zur Plattformverwaltungs-API und erfordert die Verwendung eines **Account Token (Konto-Token)**:

1. Melden Sie sich bei der [AceDataCloud-Plattform](https://platform.acedata.cloud) an.
2. Öffnen Sie die [Account-Token-Konsole](https://platform.acedata.cloud/console/platform-tokens).
3. Klicken Sie auf „Erstellen“ und speichern Sie den Token sofort im Passwortmanager oder Secret Manager.

Eine vollständige Beschreibung finden Sie unter [Verwalten von AceDataCloud-Plattform-Konto-Token](https://platform.acedata.cloud/documents/platform-token). Konto-Token werden für `platform.acedata.cloud/api/v1/**` verwendet; für den Aufruf von Geschäfts-Schnittstellen unter `api.acedata.cloud/**` werden API-Credentials verwendet, und beide können nicht miteinander vermischt werden.

```shell
export PLATFORM_TOKEN='Ihr Konto-Token'
```

Schreiben Sie den Token nicht in Frontend-Code, Protokolle oder öffentliche Repositories; falls er offengelegt wird, löschen Sie ihn bitte sofort in der Konsole und erstellen Sie ihn erneut.

### 2. Filter-IDs vorbereiten (optional)

Ohne Filterbedingungen werden die Aufzeichnungen angezeigt, die das aktuelle Konto anzeigen darf. Wenn Sie den Bereich eingrenzen müssen:

- `application_id`: aus der [Service-Antragsliste](https://platform.acedata.cloud/documents/platform-application-list) abrufen;
- `credential_id`: aus der [API-Credential-Liste](https://platform.acedata.cloud/documents/platform-credential-list) abrufen;
- `api_id`: aus der [API-Liste](https://platform.acedata.cloud/documents/platform-api-list) abrufen;
- `service_id`: aus der [Service-Liste](https://platform.acedata.cloud/documents/platform-service-list) abrufen.

Normale Benutzer müssen `user_id` nicht übergeben; wenn es explizit übergeben wird, muss es mit dem aktuellen Konto übereinstimmen, andernfalls wird `403` zurückgegeben. Administratoren können diesen Parameter zur kontoübergreifenden Filterung verwenden.

## Schnittstellenübersicht

| Element       | Inhalt                                              |
| ------------- | -------------------------------------------------- |
| Methode       | `GET`                                              |
| URL           | `https://platform.acedata.cloud/api/v1/usage/apis/` |
| Authentifizierung | `Authorization: Bearer ${PLATFORM_TOKEN}`      |
| OAuth Scope   | `usage:read` (`platform:read` / `platform` kann erweitert enthalten sein) |
| Paginierung   | `count` + `items`, standardmäßig 10 Einträge pro Seite |

## Abfragebereich

| `perspective` | Bedeutung                    |
| ------------- | ---------------------------- |
| `both`        | Standardwert; gibt Aufzeichnungen zurück, die vom aktuellen Konto bezahlt oder tatsächlich aufgerufen wurden |
| `billing`     | Gibt nur Aufzeichnungen zurück, die vom aktuellen Konto bezahlt wurden |
| `actor`       | Gibt nur Aufzeichnungen zurück, die vom aktuellen Konto tatsächlich aufgerufen wurden |

## Abfrageparameter

| Parameter         | Typ      | Erforderlich | Standard      | Beschreibung                         |
| ----------------- | -------- | ------------ | ------------- | ------------------------------------ |
| `perspective`     | string   | Nein         | `both`        | `billing`, `actor` oder `both`       |
| `user_id`         | UUID     | Nein         | —             | Nur Administratoren können nach Benutzern filtern; wiederholte Parameter werden unterstützt |
| `service_id`      | UUID     | Nein         | —             | Nach Service filtern; wiederholte Parameter werden unterstützt |
| `application_id`  | UUID     | Nein         | —             | Nach Application filtern; wiederholte Parameter werden unterstützt |
| `api_id`          | UUID     | Nein         | —             | Nach API filtern; wiederholte Parameter werden unterstützt |
| `credential_id`   | UUID     | Nein         | —             | Nach API-Credential filtern; wiederholte Parameter werden unterstützt |
| `status_code`     | integer  | Nein         | —             | Nach HTTP-Statuscode filtern; wiederholte oder durch Kommas getrennte Werte werden unterstützt |
| `created_at_from` | datetime | Nein         | —             | Untere Grenze der Erstellungszeit, ISO 8601 |
| `created_at_to`   | datetime | Nein         | —             | Obere Grenze der Erstellungszeit, ISO 8601 |
| `limit`           | integer  | Nein         | 10            | Anzahl der Einträge pro Seite, maximal 100 |
| `offset`          | integer  | Nein         | 0             | Paginierungsversatz                  |
| `ordering`        | string   | Nein         | `-created_at` | Absteigend nach Erstellungszeit       |

Wenn die Anfragezeit früher als die letzten 60 Tage liegt, gibt die Schnittstelle einen `400`-Feldvalidierungsfehler zurück und weist darauf hin, dass vollständige Aufrufdetails nur 60 Tage aufbewahrt werden.

## Anfragebeispiele

Abfrage der letzten 100 Aufzeichnungen:

```shell
curl --get 'https://platform.acedata.cloud/api/v1/usage/apis/' \
  --data-urlencode 'perspective=both' \
  --data-urlencode 'limit=100' \
  --data-urlencode 'ordering=-created_at' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

Nach Zeit, Application und Fehlerstatus filtern:

```shell
export APPLICATION_ID='Ihre Application-ID'

curl --get 'https://platform.acedata.cloud/api/v1/usage/apis/' \
  --data-urlencode "application_id=${APPLICATION_ID}" \
  --data-urlencode 'created_at_from=2026-09-01T00:00:00Z' \
  --data-urlencode 'created_at_to=2026-09-02T00:00:00Z' \
  --data-urlencode 'status_code=500' \
  --data-urlencode 'limit=100' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

Python-Paginierungsbeispiel:

```python
import os
import requests

url = "https://platform.acedata.cloud/api/v1/usage/apis/"
headers = {"Authorization": f"Bearer {os.environ['PLATFORM_TOKEN']}"}
params = {"perspective": "both", "limit": 100, "offset": 0}

response = requests.get(url, headers=headers, params=params, timeout=30)
response.raise_for_status()
data = response.json()

for usage in data["items"]:
    print(usage["created_at"], usage["status_code"], usage["deducted_amount"], usage["trace_id"])

if params["offset"] + len(data["items"]) < data["count"]:
    params["offset"] += len(data["items"])
```

## Wichtige Felder

| Feld                             | Beschreibung                              |
| -------------------------------- | ----------------------------------------- |
| `user_id`                        | Das Konto, dem diese Belastung zugeordnet wird |
| `actor_user_id`                  | Das Konto, das den Aufruf tatsächlich auslöst; kann sich von `user_id` unterscheiden, wenn andere zur Nutzung der Zugangsdaten autorisiert werden |
| `used_amount`                    | Die nach den ursprünglichen Regeln für diesen Aufruf berechnete Nutzung |
| `original_amount`                | Die ursprüngliche Nutzung vor Anwendung des Anwendungsrabatts |
| `deducted_amount`                | Das endgültig tatsächlich abgezogene Kontingent |
| `remaining_amount`               | Das verbleibende Kontingent der Application nach Abschluss dieser Belastung |
| `elapsed`                        | Die vom Server aufgezeichnete Aufrufdauer in Sekunden |
| `trace_id`                       | Die zur Untersuchung einer einzelnen Anfrage verwendete Tracking-Kennung |
| `metadata`                       | Öffentliche Metadaten; die Liste gibt nicht den vollständigen Anfrage- oder Antwortinhalt zurück |
| `api` / `service` / `credential` | Zusammenfassungen verknüpfter Objekte zur einfacheren Anzeige; können leer sein, wenn das verknüpfte Objekt nicht mehr existiert |

Die Kontingenteinheit wird durch `service.unit` der entsprechenden Application bestimmt und sollte nicht standardmäßig als US-Dollar betrachtet werden.

## Fehler und Wiederholungsversuche

| HTTP | `error`                   | Bedeutung             | Vorgehensweise                               |
| ---- | ------------------------- | -------------------- | -------------------------------------------- |
| 400  | Feldvalidierungsfehler    | Der Abfragebereich liegt vor der Aufbewahrungsfrist von 60 Tagen | Passen Sie die Startzeit auf die letzten 60 Tage an |
| 401  | `not_authenticated`       | Das Kontotoken fehlt oder ist ungültig | Prüfen Sie das Account Token und verwenden Sie nicht fälschlicherweise das fachliche Credential |
| 403  | `permission_denied`       | Die Anfrage enthält Datensätze, für deren Anzeige keine Berechtigung besteht | Entfernen Sie nicht autorisierte Benutzerfilter |
| 429  | `usage_query_in_progress` | Eine vollständig identische Abfrage wird noch ausgeführt | Warten Sie auf `Retry-After` und wiederholen Sie den Versuch mit Backoff |
| 503  | `usage_query_timeout`     | Die Abfrage überschreitet das serverseitige Sicherheitszeitlimit | Verkleinern Sie den Zeitbereich oder fügen Sie Filterbedingungen hinzu und versuchen Sie es erneut |

Für dieselbe Gruppe von Abfrageparametern darf höchstens eine Anfrage gleichzeitig in Bearbeitung sein. Verwenden Sie für umfangreiche Abfragen bevorzugt Zeitfenster von einem Tag oder weniger und überlagern Sie nicht identische Anfragen in festen Intervallen.
