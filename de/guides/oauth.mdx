---
title: "Ace Data Cloud OAuth 2.0 integrieren"
---

Lasse Benutzer deine Anwendung für den Zugriff auf ihr Ace Data Cloud-Profil, Service-Abonnements, API Keys, Nutzung oder Bestellungen autorisieren. Verwende den Standard **Authorization Code + S256 PKCE**: Die Anwendung öffnet die Autorisierungsseite, der Benutzer stimmt zu und erhält danach einen einmaligen `code`, der anschließend gegen einen OAuth Access Token eingetauscht wird.

OAuth Access Tokens werden für den Zugriff auf Kontoresourcen-APIs verwendet; für den Aufruf der Modell-API wird der entsprechende API Key verwendet. Eine OAuth-Autorisierung erstellt nicht automatisch API Keys, aktiviert keine Services und erhöht kein Guthaben.

## Integrationsmethode auswählen

| Methode            | Geeignete Szenarien                                | Nach Abschluss der Autorisierung                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Standard-OAuth-Weiterleitung   | Eigenständige Websites, Desktop- oder Mobile-Clients; eingebettete Websites initiieren die Autorisierung selbst            | Der Browser kehrt zur von der Anwendung registrierten `redirect_uri` zurück, und die Anwendung verarbeitet `code` und `state` |
| Studio-Website-Komponentenautorisierung | Die Website bettet die Studio-Startseite ein und möchte das aktuelle Studio-Konto des Besuchers verwenden | Studio sendet der Anwendung eine Nachricht mit dem Autorisierungsergebnis; die Anwendung leitet nicht weiter, und die ursprüngliche Seite bleibt erhalten                  |

Die Standardweiterleitung erfordert weder `embed=studio`, `embed_origin` noch `postMessage`. Im Studio-Komponentenmodus erstellt der Host die Autorisierungsseite und verwaltet die Nachrichtenbrücke; Dritte integrieren sich gemäß dem Komponentenprotokoll am Ende dieses Dokuments und dürfen diese beiden Parameter nicht selbst zusammensetzen.

## Endpunkte und Discovery-Dokument

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Zweck                | Adresse                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Browser-Autorisierungsseite            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| OAuth Token abrufen／aktualisieren | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Widerrufsanfrage einreichen            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Informationen zum aktuellen Benutzer            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| OAuth-Anwendungsverwaltungsseite      | [OAuth-Anwendungen](https://auth.acedata.cloud/user/oauth-apps)                            |
| Anwendungsliste／Registrierungs-API des angemeldeten Benutzers   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Öffentliche Anwendungsinformationen für die Autorisierungsseite      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Vorhandene API Keys des Benutzers     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<Benutzer-ID>&limit=100` |

Die Anwendungsverwaltungs-API erfordert eine Kontologin-Authentifizierung und ist keine anonyme dynamische Registrierungs-API (DCR). Die eigenen Discovery-/Registrierungsadressen des MCP-Dienstes und die OAuth-Kontoendpunkte in dieser Tabelle sind unterschiedliche Zugänge; beim Verbinden mit einem konkreten MCP ist gemäß dessen Dokumentation und Discovery-Ergebnissen vorzugehen.

Das Discovery-Dokument dient zum Abrufen von Endpunkten und Protokollfunktionen. Der aktuelle Ablauf gibt OAuth Tokens zurück, jedoch kein `id_token`; verarbeite dies nicht allein aufgrund des Vorhandenseins des `openid` Scope als vollständigen OpenID-Connect-Login-Ablauf.

## Berechtigungsbereiche: Aktuelle Scope-Namen verwenden

`scope` besteht aus durch Leerzeichen getrennten, groß-/kleinschreibungssensitiven Berechtigungsnamen. Neue Anwendungen verwenden konkrete Berechtigungen wie `profile:read`, `email:read`, `phone:read`.

### Wo die beantragbaren Berechtigungen abgerufen werden

Nach dem Login gibt die OAuth-Anwendungslisten-API `GET /api/v1/oauth2/applications/` `available_scopes` zurück; der Berechtigungsauswähler auf der Anwendungsverwaltungsseite verwendet denselben Katalog. Dies sind die optionalen Bereiche, die gewöhnliche Self-Service-Anwendungen verwenden sollten.

**`scopes_supported` im Discovery-Dokument enthält alle von der Plattform erkannten Berechtigungsnamen, bedeutet jedoch nicht, dass deine Anwendung jede davon beantragen kann.** Die tatsächliche Autorisierung prüft gleichzeitig:

1. ob die Berechtigung an diesen Anwendungstyp delegiert werden darf;
2. ob die Berechtigung in den erlaubten Bereichen dieser OAuth-Anwendung registriert wurde;
3. ob der aktuelle Benutzer über die angeforderte Berechtigung verfügt.

Unbekannte, nicht registrierte, nicht delegierbare oder beim Benutzer nicht vorhandene Berechtigungen geben `invalid_scope` zurück. Auch beim Einlösen und Aktualisieren des Autorisierungscodes wird erneut geprüft; Berechtigungen werden nicht automatisch ergänzt oder erweitert.

### Optionale Berechtigungen für gewöhnliche Self-Service-Anwendungen

Nachfolgend der aktuelle Katalog (2026-10-09); bei der Integration ist `available_scopes` maßgeblich.

| Scope                                            | Zweck                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Persönliche Daten lesen／aktualisieren                               |
| `email:read`                                     | E-Mail-Adresse lesen                                    |
| `phone:read`                                     | Mobiltelefonnummer und Region lesen                                |
| `billing-profile:read` / `billing-profile:write` | Rechnungsdaten lesen／verwalten                               |
| `applications:read` / `applications:write`       | Service-Abonnements lesen／verwalten                               |
| `credentials:read` / `credentials:write`         | API Keys lesen／verwalten                           |
| `usage:read`                                     | Nutzungsprotokolle lesen                                  |
| `orders:read` / `orders:write`                   | Bestellungen lesen／erstellen und verwalten                              |
| `auto-recharge:read` / `auto-recharge:write`     | Einstellungen für automatische Aufladung lesen／verwalten                             |
| `recharge-cards:redeem`                          | Aufladekarten einlösen                                   |
| `coin:read`                                      | Token-bezogene Informationen lesen                                |
| `distribution:read`                              | Vertriebsinformationen lesen                                  |
| `connections:read` / `connections:write`         | Verbindungen lesen／verwalten                                 |
| `skills:read` / `skills:write`                   | Skills lesen／verwalten                                 |
| `openid`                                         | Die aktuelle Implementierung erlaubt UserInfo auch die Rückgabe grundlegender Daten; gibt kein ID Token zurück    |
| `offline_access`                                 | Refresh Token anfordern, um nach Ablauf des Access Tokens aktualisieren zu können |

Verwende beispielsweise zum ausschließlichen Lesen persönlicher Daten `profile:read`; füge für die E-Mail-Adresse `email:read` hinzu; verwende zum Lesen vorhandener API Keys `profile:read credentials:read`. Beantrage `credentials:write` nur, wenn tatsächlich Keys erstellt oder geändert werden müssen, und füge `offline_access` nur hinzu, wenn eine Aktualisierung erforderlich ist.

Einige Berechtigungen sind nur für von der Plattform genehmigte vertrauenswürdige Anwendungen verfügbar, beispielsweise `sites:read`, `sites:write`, `platform-tokens:read`; andere Berechtigungen sind für gewöhnliche OAuth-Anwendungen Dritter nicht verfügbar. Die Client-Typen `public`／`confidential` beschreiben, ob ein Secret sicher verwahrt werden kann, und haben nichts damit zu tun, ob die Anwendung vertrauenswürdig ist. Selbst erstellte Anwendungen können vertrauenswürdige Berechtigungen nicht selbst aktivieren.

`account` ist ein Berechtigungsauswähler für Konten, der vom angegebenen offiziellen Kontoverwaltungs-MCP verwendet wird; es ist kein „Alle Berechtigungen“-Scope für Drittanwendungen und darf nicht mit anderen Scopes kombiniert werden. Dritte müssen die benötigten konkreten Berechtigungen ausdrücklich auflisten.

### Migration aus alter Dokumentation

| Alte Schreibweise                                         | Aktuelle Integration                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Die tatsächlich benötigten konkreten Berechtigungen einzeln auflisten; es gibt keinen allgemeinen Ersatzwert für „Alles auswählen“ |

Alte Namen werden nicht als kompatible Aliase akzeptiert. Aktualisiere gleichzeitig die in der OAuth-Anwendung registrierten Scopes, die Autorisierungs-URL und deine eigenen Berechtigungsprüfungen; das Ändern der Anwendungskonfiguration fügt bereits ausgestellten Tokens keine Berechtigungen hinzu, sodass Benutzer erneut autorisieren müssen.

## Schritt 1: OAuth-Anwendung registrieren

Öffne die [OAuth-Anwendungsverwaltung](https://auth.acedata.cloud/user/oauth-apps), erstelle eine Anwendung und fülle Folgendes aus:
- Name, Beschreibung, Anwendungs-Logo: Werden auf einer Seite der Autorisierungsseite der Anwendung angezeigt.
- Client-Typ: Für reine Frontend-, mobile oder Desktop-Clients **Public** wählen; für Dienste, die secret im Backend verwahren können, **Confidential** wählen.
- Rückrufadresse: In der Produktionsumgebung HTTPS verwenden und die vollständige URL registrieren, unter der die Anwendung den Rückruf tatsächlich verarbeitet.
- Berechtigungen: Aus dem auf der Seite bereitgestellten Verzeichnis die tatsächlich benötigten scopes auswählen.

`client_id` speichern. Confidential-Clients speichern `client_secret` auf der Serverseite und dürfen es nicht in HTML, Frontend-Build-Variablen oder URLs ablegen. Public-Clients verwenden beim Eintauschen von token kein secret; selbst wenn die Registrierungsantwort dieses Feld enthält, darf es nicht als Anmeldeinformation behandelt werden, die der Client geheim halten kann.

`redirect_uri` muss bei der Registrierung, Autorisierung und beim Token-Tausch exakt übereinstimmen, einschließlich Pfad, abschließendem Schrägstrich und Abfrageparametern. Jedes Konto kann maximal 20 Anwendungen erstellen. Secret wird nur beim Erstellen/Rotieren angezeigt; nach der Rotation kann das alte secret nicht weiter für Tauschvorgänge verwendet werden, die eine Client-Authentifizierung erfordern.

## Schritt 2: Autorisierung über die Schaltfläche starten

Bei jedem Klick auf Verbinden einen neuen zufälligen `state` und `code_verifier` erzeugen und berechnen:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

`state`, verifier und Rückrufadresse in der eigenen Sitzung der Anwendung speichern und dann die Autorisierungsseite mit URL-kodierten Parametern öffnen:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<完整回调地址>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<本次随机值>
  &code_challenge=<本次S256挑战值>
  &code_challenge_method=S256
```

Public-Clients müssen S256 PKCE senden. Obwohl Discovery weiterhin `plain` aufführt, dürfen Public-Clients es nicht verwenden. Confidential-Clients wird ebenfalls empfohlen, S256 zu verwenden; wenn beim Starten der Autorisierung PKCE verwendet wurde, muss beim Tausch der entsprechende verifier übermittelt werden.

Nach der Zustimmung des Benutzers erfolgt die Rückkehr zu `redirect_uri`, und die Abfrageparameter enthalten `code` sowie den unverändert zurückgegebenen `state`. Bei Ablehnung werden `error=access_denied`, eine Fehlerbeschreibung und `state` zurückgegeben. Vor der Verarbeitung des Rückrufs zuerst überprüfen, ob state mit dieser Sitzung übereinstimmt. Der Autorisierungscode ist 10 Minuten gültig und kann nur einmal eingetauscht werden; nach einem Fehler sollte die Verbindung erneut gestartet werden, statt die alte Rückruf-URL wiederholt zu aktualisieren.

## Schritt 3: OAuth token eintauschen

Public-Clients tauschen direkt im Browser oder Client ein; Confidential-Clients tauschen in ihrem eigenen Backend ein. Der Anfragekörper unterstützt Formularcodierung, und die folgenden Variablen stehen für die Daten, die die Anwendung bei dieser Autorisierung erhalten hat:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Confidential-Clients müssen auf der Serverseite zusätzlich das Formularfeld `client_secret` hinzufügen. Derzeit wird `client_secret_post` unterstützt; HTTP-Basic-Client-Authentifizierung nicht als unterstützte Methode behandeln.

Aus der erfolgreichen Antwort `access_token`, `token_type`, `expires_in` und den tatsächlich gewährten `scope` auslesen. Nur wenn `offline_access` angefordert und genehmigt wurde, gibt es einen `refresh_token`. OAuth access token nicht als API Key der Modell-API behandeln und token, verifier oder Autorisierungscode nicht in Logs, Analyseereignisse oder Freigabelinks schreiben.

## Schritt 4: Benutzerinformationen und API Key lesen

Zuerst UserInfo mit dem OAuth access token anfordern:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Die zurückgegebenen Felder hängen von scope ab: `id` ist die Benutzerkennung; mit `profile:read` oder `openid` können grundlegende Profildaten gelesen werden (wie `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); für E-Mail ist `email:read` erforderlich, für Telefonnummer und Region `phone:read`. Nicht davon ausgehen, dass nicht autorisierte Felder immer vorhanden sind.

Wenn ein vorhandener API Key benötigt wird und `credentials:read` genehmigt wurde, `id` aus UserInfo als Filterbedingung verwenden:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Die zurückgegebene Liste verwendet `count` und `items`; das Key-Feld ist **`items[*].token`**, nicht `data[0].value`. `user_id=me` ist keine gültige Benutzer-ID für diese Schnittstelle. Mehrseitige Daten mit `offset`／`limit` weiter lesen und die erste Seite nicht als alle Anmeldeinformationen behandeln.

Die passende Anmeldeinformation anhand von Anwendung, Dienst und Gültigkeitsstatus auswählen, nicht blind den ersten Eintrag nehmen. Eine leere Liste bedeutet nicht, dass die Autorisierung fehlgeschlagen ist; der Benutzer hat möglicherweise noch keinen passenden Key erstellt. Die Berechtigungskontrolle des OAuth access token und Dienstumfang, Kontingent sowie Ablaufbedingungen des API Key selbst sind unterschiedliche Einschränkungen.

**Das Erlauben des Lesens von API Key bedeutet, dass Dritte ihn speichern und verwenden können. Das Widerrufen der OAuth-Anfrage oder das Löschen des Anmeldestatus der Anwendung macht bereits kopierte API Key nicht ungültig; der Benutzer muss den Key in der Anmeldeinformationsverwaltung separat widerrufen oder rotieren.**

## Ausführbares Public / PKCE-Browserbeispiel

Die folgende Seite unter der registrierten `REDIRECT_URI` bereitstellen und `CLIENT_ID` sowie Rückrufadresse ersetzen. Die Schaltfläche startet die Standardautorisierung und liest nach der Rückkehr auf dieselbe Seite die Profildaten sowie die Anzahl vorhandener Key. Das Beispiel zeigt oder persistiert keine Key; Produktionsanwendungen verwenden die Ergebnisse entsprechend dem tatsächlichen Zweck. Zuerst auf einer eigenständigen Browserseite verifizieren und dann gemäß den späteren iframe-Anforderungen abnehmen.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Mit Ace Data Cloud verbinden</title>
<button id="connect" type="button">Konto verbinden</button>
<p id="status" role="status">Noch nicht verbunden</p>
<script type="module">
const CLIENT_ID = 'Durch deine client_id ersetzen';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`Schnittstelle gab HTTP ${response.status} zurück`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = 'Verbindung konnte nicht gestartet werden. Überprüfe die Browserspeichereinstellungen und versuche es erneut.';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('Autorisierungssitzung stimmt nicht überein. Bitte erneut verbinden.');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('Autorisierungssitzung ist abgelaufen. Bitte erneut verbinden.');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('Autorisierung wurde nicht abgeschlossen. Du kannst dich erneut verbinden.');
    if (!code) throw new Error('Dem Rückruf fehlt der Autorisierungscode. Bitte erneut verbinden.');
    status.textContent = 'Verbindung wird hergestellt…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('Autorisierungstoken wurde nicht erhalten.');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('Benutzerkennung wurde nicht erhalten.');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('Format der Anmeldedatenliste stimmt nicht überein.');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `Verbunden mit ${profile.nickname || profile.username || profile.id}; diese Seite hat ${keyCount} API Keys.`;
  } catch (error) {
    status.textContent = `Verbindung nicht abgeschlossen: ${error.message || 'Netzwerkfehler'} Bitte klicke erneut auf Verbinden.`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Der Rückruf und der Einstieg des Beispiels müssen denselben Ursprung und denselben Browser-Tab／iframe verwenden, damit das zuvor gespeicherte `sessionStorage` gelesen werden kann. Produktionsanwendungen sollten Token in ihrem eigenen Sitzungsschema verwalten, Ablauf behandeln und Autorisierungs-URL-Parameter nach Erhalt der Antwort entfernen; die Hauptoberfläche der Seite sollte zuerst gerendert werden, und Netzwerkfehler sollten nur den Verbindungsstatus beeinflussen.

## iframe in White-Label-Websites

### Die Kundenwebsite leitet selbst zur Autorisierungsseite weiter

Verwende einfach Standard-OAuth-Parameter und deine eigene Rückrufverarbeitung; `window.location.assign()` navigiert den aktuellen iframe, während die übergeordnete Seite auf der White-Label-Domain verbleibt. Es ist nicht erforderlich, für das Symbol `embed=studio` hinzuzufügen oder das Studio-Nachrichtenprotokoll zu implementieren.

Folgende Bedingungen müssen erfüllt sein:

- Anwendungsseite und Rückrufseite verwenden HTTPS, sind tatsächlich erreichbar und erlauben die Einbettung durch die White-Label-übergeordnete Domain per iframe; überprüfe bei beiden `Content-Security-Policy: frame-ancestors` und `X-Frame-Options`.
- Die Sandbox erlaubt die für die Seite erforderlichen Skripte, Formulare und Ursprungs-／Speicherfunktionen. Bei Unterstützung einer Anmeldung per Pop-up werden zudem entsprechende Pop-up-Funktionen benötigt; verwende bevorzugt die von Studio bereitgestellte Website-Komponentenkonfiguration.
- Der Browser erlaubt dem aktuellen Einbettungsszenario die für den Autorisierungsstatus benötigte Speicherung. Der Anmeldestatus der White-Label-Website und der Anmeldestatus von AuthFrontend können unterschiedlich sein; gehe nicht davon aus, dass eine Anmeldung bei der White-Label-Website bereits eine Anmeldung bei der Autorisierungsseite bedeutet.
- Der Token-Austauschdienst im Rückruf ist verfügbar, und ursprungsübergreifende Anfragen erlauben den Anwendungsursprung; DNS-, CORS- und HTTP-Fehler müssen einen erneut versuchbaren Status anzeigen und dürfen nicht das Rendern der gesamten Seite stoppen.

Die linke Seite der Autorisierungsseite liest das OAuth-Anwendungslogo; die rechte Seite liest das Favicon／Logo dieser Site, wenn der Browser einen übergeordneten Ursprung bereitstellen kann und die übergeordnete Domain die Prüfung verifizierter Websites besteht, andernfalls wird ein Standardsymbol angezeigt. Dies bestimmt nur die Markendarstellung, begründet keine Anmeldesitzung und stellt der Kundenseite keine Kontoberechtigungen bereit.

**Aktuelle Einschränkung: Wenn sich bei normalem OAuth innerhalb eines iframe erneut angemeldet werden muss, besteht noch eine Lücke im Ablauf, nach Abschluss der Anmeldung zur Autorisierungsseite zurückzukehren.** Vor der Inbetriebnahme müssen „Auth bereits angemeldet“ und „Auth nicht angemeldet／abgelaufen“ jeweils separat abgenommen werden. Bevor diese Lücke behoben und verifiziert ist, kann die erste Anmeldung über eine separate Seite mit Standard-OAuth erfolgen oder die untenstehende Studio-Komponentenautorisierung verwendet werden; verspreche nicht allein auf Grundlage bereits angemeldeter Testergebnisse, dass alle iframe-Szenarien funktionieren.

### Mit dem aktuellen Studio-Konto autorisieren

Aktiviere OAuth in Studio unter „Einstellungen → Startseite → Website-Komponenten“ und trage `client_id` sowie die registrierte Rückrufadresse ein. Website und Rückruf müssen denselben HTTPS-Ursprung verwenden und sich vom Studio-Ursprung unterscheiden. Die Drittanbieterseite muss:

1. `acedatacloud:oauth:ready` an den exakten origin der übergeordneten Website senden sowie `acedatacloud:oauth:init` empfangen und validieren.
2. Über die Schaltfläche state und PKCE verifier erzeugen und `acedatacloud:oauth:authorize` (state, S256 challenge) senden; verifier verbleibt auf der eigenen Seite.
3. Übergeordnetes Fenster, origin und state validieren, code oder error in `acedatacloud:oauth:result` behandeln und am Standard-Token-Endpunkt austauschen.
Studio zeigt die Autorisierungsseite im Komponentenbereich an; nach Zustimmung des Benutzers wird der Autorisierungscode per Nachricht zurückgegeben, die Anwendung muss nicht umleiten. Ohne Anmeldung wird `login_required` zurückgegeben, bei Ablehnung `access_denied`, bei Wartezeitüberschreitung `authorization_timeout`. Bei Kontoänderungen wird das Anwendungs-iframe neu erstellt und unvollständige Autorisierungen werden abgebrochen.

Die Komponente fordert aktuell `profile:read credentials:read` an und enthält kein `offline_access`. Gehen Sie nicht davon aus, dass Sie unbedingt ein Refresh-Token erhalten können. `embed=studio` und `embed_origin` werden vom Studio-Host und der Autorisierungsseite verwaltet, die Kundenseite muss nur das Nachrichtenprotokoll befolgen.

Ein vollständiges Button-Beispiel finden Sie im [OAuth-Integrationsleitfaden für Studio-Website-Komponenten](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Lebenszyklus, Aktualisierung und Widerruf

Die Standardgültigkeitsdauer des Access-Tokens beträgt 15 Tage; eine Aktualisierung oder erneute Autorisierung sollte anhand von `expires_in` in jeder Antwort geplant werden; das Refresh-Token gilt standardmäßig 30 Tage, die Laufzeit wird von der Dienstkonfiguration beeinflusst. Codieren Sie diese beiden Werte nicht fest als dauerhafte Zusagen.

Nach Gewährung von `offline_access` kann Folgendes aufgerufen werden:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Eine Aktualisierung gibt neue Token zurück, die Anwendung sollte den neuesten Wert speichern. Bei der Aktualisierung wird geprüft, ob die Anwendung weiterhin gültig ist, der Benutzer verfügbar ist und die Berechtigungen weiterhin gewährt sind. Bei Fehlern löschen Sie Ihren eigenen Verbindungsstatus und autorisieren Sie erneut.

**Die aktuelle OAuth-Aktualisierungsimplementierung garantiert nicht, dass das alte Refresh-Token nach der Aktualisierung sofort ungültig wird.** Behandeln Sie den Erhalt eines neuen Tokens nicht so, als wäre das alte Token widerrufen worden, und ersetzen Sie das Beenden bestehender Token nicht durch das Rotieren von Secrets.

Der Widerrufsaufruf erfolgt folgendermaßen:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Der aktuelle Widerrufs-Endpunkt gibt HTTP 200 zurück, implementiert jedoch keine sofortige Ungültigmachung ausgestellter JWTs.** Anwendungen sollten die von ihnen gespeicherten Token löschen und dürfen 200 nicht als Nachweis dafür betrachten, dass alle ausgestellten Token oder API-Keys ungültig sind. Bei kompromittierten oder kopierten API-Keys widerrufen oder rotieren Sie die entsprechenden Anmeldedaten separat.

## Häufige Fehler und Abnahme

| Phänomen／Fehler                         | Prüfung                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Verwenden Sie aktuelle Berechtigungsnamen; prüfen Sie den Anwendungsregistrierungsbereich, Delegierungsbeschränkungen und Benutzerberechtigungen. Der gesamte Discovery-Katalog ist kein für Anwendungen auswählbarer Katalog                      |
| `invalid_request`             | Pflichtparameter, exakte Rückrufadresse, S256-Challenge und -Methode für Public Clients                        |
| `invalid_client`              | Client-ID, Anwendungsstatus, Secret für Confidential Clients; prüfen Sie, ob Basic-Authentifizierung fälschlich verwendet wird             |
| `invalid_grant`               | Code abgelaufen／bereits verwendet, Verifier oder Redirect-URI stimmt nicht überein; bei Aktualisierung werden auch Anwendungs- und Berechtigungsänderungen geprüft                 |
| `access_denied`               | Benutzer lehnt ab, Verbindungsbutton wiederherstellen, Autorisierung nicht wiederholt als Schleife anzeigen                                                  |
| `unsupported_grant_type`      | Aktuell werden `authorization_code`, `refresh_token` unterstützt                             |
| HTTP 401／403                  | Unterscheiden Sie zwischen ungültigem Anmeldestatus, Token, Autorisierungs-Scope und den Zugriffsrechten der Ressource selbst                                     |
| `Failed to fetch`、DNS／CORS-Fehler | Prüfen Sie den tatsächlichen Anfragehost und die Verfügbarkeit des Kunden-Backends, dies darf nicht auf „der Benutzer hat keinen Key“ zurückgeführt werden                                      |
| Autorisiert, aber Key kann nicht gelesen werden                   | Verwenden Sie `platform.acedata.cloud`, die tatsächliche Benutzer-ID, `items[*].token`; unterscheiden Sie leere Listen, Paginierung und fehlgeschlagene Antworten |
| Ganze Seite nach Autorisierungsrückgabe leer                     | Seite zuerst rendern; Rückruf, Token, UserInfo und Anfragen nach Anmeldedaten behandeln jeweils Fehler; lassen Sie Initialisierungsfehler nicht die gesamte Seite anhalten                      |
| Nach iframe-Anmeldung wird nicht fortgefahren                 | Nach den oben genannten bestehenden Einschränkungen behandeln; Szenarien für nicht angemeldet, abgelaufen, abgelehnt und erneute Verbindung testen                                          |

Validieren Sie vor der Auslieferung mindestens: korrekten Rückruf, Ablehnung, fehlerhaften State, abgelaufenen／bereits verwendeten Code, keinen Key, Netzwerkausfall, Token-Ablauf, fehlenden erforderlichen Scope sowie die erste Anmeldung und Kontowechsel im iframe-Szenario. Speichern Sie in den Testnachweisen keine vollständigen Codes, Token oder API-Keys.
