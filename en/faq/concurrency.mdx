## Default Concurrency Limits

Per API token (in-flight requests):

| Service category | Default concurrency |
|---|---|
| LLM Chat (sync) | 20 |
| Midjourney | 5 |
| Flux / Seedream / Nano Banana | 10 |
| Sora / Veo / Kling / Hailuo / Luma | 5 |
| Suno / Producer | 5 |
| Fish Audio | 10 |

Exceeded:

```json
{
  "success": false,
  "error": {
    "code": "rate_limited",
    "message": "Concurrency limit exceeded for this token."
  }
}
```

HTTP `429`.

## Rate Limits (QPS)

- **Sync endpoints**: default 60 QPS / token
- **Async submit**: upstream-dependent (table below)
- **Polling (`/tasks`)**: default 60 QPS / token

| Service | Default QPS |
|---|---|
| Midjourney | 1 |
| Sora | 0.5 |
| Veo | 0.5 |
| Kling | 1 |
| Suno | 1 |
| Flux | 5 |

## Requesting a Raise

Email `support@acedata.cloud` with:

1. Account email or `user_id`
2. Desired concurrency / QPS
3. Business context (helps us check upstream capacity)

Typical response within 1 business day.

## Retry Strategy

For `429` / `5xx`:

```python
import time, random, requests

def call(url, headers, body, max_attempts=5):
    for i in range(max_attempts):
        r = requests.post(url, headers=headers, json=body, timeout=300)
        if r.status_code < 500 and r.status_code != 429:
            return r
        time.sleep(2 ** i + random.random())
    raise RuntimeError("max retries exceeded")
```

<Note>
  **Don't** retry 4xx (other than 429). Bad-request retries just waste quota.
</Note>

## Client Best Practices

- **Cap concurrency client-side** with a semaphore — don't depend on server rejection + backoff
- **Batch submission**: ≤ concurrency limit per wave, sleep 1–2 s between waves
- **Polling cadence**: 5–15 s per task; webhook is simpler

## Upstream Limits

The gateway queues and retries, but upstream may still:

- Per-account per-minute quota
- GPU shortage at peak
- Long queue for a particular prompt

Symptom: `task.status` stays `pending` for a long time. Set a `timeout` (e.g. 10 min) and **resubmit** instead of polling forever.

## Global Throttling

For very high traffic:

- Use Redis / a queue as a buffer
- Tag priority on important requests (contact sales for SLA-backed lanes)
- Persist `task_id` so you can resume polling after restart
