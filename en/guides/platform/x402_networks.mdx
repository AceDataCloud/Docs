Ace Data Cloud X402 currently settles around USDC and supports two types of chains: EVM and Solana. Different networks have different signing methods, asset addresses, gas behavior, and applicable scenarios, so you need to choose the network before integration.

## Network Identifiers Use CAIP-2

The `accepts[].network` in x402 v2 is a CAIP-2 identifier, not an abbreviation such as `base` or `solana`. Clients must compare networks by CAIP-2 string:

| Network             | CAIP-2 Identifier                         |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Support Matrix

| Network     | scheme  | Asset                  | Signing Method                                 | Applicable Scenario                     |
| ------ | ------- | ------------------- | ------------------------------------ | ------------------------ |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Recommended by default; mature wallet and liquidity support.         |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | Post-metered APIs such as chat and models.          |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Solana wallets, Agents, or on-chain application scenarios. |

`upto` is currently only provided on Base. The actual available items are subject to the `accepts` returned by the API. You can also check the Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

The response from Facilitator `/supported`:

```json
{
  "kinds": [
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "eip155:8453"
    },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": {
        "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708"
      }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": {
        "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq"
      }
    }
  ]
}
```

Result description:

- `exact` on Base and Solana is a fixed-amount payment path.
- Only Base provides the `upto` post-metering path, which depends on Permit2 approve.
- The `extra.facilitatorAddress` in the `upto` entry is the address that must be written into the witness when the client signs, and it must be consistent with the value returned by the server.

## Base

Base uses the official USDC contract:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

In the `exact` scheme, the client signs EIP-712 `TransferWithAuthorization`. The signing content includes:

- `from`: payment wallet address
- `to`: Ace Data Cloud receiving address
- `value`: payment amount for this transaction
- `validAfter` / `validBefore`: signature validity time window
- `nonce`: 32-byte random nonce

After the Facilitator verifies the signature, it calls USDC's `transferWithAuthorization` on-chain to complete the transfer.

Base is the most recommended production integration network, especially suitable for `upto` post-metering, because the Permit2, USDC, and wallet ecosystems are more mature.

Example of the Base `exact` verification result:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Result description:

- The API paid retry returns the model content `ADC_BASE_E2E_OK`.
- The on-chain transaction can be found on BaseScan, and the block number is `46726299`.
- `95215` atomic USDC corresponds to `0.095215` USDC, which is the actual settlement amount for this API call.

Program execution result for order payment using Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Result description:

- The final status of the platform order is `Finished`.
- The order `pay_id` is written with the same Base transaction hash.
- `1200000` atomic USDC corresponds to `1.2` USDC, which is the historical actual payment amount for this 10 Credits order under the old policy; new orders no longer receive an additional X402 payment method discount, and the specific signing amount is subject to the 402 response for this transaction.

## Solana

Solana uses SPL USDC `TransferChecked`. The client constructs a transfer transaction, signs and submits it, and then puts the transaction signature or serialized transaction into the `PAYMENT-SIGNATURE` envelope.

Characteristics of Solana:

- Uses Solana wallet adapter or base58 secret key;
- The asset is Solana USDC mint;
- Currently only supports `exact`;
- The Facilitator verifies the mint, destination, authority, and amount of the transfer instruction.

If wallet fee payer mode is used, the wallet directly submits the transaction, and the Facilitator is responsible for confirming the transaction and returning the settlement result.

Example of the Solana `exact` verification result:

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Result description:

- The paid retry has returned HTTP 200, and the model output is `ADC_SOLANA_E2E_OK`.
- Public RPC queries for on-chain signatures may encounter rate limits.
- Because public RPC queries may be rate-limited, the Solana explorer is not included here. When strict reconciliation is needed, please use your own Solana RPC or platform-side settlement records to confirm the transaction signature.

## How to Choose

| What You Want to Do        | Recommended Network           |
| ------------ | -------------- |
| Quickly complete the minimum flow     | Base `exact`   |
| Target ordinary Web3 users | Base           |
| Perform post-metering for chat completion and similar use cases   | Base `upto`    |
| Solana ecosystem applications  | Solana `exact` |

No matter which chain you choose, do not hardcode prices on the client. Prices are determined by the `accepts[].maxAmountRequired` returned by the server.

## Add New EVM Networks
Code support has been provided for native USDC fixed-amount payments on the following networks, and they are being enabled one by one by network.
Availability is subject to the `accepts` returned by the order or API; this does not mean that all networks have been enabled in production.

| Network      | Alias      | CAIP-2         | Native USDC                                  |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

These networks support only `exact`, with a token precision of 6. Do not use bridged USDC with the same name.
When using the official TypeScript/Python X402 Client, you can pass the alias or CAIP-2 identifier in the table.
The client constructs signatures using the target chain ID; the wallet must support the target network.

The official support table for the Phantom extension wallet lists Arbitrum and Polygon; Optimism and Avalanche
are currently not included in that table, and Rabby or MetaMask that supports the target chain can be used. EVM addresses can be the same across different chains,
but balances are independent of each other, and Solana addresses do not apply to EVM USDC.
See the [Phantom wallet support table](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### New network gradual rollout entry

New chain entries are hidden by default. When accessing the console or Studio, you can use `?features=x402-arbitrum`
to enable the corresponding chain, and separate multiple flags with commas. To disable a single chain, use `?features=-x402-arbitrum`,
and use `?features=none` to clear local overrides. Switches are stored separately for each domain.
Order quotes and payment retries use the same switch, and the server independently validates them; existing payment records can still be viewed.
Enabling only the page flag will not enable chains that have not yet been configured; the specific payable networks are still subject to real-time `accepts`.
