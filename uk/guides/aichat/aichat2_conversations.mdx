AI Chat v2 API (`/aichat2/conversations`) — це нове покоління інтерфейсу діалогів, повністю оновлена версія [AI Chat API](https://platform.acedata.cloud/documents/aichat-conversations). На основі простоти v1 та керованих багатораундових діалогів він розширено такими можливостями:

- **Мультимодальне введення користувача**: безпосереднє передавання тексту + зображень + блоків файлів через структуроване поле `message`, без необхідності спершу непрямо додавати їх через `references`.
- **Виклики інструментів в Agent-форматі**: вбудований набір інструментів для пошуку в Інтернеті, отримання вебсторінок, читання файлів тощо, а також можливість підключати авторизовані користувачем MCP-сервери (Google Drive, Notion, Slack, GitHub тощо); модель може самостійно виконувати багатораундові виклики інструментів в одному запиті для завершення складних завдань.
- **Структуровані потокові події**: через `accept: text/event-stream` або `application/x-ndjson` можна отримувати події `text_delta`, `tool_use`, `tool_result`, `thinking`, `citation`, `card`, `artifact` тощо для кожного токена, що полегшує їх окреме відображення на фронтенді за відповідними типами.
- **Можливість переривання / відновлення**: коли моделі потрібно, щоб користувач доповнив інформацію, вона надсилає подію `ask_user_question` і призупиняється; під час наступного виклику можна продовжити, передавши відповідь назад через `tool_results`.
- **Нові CRUD-дії**: через поле `action` в одному й тому самому endpoint можна виконувати `retrieve` / `retrieve_batch` / `update` / `delete`, без потреби в додатковому API для керування діалогами.
- **Список моделей, що постійно оновлюється**: за замовчуванням підключено сучасні моделі, такі як GPT-5.4, Claude Opus 4.8, Claude Sonnet 4.6, Gemini 3.1 Pro, GLM 5.1, DeepSeek V4, Kimi K3 тощо.

Водночас на рівні тіла запиту він **повністю зворотно сумісний із v1**: достатньо передати лише `model` + `question` (+ необов’язкові `stateful` / `id` / `references` / `preset`), щоб отримати JSON-відповідь `{answer, id}`, еквівалентну v1. Тому під час міграції з `/aichat/conversations` не потрібно переписувати клієнт — достатньо змінити шлях на `/aichat2/conversations`.

> Якщо ви зараз використовуєте `/aichat/conversations`, старий інтерфейс продовжить працювати, і ви можете мігрувати у власному темпі.

## Базове використання

Найпростіший спосіб використання повністю ідентичний v1: передайте `model` + `question` і отримайте `{answer, id}`.

Приклад CURL:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。"
  }'
```

Результат повернення:

```json
{
  "answer": "AceDataCloud 是一个聚合主流 AI 模型与多模态服务的统一 API 平台，开发者通过一个密钥即可调用 GPT、Claude、Gemini、Midjourney、Suno、Veo 等多家服务。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Приклад Python:

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

## Багатораундовий діалог

Як і у v1, передайте `stateful: true`, щоб увімкнути збереження діалогу; API поверне `id`; у наступних запитах достатньо передати цей `id`, щоб продовжити діалог, без необхідності самостійно підтримувати історію messages.

Перший запит:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "记住一个数字：42。"
  }'
```

Повернення:

```json
{
  "answer": "好的，我已经记住了 42。需要我用它做什么吗？",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Другий запит — передайте той самий `id`:
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "我刚才让你记住的数字是多少？"
  }'
```

```json
{
  "answer": "你让我记住的数字是 42。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` за замовчуванням має значення `true`; пропуск і явна передача `true` є еквівалентними. Якщо ви не хочете, щоб сервер зберігав цей раунд діалогу, можна явно встановити `stateful: false`。

## Потокова відповідь

v2 підтримує два формати потокової передачі, які вибираються відповідно до заголовка `accept`:

| Сценарій                    | `accept`               | Формат даних                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Web-фронтенд / EventSource  | `text/event-stream`    | `data: {json}\n\n`，останній рядок `data: [DONE]\n\n` |
| Сервер / CLI / потоковий парсинг Node | `application/x-ndjson` | Кожен рядок — один JSON-об’єкт                               |
| Потокова передача не потрібна                 | `application/json`（за замовчуванням） | Одноразово повертає `{answer, id}`                       |

### Приклад NDJSON

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "用三句话介绍杭州。",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # 与 v1 兼容：增量片段同时通过 delta_answer 字段提供
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

Кожен рядок NDJSON є структурованою подією; найпоширенішою є `text_delta`:

```json
{"type":"text_delta","content":"杭","delta_answer":"杭","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"州","delta_answer":"州","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"是","delta_answer":"是","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### Приклад SSE

Використання `EventSource` у браузері не підтримує користувацьке тіло запиту, рекомендується використовувати `fetch` + ручний парсинг шляхом розділення на фрагменти за `\n\n`:

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "用三句话介绍杭州。",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### Типи потокових подій

| `type`              | Значення                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| `text_delta`        | Інкрементальний текстовий фрагмент відповіді асистента. `content` містить новий вміст; для сумісності з v1 та сама подія також містить `delta_answer`（дорівнює `content`）і `id`。                  |
| `thinking`          | Процес міркування моделі（з’являється лише тоді, коли вибрана модель надає reasoning）。                                                                |
| `tool_use`          | Модель вирішує викликати інструмент; подія містить `tool_id`、`tool_name`、`input`。                                                  |
| `tool_result`       | Результат виконання інструмента, пов’язаний із попереднім `tool_use` через `tool_id`; `is_error` позначає, чи сталася помилка。                                       |
| `card`              | Структурована картка, створена інструментом（наприклад, зображення, попередній перегляд посилання），придатна для прямого відображення。                                                                    |
| `citation`          | URL-адреса джерела, що використовується для доповнення цитування відповідного текстового фрагмента。                                                                            |
| `ask_user_question` | Надсилається, коли моделі потрібно, щоб користувач доповнив інформацію; діалог переходить у стан `awaiting_user_input`，детальніше див. нижче [Відновлення призупиненого діалогу](#відновлення-призупиненого-діалогу)。                           |
| `artifact`          | Незалежний результат, згенерований моделлю（наприклад, блок коду, документ），який можна зберегти або завантажити。                                                                      |
| `system_message`    | Системне інформаційне повідомлення（не вміст користувача чи асистента），використовується лише для підказок UI。                                                                     |
| `compact`           | Подія, за якої внутрішній контекст було стиснуто; спеціальна обробка не потрібна。                                                                             |
| `error`             | У цьому раунді сталася помилка; `message` описує вміст помилки。                                                                        |
| `done`              | Потокова відповідь завершена; містить `usage`（включно з `prompt_tokens` / `completion_tokens` / `total_tokens`）і `terminal_reason`。 |

Для клієнтів, яких цікавить лише остаточна відповідь, об’єднання `content` усіх `text_delta` є еквівалентним `answer` у режимі `application/json`。

## Мультимодальний ввід

Якщо введення користувача містить зображення або файл, передайте `message`（масив）замість `question`。Кожен елемент масиву є блоком вмісту:

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "这张图片里有几只猫？" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

Підтримувані типи блоків:

- `text` — звичайний текст, обов’язкове поле `text`。
- `image_url` — зображення, обов’язкове поле `image_url.url`。
- `file_url` — файл（PDF、CSV、TXT тощо），обов’язкове поле `file_url.url`。

### Зв’язок із `references` v1

Для сумісності зі старими клієнтами v2 усе ще розпізнає поле `references: ["https://...", ...]`:
- Якщо суфікс URL є `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif`, автоматично перетворюється на блок `image_url`;
- Інші розширення перетворюються на блок `file_url`;
- Якщо також одночасно надано `question`, він додається на початку як блок `text`.

Тому, якщо ви хочете лише перейти з v1 і не хочете змінювати тіло запиту, достатньо змінити шлях на `/aichat2/conversations`, оригінальне використання `references` продовжить працювати як раніше.

Якщо потрібен більш точний контроль (наприклад, розміщувати кілька зображень між текстом або якщо порядок є дуже важливим), безпосередньо використовуйте масив `message`.

## Виклики інструментів і MCP

Ключове покращення v2 полягає в тому, що модель може самостійно викликати інструменти для виконання багатокрокових завдань, **це увімкнено за замовчуванням**, і клієнту не потрібно виконувати жодних додаткових налаштувань у запиті. Типові сценарії:

- Користувач запитує: «Допоможи мені пошукати, які нові виставки нещодавно є в Шанхаї» → модель викликає вбудований web search → упорядковує результати у відповідь.
- Користувач запитує: «Прочитай цей PDF і потім напиши резюме» → модель викликає file_read → пише резюме.
- Користувач уже авторизував Google Drive / GitHub / Notion тощо в [Connections](https://platform.acedata.cloud/connections) → модель може викликати відповідні інструменти MCP для читання та запису їхніх даних.

У потоці NDJSON / SSE виклики інструментів відображаються через два типи подій: `tool_use` і `tool_result`, наприклад:

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"上海 2026 春季展览"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"目前","delta_answer":"目前","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"上海","delta_answer":"上海","id":"f2f4b3e8-..."}
...
```

Якщо ви не хочете показувати у фронтенді деталі викликів інструментів, достатньо ігнорувати події типів `tool_use` / `tool_result` / `card` / `citation`; остаточний вивід моделі все одно надходить через потік `text_delta`.

`max_turns` може обмежувати максимальну кількість раундів, у яких модель може самостійно викликати інструменти в цьому запиті; діапазон — 1–500, за замовчуванням, якщо його пропущено, — 500. Якщо встановити його на мале значення (наприклад, `max_turns: 1`), можна примусово отримати одноразову відповідь без дозволу на будь-які виклики інструментів.

## Асинхронне виконання й авторизація без нагляду

Якщо ваш виклик походить із Webhook сповіщення, CI/CD, системи моніторингу або іншого фонового завдання, ви можете встановити `async: true`, щоб інтерфейс негайно повернув ID завдання, а виконання продовжилося у фоні:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Приклад відповіді:

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

Після цього ви можете використати `action: retrieve` + `id` для запиту результату розмови; також можна надати `callback_url`, і після завершення завдання платформа надішле `{ status, answer, usage, error }` методом POST на вашу адресу зворотного виклику. `callback_url` повинен використовувати `http` / `https`, і в ньому не можна безпосередньо вказувати `localhost` або літеральну адресу приватної IP-адреси.

У фонових завданнях зазвичай немає кому натиснути підтвердження. Якщо ви хочете, щоб певні Skill або MCP Server виконували дії надсилання, публікації, запису тощо в режимі без нагляду, явно передайте список попередньої авторизації в тілі запиту:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Значення в `allowed_skills` — це slug підключених Skill; значення в `allowed_mcp_servers` — це slug підключених MCP Server. Skill / MCP Server, не включені до попередньої авторизації, у режимі без нагляду все одно можуть лише переглядати, виконувати dry-run або відмовлятися від виконання операцій запису.

Якщо потрібен детальніший контроль, також можна використати еквівалентний об’єкт `unattended_policy`:

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

Попередня авторизація — це самі ці два списки: порожній список означає, що жодні можливості не авторизовано, додаткове поле-перемикач не потрібне.

Зверніть увагу: попередня авторизація означає лише «цей запит дозволяє цим можливостям пропускати ручне підтвердження в режимі без нагляду». Конкретний Skill усе одно повинен підтримувати `--unattended-confirm` або відповідний механізм безпеки; інакше він продовжить виконувати dry-run і не виконуватиме операції запису безпосередньо.

## Відновлення призупинених розмов

Деякі інструменти змушують модель «перепитати користувача»; у цей момент модель надсилає подію `ask_user_question`, а розмова заморожується у стані `awaiting_user_input`:

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "你希望生成的报告是中文还是英文？",
  "options": ["中文", "英文"],
  "id": "f2f4b3e8-..."
}
```

На фронтенді відрендеріть цю подію як картку, щоб користувач міг вибрати відповідь, а потім ініціюйте наступний запит із тим самим `id`, повернувши відповідь через `tool_results`:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

`tool_use_id` у тілі запиту **має** повністю збігатися з `tool_id` у момент призупинення; у разі невідповідності буде повернуто 400. Якщо у запиті одночасно присутній `tool_results`, `question` / `message` / `references` будуть проігноровані.

Якщо користувач вирішить відмовитися від цього питання, достатньо безпосередньо передати новий `question` / `message`, і платформа автоматично позначить призупинений виклик інструмента як «пропущений користувачем».

## Керування розмовами (CRUD)

v2 надає полегшене керування розмовами через поле `action` у тому самому endpoint, без необхідності відкривати окремий API.
### `action: retrieve` —— отримати сеанс

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

Повертає повний документ сеансу (включно з історією `messages`, `model`, `title`, `tools_used` тощо).

### `action: retrieve_batch` —— перелічити зведення сеансів

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

Повертає `{ items: [...], total }`. **Зведення не містить `messages`**, підходить для списку на бічній панелі; якщо користувач відкриває певний сеанс, потім використовуйте `action: retrieve`, щоб окремо отримати його повні повідомлення.

Необов’язкові параметри фільтрації: `user_id`, `application_id`, `model_group`, `model`.

### `action: update` —— змінити заголовок або переписати історію

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "План подорожі до Ханчжоу"
}
```

`messages` також можна передати, але сервер виконує сувору перевірку schema (має бути у згорнутій формі `ToolUseContent`), інакше буде повернено 400. Зазвичай рекомендується використовувати це лише для зміни `title`.

### `action: delete` —— видалити один сеанс

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Повертає `{ id, success: true }`. Після видалення відновлення неможливе, будь ласка, підтвердьте перед викликом.

## Плавна міграція з v1

Якщо ви вже використовуєте [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations), міграція на v2 майже не потребує змін коду:

1. Змініть URL з `https://api.acedata.cloud/aichat/conversations` на `https://api.acedata.cloud/aichat2/conversations`.
2. Якщо раніше ви передавали назви моделей v1 (наприклад, `gpt-3.5`, `gpt-4-browsing` тощо), під час переходу на v2 рекомендується оновитися до сучасних моделей (наприклад, `gpt-5.4`, `claude-opus-4-8`, `gemini-3.1-pro-preview` тощо).
3. Поля потоку NDJSON залишаються зворотно сумісними: кожна подія `text_delta` як і раніше містить `delta_answer` та `id`, тому клієнтам, які раніше розбирали `delta_answer` рядок за рядком, не потрібно вносити зміни.

Після міграції ви можете за потреби увімкнути нові можливості v2 (мультимодальне `message`, SSE, виклики інструментів, CRUD через `action`) і поступово впроваджувати їх у зручному темпі.

## Обробка помилок

Відповідь із помилкою має уніфікований формат:

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

Поширені помилки:

- `400 bad_request`: відсутні обов’язкові поля, `tool_use_id` не збігається, schema `messages` є недійсною тощо.
- `401 invalid_token`: заголовок `authorization` неправильний.
- `404 not_found`: сеанс, якому відповідає `id`, не існує під час `action: retrieve / update / delete`.
- `429 too_many_requests`: спрацювало обмеження швидкості.
- `500 chat_error`: помилка у висхідній LLM або в цьому раунді `completion_tokens=0` (розглядається як невикористане, плата не стягується).

У потоковій відповіді помилки надсилаються як подія `{"type":"error","message":"..."}`, після чого потік одразу завершується.

## Висновок

AI Chat v2 API, зберігаючи зворотну сумісність із v1, оновлює діалог із «одиночних / багатораундових запитань і відповідей» до «спостережуваного діалогу з Agent»: мультимодальне введення, виклики інструментів, можливість призупинення / відновлення, потокові структуровані події, вбудований CRUD. Для нових інтеграцій рекомендується одразу використовувати v2; наявні інтеграції v1 можуть плавно мігрувати поетапно. Якщо у вас виникнуть будь-які запитання, будь ласка, звертайтеся до нашої команди технічної підтримки в будь-який час.
