AI Chat v2 API (`/aichat2/conversations`) — це діалоговий інтерфейс нового покоління, що є повністю оновленою версією [AI Chat API](https://platform.acedata.cloud/documents/aichat-conversations). На основі стислості v1 та керованих багатораундових діалогів він розширює:

- **Мультимодальне введення користувача**: безпосередньо передавайте текст + зображення + блоки файлів через структуроване поле `message`, без необхідності спочатку непрямо прикріплювати їх за допомогою `references`.
- **Виклики інструментів у стилі Agent**: вбудований набір інструментів для веб-пошуку, захоплення вебсторінок, читання файлів тощо, а також можливість підключати авторизовані користувачем MCP-сервери (Google Drive, Notion, Slack, GitHub тощо), завдяки чому модель може самостійно багаторазово викликати інструменти в межах одного запиту для виконання складних завдань.
- **Структуровані потокові події**: через `accept: text/event-stream` або `application/x-ndjson` можна отримувати події `text_delta`, `tool_use`, `tool_result`, `thinking`, `citation`, `card`, `artifact` тощо для кожного токена, що зручно для окремого рендерингу на фронтенді за відповідними типами.
- **Можливість переривання / відновлення**: коли моделі потрібно, щоб користувач доповнив інформацію, вона надсилає подію `ask_user_question` і призупиняється; під час наступного виклику можна продовжити, заповнивши відповідь через `tool_results`.
- **Нові CRUD-дії**: на тому самому endpoint через поле `action` виконуйте `retrieve` / `retrieve_batch` / `update` / `delete`, без потреби в додатковому API керування діалогами.
- **Список моделей, що постійно оновлюється**: за замовчуванням підключено сучасні моделі, зокрема GPT-5.4, Claude Opus 4.8, Claude Sonnet 4.6, Gemini 3.1 Pro, GLM 5.1, DeepSeek V4, Kimi K3 тощо.

Водночас на рівні тіла запиту він **повністю зворотно сумісний із v1**: достатньо передати лише `model` + `question` (+ необов’язкові `stateful` / `id` / `references` / `preset`), щоб отримати JSON-відповідь `{answer, id}`, еквівалентну v1, тож для міграції з `/aichat/conversations` не потрібно переписувати клієнт — достатньо змінити шлях на `/aichat2/conversations`.

> Якщо ви зараз використовуєте `/aichat/conversations`, старий інтерфейс і надалі буде доступний, тож ви можете мігрувати у власному темпі.

## Базове використання

Найпростіший спосіб використання повністю такий самий, як у v1: передайте `model` + `question` і отримайте `{answer, id}`.

Приклад CURL:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。"
  }'
```

Результат відповіді:

```json
{
  "answer": "AceDataCloud 是一个聚合主流 AI 模型与多模态服务的统一 API 平台，开发者通过一个密钥即可调用 GPT、Claude、Gemini、Midjourney、Suno、Veo 等多家服务。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Приклад Python:

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

## Багатораундовий діалог

Як і у v1, передайте `stateful: true`, щоб увімкнути збереження діалогу; API поверне `id`; у наступних запитах достатньо передати назад `id`, щоб продовжити діалог, без необхідності самостійно підтримувати історію messages.

Перший запит:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "记住一个数字：42。"
  }'
```

Відповідь:

```json
{
  "answer": "好的，我已经记住了 42。需要我用它做什么吗？",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Другий запит із тим самим `id`:
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "我刚才让你记住的数字是多少？"
  }'
```

```json
{
  "answer": "你让我记住的数字是 42。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> Типове значення `stateful` — `true`; пропускання та явна передача `true` є еквівалентними. Налаштування `stateful: false` пропустить завантаження попередньої історії розмови; це не означає, що результат поточного раунду не буде збережено, і це також не застосовується до інструментальних процесів, які потребують продовження після призупинення.

### Довгі розмови та збереження оригінального тексту

Стиснення контексту лише впорядковує вміст, надісланий моделі в поточному раунді, і не замінює вже збережені записи чату. Через `action: retrieve` усе ще можна прочитати повні збережені повідомлення; явне редагування або видалення розмови все одно набуває чинності відповідно до запиту.

Модель може шукати та посторінково читати історичний оригінальний текст у межах поточної розмови. Якщо потрібно продовжити редагування статті, цитувати числа або готувати публікацію, слід прочитати відповідний оригінальний текст, а не замінювати основний текст резюме. Ця можливість не відновлює автоматично повідомлення, які вже були втрачені в старих версіях.

Якщо впорядкування контексту не вдалося, збережіть ID розмови та перевірте подію `error`; служба не перезапише оригінальний текст порожнім резюме. Операції з інструментами, завершені до збою, можуть усе ще бути дійсними, тому спершу перевірте їхні результати, щоб уникнути повторного генерування або повторної публікації. Якщо окрема розмова досягає ліміту сховища, буде явно повідомлено про помилку; наявні збережені записи не звільнятимуть місце шляхом обрізання; після експорту потрібного вмісту можна розпочати нову розмову.

## Потокові відповіді

v2 підтримує два потокові формати, що вибираються за заголовком `accept`:

| Сценарій                    | `accept`               | Форма даних                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Вебфронтенд / EventSource  | `text/event-stream`    | `data: {json}\n\n`, останній рядок `data: [DONE]\n\n` |
| Сервер / CLI / потоковий парсинг Node | `application/x-ndjson` | Один JSON-об’єкт у кожному рядку                               |
| Потоковість не потрібна                 | `application/json`（типово） | Одноразово повертає `{answer, id}`                       |

### Приклад NDJSON

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "用三句话介绍杭州。",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # 与 v1 兼容：增量片段同时通过 delta_answer 字段提供
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

Кожен рядок NDJSON є структурованою подією; найпоширенішою є `text_delta`:

```json
{"type":"text_delta","content":"杭","delta_answer":"杭","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"州","delta_answer":"州","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"是","delta_answer":"是","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### Приклад SSE

Використання `EventSource` у браузері не підтримує власне тіло запиту, тому рекомендується використовувати `fetch` + ручний парсинг шляхом розділення за `\n\n`:

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "用三句话介绍杭州。",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### Типи потокових подій

| `type`              | Значення                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `text_delta`        | Інкрементний текстовий фрагмент відповіді асистента. `content` містить новий вміст; для сумісності з v1 та сама подія також містить `delta_answer` (дорівнює `content`) та `id`.                                        |
| `thinking`          | Процес міркування моделі (з’являється лише тоді, коли обрана модель розкриває reasoning).                                                                                      |
| `tool_use`          | Модель вирішує викликати інструмент; подія містить `tool_id`, `tool_name`, `input`.                                                                        |
| `tool_result`       | Результат виконання інструмента; поєднується з попереднім `tool_use` через `tool_id`, а `is_error` позначає, чи сталася помилка.                                                             |
| `card`              | Структурована картка, створена інструментом (наприклад, зображення, попередній перегляд посилання), придатна для безпосереднього рендерингу.                                                                                          |
| `citation`          | URL-адреса джерела, що використовується для доповнення цитати відповідного текстового фрагмента.                                                                                                  |
| `ask_user_question` | Надсилається, коли моделі потрібна додаткова інформація від користувача; діалог переходить у стан `awaiting_user_input`, докладніше див. нижче в [Відновлення призупиненого діалогу](#відновлення-призупиненого-діалогу).                                                 |
| `artifact`          | Незалежний артефакт, згенерований моделлю (наприклад, блок коду, документ), який можна зберегти або завантажити.                                                                                            |
| `system_message`    | Системне інформаційне повідомлення (не вміст користувача чи асистента), призначене лише для підказок UI.                                                                                           |
| `compact`           | Контекст моделі вже впорядковано; збережені оригінальні повідомлення залишаються незмінними, клієнту не потрібно видаляти записи чату.                                                                                    |
| `error`             | У поточному раунді сталася помилка, `message` описує її вміст.                                                                                              |
| `done`              | Остаточний запис розмови поточного раунду успішно збережено; містить `usage` (включно з `prompt_tokens` / `completion_tokens` / `total_tokens`) і `terminal_reason`; усе ще потрібно визначати, чи завершено завдання, за причиною завершення. |
Для клієнтів, яких цікавить лише остаточна відповідь, об’єднання всіх `content` із `text_delta` є еквівалентом `answer` у режимі `application/json`.

## Мультимодальний ввід

Якщо ввід користувача містить зображення або файли, передавайте `message` (масив) замість `question`. Кожен елемент масиву є блоком вмісту:

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "这张图片里有几只猫？" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

Підтримувані типи блоків:

- `text` — звичайний текст, поле `text` є обов’язковим.
- `image_url` — зображення, `image_url.url` є обов’язковим.
- `file_url` — файл (PDF, CSV, TXT тощо), `file_url.url` є обов’язковим.

### Зв’язок із v1 `references`

Для сумісності зі старими клієнтами v2 також розпізнає поле `references: ["https://...", ...]`:

- Якщо суфікс URL — `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif`, він автоматично перетворюється на блок `image_url`;
- Інші розширення перетворюються на блоки `file_url`;
- Якщо водночас також надано `question`, він додається на початку як блок `text`.

Тому, якщо ви лише хочете перейти з v1 і не хочете змінювати тіло запиту, достатньо змінити шлях на `/aichat2/conversations`, а початкове використання `references` продовжить працювати як раніше.

Якщо потрібен точніший контроль (наприклад, щоб розмістити кілька зображень між текстом або якщо порядок є важливим), безпосередньо використовуйте масив `message`.

## Виклики інструментів і MCP

Ключове вдосконалення v2 полягає в тому, що модель може самостійно викликати інструменти для виконання багатокрокових завдань, **це увімкнено за замовчуванням**, і клієнту не потрібно виконувати жодних додаткових налаштувань у запиті. Типові сценарії:

- Користувач запитує «Допоможи мені знайти, які нові виставки нещодавно з’явилися в Шанхаї» → модель викликає вбудований web search → упорядковує результати у відповідь.
- Користувач запитує «Прочитай цей PDF, а потім напиши короткий виклад» → модель викликає file_read → пише короткий виклад.
- Користувач уже авторизував Google Drive / GitHub / Notion тощо в [Connections](https://platform.acedata.cloud/connections) → модель може викликати відповідні інструменти MCP для читання та запису його даних.

У потоках NDJSON / SSE виклики інструментів представлені двома типами подій: `tool_use` і `tool_result`, наприклад:

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"上海 2026 春季展览"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"目前","delta_answer":"目前","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"上海","delta_answer":"上海","id":"f2f4b3e8-..."}
...
```

Якщо ви не хочете відображати деталі викликів інструментів у фронтенді, достатньо ігнорувати події типів `tool_use` / `tool_result` / `card` / `citation`; остаточний вивід моделі все одно надходитиме через потік `text_delta`.

`max_turns` може обмежувати максимальну кількість раундів самостійних викликів інструментів моделлю в цьому запиті; діапазон становить 1–500, а за замовчуванням, якщо параметр пропущено, — 500. Встановлення малого значення (наприклад, `max_turns: 1`) може примусово обмежити відповідь одним разом і не дозволяти жодних викликів інструментів.

## Асинхронне виконання та авторизація без нагляду

Якщо ваш виклик надходить із Webhook сповіщення, CI/CD, системи моніторингу або інших фонових завдань, ви можете встановити `async: true`, щоб інтерфейс негайно повернув ID завдання, а виконання продовжувалося у фоновому режимі:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Приклад відповіді:

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

Після цього можна використовувати `action: retrieve` + `id`, щоб отримати результат розмови; також можна вказати `callback_url`, і після завершення завдання платформа надішле `{ status, answer, usage, error }` методом POST на вашу адресу зворотного виклику. `callback_url` має використовувати `http` / `https`, і не можна безпосередньо вказувати `localhost` або літеральну адресу приватної IP-адреси.

У фонових завданнях зазвичай немає людини, яка могла б натиснути підтвердження. Якщо ви хочете, щоб певні Skill або MCP Server виконували дії надсилання, публікації, запису тощо в режимі без нагляду, явно передайте список попередньої авторизації в тілі запиту:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Значення в `allowed_skills` — це slug підключених Skill; значення в `allowed_mcp_servers` — це slug підключених MCP Server. Skill / MCP Server, не включені до попередньої авторизації, у режимі без нагляду все одно можуть лише переглядати, виконувати dry-run або відмовлятися від виконання операцій запису.

Якщо потрібен детальніший контроль, також можна використовувати еквівалентний об’єкт `unattended_policy`:

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

Попередня авторизація — це самі ці два списки: порожній список означає, що жодні можливості не авторизовані, без потреби в додаткових полях-перемикачах.

Зверніть увагу: попередня авторизація лише означає, що «в цьому запиті цим можливостям дозволено пропустити ручне підтвердження в режимі без нагляду». Конкретний Skill усе одно має підтримувати `--unattended-confirm` або відповідний механізм безпеки; інакше він продовжить виконувати dry-run і не виконуватиме операції запису безпосередньо.

## Відновлення призупинених розмов

Деякі інструменти можуть змусити модель «поставити користувачу зустрічне запитання», і тоді модель надсилає подію `ask_user_question`, а розмова заморожується у стані `awaiting_user_input`:

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "你希望生成的报告是中文还是英文？",
  "options": ["中文", "英文"],
  "id": "f2f4b3e8-..."
}
```

На фронтенді відрендерте цю подію як картку, щоб користувач міг вибрати відповідь, а потім надішліть наступний запит із тим самим `id`, передавши відповідь назад через `tool_results`:
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

`tool_use_id` у тілі запиту **має** повністю збігатися з `tool_id` під час призупинення; у разі невідповідності буде повернено 400. Коли в запиті одночасно присутній `tool_results`, `question` / `message` / `references` усі будуть проігноровані.

Якщо користувач вирішить відмовитися від цього питання, достатньо напряму передати новий `question` / `message`, і платформа автоматично позначить призупинений виклик інструменту як «пропущений користувачем».

## Керування сесіями (CRUD)

v2 надає легковагове керування сесіями через поле `action` на тому самому endpoint, без потреби відкривати окремий API.

### `action: retrieve` —— отримати одну сесію

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

Повертає повний документ сесії (включно з історією `messages`, `model`, `title`, `tools_used` тощо).

### `action: retrieve_batch` —— перелічити зведення сесій

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

Повертає `{ items: [...], total }`. **Зведення не містять `messages`**, що підходить для списку на бічній панелі; якщо користувач відкриє певну сесію, потім окремо отримайте її повні повідомлення через `action: retrieve`.

Необов’язкові параметри фільтрації: `user_id`, `application_id`, `model_group`, `model`.

### `action: update` —— змінити заголовок або переписати історію

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "杭州旅行计划"
}
```

Також можна передати `messages`, але сервер виконає сувору schema-перевірку (має бути згорнута форма `ToolUseContent`); у разі невідповідності буде повернено 400. Зазвичай рекомендується використовувати це лише для зміни `title`.

### `action: delete` —— видалити одну сесію

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Повертає `{ id, success: true }`. Після видалення відновлення неможливе, будь ласка, підтвердьте перед викликом.

## Плавна міграція з v1

Якщо ви вже використовуєте [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations), міграція на v2 майже не потребує змін у коді:

1. Змініть URL з `https://api.acedata.cloud/aichat/conversations` на `https://api.acedata.cloud/aichat2/conversations`.
2. Якщо ви раніше передавали назви моделей v1 (наприклад, `gpt-3.5`, `gpt-4-browsing` тощо), під час переходу на v2 рекомендується оновитися до сучасних моделей (наприклад, `gpt-5.4`, `claude-opus-4-8`, `gemini-3.1-pro-preview` тощо).
3. Поля NDJSON-потоку залишаються зворотно сумісними: кожна подія `text_delta` як і раніше містить `delta_answer` та `id`, тому клієнти, які раніше построково аналізували `delta_answer`, не потребують змін.

Після міграції за потреби можна ввімкнути нові можливості v2 (мультимодальний `message`, SSE, виклики інструментів, `action` CRUD) і впроваджувати їх у зручному темпі.

## Обробка помилок

Відповіді з помилками уніфіковані як:

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

Поширені помилки:

- `400 bad_request`: відсутні обов’язкові поля, `tool_use_id` не збігається, schema `messages` є недійсною тощо.
- `401 invalid_token`: заголовок `authorization` неправильний.
- `404 not_found`: сесія, що відповідає `id`, не існує під час `action: retrieve / update / delete`.
- `413 conversation_storage_limit`: сесія перевищила ліміт зберігання, наявні збережені записи не було перезаписано.
- `429 too_many_requests`: спрацювало обмеження швидкості.
- `503 context_compaction_failed`: впорядкування контексту не вдалося, наявні записи збережено.
- `500 conversation_persist_failed`: остаточне збереження цього раунду не вдалося; уже отриманий текст не означає, що остаточний запис успішно збережено, будь ласка, виконайте запит за ID сесії.
- `500 chat_error`: сервіс тимчасово недоступний або в цьому раунді не було згенеровано вмісту (плата не стягуватиметься).

У потоковій відповіді помилки надсилаються як подія `{"type":"error","message":"..."}`, після чого потік завершиться. `[DONE]` означає лише завершення передавання; за наявності `error` це не можна вважати успіхом, і успішна подія `done` також не надсилатиметься.

## Висновок

API AI Chat v2, зберігаючи зворотну сумісність із v1, оновлює діалог із «одиночних / багатораундових запитань і відповідей» до «спостережуваного Agent-діалогу»: мультимодальний ввід, виклики інструментів, можливість призупинення / відновлення, потокові структуровані події, вбудований CRUD. Для нових інтеграцій рекомендується одразу використовувати v2; наявні інтеграції v1 можна плавно мігрувати поетапно. Якщо у вас є будь-які запитання, будь ласка, звертайтеся до нашої команди технічної підтримки у будь-який час.
