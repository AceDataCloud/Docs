AI Chat v2 API (`/aichat2/conversations`) — це інтерфейс діалогів нового покоління, що є повністю оновленою версією [AI Chat API](https://platform.acedata.cloud/documents/aichat-conversations). На основі лаконічності v1 та керованих багатораундових діалогів він розширює:

- **Мультимодальні введення користувача**: надсилайте текст + зображення + блоки файлів безпосередньо через структуроване поле `message`, без потреби спочатку непрямо додавати їх через `references`.
- **Виклики інструментів у стилі Agent**: вбудований набір інструментів для пошуку в інтернеті, отримання вебсторінок, читання файлів тощо, а також можливість підключення авторизованих користувачем MCP-серверів (Google Drive, Notion, Slack, GitHub тощо); модель може автономно багаторазово викликати інструменти в межах одного запиту для виконання складних завдань.
- **Структуровані потокові події**: через `accept: text/event-stream` або `application/x-ndjson` можна отримувати події `text_delta`, `tool_use`, `tool_result`, `thinking`, `citation`, `card`, `artifact` та інші для кожного токена, що спрощує окреме рендерингування відповідних типів на фронтенді.
- **Можливість переривання / відновлення**: коли моделі потрібно, щоб користувач доповнив інформацію, вона надсилає подію `ask_user_question` і призупиняється; під час наступного виклику можна продовжити, передавши відповідь через `tool_results`.
- **Нові CRUD-дії**: на тому самому endpoint через поле `action` виконуйте `retrieve` / `retrieve_batch` / `update` / `delete`, без потреби в додатковому API для керування діалогами.
- **Список моделей, що постійно оновлюється**: за замовчуванням підключено сучасні моделі, зокрема GPT-5.4, Claude Opus 4.8, Claude Sonnet 4.6, Gemini 3.1 Pro, GLM 5.1, DeepSeek V4, Kimi K3 тощо.

Водночас на рівні тіла запиту він **повністю зворотно сумісний із v1**: достатньо передати `model` + `question` (+ необов’язкові `stateful` / `id` / `references` / `preset`), щоб отримати JSON-відповідь `{answer, id}`, еквівалентну v1. Тому для міграції з `/aichat/conversations` не потрібно переписувати клієнт — достатньо змінити шлях на `/aichat2/conversations`.

> Якщо ви зараз використовуєте `/aichat/conversations`, старий інтерфейс і надалі буде доступний, і ви можете мігрувати у зручному для себе темпі.

## Базове використання

Найпростіший спосіб використання повністю ідентичний v1: передайте `model` + `question` і отримайте `{answer, id}`.

Приклад CURL:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。"
  }'
```

Результат повернення:

```json
{
  "answer": "AceDataCloud 是一个聚合主流 AI 模型与多模态服务的统一 API 平台，开发者通过一个密钥即可调用 GPT、Claude、Gemini、Midjourney、Suno、Veo 等多家服务。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Приклад Python:

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

## Багатораундовий діалог

Як і у v1, передайте `stateful: true`, щоб увімкнути збереження діалогу; API поверне `id`; у наступних запитах достатньо передавати цей `id`, щоб продовжити діалог, без потреби самостійно підтримувати історію messages.

Перший запит:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "记住一个数字：42。"
  }'
```

Повернення:

```json
{
  "answer": "好的，我已经记住了 42。需要我用它做什么吗？",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Другий запит із тим самим `id`:
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "我刚才让你记住的数字是多少？"
  }'
```

```json
{
  "answer": "你让我记住的数字是 42。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` за замовчуванням має значення `true`, пропускання та явна передача `true` є еквівалентними. Якщо ви не хочете, щоб сервер зберігав цей раунд діалогу, можна явно встановити `stateful: false`。

## Потокова відповідь

v2 підтримує два потокові формати, які вибираються відповідно до заголовка `accept`：

| Сценарій                    | `accept`               | Формат даних                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Веб-фронтенд / EventSource  | `text/event-stream`    | `data: {json}\n\n`，останній рядок `data: [DONE]\n\n` |
| Сервер / CLI / потоковий аналіз Node | `application/x-ndjson` | По одному JSON-об’єкту в рядку                               |
| Потоковий режим не потрібен                 | `application/json`（за замовчуванням） | Одноразово повертає `{answer, id}`                       |

### Приклад NDJSON

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "用三句话介绍杭州。",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # 与 v1 兼容：增量片段同时通过 delta_answer 字段提供
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

Кожен рядок NDJSON є структурованою подією, найпоширеніша з яких — `text_delta`：

```json
{"type":"text_delta","content":"杭","delta_answer":"杭","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"州","delta_answer":"州","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"是","delta_answer":"是","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### Приклад SSE

Використання `EventSource` у браузері не підтримує власне тіло запиту, рекомендується використовувати `fetch` + ручний аналіз за фрагментами `\n\n`：

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "用三句话介绍杭州。",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### Типи потокових подій

| `type`              | Значення                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| `text_delta`        | Інкрементний текстовий фрагмент відповіді асистента. `content` містить новий вміст; для сумісності з v1 та сама подія також містить `delta_answer`（дорівнює `content`）і `id`。                  |
| `thinking`          | Процес міркування моделі（з’являється лише тоді, коли вибрана модель розкриває reasoning）。                                                                |
| `tool_use`          | Модель вирішує викликати інструмент, подія містить `tool_id`、`tool_name`、`input`。                                                  |
| `tool_result`       | Результат виконання інструмента, пов’язаний із попереднім `tool_use` через `tool_id`, `is_error` позначає, чи сталася помилка。                                       |
| `card`              | Структурована картка, створена інструментом（наприклад, зображення, попередній перегляд посилання），придатна для безпосереднього рендерингу。                                                                    |
| `citation`          | URL джерела, що використовується для доповнення посилань на відповідний текстовий фрагмент。                                                                            |
| `ask_user_question` | Надсилається, коли моделі потрібна додаткова інформація від користувача; діалог переходить у стан `awaiting_user_input`, див. нижче [відновлення призупиненого діалогу](#відновлення-призупиненого-діалогу)。                           |
| `artifact`          | Незалежний артефакт, створений моделлю（наприклад, блок коду, документ），який можна зберегти або завантажити。                                                                      |
| `system_message`    | Системне інформаційне повідомлення（не є вмістом користувача чи асистента），лише для підказок в UI。                                                                     |
| `compact`           | Подія, коли внутрішній контекст було стиснуто; спеціальна обробка не потрібна。                                                                             |
| `error`             | У цьому раунді сталася помилка, `message` описує її вміст。                                                                        |
| `done`              | Потокова відповідь завершена, містить `usage`（зокрема `prompt_tokens` / `completion_tokens` / `total_tokens`）і `terminal_reason`。 |

Для клієнтів, яких цікавить лише остаточна відповідь, об’єднання `content` усіх `text_delta` еквівалентне `answer` у режимі `application/json`。

## Мультимодальне введення

Якщо введення користувача містить зображення або файли, передавайте `message`（масив）замість `question`。Кожен елемент масиву є блоком вмісту：

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "这张图片里有几只猫？" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

Підтримувані типи блоків：

- `text` — звичайний текст, поле `text` є обов’язковим。
- `image_url` — зображення, `image_url.url` є обов’язковим。
- `file_url` — файл（PDF、CSV、TXT тощо），`file_url.url` є обов’язковим。

### Зв’язок із `references` v1

Для сумісності зі старими клієнтами v2 досі розпізнає поле `references: ["https://...", ...]`：
- Суфікси URL `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif` автоматично перетворюються на блоки `image_url`;
- Інші розширення перетворюються на блоки `file_url`;
- Якщо одночасно також надано `question`, його буде розміщено на початку як блок `text`.

Тому, якщо ви лише хочете перейти з v1 і не хочете змінювати тіло запиту, достатньо змінити шлях на `/aichat2/conversations`, а попередній спосіб використання `references` продовжить працювати як звичайно.

Якщо потрібен точніший контроль (наприклад, розмістити кілька зображень між текстом або якщо порядок дуже важливий), безпосередньо використовуйте масив `message`.

## Виклики інструментів і MCP

Ключове покращення v2 полягає в тому, що модель може самостійно викликати інструменти для виконання багатокрокових завдань, **це ввімкнено за замовчуванням**, і клієнту не потрібно робити жодних додаткових налаштувань у запиті. Типові сценарії:

- Користувач запитує «Допоможи мені знайти, які нові виставки нещодавно проходять у Шанхаї» → модель викликає вбудований web search → упорядковує результати у відповідь.
- Користувач запитує «Прочитай цей PDF, а потім напиши резюме» → модель викликає file_read → пише резюме.
- Користувач уже авторизував Google Drive / GitHub / Notion тощо у [Connections](https://platform.acedata.cloud/connections) → модель може викликати відповідні інструменти MCP для читання та запису його даних.

У потоках NDJSON / SSE виклики інструментів представлені двома типами подій: `tool_use` і `tool_result`, наприклад:

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"上海 2026 春季展览"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"目前","delta_answer":"目前","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"上海","delta_answer":"上海","id":"f2f4b3e8-..."}
...
```

Якщо ви не хочете відображати у фронтенді деталі викликів інструментів, просто ігноруйте події типів `tool_use` / `tool_result` / `card` / `citation`; остаточний вивід моделі все одно передається через потік `text_delta`.

`max_turns` може обмежити максимальну кількість раундів самостійних викликів інструментів моделлю в цьому запиті, діапазон становить 1–500, а за замовчуванням, якщо не вказано, — 500. Якщо встановити мале значення (наприклад, `max_turns: 1`), можна примусово отримати одноразову відповідь і не дозволити жодних викликів інструментів.

## Асинхронне виконання та авторизація без нагляду

Якщо ваш виклик походить із webhook сповіщень, CI/CD, системи моніторингу або інших фонових завдань, ви можете встановити `async: true`, щоб інтерфейс негайно повернув ID завдання, а виконання продовжилося у фоні:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Приклад відповіді:

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

Після цього можна використати `action: retrieve` + `id` для запиту результату розмови; також можна надати `callback_url`, і після завершення завдання платформа надішле `{ status, answer, usage, error }` методом POST на вашу адресу зворотного виклику. `callback_url` має використовувати `http` / `https`, і не може безпосередньо містити `localhost` або літеральну адресу приватної IP-мережі.

Для фонових завдань зазвичай немає людини, яка може натиснути підтвердження. Якщо ви хочете, щоб певні Skill або MCP Server виконували дії надсилання, публікації, запису тощо в режимі без нагляду, явно передайте в тілі запиту список попередньої авторизації:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "我的服务报警了，用个人微信通知微信群「AceDataCloud团队」……"
}
```

Значення в `allowed_skills` — це slug підключених Skill; значення в `allowed_mcp_servers` — це slug підключених MCP Server. Skill / MCP Server, не включені до попередньої авторизації, у режимі без нагляду все ще можуть лише переглядати, виконувати dry-run або відмовлятися від виконання операцій запису.

Якщо потрібен детальніший контроль, також можна використати еквівалентний об’єкт `unattended_policy`:

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

Попередня авторизація — це саме ці два списки: порожні списки означають, що жодні можливості не авторизовані, без потреби в додатковому полі-перемикачі.

Зверніть увагу: попередня авторизація означає лише «цьому запиту дозволено пропускати ручне підтвердження для цих можливостей у режимі без нагляду». Конкретний Skill усе одно має підтримувати `--unattended-confirm` або відповідний механізм безпеки; інакше він продовжить виконувати dry-run і не виконуватиме операції запису безпосередньо.

## Відновлення призупинених розмов

Деякі інструменти можуть змусити модель «поставити користувачу зустрічне запитання»; у цей момент модель надсилає подію `ask_user_question`, а розмова заморожується у стані `awaiting_user_input`:

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "你希望生成的报告是中文还是英文？",
  "options": ["中文", "英文"],
  "id": "f2f4b3e8-..."
}
```

У фронтенді відрендерте цю подію як картку, щоб користувач вибрав відповідь, а потім надішліть наступний запит із тим самим `id`, передавши відповідь назад через `tool_results`:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

`tool_use_id` у тілі запиту **обов’язково** має повністю збігатися з `tool_id` на момент призупинення; у разі невідповідності буде повернуто 400. Коли у запиті одночасно присутній `tool_results`, `question` / `message` / `references` буде проігноровано.

Якщо користувач вирішить відмовитися від цього запитання, просто передайте новий `question` / `message`; платформа автоматично позначить призупинений виклик інструменту як «пропущено користувачем».

## Керування розмовами (CRUD)

v2 надає легковагове керування розмовами через поле `action` у тому самому endpoint, без потреби відкривати окремий API.
### `action: retrieve` —— отримати розмову

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

Повертає повний документ розмови (включно з історією `messages`, `model`, `title`, `tools_used` тощо).

### `action: retrieve_batch` —— перелічити зведення розмов

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

Повертає `{ items: [...], total }`. **Зведення не містить `messages`**, підходить для списку на бічній панелі; якщо користувач відкриває певну розмову, потім використовуйте `action: retrieve`, щоб окремо отримати її повні повідомлення.

Необов’язкові параметри фільтрації: `user_id`, `application_id`, `model_group`, `model`.

### `action: update` —— змінити заголовок або переписати історію

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "План подорожі до Ханчжоу"
}
```

Також можна передати `messages`, але сервер виконає сувору перевірку schema (має бути форма згорнутого `ToolUseContent`), у разі невідповідності буде повернено 400. Зазвичай рекомендується використовувати це лише для зміни `title`.

### `action: delete` —— видалити розмову

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Повертає `{ id, success: true }`. Після видалення відновлення неможливе, будь ласка, підтвердьте перед викликом.

## Плавна міграція з v1

Якщо ви вже використовуєте [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations), міграція на v2 майже не потребує змін у коді:

1. Змініть URL з `https://api.acedata.cloud/aichat/conversations` на `https://api.acedata.cloud/aichat2/conversations`.
2. Якщо раніше ви передавали назви моделей v1 (як-от `gpt-3.5`, `gpt-4-browsing` тощо), під час переходу на v2 рекомендується оновитися до сучасних моделей (як-от `gpt-5.4`, `claude-opus-4-8`, `gemini-3.1-pro-preview` тощо).
3. Поля потоку NDJSON залишаються зворотно сумісними: кожна подія `text_delta` як і раніше містить `delta_answer` та `id`, тому клієнтам, які раніше построково обробляли `delta_answer`, не потрібно нічого змінювати.

Після міграції за потреби можна ввімкнути нові можливості v2 (мультимодальний `message`, SSE, виклики інструментів, `action` CRUD) і впроваджувати їх у власному темпі.

## Обробка помилок

Відповіді з помилками мають уніфікований вигляд:

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

Поширені помилки:

- `400 bad_request`: відсутні обов’язкові поля, `tool_use_id` не збігається, schema `messages` некоректна тощо.
- `401 invalid_token`: заголовок `authorization` неправильний.
- `404 not_found`: розмова, що відповідає `id`, не існує під час `action: retrieve / update / delete`.
- `429 too_many_requests`: спрацювало обмеження швидкості.
- `500 chat_error`: помилка висхідної LLM або `completion_tokens=0` у цьому раунді (обробляється як невикористане, плата не стягується).

У потоковій відповіді помилка надсилається як подія `{"type":"error","message":"..."}`, після чого потік одразу завершується.

## Висновок

AI Chat v2 API, зберігаючи зворотну сумісність із v1, оновлює діалог із «одиночних / багатораундових запитань і відповідей» до «спостережуваного діалогу, орієнтованого на Agent»: мультимодальні введення, виклики інструментів, можливість призупинення / відновлення, потокові структуровані події, вбудований CRUD. Новим інтеграціям рекомендується одразу використовувати v2; наявні інтеграції v1 можуть виконати плавну міграцію поетапно. Якщо у вас виникнуть будь-які запитання, будь ласка, будь-коли звертайтеся до нашої команди технічної підтримки.
