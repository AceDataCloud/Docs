AI Chat v2 API (`/aichat2/conversations`) — це інтерфейс діалогу нового покоління, який є комплексним оновленням [AI Chat API](https://platform.acedata.cloud/documents/aichat-conversations). На основі простого v1 із підтримкою керованих багатотурових діалогів він розширює такі можливості:

- **Мультимодальне введення користувача**: безпосередня передача тексту + зображень + блоків файлів через структуроване поле `message`, без необхідності спочатку опосередковано додавати їх за допомогою `references`.
- **Виклики інструментів у стилі Agent**: вбудований набір інструментів для пошуку в Інтернеті, отримання вебсторінок, читання файлів тощо, а також можливість підключення MCP-серверів, авторизованих користувачем (Google Drive, Notion, Slack, GitHub тощо). Модель може самостійно багаторазово викликати інструменти в межах одного запиту для виконання складних завдань.
- **Структуровані потокові події**: за допомогою `accept: text/event-stream` або `application/x-ndjson` можна отримувати події `text_delta`, `tool_use`, `tool_result`, `thinking`, `citation`, `card`, `artifact` тощо для кожного токена, що полегшує їх окреме відображення на фронтенді відповідно до типу.
- **Можливість переривання / відновлення**: коли моделі потрібна додаткова інформація від користувача, вона надсилає подію `ask_user_question` і призупиняє роботу. Під час наступного виклику достатньо передати відповідь через `tool_results`, щоб продовжити виконання.
- **Нові CRUD-дії**: через поле `action` на тому самому endpoint можна виконувати `retrieve` / `retrieve_batch` / `update` / `delete`, без необхідності в додатковому API керування сеансами.
- **Постійно оновлюваний список моделей**: за замовчуванням підтримуються сучасні моделі, такі як GPT-5.4, Claude Opus 4.8, Claude Sonnet 4.6, Gemini 3.1 Pro, GLM 5.1, DeepSeek V4, Kimi K3 тощо.

Водночас на рівні тіла запиту він **повністю сумісний із попередньою версією v1**: достатньо передати лише `model` + `question` (+ необов'язкові `stateful` / `id` / `references` / `preset`), щоб отримати еквівалентну відповідь JSON `{answer, id}`, як у v1. Тому для міграції з `/aichat/conversations` не потрібно переписувати клієнтську частину — достатньо змінити шлях на `/aichat2/conversations`.

> Якщо ви наразі використовуєте `/aichat/conversations`, старий інтерфейс і надалі працюватиме. Ви можете перейти на новий у зручному для себе темпі.

## Базове використання

Найпростіший спосіб використання повністю збігається з v1: передайте `model` + `question` і отримайте `{answer, id}`.

Приклад CURL:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。"
  }'
```

Результат відповіді:

```json
{
  "answer": "AceDataCloud 是一个聚合主流 AI 模型与多模态服务的统一 API 平台，开发者通过一个密钥即可调用 GPT、Claude、Gemini、Midjourney、Suno、Veo 等多家服务。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Приклад Python:

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

## Багатотурові діалоги

Як і у v1, передайте `stateful: true`, щоб увімкнути збереження сеансу. API поверне `id`; у наступних запитах достатньо знову передати цей `id`, щоб продовжити діалог, без необхідності самостійно зберігати історію messages.

Перший запит:

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "记住一个数字：42。"
  }'
```

Відповідь:

```json
{
  "answer": "好的，我已经记住了 42。需要我用它做什么吗？",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Другий запит — передайте той самий `id`:
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "Яке число я щойно попросив тебе запам’ятати?"
  }'
```

```json
{
  "answer": "Число, яке ти попросив мене запам’ятати, — 42.",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` за замовчуванням має значення `true`; пропуск параметра та явна передача `true` еквівалентні. Встановлення `stateful: false` пропускає завантаження попередньої історії розмови; це не означає, що результати поточного запиту не будуть збережені, а також не підходить для робочих процесів із інструментами, які потребують призупинення та подальшого продовження.

### Довгі розмови та збереження оригінального тексту

Стиснення контексту лише впорядковує вміст, який надсилається моделі в межах поточного запиту, і не замінює збережену історію чату. За допомогою `action: retrieve` усе ще можна прочитати повний список збережених повідомлень; явне редагування або видалення розмови й надалі виконується відповідно до запиту.

Модель може шукати та посторінково читати оригінальний текст історії в межах поточної розмови. Якщо потрібно продовжити редагування статті, процитувати числа або підготувати матеріал до публікації, слід прочитати відповідний оригінальний текст, а не замінювати основний текст резюме. Ця можливість не відновлює автоматично повідомлення, які вже були втрачені в попередніх версіях.

Якщо впорядкування контексту не вдається, збережіть ID розмови та перевірте подію `error`; сервіс не перезапише оригінальний текст порожнім резюме. Операції з інструментами, завершені до збою, усе ще можуть бути чинними; спочатку перевірте їхні результати, щоб уникнути повторної генерації або повторної публікації. Коли одна розмова досягає ліміту сховища, система чітко повідомляє про помилку; наявні збережені записи не звільняють місце шляхом обрізання. Ви можете експортувати потрібний вміст, а потім розпочати нову розмову.

## Потокова відповідь

v2 підтримує два потокові формати, які вибираються за допомогою заголовка `accept`:

| Сценарій                    | `accept`               | Формат даних                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Вебфронтенд / EventSource  | `text/event-stream`    | `data: {json}\n\n`, останній рядок — `data: [DONE]\n\n` |
| Сервер / CLI / потоковий парсинг Node | `application/x-ndjson` | Один об'єкт JSON у кожному рядку                               |
| Без потокового режиму                 | `application/json` (за замовчуванням) | Одноразове повернення `{answer, id}`                       |

### Приклад NDJSON

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "Представ Ханчжоу трьома реченнями.",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # Сумісно з v1: фрагмент приросту також надається через поле delta_answer
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

Кожен рядок NDJSON є структурованою подією; найпоширеніша `text_delta`:

```a`:

```json
{"type":"text_delta","content":"Хан","delta_answer":"Хан","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"чж","delta_answer":"чж","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"оу","delta_answer":"оу","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### Приклад SSE

У браузері `EventSource` не підтримує власне тіло запиту, тому рекомендується використовувати `fetch` + ручне розбиття та парсинг за `\n\n`:

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "Представ Ханчжоу трьома реченнями.",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### Типи потокових подій

| `type`              | Значення                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `text_delta`        | Фрагмент тексту, що доповнює відповідь асистента. `content` містить новий вміст; для сумісності з v1 ця сама подія також містить `delta_answer` (дорівнює `content`) і `id`.                                        |
| `thinking`          | Процес міркування моделі (з'являється лише тоді, коли вибрана модель надає reasoning).                                                                                      |
| `tool_use`          | Модель вирішує викликати інструмент; подія містить `tool_id`, `tool_name`, `input`.                                                                        |
| `tool_result`       | Результат виконання інструмента, пов'язаний із попередньою подією `tool_use` через `tool_id`; `is_error` позначає, чи сталася помилка.                                                             |
| `card`              | Структурована картка, створена інструментом (наприклад, зображення або попередній перегляд посилання), придатна для безпосереднього відображення.                                                                                          |
| `citation`          | URL-адреса джерела для доповнення цитування відповідного фрагмента тексту.                                                                                                  |
| `ask_user_question` | Надсилається, коли моделі потрібна додаткова інформація від користувача; розмова переходить у стан `awaiting_user_input`. Докладніше див. нижче в розділі [Відновлення призупиненої розмови](#відновлення-призупиненої-розмови).                                                 |
| `artifact`          | Окремий результат, створений моделлю (наприклад, блок коду або документ), який можна зберегти чи завантажити.                                                                                            |
| `system_message`    | Системне інформаційне повідомлення (не є вмістом користувача чи асистента), призначене лише для відображення в інтерфейсі.                                                                                           |
| `compact`           | Контекст моделі впорядковано; збережені оригінальні повідомлення залишаються незмінними, клієнту не потрібно видаляти історію чату.                                                                                    |
| `error`             | У поточному запиті сталася помилка; `message` описує її вміст.                                                                                              |
| `done`              | Остаточний запис поточної розмови успішно збережено; містить `usage` (зокрема `prompt_tokens` / `completion_tokens` / `total_tokens`) і `terminal_reason`; для визначення завершення завдання все одно потрібно враховувати причину завершення.        |
Для клієнтів, які цікавляться лише остаточною відповіддю, об’єднання `content` усіх `text_delta` еквівалентне `answer` у режимі `application/json`.

## Мультимодальне введення

Якщо введення користувача містить зображення або файли, передавайте `message` (масив) замість `question`. Кожен елемент масиву є блоком вмісту:

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "Скільки котів на цьому зображенні?" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

Підтримувані типи блоків:

- `text` — звичайний текст, обов’язкове поле `text`.
- `image_url` — зображення, обов’язкове поле `image_url.url`.
- `file_url` — файл (PDF, CSV, TXT тощо), обов’язкове поле `file_url.url`.

### Взаємозв’язок із `references` у v1

Для сумісності зі старими клієнтами v2 і надалі розпізнає поле `references: ["https://...", ...]`:

- URL із розширеннями `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif` автоматично перетворюються на блоки `image_url`;
- інші розширення перетворюються на блоки `file_url`;
- якщо одночасно надано `question`, його буде додано на початок як блок `text`.

Тому, якщо ви хочете лише перейти з v1 і не змінювати тіло запиту, достатньо замінити шлях на `/aichat2/conversations`, а початковий спосіб використання `references` продовжить працювати без змін.

Якщо потрібен точніший контроль (наприклад, розміщення кількох зображень між текстовими фрагментами або важливий порядок), використовуйте безпосередньо масив `message`.

## Виклики інструментів і MCP

Основне вдосконалення v2 полягає в тому, що модель може самостійно викликати інструменти для виконання багатоетапних завдань. **Ця функція ввімкнена за замовчуванням**, і клієнту не потрібно виконувати жодних додаткових налаштувань у запиті. Типові сценарії:

- Користувач запитує: «Знайди, будь ласка, які нові виставки нещодавно з’явилися в Шанхаї» → модель викликає вбудований web search → упорядковує результати та формує відповідь.
- Користувач запитує: «Прочитай цей PDF, а потім напиши короткий виклад» → модель викликає file_read → створює короткий виклад.
- Користувач уже надав дозвіл Google Drive / GitHub / Notion тощо в [Connections](https://platform.acedata.cloud/connections) → модель може викликати відповідні інструменти MCP для читання та запису цих даних.

У потоках NDJSON / SSE виклики інструментів відображаються через два типи подій: `tool_use` і `tool_result`, наприклад:

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"Шанхай, весняні виставки 2026"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"Наразі","delta_answer":"Наразі","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"у Шанхаї","delta_answer":"у Шанхаї","id":"f2f4b3e8-..."}
...
```

Якщо ви не хочете відображати подробиці викликів інструментів у фронтенді, просто ігноруйте події `tool_use` / `tool_result` / `card` / `citation`. Остаточний результат моделі все одно надходитиме через потік `text_delta`.

`max_turns` дозволяє обмежити максимальну кількість циклів самостійного виклику інструментів моделлю в межах поточного запиту. Діапазон значень — від 1 до 500, значення за замовчуванням — 500, якщо параметр не вказано. Встановлення малого значення (наприклад, `max_turns: 1`) дає змогу примусово обмежити відповідь одним викликом і заборонити будь-які виклики інструментів.

## Асинхронне виконання та авторизація без нагляду

Якщо ваш запит надходить із Webhook сповіщень, CI/CD, системи моніторингу або іншого фонового завдання, можна встановити `async: true`, щоб інтерфейс негайно повернув ідентифікатор завдання, а виконання продовжилося у фоновому режимі:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "Мій сервіс надіслав сповіщення про помилку. Повідом групу WeChat «Команда AceDataCloud» через особистий обліковий запис WeChat……"
}
```

Приклад відповіді:

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

Після цього можна використовувати `action: retrieve` разом із `id`, щоб отримати результат розмови. Також можна вказати `callback_url`, і після завершення завдання платформа надішле POST-запит із `{ status, answer, usage, error }` на вашу адресу зворотного виклику. `callback_url` має використовувати `http` / `https` і не може безпосередньо містити `localhost` або буквальну адресу приватної IP-адреси.

Фонові завдання зазвичай не передбачають можливості натискання кнопки підтвердження користувачем. Якщо ви хочете, щоб певні Skill або MCP Server виконували дії надсилання, публікації, запису тощо в режимі без нагляду, явно передайте список попередньо авторизованих можливостей у тілі запиту:

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "Мій сервіс надіслав сповіщення про помилку. Повідом групу WeChat «Команда AceDataCloud» через особистий обліковий запис WeChat……"
}
```

Значення в `allowed_skills` — це slug підключених Skill; значення в `allowed_mcp_servers` — це slug підключених MCP Server. Skill / MCP Server, не включені до списку попередньої авторизації, у режимі без нагляду й надалі зможуть лише попередньо переглядати, виконувати dry-run або відмовлятися від операцій запису.

Якщо потрібен детальніший контроль, можна також використовувати еквівалентний об’єкт `unattended_policy`:

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

Попередня авторизація визначається саме цими двома списками: якщо список порожній, жодні можливості не авторизуються, тому додаткове поле перемикача не потрібне.

Зверніть увагу: попередня авторизація означає лише те, що «цей запит дозволяє зазначеним можливостям пропускати ручне підтвердження в режимі без нагляду». Відповідний Skill усе одно повинен підтримувати `--unattended-confirm` або відповідний механізм безпеки; інакше він продовжить виконувати dry-run і не виконуватиме операції запису безпосередньо.

## Відновлення призупинених розмов

Деякі інструменти можуть змусити модель «поставити користувачеві уточнювальне запитання». У такому разі модель надсилає подію `ask_user_question`, а розмова переходить у стан `awaiting_user_input` і призупиняється:

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "Якою мовою ви хочете створити звіт — китайською чи англійською?",
  "options": ["Китайська", "Англійська"],
  "id": "f2f4b3e8-..."
}
```

На фронтенді відобразіть цю подію у вигляді картки, щоб користувач міг вибрати відповідь, а потім надішліть наступний запит із тим самим `id`, передавши відповідь через `tool_results`:
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

У тілі запиту `tool_use_id` **обов’язково** має повністю збігатися з `tool_id`, отриманим під час призупинення; у разі невідповідності буде повернуто помилку 400. Якщо в запиті одночасно присутній `tool_results`, поля `question` / `message` / `references` будуть проігноровані.

Якщо користувач вирішить відмовитися від цього питання, достатньо безпосередньо передати новий `question` / `message`, і платформа автоматично позначить призупинений виклик інструмента як «користувач пропустив».

## Керування сеансами (CRUD)

У v2 легке керування сеансами реалізовано через поле `action` на тому самому endpoint, без потреби створювати окремий API.

### `action: retrieve` —— Отримати один сеанс

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

Повертає повний документ сеансу (включно з історією `messages`, `model`, `title`, `tools_used` тощо).

### `action: retrieve_batch` —— Отримати список коротких описів сеансів

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

Повертає `{ items`&#123;"type":"error","message":"..."&#125;`s`**，підходить для створення списку сеансів у бічній панелі`[DONE]`，а потім окремого отримання повних повідомлень за допомогою `action: retrieve`.

Необов’язкові параметри фільтрації: `user_id`、`application_id`、`model_group`、`model`。

### `action: update` —— Змінити заголовок або переписати історію

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "杭州旅行计划"
}
```

Також можна передати `messages`, але сервер виконає сувору перевірку схеми (обов’язково має використовуватися згорнута форма `ToolUseContent`); якщо формат не відповідає вимогам, буде повернуто помилку 400. Зазвичай рекомендується використовувати цей метод лише для зміни `title`.

### `action: delete` —— Видалити один сеанс

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Повертає `{ id, success: true }`. Після видалення відновити сеанс неможливо, тому перед викликом переконайтеся у правильності дії.

## Плавний перехід із v1

Якщо ви вже використовуєте [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations), перехід на v2 майже не потребує змін у коді:

1. Змініть URL з `https://api.acedata.cloud/aichat/conversations` на `https://api.acedata.cloud/aichat2/conversations`.
2. Якщо раніше ви передавали назви моделей v1 (наприклад, `gpt-3.5`、`gpt-4-browsing` тощо), під час переходу на v2 рекомендується оновити їх до сучасних моделей (наприклад, `gpt-5.4`、`claude-opus-4-8`、`gemini-3.1-pro-preview` тощо).
3. Поля потоку NDJSON залишаються зворотно сумісними: кожна подія `text_delta` і надалі містить `delta_answer` та `id`, тому клієнтам, які раніше аналізували `delta_answer` построково, не потрібно вносити зміни.

Після переходу можна за потреби ввімкнути нові можливості v2 (мультимодальний `message`, SSE, виклики інструментів, CRUD через `action`) і впроваджувати їх поступово.

## Обробка помилок

Формат відповідей із помилками уніфікований:

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

Поширені помилки:

- `400 bad_request`：відсутні обов’язкові поля, `tool_use_id` не збігається, недійсна схема `messages` тощо.
- `401 invalid_token`：неправильний заголовок `authorization`.
- `404 not_found`：сеанс, що відповідає `id`, не існує під час виконання `action: retrieve / update / delete`.
- `413 conversation_storage_limit`：перевищено ліміт сховища сеансу, наявні збережені записи не перезаписано.
- `429 too_many_requests`：спрацьовує обмеження частоти запитів.
- `503 context_compaction_failed`：не вдалося впорядкувати контекст, наявні записи збережено.
- `500 conversation_persist_failed`：не вдалося остаточно зберегти поточний сеанс; отримання тексту не означає, що остаточний запис успішно збережено, будь ласка, перевірте його за ID сеансу.
- `500 chat_error`：сервіс тимчасово недоступний або в цьому циклі не було згенеровано вміст (плата не стягується).

У потоковій відповіді помилки надсилаються як події `{"type":"error","message":"..."}`, після чого потік завершується. `[DONE]` лише означає завершення передавання даних; за наявності `error` це не можна вважати успішним виконанням, і подія успішного завершення `done` не надсилатиметься.

## Висновок

AI Chat v2 API, зберігаючи зворотну сумісність із v1, перетворює діалог із «однораундового / багаторазового запитання-відповіді» на «діалог із можливостями Agent та спостережуваністю»: мультимодальний ввід, виклики інструментів, можливість призупинення / відновлення, структуровані потокові події, вбудований CRUD. Для нових інтеграцій рекомендується одразу використовувати v2; наявні інтеграції v1 можна поступово й плавно мігрувати. Якщо у вас виникнуть будь-які запитання, будь ласка, звертайтеся до нашої служби технічної підтримки в будь-який час.
