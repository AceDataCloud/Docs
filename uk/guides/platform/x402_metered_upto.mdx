---
title: "Схеми виставлення рахунків X402 `exact` та `upto`"
description: "Platform API guide - Ace Data Cloud"
---

Ace Data Cloud X402 наразі використовує два типи scheme: `exact` та `upto`. Вони вирішують різні проблеми виставлення рахунків.

## `exact`

`exact` означає, що ціну цього запиту можна визначити ще до його надходження до цільового API. Сума, підписана клієнтом, є остаточною сумою списання.

Підходить для:

- Генерації зображень із фіксованою ціною;
- Створення відеозавдань із фіксованою ціною;
- API пошуку або інструментів із фіксованою ціною;
- Оплати замовлень.

EVM `exact` використовує USDC EIP-3009 `TransferWithAuthorization`:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": {
    "authorization": {
      "from": "0x...",
      "to": "0x...",
      "value": "95215",
      "validAfter": "1780237345",
      "validBefore": "1780240945",
      "nonce": "0x..."
    },
    "signature": "0x..."
  }
}
```

Facilitator перевіряє підпис і суму на етапі `/verify`, а на етапі `/settle` надсилає цю авторизацію в блокчейн.

## `upto`

`upto` означає, що клієнт авторизує максимальний ліміт, а Ace Data Cloud здійснює розрахунок за фактичним використанням після завершення запиту; фактичне списання не може перевищувати ліміт.

Підходить для:

- Чат-доповнень: остаточна ціна залежить від prompt tokens і completion tokens;
- Потокових відповідей: фактична довжина виводу стає відомою лише після завершення;
- Майбутніх API із післяплатним обліком.

`upto` використовує Permit2 `PermitWitnessTransferFrom`. Клієнт підписує не фіксований переказ, а авторизацію ліміту з witness:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2Authorization": {
      "from": "0x...",
      "spender": "0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002",
      "nonce": "123456789",
      "deadline": "1780240945",
      "permitted": {
        "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "amount": "95215"
      },
      "witness": {
        "to": "0x...",
        "facilitator": "0x...",
        "validAfter": "1780237345"
      }
    },
    "signature": "0x..."
  }
}
```

`permitted.amount` є лімітом, а не обов’язково остаточною сумою списання. Gateway на етапі `/record` перетворює фактичне використання на `amount` і передає його Facilitator. Facilitator дозволяє розрахунок лише за умови `amount &lt;= permitted.amount`.

Результат виконання програми Base `upto`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
elapsed_ms 5104
content ADC_BASE_UPTO_OK
id chatcmpl-DlcbyS4IT8kUAMo4Ri97HiIHc9T8V
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Пояснення:

- Ліміт авторизації, повернений у 402, становить `95215` atomic USDC, клієнт підписує цей ліміт.
- Після фактичної відповіді моделі розраховується лише `3` atomic USDC, а транзакцію в блокчейні вже можна перевірити в BaseScan.
- Цей результат демонструє ключову відмінність `upto`: підписана сума є лімітом, а on-chain settlement може бути меншим за ліміт.
- Якщо фактичне використання перевищує ліміт, Facilitator має відхилити settlement, і клієнту потрібно повторно авторизувати вищий ліміт.

`upto` наразі доступний лише в Base. Якщо потрібен післяплатний облік, використовуйте Base.

## Чому потрібен Permit2 approve

Зрештою `upto` дозволяє x402 proxy стягувати USDC із платіжного гаманця через Permit2. Перед першим використанням платіжний гаманець повинен надати Permit2 одноразовий ERC-20 allowance.

Python CLI:

```bash
pip install 'acedatacloud-x402[cli]'
X402_PRIVATE_KEY=0x... acedatacloud-x402 approve-permit2 --network base
```

Програмним способом:

```python
from acedatacloud_x402 import EVMAccountSigner, approve_permit2

approve_permit2(
    rpc_url="https://mainnet.base.org",
    signer=EVMAccountSigner.from_private_key("0x..."),
    token_address="0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
)
```

Після завершення авторизації для кожного запиту все одно потрібно підписувати новий `upto` envelope, оскільки nonce, deadline, witness і ліміт суми щоразу відрізняються.

## Розрахунок із нульовою сумою

`upto` підтримує ситуації, коли фактична сума дорівнює 0. Наприклад, якщо цільовий API не зміг успішно створити використання, що підлягає оплаті, Gateway може передати `amount = "0"`. Facilitator поверне успіх, але не надсилатиме транзакцію в блокчейн.

Це дає змогу уникнути проблеми «запит не був успішним, але все одно стягується on-chain комісія».

## Рекомендації щодо вибору

| Сценарій                   | Рекомендація                       |
| -------------------------- | ---------------------------------- |
| API із фіксованою ціною    | Використовуйте `exact`, логіка проста. |
| Оплата замовлень           | Використовуйте `exact`.            |
| Чат-доповнення, оплата за token | Використовуйте Base `upto`.        |
| Permit2 approve ще не виконано | Спочатку запустіть `exact`, а потім перейдіть на `upto`. |

Якщо ви не впевнені, що вибрати, спочатку використовуйте поведінку SDK за замовчуванням; SDK вибере payment requirement відповідної мережі, повернутий сервером.

## Контрольний список Base `upto`

Під час інтеграції або діагностики переконайтеся, що наведені нижче параметри походять з однієї й тієї самої відповіді 402 і залишаються однаковими під час підписання клієнтом:

| Параметр                   | Пункт перевірки                                          |
| -------------------------- | -------------------------------------------------------- |
| `network`                  | Має бути `eip155:8453`.                                  |
| `scheme`                   | Має бути `upto`.                                         |
| `extra.chainId`            | Base chain id — `8453`.                                  |
| `asset`                    | Використовуйте адресу контракту Base USDC із відповіді 402. |
| `extra.facilitatorAddress` | Має брати участь у witness і відповідати Facilitator `/supported`. |
| Permit2 allowance          | Платіжний гаманець має спершу авторизувати Permit2 для Base USDC. |

Поширені помилки та способи їх усунення:

| Помилка                                           | Спосіб усунення                                                                          |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `invalid_upto_evm_payload_invalid_signature` | Перевірте, чи відповідають chain id, адреса facilitator, Permit2 domain, spender, обліковий запис підпису та witness відповіді 402. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Виконайте Permit2 approve для USDC цільового ланцюга та повторно надішліть запит.         |
| `amount exceeds permitted amount`            | Фактичне використання перевищує підписаний ліміт; потрібно повторно підписати вищий ліміт. |
