[X402](https://www.x402.org/) — це запропонований Coinbase ончейн-протокол платежів «з тарифікацією за HTTP 402»: сервер повертає `402 Payment Required` для запитів без token, додаючи поле `accepts: [...]` зі списком прийнятних мереж / активів / цін; клієнт локально підписує авторизацію (на EVM це Permit2 / EIP-712, на Solana — авторизація SPL token transfer), поміщає base64-encoded envelope у заголовок `PAYMENT-SIGNATURE` і повторно надсилає запит. Після перевірки сервер фактично виконує ончейн-розрахунок, а потім повертає бізнес-результат.

> X402-клієнт Ace Data Cloud безпосередньо викликає цільовий API та використовує `402 Payment Required` і `accepts`, що повертаються цим запитом у реальному часі, як основу для ціни та підпису. Платіжні можливості Facilitator можна перевірити за адресою [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

І `@acedatacloud/sdk`, і `acedatacloud` надають хук `paymentHandler`: коли запит, відправлений самим SDK, отримує `402`, викликається введений вами handler, щоб отримати заголовок `PAYMENT-SIGNATURE`, після чого початковий запит надсилається повторно. Використовуйте `@acedatacloud/x402-client` / `acedatacloud-x402` разом із SDK, і **весь процес буде повністю прозорим для бізнес-коду** — вам достатньо використовувати `client.openai.chat.completions.create(...)`, і все виглядає так само, як у token-режимі, але під капотом це оплата за виклик без потреби попереднього поповнення.

У цій статті:

- реально пройдено ланцюжок «без token + інʼєкція X402 handler» на TS-боці ([перевірка T12](#四真实运行验证))
- перелічено відмінності між двома ланцюжками підпису EVM / Solana
- наведено три адаптації: режим приватного ключа `viem`, режим браузерного гаманця, режим Python `EVMAccountSigner`
- детально пояснено поле `preferScheme` / `prefer_scheme`, на якому легко помилитися

## I. Огляд протоколу (обовʼязково до прочитання)

Один успішний X402-виклик включає **3 HTTP RTT**:

```text
1. SDK -> /openai/v1/chat/completions               (无 Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK 内部 -> paymentHandler({ url, method, body, accepts })   (本地签名，0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (PAYMENT-SIGNATURE 头注入)
   <- 200 + business response   (结算在服务端完成)
```

X402 envelope — це JSON, який після base64-кодування поміщається в заголовок `PAYMENT-SIGNATURE`. Структура (уривок):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

На верхньому рівні envelope містить `x402Version: 2` і використовує обʼєкт `accepted`, щоб оголосити вибрані для цього разу `scheme` та `network` (ідентифікатор CAIP-2).

| scheme  | Значення                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Фіксована ціна (сценарії з визначеною ціною, як-от генерація зображень / відео, пошук тощо). Підписана сума = сума, яку вимагає сервер.                                                         |
| `upto`  | Тарифікація за обсягом (chat completions / token-подібні). Підписується сума **верхньої межі**, а фактично розраховується лише використана частина (на основі Permit2 + witness). **Наполегливо рекомендується** для API типу сесій. |

`preferScheme` / `prefer_scheme` використовується для вибору пріоритету, коли сервер **одночасно надає кілька scheme**. Якщо сервер надає лише `exact`, це поле буде проігноровано; якщо вказано `upto`, але сервер його не надає, буде виконано відкат до першого відповідного варіанта.

## II. TypeScript: два способи використання — браузерний гаманець + серверний viem

### Встановлення

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Перевірені номери версій:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Повна сигнатура `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' 必填
  evmProvider?: EVMProvider;                // network='base' 必填，EIP-1193
  evmAddress?: string;                      // network='base' 必填
  preferScheme?: 'exact' | 'upto';
}
```

Повернуте значення — це `(ctx) => Promise&lt;{ headers: Record<string, string> }>`, що точно відповідає сигнатурі хука `paymentHandler` SDK.

### Спосіб використання 1: браузер (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. 让用户连钱包
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. 切到 Base 主网
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. 构造 SDK 客户端，注入 X402 handler
//    注意：不传 apiToken，让 SDK 走 402 路径
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat 类必选 upto
  })
});

// 4. 正常调
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Під час першого виклику браузер покаже **два запити на підпис**: перший — одноразовий approve Permit2 для USDC (сума — `MaxUint256`, записується в блокчейн); другий — EIP-712-підпис X402 envelope (не записується в блокчейн, лише для перевірки facilitator). Наступні виклики потребують лише другого підпису, а з точки зору досвіду це «один клік підпису → отримання результату».

### Спосіб використання 2: Node-сервер + приватний ключ viem (підходить для бекенду / CLI)

`@acedatacloud/x402-client` на TS-боці **приймає лише EIP-1193 provider** — він не працює напряму з приватними ключами. У сценаріях Node / CLI стандартний підхід — використати [`viem`](https://viem.sh/), щоб обгорнути приватний ключ у `WalletClient`, а потім використати [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) або внутрішній EIP-1193-адаптер viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient 自带 EIP-1193 兼容的 .request()，可以直接当 evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request 满足 EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Якщо вважаєте, що адаптація EIP-1193 у viem недостатньо стабільна, також можна піти нижчорівневим шляхом через [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts), самостійно зібрати шлях `accepts → signed envelope → PAYMENT-SIGNATURE header`, пропустивши SDK-хук; утім, усе ж рекомендується насамперед використовувати `createX402PaymentHandler`, щоб не підтримувати оновлення протоколу самостійно.

### Використання 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

У мережі Solana наразі **доступна лише схема `exact`**, тому `preferScheme` у Solana не працює.

## III. Python: режим приватного ключа

`acedatacloud-x402` у Python використовує шлях **безпосереднього підписання приватним ключем** (без абстракції EIP-1193), що більше підходить для серверної частини / виконавців завдань.

### Встановлення

```bash
pip install acedatacloud acedatacloud-x402
```

Перевірені номери версій:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. 从私钥构造签名器
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. 构造 SDK：不传 api_token，让 SDK 走 402 路径
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # chat 类一定选 upto
    )
)

# 3. 正常调
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # 可选
    )
)
```

### Одноразовий approve (лише під час першого використання EVM)

У EVM Base X402 використовує Permit2, тому гаманцю потрібно один раз виконати approve `MaxUint256` для USDC на контракт Permit2. `acedatacloud-x402` містить вбудований `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Цю транзакцію потрібно надіслати лише один раз, після чого всі платежі X402 EVM використовуватимуть цей дозвіл. Для Solana це не потрібно.

## IV. Перевірка реального запуску

Мета тестування: **TS SDK без передавання token, з ін’єкцією X402 handler, може нормально створювати та надсилати запити** (полегшена перевірка без витрат реального ончейн USDC).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // 占位 provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Вивід:

```text
handler_type function
client_ctor_ok AceDataCloud
```

Результат показує:

- `apiToken` не передається, і створення SDK **не викликає помилки**, що доводить: режим X402 справді є легітимною заміною token.
- `createX402PaymentHandler` повертає функцію (хук), яку SDK викличе лише після отримання 402.
- Наскрізний тест із реальною ончейн-оплатою не додано до цього посібника, оскільки він передбачає реальне списання USDC; можна звернутися до прикладу e2e у [посібнику з інтеграції X402](https://platform.acedata.cloud/documents/x402-integration).

> На стороні Python `create_x402_payment_handler` також пройшов таку саму перевірку — функція повертає callable, а створення `AceDataCloud(...)` із передаванням `payment_handler=...` не викликає помилки. Семантика на обох сторонах узгоджена.

## V. Порівняння з «режимом Bearer token»

| Вимір              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Сценарії використання | Власний бекенд, довгострокові проєкти                                                         | Сторонні розробники, оплата за запитом, Agentic-виклики                        |
| Реєстрація              | Потрібно подати заявку в [консолі](https://platform.acedata.cloud/console/applications) | Не потрібна; достатньо мати ончейн-гаманець                                     |
| Точність білінгу            | Попереднє поповнення, списання за таблицею token                                                   | У реальному часі ончейн за виклик                                         |
| Баланс              | Можна переглянути в консолі                                                           | Перевіряється за USDC в ончейн-гаманці                                      |
| Початкові витрати            | Безкоштовний ліміт одразу після реєстрації через email                                                        | Потрібно перевести USDC на Base, перший Permit2 approve              |
| Підходить для chat-класу       | ✅                                                                 | ✅（обов’язково `preferScheme=upto`）                       |
| Підходить для одноразової оплати / оплати за інший акаунт | ❌                                                                 | ✅                                               |
| Зміни в коді            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Два режими можуть співіснувати — в одному й тому самому процесі достатньо налаштувати різні способи автентифікації для різних екземплярів `client`.

## VI. Поширені пастки

1. **Для chat-класу обов’язково `preferScheme=upto`**: використання `exact` змусить facilitator списувати USDC за `maxAmountRequired` (а не за фактичне використання).
2. **На стороні Node не передавайте голий приватний ключ у `createX402PaymentHandler`**: TS-пакет не приймає `{ privateKey }`, його обов’язково потрібно обгорнути в EIP-1193 provider (рекомендовано viem `WalletClient`).
3. **Перший виклик передбачає подвійний підпис**: перший раз підписується Permit2 approve (он-чейн, з gas), другий раз підписується X402 envelope (не он-чейн). У наступних викликах залишається лише другий.
4. **У Solana немає концепції Permit2**: безпосередньо підписується авторизація SPL token transfer, approve не потрібен; але наразі в мережі Solana підтримується лише `exact`.
5. **Розрізняйте бізнес-помилки та помилки платежу**: 402 → збій handler викидає `X402SignError` (конкретний тип залежить від мережі); помилки бізнес-інтерфейсу після повторного надсилання (401 / 422 / 5xx) усе ще класифікуються як звичайні винятки SDK.
6. **Найстабільніший спосіб адаптації `viem`**: `evmProvider: walletClient as any` втратить перевірку типів, але має найкращу сумісність; якщо потрібно зберегти типізацію, окремо обгорніть `.transport.request` viem в об’єкт `{ request }` і передайте його.
