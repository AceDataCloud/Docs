Ace Data Cloud X402 наразі здійснює розрахунки в USDC та підтримує два типи мереж: EVM і Solana. Способи підпису, адреси активів, поведінка gas і сценарії застосування відрізняються залежно від мережі, тому перед інтеграцією потрібно спочатку вибрати мережу.

## Ідентифікатори мереж використовують CAIP-2

`accepts[].network` у x402 v2 є ідентифікатором CAIP-2, а не скороченою назвою на кшталт `base` чи `solana`. Клієнт повинен зіставляти мережі за рядком CAIP-2:

| Мережа             | Ідентифікатор CAIP-2                       |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Матриця підтримки

| Мережа     | scheme  | Актив                  | Спосіб підпису                                 | Сценарії застосування                     |
| ------ | ------- | ------------------- | ------------------------------------ | ------------------------ |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Рекомендовано за замовчуванням, підтримка гаманців і ліквідності зріла.         |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | API з обліком після використання, як-от чат і моделі.          |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Гаманці Solana, Agent або сценарії ончейн-застосунків. |

`upto` наразі доступний лише на Base. Фактично доступні елементи визначаються значенням `accepts`, яке повертає API. Ви також можете переглянути Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

Відповідь Facilitator `/supported`:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Пояснення результатів:

- `exact` для Base і Solana є шляхом оплати з фіксованою сумою.
- Лише Base надає шлях обліку після використання `upto`, який залежить від Permit2 approve.
- `extra.facilitatorAddress` у записі `upto` — це адреса, яку клієнт повинен записати у witness під час підпису, і вона повинна збігатися зі значенням, яке повертає сервер.

## Base

Base використовує офіційний контракт USDC:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

У схемі `exact` клієнт підписує EIP-712 `TransferWithAuthorization`. Вміст підпису включає:

- `from`: адресу гаманця платника
- `to`: адресу отримувача Ace Data Cloud
- `value`: суму цієї оплати
- `validAfter` / `validBefore`: часовий проміжок чинності підпису
- `nonce`: 32-байтовий випадковий nonce

Після перевірки підпису Facilitator викличе в ончейні `transferWithAuthorization` USDC для завершення переказу.

Base є найбільш рекомендованою мережею для повноцінної інтеграції, особливо для обліку після використання `upto`, оскільки екосистема Permit2, USDC і гаманців є зрілішою.

Приклад результату перевірки Base `exact`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Пояснення результатів:

- Повторний запит API після оплати повертає вміст моделі `ADC_BASE_E2E_OK`.
- Ончейн-транзакцію вже можна знайти в BaseScan, номер блоку — `46726299`.
- `95215` atomic USDC відповідає `0.095215` USDC, що є фактичною сумою розрахунку за цей виклик API.

Результат виконання програми для оплати замовлення через Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Пояснення результатів:

- Кінцевий статус замовлення на платформі — `Finished`.
- `pay_id` замовлення записується в той самий хеш транзакції Base.
- `1200000` atomic USDC відповідає `1.2` USDC, що є історичною фактично сплаченою сумою цього замовлення на 10 Credits за старою політикою; нові замовлення більше не отримують додаткову знижку за спосіб оплати X402, а конкретна сума підпису визначається відповіддю 402 цього разу.

## Solana

Solana використовує SPL USDC `TransferChecked`. Клієнт сформує транзакцію переказу, підпише та надішле її, а потім помістить підпис транзакції або серіалізовану транзакцію до envelope `PAYMENT-SIGNATURE`.

Особливості Solana:

- Використовуються Solana wallet adapter або base58 secret key;
- Активом є Solana USDC mint;
- Наразі підтримується лише `exact`;
- Facilitator перевіряє mint, destination, authority та amount інструкції transfer.

Якщо використовується режим wallet fee payer, гаманець безпосередньо надсилає транзакцію, а Facilitator відповідає за підтвердження транзакції та повернення результату settlement.

Приклад результату перевірки Solana `exact`:

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Пояснення результатів:

- Повторний запит після оплати вже повернув HTTP 200, а модель вивела `ADC_SOLANA_E2E_OK`.
- Під час запиту ончейн signature через публічний RPC можна зіткнутися з обмеженням частоти.
- Оскільки запити до публічного RPC можуть бути обмежені за частотою, тут не вказано Solana explorer. Якщо потрібна сувора звірка, використовуйте власний Solana RPC або записи про розрахунки на боці платформи для підтвердження підпису транзакції.

## Як вибрати

| Що ви хочете зробити        | Рекомендована мережа           |
| ------------ | -------------- |
| Швидко пройти мінімальний шлях     | Base `exact`   |
| Для звичайних користувачів Web3 | Base           |
| Виконувати облік після використання для доповнення чатів тощо   | Base `upto`    |
| Застосунки екосистеми Solana  | Solana `exact` |

Незалежно від вибраного ланцюга, не кодуйте ціну жорстко в клієнті. Ціна визначається значенням `accepts[].maxAmountRequired`, яке повертає сервер.

## Додавання нової EVM-мережі
Підтримку коду для платежів із фіксованою сумою в нативному USDC у наведених нижче мережах надано, відкриття відбувається по черзі за мережами.
Доступність визначається `accepts`, що повертається замовленням або API; це не означає, що всі мережі увімкнено у production.

| Мережа        | Псевдонім   | CAIP-2         | Нативний USDC                                |
| ------------- | ----------- | -------------- | -------------------------------------------- |
| Arbitrum One  | `arbitrum`  | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

Ці мережі підтримують лише `exact`, точність валюти становить 6. Не використовуйте однойменний мостовий USDC.
Під час використання офіційного TypeScript/Python X402 Client можна передати скорочену назву з таблиці або ідентифікатор CAIP-2.
Клієнт використовує ID цільового ланцюга для створення підпису; гаманець має підтримувати цільову мережу.

Офіційна таблиця підтримки гаманця-розширення Phantom містить Arbitrum і Polygon; Optimism, Avalanche
наразі не внесені до цієї таблиці, можна використовувати Rabby або MetaMask, що підтримують цільовий ланцюг. EVM-адреси можуть бути однаковими в різних ланцюгах,
але баланси є незалежними один від одного, адреси Solana не застосовні до EVM USDC.
Див. [таблицю підтримки гаманця Phantom](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### Вхід для поступового розгортання нових мереж

Вхід для нових ланцюгів приховано за замовчуванням. Під час доступу до консолі або Studio можна використати `?features=x402-arbitrum`,
щоб увімкнути відповідний ланцюг; кілька flag розділяються комами. Щоб вимкнути один ланцюг, використовуйте `?features=-x402-arbitrum`,
щоб очистити локальні перевизначення, використовуйте `?features=none`. Перемикачі зберігаються окремо для кожного домену.
Котирування замовлень і повторні спроби платежів використовують той самий перемикач, сервер виконує незалежну перевірку; наявні записи про платежі все ще можна переглядати.
Увімкнення лише page flag не активує ланцюг, який ще не налаштовано, конкретні мережі, доступні для оплати, як і раніше визначаються реальним часом `accepts`.
