Ace Data Cloud X402 наразі здійснює розрахунки в USDC і підтримує два типи мереж: EVM та Solana. Спосіб підпису, адреси активів, поведінка gas і відповідні сценарії відрізняються залежно від мережі, тому перед інтеграцією потрібно спочатку вибрати мережу.

## Ідентифікатори мереж використовують CAIP-2

`accepts[].network` у x402 v2 є ідентифікатором CAIP-2, а не скороченими назвами на кшталт `base` чи `skale`. Під час зіставлення мереж клієнт повинен порівнювати рядки CAIP-2:

| Мережа             | Ідентифікатор CAIP-2                                 |
| -------------- | ----------------------------------------- |
| Base           | `eip155:8453`                             |
| SKALE Base     | `eip155:1187947933`                       |
| Solana mainnet | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` |

## Матриця підтримки

| Мережа     | scheme  | Актив                  | Спосіб підпису                                 | Сценарій застосування                        |
| ------ | ------- | ------------------- | ------------------------------------ | --------------------------- |
| Base   | `exact` | Base USDC           | EIP-3009 `TransferWithAuthorization` | Рекомендовано за замовчуванням, зріла підтримка гаманців і ліквідності.            |
| Base   | `upto`  | Base USDC + Permit2 | Permit2 `PermitWitnessTransferFrom`  | API з післяоплатним обліком для чатів, моделей тощо.             |
| SKALE  | `exact` | Bridged USDC у SKALE  | EIP-3009 `TransferWithAuthorization` | Низька вартість gas, підходить для перевірки EVM-платежів і недорогих викликів. |
| Solana | `exact` | Solana USDC         | SPL `TransferChecked`                | Сценарії Solana-гаманців, Agent або ончейн-застосунків.    |

`upto` наразі доступний лише у Base. Фактично доступні варіанти визначаються полем `accepts`, яке повертає API. Ви також можете переглянути Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

Відповідь Facilitator `/supported`:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    { "x402Version": 2, "scheme": "exact", "network": "eip155:1187947933" },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ]
}
```

Пояснення результатів:

- `exact` у Base, SKALE та Solana є шляхом оплати фіксованої суми.
- Лише Base надає шлях післяоплатного обліку `upto`, який залежить від approve Permit2.
- `extra.facilitatorAddress` у записі `upto` — це адреса, яку клієнт має записати у witness під час підписання; вона повинна збігатися зі значенням, повернутим сервером.

## Base

Base використовує офіційний контракт USDC:

```text
0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913
```

У схемі `exact` клієнт підписує EIP-712 `TransferWithAuthorization`. Вміст підпису включає:

- `from`: адресу гаманця платника
- `to`: адресу отримання Ace Data Cloud
- `value`: суму цього платежу
- `validAfter` / `validBefore`: часовий проміжок чинності підпису
- `nonce`: випадковий nonce довжиною 32 байти

Після перевірки підпису Facilitator викликає в мережі `transferWithAuthorization` USDC для завершення переказу.

Base є найбільш рекомендованою мережею для офіційної інтеграції, особливо для післяоплатного обліку `upto`, оскільки екосистеми Permit2, USDC та гаманців у ній є зрілішими.

Приклад результату перевірки Base `exact`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC
```

Пояснення результатів:

- Повторний запит API після оплати повертає вміст моделі `ADC_BASE_E2E_OK`.
- Ончейн-транзакцію можна переглянути в BaseScan, номер блоку — `46726299`.
- `95215` atomic USDC відповідає `0.095215` USDC і є фактичною сумою розрахунку за цей виклик API.

Результат виконання програми для оплати замовлення через Base `exact`:

```text
order 78481793-304e-47f7-bc0c-8231aec9cc1e
state Finished
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Пояснення результатів:

- Кінцевий статус замовлення на платформі — `Finished`.
- `pay_id` замовлення записується в той самий хеш транзакції Base.
- `1200000` atomic USDC відповідає `1.2` USDC — це історична фактично сплачена сума цього замовлення на 10 Credits за старою політикою; нові замовлення більше не отримують додаткову знижку за спосіб оплати X402, а конкретна сума підпису визначається відповіддю 402 цього разу.

## SKALE

SKALE використовує bridged USDC, а спосіб підпису подібний до Base — також EIP-3009. Він підходить для EVM-сценаріїв оплати з низькою вартістю gas; фактичні виклики все одно визначаються полем `accepts`, яке повертає API.

Типовий `accepts` 402 у SKALE міститиме:

```json
{
  "network": "eip155:1187947933",
  "scheme": "exact",
  "extra": {
    "name": "Bridged USDC (SKALE Bridge)",
    "version": "2",
    "chainId": 1187947933,
    "verifyingContract": "0x85889c8c714505E0c94b30fcfcF64fE3Ac8FCb20"
  }
}
```

SKALE наразі надає лише `exact`. Якщо вам потрібен післяоплатний облік, використовуйте Base `upto`.

Приклад результату перевірки SKALE `exact`:

```text
content ADC_SKALE_E2E_OK
tx 0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
block 1969317
explorer https://skale-base-explorer.skalenodes.com/tx/0x9fd09901e74c763325fe118b2bc64765c3fca785b86b24a78b97964384db084f
paid 0.095215 USDC
```

Пояснення результатів:
- API paid retry returns model content `ADC_SKALE_E2E_OK`.
- The transaction can be queried in the SKALE explorer, and the block number is `1969317`.
- The settlement amount for this `exact` payment is `0.095215` USDC.

## Solana

Solana uses SPL USDC `TransferChecked`. The client constructs a transfer transaction, signs and submits it, then places the transaction signature or serialized transaction into the `PAYMENT-SIGNATURE` envelope.

Solana characteristics:

- Uses a Solana wallet adapter or base58 secret key;
- The asset is the Solana USDC mint;
- Currently only `exact` is supported;
- The Facilitator validates the transfer instruction's mint, destination, authority, and amount.

If wallet fee payer mode is used, the wallet submits the transaction directly, and the Facilitator is responsible for confirming the transaction and returning the settlement result.

Solana `exact` verification result example:

```text
payer AY2RmGm2zPxB1uKvvF4dKyYdr2VySyL3wcD1MKJZoLRd
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run
```

Result description:

- paid retry has already returned HTTP 200, and the model output `ADC_SOLANA_E2E_OK`.
- Rate limiting may be encountered when querying the on-chain signature through a public RPC.
- Because public RPC queries may be rate-limited, the Solana explorer is not listed here. When strict reconciliation is required, please use your own Solana RPC or platform-side settlement records to confirm the transaction signature.

## How to choose

| What you want to do        | Recommended network                         |
| ------------ | ---------------------------- |
| Quickly run through the minimal flow     | SKALE `exact` or Base `exact` |
| Target regular Web3 users | Base                         |
| Perform postpaid metering such as chat completions   | Base `upto`                  |
| Solana ecosystem applications  | Solana `exact`               |
| Low-cost EVM payment verification | SKALE `exact`                |

Regardless of which chain you choose, do not hardcode prices in the client. Prices are determined by the `accepts[].maxAmountRequired` returned by the server.

## Newly added EVM networks

Code support has been provided for native USDC fixed-amount payments on the following networks, which will be enabled one by one by network.
Availability is subject to the `accepts` returned by orders or APIs; this does not mean that all networks have been enabled in production.

| Network      | Alias      | CAIP-2         | Native USDC                                  |
| ------------ | ---------- | -------------- | -------------------------------------------- |
| Arbitrum One | `arbitrum` | `eip155:42161` | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

These networks support only `exact`, with a token precision of 6. Do not use bridged USDC with the same name.
When using the official TypeScript/Python X402 Client, you can pass the alias or CAIP-2 identifier from the table.
The client constructs the signature using the target chain ID; the wallet must support the target network.

The official support table for the Phantom extension wallet lists Arbitrum and Polygon; Optimism and Avalanche
are currently not included in the table, so you can use Rabby or MetaMask that supports the target chain. EVM addresses can be the same across different chains,
but balances are independent of each other, and Solana addresses do not apply to EVM USDC.
See the [Phantom wallet support table](https://docs.phantom.com/wallet-sdks-overview#chain-support).

### New network gradual rollout entry

New chain entries are hidden by default. When accessing the console or Studio, use `?features=x402-arbitrum`
to enable the corresponding chain; separate multiple flags with commas. To disable a single chain, use `?features=-x402-arbitrum`,
and to clear local overrides, use `?features=none`. Switches are stored separately for each domain.
Order quotes and payment retries use the same switch, and the server validates independently; existing payment records can still be viewed.
Enabling only the page flag will not enable chains that have not yet been configured; the networks that can actually be paid on are still subject to real-time `accepts`.
