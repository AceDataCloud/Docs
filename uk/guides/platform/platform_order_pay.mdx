Створити або оновити платіжну сесію для замовлення `Pending`. Платіжна дія звертатиметься до платіжного каналу та може змінити статус замовлення, перед викликом необхідно підтвердити ID замовлення, суму та спосіб оплати.

## Огляд інтерфейсу

| Пункт    | Вміст                                                             |
| ---- | -------------------------------------------------------------- |
| Метод   | `POST`                                                         |
| URL  | `https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/` |
| Авторизація   | Платежі типу керованого перенаправлення можуть бути анонімними; інші способи потребують стану входу або Account Token                            |
| Body | JSON, для неоплачених замовлень обов’язково потрібно надати `pay_way`                                       |

## Межі анонімної оплати

Анонімний доступ використовується для сценаріїв, коли після відкриття скопійованого платіжного посилання втрачено стан входу, не потребує та не повинен містити довгостроковий Account Token. Анонімний виклик:

- дозволяє лише налаштовані на сервері способи оплати з керованим перенаправленням;
- фіксовано використовує сторінку оплати для комп’ютера;
- не може отримувати замовлення з нульовою вартістю;
- обмежується за IP та окремим замовленням;
- повертає мінімальну проєкцію замовлення, без акаунта, Application або внутрішніх metadata.

Автентифікований викликаючий має бути власником замовлення або суперкористувачем. Способи, яким потрібен контекст користувача, як-от X402, обмін винагород тощо, не можуть викликатися анонімно.

## Приклад запиту

```shell
export ORDER_ID='你的 Pending 订单 ID'

curl -X POST \
  "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}/pay/" \
  -H 'Content-Type: application/json' \
  -d '{"pay_way":"Stripe"}'
```

Способи оплати, що потребують автентифікації:

```shell
export PLATFORM_TOKEN='你的账户令牌'

curl -X POST \
  "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}/pay/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"pay_way":"X402"}'
```

`pay_way` використовує фактичні значення, що підтримуються моделлю замовлення, наприклад `WechatPay`, `AliPay`, `Stripe`, `Card`, `Airwallex`, `X402`, `PayPal`, `AppleIAP`, `Reward`, `BankTransfer`. Не кожне значення доступне для анонімних запитів або на кожному сайті.

## Опис відповіді

Успішна відповідь — це оновлений об’єкт замовлення, який зазвичай надає точку входу для наступного кроку через `pay_url`; різні способи оплати також можуть повертати в контрольованих полях інформацію, необхідну клієнту для продовження оплати. Анонімна відповідь використовує мінімальний білий список полів, автентифікований власник отримує повні відомості.

Не покладайтеся на старі назви полів, як-от `payment_url`, `qr_code_url` або `payment_method`; поточний контракт Order використовує `pay_url` і `pay_way`.

## Банківський переказ

Як особисті, так і корпоративні акаунти після входу можуть використовувати `BankTransfer`, корпоративна верифікація не потрібна. Як внутрішні перекази в юанях, так і міжнародні перекази в доларах США вимагають, щоб сума замовлення становила щонайменше 300 доларів США; сума до сплати в юанях визначається сумою, відображеною під час оплати.

Перед оплатою можна через `GET /api/v1/orders/{order_id}/payment-options/` запитати доступні для поточного замовлення маршрути переказу та пороги сум. Банківський переказ має ініціюватися власником замовлення після входу та обмежується конфігурацією каналу отримання коштів і сферою застосовності тарифного плану; анонімні запити його використовувати не можуть.

## Покупки в застосунку iOS

Власник замовлення після входу може передати `pay_way: "AppleIAP"`. Цей запит оновлює неоплачене замовлення відповідно до `metadata.apple_price` вибраного тарифного плану та скасовує знижку, не здійснює списання, не нараховує кредити й не повертає платіжне посилання. Для старих неоплачених замовлень спершу потрібно виконати цей крок, а потім ініціювати нативну оплату Apple. Підтримується лише один тарифний план Usage із налаштованим товаром Apple і ціною; непідтримувані тарифні плани або пакетні замовлення повертають `400`.

Після нативної оплати Apple подайте `transaction_id` через `/api/v1/orders/{id}/apple-verify/`, щоб завершити серверну перевірку та нарахування кредитів. Кількість кредитів походить із тарифного плану; сума використовує незалежну встановлену ціну Apple у доларах США, без додавання знижок учасника або націнки сайту, а сума списання в місцевій валюті в інших регіонах визначається сторінкою підтвердження Apple.

## Помилки та повторні спроби

- Замовлення не є `Pending`: повертається `400`; не створюйте платіжну сесію повторно.
- Не надано `pay_way`: для замовлень із ненульовою сумою повертається `400`.
- Анонімний виклик використав недозволений спосіб або замовлення з нульовою вартістю: повертається `403`, після входу власник має повторити спробу.
- Автентифікований викликаючий не є власником замовлення: повертається `403`.
- Збій платіжного каналу: не надсилайте повторно бездумно; спершу запитайте деталі замовлення, підтвердьте, що воно все ще `Pending`, а потім повторіть спробу.
