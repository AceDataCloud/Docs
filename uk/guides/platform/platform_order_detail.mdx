Запит замовлення за ID замовлення. Цей ендпойнт підтримує два режими читання: анонімний доступ повертає лише мінімальні поля, потрібні для сторінки оплати; власник замовлення з Account Token отримує повні деталі.

## Огляд інтерфейсу

| Пункт   | Вміст                                                        |
| --- | --------------------------------------------------------- |
| Метод  | `GET`                                                     |
| URL | `https://platform.acedata.cloud/api/v1/orders/{order_id}` |
| Авторизація  | Необов’язкова; анонімно — мінімальна проєкція, автентифікований власник — повна проєкція                                    |

`/orders/{id}` і `/orders/{id}/` наразі обидва доступні. ID замовлення є частиною посилання для оплати, його слід розглядати як чутливий непрозорий ідентифікатор і не поширювати публічно.

## Анонімний запит

Сторінка оплати може виконати пряме читання у разі втрати стану входу:

```shell
export ORDER_ID='你的订单 ID'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json'
```

Анонімна відповідь містить лише `id`, `description`, `price`, `state`, `pay_way`, `pay_url`, `expired_at`, `created_at`. Вона не повертає обліковий запис, Application, Package, внутрішні ідентифікатори платежу або metadata.

## Автентифікований запит

```shell
export PLATFORM_TOKEN='你的账户令牌'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

Власник замовлення отримає повні деталі Order, включно з `application` / `applications`, `package` / `packages`, `bank_details`, `invoice_automation` і полями моделі. Якщо користувач автентифікований, але не є власником замовлення, повертається `403`; за винятком супер адміністратора.

## Ключові поля

| Поле            | Опис                                                          |
| ------------- | ----------------------------------------------------------- |
| `state`       | `Pending`, `Paid`, `Finished`, `Expired`, `Failed` або `Refunded` |
| `pay_way`     | Поточний спосіб оплати замовлення; назва поля не є `payment_method`                             |
| `pay_url`     | Адреса розміщеної сторінки оплати або QR-коду, може бути порожньою                                           |
| `price`       | Остаточна сума до сплати за замовлення, поточна модель замовлення не надає поля `final_price`                         |
| `amount`      | Кількість квоти пакета; видима лише в повній автентифікованій відповіді                                            |
| `finished_at` | Час завершення замовлення; назва поля не є `paid_at`                                      |

Повна відповідь може містити додаткові поля залежно від способу оплати; клієнт повинен читати їх за потреби та завжди уникати запису чутливих metadata з повної відповіді.

## Обробка помилок

- `404`: ID замовлення не існує.
- `403`: користувач увійшов у систему, але не є власником замовлення.
- Анонімний запит не повертає `401`; він отримує лише мінімальну публічну проєкцію.

## Сторнування рахунку-фактури та повторне подання заявки

Через `GET /api/v1/orders/{order_id}/invoice/` можна отримати поточний рахунок-фактуру замовлення. Після автоматичного подання на сторнування рахунок-фактура все ще має статус `Issued`, а `red_state` вказує хід сторнування; успішне подання не означає завершення сторнування. Під час очікування підтвердження, виписки червоного рахунку або архівації замовлення не може повторно подати заявку на рахунок-фактуру.

Коли адміністратор подає заявку на сторнування через помилку в даних для виставлення рахунку, таких як назва або податковий номер, причиною сторнування є «помилка у виставленні рахунку»; автоматичне сторнування, спричинене поверненням коштів за замовлення, усе ще використовує «припинення послуги».

Після успішного виписування та архівації червоного рахунку оригінальний рахунок-фактура стає `Voided`, і лише тоді замовлення може повторно подати заявку. Оригінальний рахунок-фактуру можна переглянути в історії рахунків-фактур. У разі невдалого сторнування або коли результат потребує перевірки, ним займається фінансова перевірка, а обмеження на виставлення рахунку для замовлення не буде знято достроково. Рахунки-фактури, виставлені вручну, спочатку мають бути анульовані або сторновані в податковій чи системі виставлення рахунків, після чого фінансовий відділ підтверджує це на платформі.
