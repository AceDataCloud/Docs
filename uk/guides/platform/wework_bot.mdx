Розгорніть власний екземпляр облікового запису корпоративного WeChat, увійдіть за допомогою сканування QR-коду в мобільному корпоративному WeChat, використовуйте REST API або MCP для читання облікового запису, контактів, чатів і локально синхронізованих повідомлень. Екземпляр відповідає звичайному обліковому запису корпоративного WeChat і не потребує приватного сервера або налаштування домену корпоративної пошти.

Наразі це Alpha-версія. Читання облікового запису пройшло реальну перевірку сеансів; надсилання текстових повідомлень від імені власника та зворотне читання подій пройшли реальне приймання; інші контакти, операції з групами та відновлення нового екземпляра ще мають пройти перевірку в середовищі розгортання. Надсилання медіа, відповіді з цитуванням, реальний @, керування учасниками груп і підтвердження доставки ще не відкриті. Будь ласка, орієнтуйтеся на значення, яке повертає екземпляр `/api/capabilities`.

## Розгортання та вхід

У категорії Deployment відкрийте сервіс і виберіть тариф тривалості екземпляра. Після розгортання відкрийте сторінку керування та відскануйте QR-код корпоративного WeChat обліковим записом власника; якщо потрібне підтвердження на телефоні або інші кроки входу, відкрийте віддалений робочий стіл і введіть пароль робочого столу цього екземпляра. Облікові дані API та пароль робочого столу є незалежними. Дані входу зберігаються на диску екземпляра; при перебудові контейнера диск зберігається; видалення диска видалить локальний сеанс.

Кожен екземпляр оплачується окремо та працює відповідно до придбаної тривалості. Виклики REST / MCP не оплачуються окремо за повідомлення, фактична ціна визначається сторінкою тарифу. Наразі за замовчуванням використовується довідковий тариф тривалості для WeChat-бота, перед остаточним відкриттям необхідно підтвердити ціноутворення з урахуванням ресурсів виконання.

## API та MCP

Використовуйте API-адресу екземпляра зі сторінки керування, усі інтерфейси облікового запису передають `Authorization: Bearer &lt;токен API екземпляра>`. Ці шляхи належать спеціальному екземпляру, а не спільному API-шлюзу. Адреса MCP — це адреса екземпляра з додаванням `/mcp/`, використовується той самий Bearer token.

| Інтерфейс | Призначення |
| -------------------------------------------------------- | ------------------------------------------- |
| `GET /api/status`、`GET /api/auth/status` | Чи готовий обліковий запис та список можливостей |
| `GET /api/auth/qr` | Поточний QR-код входу PNG Base64 |
| `GET /api/account` | Поточний обліковий запис |
| `GET /api/contacts?kind=all` | Внутрішні колеги та зовнішні контакти, можна вказати internal / external |
| `GET /api/conversations` | Локальні чати, збереження оригінального ID чату |
| `GET /api/messages` | Локально синхронізовані повідомлення; параметри conversation_id, after_rowid, limit |
| `POST /api/search` | Пошук контактів, чатів і локального тексту |
| `POST /api/messages` | Асинхронне завдання надсилання тексту, необхідно надати Idempotency-Key |
| `POST /api/messages/send` | Той самий вхід надсилання, підтримує одну або кілька цілей |
| `GET /api/groups/{conversation_id}` | Локально синхронізована інформація про групи та учасників |
| `GET /api/tasks` | Останні завдання та результати для кожної цілі |
| `GET /api/tasks/{id}` | Запит результату надсилання |
| `POST /api/tasks/{id}/cancel` | Скасування завдань, які ще не розпочалися |
| `POST /api/runtime/pause`、`POST /api/runtime/resume` | Призупинення автоматизації; відновлення після перевірки власника |
| `GET /api/diagnostics`、`GET /api/diagnostics/screenshot` | Стан екземпляра та поточний екран, обидва потребують автентифікації |
| `GET /api/events?after=0` | Події повідомлень із можливістю відновлення курсора |
| `WS /ws` | Потік подій повідомлень, автентифікація Bearer |

Тіло надсилання містить `target`, `type: "text"` і `text`. `target` приймає ID чату, ID контакту, ID користувача підприємства або унікальне повне ім’я; переважно використовувати ID; якщо відображуване ім’я все ще не може однозначно визначити об’єкт, екземпляр відхилить операцію і не буде вгадувати об’єкт. Контакти без локального чату спочатку відкриють чат через клієнт і після перевірки фактичного ID чату виконають надсилання. Заголовок запиту `Idempotency-Key` містить 8–128 символів: літери, цифри або `_.:-`. Повторні запити однієї операції повинні використовувати той самий ключ і те саме тіло запиту.

Заміна `target` на масив `targets` дозволяє послідовне надсилання 1–50 чітко визначеним цілям. Обидва параметри не можна надавати одночасно. Усі цілі спочатку проходять ідентифікаційний аналіз, різні псевдоніми, що вказують на один об’єкт, будуть відхилені. Якщо одна з цілей не вдається, подальше надсилання припиняється, результати завдання записуються окремо як `succeeded`, `failed`, `unknown` або `not_attempted`; не вважайте частковий успіх повним успіхом. Цей процес також має пройти реальну перевірку в середовищі розгортання для визначених контактів.

Завдання можуть перебувати у стані queued, running, submitting, succeeded, failed, unknown або cancelled. `succeeded` означає, що після надсилання було знайдено точний текст у відповідному чаті та ID повідомлення сервера, `delivered` все ще має значення null і не означає, що інша сторона отримала повідомлення. unknown означає, що результат невизначений, перевірте історію записів і не надсилайте повторно з новим ключем. Екземпляр не буде автоматично повторно надсилати перервані завдання.

Історія містить лише вміст, який уже синхронізував клієнт, і не може гарантувати повну історію. Нетекстові повідомлення можуть повертатися з типом unknown, завантаження вкладень ще не відкрите. Події зберігають останні 10 000 записів, `gap` означає, що курсор перевищив вікно збереження. Під час першого підключення стара історія не буде повторно відтворюватися як нові повідомлення.

`server_accepted` і `server_id` в історії повідомлень можна використовувати для перевірки, чи прийняв сервер локальне повідомлення; якщо є лише локальний запис без ID сервера, не можна вважати надсилання успішним. Ці поля не означають, що одержувач отримав або прочитав повідомлення. Записи подій зберігають стан на момент створення, для запиту поточного підтвердженого стану слід використовувати інтерфейс історії повідомлень.

## Обліковий запис і облікові дані

Використовуйте лише облікові записи, якими маєте право керувати особисто. Налаштовуйте API token лише у довірених застосунках; він може отримувати доступ до даних облікового запису цього екземпляра. Не публікуйте паролі, QR-коди або скриншоти чатів у відкритих місцях. Призупинення екземпляра перерве події в реальному часі. Після виходу з облікового запису або видалення пристрою на мобільному телефоні потрібно повторно увійти.

Поточне введення тексту підтримує лише один рядок, переноси рядків будуть явно відхилені перед надсиланням. Якщо клієнт вимагає безпечної перевірки або повторного входу, власник облікового запису повинен виконати це через віддалений робочий стіл; екземпляр не буде обходити перевірку. Завдання після переривання перевірки можуть повернути unknown, спочатку перевірте записи повідомлень і не надсилайте повторно з новим ключем ідемпотентності.

Після виявлення запиту безпеки, виходу з облікового запису або зміни облікового запису черга автоматизації буде збережена та призупинена. Після завершення перевірки телефону можна через консоль екземпляра «Відновити після перевірки» продовжити невиконані завдання; завдання, які вже були відправлені, але мають невизначений результат, не будуть повторно надсилатися. Звичайна віддалена офісна робота також може викликати перевірку безпеки корпоративного WeChat. Офіційне пояснення про відсутність блокування протягом 24 годин після перевірки не означає, що виявлення було усунено, і не означає, що екземпляр може гарантувати довготривалу роботу без нагляду.
