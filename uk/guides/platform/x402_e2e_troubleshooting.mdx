X402 охоплює HTTP, SDK, підписи, Facilitator і ончейн-транзакції. Під час усунення проблем із підписами або розрахунками рекомендується поетапно перевіряти в порядку «публічна точка входу -> відповідь 402 -> SDK payment handler -> ончейн settlement». Цей посібник описує способи перевірки кожного рівня та перелічує поширені помилки.

## Перевірка публічної точки входу

Декларація можливостей Facilitator:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Якщо повертаються `facilitator`, `supportedKinds` і протокольні ендпоінти, це означає, що метадані можливостей у нормі. Виявлення API-ресурсів виведено з експлуатації; безпосередньо викликайте цільовий API та орієнтуйтеся на відповідь 402 у реальному часі.

Підтримувані можливості Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

Якщо повертається `kinds`, це означає, що точка входу Facilitator працює нормально.

## Перевірка 402 `accepts`

Надішліть неавторизований запит, який не списує кошти:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Перевірте, чи містить повернений `accepts` мережу, яку ви хочете використовувати. `network` є ідентифікатором CAIP-2:

- `eip155:8453` + `exact`（Base）
- `eip155:8453` + `upto`（Base, облік після використання）
- `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` + `exact`（Solana）

Якщо цільова мережа відсутня, це означає, що цей API або поточне середовище не налаштовані з відповідним способом отримання платежів X402.

## Запуск розширених інструментів перевірки X402Client

Репозиторій X402Client надає розширені інструменти перевірки, які можна використовувати для підтвердження вибору відповіді 402, генерації підпису, paid retry та ончейн settlement. Вони потребують funded wallet, RPC, приватного ключа й залежностей для розробки. Для звичайної інтеграції в бізнес-застосунок рекомендується передусім використовувати TypeScript або Python SDK; запускайте ці інструменти лише тоді, коли потрібно локалізувати проблеми з підписом або ончейн-розрахунком.

Адреса репозиторію: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)

```bash
git clone https://github.com/AceDataCloud/X402Client.git
cd X402Client/typescript
npm install
npm install --no-save ethers @solana/spl-token bs58 tsx
```

Base:

```bash
export X402B_BASE_PAYER_PRIVATE_KEY=0x...
TEST_API_PATH='/openai/chat/completions' \
TEST_BODY='{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}],"max_tokens":10}' \
npx tsx scripts/test-real-e2e.ts
```

Solana:

```bash
export X402B_SOLANA_PAYER_PRIVATE_KEY=...
npx tsx scripts/test-solana-e2e.ts
```

Інструменти перевірки зазвичай виводять:

1. Відповідь 402 першого запиту.
2. Вибрану payment requirement.
3. Підсумок підписаного `PAYMENT-SIGNATURE`.
4. HTTP-статус і тіло відповіді після повторної спроби.
5. Ончейн settlement transaction або причину помилки Facilitator у разі невдачі.

Не надсилайте приватні ключі або повний `PAYMENT-SIGNATURE` до систем журналювання чи в тікети.

Приклад результатів перевірки публічного API:

```text
Base exact
HTTP 402 -> HTTP 200
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC

Solana exact
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run because public RPC lookup hit 429

Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Пояснення:

- Base `exact`, Solana `exact` і Base `upto` усі виконали paid retry від HTTP 402 до HTTP 200.
- Ончейн-транзакцію Base `exact` можна знайти в BaseScan, а сума розрахунку становить `95215` atomic USDC.
- Ліміт підпису Base `upto` становить `95215` atomic USDC, але фактичний ончейн settlement становить `3` atomic USDC, що означає списання за фактичним використанням при обліку після використання.
- Для шляху Solana підтверджено paid retry і виведення моделі. Публічний RPC може обмежувати частоту запитів; якщо потрібна сувора ончейн-звірка, використовуйте власний Solana RPC або підтвердіть підпис транзакції через записи розрахунків на стороні платформи.

## SDK smoke test

Розширені інструменти перевірки використовуються для перевірки підписів і ончейн-розрахунків. Бізнес-сторона також має виконати SDK smoke test, щоб підтвердити, що код застосунку може автоматично обробляти 402 через payment handler. Нижче показано лише основні фрагменти; для повного коду потрібно додати wallet, provider та import.

TypeScript:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const res = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly ADC_SDK_X402_OK' }],
  max_tokens: 8
});
```

Python:

```python
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
    )
)

res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly ADC_PY_X402_OK"}],
    max_tokens=8,
)
```

Якщо модель повертає фіксований рядок згідно з вимогами, це означає, що SDK, payment handler, Gateway, Facilitator і цільовий API з'єднані в один ланцюг.

Наведені вище два smoke test використовують Base `exact` і здійснюють розрахунок за фіксованою сумою, вказаною в котируванні 402. Chat completions належать до сценаріїв із вимірюванням за token, тому для робочої інтеграції рекомендується передавати `preferScheme: 'upto'` (у Python — `prefer_scheme="upto"`), щоб здійснювати розрахунок за фактичним використанням.

Об'єкт, який повертає Python SDK, є `dict`; для читання вмісту можна використовувати `res["choices"][0]["message"]["content"]`.

## E2E оплати замовлення

Оплата замовлення використовує платформний API `platform.acedata.cloud` і потребує токена облікового запису платформи. Повний ланцюг такий: створення Pending замовлення, `POST /api/v1/orders/{order_id}/pay/` запускає 402, після чого виконується повторна спроба з `PAYMENT-SIGNATURE`.

Приклад результатів перевірки оплати замовлення на невелику суму:

> Наведені нижче записи транзакцій є історичними зразками фактичних тестів за старою політикою; суми й хеші транзакцій збережено без змін. Нові замовлення X402 більше не мають знижок за способом оплати; використовуйте `amount` із поточної відповіді 402 як основу для підпису й оплати.
```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
accepts [('eip155:8453', 'exact', '1200000'), ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000')]

status 200
order state Finished
pay_way X402
pay_id 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}

Base tx status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Пояснення результатів:

- Після створення замовлення його статус — `Pending`, а ціна — `1.26`.
- Перший запит `pay/` повертає HTTP 402, у `accepts` є Base `exact` і Solana `exact`, суми обох становлять `1200000` atomic USDC.
- Після повторної спроби з Base `PAYMENT-SIGNATURE` повертається HTTP 200, статус замовлення змінюється на `Finished`, а `pay_way` — `X402`.
- Після декодування `PAYMENT-RESPONSE` відображаються `success=True`、`network=base`, а також той самий хеш транзакції.
- На BaseScan статус транзакції — `1`, сума переказу — `1200000` atomic USDC, тобто `1.2` USDC.
- Ціна створення `1.26` була сплачена протягом періоду старої політики знижок на X402, остаточна сума підпису та розрахунку становить `1.2` USDC.

Якщо під час оплати замовлення немає `Authorization: Bearer {platform_token}`, або замовлення не належить поточному обліковому запису, збій відбудеться на рівні прав доступу платформи; це відрізняється від безоблікового X402 API при прямому виклику `x402.acedata.cloud`.

## Поширені помилки

| Явище                                           | Напрямок перевірки                                                        |
| -------------------------------------------- | ------------------------------------------------------------------- |
| Перший запит не є 402                                  | Перевірте, чи не було помилково додано `Authorization`, або чи цей API ще не має X402 pricing.                  |
| `No payment requirement for network`         | Цільова мережа не входить до `accepts`, змініть мережу або перевірте конфігурацію Gateway.                               |
| `invalid_402`                                | Відповідь 402 не є валідним JSON, перевірте проксі, шлюз або сторінку помилки.                                        |
| `Authorization nonce already processed`      | Повторно використано той самий `PAYMENT-SIGNATURE`, підпишіть заново.                                  |
| `invalid_upto_evm_payload_invalid_signature` | Перевірте chainId для `upto`, Permit2 domain, адресу facilitator, а також відповідність облікового запису підпису.         |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Виконайте `approve-permit2` для USDC цільового ланцюга.                                     |
| `Payer has insufficient USDC balance`        | У гаманці платника недостатньо USDC.                                                       |
| HTTP 200, але немає tx hash                         | Фактична сума `upto` може бути 0, або запис settlement ще асинхронно записується.                             |
| Solana `Missing transaction payload`         | У envelope `PAYMENT-SIGNATURE` немає серіалізованої транзакції або signature, перевірте wallet adapter. |

## Контрольний список Base `upto`

`upto` наразі доступний лише на Base (`eip155:8453`). Оскільки підпис `upto` прив’язує більше параметрів EVM typed data, під час інтеграції слід особливо перевірити, що поточні поля у відповіді 402 повністю збігаються з клієнтським підписом.

```text
Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Якщо Base `upto` повертає `invalid_upto_evm_payload_invalid_signature`, першочергово перевірте:

1. `extra.chainId` у записі `eip155:8453` + `upto`, який повертає API (має бути `8453`).
2. `extra.facilitatorAddress`, який повертає API.
3. Адресу Base `upto` facilitator, яку повертає `https://facilitator.acedata.cloud/supported`.
4. Permit2 domain, spender, контракт USDC та обліковий запис підпису.
5. Чи гаманець уже виконав approve Permit2 для Base USDC.

Digest підпису `upto` одночасно прив’язує Permit2 domain, chain ID, spender, адресу одержувача, адресу facilitator і validAfter. Якщо будь-який із них не збігається, Facilitator відновить неправильний signer, що призведе до повернення invalid signature. Якщо все це збігається, але все одно повертається 402, наступним кроком перевірте Permit2 allowance; за відсутності авторизації повертається `PERMIT2_ALLOWANCE_REQUIRED`.

## Збереження інформації для перевірки

Одна повна перевірка щонайменше зберігає:

- API path і стислий виклад тіла запиту;
- вибрані network і scheme;
- `maxAmountRequired`;
- адресу гаманця payer;
- остаточний HTTP статус;
- модельний вивід або ID завдання у відповіді;
- посилання на settlement transaction;
- Gateway trace ID або ID запису використання платформи.

Не зберігайте приватні ключі, повний `PAYMENT-SIGNATURE`, повний EIP-712 signature або seed-фразу.

## Структуровані помилки оплати

Помилки X402 після підпису повертатимуть стабільні `code`, безпечні параметри інтерполяції, етап і прапорець повторної спроби у `extensions.acedatacloud.paymentError`. Першочергово використовуйте цю структуру для діагностики, не аналізуйте англійський верхньорівневий `error` і не просіть користувача надати підпис гаманця або оригінальний текст симуляції в ланцюгу.

- `charged: false`: перевірка була явно відхилена до settlement, цього разу списання не було ініційовано.
- Не містить `charged`: результат невідомий або вже перейшов до етапу settlement, спочатку перевірте замовлення та стан у ланцюгу, прямо повторювати оплату заборонено.
- `settlement_pending`: поки що не повторюйте оплату, спочатку оновіть замовлення або зверніться до підтримки.
- Нерозпізнаний code: обробляйте як `payment_failed` і зберігайте публічний технічний код для пошуку службою підтримки.
