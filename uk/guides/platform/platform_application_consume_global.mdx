---
title: "Налаштування спільного використання глобального балансу AceDataCloud Application"
description: "Platform API guide - Ace Data Cloud"
---

Налаштуйте `allow_consume_global`. Після ввімкнення Application з оплатою за використання, що відповідають умовам, можуть продовжувати використовувати глобальний баланс облікового запису, коли власного балансу недостатньо.

## Підготовка

- Створіть і безпечно збережіть [Account Token](https://platform.acedata.cloud/documents/platform-token).
- Отримайте `application_id` Application, яким ви володієте, зі [списку заявок на послуги](https://platform.acedata.cloud/documents/platform-application-list).

```shell
export PLATFORM_TOKEN='ваш токен облікового запису'
export APPLICATION_ID='ваш Application ID'
```

## Огляд інтерфейсу

| Параметр    | Вміст                                                                                                  |
| ---- | -------------------------------------------------------------------------------------------------- |
| Метод   | `POST`                                                                                             |
| URL  | `https://platform.acedata.cloud/api/v1/applications/{application_id}/update-allow-consume-global/` |
| Авторизація   | Account Token                                                                                      |
| Body | JSON                                                                                               |

```shell
curl -X POST \
  "https://platform.acedata.cloud/api/v1/applications/${APPLICATION_ID}/update-allow-consume-global/" \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"allow_consume_global": true}'
```

У разі успіху повертається оновлений об’єкт Application. Орієнтуйтеся на `allow_consume_global` у відповіді, а не припускайте, що значення запиту обов’язково було збережено.

> Application типу `Period` не дозволено використовувати глобальний баланс. Навіть якщо надіслати запит зі значенням `true`, сервер збереже для цього поля значення `false`.

## Обробка помилок

- `401`: Account Token недійсний або відсутній.
- `403`: Поточний обліковий запис не є власником цього Application.
- `404`: Application ID не існує.

Використовуйте фактичні плани, доступні в консолі платформи та повернуті під час [створення замовлення](https://platform.acedata.cloud/documents/platform-order-create), як джерело істини для поповнення глобального балансу та доступних пакетів; не припускайте, що існує пакет типу `Wallet`.

## Застосунки з авторизованим овердрафтом

Коли поле лише для читання `allow_overdraft=true` застосунку з оплатою за використання, цей застосунок може продовжувати списувати кошти з власного балансу, навіть якщо баланс стає від’ємним, і не перемикатиметься на глобальний обліковий запис через недостатній баланс. Застосунки без увімкненого овердрафту й надалі дотримуються `allow_consume_global`; чи дозволено овердрафт після перемикання, визначається налаштуванням фактичного глобального Application, з якого здійснюється списання.

## Обмеження паралельності для пробних облікових записів

Система використовує позначку користувача лише для читання `has_recharged`, щоб фіксувати, чи було успішно завершено платне поповнення або чи адміністратор вручну додав кредити; позначка оновлюється після успішного виконання операції, а для історичних користувачів вона буде уніфіковано заповнена на основі замовлень або явних записів про додавання кредитів. Для облікових записів, які не здійснювали платного поповнення та не отримували ручного додавання кредитів від адміністратора, в межах усього облікового запису одночасно дозволяється виконувати лише один платний запит; різні API Key і різні сервіси спільно використовують це єдине місце. Бонуси, картки обміну та передані ліміти не вважаються платним поповненням. Облікові записи, які вже завершили платне поповнення або отримали ручне додавання кредитів від адміністратора, не підпадають під це обмеження пробної паралельності й надалі дотримуються чинних перевірок балансу та лімітів облікових даних.

Коли наявний запит уже виконується, новий запит повертає `429 too_many_requests`. Безкоштовні інтерфейси опитування, такі як перевірка завдань, і надалі можна викликати нормально. Автентифікація підключень Realtime використовує наявний процес поетапного виставлення рахунків і не займає це місце для звичайних запитів.

Коли асинхронний інтерфейс повертає «прийнято», завдання все ще виконується, тому перед надсиланням наступного запиту на генерацію необхідно дочекатися остаточного результату. Розрив мережі або тайм-аут проксі не означає, що завдання вже зупинено; якщо завдання тривалий час не має кінцевого стану, надайте `trace_id` службі підтримки для перевірки.

Це обмеження не змінює доступні для пробного використання інтерфейси й не змінює наявні правила виставлення рахунків. Вартість, як і раніше, розраховується після завершення запиту на основі фактичного використання.
