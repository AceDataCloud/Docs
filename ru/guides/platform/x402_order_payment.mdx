Помимо прямой оплаты по API-запросам, Ace Data Cloud также поддерживает оплату заказов в консоли через X402. Основной протокол оплаты заказов и API-вызовов одинаков: первый запрос возвращает 402, клиент подписывает `PAYMENT-SIGNATURE`, затем повторяет тот же запрос.

Разница в том, что оплата заказов относится к API платформы и требует токена аккаунта; тогда как AI API, вызываемый напрямую через `x402.acedata.cloud`, может использовать только X402 и не требует API Token.

## Подготовка заказа

Перейдите в [консоль Ace Data Cloud](https://platform.acedata.cloud/console/orders), выберите заказ, который необходимо оплатить, и запишите ID заказа.

Если у вас ещё нет заказа, вы можете создать неоплаченный заказ на странице тарифов. Цена заказа определяется отображением на странице, а `amount` в ответе X402 402 является окончательным основанием для подписи.

## Создание токена аккаунта

Запросы на оплату заказов требуют токена аккаунта. Откройте [страницу Platform Token](https://platform.acedata.cloud/console/platform-tokens), создайте token в формате `platform-v1-...`.

В последующих запросах используйте:

```http
Authorization: Bearer {platform_token}
```

Токен аккаунта отличается от обычного API Token. Обычный API Token используется для потребления API-кредитов; токен аккаунта используется для операций с ресурсами платформы от имени вашего аккаунта, например для оплаты заказов.

## Вызов 402

Сначала отправьте один запрос без `PAYMENT-SIGNATURE`:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

Статус ответа будет 402, а ответ содержит `accepts`:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

Для оплаты заказов используется официальный x402 v2: `x402Version` равен `2`, `network` использует идентификатор CAIP-2, а поле суммы — `amount`.

Результат выполнения программы при создании заказа на 10 Credits и вызове 402:

> Следующие записи транзакций являются историческими фактическими образцами при старой политике, суммы и хеши транзакций сохранены без изменений. Для новых заказов X402 скидка за способ оплаты больше не применяется; используйте `amount` из текущего ответа 402 как основание для подписи и оплаты.

```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
error Payment required for this order.
accepts [
  ('eip155:8453', 'exact', '1200000', '0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000', '5iVXFrYaYWX2GUTbkQj8mDBoBhAX8bneYigS2LJTia43')
]
description Ace Data Cloud Credits x 10.0
```

Пояснение результатов:

- После успешного создания заказа его статус — `Pending`, в этот момент ещё нет оплаты в блокчейне.
- Первый запрос `pay/` не содержит `PAYMENT-SIGNATURE`, поэтому возвращается HTTP 402.
- `accepts` одновременно предоставляет Base `exact` и Solana `exact`; в дальнейшем в этом руководстве выбирается Base.
- Цена при создании заказа составляет `1.26`; при оплате в период действия старой политики скидок X402 фактическая сумма подписи и расчёта составляет `1.2` USDC, что соответствует `1200000` atomic USDC.

Обратите внимание, что `resource` — это поле, возвращаемое сервером и участвующее в подписи; клиент не должен самостоятельно изменять протокол, путь или ID заказа в нём.

## Подпись и повторная попытка

Для оплаты заказа можно повторно использовать низкоуровневые функции подписи из `@acedatacloud/x402-client` или `acedatacloud-x402`. Ниже приведён пример TypeScript:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

Результат выполнения программы после подписи и повторной попытки того же заказа с Base `exact`:

```text
status 200
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
has_x_payment_response True
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order {'id': '78481793-304e-47f7-bc0c-8231aec9cc1e', 'state': 'Finished', 'pay_way': 'X402', 'price': 1.2, 'pay_id': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}
```

Результат подтверждения в блокчейне:
```text

status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer {"from":"0x5d4f08D5c2bb60703284bc06671Eb680fA41B105","to":"0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7","value":"1200000"}
```

Пояснение результатов:

- `status 200` означает, что интерфейс оплаты заказа платформы принял эту `PAYMENT-SIGNATURE`.
- `has_x_payment_response True` означает, что заголовок ответа содержит закодированную в Base64 квитанцию `PAYMENT-RESPONSE`.
- `settle_header.success=True` и `network=base` означают, что Facilitator завершил settlement в Base.
- Итоговый статус заказа — `Finished`, `pay_way` — `X402`, `pay_id` содержит хеш транзакции в блокчейне.
- Событие `Transfer` в BaseScan показывает, что адрес плательщика перевёл `1200000` atomic USDC на адрес получения платежей платформы, то есть `1.2` USDC.

## Успешный ответ и квитанция

После успешной оплаты заказа тело ответа содержит информацию о заказе. Платформа также передаёт в заголовке ответа `PAYMENT-RESPONSE` закодированный в Base64 settlement response, который после декодирования обычно включает следующие поля:

| Поле            | Описание                           |
| ------------- | ---------------------------- |
| `success`     | Был ли settlement Facilitator успешным. |
| `transaction` | Хеш транзакции settlement в блокчейне.                    |
| `network`     | Платёжная сеть.                        |
| `payer`       | Адрес кошелька плательщика.                      |
| `amount`      | Фактическая сумма settlement в atomic units.      |

Если вам требуется сверка, рекомендуется одновременно сохранять ID заказа, адрес кошелька плательщика, `transaction` и итоговый статус заказа.

## Примечания

- Для оплаты заказа требуется токен учётной записи платформы, нельзя завершить её, используя только подпись X402-кошелька.
- `amount` использует USDC atomic units, `1200000` означает `1.2` USDC.
- Не формируйте адрес получения платежа или адрес актива самостоятельно, ориентируйтесь на `accepts` в ответе 402.
- Если одна и та же `PAYMENT-SIGNATURE` отправляется повторно, Facilitator применяет защиту от повторного воспроизведения по nonce.

## Ответ при неудачной оплате

Первый HTTP 402 без `PAYMENT-SIGNATURE` является нормальным платёжным вызовом и не означает неудачу оплаты. При сбое проверки или settlement после подписи стандартная строка `error` всё ещё сохраняется как совместимый резервный вариант, а стабильная структура ошибки возвращается в `extensions.acedatacloud.paymentError`:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

Клиент должен в первую очередь локализовать по `code`, а для неизвестных code использовать общее сообщение о неудаче оплаты. `charged` — трёхсоставное поле: `false` возвращается только при явном отклонении до settlement; отсутствие поля означает, что статус списания неизвестен, и не может интерпретироваться как «средства не списаны». После перехода текущего заказа в `Failed` повторить оплату того же заказа нельзя; исправьте проблему с кошельком и создайте новый заказ.

`metadata.x402.last_error` и `metadata.x402.errors` в списке и деталях заказов сохраняют тот же набор `code`, `stage`, `retryable`, `charged` и `params`; публичный пояснительный текст сохраняется в `reason`, а время возникновения — в `timestamp`. Например, `insufficient_token_balance` означает недостаточный баланс USDC в выбранной сети, а `invalid_signature` означает недействительную платёжную подпись; повторное чтение заказа не изменит их на универсальный `payment_failed`.

Не записывайте и не отправляйте полную `PAYMENT-SIGNATURE`, подпись кошелька, payload авторизации, исходную диагностику Facilitator или RPC-ответы. Для проверки службе поддержки достаточно ID заказа и публичного `code` ошибки.

## Выкуп и сжигание ACE для платежей Base и Solana

После включения стратегии выкупа 3% от фактически полученных соответствующих требованиям Circle USDC в основной сети Base и USDC в основной сети Solana используются для покупки и сжигания ACE без дополнительного списания средств с кошелька плательщика. Начисление происходит один раз при пополнении, а при последующем использовании этих Credits для вызова API повторного начисления не происходит; к историческим заказам со скидкой и заказам со старой стратегией начисление задним числом автоматически не применяется.

Платежи Base сохраняют квитанцию о платеже в сети Base, а покупка и сжигание ACE выполняются асинхронно в Solana. Для соответствующих требованиям платежей точно начисляется 3% от фактически полученной суммы, без фиксированного лимита суммы выкупа на одну транзакцию или в день; доступные средства, рыночные котировки и подтверждения в блокчейне всё ещё могут влиять на время завершения. Объект `ace_burn` в деталях заказа предоставляет `settlement_network`, `settlement_transaction` и `execution_network`, а после завершения — `swap_signature` и `burn_signature`. `Pending` или `Processing` не означает, что сжигание уже выполнено; только `Completed` означает, что окончательное доказательство в блокчейне проверено. Если платёж Base ещё не достиг окончательного подтверждения, выкуп ожидает подтверждения, но это не влияет на уже зачисленные Credits.
