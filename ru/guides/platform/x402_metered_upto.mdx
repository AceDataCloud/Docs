---
title: "Схемы выставления счетов X402 `exact` и `upto`"
description: "Platform API guide - Ace Data Cloud"
---

Ace Data Cloud X402 в настоящее время использует два типа схем: `exact` и `upto`. Они решают разные задачи выставления счетов.

## `exact`

`exact` означает, что цену данного запроса можно определить до его поступления в целевой API. Сумма, подписанная клиентом, является итоговой суммой списания.

Подходит для:

- Генерации изображений с фиксированной ценой;
- Создания видеозадач с фиксированной ценой;
- Поисковых или инструментальных API с фиксированной ценой;
- Оплаты заказов.

EVM `exact` использует USDC EIP-3009 `TransferWithAuthorization`:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": {
    "authorization": {
      "from": "0x...",
      "to": "0x...",
      "value": "95215",
      "validAfter": "1780237345",
      "validBefore": "1780240945",
      "nonce": "0x..."
    },
    "signature": "0x..."
  }
}
```

Facilitator на этапе `/verify` проверяет подпись и сумму, а на этапе `/settle` отправляет эту авторизацию в блокчейн.

## `upto`

`upto` означает, что клиент авторизует максимальный верхний предел, а Ace Data Cloud после завершения запроса производит расчёт по фактическому использованию; фактическое списание не может превышать верхний предел.

Подходит для:

- Чат-дополнений: итоговая цена зависит от prompt tokens и completion tokens;
- Потоковых ответов: фактическая длина вывода становится известна только после завершения;
- Будущих API с постфактумным учётом.

`upto` использует Permit2 `PermitWitnessTransferFrom`. Клиент подписывает не фиксированный перевод, а авторизацию верхнего предела с witness:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2Authorization": {
      "from": "0x...",
      "spender": "0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002",
      "nonce": "123456789",
      "deadline": "1780240945",
      "permitted": {
        "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "amount": "95215"
      },
      "witness": {
        "to": "0x...",
        "facilitator": "0x...",
        "validAfter": "1780237345"
      }
    },
    "signature": "0x..."
  }
}
```

`permitted.amount` является верхним пределом и не обязательно является итоговым списанием. Gateway на этапе `/record` преобразует фактическое использование в `amount` и передаёт его Facilitator. Facilitator разрешает расчёт только при `amount &lt;= permitted.amount`.

Результат выполнения программы Base `upto`:

```text
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
elapsed_ms 5104
content ADC_BASE_UPTO_OK
id chatcmpl-DlcbyS4IT8kUAMo4Ri97HiIHc9T8V
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Пояснение:

- Верхний предел авторизации, возвращаемый в 402, составляет `95215` atomic USDC, клиент подписывает этот верхний предел.
- После фактического ответа модели рассчитывается только `3` atomic USDC, транзакция в блокчейне доступна для проверки на BaseScan.
- Этот результат показывает ключевое различие `upto`: подписанная сумма является верхним пределом, а settlement в блокчейне может быть меньше верхнего предела.
- Если фактическое использование превышает верхний предел, Facilitator должен отклонить settlement, и клиенту необходимо повторно авторизовать более высокий верхний предел.

`upto` в настоящее время предоставляется только в Base. Если требуется постфактумный учёт, используйте Base.

## Почему нужен Permit2 approve

В конечном итоге `upto` позволяет x402 proxy получать USDC из кошелька плательщика через Permit2. Перед первым использованием кошелёк плательщика должен один раз предоставить Permit2 ERC-20 allowance.

Python CLI:

```bash
pip install 'acedatacloud-x402[cli]'
X402_PRIVATE_KEY=0x... acedatacloud-x402 approve-permit2 --network base
```

Программный способ:

```python
from acedatacloud_x402 import EVMAccountSigner, approve_permit2

approve_permit2(
    rpc_url="https://mainnet.base.org",
    signer=EVMAccountSigner.from_private_key("0x..."),
    token_address="0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
)
```

После завершения авторизации для каждого запроса всё равно необходимо подписывать новый `upto` envelope, поскольку nonce, deadline, witness и верхний предел суммы различаются.

## Расчёт с нулевой суммой

`upto` поддерживает случаи, когда фактическая сумма равна 0. Например, если целевой API не смог успешно создать тарифицируемое использование, Gateway может передать `amount = "0"`. Facilitator вернёт успех, но не будет отправлять транзакцию в блокчейн.

Это позволяет избежать проблемы «запрос не был успешным, но комиссия в блокчейне всё равно списана».

## Рекомендации по выбору

| Сценарий                   | Рекомендация                       |
| -------------------------- | ---------------------------------- |
| API с фиксированной ценой  | Используйте `exact`, логика проста. |
| Оплата заказов             | Используйте `exact`.               |
| Чат-дополнения, тарификация по token | Используйте Base `upto`. |
| Permit2 approve ещё не выполнен | Сначала запустите `exact`, затем перейдите на `upto`. |

Если вы не уверены, что выбрать, сначала используйте поведение SDK по умолчанию; SDK выберет соответствующее требование к оплате сети, возвращённое сервером.

## Контрольный список Base `upto`

При интеграции или устранении неполадок убедитесь, что следующие параметры получены из одного и того же ответа 402 и остаются согласованными при подписании клиентом:

| Параметр                   | Контрольная точка                                          |
| -------------------------- | ---------------------------------------------------------- |
| `network`                  | Должен быть `eip155:8453`.                                 |
| `scheme`                   | Должен быть `upto`.                                        |
| `extra.chainId`            | Base chain id равен `8453`.                                |
| `asset`                    | Используйте адрес контракта Base USDC из ответа 402.        |
| `extra.facilitatorAddress` | Должен участвовать в witness и совпадать с Facilitator `/supported`. |
| Permit2 allowance          | Кошелёк плательщика должен сначала авторизовать Permit2 для Base USDC. |

Распространённые ошибки и способы обработки:

| Ошибка                                        | Способ обработки                                                                          |
| --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `invalid_upto_evm_payload_invalid_signature` | Проверьте, совпадают ли chain id, адрес facilitator, Permit2 domain, spender, аккаунт подписи и witness с ответом 402. |
| `PERMIT2_ALLOWANCE_REQUIRED`                  | Выполните Permit2 approve для USDC целевой сети, затем повторно отправьте запрос.         |
| `amount exceeds permitted amount`             | Фактическое использование превышает подписанный верхний предел, необходимо повторно подписать более высокий верхний предел. |
