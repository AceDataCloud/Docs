[X402](https://www.x402.org/) — это предложенный Coinbase протокол ончейн-платежей «оплата по HTTP 402»: сервер возвращает `402 Payment Required` на запросы без token, прикладывая поле `accepts: [...]` со списком принимаемых сетей / активов / цен; клиент локально подписывает авторизацию (на EVM это Permit2 / EIP-712, на Solana — авторизация перевода SPL token), помещает base64-encoded envelope в заголовок `PAYMENT-SIGNATURE` и отправляет запрос повторно. После проверки сервер действительно выполняет ончейн-расчёт, а затем возвращает бизнес-результат.

> X402-клиент Ace Data Cloud напрямую вызывает целевой API и использует возвращаемые этим запросом в реальном времени `402 Payment Required` и `accepts` как основу для цены и подписи. Платёжные возможности Facilitator можно проверить через [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

И `@acedatacloud/sdk`, и `acedatacloud` предоставляют хук `paymentHandler`: когда запрос, отправленный самим SDK, получает `402`, вызывается внедрённый вами handler для получения заголовка `PAYMENT-SIGNATURE`, после чего исходный запрос отправляется повторно. Используйте `@acedatacloud/x402-client` / `acedatacloud-x402` вместе с SDK, и **весь процесс будет полностью прозрачен для бизнес-кода** — вам достаточно вызвать `client.openai.chat.completions.create(...)`, внешне это выглядит точно так же, как режим token, но под капотом это оплата за вызовы без необходимости предварительного пополнения.

В этой статье:

- Реально пройдена TS-цепочка «без token + внедрение X402 handler» ([проверка T12](#四真实运行验证))
- Перечислены различия между двумя цепочками подписания EVM / Solana
- Приведены три адаптации: режим приватного ключа `viem`, режим браузерного кошелька и Python-режим `EVMAccountSigner`
- Разъяснено легко вызывающее проблемы поле `preferScheme` / `prefer_scheme`

## I. Обзор протокола (обязательно к прочтению)

Один успешный X402-вызов включает **3 HTTP RTT**:

```text
1. SDK -> /openai/v1/chat/completions               (无 Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK 内部 -> paymentHandler({ url, method, body, accepts })   (本地签名，0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (PAYMENT-SIGNATURE 头注入)
   <- 200 + business response   (结算在服务端完成)
```

X402 envelope — это JSON, который после base64-кодирования помещается в заголовок `PAYMENT-SIGNATURE`. Структура (фрагмент):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

На верхнем уровне envelope находится `x402Version: 2`, а объект `accepted` объявляет выбранные для этого раза `scheme` и `network` (идентификатор CAIP-2).

| scheme  | Значение                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Фиксированная цена (сценарии с установленной ценой, такие как генерация изображений / видео, поиск и т. д.). Подписываемая сумма = сумма, требуемая сервером.                                                         |
| `upto`  | Тарификация по потреблению (chat completions / token-подобные сценарии). Подписывается сумма-**лимит**, фактически списывается только использованная часть (на основе Permit2 + witness). **Настоятельно рекомендуется** для API сессий. |

`preferScheme` / `prefer_scheme` используется для выбора предпочтения, когда сервер **одновременно предоставляет несколько scheme**. Если сервер публикует только `exact`, это поле будет проигнорировано; если задано `upto`, но сервер его не публикует, произойдёт откат к первому совпадающему варианту.

## II. TypeScript: два способа — браузерный кошелёк + серверный viem

### Установка

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Протестированные номера версий:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Полная сигнатура `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' 必填
  evmProvider?: EVMProvider;                // network='base' 必填，EIP-1193
  evmAddress?: string;                      // network='base' 必填
  preferScheme?: 'exact' | 'upto';
}
```

Возвращаемое значение — `(ctx) => Promise&lt;{ headers: Record<string, string> }>`, что точно соответствует сигнатуре хука `paymentHandler` SDK.

### Вариант 1: браузер (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. 让用户连钱包
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. 切到 Base 主网
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. 构造 SDK 客户端，注入 X402 handler
//    注意：不传 apiToken，让 SDK 走 402 路径
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat 类必选 upto
  })
});

// 4. 正常调
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

При первом вызове браузер покажет **два запроса на подпись**: первый — одноразовый approve Permit2 для USDC (сумма — `MaxUint256`, записывается в сеть); второй — EIP-712-подпись X402 envelope (не записывается в сеть, нужна только для проверки facilitator). В последующих вызовах потребуется только вторая подпись, то есть по ощущениям это «один клик подписи → получить результат».

### Вариант 2: Node-сервер + приватный ключ viem (подходит для бэкенда / CLI)

`@acedatacloud/x402-client` на TS-стороне **принимает только EIP-1193 provider** — он не управляет приватными ключами напрямую. В сценариях Node / CLI стандартный подход — упаковать приватный ключ в `WalletClient` с помощью [`viem`](https://viem.sh/), а затем использовать EIP-1193-адаптацию из [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) или внутреннюю адаптацию viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// viem WalletClient has EIP-1193-compatible .request() built in and can be directly used as evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request satisfies EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> If you feel viem's EIP-1193 adaptation is not stable enough, you can also use the lower-level [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts) and wire together the `accepts → signed envelope → PAYMENT-SIGNATURE header` path yourself, bypassing the SDK hook; however, it is still recommended to prioritize `createX402PaymentHandler`, so you do not have to maintain protocol upgrades yourself.

### Usage 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

On the Solana chain, currently **only the `exact` scheme is exposed**, so `preferScheme` does not take effect on Solana.

## III. Python: Private Key Mode

Python's `acedatacloud-x402` uses the approach of **signing directly with the private key** (without an EIP-1193 abstraction), making it more suitable for servers / task executors.

### Installation

```bash
pip install acedatacloud acedatacloud-x402
```

Tested version numbers:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. Construct a signer from the private key
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. Construct the SDK: do not pass api_token, allowing the SDK to use the 402 path
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # chat-type calls must use upto
    )
)

# 3. Call normally
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # optional
    )
)
```

### One-Time Approve (EVM First Time Only)

X402 on EVM Base uses Permit2, requiring the wallet to perform a one-time `MaxUint256` approve for USDC to the Permit2 contract. `acedatacloud-x402` includes `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

This transaction only needs to be sent once; all subsequent X402 EVM payments use this authorization. Solana does not need it.

## IV. Real Runtime Verification

Test objective: **the TS SDK does not pass a token, injects an X402 handler, and can normally construct and initiate requests** (a lightweight verification that does not consume real on-chain USDC).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // placeholder provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Output:

```text
handler_type function
client_ctor_ok AceDataCloud
```

The results indicate:

- No `apiToken` was passed, and SDK construction **does not throw an error**, proving that X402 mode is indeed a valid alternative to a token.
- `createX402PaymentHandler` returns a function (hook), which the SDK calls only upon receiving a 402 response.
- The end-to-end test for actual on-chain payment was not included in this tutorial because it involves real USDC deductions; you can refer to the e2e example in the [X402 Integration Guide](https://platform.acedata.cloud/documents/x402-integration).

> The Python-side `create_x402_payment_handler` performs the same verification — the function return value is callable, and constructing `AceDataCloud(...)` does not throw an error when injecting `payment_handler=...`. The semantics are aligned on both sides.

## V. Comparison with “Bearer Token Mode”

| Dimension              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Applicable scenarios            | Your own backend, long-term projects                                                         | Third-party developers, pay-per-use, Agentic calls                        |
| Registration              | Requires application through the [console](https://platform.acedata.cloud/console/applications) | Not required; only an on-chain wallet is needed                                     |
| Billing precision            | Prepaid, charged according to the token price list                                                   | Settled on-chain in real time per call                                         |
| Balance              | Can be viewed in the console                                                           | Check the on-chain wallet USDC                                      |
| Initial cost            | Free credits are provided upon email registration                                                        | Requires bridging USDC to Base and an initial Permit2 approve              |
| Suitable for chat-type calls       | ✅                                                                 | ✅ (must use `preferScheme=upto`)                       |
| Suitable for one-time payment / cross-account sponsored payment | ❌                                                                 | ✅                                               |
| Code changes            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Два режима могут сосуществовать — в одном и том же процессе достаточно настроить разные способы аутентификации для разных экземпляров `client`.

## VI. Распространённые ошибки

1. **Для chat-классов обязательно `preferScheme=upto`**: использование `exact` заставит facilitator списывать USDC по `maxAmountRequired` (а не по фактическому потреблению).
2. **На стороне Node не передавайте голый приватный ключ в `createX402PaymentHandler`**: TS-пакет не принимает `{ privateKey }`, его обязательно нужно обернуть в EIP-1193 provider (рекомендуется viem `WalletClient`).
3. **Первый вызов требует двойной подписи**: первая подпись — Permit2 approve (он-чейн, с gas), вторая подпись — X402 envelope (не он-чейн). В последующих вызовах остаётся только вторая.
4. **В Solana нет концепции Permit2**: авторизация перевода SPL token подписывается напрямую, approve не требуется; однако в настоящее время в сети Solana поддерживается только `exact`.
5. **Различайте ошибки бизнеса и ошибки платежа**: 402 → сбой handler выбрасывает `X402SignError` (конкретный тип зависит от сети); ошибки бизнес-интерфейса после последующей повторной отправки (401 / 422 / 5xx) по-прежнему классифицируются как обычные исключения SDK.
6. **Самый стабильный способ адаптации `viem`**: `evmProvider: walletClient as any` лишается проверки типов, но обладает наилучшей совместимостью; если нужно сохранить типы, отдельно оберните `.transport.request` из viem в объект `{ request }` и передайте его.
