---
title: "Подключение Ace Data Cloud OAuth 2.0"
---

Разрешите пользователям авторизовать ваше приложение для доступа к их профилю Ace Data Cloud, подпискам на сервисы, API Key, использованию или заказам. Используйте стандартный **Authorization Code + S256 PKCE**: приложение открывает страницу авторизации, пользователь соглашается и получает одноразовый `code`, который затем обменивается на OAuth access token.

OAuth access token используется для доступа к интерфейсам ресурсов аккаунта; для вызова API моделей используется соответствующий API Key. OAuth-авторизация не создаёт автоматически API Key, не подключает сервисы и не увеличивает баланс.

## Выберите способ подключения

| Способ            | Сценарий применения                                | После завершения авторизации                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Стандартный OAuth-переход   | Независимый веб-сайт, настольный или мобильный клиент; встроенный сайт самостоятельно инициирует авторизацию            | Браузер возвращается на зарегистрированный приложением `redirect_uri`, приложение обрабатывает `code` и `state` |
| Авторизация через компонент сайта Studio | Сайт встраивает главную страницу Studio и хочет использовать текущий аккаунт Studio посетителя | Studio отправляет приложению сообщение с результатом авторизации, приложение не выполняет переход, исходная страница сохраняется                  |

Стандартный переход не требует `embed=studio`, `embed_origin` или `postMessage`. В режиме компонента Studio хост создаёт страницу авторизации и поддерживает мост сообщений; третьи стороны подключаются согласно протоколу компонента в конце этой статьи, не формируйте эти два параметра самостоятельно.

## Эндпоинты и документ обнаружения

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Назначение                | Адрес                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Страница авторизации в браузере            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| Получение／обновление OAuth token | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Отправка запроса на отзыв            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Информация о текущем пользователе            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| Страница управления OAuth-приложениями      | [OAuth-приложения](https://auth.acedata.cloud/user/oauth-apps)                            |
| Список приложений／интерфейс регистрации для вошедшего пользователя   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Публичные сведения о приложении, используемые страницей авторизации      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Существующие API Key пользователя     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<ID пользователя>&limit=100` |

Интерфейс управления приложениями требует аутентификации аккаунта и не является интерфейсом анонимной динамической регистрации (DCR). Собственные адреса обнаружения／регистрации MCP-сервисов и OAuth-эндпоинты аккаунта из этой таблицы являются разными входами; при подключении к конкретному MCP действуйте согласно документации и результатам обнаружения этого сервиса.

Документ обнаружения используется для получения эндпоинтов и возможностей протокола. Текущий процесс возвращает OAuth token, но не возвращает `id_token`; не обрабатывайте его как полноценный процесс входа OpenID Connect только из-за наличия scope `openid`.

## Области разрешений: используйте текущие имена scope

`scope` — это разделённые пробелами, чувствительные к регистру имена разрешений. Новые приложения используют конкретные разрешения, такие как `profile:read`, `email:read`, `phone:read`.

### Где получить доступные для запроса разрешения

После входа интерфейс списка OAuth-приложений `GET /api/v1/oauth2/applications/` возвращает `available_scopes`; селектор разрешений на странице управления приложением использует тот же каталог. Это доступные области, которые должны использовать обычные самостоятельные приложения.

**`scopes_supported` в Discovery содержит все имена разрешений, распознаваемые платформой, и не означает, что ваше приложение может запросить каждое из них.** Фактическая авторизация одновременно проверяет:

1. разрешено ли делегирование разрешения этому типу приложения;
2. зарегистрировано ли разрешение в разрешённых областях этого OAuth-приложения;
3. имеет ли текущий пользователь запрашиваемое разрешение.

Неизвестные, незарегистрированные, неразрешённые для делегирования разрешения или разрешения, которыми пользователь не обладает, возвращают `invalid_scope`. При обмене кода авторизации и обновлении также выполняется повторная проверка; разрешения не будут автоматически дополнены или повышены.

### Доступные разрешения для обычных самостоятельных приложений

Ниже приведён текущий каталог (2026-10-09); при подключении ориентируйтесь на `available_scopes`.

| Scope                                            | Назначение                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Чтение／обновление профиля                               |
| `email:read`                                     | Чтение электронной почты                                    |
| `phone:read`                                     | Чтение номера телефона и региона                                |
| `billing-profile:read` / `billing-profile:write` | Чтение／управление платёжными данными                               |
| `applications:read` / `applications:write`       | Чтение／управление подписками на сервисы                               |
| `credentials:read` / `credentials:write`         | Чтение／управление API Key                           |
| `usage:read`                                     | Чтение записей об использовании                                  |
| `orders:read` / `orders:write`                   | Чтение／создание и управление заказами                              |
| `auto-recharge:read` / `auto-recharge:write`     | Чтение／управление настройками автоматического пополнения                             |
| `recharge-cards:redeem`                          | Погашение карт пополнения                                   |
| `coin:read`                                      | Чтение информации, связанной с токенами                                |
| `distribution:read`                              | Чтение информации о дистрибуции                                  |
| `connections:read` / `connections:write`         | Чтение／управление подключениями                                 |
| `skills:read` / `skills:write`                   | Чтение／управление навыками                                 |
| `openid`                                         | Текущая реализация также позволяет UserInfo возвращать основные данные; ID Token не возвращается    |
| `offline_access`                                 | Запрос refresh token для обновления после истечения access token |

Например, для чтения только профиля используйте `profile:read`; если также нужна электронная почта, добавьте `email:read`; для чтения существующих API Key используйте `profile:read credentials:read`. Запрашивайте `credentials:write` только если действительно необходимо создавать или изменять Key, а `offline_access` добавляйте только при необходимости обновления.

Некоторые разрешения предназначены только для доверенных приложений, одобренных платформой, например `sites:read`, `sites:write`, `platform-tokens:read`; другие разрешения не открыты для обычных сторонних OAuth-приложений. Тип клиента `public`／`confidential` описывает, может ли он хранить secret, и не связан с тем, является ли приложение доверенным. Самостоятельно созданные приложения не могут включать доверенные разрешения самостоятельно.

`account` — это селектор разрешений аккаунта, используемый указанным официальным MCP управления аккаунтом, а не scope «все разрешения» для сторонних приложений; его нельзя смешивать с другими scope. Третьи стороны должны явно перечислять необходимые конкретные разрешения.

### Миграция со старой документации

| Старое написание                                         | Текущий способ подключения                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | По пунктам перечислите фактически необходимые конкретные разрешения, универсальной замены «выбрать всё» нет |

Старые имена не принимаются в качестве совместимых псевдонимов. Одновременно обновите scopes, зарегистрированные для OAuth-приложения, URL авторизации и собственную проверку разрешений; изменение конфигурации приложения не добавляет разрешения уже выданным token, пользователю необходимо повторно авторизоваться.

## Шаг 1: зарегистрируйте OAuth-приложение

Откройте [управление OAuth-приложениями](https://auth.acedata.cloud/user/oauth-apps), создайте приложение и заполните:
- Название, описание, логотип приложения: отображаются на стороне приложения на странице авторизации.
- Тип клиента: для чистого фронтенда, мобильных или десктопных клиентов выберите **Public**; для сервисов, которые могут хранить secret на бэкенде, выберите **Confidential**.
- Адрес обратного вызова: в production используйте HTTPS и зарегистрируйте полный URL, по которому приложение действительно обрабатывает callback.
- Права: выберите из предоставленного на странице каталога scopes, которые действительно нужны.

Сохраните `client_id`. Confidential-клиенты хранят `client_secret` на серверной стороне; его нельзя помещать в HTML, переменные фронтенд-сборки или URL. Public-клиенты не используют secret при получении token; даже если ответ регистрации содержит это поле, нельзя считать его учётными данными, которые клиент способен хранить в секрете.

`redirect_uri` при регистрации, авторизации и получении token должен точно совпадать, включая путь, завершающий слеш и параметры запроса. Каждая учётная запись может создать не более 20 приложений. Secret отображается только при создании／ротации; после ротации старый secret больше нельзя использовать для обменов, требующих аутентификации клиента.

## Шаг 2: кнопка запускает авторизацию

При каждом нажатии подключения генерируйте новые случайные `state` и `code_verifier`, вычисляйте:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Сохраните `state`, verifier и адрес обратного вызова в собственной сессии приложения, затем откройте страницу авторизации с параметрами в URL-кодировке:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<完整回调地址>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<本次随机值>
  &code_challenge=<本次S256挑战值>
  &code_challenge_method=S256
```

Public-клиенты обязательно должны отправлять S256 PKCE. Хотя Discovery также перечисляет `plain`, Public-клиенты не могут его использовать. Confidential-клиентам также рекомендуется использовать S256; если PKCE использовался при запуске авторизации, при обмене обязательно нужно передать соответствующий verifier.

После согласия пользователя происходит возврат на `redirect_uri`, а параметры запроса содержат `code` и возвращённый без изменений `state`. При отказе возвращаются `error=access_denied`, описание ошибки и `state`. Перед обработкой callback сначала проверьте, что state соответствует текущей сессии. Срок действия кода авторизации составляет 10 минут, и его можно обменять только один раз; после ошибки следует заново начать подключение, не обновляйте многократно старый callback URL.

## Шаг 3: получение OAuth token

Public-клиенты выполняют обмен непосредственно из браузера или клиента; Confidential-клиенты выполняют обмен на собственном бэкенде. Тело запроса поддерживает form-кодирование, следующие переменные представляют данные, полученные приложением в текущей авторизации:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Confidential-клиентам также необходимо добавить поле формы `client_secret` на серверной стороне. В настоящее время поддерживается `client_secret_post`; не считайте HTTP Basic-аутентификацию клиента поддерживаемым способом.

В успешном ответе прочитайте `access_token`, `token_type`, `expires_in` и фактически предоставленный `scope`. `refresh_token` будет только при запросе и предоставлении `offline_access`. Не используйте OAuth access token как API Key модельного API и не записывайте token, verifier или код авторизации в логи, аналитические события или ссылки для общего доступа.

## Шаг 4: чтение информации о пользователе и API Key

Сначала запросите UserInfo с помощью OAuth access token:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Возвращаемые поля зависят от scope: `id` является идентификатором пользователя; `profile:read` или `openid` позволяют читать базовые сведения (такие как `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`); для email требуется `email:read`, для номера телефона и региона требуется `phone:read`. Не полагайтесь на то, что неавторизованные поля всегда присутствуют.

Если требуется существующий API Key и предоставлен `credentials:read`, используйте `id` из UserInfo в качестве условия фильтрации:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Возвращаемый список использует `count` и `items`, поле Key — **`items[*].token`**, а не `data[0].value`. `user_id=me` не является допустимым пользовательским ID для этого интерфейса. Для многостраничных данных продолжайте чтение с помощью `offset`／`limit`, не считайте первую страницу всеми учётными данными.

Выбирайте подходящие учётные данные в соответствии с приложением, сервисом и действительным статусом, не берите вслепую первую запись. Пустой список не означает ошибку авторизации; пользователь, возможно, ещё не создал подходящий Key. Управление правами OAuth access token и собственная область сервисов, квоты и условия истечения срока действия API Key — это разные ограничения.

**Разрешение на чтение API Key означает, что третья сторона может сохранить и использовать его. Отзыв OAuth-запроса или очистка состояния входа приложения не сделают уже скопированный API Key недействительным; пользователю необходимо отдельно отозвать или ротировать этот Key в управлении учётными данными.**

## Запускаемый браузерный пример Public / PKCE

Разверните следующую страницу по зарегистрированному вами `REDIRECT_URI`, замените `CLIENT_ID` и адрес обратного вызова. Кнопка запускает стандартную авторизацию, а после возврата на ту же страницу считываются личные данные и количество существующих Key. Пример не отображает и не сохраняет Key; production-приложения используют результаты в соответствии с фактическими целями. Сначала проверьте на отдельной странице браузера, затем выполните приёмку в соответствии с последующими требованиями к iframe.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Подключение Ace Data Cloud</title>
<button id="connect" type="button">Подключить аккаунт</button>
<p id="status" role="status">Ещё не подключено</p>
<script type="module">
const CLIENT_ID = 'Замените на ваш client_id';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`API вернул HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = 'Не удалось начать подключение, проверьте настройки хранилища браузера и повторите попытку.';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('Сеанс авторизации не совпадает, подключитесь заново.');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('Сеанс авторизации истёк, подключитесь заново.');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('Авторизация не завершена, можно подключиться заново.');
    if (!code) throw new Error('В callback отсутствует код авторизации, подключитесь заново.');
    status.textContent = 'Подключение…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('Не получен токен авторизации.');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('Не получен идентификатор пользователя.');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('Формат списка учётных данных не соответствует.');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `Подключено: ${profile.nickname || profile.username || profile.id}; на этой странице ${keyCount} API Key.`;
  } catch (error) {
    status.textContent = `Подключение не завершено: ${error.message || 'сетевая ошибка'} Нажмите подключение ещё раз.`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Callback и точка входа в примере должны находиться в одном origin, в той же вкладке браузера／iframe, чтобы можно было прочитать ранее сохранённый `sessionStorage`. В production-приложениях токены следует управлять в рамках собственной схемы сессий, обрабатывать истечение срока действия и очищать параметры URL авторизации после получения ответа; основной интерфейс страницы должен быть отрисован первым, а сбой сети должен влиять только на статус подключения.

## iframe на white-label сайте

### Сайт клиента самостоятельно перенаправляет на страницу авторизации

Достаточно использовать стандартные OAuth-параметры и собственную обработку callback; `window.location.assign()` навигирует текущий iframe, а родительская страница остаётся на white-label домене. Не нужно добавлять `embed=studio` ради иконки или реализовывать протокол сообщений Studio.

Необходимо выполнить следующие условия:

- Страница приложения и страница callback используют HTTPS, фактически доступны и разрешают встраивание через iframe белому родительскому домену; проверьте у обеих сторон `Content-Security-Policy: frame-ancestors` и `X-Frame-Options`.
- Sandbox разрешает необходимые странице скрипты, формы и возможности origin／хранилища. При поддержке входа через всплывающие окна также требуются соответствующие возможности всплывающих окон; предпочтительно использовать конфигурацию компонента Website, предоставляемую Studio.
- Браузер разрешает хранилище, необходимое для состояния авторизации, в текущем сценарии встраивания. Состояние входа на white-label сайте и состояние входа в AuthFrontend могут различаться; не следует предполагать, что вход на white-label сайт означает вход на страницу авторизации.
- Сервис обмена token в callback доступен, междоменные запросы разрешают origin приложения; DNS, CORS, HTTP-ошибки должны отображать состояние с возможностью повторной попытки и не должны останавливать отрисовку всей страницы.

Левая сторона страницы авторизации получает OAuth Logo приложения; правая сторона получает favicon／logo этого Site, когда браузер может предоставить родительский origin и родительский домен проходит проверку верифицированного сайта, иначе отображается иконка по умолчанию. Это определяет только отображение бренда, не создаёт сеанс входа и не предоставляет разрешения аккаунта странице клиента.

**Текущее ограничение: при необходимости повторного входа обычный OAuth внутри iframe всё ещё имеет пробел в процессе продолжения возврата на страницу авторизации после завершения входа.** Перед запуском необходимо отдельно принять сценарии «Auth уже выполнен» и «Auth не выполнен／истёк». До устранения и проверки этого пробела для первого входа можно использовать отдельную страницу для выполнения стандартного OAuth либо авторизацию через компонент Studio ниже; не обещайте работоспособность всех iframe-сценариев, основываясь только на результатах тестирования в состоянии выполненного входа.

### Использование авторизации текущего аккаунта Studio

В Studio откройте OAuth в разделе «Настройки → Главная → Компоненты сайта», укажите `client_id` и зарегистрированный callback-адрес. Сайт и callback должны использовать один и тот же HTTPS origin и отличаться от origin Studio. Сторонней странице необходимо:

1. Отправить `acedatacloud:oauth:ready` в origin точного родительского сайта, получить и проверить `acedatacloud:oauth:init`.
2. Кнопка генерирует state и PKCE verifier, отправляет `acedatacloud:oauth:authorize` (state, S256 challenge); verifier остаётся внутри собственной страницы.
3. Проверить родительское окно, origin и state, обработать code или error в `acedatacloud:oauth:result` и обменять их через стандартный token endpoint.
Studio отображает страницу авторизации в области компонента, после согласия пользователя код авторизации возвращается сообщением, приложению не требуется перенаправление. При отсутствии входа возвращается `login_required`, при отказе возвращается `access_denied`, при тайм-ауте ожидания возвращается `authorization_timeout`. При смене аккаунта iframe приложения пересоздаётся, а незавершённые авторизации отменяются.

Компонент в настоящее время запрашивает `profile:read credentials:read` и не включает `offline_access`. Не предполагавайте, что refresh token обязательно будет получен. `embed=studio`, `embed_origin` поддерживаются хостом Studio и страницей авторизации, клиентской странице нужно только соблюдать протокол сообщений.

Полный пример кнопки см. в [Руководстве по интеграции OAuth для компонентов сайта Studio](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md)。

## Жизненный цикл, обновление и отзыв

Срок действия access token по умолчанию составляет 15 дней, обновление или повторную авторизацию следует планировать по `expires_in` из каждого ответа; срок действия refresh token по умолчанию составляет 30 дней, срок зависит от конфигурации сервиса. Не следует жёстко задавать эти два значения как постоянные гарантии.

После получения `offline_access` можно вызвать:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Обновление возвращает новые token, приложение должно сохранять последние значения. При обновлении проверяется, остаётся ли приложение действительным, доступен ли пользователь и по-прежнему ли предоставлены разрешения. При сбое очистите собственное состояние подключения и выполните повторную авторизацию.

**Текущая реализация OAuth-обновления не гарантирует немедленную недействительность старого refresh token после обновления.** Не считайте получение нового token подтверждением отзыва старого token и не заменяйте прекращение действия существующих token ротацией secret.

Способ вызова запроса отзыва:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Текущий endpoint отзыва возвращает HTTP 200, но не реализует немедленную недействительность уже выпущенных JWT.** Приложение должно удалить сохранённые у себя token и не может считать 200 доказательством того, что все выпущенные token или API Key стали недействительными. Для утёкших или скопированных API Key необходимо отдельно отозвать или ротировать соответствующие учётные данные.

## Распространённые ошибки и приёмка

| Явление／ошибка                         | Проверка                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Используйте актуальные имена разрешений; проверьте область регистрации приложения, ограничения делегирования и разрешения пользователя. Полный каталог Discovery не является каталогом, доступным для выбора приложением                      |
| `invalid_request`             | Обязательные параметры, точный адрес обратного вызова, challenge и method S256 для Public-клиента                        |
| `invalid_client`              | client ID, статус приложения, secret Confidential-клиента; проверьте, не используется ли по ошибке Basic-аутентификация             |
| `invalid_grant`               | code истёк／уже использован, verifier или redirect URI не совпадают; при обновлении также проверяются изменения приложения и разрешений                 |
| `access_denied`               | Пользователь отказал, восстановите кнопку подключения, не открывайте авторизацию циклически                                                  |
| `unsupported_grant_type`      | В настоящее время поддерживаются `authorization_code`, `refresh_token`                             |
| HTTP 401／403                  | Различайте недействительное состояние входа, token, scope авторизации и права доступа к самому ресурсу                                     |
| `Failed to fetch`、ошибки DNS／CORS | Сверьте реальный хост запроса и доступность клиентского backend, нельзя объяснять это тем, что «у пользователя нет Key»                                      |
| Авторизация выполнена, но Key не читается                   | Используйте `platform.acedata.cloud`, реальный user ID, `items[*].token`; различайте пустой список, пагинацию и ответы с ошибками |
| После возврата из авторизации вся страница пустая                     | Сначала отрисуйте страницу; отдельно обрабатывайте ошибки обратного вызова, token, UserInfo и запросов учётных данных; не допускайте, чтобы ошибка инициализации останавливала всю страницу                      |
| После входа в iframe процесс не продолжается                 | Обрабатывайте в соответствии с существующими ограничениями выше, тестируйте сценарии отсутствия входа, истечения срока, отказа и повторного подключения                                          |

Перед поставкой как минимум проверьте: корректный обратный вызов, отказ, ошибочный state, истёкший／уже использованный code, отсутствие Key, сбой сети, истечение token, отсутствие требуемого scope, а также первый вход и смену аккаунта в сценарии iframe. В доказательствах тестирования не сохраняйте полные code, token или API Key.
