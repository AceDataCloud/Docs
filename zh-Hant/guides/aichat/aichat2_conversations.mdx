AI Chat v2 API（`/aichat2/conversations`）是新一代的對話介面，是 [AI Chat API](https://platform.acedata.cloud/documents/aichat-conversations) 的全面升級版本。它在 v1 簡潔、託管多輪對話的基礎上，擴充了：

- **多模態使用者輸入**：透過結構化的 `message` 欄位直接傳送文字 + 圖片 + 檔案區塊，無需先使用 `references` 間接附加。
- **Agent 化工具呼叫**：內建一套網路搜尋、網頁擷取、檔案讀取等工具，並可掛載使用者授權的 MCP 伺服器（Google Drive、Notion、Slack、GitHub 等），模型可在單次請求中多輪自主呼叫工具，以完成複雜任務。
- **結構化串流事件**：透過 `accept: text/event-stream` 或 `application/x-ndjson`，可取得逐 token 的 `text_delta`、`tool_use`、`tool_result`、`thinking`、`citation`、`card`、`artifact` 等事件，方便在前端依照對應類型分別呈現。
- **可中斷 / 可恢復**：模型在需要使用者補充資訊時，會發出 `ask_user_question` 事件並暫停，下次呼叫時透過 `tool_results` 回填答案即可繼續。
- **新增 CRUD 動作**：在同一個 endpoint 上透過 `action` 欄位完成 `retrieve` / `retrieve_batch` / `update` / `delete`，無需額外的對話管理 API。
- **持續更新的模型清單**：預設支援 GPT-5.4、Claude Opus 4.8、Claude Sonnet 4.6、Gemini 3.1 Pro、GLM 5.1、DeepSeek V4、Kimi K3 等當代模型。

同時，它在請求主體層面**完全向下相容 v1**：只傳送 `model` + `question`（+ 可選的 `stateful` / `id` / `references` / `preset`），即可取得與 v1 等價的 `{answer, id}` JSON 回應，因此從 `/aichat/conversations` 遷移過來時，不需要重新撰寫用戶端，只需將路徑替換為 `/aichat2/conversations`。

> 如果你目前正在使用 `/aichat/conversations`，舊版介面仍會持續提供服務，可以依照自己的步調進行遷移。

## 基本使用方式

最簡單的使用方式與 v1 完全相同：傳送 `model` + `question`，即可取得 `{answer, id}`。

CURL 範例：

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。"
  }'
```

回傳結果：

```json
{
  "answer": "AceDataCloud 是一个聚合主流 AI 模型与多模态服务的统一 API 平台，开发者通过一个密钥即可调用 GPT、Claude、Gemini、Midjourney、Suno、Veo 等多家服务。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

Python 範例：

```python
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/json",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "question": "用一句话介绍下 AceDataCloud。",
}

response = requests.post(url, json=payload, headers=headers)
print(response.json())
```

## 多輪對話

與 v1 相同，傳送 `stateful: true` 即可啟用對話儲存功能，API 會回傳一個 `id`；後續請求只要帶上該 `id`，即可繼續對話，無需自行維護 messages 歷史紀錄。

第一次請求：

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "question": "记住一个数字：42。"
  }'
```

回傳：

```json
{
  "answer": "好的，我已经记住了 42。需要我用它做什么吗？",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

第二次請求，帶上相同的 `id`：
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "question": "我剛才讓你記住的數字是多少？"
  }'
```

```json
{
  "answer": "你讓我記住的數字是 42。",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

> `stateful` 預設為 `true`，省略和明確傳入 `true` 的效果相同。設定 `stateful: false` 會跳過載入先前的對話歷史；這不代表本輪結果不會被儲存，也不適用於需要暫停後繼續的工具流程。

### 長對話與原文保留

上下文壓縮只整理本輪傳送給模型的內容，不會取代已儲存的聊天記錄。透過 `action: retrieve` 仍可讀取完整的已儲存訊息；明確編輯、刪除對話仍會依照請求生效。

模型可在目前對話中搜尋並分頁讀取歷史原文。需要繼續修改文章、引用數字或準備發布時，應讀取對應原文，不能用摘要取代正文。此功能不會自動恢復舊版本中已經遺失的訊息。

如果上下文整理失敗，請保留對話 ID 並檢查 `error` 事件；服務不會用空摘要覆蓋原文。失敗前已完成的工具操作可能仍然有效，請先查詢其結果，避免重複生成或重複發布。單一對話達到儲存上限時會明確回報錯誤，既有儲存記錄不會透過裁剪來騰出空間；可匯出所需內容後開啟新對話。

## 串流回應

v2 支援兩種串流格式，依照 `accept` 標頭選擇：

| 情境                    | `accept`               | 資料形式                                       |
| --------------------- | ---------------------- | ------------------------------------------ |
| Web 前端 / EventSource  | `text/event-stream`    | `data: {json}\n\n`，最後一行 `data: [DONE]\n\n` |
| 伺服器端 / CLI / Node 串流解析 | `application/x-ndjson` | 每行一個 JSON 物件                               |
| 不需要串流                 | `application/json`（預設） | 一次性回傳 `{answer, id}`                       |

### NDJSON 範例

```python
import json
import requests

url = "https://api.acedata.cloud/aichat2/conversations"

headers = {
    "accept": "application/x-ndjson",
    "authorization": "Bearer {token}",
    "content-type": "application/json",
}

payload = {
    "model": "gpt-5.4",
    "stateful": True,
    "question": "用三句話介紹杭州。",
}

with requests.post(url, json=payload, headers=headers, stream=True) as resp:
    answer = ""
    for line in resp.iter_lines():
        if not line:
            continue
        event = json.loads(line)
        if event.get("type") == "text_delta":
            # 與 v1 相容：增量片段同時透過 delta_answer 欄位提供
            answer += event["content"]
            print(event["delta_answer"], end="", flush=True)
        elif event.get("type") == "done":
            print()
            print("usage =", event.get("usage"))
```

NDJSON 的每一行都是結構化事件，最常見的是 `text_delta`：

```json
{"type":"text_delta","content":"杭","delta_answer":"杭","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"州","delta_answer":"州","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"是","delta_answer":"是","id":"f2f4b3e8-..."}
...
{"type":"done","conversation_id":"f2f4b3e8-...","usage":{"prompt_tokens":21,"completion_tokens":58,"total_tokens":79},"terminal_reason":"natural_stop"}
```

### SSE 範例

瀏覽器端使用的 `EventSource` 不支援自訂請求主體，建議使用 `fetch` + 手動依照 `\n\n` 切片解析：

```javascript
const resp = await fetch("https://api.acedata.cloud/aichat2/conversations", {
  method: "POST",
  headers: {
    accept: "text/event-stream",
    authorization: "Bearer {token}",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "gpt-5.4",
    stateful: true,
    question: "用三句話介紹杭州。",
  }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";
  for (const block of blocks) {
    const dataLine = block.split("\n").find((l) => l.startsWith("data: "));
    if (!dataLine) continue;
    const payload = dataLine.slice(6);
    if (payload === "[DONE]") return;
    const event = JSON.parse(payload);
    if (event.type === "text_delta") process.stdout.write(event.content);
  }
}
```

### 串流事件類型

| `type`              | 含義                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `text_delta`        | 助手回答的增量文字片段。`content` 為新增內容；為了相容 v1，同一事件還會攜帶 `delta_answer`（等於 `content`）和 `id`。                                        |
| `thinking`          | 模型的思考過程（僅在所選模型公開 reasoning 時出現）。                                                                                      |
| `tool_use`          | 模型決定呼叫一項工具，事件會攜帶 `tool_id`、`tool_name`、`input`。                                                                        |
| `tool_result`       | 工具執行結果，透過 `tool_id` 與上一個 `tool_use` 配對，`is_error` 用來標示是否失敗。                                                             |
| `card`              | 工具產生的結構化卡片（例如圖片、連結預覽），適合直接呈現。                                                                                          |
| `citation`          | 用於補充對應文字片段引用來源的 URL。                                                                                                  |
| `ask_user_question` | 模型需要使用者補充資訊時發出，對話會進入 `awaiting_user_input` 狀態，詳見下文 [恢復暫停的對話](#恢復暫停的對話)。                                                 |
| `artifact`          | 模型產生的獨立成果（例如程式碼區塊、文件），可儲存或下載。                                                                                            |
| `system_message`    | 系統提示訊息（非使用者與助手的內容），僅用於 UI 提示。                                                                                           |
| `compact`           | 模型上下文已整理；已儲存的原始訊息維持不變，客戶端無需刪除聊天記錄。                                                                                    |
| `error`             | 本輪發生錯誤，`message` 描述錯誤內容。                                                                                              |
| `done`              | 本輪最終對話記錄儲存成功，攜帶 `usage`（包含 `prompt_tokens` / `completion_tokens` / `total_tokens`）和 `terminal_reason`；仍需依照終止原因判斷任務是否完成。 |
對於只關心最終答案的客戶端，將所有 `text_delta` 的 `content` 串接起來，就等同於 `application/json` 模式下的 `answer`。

## 多模態輸入

如果使用者輸入包含圖片或檔案，請傳入 `message`（陣列）來取代 `question`。陣列中的每個元素都是一個內容區塊：

```json
{
  "model": "gpt-5.4",
  "stateful": true,
  "message": [
    { "type": "text", "text": "這張圖片裡有幾隻貓？" },
    { "type": "image_url", "image_url": { "url": "https://cdn.acedata.cloud/cats.jpg" } }
  ]
}
```

支援的區塊類型：

- `text` — 一般文字，必須包含 `text` 欄位。
- `image_url` — 圖片，必須包含 `image_url.url`。
- `file_url` — 檔案（PDF、CSV、TXT 等），必須包含 `file_url.url`。

### 與 v1 `references` 的關係

為了相容舊版客戶端，v2 仍然支援 `references: ["https://...", ...]` 欄位：

- URL 副檔名為 `jpg / jpeg / png / gif / bmp / webp / svg / heic / heif` 時，會自動轉換成 `image_url` 區塊；
- 其他副檔名則會轉換成 `file_url` 區塊；
- 如果同時提供了 `question`，則會將其作為一個 `text` 區塊放在最前面。

因此，如果只想從 v1 遷移，又不想修改請求主體，只要將路徑替換為 `/aichat2/conversations` 即可，原本的 `references` 用法仍可正常運作。

如果需要更精細的控制（例如將多張圖片放在文字之間，或是順序很重要），就直接使用 `message` 陣列。

## 工具呼叫與 MCP

v2 的核心強化功能是模型可以自主呼叫工具來完成多步驟任務，**此功能預設為啟用狀態**，客戶端不需要在請求中進行任何額外設定。常見情境：

- 使用者詢問「幫我搜尋一下最近上海有哪些新展覽」→ 模型呼叫內建的 web search → 整理搜尋結果並產生回答。
- 使用者詢問「讀取這份 PDF，然後撰寫摘要」→ 模型呼叫 file_read → 撰寫摘要。
- 使用者已在 [Connections](https://platform.acedata.cloud/connections) 中授權 Google Drive / GitHub / Notion 等服務 → 模型可以呼叫對應的 MCP 工具來讀取或寫入其資料。

在 NDJSON / SSE 串流中，工具呼叫會透過 `tool_use` 和 `tool_result` 這兩種類型的事件呈現，例如：

```json
{"type":"tool_use","tool_id":"toolu_01ABCDEF","tool_name":"web_search","input":{"query":"上海 2026 春季展覽"},"id":"f2f4b3e8-..."}
{"type":"tool_result","tool_id":"toolu_01ABCDEF","output":"...","is_error":false,"id":"f2f4b3e8-..."}
{"type":"text_delta","content":"目前","delta_answer":"目前","id":"f2f4b3e8-..."}
{"type":"text_delta","content":"上海","delta_answer":"上海","id":"f2f4b3e8-..."}
...
```

如果不想在前端顯示工具呼叫的詳細資訊，只要忽略 `tool_use` / `tool_result` / `card` / `citation` 這幾類事件即可，模型的最終輸出仍會透過 `text_delta` 傳出。

`max_turns` 可以限制模型在本次請求中最多自主呼叫工具的輪數，範圍為 1–500，若省略則預設為 500。將其設為較小的值（例如 `max_turns: 1`），即可強制模型只進行單次回答，不允許任何工具呼叫。

## 非同步執行與無人值守授權

如果請求來自告警 Webhook、CI/CD、監控系統或其他背景任務，可以設定 `async: true`，讓介面立即回傳任務 ID，並在背景繼續執行：

```json
{
  "model": "gpt-5.5",
  "async": true,
  "question": "我的服務發出警報了，請使用個人微信通知微信群組「AceDataCloud團隊」……"
}
```

回傳範例：

```json
{
  "task_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "conversation_id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "status": "queued"
}
```

之後可以使用 `action: retrieve` + `id` 查詢對話結果；也可以提供 `callback_url`，任務完成後，平台會將 `{ status, answer, usage, error }` POST 至你的回呼網址。`callback_url` 必須使用 `http` / `https`，且不能直接填寫 `localhost` 或私有 IP 位址。

背景任務通常沒有任何人可以點擊確認。如果希望某些 Skill 或 MCP Server 在無人值守模式下執行傳送、發布、寫入等操作，請在請求主體中明確傳入預先授權清單：

```json
{
  "model": "gpt-5.5",
  "async": true,
  "allowed_skills": ["acedatacloud/personal-wechat"],
  "allowed_mcp_servers": [],
  "question": "我的服務發出警報了，請使用個人微信通知微信群組「AceDataCloud團隊」……"
}
```

`allowed_skills` 中的值是已連線 Skill 的 slug；`allowed_mcp_servers` 中的值是已連線 MCP Server 的 slug。未列入預先授權清單的 Skill / MCP Server，在無人值守模式下仍然只能預覽、執行 dry-run，或拒絕執行寫入操作。

如果需要更細緻的控制，也可以使用功能等效的 `unattended_policy` 物件：

```json
{
  "unattended_policy": {
    "allowed_skills": ["acedatacloud/personal-wechat"],
    "allowed_mcp_servers": [],
    "expires_at": 1790000000
  }
}
```

預先授權本身就是這兩個清單：清單為空代表不授權任何能力，不需要額外的開關欄位。

注意：預先授權僅代表「本次請求允許這些能力在無人值守模式下略過人工確認」。具體的 Skill 仍必須支援 `--unattended-confirm` 或相應的安全機制；否則它仍會執行 dry-run，而不會直接執行寫入操作。

## 恢復暫停的對話

某些工具會讓模型「反問使用者」，此時模型會發出一個 `ask_user_question` 事件，並將對話凍結在 `awaiting_user_input` 狀態：

```json
{
  "type": "ask_user_question",
  "tool_id": "toolu_01XYZW",
  "tool_name": "ask_user_question",
  "question": "你希望產生的報告使用中文還是英文？",
  "options": ["中文", "英文"],
  "id": "f2f4b3e8-..."
}
```

在前端將此事件呈現為卡片，讓使用者選擇答案，接著使用相同的 `id` 發起下一次請求，並透過 `tool_results` 回填答案：
```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: text/event-stream' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "model": "gpt-5.4",
    "stateful": true,
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
    "tool_results": [
      {
        "tool_use_id": "toolu_01XYZW",
        "output": "中文"
      }
    ]
  }'
```

請求本文中的 `tool_use_id` **必須**與暫停時的 `tool_id` 完全一致；不一致會返回 400。當請求中同時存在 `tool_results` 時，`question` / `message` / `references` 都會被忽略。

如果使用者決定放棄這個問題，直接傳送一個新的 `question` / `message` 即可，平台會自動將暫停的工具呼叫標記為「使用者已跳過」。

## 會話管理（CRUD）

v2 在同一個 endpoint 上透過 `action` 欄位提供輕量級會話管理，無需另外開設 API。

### `action: retrieve` —— 取得一個會話

```shell
curl -X POST 'https://api.acedata.cloud/aichat2/conversations' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer {token}' \
  -H 'content-type: application/json' \
  -d '{
    "action": "retrieve",
    "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
  }'
```

返回完整的會話文件（包含 `messages` 歷史紀錄、`model`、`title`、`tools_used` 等）。

### `action: retrieve_batch` —— 列出會話摘要

```json
{
  "action": "retrieve_batch",
  "model_group": "chatgpt",
  "limit": 20,
  "offset": 0
}
```

返回 `{ items: [...], total }`。**摘要不包含 `messages`**，適合用於側邊欄列表；如果使用者點開某條會話，再使用 `action: retrieve` 單獨取得其完整訊息。

可選篩選參數：`user_id`、`application_id`、`model_group`、`model`。

### `action: update` —— 修改標題或重寫歷史紀錄

```json
{
  "action": "update",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44",
  "title": "杭州旅行計畫"
}
```

也可以傳送 `messages`，但伺服器端會進行嚴格的 schema 驗證（必須是折疊後的 `ToolUseContent` 形式），不符合會返回 400。一般只建議用來修改 `title`。

### `action: delete` —— 刪除一個會話

```json
{
  "action": "delete",
  "id": "f2f4b3e8-0c0a-4d3a-aaa2-7ff80c0a1c44"
}
```

返回 `{ id, success: true }`。刪除後無法復原，請確認後再呼叫。

## 從 v1 平順遷移

如果你已經在使用 [`/aichat/conversations`](https://platform.acedata.cloud/documents/aichat-conversations)，遷移到 v2 幾乎不需要修改程式碼：

1. 將 URL 從 `https://api.acedata.cloud/aichat/conversations` 改為 `https://api.acedata.cloud/aichat2/conversations`。
2. 如果你之前傳送的是 v1 模型名稱（如 `gpt-3.5`、`gpt-4-browsing` 等），切換到 v2 時建議升級為當代模型（如 `gpt-5.4`、`claude-opus-4-8`、`gemini-3.1-pro-preview` 等）。
3. NDJSON 串流的欄位保持向後相容：每個 `text_delta` 事件仍然帶有 `delta_answer` 與 `id`，因此原本按行解析 `delta_answer` 的用戶端無需修改。

遷移之後可以視需求啟用 v2 的新功能（多模態 `message`、SSE、工具呼叫、`action` CRUD），按照自己的步調逐步推進即可。

## 錯誤處理

錯誤回應統一為：

```json
{
  "error": {
    "code": "chat_error",
    "message": "model service returned an error"
  },
  "trace_id": "2cf86e86-22a4-46e1-ac2f-032c0f2a4e89"
}
```

常見錯誤：

- `400 bad_request`：缺少必填欄位、`tool_use_id` 不匹配、`messages` schema 不合法等。
- `401 invalid_token`：`authorization` 標頭不正確。
- `404 not_found`：執行 `action: retrieve / update / delete` 時，`id` 對應的會話不存在。
- `413 conversation_storage_limit`：會話超過儲存限制，且未覆蓋既有儲存紀錄。
- `429 too_many_requests`：觸發速率限制。
- `503 context_compaction_failed`：上下文整理失敗，既有紀錄會保留。
- `500 conversation_persist_failed`：本輪最終儲存失敗；已收到文字不代表最終紀錄儲存成功，請依照會話 ID 查詢。
- `500 chat_error`：服務暫時無法使用，或本輪未產生內容（不會扣費）。

在串流回應中，錯誤會以 `{"type":"error","message":"..."}` 事件發出，隨後串流便會結束。`[DONE]` 僅表示傳輸結束；如果存在 `error`，就不能視為成功，也不會傳送成功的 `done` 事件。

## 結論

AI Chat v2 API 在向後相容 v1 的同時，將對話從「單輪 / 多輪問答」升級為「Agent 化的可觀測對話」：多模態輸入、工具呼叫、可暫停 / 可恢復、串流結構化事件、內建 CRUD。建議新接入的專案直接使用 v2；既有的 v1 整合可以分階段平順遷移。如有任何問題，請隨時聯絡我們的技術支援團隊。
