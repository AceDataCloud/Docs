Το X402 περιλαμβάνει HTTP, SDK, υπογραφές, Facilitator και συναλλαγές on-chain. Κατά τη διερεύνηση προβλημάτων υπογραφής ή εκκαθάρισης, συνιστάται να επιβεβαιώνετε επίπεδο προς επίπεδο με τη σειρά «δημόσιο σημείο εισόδου -> απόκριση 402 -> SDK payment handler -> on-chain settlement». Αυτό το εγχειρίδιο εξηγεί τις μεθόδους ελέγχου για κάθε επίπεδο και παραθέτει συνηθισμένα σφάλματα.

## Έλεγχος του δημόσιου σημείου εισόδου

Δήλωση δυνατοτήτων Facilitator:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

Εάν επιστραφούν τα `facilitator`, `supportedKinds` και τα πρωτοκολλιακά endpoints, αυτό σημαίνει ότι τα μεταδεδομένα δυνατοτήτων λειτουργούν κανονικά. Η ανακάλυψη πόρων API έχει καταργηθεί· καλέστε απευθείας το API-στόχο και χρησιμοποιήστε ως αναφορά την απόκριση 402 σε πραγματικό χρόνο.

Υποστηριζόμενες δυνατότητες Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

Εάν επιστραφεί το `kinds`, αυτό σημαίνει ότι το σημείο εισόδου του Facilitator λειτουργεί κανονικά.

## Έλεγχος του 402 `accepts`

Στείλτε ένα μη αυθεντικοποιημένο αίτημα που δεν θα χρεωθεί:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

Ελέγξτε εάν το επιστρεφόμενο `accepts` περιλαμβάνει το δίκτυο που θέλετε να χρησιμοποιήσετε. Το `network` είναι αναγνωριστικό CAIP-2:

- `eip155:8453` + `exact`（Base）
- `eip155:8453` + `upto`（Base, μεταγενέστερη μέτρηση）
- `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` + `exact`（Solana）

Εάν δεν υπάρχει το δίκτυο-στόχος, αυτό σημαίνει ότι αυτό το API ή το τρέχον περιβάλλον δεν έχει ρυθμίσει την αντίστοιχη μέθοδο είσπραξης X402.

## Εκτέλεση του προηγμένου εργαλείου επαλήθευσης X402Client

Το αποθετήριο X402Client παρέχει προηγμένα εργαλεία επαλήθευσης, τα οποία μπορούν να χρησιμοποιηθούν για την επιβεβαίωση της επιλογής απόκρισης 402, της δημιουργίας υπογραφής, του paid retry και του on-chain settlement. Απαιτούν funded wallet, RPC, ιδιωτικό κλειδί και εξαρτήσεις ανάπτυξης. Για συνηθισμένη επιχειρησιακή ενσωμάτωση συνιστάται να χρησιμοποιείτε κατά προτεραιότητα το TypeScript ή Python SDK· εκτελέστε αυτά τα εργαλεία μόνο όταν χρειάζεται να εντοπίσετε προβλήματα υπογραφής ή on-chain εκκαθάρισης.

Διεύθυνση αποθετηρίου: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)

```bash
git clone https://github.com/AceDataCloud/X402Client.git
cd X402Client/typescript
npm install
npm install --no-save ethers @solana/spl-token bs58 tsx
```

Base:

```bash
export X402B_BASE_PAYER_PRIVATE_KEY=0x...
TEST_API_PATH='/openai/chat/completions' \
TEST_BODY='{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}],"max_tokens":10}' \
npx tsx scripts/test-real-e2e.ts
```

Solana:

```bash
export X402B_SOLANA_PAYER_PRIVATE_KEY=...
npx tsx scripts/test-solana-e2e.ts
```

Τα εργαλεία επαλήθευσης συνήθως εκτυπώνουν:

1. Την απόκριση 402 του πρώτου αιτήματος.
2. Το επιλεγμένο payment requirement.
3. Τη σύνοψη του υπογεγραμμένου `PAYMENT-SIGNATURE`.
4. Την κατάσταση HTTP και το σώμα απόκρισης μετά την επανάληψη.
5. Τη συναλλαγή on-chain settlement ή, σε περίπτωση αποτυχίας, την αιτία σφάλματος του Facilitator.

Μην στέλνετε ιδιωτικά κλειδιά ή πλήρη `PAYMENT-SIGNATURE` στο σύστημα καταγραφής ή σε tickets.

Παράδειγμα αποτελεσμάτων επαλήθευσης δημόσιου API:

```text
Base exact
HTTP 402 -> HTTP 200
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC

Solana exact
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run because public RPC lookup hit 429

Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Επεξήγηση:

- Τα Base `exact`, Solana `exact` και Base `upto` ολοκλήρωσαν όλα το paid retry από HTTP 402 σε HTTP 200.
- Η on-chain συναλλαγή του Base `exact` μπορεί να αναζητηθεί στο BaseScan και το ποσό εκκαθάρισης είναι `95215` atomic USDC.
- Το όριο υπογραφής του Base `upto` είναι `95215` atomic USDC, αλλά το πραγματικό on-chain settlement είναι `3` atomic USDC, γεγονός που δείχνει ότι η μεταγενέστερη μέτρηση χρεώνει βάσει της πραγματικής χρήσης.
- Η διαδρομή Solana έχει επιβεβαιώσει το paid retry και την έξοδο του μοντέλου. Τα δημόσια RPC ενδέχεται να περιορίζουν τον ρυθμό· όταν απαιτείται αυστηρή on-chain συμφωνία, χρησιμοποιήστε δικό σας Solana RPC ή επιβεβαιώστε την υπογραφή συναλλαγής μέσω των εγγραφών εκκαθάρισης της πλατφόρμας.

## SDK smoke test

Τα προηγμένα εργαλεία επαλήθευσης χρησιμοποιούνται για τον έλεγχο υπογραφών και on-chain εκκαθάρισης. Η επιχειρησιακή πλευρά θα πρέπει επίσης να εκτελεί SDK smoke test, για να επιβεβαιώνει ότι ο κώδικας της εφαρμογής μπορεί να διαχειρίζεται αυτόματα το 402 μέσω του payment handler. Παρακάτω εμφανίζονται μόνο τα βασικά αποσπάσματα· ο πλήρης κώδικας χρειάζεται να συμπληρώσει wallet, provider και import.

TypeScript:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const res = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly ADC_SDK_X402_OK' }],
  max_tokens: 8
});
```

Python:

```python
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
    )
)

res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly ADC_PY_X402_OK"}],
    max_tokens=8,
)
```

Εάν το μοντέλο επιστρέψει τη σταθερή συμβολοσειρά όπως ζητείται, αυτό σημαίνει ότι το SDK, ο payment handler, το Gateway, ο Facilitator και το API-στόχος έχουν συνδεθεί επιτυχώς.

Τα δύο παραπάνω smoke test χρησιμοποιούν Base `exact` και εκκαθαρίζουν το σταθερό ποσό που αναφέρεται στην προσφορά 402. Η συμπλήρωση συνομιλίας αποτελεί σενάριο μέτρησης βάσει token· για επίσημη ενσωμάτωση συνιστάται να περάσετε `preferScheme: 'upto'` (στην Python `prefer_scheme="upto"`), ώστε η εκκαθάριση να γίνεται βάσει της πραγματικής χρήσης.

Το αντικείμενο επιστροφής του Python SDK είναι `dict` και μπορείτε να χρησιμοποιήσετε το `res["choices"][0]["message"]["content"]` για να διαβάσετε το περιεχόμενο.

## E2E πληρωμής παραγγελιών

Η πληρωμή παραγγελιών χρησιμοποιεί το API της πλατφόρμας `platform.acedata.cloud` και απαιτεί token λογαριασμού πλατφόρμας. Η πλήρης ροή είναι: δημιουργία Pending παραγγελίας, ενεργοποίηση 402 μέσω `POST /api/v1/orders/{order_id}/pay/`, και στη συνέχεια επανάληψη με `PAYMENT-SIGNATURE`.

Παράδειγμα αποτελεσμάτων επαλήθευσης πληρωμής παραγγελίας μικρού ποσού:

> Οι παρακάτω εγγραφές συναλλαγών είναι ιστορικά δείγματα πραγματικών δοκιμών υπό την παλιά πολιτική, και τα ποσά και τα hashes συναλλαγών διατηρούνται όπως ήταν. Οι νέες παραγγελίες X402 δεν παρέχουν πλέον εκπτώσεις μεθόδου πληρωμής· χρησιμοποιήστε το `amount` της τρέχουσας απόκρισης 402 ως βάση για την υπογραφή και την πληρωμή.
```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
accepts [('eip155:8453', 'exact', '1200000'), ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000')]

status 200
order state Finished
pay_way X402
pay_id 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}

Base tx status 1
block 46726704
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Επεξήγηση αποτελεσμάτων:

- Μετά τη δημιουργία της παραγγελίας, η κατάσταση της παραγγελίας είναι `Pending` και η τιμή είναι `1.26`.
- Το πρώτο αίτημα `pay/` επιστρέφει HTTP 402, και στο `accepts` υπάρχουν Base `exact` και Solana `exact`, με τα ποσά να είναι και τα δύο `1200000` atomic USDC.
- Μετά την επανάληψη με το Base `PAYMENT-SIGNATURE`, επιστρέφει HTTP 200, η κατάσταση της παραγγελίας αλλάζει σε `Finished` και το `pay_way` είναι `X402`.
- Μετά την αποκωδικοποίηση του `PAYMENT-RESPONSE`, εμφανίζονται `success=True`, `network=base`, και το ίδιο hash συναλλαγής παρέχεται.
- Στο BaseScan η κατάσταση συναλλαγής είναι `1`, και το ποσό μεταφοράς είναι `1200000` atomic USDC, δηλαδή `1.2` USDC.
- Η τιμή δημιουργίας `1.26` πληρώθηκε κατά την περίοδο της παλιάς πολιτικής έκπτωσης πληρωμών X402, και το τελικό υπογεγραμμένο και εκκαθαρισμένο ποσό είναι `1.2` USDC.

Εάν η πληρωμή της παραγγελίας δεν έχει `Authorization: Bearer {platform_token}`, ή εάν η παραγγελία δεν ανήκει στον τρέχοντα λογαριασμό, θα αποτύχει στο επίπεδο δικαιωμάτων της πλατφόρμας· αυτό διαφέρει από το X402 API χωρίς λογαριασμό που καλείται απευθείας στο `x402.acedata.cloud`.

## Συνήθη σφάλματα

| Φαινόμενο                                           | Κατεύθυνση ελέγχου                                                                |
| -------------------------------------------- | ------------------------------------------------------------------- |
| Το πρώτο αίτημα δεν είναι 402                                  | Ελέγξτε εάν μεταφέρθηκε κατά λάθος `Authorization`, ή εάν αυτό το API δεν έχει ακόμη X402 pricing.                  |
| `No payment requirement for network`         | Το δίκτυο-στόχος δεν βρίσκεται στο `accepts`, αλλάξτε δίκτυο ή ελέγξτε τη διαμόρφωση του Gateway.                               |
| `invalid_402`                                | Η απόκριση 402 δεν είναι έγκυρο JSON, ελέγξτε τον proxy, το gateway ή τη σελίδα σφάλματος.                                        |
| `Authorization nonce already processed`      | Χρησιμοποιήθηκε επανειλημμένα το ίδιο `PAYMENT-SIGNATURE`, υπογράψτε ξανά.                                  |
| `invalid_upto_evm_payload_invalid_signature` | Ελέγξτε εάν το chainId του `upto`, το Permit2 domain, η διεύθυνση facilitator και ο λογαριασμός υπογραφής είναι συνεπή.         |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Εκτελέστε `approve-permit2` για το USDC της αλυσίδας-στόχου.                                     |
| `Payer has insufficient USDC balance`        | Το πορτοφόλι πληρωμής δεν έχει επαρκές USDC.                                                       |
| HTTP 200 αλλά χωρίς tx hash                         | Το πραγματικό ποσό του `upto` μπορεί να είναι 0, ή η εγγραφή settlement εξακολουθεί να γράφεται ασύγχρονα.                             |
| Solana `Missing transaction payload`         | Δεν υπάρχει σειριοποιημένη συναλλαγή ή signature στο envelope `PAYMENT-SIGNATURE`, ελέγξτε το wallet adapter. |

## Λίστα ελέγχου Base `upto`

Το `upto` προς το παρόν παρέχεται μόνο στο Base (`eip155:8453`). Επειδή η υπογραφή `upto` δεσμεύει περισσότερες παραμέτρους EVM typed data, κατά την ενσωμάτωση θα πρέπει να επιβεβαιώνεται ιδιαίτερα ότι τα πεδία πραγματικού χρόνου στην απόκριση 402 συμφωνούν πλήρως με την υπογραφή του πελάτη.

```text
Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

Εάν το Base `upto` επιστρέψει `invalid_upto_evm_payload_invalid_signature`, ελέγξτε κατά προτεραιότητα:

1. Το `extra.chainId` (θα πρέπει να είναι `8453`) στην εγγραφή `eip155:8453` + `upto` που επιστρέφει το API.
2. Το `extra.facilitatorAddress` που επιστρέφει το API.
3. Τη διεύθυνση facilitator Base `upto` που επιστρέφει το `https://facilitator.acedata.cloud/supported`.
4. Το Permit2 domain, το spender, το συμβόλαιο USDC και τον λογαριασμό υπογραφής.
5. Εάν το πορτοφόλι έχει ήδη κάνει approve Permit2 για το Base USDC.

Το digest υπογραφής του `upto` δεσμεύει ταυτόχρονα το Permit2 domain, το chain ID, το spender, τη διεύθυνση παραλήπτη, τη διεύθυνση facilitator και το validAfter. Εάν οποιοδήποτε στοιχείο δεν συμφωνεί, ο Facilitator θα ανακτήσει λάθος signer, με αποτέλεσμα να επιστρέψει invalid signature. Εάν αυτά συμφωνούν όλα αλλά εξακολουθεί να επιστρέφεται 402, ελέγξτε στη συνέχεια το Permit2 allowance· όταν δεν υπάρχει εξουσιοδότηση, επιστρέφεται `PERMIT2_ALLOWANCE_REQUIRED`.

## Αποθήκευση πληροφοριών επαλήθευσης

Μια πλήρης επαλήθευση αποθηκεύει τουλάχιστον:

- API path και σύνοψη σώματος αιτήματος·
- το επιλεγμένο network και scheme·
- `maxAmountRequired`·
- διεύθυνση πορτοφολιού payer·
- τελική κατάσταση HTTP·
- την έξοδο μοντέλου ή το ID εργασίας στην απόκριση·
- σύνδεσμο settlement transaction·
- Gateway trace ID ή ID εγγραφής χρήσης πλατφόρμας.

Μην αποθηκεύετε ιδιωτικά κλειδιά, πλήρες `PAYMENT-SIGNATURE`, πλήρες EIP-712 signature ή μνημονική φράση.

## Δομημένα σφάλματα πληρωμής

Οι αποτυχίες X402 μετά την υπογραφή επιστρέφουν στα `extensions.acedatacloud.paymentError` σταθερό `code`, ασφαλείς παραμέτρους παρεμβολής, στάδιο και σημαία επαναληψιμότητας. Χρησιμοποιήστε κατά προτεραιότητα αυτή τη δομή για έλεγχο, μην αναλύετε το αγγλικό `error` ανώτατου επιπέδου και μην απαιτείτε από τον χρήστη να παρέχει υπογραφές πορτοφολιού ή το πρωτότυπο κείμενο προσομοίωσης on-chain.

- `charged: false`：Η επαλήθευση απορρίφθηκε ρητά πριν από το settlement, και δεν ξεκίνησε χρέωση αυτή τη φορά.
- Χωρίς `charged`：Το αποτέλεσμα είναι άγνωστο ή έχει ήδη εισέλθει στο στάδιο settlement, ελέγξτε πρώτα την παραγγελία και την κατάσταση on-chain, και απαγορεύεται η άμεση επανάληψη της πληρωμής.
- `settlement_pending`：Μην επαναλάβετε την πληρωμή προς το παρόν, ανανεώστε πρώτα την παραγγελία ή επικοινωνήστε με την υποστήριξη.
- Μη αναγνωρισμένο code：Αντιμετωπίστε το ως `payment_failed`, και διατηρήστε τον δημόσιο τεχνικό κωδικό για αναζήτηση από την εξυπηρέτηση πελατών.
