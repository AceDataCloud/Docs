Ο Facilitator είναι το στοιχείο εκκαθάρισης στην πλευρά διακομιστή της ροής X402. Ο πελάτης είναι υπεύθυνος για την υπογραφή, ενώ το Gateway ή ο διακομιστής σας είναι υπεύθυνος για την κλήση των `/verify` και `/settle` του Facilitator.

Η διεύθυνση του Facilitator παραγωγής του Ace Data Cloud είναι:

```text
https://facilitator.acedata.cloud
```

Αποθετήριο πηγαίου κώδικα: [https://github.com/AceDataCloud/FacilitatorX402](https://github.com/AceDataCloud/FacilitatorX402)

## Συμβάσεις v2 wire

Η ροή X402 του Ace Data Cloud χρησιμοποιεί πλέον πλήρως το επίσημο x402 v2 και δεν δέχεται πλέον την κεφαλίδα αιτήματος `X-Payment` του v1. Κατά την ενσωμάτωση, πρέπει να προσέξετε τρία σημεία:

- Η κεφαλίδα αιτήματος είναι `PAYMENT-SIGNATURE`, και η τιμή είναι ένα JSON envelope κωδικοποιημένο σε base64.
- Το ανώτατο επίπεδο του envelope πρέπει να είναι `x402Version: 2` και να χρησιμοποιεί το αντικείμενο `accepted` για να δηλώσει το `scheme` και το `network` που επιλέχθηκαν αυτήν τη φορά.
- Το `network` χρησιμοποιεί αναγνωριστικό CAIP-2 (όπως `eip155:8453`) και δεν μπορεί να γραφτεί με συντομογραφίες όπως `base`.

Δομή envelope:

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "exact",
    "network": "eip155:8453"
  },
  "payload": { "...": "..." }
}
```

Εκτός από το JSON body, η απόκριση 402 θα περιέχει επίσης μια κεφαλίδα απόκρισης `PAYMENT-REQUIRED`, της οποίας η τιμή είναι η base64 κωδικοποίηση του ίδιου περιεχομένου challenge, διευκολύνοντας τον πελάτη να διαβάσει τις απαιτήσεις πληρωμής χωρίς να αναλύσει το body.

## Βασικές διεπαφές

### `GET /supported`

Δείτε τα υποστηριζόμενα δίκτυα και scheme:

```bash
curl https://facilitator.acedata.cloud/supported
```

Παράδειγμα απόκρισης:

```json
{
  "kinds": [
    { "x402Version": 2, "scheme": "exact", "network": "eip155:8453" },
    {
      "x402Version": 2,
      "scheme": "upto",
      "network": "eip155:8453",
      "extra": { "facilitatorAddress": "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708" }
    },
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
      "extra": { "feePayer": "3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq" }
    }
  ],
  "extensions": [],
  "signers": {
    "eip155:*": [
      "0xd019238EAA8a9Ca13C5792Ca10B4029D6ce25708"
    ],
    "solana:*": ["3SPm6qbgsDkj24MuR8Ss4sH97fziqyCiqFKDyeVU2igq"]
  }
}
```

Επεξήγηση αποτελεσμάτων:

- Το `network` χρησιμοποιεί αναγνωριστικό CAIP-2, όχι συντομογραφίες όπως `base`, `solana`.
- Το `/supported` υποδεικνύει ότι ο Facilitator διαθέτει τις αντίστοιχες δυνατότητες επαλήθευσης και εκκαθάρισης.
- Τόσο το Base όσο και το Solana υποστηρίζουν `exact`· το `upto` παρέχεται προς το παρόν μόνο στο Base.
- Τα `signers` είναι οι διευθύνσεις που χρησιμοποιεί ο Facilitator για την υποβολή συναλλαγών εκκαθάρισης.
- Το αν ένα συγκεκριμένο API επιτρέπει αυτές τις επιλογές εξακολουθεί να καθορίζεται από το `accepts` του 402 αυτού του API.

### `POST /verify`

Επαληθεύει αν το `PAYMENT-SIGNATURE` που αποστέλλεται από τον πελάτη ικανοποιεί μια συγκεκριμένη payment requirement.

Σώμα αιτήματος:

```json
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "accepted": {
      "scheme": "exact",
      "network": "eip155:8453"
    },
    "payload": { "...": "..." }
  },
  "paymentRequirements": {
    "scheme": "exact",
    "network": "eip155:8453",
    "asset": "0x...",
    "amount": "95215",
    "payTo": "0x...",
    "maxTimeoutSeconds": 3600,
    "extra": { "...": "..." }
  }
}
```

Τα πεδία `paymentRequirements` του v2 είναι `scheme`, `network`, `asset`, `amount`, `payTo`, `maxTimeoutSeconds` και `extra`, ενώ το πεδίο ποσού είναι το `amount`. Το `accepts[]` στην απόκριση API 402 επιστρέφει επιπλέον το `maxAmountRequired` ώστε να διαβάσει ο πελάτης το ανώτατο όριο, αλλά αυτό δεν ανήκει στα πεδία του σώματος αιτήματος του Facilitator.

Επιτυχής απόκριση:

```json
{
  "isValid": true,
  "invalidReason": null,
  "payer": "0x..."
}
```

Μετά την αποκωδικοποίηση, η κεφαλίδα απόκρισης `PAYMENT-RESPONSE` για πληρωμές παραγγελιών παραγωγής περιέχει το αποτέλεσμα settlement. Το αποτέλεσμα εκτέλεσης του προγράμματος για πληρωμή παραγγελίας Base:

```text
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order 78481793-304e-47f7-bc0c-8231aec9cc1e state Finished pay_way X402 price 1.2
explorer https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
transfer value 1200000 atomic USDC
```

Επεξήγηση αποτελεσμάτων:

- Το `success=True` υποδεικνύει ότι το Facilitator settlement ολοκληρώθηκε επιτυχώς.
- Το `transaction` είναι το hash της συναλλαγής on-chain και το `pay_id` της παραγγελίας γράφεται επίσης με την ίδια τιμή.
- Στον explorer μπορείτε να δείτε τη μεταφορά `1200000` atomic USDC του Base USDC.
- Το `errorReason=None` υποδεικνύει ότι αυτό το settlement δεν επέστρεψε επιχειρησιακό σφάλμα.

Η αποτυχία επαλήθευσης συνήθως επιστρέφει επίσης HTTP 200, αλλά το `isValid` είναι `false`. Η επιχειρησιακή πλευρά θα πρέπει να διαβάζει το `invalidReason`, αντί να εξετάζει μόνο τον κωδικό κατάστασης HTTP.

### `POST /settle`

Εκκαθαρίζει on-chain την εξουσιοδότηση που έχει ήδη επαληθευτεί.

Το σώμα αιτήματος είναι βασικά ίδιο με το `/verify`. Η διαφορά του `upto` είναι ότι το `paymentRequirements.amount` ξαναγράφεται στο πραγματικό ποσό εκκαθάρισης κατά το settle· το ανώτατο όριο υπογραφής καταγράφεται από τον Facilitator στο στάδιο verify και κατά το settle επαληθεύεται ότι το πραγματικό ποσό δεν υπερβαίνει αυτό το όριο.

Επιτυχής απόκριση:

```json
{
  "success": true,
  "errorReason": null,
  "transaction": "0x...",
  "network": "eip155:8453",
  "payer": "0x...",
  "amount": "3"
}
```

Αν το πραγματικό ποσό του `upto` είναι 0, το `transaction` μπορεί να είναι κενό string, υποδεικνύοντας ότι δεν χρειάζεται να σταλεί συναλλαγή on-chain.

## Πώς χρησιμοποιεί το Ace Data Cloud Gateway τον Facilitator

Η ροή του Ace Data Cloud API Gateway είναι η εξής:

1. Ο πελάτης ζητά το API για πρώτη φορά, χωρίς `Authorization` και `PAYMENT-SIGNATURE`.
2. Το Gateway υπολογίζει την εκτιμώμενη τιμή του αιτήματος, επιστρέφει 402 και `accepts`.
3. Ο πελάτης υπογράφει και επαναλαμβάνει το αίτημα με `PAYMENT-SIGNATURE`.
4. Το Gateway αποκωδικοποιεί το `PAYMENT-SIGNATURE` και επιλέγει την αντίστοιχη payment requirement.
5. Το Gateway καλεί το `/verify` του Facilitator.
6. Μετά την επιτυχία του `/verify`, το Gateway επιτρέπει το αίτημα προς το API στόχο.
7. Αφού επιστρέψει το API στόχος, το Gateway καλεί το `/settle` του Facilitator στο στάδιο `/record`.
8. Το Gateway γράφει το hash της συναλλαγής on-chain στα metadata της εγγραφής χρήσης.

Το `exact` εκκαθαρίζει το υπογεγραμμένο ποσό στο βήμα 7· το `upto` γράφει το `amount` με βάση την πραγματική χρήση στο βήμα 7 και, στη συνέχεια, εκκαθαρίζει το πραγματικό ποσό.

## Πώς να ενσωματώσετε το δικό σας API

Αν θέλετε το δικό σας API να υποστηρίζει X402, μπορείτε να το υλοποιήσετε με αυτήν τη δομή:
1. Προετοιμάστε `paymentRequirements` για κάθε επί πληρωμή διεπαφή, συμπεριλαμβανομένων του δικτύου, του ποσού, της διεύθυνσης παραλήπτη, της διεύθυνσης asset και του signature domain.
2. Εάν το αίτημα δεν έχει `PAYMENT-SIGNATURE`, επιστρέψτε HTTP 402 και `accepts`.
3. Εάν το αίτημα έχει `PAYMENT-SIGNATURE`, κάντε Base64 αποκωδικοποίηση για να λάβετε το `paymentPayload`.
4. Καλέστε το Facilitator `/verify`.
5. Μετά την επιτυχή επαλήθευση, εκτελέστε τη λογική επιχειρηματικής λειτουργίας.
6. Μετά την επιτυχία της επιχειρηματικής λειτουργίας, καλέστε το Facilitator `/settle`.
7. Αποθηκεύστε τα `payer`, `transaction`, `amount`, `network` για συμφωνία λογαριασμών.

Ο διακομιστής πρέπει να χρησιμοποιεί τα `paymentRequirements` που δημιούργησε ο ίδιος για να καλέσει τα `/verify` και `/settle`, μην εμπιστεύεστε το ποσό, τη διεύθυνση παραλήπτη ή τη διεύθυνση asset που επιστρέφει ο πελάτης.

## Προστασία από επανάληψη

Το Facilitator καταγράφει nonce. Η εξουσιοδότηση με το ίδιο nonce δεν μπορεί να επαληθευτεί και να εκκαθαριστεί επανειλημμένα.

Αυτό σημαίνει:

- Ο πελάτης πρέπει να υπογράφει ένα νέο envelope σε κάθε αίτημα;
- Εάν το `/settle` έχει ήδη υποβάλει τη συναλλαγή αλλά προσωρινά δεν υπάρχει επιβεβαίωση, μπορείτε να επαναλάβετε το `/settle` με το ίδιο nonce για ιδεμπότειο έλεγχο συμφωνίας;
- Μην αποθηκεύετε στην cache το ίδιο `PAYMENT-SIGNATURE` και στη συνέχεια το χρησιμοποιείτε για πολλαπλές κλήσεις API.

## Συνήθη σφάλματα

| Σφάλμα                                           | Συνήθης αιτία                                                             |
| -------------------------------------------- | ---------------------------------------------------------------- |
| `Authorization nonce already processed`      | Χρησιμοποιήθηκε επανειλημμένα το ίδιο `PAYMENT-SIGNATURE`.                                    |
| `Authorization destination mismatch`         | Το `to` στην υπογραφή του πελάτη δεν συμφωνεί με το `payTo` του payment requirement.                |
| `invalid_upto_evm_payload_invalid_signature` | Τα chainId, facilitator, Permit2 domain ή η διεύθυνση υπογραφής των `upto` typed data δεν συμφωνούν. |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | Το πορτοφόλι δεν έχει ακόμη κάνει approve επαρκές USDC allowance για το Permit2.                        |
| `Payer has insufficient USDC balance`        | Το πορτοφόλι πληρωμής δεν έχει επαρκές USDC.                                                    |
| `Solana signer private key not configured`   | Το Facilitator χρειάζεται να υπογράψει ως fee payer, αλλά ο διακομιστής δεν διαθέτει ρύθμιση Solana signer.           |
