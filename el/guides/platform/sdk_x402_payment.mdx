Το [X402](https://www.x402.org/) είναι ένα πρωτόκολλο on-chain πληρωμών «χρέωσης μέσω HTTP 402» που προτάθηκε από την Coinbase: ο διακομιστής επιστρέφει `402 Payment Required` σε αιτήματα χωρίς token, με το πεδίο `accepts: [...]` να παραθέτει αποδεκτές αλυσίδες / assets / τιμές· ο πελάτης υπογράφει τοπικά μια εξουσιοδότηση (Permit2 / EIP-712 στο EVM, εξουσιοδότηση SPL token transfer στο Solana), τοποθετεί το base64 envelope στην κεφαλίδα `PAYMENT-SIGNATURE` και επαναστέλνει το αίτημα. Αφού ο διακομιστής το επαληθεύσει, εκτελεί πραγματικά την on-chain εκκαθάριση και στη συνέχεια επιστρέφει το επιχειρηματικό αποτέλεσμα.

> Ο πελάτης X402 του Ace Data Cloud καλεί απευθείας το API στόχο και χρησιμοποιεί το `402 Payment Required` και το `accepts` που επιστρέφονται σε πραγματικό χρόνο από αυτό το αίτημα ως βάση για την τιμή και την υπογραφή. Οι δυνατότητες πληρωμών του Facilitator μπορούν να επαληθευτούν στο [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

Τα `@acedatacloud/sdk` και `acedatacloud` εκθέτουν και τα δύο ένα hook `paymentHandler`: όταν ένα αίτημα που στέλνεται από το ίδιο το SDK λάβει `402`, καλεί τον handler που εισαγάγατε για να αποκτήσει την κεφαλίδα `PAYMENT-SIGNATURE` και έπειτα επαναστέλνει το αρχικό αίτημα. Χρησιμοποιώντας το `@acedatacloud/x402-client` / `acedatacloud-x402` μαζί με το SDK, **ολόκληρη η ροή είναι πλήρως διαφανής για τον επιχειρηματικό κώδικα**——χρησιμοποιείτε μόνο `client.openai.chat.completions.create(...)`, το οποίο μοιάζει ακριβώς με τη λειτουργία token, αλλά από κάτω χρεώνεται ανά κλήση και δεν απαιτείται προπληρωμή.

Αυτό το άρθρο:

- Εκτελεί πραγματικά τη ροή «χωρίς token + εισαγωγή X402 handler» στο TS ([Επαλήθευση T12](#τέσσερα-επαλήθευση-πραγματικής-εκτέλεσης))
- Παραθέτει τις διαφορές μεταξύ των δύο ροών υπογραφής EVM / Solana
- Παρουσιάζει τρεις προσαρμογές: λειτουργία ιδιωτικού κλειδιού `viem`, λειτουργία browser wallet και λειτουργία Python `EVMAccountSigner`
- Εξηγεί ξεκάθαρα το πεδίο `preferScheme` / `prefer_scheme`, στο οποίο είναι εύκολο να γίνουν λάθη

## Ι. Επισκόπηση πρωτοκόλλου (απαραίτητο)

Μια επιτυχημένη κλήση X402 περιλαμβάνει **3 HTTP RTT**:

```text
1. SDK -> /openai/v1/chat/completions               (χωρίς Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK εσωτερικά -> paymentHandler({ url, method, body, accepts })   (τοπική υπογραφή, 0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (εισαγωγή κεφαλίδας PAYMENT-SIGNATURE)
   <- 200 + επιχειρηματική απόκριση   (η εκκαθάριση ολοκληρώνεται στον διακομιστή)
```

Το X402 envelope είναι ένα τμήμα JSON, το οποίο μετά από base64 τοποθετείται στην κεφαλίδα `PAYMENT-SIGNATURE`. Η δομή (απόσπασμα):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

Το κορυφαίο επίπεδο του envelope είναι `x402Version: 2` και δηλώνει το `scheme` και το `network` που επιλέχθηκαν για αυτή τη φορά μέσω του αντικειμένου `accepted` (αναγνωριστικό CAIP-2).

| scheme  | Σημασία                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | Σταθερή τιμή (σενάρια τιμολόγησης όπως δημιουργία εικόνων / βίντεο, αναζήτηση κ.λπ.). Το υπογεγραμμένο ποσό = το ποσό που απαιτεί ο διακομιστής.                                                         |
| `upto`  | Μετρημένη χρέωση (chat completions / τύπου token). Υπογράφεται ένα ποσό **ανώτατου ορίου**, ενώ στην πραγματικότητα εκκαθαρίζεται μόνο το μέρος που χρησιμοποιήθηκε (βάσει Permit2 + witness). **Συνιστάται έντονα** για API τύπου συνεδρίας. |

Το `preferScheme` / `prefer_scheme` χρησιμοποιείται για την επιλογή προτίμησης όταν ο διακομιστής **παρέχει ταυτόχρονα πολλαπλά scheme**. Εάν ο διακομιστής εκθέτει μόνο `exact`, αυτό το πεδίο αγνοείται· εάν οριστεί `upto` αλλά ο διακομιστής δεν το εκθέτει, γίνεται fallback στο πρώτο ταιριαστό στοιχείο.

## ΙΙ. TypeScript: δύο τρόποι χρήσης, browser wallet + viem στον διακομιστή

### Εγκατάσταση

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

Οι εκδόσεις που δοκιμάστηκαν:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### Πλήρης υπογραφή του `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // network='solana' 必填
  evmProvider?: EVMProvider;                // network='base' 必填，EIP-1193
  evmAddress?: string;                      // network='base' 必填
  preferScheme?: 'exact' | 'upto';
}
```

Η επιστρεφόμενη τιμή είναι ένα `(ctx) => Promise&lt;{ headers: Record<string, string> }>` και αντιστοιχεί ακριβώς στην υπογραφή του hook `paymentHandler` του SDK.

### Χρήση 1: Browser (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. 让用户连钱包
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. 切到 Base 主网
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. 构造 SDK 客户端，注入 X402 handler
//    注意：不传 apiToken，让 SDK 走 402 路径
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // chat 类必选 upto
  })
});

// 4. 正常调
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

Στην πρώτη κλήση, το browser θα εμφανίσει **δύο προτροπές υπογραφής**: η πρώτη είναι ένα εφάπαξ Permit2 approve για USDC (το ποσό είναι `MaxUint256`, εγγράφεται on-chain)· η δεύτερη είναι η υπογραφή EIP-712 του X402 envelope (δεν εγγράφεται on-chain, χρησιμοποιείται μόνο για επαλήθευση από τον facilitator). Οι επόμενες κλήσεις απαιτούν μόνο τη δεύτερη υπογραφή και η εμπειρία είναι «κλικ μία φορά για υπογραφή → λήψη αποτελέσματος».

### Χρήση 2: Node διακομιστής + ιδιωτικό κλειδί viem (κατάλληλο για backend / CLI)

Το `@acedatacloud/x402-client` στην πλευρά TS **δέχεται μόνο EIP-1193 provider**——δεν διαχειρίζεται απευθείας ιδιωτικά κλειδιά. Σε σενάρια Node / CLI, η τυπική πρακτική είναι να χρησιμοποιήσετε το [`viem`](https://viem.sh/) για να τυλίξετε το ιδιωτικό κλειδί σε `WalletClient`, και στη συνέχεια να περάσετε από το [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) ή τον εσωτερικό EIP-1193 adapter του viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// Το viem WalletClient διαθέτει εγγενώς .request() συμβατό με EIP-1193, και μπορεί να χρησιμοποιηθεί απευθείας ως evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // το walletClient.request πληροί το EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> Αν θεωρείτε ότι η προσαρμογή EIP-1193 του viem δεν είναι αρκετά σταθερή, μπορείτε επίσης να χρησιμοποιήσετε το χαμηλότερου επιπέδου [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts), να συνδέσετε μόνοι σας τη ροή `accepts → signed envelope → PAYMENT-SIGNATURE header` και να παρακάμψετε το hook του SDK· ωστόσο, συνιστάται να προτιμήσετε το `createX402PaymentHandler`, ώστε να μη χρειάζεται να συντηρείτε μόνοι σας τις αναβαθμίσεις του πρωτοκόλλου.

### Χρήση 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

Στο δίκτυο Solana προς το παρόν **εκτίθεται μόνο το scheme `exact`**, επομένως το `preferScheme` δεν έχει επίδραση στο Solana.

## Τρία, Python: λειτουργία ιδιωτικού κλειδιού

Το `acedatacloud-x402` της Python ακολουθεί τη διαδρομή της **άμεσης υπογραφής με ιδιωτικό κλειδί** (δεν υπάρχει αφαίρεση EIP-1193), και είναι καταλληλότερο για διακομιστές / εκτελεστές εργασιών.

### Εγκατάσταση

```bash
pip install acedatacloud acedatacloud-x402
```

Δοκιμασμένες εκδόσεις:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. Κατασκευή υπογράφοντα από το ιδιωτικό κλειδί
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. Κατασκευή SDK: μην περάσετε api_token, ώστε το SDK να ακολουθήσει τη διαδρομή 402
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # για τύπου chat επιλέξτε οπωσδήποτε upto
    )
)

# 3. Κανονική κλήση
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(

        rpc_url="https://api.mainnet-beta.solana.com",  # προαιρετικό
    )

```

### Εφάπαξ approve (μόνο την πρώτη φορά σε EVM)

Στο EVM Base, το X402 χρησιμοποιεί Permit2 και απαιτεί από το πορτοφόλι να κάνει μία φορά approve `MaxUint256` USDC για το συμβόλαιο Permit2. Το `acedatacloud-x402` έχει ενσωματωμένο το `approve_permit2`:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

Αυτή η συναλλαγή χρειάζεται να σταλεί μόνο μία φορά· στη συνέχεια, όλες οι πληρωμές X402 EVM χρησιμοποιούν αυτή την εξουσιοδότηση. Το Solana δεν τη χρειάζεται.

## Τέσσερα, επαλήθευση πραγματικής εκτέλεσης

Στόχος δοκιμής: **το TS SDK δεν λαμβάνει token, γίνεται έγχυση X402 handler και μπορεί κανονικά να κατασκευάσει και να εκκινήσει αιτήματα** (ελαφριά επαλήθευση χωρίς κατανάλωση πραγματικού USDC on-chain).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // placeholder provider
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

Έξοδος:

```text
handler_type function
client_ctor_ok AceDataCloud
```

Τα αποτελέσματα δείχνουν:

- Δεν πέρασε `apiToken` και η κατασκευή του SDK **δεν εμφάνισε σφάλμα**, αποδεικνύοντας ότι η λειτουργία X402 είναι πράγματι έγκυρο υποκατάστατο του token.
- Το `createX402PaymentHandler` επιστρέφει συνάρτηση (hook), την οποία το SDK καλεί μόνο όταν λάβει 402.
- Η end-to-end δοκιμή με πραγματική on-chain πληρωμή δεν περιλαμβάνεται σε αυτό το εγχειρίδιο, επειδή περιλαμβάνει πραγματική χρέωση USDC· μπορείτε να ανατρέξετε στο παράδειγμα e2e στον [οδηγό ενσωμάτωσης X402](https://platform.acedata.cloud/documents/x402-integration).

> Το `create_x402_payment_handler` της Python έκανε επίσης την ίδια επαλήθευση —— η τιμή επιστροφής της συνάρτησης είναι callable και η κατασκευή `AceDataCloud(...)` δεν εμφανίζει σφάλμα όταν γίνεται έγχυση `payment_handler=...`. Η σημασιολογία είναι ευθυγραμμισμένη και στις δύο πλευρές.

## Πέντε, σύγκριση με τη «λειτουργία Bearer token»

| Διάσταση              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| Σενάρια χρήσης            | Εσωτερικό backend, μακροχρόνια έργα                                                         | Προγραμματιστές τρίτων, πληρωμή ανά χρήση και κατά απαίτηση, Agentic κλήσεις                        |
| Εγγραφή              | Απαιτεί αίτηση στην [κονσόλα](https://platform.acedata.cloud/console/applications) | Δεν απαιτείται· αρκεί να έχετε on-chain πορτοφόλι                                     |
| Ακρίβεια χρέωσης            | Προφόρτιση, χρέωση σύμφωνα με τον πίνακα token                                                   | Πραγματικός χρόνος, on-chain ανά κλήση                                         |
| Υπόλοιπο              | Μπορεί να προβληθεί στην κονσόλα                                                           | Ελέγξτε το USDC του on-chain πορτοφολιού                                      |
| Αρχικό κόστος            | Δωρεάν πίστωση με την εγγραφή μέσω email                                                        | Απαιτεί μεταφορά USDC στο Base, πρώτο Permit2 approve              |
| Κατάλληλο για τύπου chat       | ✅                                                                 | ✅ (πρέπει να χρησιμοποιηθεί `preferScheme=upto`)                       |
| Κατάλληλο για εφάπαξ πληρωμές / πληρωμές εκ μέρους άλλων λογαριασμών | ❌                                                                 | ✅                                               |
| Αλλαγές κώδικα            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
Οι δύο λειτουργίες μπορούν να συνυπάρχουν — μέσα στην ίδια διεργασία, αρκεί να ρυθμίσετε διαφορετικές μεθόδους πιστοποίησης για διαφορετικά `client` instances.

## Έξι, συνηθισμένες παγίδες

1. **Η κλάση chat πρέπει να έχει `preferScheme=upto`**: η χρήση του `exact` θα κάνει τον facilitator να χρεώσει USDC βάσει του `maxAmountRequired` (και όχι της πραγματικής χρήσης).
2. **Στην πλευρά του Node μην περνάτε γυμνό ιδιωτικό κλειδί στο `createX402PaymentHandler`**: το πακέτο TS δεν δέχεται `{ privateKey }`, πρέπει να το ενθυλακώσετε σε EIP-1193 provider (προτείνεται το viem `WalletClient`).
3. **Η πρώτη κλήση έχει διπλή υπογραφή**: η πρώτη υπογράφει το Permit2 approve (on-chain, με gas), η δεύτερη υπογράφει το X402 envelope (όχι on-chain). Οι επόμενες κλήσεις διατηρούν μόνο τη δεύτερη.
4. **Το Solana δεν έχει έννοια Permit2**: υπογράφει απευθείας την εξουσιοδότηση μεταφοράς SPL token, χωρίς να απαιτείται approve· όμως προς το παρόν το Solana on-chain υποστηρίζει μόνο `exact`.
5. **Διαχωρίστε τα επιχειρηματικά σφάλματα από τα σφάλματα πληρωμής**: 402 → η αποτυχία του handler εγείρει `X402SignError` (ο συγκεκριμένος τύπος διαφέρει ανά αλυσίδα)· μετά την επαναποστολή, τα σφάλματα του επιχειρηματικού API (401 / 422 / 5xx) εξακολουθούν να κατηγοριοποιούνται ως συνήθεις εξαιρέσεις SDK.
6. **Ο πιο σταθερός τρόπος προσαρμογής του `viem`**: το `evmProvider: walletClient as any` χάνει τον έλεγχο τύπων, αλλά έχει την καλύτερη συμβατότητα· αν θέλετε να διατηρήσετε τους τύπους, τυλίξτε ξεχωριστά το `.transport.request` του viem σε ένα αντικείμενο `{ request }` και περάστε το.
