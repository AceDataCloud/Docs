---
title: "Ενσωμάτωση Ace Data Cloud OAuth 2.0"
---

Επιτρέψτε στους χρήστες να εξουσιοδοτήσουν την εφαρμογή σας να αποκτά πρόσβαση στο προφίλ τους στο Ace Data Cloud, στις συνδρομές υπηρεσιών, στα API Key, στη χρήση ή στις παραγγελίες τους. Χρησιμοποιήστε το τυπικό **Authorization Code + S256 PKCE**: η εφαρμογή ανοίγει τη σελίδα εξουσιοδότησης, ο χρήστης συναινεί και στη συνέχεια λαμβάνει ένα εφάπαξ `code`, το οποίο ανταλλάσσεται με OAuth access token.

Το OAuth access token χρησιμοποιείται για πρόσβαση στις διεπαφές πόρων λογαριασμού· για την κλήση του API μοντέλου χρησιμοποιήστε το αντίστοιχο API Key. Η OAuth εξουσιοδότηση δεν δημιουργεί αυτόματα API Key, δεν ενεργοποιεί υπηρεσίες και δεν αυξάνει το υπόλοιπο.

## Επιλέξτε τρόπο ενσωμάτωσης

| Τρόπος            | Κατάλληλο σενάριο                                | Μετά την ολοκλήρωση της εξουσιοδότησης                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Τυπική ανακατεύθυνση OAuth   | Ανεξάρτητοι ιστότοποι, επιτραπέζιοι ή κινητοί πελάτες· οι ενσωματωμένοι ιστότοποι ξεκινούν μόνοι τους την εξουσιοδότηση            | Ο περιηγητής επιστρέφει στο `redirect_uri` που έχει καταχωρίσει η εφαρμογή και η εφαρμογή επεξεργάζεται τα `code` και `state` |
| Εξουσιοδότηση στοιχείου ιστότοπου Studio | Ο ιστότοπος ενσωματώνει την αρχική σελίδα του Studio και επιθυμεί να χρησιμοποιεί τον τρέχοντα λογαριασμό Studio του επισκέπτη | Το Studio στέλνει μήνυμα αποτελέσματος εξουσιοδότησης στην εφαρμογή, η εφαρμογή δεν ανακατευθύνεται και διατηρείται η αρχική σελίδα                  |

Η τυπική ανακατεύθυνση δεν απαιτεί `embed=studio`, `embed_origin` ή `postMessage`. Στη λειτουργία στοιχείου Studio, ο host δημιουργεί τη σελίδα εξουσιοδότησης και διατηρεί τη γέφυρα μηνυμάτων· τα τρίτα μέρη ενσωματώνονται σύμφωνα με το πρωτόκολλο στοιχείου στο τέλος αυτού του κειμένου και δεν πρέπει να συνθέτουν μόνα τους αυτές τις δύο παραμέτρους.

## Τερματικά σημεία και έγγραφο ανακάλυψης

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Χρήση                | Διεύθυνση                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Σελίδα εξουσιοδότησης περιηγητή            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| Ανταλλαγή／ανανέωση OAuth token | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Υποβολή αιτήματος ανάκλησης            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Πληροφορίες τρέχοντος χρήστη            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| Σελίδα διαχείρισης εφαρμογών OAuth      | [Εφαρμογές OAuth](https://auth.acedata.cloud/user/oauth-apps)                            |
| Λίστα εφαρμογών／διεπαφή εγγραφής του συνδεδεμένου χρήστη   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Δημόσια στοιχεία εφαρμογής που χρησιμοποιούνται από τη σελίδα εξουσιοδότησης      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Υπάρχον API Key του χρήστη     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<ID χρήστη>&limit=100` |

Οι διεπαφές διαχείρισης εφαρμογών απαιτούν πιστοποίηση σύνδεσης λογαριασμού και δεν είναι διεπαφές ανώνυμης δυναμικής εγγραφής (DCR). Τα δικά τους τερματικά σημεία ανακάλυψης／εγγραφής των υπηρεσιών MCP είναι διαφορετικές είσοδοι από τα τερματικά σημεία OAuth λογαριασμού αυτού του πίνακα· κατά τη σύνδεση σε συγκεκριμένο MCP, ακολουθήστε την τεκμηρίωση και τα αποτελέσματα ανακάλυψης της υπηρεσίας.

Το έγγραφο ανακάλυψης χρησιμοποιείται για τη λήψη τερματικών σημείων και δυνατοτήτων πρωτοκόλλου. Η τρέχουσα ροή επιστρέφει OAuth token, όχι `id_token`· μην χειρίζεστε τη διαδικασία ως πλήρη ροή σύνδεσης OpenID Connect μόνο και μόνο επειδή υπάρχει το scope `openid`.

## Εύρος δικαιωμάτων: χρησιμοποιήστε τα τρέχοντα ονόματα scope

Το `scope` είναι όνομα δικαιώματος διαχωρισμένο με κενά και με διάκριση πεζών-κεφαλαίων. Οι νέες εφαρμογές χρησιμοποιούν συγκεκριμένα δικαιώματα όπως `profile:read`, `email:read`, `phone:read`.

### Από πού λαμβάνετε τα αιτήσιμα δικαιώματα

Μετά τη σύνδεση, η διεπαφή λίστας εφαρμογών OAuth `GET /api/v1/oauth2/applications/` επιστρέφει `available_scopes`· ο επιλογέας δικαιωμάτων στη σελίδα διαχείρισης εφαρμογών χρησιμοποιεί τον ίδιο κατάλογο. Αυτά είναι τα προαιρετικά scopes που πρέπει να χρησιμοποιούν οι συνήθεις εφαρμογές αυτοεξυπηρέτησης.

**Το `scopes_supported` του Discovery περιλαμβάνει όλα τα ονόματα δικαιωμάτων που αναγνωρίζονται από την πλατφόρμα, αλλά δεν σημαίνει ότι η εφαρμογή σας μπορεί να αιτηθεί κάθε ένα από αυτά.** Η πραγματική εξουσιοδότηση ελέγχει ταυτόχρονα:

1. αν το δικαίωμα επιτρέπεται να εκχωρηθεί σε αυτόν τον τύπο εφαρμογής·
2. αν το δικαίωμα έχει καταχωριστεί στα επιτρεπόμενα scopes αυτής της εφαρμογής OAuth·
3. αν ο τρέχων χρήστης διαθέτει το αιτούμενο δικαίωμα.

Άγνωστα, μη καταχωρισμένα, μη επιτρεπόμενα προς εκχώρηση δικαιώματα ή δικαιώματα που δεν διαθέτει ο χρήστης επιστρέφουν `invalid_scope`. Οι ανταλλαγές κωδικών εξουσιοδότησης και οι ανανεώσεις ελέγχονται επίσης εκ νέου· τα δικαιώματα δεν συμπληρώνονται ούτε αναβαθμίζονται αυτόματα.

### Προαιρετικά δικαιώματα για συνήθεις εφαρμογές αυτοεξυπηρέτησης

Ακολουθεί ο τρέχων κατάλογος (2026-10-09)· κατά την ενσωμάτωση, χρησιμοποιήστε ως αναφορά το `available_scopes`.

| Scope                                            | Χρήση                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Ανάγνωση／ενημέρωση προσωπικού προφίλ                               |
| `email:read`                                     | Ανάγνωση email                                    |
| `phone:read`                                     | Ανάγνωση αριθμού κινητού και περιοχής                                |
| `billing-profile:read` / `billing-profile:write` | Ανάγνωση／διαχείριση στοιχείων χρέωσης                               |
| `applications:read` / `applications:write`       | Ανάγνωση／διαχείριση συνδρομών υπηρεσιών                               |
| `credentials:read` / `credentials:write`         | Ανάγνωση／διαχείριση API Key                           |
| `usage:read`                                     | Ανάγνωση ιστορικού κλήσεων                                  |
| `orders:read` / `orders:write`                   | Ανάγνωση／δημιουργία και διαχείριση παραγγελιών                              |
| `auto-recharge:read` / `auto-recharge:write`     | Ανάγνωση／διαχείριση ρυθμίσεων αυτόματης επαναφόρτισης                             |
| `recharge-cards:redeem`                          | Εξαργύρωση καρτών επαναφόρτισης                                   |
| `coin:read`                                      | Ανάγνωση πληροφοριών σχετικών με token                                |
| `distribution:read`                              | Ανάγνωση πληροφοριών διανομής                                  |
| `connections:read` / `connections:write`         | Ανάγνωση／διαχείριση συνδέσεων                                 |
| `skills:read` / `skills:write`                   | Ανάγνωση／διαχείριση δεξιοτήτων                                 |
| `openid`                                         | Η τρέχουσα υλοποίηση επιτρέπει επίσης στο UserInfo να επιστρέφει βασικά στοιχεία· δεν επιστρέφεται ID Token    |
| `offline_access`                                 | Αίτηση refresh token, για ανανέωση μετά τη λήξη του access token |

Για παράδειγμα, για ανάγνωση μόνο του προσωπικού προφίλ χρησιμοποιήστε `profile:read`· αν χρειάζεται email, προσθέστε `email:read`· για ανάγνωση υπαρχόντων API Key χρησιμοποιήστε `profile:read credentials:read`. Αιτηθείτε `credentials:write` μόνο όταν χρειάζεται πράγματι να δημιουργήσετε ή να τροποποιήσετε Key, και προσθέστε `offline_access` μόνο όταν χρειάζεται ανανέωση.

Ορισμένα δικαιώματα προορίζονται μόνο για αξιόπιστες εφαρμογές που έχουν εγκριθεί από την πλατφόρμα, όπως `sites:read`, `sites:write`, `platform-tokens:read`· άλλα δικαιώματα δεν είναι διαθέσιμα για συνήθεις εφαρμογές OAuth τρίτων. Οι τύποι πελάτη `public`／`confidential` περιγράφουν το αν μπορεί να διαφυλαχθεί ένα secret και δεν σχετίζονται με το αν η εφαρμογή είναι αξιόπιστη. Οι εφαρμογές που δημιουργούνται μέσω αυτοεξυπηρέτησης δεν μπορούν να ενεργοποιήσουν μόνες τους αξιόπιστα δικαιώματα.

Το `account` είναι ο επιλογέας δικαιωμάτων λογαριασμού που χρησιμοποιείται από το καθορισμένο επίσημο MCP διαχείρισης λογαριασμού, δεν είναι scope «όλων των δικαιωμάτων» για εφαρμογές τρίτων και δεν μπορεί να χρησιμοποιηθεί μαζί με άλλα scope. Τα τρίτα μέρη πρέπει να αναφέρουν ρητά τα συγκεκριμένα δικαιώματα που χρειάζονται.

### Μετάβαση από παλαιά τεκμηρίωση

| Παλαιά γραφή                                         | Τρέχουσα προσέγγιση                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Αναφέρετε ξεχωριστά τα συγκεκριμένα δικαιώματα που απαιτούνται πραγματικά· δεν υπάρχει γενική τιμή αντικατάστασης «επιλογής όλων» |

Τα παλαιά ονόματα δεν γίνονται αποδεκτά ως συμβατά ψευδώνυμα. Ενημερώστε ταυτόχρονα τα scopes που έχουν καταχωριστεί στην εφαρμογή OAuth, το URL εξουσιοδότησης και τον δικό σας έλεγχο δικαιωμάτων· η τροποποίηση της διαμόρφωσης της εφαρμογής δεν προσθέτει δικαιώματα σε ήδη εκδομένα token και απαιτεί νέα εξουσιοδότηση από τον χρήστη.

## Βήμα 1: Καταχώριση εφαρμογής OAuth

Ανοίξτε τη [Διαχείριση εφαρμογών OAuth](https://auth.acedata.cloud/user/oauth-apps), δημιουργήστε μια εφαρμογή και συμπληρώστε:
- Όνομα, περιγραφή, λογότυπο εφαρμογής: εμφανίζονται στη μία πλευρά της εφαρμογής στη σελίδα εξουσιοδότησης.
- Τύπος πελάτη: για καθαρά frontend, κινητούς ή desktop πελάτες επιλέξτε **Public**· για υπηρεσίες που μπορούν να διατηρούν το secret στο backend επιλέξτε **Confidential**.
- Διεύθυνση επανακλήσης: στο περιβάλλον παραγωγής χρησιμοποιήστε HTTPS και καταχωρίστε το πλήρες URL που πραγματικά χειρίζεται την επανακλήση η εφαρμογή.
- Δικαιώματα: επιλέξτε τα scopes που πραγματικά χρειάζονται από τον κατάλογο που παρέχει η σελίδα.

Αποθηκεύστε το `client_id`. Οι Confidential πελάτες αποθηκεύουν το `client_secret` στην πλευρά του διακομιστή και δεν μπορούν να το τοποθετούν σε HTML, μεταβλητές build του frontend ή URL. Οι Public πελάτες δεν χρησιμοποιούν secret για την ανταλλαγή token· ακόμη και αν η απάντηση εγγραφής περιέχει αυτό το πεδίο, δεν μπορεί να θεωρείται διαπιστευτήριο που ο πελάτης μπορεί να διατηρήσει μυστικό.

Το `redirect_uri` πρέπει να είναι ακριβώς το ίδιο κατά την εγγραφή, την εξουσιοδότηση και την ανταλλαγή token, συμπεριλαμβανομένης της διαδρομής, της τελικής κάθετου και των παραμέτρων ερωτήματος. Κάθε λογαριασμός μπορεί να δημιουργήσει έως 20 εφαρμογές. Το Secret εμφανίζεται μόνο κατά τη δημιουργία／περιστροφή· μετά την περιστροφή, το παλιό secret δεν μπορεί να συνεχίσει να πραγματοποιεί ανταλλαγές που απαιτούν πιστοποίηση πελάτη.

## Βήμα 2: Το κουμπί εκκινεί την εξουσιοδότηση

Σε κάθε κλικ σύνδεσης, δημιουργήστε νέο τυχαίο `state` και `code_verifier`, υπολογίστε:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Αποθηκεύστε το `state`, το verifier και τη διεύθυνση επανακλήσης στη δική σας συνεδρία της εφαρμογής, και έπειτα ανοίξτε τη σελίδα εξουσιοδότησης με παραμέτρους κωδικοποιημένες σε URL:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<完整回调地址>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<本次随机值>
  &code_challenge=<本次S256挑战值>
  &code_challenge_method=S256
```

Οι Public πελάτες πρέπει να στέλνουν S256 PKCE. Παρόλο που το Discovery εξακολουθεί να παραθέτει το `plain`, οι Public πελάτες δεν μπορούν να το χρησιμοποιούν. Οι Confidential πελάτες επίσης συνιστάται να χρησιμοποιούν S256· αν χρησιμοποιήθηκε PKCE κατά την εκκίνηση της εξουσιοδότησης, πρέπει να υποβληθεί το αντίστοιχο verifier κατά την ανταλλαγή.

Αφού ο χρήστης συναινέσει, επιστρέφει στο `redirect_uri`, και οι παράμετροι ερωτήματος περιλαμβάνουν το `code` και το `state` που επιστρέφεται αυτούσιο. Σε περίπτωση απόρριψης, επιστρέφονται `error=access_denied`, η περιγραφή σφάλματος και το `state`. Πριν από την επεξεργασία της επανακλήσης, επαληθεύστε πρώτα ότι το state αντιστοιχεί στην τρέχουσα συνεδρία. Ο κωδικός εξουσιοδότησης ισχύει για 10 λεπτά και μπορεί να ανταλλαχθεί μόνο μία φορά· μετά από αποτυχία, θα πρέπει να εκκινήσετε ξανά τη σύνδεση και να μην ανανεώνετε επανειλημμένα το παλιό URL επανακλήσης.

## Βήμα 3: Ανταλλαγή για OAuth token

Οι Public πελάτες ανταλλάσσουν απευθείας από το πρόγραμμα περιήγησης ή τον πελάτη· οι Confidential πελάτες ανταλλάσσουν στο δικό τους backend. Το σώμα αιτήματος υποστηρίζει κωδικοποίηση φόρμας, και οι ακόλουθες μεταβλητές αντιπροσωπεύουν τα δεδομένα που έλαβε η εφαρμογή από την τρέχουσα εξουσιοδότηση:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Οι Confidential πελάτες πρέπει επίσης να προσθέσουν το πεδίο φόρμας `client_secret` στην πλευρά του διακομιστή. Προς το παρόν υποστηρίζεται το `client_secret_post`, μην θεωρείτε την πιστοποίηση πελάτη HTTP Basic ως υποστηριζόμενη μέθοδο.

Στην επιτυχή απόκριση διαβάστε τα `access_token`, `token_type`, `expires_in` και το πραγματικά εκχωρημένο `scope`. Μόνο αν ζητηθεί και εγκριθεί το `offline_access` υπάρχει `refresh_token`. Μην θεωρείτε το OAuth access token ως API Key του API μοντέλου και μην γράφετε token, verifier ή κωδικούς εξουσιοδότησης σε αρχεία καταγραφής, συμβάντα αναλυτικών στοιχείων ή συνδέσμους κοινής χρήσης.

## Βήμα 4: Ανάγνωση πληροφοριών χρήστη και API Key

Χρησιμοποιήστε πρώτα το OAuth access token για να ζητήσετε το UserInfo:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Τα πεδία που επιστρέφονται εξαρτώνται από το scope: το `id` είναι το αναγνωριστικό χρήστη· με `profile:read` ή `openid` μπορούν να διαβαστούν βασικά στοιχεία (όπως `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`)· για email απαιτείται `email:read`, και για αριθμό τηλεφώνου και περιοχή απαιτείται `phone:read`. Μην βασίζεστε στο ότι μη εξουσιοδοτημένα πεδία υπάρχουν πάντα.

Όταν χρειάζεται υπάρχον API Key και έχει εγκριθεί το `credentials:read`, χρησιμοποιήστε το `id` του UserInfo ως συνθήκη φιλτραρίσματος:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Η επιστρεφόμενη λίστα χρησιμοποιεί `count` και `items`, και το πεδίο Key είναι **`items[*].token`**, όχι `data[0].value`. Το `user_id=me` δεν είναι έγκυρο ID χρήστη για αυτό το API. Για δεδομένα πολλών σελίδων, συνεχίστε την ανάγνωση με `offset`／`limit`, μην θεωρείτε την πρώτη σελίδα ως όλα τα διαπιστευτήρια.

Επιλέξτε τα κατάλληλα διαπιστευτήρια ανάλογα με την εφαρμογή, την υπηρεσία και την κατάσταση ισχύος, και μην παίρνετε τυφλά το πρώτο. Μια κενή λίστα δεν σημαίνει αποτυχία εξουσιοδότησης· ο χρήστης ενδέχεται να μην έχει ακόμη δημιουργήσει κατάλληλο Key. Ο έλεγχος δικαιωμάτων του OAuth access token και το εύρος υπηρεσιών, οι ποσοστώσεις και οι όροι λήξης του ίδιου του API Key είναι διαφορετικοί περιορισμοί.

**Η άδεια ανάγνωσης API Key σημαίνει ότι τρίτος μπορεί να το αποθηκεύσει και να το χρησιμοποιήσει. Η ανάκληση του αιτήματος OAuth ή η εκκαθάριση της κατάστασης σύνδεσης της εφαρμογής δεν καθιστά άκυρο το ήδη αντιγραμμένο API Key· απαιτείται ο χρήστης να ανακαλέσει ή να περιστρέψει ξεχωριστά το Key στη διαχείριση διαπιστευτηρίων.**

## Εκτελέσιμο παράδειγμα προγράμματος περιήγησης Public / PKCE

Αναπτύξτε την παρακάτω σελίδα στο καταχωρισμένο `REDIRECT_URI`, αντικαταστήστε τα `CLIENT_ID` και τη διεύθυνση επανακλήσης. Το κουμπί εκκινεί την τυπική εξουσιοδότηση, και μετά την επιστροφή στην ίδια σελίδα διαβάζει το προφίλ και τον αριθμό των υπαρχόντων Key. Το παράδειγμα δεν εμφανίζει ούτε διατηρεί Key· η εφαρμογή παραγωγής καταναλώνει τα αποτελέσματα σύμφωνα με την πραγματική χρήση. Επαληθεύστε πρώτα σε ανεξάρτητη σελίδα προγράμματος περιήγησης και έπειτα πραγματοποιήστε την αποδοχή σύμφωνα με τις απαιτήσεις iframe που ακολουθούν.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Σύνδεση με το Ace Data Cloud</title>
<button id="connect" type="button">Σύνδεση λογαριασμού</button>
<p id="status" role="status">Δεν έχει συνδεθεί ακόμη</p>
<script type="module">

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`Η διεπαφή επέστρεψε HTTP ${response.status}`);
```

## iframe σε white-label ιστότοπους

### Ο ιστότοπος του πελάτη μεταβαίνει μόνος του στη σελίδα εξουσιοδότησης

Αρκεί να χρησιμοποιηθούν οι τυπικές παράμετροι OAuth και ο δικός του χειρισμός επανάκλησης· το `window.location.assign()` πλοηγεί το τρέχον iframe και η γονική σελίδα παραμένει στο white-label domain. Δεν χρειάζεται να προστεθεί `embed=studio` για το εικονίδιο ή να υλοποιηθεί το πρωτόκολλο μηνυμάτων του Studio.

Πρέπει να πληρούνται οι ακόλουθες προϋποθέσεις:

- Η σελίδα εφαρμογής και η σελίδα επανάκλησης χρησιμοποιούν HTTPS, είναι πραγματικά προσβάσιμες και επιτρέπουν την ενσωμάτωση μέσω iframe από το white-label γονικό domain· ελέγξτε και για τις δύο τις `Content-Security-Policy: frame-ancestors` και `X-Frame-Options`.
- Το sandbox επιτρέπει τα script, τις φόρμες και τις δυνατότητες προέλευσης／αποθήκευσης που χρειάζεται η σελίδα. Η υποστήριξη σύνδεσης με αναδυόμενο παράθυρο απαιτεί επίσης τις αντίστοιχες δυνατότητες αναδυόμενων παραθύρων· προτιμήστε τη διαμόρφωση του στοιχείου Website που παρέχει το Studio.
- Το πρόγραμμα περιήγησης επιτρέπει την αποθήκευση που απαιτείται για την κατάσταση εξουσιοδότησης στο τρέχον ενσωματωμένο σενάριο. Η κατάσταση σύνδεσης του white-label ιστότοπου και η κατάσταση σύνδεσης του AuthFrontend ενδέχεται να διαφέρουν· δεν πρέπει να υποτίθεται ότι η σύνδεση στον white-label ιστότοπο σημαίνει ότι ο χρήστης έχει ήδη συνδεθεί στη σελίδα εξουσιοδότησης.
- Η υπηρεσία ανταλλαγής token στην επανάκληση είναι διαθέσιμη και τα αιτήματα μεταξύ προελεύσεων επιτρέπουν την προέλευση της εφαρμογής· τα σφάλματα DNS, CORS και HTTP πρέπει όλα να εμφανίζουν κατάσταση με δυνατότητα επανάληψης και δεν πρέπει να σταματούν την απόδοση ολόκληρης της σελίδας.

Η αριστερή πλευρά της σελίδας εξουσιοδότησης διαβάζει το Logo της εφαρμογής OAuth· η δεξιά πλευρά διαβάζει το favicon／logo αυτού του Site όταν το πρόγραμμα περιήγησης μπορεί να παρέχει τη γονική προέλευση και το γονικό domain περνά τον έλεγχο επαληθευμένου ιστότοπου, διαφορετικά εμφανίζει το προεπιλεγμένο εικονίδιο. Αυτό καθορίζει μόνο την εμφάνιση επωνυμίας, δεν δημιουργεί συνεδρία σύνδεσης και δεν παρέχει δικαιώματα λογαριασμού στη σελίδα του πελάτη.

**Τρέχων περιορισμός: όταν το κανονικό OAuth μέσα σε iframe απαιτεί εκ νέου σύνδεση, υπάρχει ακόμη κενό στη ροή συνέχισης πίσω στη σελίδα εξουσιοδότησης μετά την ολοκλήρωση της σύνδεσης.** Πριν από την κυκλοφορία, πρέπει να γίνει ξεχωριστή αποδοχή για τις περιπτώσεις «Το Auth είναι συνδεδεμένο» και «Το Auth δεν είναι συνδεδεμένο／έχει λήξει». Πριν διορθωθεί και επαληθευτεί αυτό το κενό, η πρώτη σύνδεση μπορεί να ολοκληρωθεί μέσω ανεξάρτητης σελίδας με τυπικό OAuth ή να χρησιμοποιηθεί η εξουσιοδότηση του στοιχείου Studio παρακάτω· μην υπόσχεστε ότι όλα τα σενάρια iframe λειτουργούν βασιζόμενοι μόνο σε αποτελέσματα δοκιμών όταν ο χρήστης είναι ήδη συνδεδεμένος.

### Χρήση του τρέχοντος λογαριασμού Studio για εξουσιοδότηση

Στο Studio, ενεργοποιήστε το OAuth στις «Ρυθμίσεις → Αρχική σελίδα → Στοιχεία ιστότοπου» και συμπληρώστε το `client_id` και τη δηλωμένη διεύθυνση επανάκλησης. Ο ιστότοπος και η επανάκληση πρέπει να χρησιμοποιούν την ίδια προέλευση HTTPS και να διαφέρουν από την προέλευση του Studio. Η σελίδα τρίτου μέρους χρειάζεται να:

1. Στείλει το `acedatacloud:oauth:ready` στην ακριβή origin του γονικού ιστότοπου, να λάβει και να επαληθεύσει το `acedatacloud:oauth:init`.
2. Το κουμπί να δημιουργεί state και PKCE verifier και να στέλνει το `acedatacloud:oauth:authorize` (state, S256 challenge)· το verifier παραμένει στη δική του σελίδα.
3. Επαληθεύσει το γονικό παράθυρο, την origin και το state, να χειριστεί το code ή error στο `acedatacloud:oauth:result` και να το ανταλλάξει μέσω του τυπικού endpoint token.
Το Studio εμφανίζει τη σελίδα εξουσιοδότησης στην περιοχή του στοιχείου· αφού ο χρήστης συναινέσει, επιστρέφει τον κωδικό εξουσιοδότησης μέσω μηνύματος και η εφαρμογή δεν χρειάζεται να ανακατευθύνει. Όταν δεν υπάρχει σύνδεση επιστρέφεται `login_required`, όταν απορρίπτεται επιστρέφεται `access_denied` και όταν λήξει ο χρόνος αναμονής επιστρέφεται `authorization_timeout`. Η αλλαγή λογαριασμού θα αναδημιουργήσει το iframe της εφαρμογής και θα ακυρώσει τις μη ολοκληρωμένες εξουσιοδοτήσεις.

Το στοιχείο ζητά επί του παρόντος `profile:read credentials:read` και δεν περιλαμβάνει `offline_access`. Μην υποθέτετε ότι θα λαμβάνεται οπωσδήποτε refresh token. Τα `embed=studio` και `embed_origin` διατηρούνται από τον κεντρικό υπολογιστή Studio και τη σελίδα εξουσιοδότησης· η σελίδα πελάτη χρειάζεται μόνο να τηρεί το πρωτόκολλο μηνυμάτων.

Για ένα πλήρες παράδειγμα κουμπιού, δείτε τον [Οδηγό ενσωμάτωσης OAuth στοιχείων ιστότοπου Studio](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Κύκλος ζωής, ανανέωση και ανάκληση

Η προεπιλεγμένη διάρκεια ισχύος του access token είναι 15 ημέρες και η ανανέωση ή επανεξουσιοδότηση θα πρέπει να προγραμματίζεται με βάση το `expires_in` κάθε απόκρισης· το refresh token έχει προεπιλεγμένη διάρκεια 30 ημερών και η διάρκειά του επηρεάζεται από τη ρύθμιση της υπηρεσίας. Μην κωδικοποιείτε αυτές τις δύο τιμές ως μόνιμες δεσμεύσεις.

Αφού εγκριθεί το `offline_access`, μπορείτε να καλέσετε:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Η ανανέωση επιστρέφει νέα token και η εφαρμογή θα πρέπει να αποθηκεύει τις πιο πρόσφατες τιμές. Κατά την ανανέωση ελέγχεται αν η εφαρμογή εξακολουθεί να είναι έγκυρη, αν ο χρήστης είναι διαθέσιμος και αν τα δικαιώματα εξακολουθούν να έχουν εγκριθεί. Σε περίπτωση αποτυχίας, εκκαθαρίστε τη δική σας κατάσταση σύνδεσης και εξουσιοδοτήστε ξανά.

**Η τρέχουσα υλοποίηση ανανέωσης OAuth δεν εγγυάται ότι το παλιό refresh token καθίσταται αμέσως άκυρο μετά την ανανέωση.** Μην αντιμετωπίζετε τη λήψη νέου token ως ένδειξη ότι το παλιό token έχει ανακληθεί και μη χρησιμοποιείτε την εναλλαγή secret ως υποκατάστατο του τερματισμού υπαρχόντων token.

Ο τρόπος κλήσης του αιτήματος ανάκλησης είναι:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Το τρέχον endpoint ανάκλησης επιστρέφει HTTP 200, αλλά δεν υλοποιεί άμεση ακύρωση των JWT που έχουν εκδοθεί.** Η εφαρμογή θα πρέπει να εκκαθαρίζει τα token που έχει αποθηκεύσει η ίδια και δεν μπορεί να θεωρεί το 200 ως απόδειξη ότι όλα τα εκδοθέντα token ή API Key έχουν καταστεί άκυρα. Για API Key που έχουν διαρρεύσει ή αντιγραφεί, ανακαλέστε ή εναλλάξτε ξεχωριστά τα αντίστοιχα διαπιστευτήρια.

## Συνήθη σφάλματα και αποδοχή

| Σύμπτωμα／σφάλμα                         | Έλεγχος                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Χρησιμοποιήστε τα τρέχοντα ονόματα δικαιωμάτων· ελέγξτε το εύρος καταχώρισης της εφαρμογής, τους περιορισμούς εκχώρησης και τα δικαιώματα χρήστη. Ο πλήρης κατάλογος Discovery δεν είναι κατάλογος επιλογών εφαρμογής                      |
| `invalid_request`             | Υποχρεωτικές παράμετροι, ακριβής διεύθυνση callback, S256 challenge και method για Public πελάτες                        |
| `invalid_client`              | client ID, κατάσταση εφαρμογής, secret για Confidential πελάτες· ελέγξτε αν χρησιμοποιείται εσφαλμένα Basic authentication             |
| `invalid_grant`               | Ο code έχει λήξει／έχει καταναλωθεί, ή το verifier ή redirect URI δεν ταιριάζει· κατά την ανανέωση ελέγχονται επίσης αλλαγές εφαρμογής και δικαιωμάτων                 |
| `access_denied`               | Ο χρήστης απέρριψε, επαναφέρετε το κουμπί σύνδεσης, μην εμφανίζετε επαναλαμβανόμενα την εξουσιοδότηση                                                  |
| `unsupported_grant_type`      | Προς το παρόν υποστηρίζονται τα `authorization_code`、`refresh_token`                             |
| HTTP 401／403                  | Διακρίνετε μεταξύ μη έγκυρης κατάστασης σύνδεσης, token, scope εξουσιοδότησης και δικαιωμάτων πρόσβασης του ίδιου του πόρου                                     |
| `Failed to fetch`、σφάλματα DNS／CORS | Επαληθεύστε τον πραγματικό κεντρικό υπολογιστή αιτήματος και τη διαθεσιμότητα του backend πελάτη· δεν μπορεί να αποδοθεί στο ότι «ο χρήστης δεν έχει Key»                                      |
| Έχει εξουσιοδοτηθεί αλλά δεν μπορεί να διαβαστεί το Key                   | Χρησιμοποιήστε `platform.acedata.cloud`, το πραγματικό user ID, `items[*].token`· διακρίνετε μεταξύ κενής λίστας, σελιδοποίησης και αποτυχημένων αποκρίσεων |
| Κενή ολόκληρη σελίδα μετά την επιστροφή εξουσιοδότησης                     | Αποδώστε πρώτα τη σελίδα· χειριστείτε ξεχωριστά τα σφάλματα για callback, token, UserInfo και αιτήματα διαπιστευτηρίων· μην επιτρέπετε σε εξαίρεση αρχικοποίησης να σταματά ολόκληρη τη σελίδα                      |
| Δεν συνεχίζει μετά τη σύνδεση στο iframe                 | Χειριστείτε σύμφωνα με τους υπάρχοντες περιορισμούς παραπάνω· δοκιμάστε σενάρια χωρίς σύνδεση, ληγμένης σύνδεσης, απόρριψης και επανασύνδεσης                                          |

Πριν από την παράδοση, επαληθεύστε τουλάχιστον: σωστό callback, απόρριψη, εσφαλμένο state, ληγμένο／ήδη καταναλωμένο code, χωρίς Key, αποτυχία δικτύου, ληγμένο token, απουσία απαιτούμενου scope, καθώς και την πρώτη σύνδεση και αλλαγή λογαριασμού σε σενάρια iframe. Μην αποθηκεύετε πλήρη code, token ή API Key στα αποδεικτικά δοκιμών.
