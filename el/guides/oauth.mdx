---
title: "Ενσωμάτωση Ace Data Cloud OAuth 2.0"
---

Επιτρέψτε στους χρήστες να εξουσιοδοτούν την εφαρμογή σας να έχει πρόσβαση στο προφίλ Ace Data Cloud, στις συνδρομές υπηρεσιών, στα API Key, στη χρήση ή στις παραγγελίες τους. Χρησιμοποιήστε το πρότυπο **Authorization Code + S256 PKCE**: η εφαρμογή ανοίγει τη σελίδα εξουσιοδότησης, ο χρήστης συναινεί και στη συνέχεια λαμβάνει ένα εφάπαξ `code`, το οποίο ανταλλάσσεται για OAuth access token.

Το OAuth access token χρησιμοποιείται για την πρόσβαση σε διεπαφές πόρων λογαριασμού· για την κλήση του API μοντέλων χρησιμοποιήστε το αντίστοιχο API Key. Η OAuth εξουσιοδότηση δεν δημιουργεί αυτόματα API Key, δεν ενεργοποιεί υπηρεσίες και δεν αυξάνει το υπόλοιπο.

## Επιλογή τρόπου ενσωμάτωσης

| Τρόπος            | Κατάλληλο σενάριο                                | Μετά την ολοκλήρωση της εξουσιοδότησης                                           |
| ------------- | ----------------------------------- | ----------------------------------------------- |
| Τυπική ανακατεύθυνση OAuth   | Ανεξάρτητοι ιστότοποι, εφαρμογές υπολογιστή ή κινητού· ενσωματωμένοι ιστότοποι που ξεκινούν μόνοι τους την εξουσιοδότηση            | Ο περιηγητής επιστρέφει στο `redirect_uri` που έχει καταχωρίσει η εφαρμογή και η εφαρμογή επεξεργάζεται τα `code` και `state` |
| Εξουσιοδότηση στοιχείου ιστότοπου Studio | Ο ιστότοπος ενσωματώνει την αρχική σελίδα του Studio και επιθυμεί να χρησιμοποιεί τον τρέχοντα λογαριασμό Studio του επισκέπτη | Το Studio στέλνει στην εφαρμογή μήνυμα με το αποτέλεσμα εξουσιοδότησης, η εφαρμογή δεν ανακατευθύνεται και η αρχική σελίδα διατηρείται                  |

Η τυπική ανακατεύθυνση δεν απαιτεί `embed=studio`, `embed_origin` ή `postMessage`. Στη λειτουργία στοιχείου Studio, ο host δημιουργεί τη σελίδα εξουσιοδότησης και διατηρεί τη γέφυρα μηνυμάτων· τρίτοι ενσωματώνονται σύμφωνα με το πρωτόκολλο στοιχείου στο τέλος αυτού του κειμένου και δεν πρέπει να συνθέτουν μόνοι τους αυτές τις δύο παραμέτρους.

## Endpoints και έγγραφο discovery

```bash
curl https://auth.acedata.cloud/.well-known/oauth-authorization-server
```

| Χρήση                | Διεύθυνση                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| Σελίδα εξουσιοδότησης περιηγητή            | `https://auth.acedata.cloud/oauth2/authorize`                                     |
| Ανταλλαγή／ανανέωση OAuth token | `POST https://auth.acedata.cloud/oauth2/token`                                    |
| Υποβολή αιτήματος ανάκλησης            | `POST https://auth.acedata.cloud/oauth2/revoke`                                   |
| Πληροφορίες τρέχοντος χρήστη            | `GET https://auth.acedata.cloud/api/v1/users/me`                                  |
| Σελίδα διαχείρισης εφαρμογών OAuth      | [Εφαρμογές OAuth](https://auth.acedata.cloud/user/oauth-apps)                            |
| Λίστα εφαρμογών／διεπαφή εγγραφής του συνδεδεμένου χρήστη   | `https://auth.acedata.cloud/api/v1/oauth2/applications/`                          |
| Δημόσια στοιχεία εφαρμογής που χρησιμοποιεί η σελίδα εξουσιοδότησης      | `GET https://auth.acedata.cloud/api/v1/oauth2/application/<client_id>/`           |
| Υφιστάμενα API Key του χρήστη     | `GET https://platform.acedata.cloud/api/v1/credentials/?user_id=<ID χρήστη>&limit=100` |

Η διεπαφή διαχείρισης εφαρμογών απαιτεί πιστοποίηση σύνδεσης λογαριασμού και δεν είναι διεπαφή ανώνυμης δυναμικής εγγραφής (DCR). Τα endpoints discovery／εγγραφής της ίδιας της υπηρεσίας MCP είναι διαφορετικά σημεία εισόδου από τα OAuth endpoints λογαριασμού αυτού του πίνακα· όταν συνδέεστε σε συγκεκριμένο MCP, ενεργήστε σύμφωνα με την τεκμηρίωση και τα αποτελέσματα discovery της υπηρεσίας.

Το έγγραφο discovery χρησιμοποιείται για τη λήψη endpoints και δυνατοτήτων πρωτοκόλλου. Η τρέχουσα ροή επιστρέφει OAuth token, δεν επιστρέφει `id_token`· μην επεξεργάζεστε τη ροή ως πλήρη διαδικασία σύνδεσης OpenID Connect μόνο και μόνο επειδή υπάρχει το scope `openid`.

## Εύρος δικαιωμάτων: χρησιμοποιήστε τα τρέχοντα ονόματα scope

Το `scope` είναι όνομα δικαιώματος διαχωρισμένο με κενά και με διάκριση πεζών-κεφαλαίων. Οι νέες εφαρμογές χρησιμοποιούν συγκεκριμένα δικαιώματα όπως `profile:read`, `email:read`, `phone:read`.

### Από πού λαμβάνετε τα διαθέσιμα δικαιώματα προς αίτηση

Μετά τη σύνδεση, η διεπαφή λίστας εφαρμογών OAuth `GET /api/v1/oauth2/applications/` επιστρέφει `available_scopes`· ο επιλογέας δικαιωμάτων στη σελίδα διαχείρισης εφαρμογών χρησιμοποιεί τον ίδιο κατάλογο. Αυτά είναι τα προαιρετικά scopes που πρέπει να χρησιμοποιούν οι συνήθεις εφαρμογές self-service.

**Το `scopes_supported` του Discovery περιλαμβάνει όλα τα ονόματα δικαιωμάτων που αναγνωρίζει η πλατφόρμα και δεν σημαίνει ότι η εφαρμογή σας μπορεί να ζητήσει καθένα από αυτά.** Η πραγματική εξουσιοδότηση ελέγχει ταυτόχρονα:

1. εάν το δικαίωμα επιτρέπεται να εκχωρηθεί σε αυτόν τον τύπο εφαρμογής·
2. εάν το δικαίωμα έχει καταχωριστεί στα επιτρεπόμενα scopes αυτής της εφαρμογής OAuth·
3. εάν ο τρέχων χρήστης διαθέτει το αιτούμενο δικαίωμα.

Άγνωστα, μη καταχωρισμένα, μη επιτρεπόμενα για εκχώρηση δικαιώματα ή δικαιώματα που δεν διαθέτει ο χρήστης επιστρέφουν `invalid_scope`. Κατά την ανταλλαγή κωδικού εξουσιοδότησης και την ανανέωση γίνεται επίσης επανέλεγχος· τα δικαιώματα δεν συμπληρώνονται ούτε αναβαθμίζονται αυτόματα.

### Προαιρετικά δικαιώματα για συνήθεις εφαρμογές self-service

Ακολουθεί ο τρέχων κατάλογος (2026-10-09)· κατά την ενσωμάτωση, χρησιμοποιήστε το `available_scopes` ως αναφορά.

| Scope                                            | Χρήση                                      |
| ------------------------------------------------ | --------------------------------------- |
| `profile:read` / `profile:write`                 | Ανάγνωση／ενημέρωση προσωπικού προφίλ                               |
| `email:read`                                     | Ανάγνωση email                                    |
| `phone:read`                                     | Ανάγνωση αριθμού κινητού και περιοχής                                |
| `billing-profile:read` / `billing-profile:write` | Ανάγνωση／διαχείριση στοιχείων χρέωσης                               |
| `applications:read` / `applications:write`       | Ανάγνωση／διαχείριση συνδρομών υπηρεσιών                               |
| `credentials:read` / `credentials:write`         | Ανάγνωση／διαχείριση API Key                           |
| `usage:read`                                     | Ανάγνωση αρχείων κλήσεων                                  |
| `orders:read` / `orders:write`                   | Ανάγνωση／δημιουργία και διαχείριση παραγγελιών                              |
| `auto-recharge:read` / `auto-recharge:write`     | Ανάγνωση／διαχείριση ρυθμίσεων αυτόματης επαναφόρτισης                             |
| `recharge-cards:redeem`                          | Εξαργύρωση καρτών επαναφόρτισης                                   |
| `coin:read`                                      | Ανάγνωση πληροφοριών σχετικών με tokens                                |
| `distribution:read`                              | Ανάγνωση πληροφοριών διανομής                                  |
| `connections:read` / `connections:write`         | Ανάγνωση／διαχείριση συνδέσεων                                 |
| `skills:read` / `skills:write`                   | Ανάγνωση／διαχείριση δεξιοτήτων                                 |
| `openid`                                         | Η τρέχουσα υλοποίηση επιτρέπει επίσης στο UserInfo να επιστρέφει βασικά στοιχεία· δεν επιστρέφει ID Token    |
| `offline_access`                                 | Αίτημα refresh token, ώστε να γίνεται ανανέωση μετά τη λήξη του access token |

Για παράδειγμα, για ανάγνωση μόνο του προσωπικού προφίλ χρησιμοποιήστε `profile:read`· αν χρειάζεστε και email, προσθέστε `email:read`· για ανάγνωση υπαρχόντων API Key χρησιμοποιήστε `profile:read credentials:read`. Ζητήστε `credentials:write` μόνο όταν χρειάζεται πράγματι να δημιουργήσετε ή να τροποποιήσετε Key και προσθέστε `offline_access` όταν χρειάζεται ανανέωση.

Ορισμένα δικαιώματα προορίζονται μόνο για αξιόπιστες εφαρμογές εγκεκριμένες από την πλατφόρμα, όπως `sites:read`, `sites:write`, `platform-tokens:read`· άλλα δικαιώματα δεν είναι διαθέσιμα σε συνήθεις εφαρμογές OAuth τρίτων. Οι τύποι client `public`／`confidential` περιγράφουν εάν μπορεί να διατηρηθεί με ασφάλεια ένα secret και δεν σχετίζονται με το εάν η εφαρμογή είναι αξιόπιστη. Οι εφαρμογές που δημιουργούνται self-service δεν μπορούν να ενεργοποιήσουν μόνες τους αξιόπιστα δικαιώματα.

Το `account` είναι ο επιλογέας δικαιωμάτων λογαριασμού που χρησιμοποιείται από το καθορισμένο επίσημο MCP διαχείρισης λογαριασμού, δεν είναι scope «όλων των δικαιωμάτων» για εφαρμογές τρίτων και δεν μπορεί να χρησιμοποιηθεί μαζί με άλλα scope. Τρίτοι πρέπει να αναφέρουν ρητά τα συγκεκριμένα δικαιώματα που χρειάζονται.

### Μετάβαση από την παλιά τεκμηρίωση

| Παλιά γραφή                                         | Τρέχων τρόπος                       |
| ------------------------------------------- | -------------------------- |
| `profile`                                   | `profile:read`             |
| `email`                                     | `email:read`               |
| `phone`                                     | `phone:read`               |
| `platform`、`platform:read`、`platform:write` | Αναφέρετε ξεχωριστά τα συγκεκριμένα δικαιώματα που χρειάζεστε πραγματικά· δεν υπάρχει γενική τιμή αντικατάστασης «επιλογή όλων» |

Τα παλιά ονόματα δεν γίνονται δεκτά ως συμβατά ψευδώνυμα. Ενημερώστε ταυτόχρονα τα scopes που έχουν καταχωριστεί για την εφαρμογή OAuth, το URL εξουσιοδότησης και τον δικό σας έλεγχο δικαιωμάτων· η τροποποίηση της ρύθμισης εφαρμογής δεν προσθέτει δικαιώματα σε ήδη εκδομένα token και απαιτείται νέα εξουσιοδότηση από τον χρήστη.

## Βήμα 1: Καταχώριση εφαρμογής OAuth

Ανοίξτε τη [Διαχείριση εφαρμογών OAuth](https://auth.acedata.cloud/user/oauth-apps), δημιουργήστε μια εφαρμογή και συμπληρώστε:
- Όνομα, περιγραφή, λογότυπο εφαρμογής: εμφανίζονται στην πλευρά της εφαρμογής στη σελίδα εξουσιοδότησης.
- Τύπος πελάτη: για καθαρά frontend, mobile ή desktop clients επιλέξτε **Public**· για υπηρεσίες που μπορούν να διατηρούν το secret στο backend επιλέξτε **Confidential**.
- Διεύθυνση επανακλήσης: χρησιμοποιήστε HTTPS στο περιβάλλον παραγωγής και καταχωρίστε το πλήρες URL που πραγματικά χειρίζεται την επανακλήση η εφαρμογή.
- Δικαιώματα: επιλέξτε τα scopes που πραγματικά χρειάζεστε από τον κατάλογο που παρέχεται στη σελίδα.

Αποθηκεύστε το `client_id`. Οι Confidential clients αποθηκεύουν το `client_secret` στην πλευρά του διακομιστή και δεν μπορούν να το τοποθετούν σε HTML, μεταβλητές frontend build ή URL. Οι Public clients δεν χρησιμοποιούν secret για την ανταλλαγή token· ακόμη και αν η απόκριση εγγραφής περιλαμβάνει αυτό το πεδίο, δεν μπορεί να αντιμετωπίζεται ως διαπιστευτήριο που ο client μπορεί να διατηρήσει μυστικό.

Το `redirect_uri` πρέπει να είναι ακριβώς ίδιο κατά την εγγραφή, την εξουσιοδότηση και την ανταλλαγή token, συμπεριλαμβανομένων της διαδρομής, της τελικής κάθετου και των παραμέτρων ερωτήματος. Κάθε λογαριασμός μπορεί να δημιουργήσει έως 20 εφαρμογές. Το Secret εμφανίζεται μόνο κατά τη δημιουργία／περιστροφή· μετά την περιστροφή, το παλιό secret δεν μπορεί πλέον να συνεχίσει ανταλλαγές που απαιτούν ταυτοποίηση client.

## Βήμα 2: Το κουμπί ξεκινά την εξουσιοδότηση

Σε κάθε κλικ σύνδεσης, δημιουργήστε νέο τυχαίο `state` και `code_verifier`, υπολογίστε:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Αποθηκεύστε το `state`, το verifier και τη διεύθυνση επανακλήσης στη συνεδρία της ίδιας της εφαρμογής και, στη συνέχεια, ανοίξτε τη σελίδα εξουσιοδότησης με παραμέτρους κωδικοποιημένες σε URL:

```text
https://auth.acedata.cloud/oauth2/authorize
  ?response_type=code
  &client_id=<client_id>
  &redirect_uri=<πλήρης διεύθυνση επανακλήσης>
  &scope=profile%3Aread%20credentials%3Aread
  &state=<τυχαία τιμή αυτής της φοράς>
  &code_challenge=<τιμή πρόκλησης S256 αυτής της φοράς>
  &code_challenge_method=S256
```

Οι Public clients πρέπει να στέλνουν S256 PKCE. Παρόλο που το Discovery εξακολουθεί να αναφέρει το `plain`, οι Public clients δεν μπορούν να το χρησιμοποιούν. Συνιστάται επίσης οι Confidential clients να χρησιμοποιούν S256· εάν χρησιμοποιήθηκε PKCE κατά την έναρξη της εξουσιοδότησης, τότε πρέπει να υποβληθεί το αντίστοιχο verifier κατά την ανταλλαγή.

Αφού ο χρήστης συναινέσει, επιστρέφει στο `redirect_uri`, και οι παράμετροι ερωτήματος περιλαμβάνουν `code` και το `state` που επιστράφηκε αυτούσιο. Σε περίπτωση απόρριψης, επιστρέφονται `error=access_denied`, περιγραφή σφάλματος και `state`. Πριν από την επεξεργασία της επανακλήσης, επαληθεύστε πρώτα ότι το state αντιστοιχεί στην τρέχουσα συνεδρία. Ο κωδικός εξουσιοδότησης ισχύει για 10 λεπτά και μπορεί να ανταλλαχθεί μόνο μία φορά· μετά από αποτυχία, ξεκινήστε ξανά τη σύνδεση και μην ανανεώνετε επανειλημμένα το παλιό URL επανακλήσης.

## Βήμα 3: Ανταλλαγή για OAuth token

Οι Public clients πραγματοποιούν την ανταλλαγή απευθείας από τον browser ή τον client· οι Confidential clients πραγματοποιούν την ανταλλαγή στο δικό τους backend. Το σώμα του αιτήματος υποστηρίζει κωδικοποίηση φόρμας και οι ακόλουθες μεταβλητές αντιπροσωπεύουν τα δεδομένα που έλαβε η εφαρμογή από την τρέχουσα εξουσιοδότηση:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=authorization_code \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode "code=$AUTHORIZATION_CODE" \
  --data-urlencode "code_verifier=$PKCE_VERIFIER"
```

Οι Confidential clients πρέπει επίσης να προσθέσουν το πεδίο φόρμας `client_secret` στην πλευρά του διακομιστή. Προς το παρόν υποστηρίζεται το `client_secret_post`· μην θεωρείτε την ταυτοποίηση HTTP Basic client ως υποστηριζόμενη μέθοδο.

Στην επιτυχή απόκριση, διαβάστε τα `access_token`, `token_type`, `expires_in` και το scope που πραγματικά εκχωρήθηκε. Υπάρχει `refresh_token` μόνο εάν ζητήθηκε και εγκρίθηκε το `offline_access`. Μην αντιμετωπίζετε το OAuth access token ως API Key του model API και μην γράφετε token, verifier ή κωδικούς εξουσιοδότησης σε logs, analytics events ή κοινόχρηστους συνδέσμους.

## Βήμα 4: Ανάγνωση πληροφοριών χρήστη και API Key

Χρησιμοποιήστε πρώτα το OAuth access token για να ζητήσετε το UserInfo:

```bash
curl https://auth.acedata.cloud/api/v1/users/me \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Τα πεδία επιστροφής εξαρτώνται από το scope: το `id` είναι το αναγνωριστικό χρήστη· με `profile:read` ή `openid` μπορούν να διαβαστούν βασικά στοιχεία (όπως `username`, `nickname`, `avatar`, `is_verified`, `date_joined`, `registration_method`)· για email απαιτείται `email:read`, και για αριθμό τηλεφώνου και περιοχή απαιτείται `phone:read`. Μην βασίζεστε στο ότι μη εξουσιοδοτημένα πεδία θα υπάρχουν πάντα.

Όταν απαιτείται υπάρχον API Key και έχει εγκριθεί το `credentials:read`, χρησιμοποιήστε το `id` του UserInfo ως συνθήκη φιλτραρίσματος:

```bash
curl "https://platform.acedata.cloud/api/v1/credentials/?user_id=$USER_ID&limit=100&offset=0" \
  -H "Authorization: Bearer $OAUTH_ACCESS_TOKEN"
```

Η λίστα επιστροφής χρησιμοποιεί `count` και `items`, και το πεδίο Key είναι **`items[*].token`**, όχι `data[0].value`. Το `user_id=me` δεν είναι έγκυρο user ID για αυτό το API. Για δεδομένα πολλών σελίδων, συνεχίστε την ανάγνωση με `offset`／`limit` και μην αντιμετωπίζετε την πρώτη σελίδα ως όλα τα διαπιστευτήρια.

Επιλέξτε το κατάλληλο διαπιστευτήριο ανάλογα με την εφαρμογή, την υπηρεσία και την κατάσταση ισχύος· μην παίρνετε τυφλά το πρώτο. Μια κενή λίστα δεν σημαίνει αποτυχία εξουσιοδότησης· ο χρήστης μπορεί να μην έχει ακόμη δημιουργήσει κατάλληλο Key. Ο έλεγχος δικαιωμάτων του OAuth access token και το εύρος υπηρεσιών, η ποσόστωση και οι όροι λήξης του ίδιου του API Key είναι διαφορετικοί περιορισμοί.

**Η άδεια ανάγνωσης API Key σημαίνει ότι τρίτος μπορεί να το αποθηκεύσει και να το χρησιμοποιήσει. Η ανάκληση του OAuth αιτήματος ή η εκκαθάριση της κατάστασης σύνδεσης της εφαρμογής δεν καθιστά άκυρο ένα API Key που έχει ήδη αντιγραφεί· ο χρήστης πρέπει να ανακαλέσει ή να περιστρέψει ξεχωριστά αυτό το Key στη διαχείριση διαπιστευτηρίων.**

## Εκτελέσιμο παράδειγμα Public / PKCE browser

Αναπτύξτε την παρακάτω σελίδα στο καταχωρισμένο `REDIRECT_URI`, αντικαταστήστε τα `CLIENT_ID` και τη διεύθυνση επανακλήσης. Το κουμπί ξεκινά την τυπική εξουσιοδότηση και, αφού επιστρέψει στην ίδια σελίδα, διαβάζει τα προσωπικά στοιχεία και τον αριθμό των υπαρχόντων Key. Το παράδειγμα δεν εμφανίζει ούτε διατηρεί Key· οι εφαρμογές παραγωγής καταναλώνουν τα αποτελέσματα σύμφωνα με την πραγματική χρήση. Επαληθεύστε πρώτα σε ανεξάρτητη σελίδα browser και, στη συνέχεια, πραγματοποιήστε την αποδοχή σύμφωνα με τις ακόλουθες απαιτήσεις iframe.
```html
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>Σύνδεση με το Ace Data Cloud</title>
<button id="connect" type="button">Σύνδεση λογαριασμού</button>
<p id="status" role="status">Δεν έχει συνδεθεί ακόμη</p>
<script type="module">
const CLIENT_ID = 'αντικαταστήστε με το client_id σας';
const REDIRECT_URI = 'https://your-app.example/connect';
const AUTH_ORIGIN = 'https://auth.acedata.cloud';
const button = document.querySelector('#connect');
const status = document.querySelector('#status');
const storageKey = state => `ace-oauth:${state}`;

function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

async function requestJson(url, options = {}) {
  const response = await fetch(url, { ...options, signal: AbortSignal.timeout(15000) });
  if (!response.ok) throw new Error(`Η διεπαφή επέστρεψε HTTP ${response.status}`);
  return response.json();
}

button.addEventListener('click', async () => {
  button.disabled = true;
  try {
    const state = base64url(crypto.getRandomValues(new Uint8Array(24)));
    const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
    const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
    sessionStorage.setItem(storageKey(state), JSON.stringify({
      verifier, redirectUri: REDIRECT_URI, createdAt: Date.now()
    }));
    const url = new URL('/oauth2/authorize', AUTH_ORIGIN);
    url.search = new URLSearchParams({
      response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
      scope: 'profile:read credentials:read', state,
      code_challenge: base64url(new Uint8Array(digest)), code_challenge_method: 'S256'
    }).toString();
    window.location.assign(url);
  } catch {
    status.textContent = 'Δεν είναι δυνατή η έναρξη της σύνδεσης, ελέγξτε τις ρυθμίσεις αποθήκευσης του προγράμματος περιήγησης και δοκιμάστε ξανά.';
    button.disabled = false;
  }
});

async function handleCallback() {
  const url = new URL(window.location.href);
  if (!url.searchParams.has('code') && !url.searchParams.has('error')) return;
  button.disabled = true;
  try {
    const state = url.searchParams.get('state');
    const raw = state && sessionStorage.getItem(storageKey(state));
    if (!raw) throw new Error('Η συνεδρία εξουσιοδότησης δεν ταιριάζει, συνδεθείτε ξανά.');
    const transaction = JSON.parse(raw);
    const age = Date.now() - transaction.createdAt;
    if (!Number.isFinite(age) || age < 0 || age > 10 * 60 * 1000 ||
        transaction.redirectUri !== REDIRECT_URI || !transaction.verifier) {
      throw new Error('Η συνεδρία εξουσιοδότησης έχει λήξει, συνδεθείτε ξανά.');
    }
    sessionStorage.removeItem(storageKey(state));
    const code = url.searchParams.get('code');
    const denied = url.searchParams.get('error');
    for (const key of ['code', 'state', 'error', 'error_description']) url.searchParams.delete(key);
    window.history.replaceState({}, '', url);
    if (denied) throw new Error('Η εξουσιοδότηση δεν ολοκληρώθηκε, μπορείτε να συνδεθείτε ξανά.');
    if (!code) throw new Error('Δεν υπάρχει κωδικός εξουσιοδότησης στην επιστροφή κλήσης, συνδεθείτε ξανά.');
    status.textContent = 'Σύνδεση…';
    const token = await requestJson(`${AUTH_ORIGIN}/oauth2/token`, {
      method: 'POST',
      body: new URLSearchParams({
        grant_type: 'authorization_code', client_id: CLIENT_ID,
        redirect_uri: REDIRECT_URI, code, code_verifier: transaction.verifier
      })
    });
    if (!token.access_token) throw new Error('Δεν λήφθηκε διακριτικό εξουσιοδότησης.');
    const headers = { Authorization: `Bearer ${token.access_token}` };
    const profile = await requestJson(`${AUTH_ORIGIN}/api/v1/users/me`, { headers });
    if (!profile.id) throw new Error('Δεν λήφθηκε αναγνωριστικό χρήστη.');
    const keysUrl = new URL('https://platform.acedata.cloud/api/v1/credentials/');
    keysUrl.search = new URLSearchParams({ user_id: profile.id, limit: '100' }).toString();
    const credentials = await requestJson(keysUrl, { headers });
    if (!Array.isArray(credentials.items)) throw new Error('Η μορφή της λίστας διαπιστευτηρίων δεν είναι έγκυρη.');
    const keyCount = credentials.items.filter(item => typeof item.token === 'string' && item.token).length;
    status.textContent = `Συνδέθηκε ${profile.nickname || profile.username || profile.id}· υπάρχουν ${keyCount} API Key σε αυτήν τη σελίδα.`;
  } catch (error) {
    status.textContent = `Η σύνδεση δεν ολοκληρώθηκε: ${error.message || 'σφάλμα δικτύου'} Κάντε ξανά κλικ στη σύνδεση.`;
  } finally {
    button.disabled = false;
  }
}

await handleCallback();
</script>
</html>
```

Η επιστροφή κλήσης και το σημείο εισόδου του παραδείγματος πρέπει να βρίσκονται στην ίδια προέλευση, στην ίδια καρτέλα προγράμματος περιήγησης／iframe, ώστε να είναι δυνατή η ανάγνωση του αρχικά αποθηκευμένου `sessionStorage`. Οι εφαρμογές παραγωγής θα πρέπει να διαχειρίζονται τα διακριτικά στο δικό τους σχήμα συνεδρίας, να χειρίζονται τη λήξη και να καθαρίζουν τις παραμέτρους URL εξουσιοδότησης μετά τη λήψη της απόκρισης· η κύρια διεπαφή της σελίδας θα πρέπει να αποδίδεται πρώτα και οι αποτυχίες δικτύου να επηρεάζουν μόνο την κατάσταση σύνδεσης.

## iframe σε ιστοτόπους white-label

### Ο ιστότοπος πελάτη μεταβαίνει μόνος του στη σελίδα εξουσιοδότησης

Αρκεί η χρήση των τυπικών παραμέτρων OAuth και του δικού σας χειρισμού επιστροφής κλήσης· το `window.location.assign()` πλοηγεί το τρέχον iframe, ενώ η γονική σελίδα παραμένει στο domain white-label. Δεν χρειάζεται να προσθέσετε `embed=studio` για το εικονίδιο ή να υλοποιήσετε το πρωτόκολλο μηνυμάτων Studio.

Πρέπει να πληρούνται οι ακόλουθες προϋποθέσεις:

- Η σελίδα εφαρμογής και η σελίδα επιστροφής κλήσης χρησιμοποιούν HTTPS, είναι πράγματι προσβάσιμες και επιτρέπουν την ενσωμάτωση μέσω iframe από το γονικό domain white-label· ελέγξτε τα `Content-Security-Policy: frame-ancestors` και `X-Frame-Options` και των δύο πλευρών.
- Το sandbox επιτρέπει τα script, τις φόρμες και τις δυνατότητες προέλευσης／αποθήκευσης που χρειάζεται η σελίδα. Όταν υποστηρίζεται σύνδεση με αναδυόμενο παράθυρο, απαιτούνται και οι αντίστοιχες δυνατότητες αναδυόμενων παραθύρων· προτιμήστε τη ρύθμιση του στοιχείου Website που παρέχει το Studio.
- Το πρόγραμμα περιήγησης επιτρέπει στον τρέχοντα ενσωματωμένο τρόπο χρήσης την αποθήκευση που απαιτείται για την κατάσταση εξουσιοδότησης. Η κατάσταση σύνδεσης του ιστότοπου white-label και η κατάσταση σύνδεσης του AuthFrontend ενδέχεται να διαφέρουν· δεν πρέπει να υποθέτετε ότι η σύνδεση στον ιστότοπο white-label σημαίνει ότι έχει γίνει ήδη σύνδεση στη σελίδα εξουσιοδότησης.
- Η υπηρεσία ανταλλαγής token στην επιστροφή κλήσης είναι διαθέσιμη και τα αιτήματα μεταξύ προελεύσεων επιτρέπουν την προέλευση της εφαρμογής· τα σφάλματα DNS, CORS και HTTP πρέπει όλα να εμφανίζουν κατάσταση που επιτρέπει επανάληψη, χωρίς να σταματά η απόδοση ολόκληρης της σελίδας.

Η αριστερή πλευρά της σελίδας εξουσιοδότησης διαβάζει το Logo της εφαρμογής OAuth· η δεξιά πλευρά διαβάζει το favicon／logo αυτού του Site όταν το πρόγραμμα περιήγησης μπορεί να παρέχει τη γονική προέλευση και το γονικό domain περνά την επαλήθευση επαληθευμένου ιστότοπου, διαφορετικά εμφανίζει το προεπιλεγμένο εικονίδιο. Αυτό καθορίζει μόνο την εμφάνιση της επωνυμίας, δεν δημιουργεί συνεδρία σύνδεσης και δεν παρέχει δικαιώματα λογαριασμού στη σελίδα πελάτη.

**Τρέχων περιορισμός: όταν το συνηθισμένο OAuth σε iframe χρειάζεται νέα σύνδεση, εξακολουθεί να υπάρχει κενό στη ροή συνέχισης προς τη σελίδα εξουσιοδότησης μετά την ολοκλήρωση της σύνδεσης.** Πριν από την κυκλοφορία πρέπει να γίνεται ξεχωριστή αποδοχή για τις περιπτώσεις «Auth συνδεδεμένο» και «Auth μη συνδεδεμένο／έχει λήξει». Πριν διορθωθεί και επαληθευτεί αυτό το κενό, η πρώτη σύνδεση μπορεί να ολοκληρώνει το τυπικό OAuth σε ανεξάρτητη σελίδα ή να χρησιμοποιεί την παρακάτω εξουσιοδότηση στοιχείου Studio· μην υπόσχεστε ότι όλα τα σενάρια iframe λειτουργούν βασιζόμενοι μόνο σε αποτελέσματα δοκιμών με ήδη συνδεδεμένο χρήστη.

### Χρήση του τρέχοντος λογαριασμού Studio για εξουσιοδότηση

Στο Studio «Ρυθμίσεις → Αρχική σελίδα → Στοιχεία ιστοτόπου» ενεργοποιήστε το OAuth και συμπληρώστε το `client_id` και τη δηλωμένη διεύθυνση επιστροφής κλήσης. Ο ιστότοπος και η επιστροφή κλήσης πρέπει να χρησιμοποιούν την ίδια προέλευση HTTPS και να διαφέρουν από την προέλευση του Studio. Η σελίδα τρίτου μέρους πρέπει:

1. Να στείλει `acedatacloud:oauth:ready` στην ακριβή προέλευση του γονικού ιστότοπου, να λάβει και να επικυρώσει το `acedatacloud:oauth:init`.
2. Το κουμπί να δημιουργεί state και PKCE verifier και να στέλνει `acedatacloud:oauth:authorize` (state, S256 challenge)· ο verifier παραμένει στη δική της σελίδα.
3. Να επικυρώνει το γονικό παράθυρο, την προέλευση και το state, να χειρίζεται το code ή error στο `acedatacloud:oauth:result` και να το ανταλλάσσει στο τυπικό endpoint token.
Το Studio εμφανίζει τη σελίδα εξουσιοδότησης στην περιοχή του στοιχείου· αφού ο χρήστης συναινέσει, επιστρέφει τον κωδικό εξουσιοδότησης μέσω μηνύματος και η εφαρμογή δεν χρειάζεται να ανακατευθύνει. Όταν δεν υπάρχει σύνδεση επιστρέφεται `login_required`, σε περίπτωση απόρριψης επιστρέφεται `access_denied`, και όταν παρέλθει το χρονικό όριο αναμονής επιστρέφεται `authorization_timeout`. Η αλλαγή λογαριασμού θα αναδημιουργήσει το iframe της εφαρμογής και θα ακυρώσει τις μη ολοκληρωμένες εξουσιοδοτήσεις.

Το στοιχείο ζητά επί του παρόντος `profile:read credentials:read`, χωρίς να περιλαμβάνει `offline_access`. Μην υποθέτετε ότι θα λάβετε οπωσδήποτε refresh token. Τα `embed=studio` και `embed_origin` διατηρούνται από τον κεντρικό υπολογιστή του Studio και τη σελίδα εξουσιοδότησης· η σελίδα πελάτη χρειάζεται μόνο να τηρεί το πρωτόκολλο μηνυμάτων.

Για πλήρες παράδειγμα κουμπιού, δείτε τον [Οδηγό ενσωμάτωσης OAuth στοιχείου ιστότοπου Studio](https://github.com/AceDataCloud/Nexior/blob/main/docs/integrations/studio-home-oauth.md).

## Κύκλος ζωής, ανανέωση και ανάκληση

Η προεπιλεγμένη διάρκεια ισχύος του access token είναι 15 ημέρες· ο προγραμματισμός ανανέωσης ή επανεξουσιοδότησης πρέπει να βασίζεται στο `expires_in` κάθε απόκρισης. Το refresh token έχει προεπιλεγμένη διάρκεια 30 ημερών, η οποία επηρεάζεται από τη ρύθμιση της υπηρεσίας. Μην κωδικοποιείτε αυτές τις δύο τιμές ως μόνιμες εγγυήσεις.

Αφού εγκριθεί το `offline_access`, μπορείτε να καλέσετε:

```bash
curl https://auth.acedata.cloud/oauth2/token \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode "refresh_token=$OAUTH_REFRESH_TOKEN"
```

Η ανανέωση επιστρέφει νέα token και η εφαρμογή πρέπει να αποθηκεύει την πιο πρόσφατη τιμή. Κατά την ανανέωση ελέγχεται αν η εφαρμογή παραμένει έγκυρη, αν ο χρήστης είναι διαθέσιμος και αν τα δικαιώματα εξακολουθούν να είναι εγκεκριμένα. Σε περίπτωση αποτυχίας, εκκαθαρίστε τη δική σας κατάσταση σύνδεσης και εξουσιοδοτήστε ξανά.

**Η τρέχουσα υλοποίηση ανανέωσης OAuth δεν εγγυάται ότι το παλιό refresh token καθίσταται αμέσως άκυρο μετά την ανανέωση.** Μην θεωρείτε ότι η λήψη νέου token σημαίνει ότι το παλιό token έχει ανακληθεί, και μην χρησιμοποιείτε την εναλλαγή secret ως υποκατάστατο του τερματισμού υπαρχόντων token.

Ο τρόπος κλήσης του αιτήματος ανάκλησης είναι:

```bash
curl https://auth.acedata.cloud/oauth2/revoke \
  --data-urlencode "token=$OAUTH_ACCESS_TOKEN"
```

**Το τρέχον endpoint ανάκλησης επιστρέφει HTTP 200, αλλά δεν υλοποιεί άμεση ακύρωση ήδη εκδομένων JWT.** Η εφαρμογή πρέπει να εκκαθαρίζει τα token που έχει αποθηκεύσει η ίδια και δεν μπορεί να θεωρεί το 200 ως απόδειξη ότι όλα τα ήδη εκδομένα token ή API Key έχουν καταστεί άκυρα. Για API Key που έχουν διαρρεύσει ή αντιγραφεί, ανακαλέστε ή εναλλάξτε ξεχωριστά τα αντίστοιχα διαπιστευτήρια.

## Συνήθη σφάλματα και αποδοχή

| Σύμπτωμα／σφάλμα                         | Έλεγχος                                                                    |
| ----------------------------- | --------------------------------------------------------------------- |
| `invalid_scope`               | Χρησιμοποιήστε τα τρέχοντα ονόματα δικαιωμάτων· ελέγξτε το καταχωρισμένο εύρος της εφαρμογής, τους περιορισμούς ανάθεσης και τα δικαιώματα χρήστη. Ολόκληρος ο κατάλογος Discovery δεν είναι κατάλογος επιλέξιμος από την εφαρμογή                      |
| `invalid_request`             | Απαιτούμενες παράμετροι, ακριβής διεύθυνση επανάκλησης, S256 challenge και method για Public πελάτη                        |
| `invalid_client`              | client ID, κατάσταση εφαρμογής, secret Confidential πελάτη· ελέγξτε αν χρησιμοποιείται εσφαλμένα Basic authentication             |
| `invalid_grant`               | Ο code έληξε／έχει ήδη καταναλωθεί, ή το verifier ή το redirect URI δεν ταιριάζει· κατά την ανανέωση ελέγχονται επίσης αλλαγές στην εφαρμογή και στα δικαιώματα                 |
| `access_denied`               | Ο χρήστης απέρριψε· επαναφέρετε το κουμπί σύνδεσης, μην εμφανίζετε επανειλημμένα την εξουσιοδότηση                                                  |
| `unsupported_grant_type`      | Υποστηρίζονται επί του παρόντος `authorization_code`、`refresh_token`                             |
| HTTP 401／403                  | Διακρίνετε μεταξύ μη έγκυρης κατάστασης σύνδεσης, token, scope εξουσιοδότησης και δικαιωμάτων πρόσβασης στον ίδιο τον πόρο                                     |
| `Failed to fetch`、σφάλμα DNS／CORS | Επαληθεύστε τον πραγματικό κεντρικό υπολογιστή του αιτήματος και τη διαθεσιμότητα του backend πελάτη· δεν μπορεί να αποδοθεί στο ότι «ο χρήστης δεν έχει Key»                                      |
| Έχει εξουσιοδοτηθεί αλλά δεν μπορεί να διαβάσει Key                   | Χρησιμοποιήστε `platform.acedata.cloud`, πραγματικό user ID, `items[*].token`· διακρίνετε κενή λίστα, σελιδοποίηση και αποτυχημένες αποκρίσεις |
| Κενή πλήρης σελίδα μετά την επιστροφή εξουσιοδότησης                     | Πρώτα αποδώστε τη σελίδα· χειριστείτε ξεχωριστά τα σφάλματα για callback, token, UserInfo και αιτήματα διαπιστευτηρίων· μην αφήνετε μια εξαίρεση αρχικοποίησης να σταματά ολόκληρη τη σελίδα                      |
| Το iframe δεν συνεχίζει μετά τη σύνδεση                 | Χειριστείτε σύμφωνα με τους υπάρχοντες περιορισμούς παραπάνω· δοκιμάστε σενάρια χωρίς σύνδεση, ληγμένης σύνδεσης, απόρριψης και επανασύνδεσης                                          |

Πριν από την παράδοση, επαληθεύστε τουλάχιστον: σωστό callback, απόρριψη, εσφαλμένο state, ληγμένο／ήδη καταναλωμένο code, χωρίς Key, αποτυχία δικτύου, ληγμένο token, έλλειψη απαιτούμενου scope, καθώς και την πρώτη σύνδεση και την αλλαγή λογαριασμού σε σενάρια iframe. Μην αποθηκεύετε πλήρη code, token ή API Key στα αποδεικτικά δοκιμών.

## Επαλήθευση δύο βημάτων και επανεξουσιοδότηση

Αφού ο χρήστης ενεργοποιήσει την επαλήθευση δύο βημάτων, το Ace Data Cloud ολοκληρώνει στη σελίδα εξουσιοδότησης την επαλήθευση του κωδικού της εφαρμογής ελέγχου ταυτότητας ή του εφάπαξ κωδικού ανάκτησης και στη συνέχεια παραδίδει τον κωδικό εξουσιοδότησης. Η εφαρμογή σας συνεχίζει να χρησιμοποιεί την τυπική ροή OAuth και δεν πρέπει να ζητά, αποθηκεύει ή προωθεί κλειδιά εφαρμογής ελέγχου ταυτότητας και κωδικούς ανάκτησης.

Αφού ο χρήστης ενεργοποιήσει, αλλάξει ή απενεργοποιήσει την επαλήθευση δύο βημάτων ή ανακτήσει τον λογαριασμό του, οι προηγούμενες συνεδρίες λογαριασμού, τα refresh token και τα σχετικά token εξουσιοδότησης πλατφόρμας ενδέχεται να καταστούν άκυρα. Όταν λάβετε μη έγκυρη συνεδρία ή `invalid_grant`, ξεκινήστε ξανά μια ορατή στον χρήστη ροή εξουσιοδότησης· μην χρησιμοποιείτε επανειλημμένα παλιούς κωδικούς εξουσιοδότησης και μην επιχειρείτε να παρακάμψετε την επαλήθευση. Η μέθοδος πιστοποίησης των συνηθισμένων model API Key παραμένει αμετάβλητη· αν υπάρχει υποψία παραβίασης λογαριασμού, ελέγξτε και ανακαλέστε ξεχωριστά τα επηρεαζόμενα API Key.
