يتضمن X402 بروتوكول HTTP وSDK والتوقيع وFacilitator والمعاملات على السلسلة. عند استكشاف مشكلات التوقيع أو التسوية وإصلاحها، يُوصى بالتأكد طبقةً بطبقة وفق الترتيب «المدخل العام -> استجابة 402 -> معالج دفع SDK -> التسوية على السلسلة». يوضح هذا الدليل طرق الفحص لكل طبقة، ويسرد الأخطاء الشائعة.

## فحص المدخل العام

إعلان قدرات Facilitator:

```bash
curl https://facilitator.acedata.cloud/.well-known/x402
```

إذا أعاد `facilitator` و`supportedKinds` ونقاط نهاية البروتوكول، فهذا يشير إلى أن بيانات تعريف القدرات سليمة. تم إيقاف اكتشاف موارد API؛ يُرجى استدعاء API المستهدف مباشرةً، والاعتماد على استجابة 402 الفورية.

القدرات المدعومة من Facilitator:

```bash
curl https://facilitator.acedata.cloud/supported
```

إذا أعاد `kinds`، فهذا يشير إلى أن مدخل Facilitator يعمل بشكل سليم.

## فحص `accepts` الخاص بـ 402

أرسل طلبًا غير موثّق لا يترتب عليه رسوم:

```bash
curl -sS -X POST https://x402.acedata.cloud/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "hi"}],
    "max_tokens": 1
  }'
```

تحقق مما إذا كانت `accepts` المعادة تتضمن الشبكة التي تريد استخدامها. `network` هو معرّف CAIP-2:

- `eip155:8453` + `exact` (Base)
- `eip155:8453` + `upto` (Base، قياس لاحق)
- `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` + `exact` (Solana)

إذا لم تكن الشبكة المستهدفة موجودة، فهذا يشير إلى أن API هذا أو البيئة الحالية لا يملك طريقة تحصيل X402 المقابلة مهيأة.

## تشغيل أدوات التحقق المتقدمة لـ X402Client

يوفر مستودع X402Client أدوات تحقق متقدمة يمكن استخدامها للتأكد من اختيار استجابة 402، وإنشاء التوقيع، وpaid retry، والتسوية على السلسلة. تتطلب هذه الأدوات محفظة ممولة وRPC ومفتاحًا خاصًا وتبعيات تطوير. بالنسبة للتكاملات التجارية العادية، يُوصى بإعطاء الأولوية لاستخدام SDK الخاص بـ TypeScript أو Python؛ ولا تشغّل هذه الأدوات إلا عند الحاجة إلى تحديد مشكلات التوقيع أو التسوية على السلسلة.

عنوان المستودع: [https://github.com/AceDataCloud/X402Client](https://github.com/AceDataCloud/X402Client)

```bash
git clone https://github.com/AceDataCloud/X402Client.git
cd X402Client/typescript
npm install
npm install --no-save ethers @solana/spl-token bs58 tsx
```

Base:

```bash
export X402B_BASE_PAYER_PRIVATE_KEY=0x...
TEST_API_PATH='/openai/chat/completions' \
TEST_BODY='{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}],"max_tokens":10}' \
npx tsx scripts/test-real-e2e.ts
```

Solana:

```bash
export X402B_SOLANA_PAYER_PRIVATE_KEY=...
npx tsx scripts/test-solana-e2e.ts
```

تطبع أدوات التحقق عادةً:

1. استجابة 402 للطلب الأول.
2. payment requirement المحدد.
3. ملخص `PAYMENT-SIGNATURE` بعد التوقيع.
4. حالة HTTP ونص الاستجابة بعد إعادة المحاولة.
5. settlement transaction على السلسلة، أو سبب خطأ Facilitator عند الفشل.

لا ترسل المفتاح الخاص أو `PAYMENT-SIGNATURE` الكامل إلى نظام السجلات أو التذاكر.

مثال على نتائج التحقق من API العام:

```text
Base exact
HTTP 402 -> HTTP 200
content ADC_BASE_E2E_OK
tx 0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
block 46726299
explorer https://basescan.org/tx/0x408430ab3451bc22a51e510cdb4b063d6b9686724fea7a31fc109af20f5cd2f3
transfer value 95215 atomic USDC

Solana exact
HTTP 402 -> HTTP 200
content ADC_SOLANA_E2E_OK
chain signature not confirmed in this run because public RPC lookup hit 429

Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
block 46726437
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

توضيح:

- أكملت كل من Base `exact` وSolana `exact` وBase `upto` عملية paid retry من HTTP 402 إلى HTTP 200.
- يمكن التحقق من المعاملة على السلسلة لـ Base `exact` في BaseScan، ومبلغ التسوية هو `95215` atomic USDC.
- الحد الأعلى للتوقيع في Base `upto` هو `95215` atomic USDC، لكن settlement الفعلي على السلسلة هو `3` atomic USDC، مما يشير إلى أن القياس اللاحق يخصم الرسوم حسب الاستخدام الفعلي.
- تم تأكيد paid retry وإخراج النموذج لمسار Solana. قد يطبق RPC العام تحديدًا للمعدل؛ عند الحاجة إلى مطابقة صارمة على السلسلة، يُرجى استخدام Solana RPC خاص بك أو سجلات التسوية من جهة المنصة لتأكيد توقيع المعاملة.

## اختبار SDK السريع

تُستخدم أدوات التحقق المتقدمة لفحص التوقيع والتسوية على السلسلة. ينبغي لجهة الأعمال أيضًا تنفيذ اختبار SDK سريع للتأكد من أن كود التطبيق يمكنه معالجة 402 تلقائيًا من خلال payment handler. فيما يلي لا تُعرض سوى المقاطع الأساسية، ويجب استكمال المحفظة وprovider وimport في الكود الكامل.

TypeScript:

```ts
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider,
    evmAddress: wallet.address
  })
});

const res = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Reply with exactly ADC_SDK_X402_OK' }],
  max_tokens: 8
});
```

Python:

```python
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
    )
)

res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly ADC_PY_X402_OK"}],
    max_tokens=8,
)
```

إذا أعاد النموذج السلسلة الثابتة كما هو مطلوب، فهذا يشير إلى أن SDK وpayment handler وGateway وFacilitator وAPI المستهدف متصلة معًا.

يستخدم اختبارا smoke test أعلاه Base `exact`، مع التسوية بالمبلغ الثابت المعروض في عرض سعر 402. تعد إكمالات المحادثة سيناريو يُقاس بحسب token، ويوصى عند التكامل الرسمي بتمرير `preferScheme: 'upto'` (وفي Python يكون `prefer_scheme="upto"`) للتسوية حسب الاستخدام الفعلي.

كائن الإرجاع لـ Python SDK هو `dict`، ويمكن استخدام `res["choices"][0]["message"]["content"]` لقراءة المحتوى.

## E2E لدفع الطلبات

يستخدم دفع الطلبات API المنصة الخاص بـ `platform.acedata.cloud`، ويتطلب رمز حساب المنصة. السلسلة الكاملة هي: إنشاء طلب Pending، ثم يقوم `POST /api/v1/orders/{order_id}/pay/` بتشغيل 402، ثم إعادة المحاولة مع `PAYMENT-SIGNATURE`.

مثال على نتائج التحقق من دفع طلب صغير:

> سجلات المعاملات التالية هي عينات اختبار تاريخية فعلية ضمن السياسة القديمة، وقد تم الاحتفاظ بالمبالغ وتجزئات المعاملات كما هي. لم تعد طلبات X402 الجديدة تتضمن خصومات على طريقة الدفع؛ يُرجى اعتماد `amount` في استجابة 402 لهذه المرة كأساس للتوقيع والدفع.
```text
تم إنشاء الطلب 78481793-304e-47f7-bc0c-8231aec9cc1e
تم إنشاء الحالة Pending
تم إنشاء السعر 1.26

http_status=402
x402Version 2
accepts [('eip155:8453', 'exact', '1200000'), ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000')]

status 200
حالة الطلب Finished
pay_way X402
pay_id 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}

حالة معاملة Base 1
الكتلة 46726704
المستكشف https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
قيمة التحويل 1200000 atomic USDC
```

شرح النتيجة:

- بعد إنشاء الطلب، تكون حالة الطلب `Pending`، والسعر هو `1.26`.
- يعيد طلب `pay/` الأول HTTP 402، ويوجد في `accepts` كل من Base `exact` وSolana `exact`، والمبالغ كلها `1200000` atomic USDC.
- بعد إعادة المحاولة باستخدام Base `PAYMENT-SIGNATURE`، يعيد HTTP 200، وتتغير حالة الطلب إلى `Finished`، ويكون `pay_way` هو `X402`.
- بعد فك ترميز `PAYMENT-RESPONSE`، يظهر `success=True` و`network=base`، ويُعطى نفس هاش المعاملة.
- حالة المعاملة على BaseScan هي `1`، ومبلغ التحويل هو `1200000` atomic USDC، أي `1.2` USDC.
- تم دفع سعر الإنشاء `1.26` خلال فترة سياسة خصم الدفع القديمة لـ X402، وكان مبلغ التوقيع والتسوية النهائي هو `1.2` USDC.

إذا لم يكن دفع الطلب يتضمن `Authorization: Bearer {platform_token}`، أو إذا لم يكن الطلب تابعًا للحساب الحالي، فسيفشل في طبقة صلاحيات المنصة؛ وهذا يختلف عن واجهة X402 API بلا حساب عند استدعاء `x402.acedata.cloud` مباشرةً.

## الأخطاء الشائعة

| الظاهرة                                           | اتجاه التحقق                                                                |
| -------------------------------------------- | ------------------------------------------------------------------- |
| الطلب الأول ليس 402                                  | تحقق مما إذا كان `Authorization` مرفقًا بالخطأ، أو مما إذا كانت واجهة API هذه لا تحتوي على تسعير X402 بعد.                  |
| `No payment requirement for network`         | الشبكة المستهدفة ليست ضمن `accepts`، غيّر الشبكة أو تحقق من إعداد Gateway.                               |
| `invalid_402`                                | استجابة 402 ليست JSON صالحًا، تحقق من الوكيل أو البوابة أو صفحة الخطأ.                                        |
| `Authorization nonce already processed`      | تمت إعادة استخدام `PAYMENT-SIGNATURE` نفسه، وقّع من جديد.                                  |
| `invalid_upto_evm_payload_invalid_signature` | تحقق من توافق chainId الخاص بـ `upto`، وPermit2 domain، وعنوان facilitator، وحساب التوقيع.         |
| `PERMIT2_ALLOWANCE_REQUIRED`                 | نفّذ `approve-permit2` لـ USDC على السلسلة المستهدفة.                                     |
| `Payer has insufficient USDC balance`        | رصيد USDC في محفظة الدفع غير كافٍ.                                                       |
| HTTP 200 لكن بدون tx hash                         | قد يكون المبلغ الفعلي لـ `upto` هو 0، أو أن سجل settlement ما زال يُكتب بشكل غير متزامن.                             |
| Solana `Missing transaction payload`         | لا يحتوي envelope الخاص بـ `PAYMENT-SIGNATURE` على معاملة متسلسلة أو signature، تحقق من wallet adapter. |

## قائمة التحقق لـ Base `upto`

يُوفر `upto` حاليًا على Base فقط (`eip155:8453`). نظرًا لأن توقيع `upto` يربط المزيد من معلمات EVM typed data، ينبغي عند التكامل التأكد بشكل خاص من أن الحقول الفورية في استجابة 402 تتطابق تمامًا مع توقيع العميل.

```text
Base upto
HTTP 402 -> HTTP 200
content ADC_BASE_UPTO_OK
tx 0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
explorer https://basescan.org/tx/0x4b0b836ce1cd1171cdbc37df1637150b024214ec28e7f6f2d09122f15cbfc036
signed ceiling 95215 atomic USDC
transfer value 3 atomic USDC
```

إذا أعاد Base `upto` القيمة `invalid_upto_evm_payload_invalid_signature`، فتحقق بالأولوية من:

1. `extra.chainId` (ينبغي أن يكون `8453`) في بند `eip155:8453` + `upto` الذي أعادته API.
2. `extra.facilitatorAddress` الذي أعادته API.
3. عنوان Base `upto` facilitator الذي يعيده `https://facilitator.acedata.cloud/supported`.
4. Permit2 domain، وspender، وعقد USDC، وحساب التوقيع.
5. ما إذا كانت المحفظة قد نفذت بالفعل approve Permit2 لـ Base USDC.

يربط digest توقيع `upto` في الوقت نفسه Permit2 domain، ومعرّف السلسلة، وspender، وعنوان المستلم، وعنوان facilitator، وvalidAfter. إذا لم يتطابق أي بند، فسيستعيد Facilitator signer خاطئًا، ومن ثم يعيد invalid signature. إذا كانت هذه كلها متطابقة لكنه لا يزال يعيد 402، فتحقق في الخطوة التالية من Permit2 allowance؛ وعند عدم وجود تفويض يعيد `PERMIT2_ALLOWANCE_REQUIRED`.

## حفظ معلومات التحقق

يجب أن تحفظ عملية تحقق كاملة واحدة على الأقل:

- API path وملخص نص الطلب؛
- network وscheme المختاران؛
- `maxAmountRequired`؛
- عنوان محفظة payer؛
- حالة HTTP النهائية؛
- مخرجات النموذج أو معرّف المهمة في الاستجابة؛
- رابط settlement transaction؛
- Gateway trace ID أو معرّف سجل استخدام المنصة.

لا تحفظ المفتاح الخاص، أو `PAYMENT-SIGNATURE` الكامل، أو EIP-712 signature الكامل، أو العبارة الاستذكارية.

## أخطاء الدفع المنظمة

سيعيد فشل X402 بعد التوقيع `code` ثابتًا، ومعلمات إدراج آمنة، ومرحلة، وعلامة إمكانية إعادة المحاولة في `extensions.acedatacloud.paymentError`. استخدم هذه البنية بالأولوية للتحقق، ولا تحلل `error` الإنجليزي في المستوى الأعلى، ولا تطلب من المستخدم تقديم توقيع المحفظة أو النص الأصلي للمحاكاة على السلسلة.

- `charged: false`: تم رفض التحقق بوضوح قبل التسوية، ولم يتم بدء أي خصم هذه المرة.
- بدون `charged`: النتيجة غير معروفة أو دخلت بالفعل مرحلة التسوية، تحقق أولًا من الطلب وحالة السلسلة، ويُمنع تكرار الدفع مباشرةً.
- `settlement_pending`: لا تكرر الدفع مؤقتًا، حدّث الطلب أولًا أو تواصل مع الدعم.
- code غير معروف: تعامل معه على أنه `payment_failed`، واحتفظ بالرمز التقني العام ليتمكن دعم العملاء من البحث.
