الاستعلام عن طلب عبر معرّف الطلب. تدعم نقطة النهاية هذه وضعَي قراءة: الوصول المجهول يعيد فقط الحد الأدنى من الحقول المطلوبة لصفحة الدفع؛ بينما يعيد مالك الطلب الذي يحمل Account Token التفاصيل الكاملة.

## نظرة عامة على الواجهة

| البند   | المحتوى                                                        |
| --- | --------------------------------------------------------- |
| الطريقة  | `GET`                                                     |
| URL | `https://platform.acedata.cloud/api/v1/orders/{order_id}` |
| المصادقة  | اختيارية؛ المجهول يحصل على إسقاط أدنى، والمالك المصادق عليه يحصل على إسقاط كامل                                    |

يعمل كل من `/orders/{id}` و`/orders/{id}/` حاليًا. يُعد معرّف الطلب جزءًا من رابط الدفع، ويجب اعتباره معرّفًا حساسًا ومعتمًا، ولا تنشره علنًا.

## الاستعلام المجهول

يمكن لصفحة الدفع القراءة مباشرةً عند فقدان حالة تسجيل الدخول:

```shell
export ORDER_ID='你的订单 ID'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json'
```

تحتوي الاستجابة المجهولة فقط على `id` و`description` و`price` و`state` و`pay_way` و`pay_url` و`expired_at` و`created_at`. وهي لا تعيد الحساب أو Application أو Package أو معرّفات الدفع الداخلية أو metadata.

## الاستعلام المصادق عليه

```shell
export PLATFORM_TOKEN='你的账户令牌'
curl "https://platform.acedata.cloud/api/v1/orders/${ORDER_ID}" \
  -H 'Accept: application/json' \
  -H "Authorization: Bearer ${PLATFORM_TOKEN}"
```

يتلقى مالك الطلب تفاصيل Order الكاملة، بما في ذلك `application` / `applications` و`package` / `packages` و`bank_details` و`invoice_automation` وحقول النموذج. إذا كان المستخدم مصادقًا عليه لكنه ليس مالك الطلب، فسيُعاد `403`؛ باستثناء المشرفين الفائقين.

## الحقول الرئيسية

| الحقل            | الوصف                                                          |
| ------------- | ----------------------------------------------------------- |
| `state`       | `Pending` أو `Paid` أو `Finished` أو `Expired` أو `Failed` أو `Refunded` |
| `pay_way`     | طريقة الدفع الحالية للطلب؛ اسم الحقل ليس `payment_method`                             |
| `pay_url`     | عنوان صفحة الدفع المستضافة أو رمز QR، وقد يكون فارغًا                                           |
| `price`       | المبلغ النهائي المستحق للطلب، ولا يوفر نموذج الطلب الحالي حقل `final_price`                         |
| `amount`      | كمية رصيد الباقة؛ مرئية فقط في الاستجابة الكاملة المصادق عليها                                            |
| `finished_at` | وقت إكمال الطلب؛ اسم الحقل ليس `paid_at`                                      |

قد تضيف الاستجابة الكاملة حقولًا وفقًا لطريقة الدفع، وينبغي للعميل قراءتها حسب الحاجة، وتجنب دائمًا تسجيل metadata الحساسة في الاستجابة الكاملة.

## معالجة الأخطاء

- `404`: معرّف الطلب غير موجود.
- `403`: تم تسجيل الدخول لكن المستخدم ليس مالك الطلب.
- لا تعيد الطلبات المجهولة `401`؛ بل تحصل فقط على الإسقاط العام الأدنى.

## إلغاء الفاتورة باللون الأحمر وإعادة الطلب

يمكن قراءة الفاتورة الحالية للطلب عبر `GET /api/v1/orders/{order_id}/invoice/`. بعد تقديم الإلغاء التلقائي باللون الأحمر، تظل الفاتورة `Issued`، ويشير `red_state` إلى تقدم الإلغاء باللون الأحمر؛ نجاح التقديم لا يعني اكتمال الإلغاء باللون الأحمر. أثناء انتظار التأكيد، أو إصدار فاتورة حمراء، أو الأرشفة، لا يمكن للطلب إعادة طلب فاتورة.

عندما يطلب المسؤول إلغاءً باللون الأحمر بسبب خطأ في معلومات الفوترة مثل الاسم أو الرقم الضريبي، يكون سبب الإلغاء باللون الأحمر هو “خطأ في الفوترة”؛ بينما يستمر الإلغاء التلقائي باللون الأحمر الناتج عن استرداد الطلب في استخدام “إنهاء الخدمة”.

بعد إصدار الفاتورة الحمراء وأرشفتها بنجاح، تصبح الفاتورة الأصلية `Voided`، وعندها فقط يمكن للطلب إعادة التقديم. يمكن عرض الفاتورة الأصلية في سجل الفواتير. عند فشل الإلغاء باللون الأحمر أو عندما تكون النتيجة قيد التحقق، يتولى القسم المالي المراجعة، ولن يُرفع قيد الفوترة عن الطلب مبكرًا. يجب أولًا إلغاء الفواتير الصادرة يدويًا أو إلغاؤها باللون الأحمر في النظام الضريبي أو نظام الفوترة، ثم يؤكد القسم المالي ذلك على المنصة.
