[X402](https://www.x402.org/) هو بروتوكول دفع على السلسلة «يتم فيه الفوترة وفق HTTP 402» اقترحته Coinbase: يعيد الخادم `402 Payment Required` على الطلبات التي لا تحتوي على token، مرفقًا بحقل `accepts: [...]` يسرد السلاسل / الأصول / الأسعار المقبولة؛ يوقّع العميل محليًا تفويضًا (Permit2 / EIP-712 على EVM، وتفويض تحويل SPL token على Solana)، ويضع envelope بعد ترميزه بـ base64 في ترويسة `PAYMENT-SIGNATURE` ثم يعيد الإرسال. بعد التحقق، ينفّذ الخادم التسوية فعليًا على السلسلة، ثم يعيد نتيجة العمل.

> يستدعي عميل X402 الخاص بـ Ace Data Cloud واجهة API المستهدفة مباشرةً، ويستخدم `402 Payment Required` و`accepts` المعادين لحظيًا من هذا الطلب كأساس للسعر والتوقيع. يمكن التحقق من قدرة دفع الـ Facilitator عبر [`/.well-known/x402`](https://facilitator.acedata.cloud/.well-known/x402).

يكشف كل من `@acedatacloud/sdk` و`acedatacloud` عن خطاف `paymentHandler`: عندما يتلقى طلب صادر من SDK نفسه `402`، يستدعي handler الذي تحقنه للحصول على ترويسة `PAYMENT-SIGNATURE`، ثم يعيد إرسال الطلب الأصلي. بدمج `@acedatacloud/x402-client` / `acedatacloud-x402` مع SDK، **تكون العملية كاملةً شفافة تمامًا لكود العمل**——تستخدم فقط `client.openai.chat.completions.create(...)`، ويبدو الأمر مطابقًا تمامًا لوضع token، لكن الدفع في الطبقة السفلية يكون لكل استدعاء ولا يتطلب شحنًا مسبقًا.

هذه المقالة:

- تربط فعليًا سلسلة «بدون token + حقن X402 handler» على طرف TS ([تحقق T12](#رابعًاالتحقق-من-التشغيل-الفعلي))
- تسرد الفروقات بين سلسلتي التوقيع EVM / Solana
- تقدّم ثلاث طرق تكييف: وضع المفتاح الخاص `viem`، ووضع محفظة المتصفح، ووضع Python `EVMAccountSigner`
- توضّح حقل `preferScheme` / `prefer_scheme` السهل الوقوع في مشكلاته

## أولًا، نظرة عامة على البروتوكول (لا بد من قراءتها)

يتضمن استدعاء X402 ناجح واحد **3 HTTP RTT**:

```text
1. SDK -> /openai/v1/chat/completions               (بدون Authorization)
   <- 402 Payment Required
      { accepts: [{ scheme:'upto', network:'eip155:8453', maxAmountRequired:'10000', ... }] }

2. SDK داخليًا -> paymentHandler({ url, method, body, accepts })   (توقيع محلي، 0 RTT)
   <- { headers: { 'PAYMENT-SIGNATURE': '<base64-envelope>' } }

3. SDK -> /openai/v1/chat/completions               (حقن ترويسة PAYMENT-SIGNATURE)
   <- 200 + استجابة العمل   (تكتمل التسوية على الخادم)
```

إن X402 envelope هو جزء من JSON، يُوضع في ترويسة `PAYMENT-SIGNATURE` بعد ترميزه بـ base64. البنية (مقتطف):

```json
{
  "x402Version": 2,
  "accepted": {
    "scheme": "upto",
    "network": "eip155:8453"
  },
  "payload": {
    "permit2": {
      "permitted": [{ "token": "0x...USDC", "amount": "10000" }],
      "nonce": "...",
      "deadline": "..."
    },
    "witness": { "...metered-billing-fields..." },
    "signature": "0x..."
  }
}
```

تكون الطبقة العليا من envelope هي `x402Version: 2`، ويُعلن عن `scheme` و`network` المختارين لهذه المرة باستخدام كائن `accepted` (معرّف CAIP-2).

| scheme  | المعنى                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------ |
| `exact` | سعر ثابت (سيناريوهات التسعير مثل توليد الصور / الفيديو، والبحث، وغيرها). المبلغ الموقّع = المبلغ الذي يطلبه الخادم.                                                         |
| `upto`  | فوترة مقاسة (مثل chat completions / token). يُوقّع مبلغًا **أقصى**، وتتم تسوية الجزء المستخدم فعليًا فقط (استنادًا إلى Permit2 + witness). **يوصى بشدة** به لواجهات API من نوع المحادثة. |

يُستخدم `preferScheme` / `prefer_scheme` لاختيار التفضيل عندما يوفّر الخادم **عدة scheme** في الوقت نفسه. إذا كان الخادم يكشف `exact` فقط، فسيتم تجاهل هذا الحقل؛ وإذا تم تعيين `upto` لكن الخادم لا يكشفه، فسيتم الرجوع إلى أول عنصر مطابق.

## ثانيًا، TypeScript: مجموعتا استخدام لمحفظة المتصفح + viem على الخادم

### التثبيت

```bash
npm install @acedatacloud/sdk @acedatacloud/x402-client
```

أرقام الإصدارات المختبرة:

```text
@acedatacloud/sdk@2026.504.2
@acedatacloud/x402-client@2026.531.3
```

### التوقيع الكامل لـ `createX402PaymentHandler`

```ts
export interface X402PaymentHandlerOptions {
  network: 'solana' | 'base';
  solanaWallet?: SolanaWalletAdapter;       // إلزامي عندما network='solana'
  evmProvider?: EVMProvider;                // إلزامي عندما network='base'، EIP-1193
  evmAddress?: string;                      // إلزامي عندما network='base'
  preferScheme?: 'exact' | 'upto';
}
```

القيمة المعادة هي `(ctx) => Promise&lt;{ headers: Record<string, string> }>`، وهي تتوافق تمامًا مع توقيع خطاف `paymentHandler` الخاص بـ SDK.

### الاستخدام 1: المتصفح (MetaMask / WalletConnect)

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

// 1. اطلب من المستخدم الاتصال بالمحفظة
const accounts: string[] = await (window as any).ethereum.request({
  method: 'eth_requestAccounts'
});
const userAddress = accounts[0];

// 2. انتقل إلى شبكة Base الرئيسية
await (window as any).ethereum.request({
  method: 'wallet_switchEthereumChain',
  params: [{ chainId: '0x2105' }]   // 8453 = Base
});

// 3. أنشئ عميل SDK، وحقن X402 handler
//    ملاحظة: لا تمرر apiToken، لكي يمر SDK عبر مسار 402
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: (window as any).ethereum,
    evmAddress: userAddress,
    preferScheme: 'upto'   // يجب اختيار upto لفئات chat
  })
});

// 4. استدعِ بشكل عادي
const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

في أول استدعاء، سيظهر في المتصفح **طلبا توقيع**: الأول هو approve لمرة واحدة لـ Permit2 على USDC (المبلغ هو `MaxUint256`، ويُكتب على السلسلة)؛ والثاني هو توقيع EIP-712 لـ X402 envelope (لا يُكتب على السلسلة، وإنما للتحقق من قِبل facilitator). تحتاج الاستدعاءات اللاحقة إلى التوقيع الثاني فقط، وتجربة الاستخدام هي «انقر توقيعًا واحدًا → احصل على النتيجة».

### الاستخدام 2: خادم Node + مفتاح viem الخاص (مناسب للواجهة الخلفية / CLI)

يقبل `@acedatacloud/x402-client` على طرف TS **مزوّد EIP-1193 فقط**——ولا يدير المفاتيح الخاصة مباشرةً. في سيناريوهات Node / CLI، الطريقة القياسية هي استخدام [`viem`](https://viem.sh/) لتغليف المفتاح الخاص في `WalletClient`، ثم المرور عبر تكييف EIP-1193 الخاص بـ [`@ethereumjs/util`](https://www.npmjs.com/package/@ethereumjs/util) أو الداخلي في viem.
```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { createWalletClient, http } from 'viem';
import { base } from 'viem/chains';
import { privateKeyToAccount } from 'viem/accounts';

const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const walletClient = createWalletClient({
  account,
  chain: base,
  transport: http(process.env.BASE_RPC_URL)
});

// يأتي viem WalletClient مزودًا بـ .request() المتوافق مع EIP-1193، ويمكن استخدامه مباشرةً كـ evmProvider
const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'base',
    evmProvider: walletClient as any,   // walletClient.request يفي بمتطلبات EIP-1193
    evmAddress: account.address,
    preferScheme: 'upto'
  })
});

const res: any = await client.openai.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'hi' }],
  max_tokens: 20
});
console.log(res.choices[0].message.content);
```

> إذا شعرت أن توافق EIP-1193 الخاص بـ viem غير مستقر بما يكفي، يمكنك أيضًا اتباع المسار منخفض المستوى عبر [`signEVMUptoPayment`](https://github.com/AceDataCloud/SDK/blob/main/typescript/packages/x402-client/src/evm.ts)، وربط مسار `accepts → signed envelope → PAYMENT-SIGNATURE header` بنفسك، مع تجاوز خطاف SDK؛ لكن يُوصى بأن يكون الخيار الأول هو `createX402PaymentHandler`، حتى لا تضطر إلى صيانة ترقيات البروتوكول بنفسك.

### الاستخدام 3: Solana

```ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';
import { Keypair } from '@solana/web3.js';

const kp = Keypair.fromSecretKey(/* Uint8Array */);

const client = new AceDataCloud({
  paymentHandler: createX402PaymentHandler({
    network: 'solana',
    solanaWallet: {
      publicKey: kp.publicKey,
      signTransaction: async (tx) => {
        tx.sign([kp]);
        return tx;
      }
    }
  })
});
```

على سلسلة Solana، يتم حاليًا **كشف مخطط `exact` فقط**، لذلك لا يكون لـ `preferScheme` أي تأثير على Solana.

## ثالثًا، Python: وضع المفتاح الخاص

يتبع `acedatacloud-x402` في Python مسار **التوقيع المباشر باستخدام المفتاح الخاص** (ولا توجد تجريدات EIP-1193)، وهو أنسب للخوادم / منفذات المهام.

### التثبيت

```bash
pip install acedatacloud acedatacloud-x402
```

إصدارات تم اختبارها فعليًا:

```text
acedatacloud==2026.4.26.1
acedatacloud-x402==2026.5.31.3
```

### EVM (Base)

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    EVMAccountSigner,
)

# 1. إنشاء الموقّع من المفتاح الخاص
signer = EVMAccountSigner.from_private_key(os.environ["EVM_PRIVATE_KEY"])

# 2. إنشاء SDK: لا تمرر api_token، ودع SDK يسلك مسار 402
client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="base",
        evm_signer=signer,
        prefer_scheme="upto",   # يجب اختيار upto لعمليات chat
    )
)

# 3. استدعاء عادي
res = client.openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "hi"}],
    max_tokens=20,
)
print(res["choices"][0]["message"]["content"])
```

### Solana

```python
import os
from acedatacloud import AceDataCloud
from acedatacloud_x402 import (
    create_x402_payment_handler,
    SolanaKeypairSigner,
)

signer = SolanaKeypairSigner.from_secret_key_base58(os.environ["SOLANA_PRIVATE_KEY"])

client = AceDataCloud(
    payment_handler=create_x402_payment_handler(
        network="solana",
        solana_signer=signer,
        rpc_url="https://api.mainnet-beta.solana.com",  # اختياري
    )
)
```

### approve لمرة واحدة (EVM فقط في المرة الأولى)

في EVM Base، يستخدم X402 Permit2، ويحتاج المحفظة إلى تنفيذ `approve` واحد بقيمة `MaxUint256` لعقد Permit2 بالنسبة إلى USDC. يتضمن `acedatacloud-x402` دالة `approve_permit2` مدمجة:

```python
from acedatacloud_x402 import approve_permit2

tx_hash = approve_permit2(
    evm_signer=signer,
    rpc_url=os.environ["BASE_RPC_URL"],
)
print("permit2_approve_tx", tx_hash)
```

تحتاج إلى إرسال هذه المعاملة مرة واحدة فقط، وبعد ذلك تستخدم جميع مدفوعات X402 EVM هذا التفويض. لا تحتاج Solana إلى ذلك.

## رابعًا، التحقق من التشغيل الفعلي

هدف الاختبار: **لا يمرر TS SDK رمزًا مميزًا، ويحقن معالج X402، ويمكنه الإنشاء وإطلاق الطلبات بشكل طبيعي** (تحقق خفيف لا يستهلك USDC حقيقيًا على السلسلة).

```ts
// /tmp/sdk-tests/ts/x402-wire-test.ts
import { AceDataCloud } from '@acedatacloud/sdk';
import { createX402PaymentHandler } from '@acedatacloud/x402-client';

const handler = createX402PaymentHandler({
  network: 'base',
  evmProvider: { request: async () => '0x0' } as any,   // provider نائب
  evmAddress: '0x0000000000000000000000000000000000000000',
  preferScheme: 'upto'
});

console.log('handler_type', typeof handler);   // function

const client = new AceDataCloud({
  paymentHandler: handler
});

console.log('client_ctor_ok', client.constructor.name);   // AceDataCloud
```

المخرجات:

```text
handler_type function
client_ctor_ok AceDataCloud
```

توضح النتائج:

- لم يتم تمرير `apiToken`، ولا يُظهر إنشاء SDK **أي خطأ**، مما يثبت أن وضع X402 هو بالفعل بديل قانوني للرمز المميز.
- تُرجع `createX402PaymentHandler` دالة (خطافًا)، ولا يستدعيها SDK إلا عند تلقي 402.
- لم يتم تضمين اختبار شامل من طرف إلى طرف لنجاح الدفع الفعلي على السلسلة في هذا الدليل، لأنه يتضمن خصم USDC حقيقيًا؛ يمكنك الرجوع إلى مثال e2e في [دليل تكامل X402](https://platform.acedata.cloud/documents/x402-integration).

> أجرت جهة Python في `create_x402_payment_handler` التحقق نفسه أيضًا —— قيمة إرجاع الدالة هي callable، ولا يُظهر إنشاء `AceDataCloud(...)` أي خطأ عند حقن `payment_handler=...`. الدلالات متوافقة على الجانبين.

## خامسًا، المقارنة مع «وضع Bearer token»

| البعد              | API Token                                                         | X402                                            |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------- |
| سيناريوهات الاستخدام | الخلفية الخاصة بك، المشاريع طويلة الأجل                                      | مطورو الطرف الثالث، الدفع حسب المرة وحسب الحاجة، استدعاءات Agentic            |
| التسجيل              | يتطلب التقديم من [لوحة التحكم](https://platform.acedata.cloud/console/applications) | لا يتطلب ذلك؛ يكفي وجود محفظة على السلسلة                         |
| دقة الفوترة            | شحن مسبق، وفق جدول token                                           | على السلسلة في الوقت الفعلي لكل استدعاء                         |
| الرصيد              | يمكن عرضه في لوحة التحكم                                                           | تحقق من USDC في المحفظة على السلسلة                              |
| تكلفة المرة الأولى            | يمنح التسجيل بالبريد الإلكتروني رصيدًا مجانيًا                                                        | يتطلب ربط USDC إلى Base، وPermit2 approve لأول مرة              |
| مناسب لعمليات chat       | ✅                                                                 | ✅ (يجب استخدام `preferScheme=upto`)                       |
| مناسب للدفع لمرة واحدة / الدفع نيابةً عن حسابات متعددة | ❌                                                                 | ✅                                               |
| تعديلات الكود            | `apiToken: '...'`                                                 | `paymentHandler: createX402PaymentHandler(...)` |
يمكن أن يتعايش النمطان — في العملية نفسها، يكفي إعداد طرق مصادقة مختلفة لمثيلات `client` مختلفة.

## سادسًا، الأخطاء الشائعة

1. **يجب أن يكون `preferScheme=upto` لفئة chat**: استخدام `exact` سيجعل facilitator يخصم USDC وفقًا لـ `maxAmountRequired` (وليس وفقًا للاستخدام الفعلي).
2. **لا تمرّر مفتاحًا خاصًا خامًا إلى `createX402PaymentHandler` في طرف Node**: حزمة TS لا تقبل `{ privateKey }`، ويجب تغليفه ضمن provider متوافق مع EIP-1193 (يوصى بـ viem `WalletClient`).
3. **الاستدعاء الأول يتضمن توقيعين**: الأول يوقّع Permit2 approve (على السلسلة، ويتطلب gas)، والثاني يوقّع X402 envelope (ليس على السلسلة). الاستدعاءات اللاحقة لا يبقى فيها سوى الثاني.
4. **لا يوجد مفهوم Permit2 في Solana**: يتم توقيع تفويض نقل SPL token مباشرةً، ولا حاجة إلى approve؛ لكن حاليًا تدعم سلسلة Solana فقط `exact`.
5. **ميّز بين أخطاء الأعمال وأخطاء الدفع**: 402 → فشل handler ويرمي `X402SignError` (يختلف النوع المحدد حسب السلسلة)؛ أما أخطاء واجهة الأعمال بعد إعادة الإرسال (401 / 422 / 5xx) فتظل مصنفة كاستثناءات SDK عادية.
6. **الطريقة الأكثر استقرارًا لتكييف `viem`**: سيؤدي `evmProvider: walletClient as any` إلى فقدان التحقق من الأنواع لكنه يوفر أفضل توافق؛ وإذا أردت الاحتفاظ بالأنواع، فاستخدم `.transport.request` من viem لتغليف كائن `{ request }` منفصل وتمريره.
