بالإضافة إلى الدفع مباشرةً حسب طلبات API، تدعم Ace Data Cloud أيضًا دفع طلبات وحدة تحكم X402. البروتوكول الأساسي لدفع الطلبات واستدعاءات API هو نفسه: يعيد الطلب الأول 402، ويوقّع العميل `PAYMENT-SIGNATURE`، ثم يعيد المحاولة باستخدام الطلب نفسه.

يكمن الاختلاف في أن دفع الطلبات يتبع Platform API ويتطلب رمز حساب؛ بينما يمكن استدعاء AI API الخاص بـ `x402.acedata.cloud` مباشرةً باستخدام X402 فقط، دون الحاجة إلى API Token.

## تجهيز الطلب

ادخل إلى [وحدة تحكم Ace Data Cloud](https://platform.acedata.cloud/console/orders)، واختر الطلب الذي تحتاج إلى دفعه، وسجّل معرّف الطلب.

إذا لم يكن لديك طلب بعد، يمكنك إنشاء طلب بانتظار الدفع في صفحة الباقات. يعتمد سعر الطلب على ما هو معروض في الصفحة، ويُعدّ `amount` في استجابة X402 402 هو الأساس النهائي للتوقيع.

## إنشاء رمز الحساب

يتطلب طلب دفع الطلب رمز حساب. افتح [صفحة Platform Token](https://platform.acedata.cloud/console/platform-tokens)، وأنشئ token بتنسيق `platform-v1-...`.

تستخدم الطلبات اللاحقة:

```http
Authorization: Bearer {platform_token}
```

يختلف رمز الحساب عن API Token العادي. يُستخدم API Token العادي لاستهلاك حصة API؛ بينما يُستخدم رمز الحساب لتمثيل حسابك في تشغيل موارد المنصة، مثل دفع الطلبات.

## تشغيل 402

أرسل أولًا طلبًا واحدًا دون `PAYMENT-SIGNATURE`:

```http
POST https://platform.acedata.cloud/api/v1/orders/{order_id}/pay/
Authorization: Bearer {platform_token}
Content-Type: application/json

{
  "pay_way": "X402"
}
```

تكون حالة الإرجاع 402، وتتضمن الاستجابة `accepts`:

```json
{
  "x402Version": 2,
  "error": "Payment required for this order.",
  "resource": {
    "url": "http://platform.acedata.cloud/api/v1/orders/.../pay/",
    "description": "Ace Data Cloud Credits x 10.0",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "1200000",
      "payTo": "0x...",
      "maxTimeoutSeconds": 120,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "chainId": 8453,
        "verifyingContract": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
        "decimals": 6
      }
    }
  ],
  "paywall": {
    "app_name": "Ace Data Cloud",
    "app_logo": "https://cdn.acedata.cloud/favicon.ico"
  }
}
```

يستخدم دفع الطلبات x402 v2 الرسمي: تكون `x402Version` هي `2`، وتستخدم `network` معرّف CAIP-2، وحقل المبلغ هو `amount`.

نتيجة تشغيل البرنامج لإنشاء طلب 10 Credits وتشغيل 402:

> سجلات المعاملات التالية هي عينات تاريخية مختبرة فعليًا ضمن السياسة القديمة، وقد تم الاحتفاظ بالمبالغ وتجزئات المعاملات كما هي. لم تعد طلبات X402 الجديدة تتضمن خصومات لطريقة الدفع؛ يُرجى اعتماد `amount` في استجابة 402 الحالية كأساس للتوقيع والدفع.

```text
created order 78481793-304e-47f7-bc0c-8231aec9cc1e
created state Pending
created price 1.26

http_status=402
x402Version 2
error Payment required for this order.
accepts [
  ('eip155:8453', 'exact', '1200000', '0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7'),
  ('solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp', 'exact', '1200000', '5iVXFrYaYWX2GUTbkQj8mDBoBhAX8bneYigS2LJTia43')
]
description Ace Data Cloud Credits x 10.0
```

توضيح النتائج:

- بعد إنشاء الطلب بنجاح، تكون حالته `Pending`، ولا يوجد دفع على السلسلة في هذه المرحلة.
- لم يحمل طلب `pay/` الأول `PAYMENT-SIGNATURE`، ولذلك أعاد HTTP 402.
- يعرض `accepts` كلاً من Base `exact` وSolana `exact`، ويختار هذا الدليل Base لاحقًا.
- كان السعر عند إنشاء الطلب هو `1.26`، وخلال سياسة خصم دفع X402 القديمة، كان مبلغ التوقيع والتسوية الفعلي هو `1.2` USDC، ويقابله `1200000` atomic USDC.

لاحظ أن `resource` هنا هو حقل يُرجعه الخادم ويشارك في التوقيع، ويجب على العميل ألا يعيد كتابة البروتوكول أو المسار أو معرّف الطلب فيه بنفسه.

## التوقيع وإعادة المحاولة

يمكن لدفع الطلبات إعادة استخدام `@acedatacloud/x402-client` أو دالة التوقيع منخفضة المستوى في `acedatacloud-x402`. فيما يلي مثال TypeScript:

```ts
import { Wallet } from 'ethers';
import { signEVMPayment } from '@acedatacloud/x402-client';

const platformToken = process.env.ACE_PLATFORM_TOKEN!;
const orderId = process.env.ACE_ORDER_ID!;
const wallet = new Wallet(process.env.EVM_PRIVATE_KEY!);

const url = `https://platform.acedata.cloud/api/v1/orders/${orderId}/pay/`;
const body = { pay_way: 'X402' };

const first = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify(body)
});

if (first.status !== 402) {
  throw new Error(`expected 402, got ${first.status}`);
}

const paymentRequired = await first.json();
const requirement = paymentRequired.accepts.find(
  (item: any) => item.network === 'eip155:8453' && item.scheme === 'exact'
);

const evmProvider = {
  async request({ method, params }: { method: string; params?: unknown[] }) {
    if (method !== 'eth_signTypedData_v4') throw new Error(`unsupported method: ${method}`);
    const [, typedDataJson] = params as [string, string];
    const typedData = JSON.parse(typedDataJson);
    return wallet.signTypedData(typedData.domain, typedData.types, typedData.message);
  }
};

const envelope = await signEVMPayment(requirement, evmProvider, wallet.address);
const xPayment = Buffer.from(JSON.stringify(envelope), 'utf8').toString('base64');

const paid = await fetch(url, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${platformToken}`,
    'Content-Type': 'application/json',
    'PAYMENT-SIGNATURE': xPayment
  },
  body: JSON.stringify(body)
});

if (!paid.ok) {
  throw new Error(`payment failed: ${paid.status} ${await paid.text()}`);
}

console.log(await paid.json());
```

نتيجة تشغيل البرنامج بعد توقيع الطلب نفسه باستخدام Base `exact` وإعادة المحاولة:

```text
status 200
payer 0x5d4f08D5c2bb60703284bc06671Eb680fA41B105
has_x_payment_response True
settle_header {'success': True, 'network': 'base', 'transaction': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151', 'errorReason': None}
order {'id': '78481793-304e-47f7-bc0c-8231aec9cc1e', 'state': 'Finished', 'pay_way': 'X402', 'price': 1.2, 'pay_id': '0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151'}
```

نتيجة التأكيد على السلسلة:
```text
tx 0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
الحالة 1
الكتلة 46726704
المستكشف https://basescan.org/tx/0xfec08cc00a159ea1ec692b32faa9bf3d17595a986301169e689d94f58bc44151
التحويل {"from":"0x5d4f08D5c2bb60703284bc06671Eb680fA41B105","to":"0x4F0E2D3477a1B94CF33d16E442CEe4733dadCeE7","value":"1200000"}
```

شرح النتيجة:

- يشير `status 200` إلى أن واجهة دفع طلبات المنصة قبلت `PAYMENT-SIGNATURE` هذه.
- يشير `has_x_payment_response True` إلى أن ترويسة الاستجابة تتضمن إيصال `PAYMENT-RESPONSE` مرمّزًا بـ Base64.
- يشير `settle_header.success=True` و`network=base` إلى أن الـ Facilitator قد أكمل تسوية Base.
- حالة الطلب النهائية هي `Finished`، و`pay_way` هي `X402`، ويُكتب تجزئة معاملة على السلسلة في `pay_id`.
- يُظهر حدث `Transfer` على BaseScan أن عنوان الدفع حوّل `1200000` atomic USDC إلى عنوان استلام المنصة، أي `1.2` USDC.

## الاستجابة الناجحة والإيصال

بعد نجاح دفع الطلب، يكون جسم الاستجابة هو معلومات الطلب. كما تحمل المنصة في ترويسة الاستجابة `PAYMENT-RESPONSE` استجابة تسوية مرمّزة بـ Base64، وتشمل الحقول الشائعة بعد فك الترميز ما يلي:

| الحقل            | الوصف                           |
| ------------- | ---------------------------- |
| `success`     | ما إذا كانت تسوية الـ Facilitator ناجحة. |
| `transaction` | تجزئة معاملة التسوية على السلسلة.                    |
| `network`     | شبكة الدفع.                        |
| `payer`       | عنوان محفظة الدافع.                      |
| `amount`      | مبلغ التسوية الفعلي، باستخدام atomic units.      |

إذا كنت بحاجة إلى المطابقة، يُوصى بحفظ معرّف الطلب وعنوان محفظة الدافع و`transaction` وحالة الطلب النهائية في الوقت نفسه.

## ملاحظات

- يتطلب دفع الطلب رمز حساب المنصة، ولا يمكن إتمامه بالاعتماد على توقيع محفظة X402 فقط.
- يستخدم `amount` وحدات USDC atomic units، ويمثل `1200000` مقدار `1.2` USDC.
- لا تُنشئ عنوان الاستلام أو عنوان الأصل بنفسك، واعتمد على `accepts` في استجابة 402.
- إذا تم إرسال `PAYMENT-SIGNATURE` نفسها بشكل متكرر، فسيجري الـ Facilitator حماية من إعادة التشغيل وفقًا لـ nonce.

## استجابة فشل الدفع

إن أول HTTP 402 لا يحمل `PAYMENT-SIGNATURE` هو تحدٍ عادي للدفع، ولا يعني فشل الدفع. يظل فشل التحقق أو التسوية بعد التوقيع محتفظًا بـ `error` النصي القياسي كبديل متوافق، ويُرجع بنية خطأ مستقرة في `extensions.acedatacloud.paymentError`:

```json
{
  "code": "insufficient_token_balance",
  "params": { "network": "eip155:8453" },
  "stage": "verify",
  "retryable": true,
  "charged": false
}
```

ينبغي للعميل إعطاء الأولوية للتوطين وفقًا لـ `code`، وإرجاع code غير المعروف إلى فشل الدفع العام. `charged` حقل ثلاثي الحالات: لا يُرجع `false` إلا عند الرفض الصريح قبل التسوية؛ ويعني غياب الحقل أن حالة الخصم غير معروفة، ولا يمكن تفسيره على أنه «لم يتم الخصم». بعد دخول الطلب الحالي إلى `Failed`، لا يمكن إعادة محاولة الطلب الأصلي، ويُرجى إنشاء طلب جديد بعد تصحيح مشكلة المحفظة.

يحتفظ `metadata.x402.last_error` و`metadata.x402.errors` في قائمة الطلبات وتفاصيلها بالمجموعة نفسها من `code` و`stage` و`retryable` و`charged` و`params`؛ ويُحفظ نص الوصف العام في `reason`، ويُحفظ وقت الحدوث في `timestamp`. على سبيل المثال، يشير `insufficient_token_balance` إلى عدم كفاية رصيد USDC على الشبكة المحددة، ويشير `invalid_signature` إلى أن توقيع الدفع غير صالح؛ وإعادة قراءة الطلب لن تغيّرها إلى `payment_failed` العامة.

لا تسجّل أو ترسل `PAYMENT-SIGNATURE` بالكامل، أو توقيع المحفظة، أو payload التفويض، أو تشخيصات الـ Facilitator الخام، أو استجابة RPC. يحتاج فريق دعم العملاء فقط إلى معرّف الطلب و`code` الخطأ العامة للتحقق.
